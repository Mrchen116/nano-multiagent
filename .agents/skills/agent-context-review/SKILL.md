# Agent Context Review

站在当轮 LLM 的位置判断：它应知道什么、能实际看到什么，是否足以完成预期下一步。先按 [通用规范](../../../docs/development/agent-context-engineering.md) 界定受影响消费链及必要交互，不逐项制造全量 checklist。caller 提供目标、范围/版本、当前阶段和证据；作者自检与独立审查明确区分，不因加载本 skill 自动取得独立身份。

## 设计模式

沿 Consumer 的任务检查来源/owner、选择/组装、交付时点、保留/失效与恢复。用必要的模型可见样例判断参数是否可得、状态/失败是否可理解、是否能找到正确入口，核对与现有工具、Skills、Memory 及权限边界的交互。

说明实现后需观察哪些输入和行动，将其交回当前设计与执行安排；尚无实现时只给方案判断，不要求运行不存在的系统或伪造运行结论。

## 实施模式

1. 先写清场景与预期行动，然后按 [实际 Context 入口](../../../docs/development/llm-integration.md#观察实际-agent-context) 读取真实运行中交付的相关输入：首次请求、受影响的工具结果后的下一请求，以及动态加载、提醒或恢复点。范围由问题决定，不只搜索关键词或看摘要。
2. 从当轮 Agent 可获得的信息判断来源、状态、参数、入口及下一步是否清楚。实际加载后的 Skill/Memory 正文也是输入；初始目录正确不能证明动态内容正确。
3. 对照实际调用、响应和产品结果，再回源码解释装配与定位原因。一次任务成功不能替代输入判断，源码正确也不能替代运行观察。

复用版本/locator 明确且仍有效的证据，缺关键输入才补捕获或有界任务。确定性装配问题可用受控 provider 的实际出站输入验证；涉及模型理解和选择本身时需代表性真实模型行为。区分静态文档、装配预览、受控请求、真实 provider 输入和实际行为；没有必要运行证据时只给静态判断或未验证，不把读源码改称实施验收通过。仓库 skill 的实际消费可通过独立 Agent 执行及其读取/输出记录观察，不能用文本校验代替。

## 返回与结束

返回模式、实际范围/版本、预期与观察、证据定位及限制。每个问题说明 Surface、失败条件/机制、用户或任务影响、建议和证据状态；CONFIRMED 是直接证据，PLAUSIBLE 是机制有据但条件未证实，REFUTED 有反证且不列存活缺陷。缺必要证据与已确认缺陷分开。

沿用 caller 的结果位置，不另建 Gate、Agent 或报告，不改受审对象、不扩大运行授权。相关问题已有充分判断后结束，只按实际变化补验；原件按 [Evidence](../../../docs/development/evidence.md) 保留本机，返回必要脱敏结论。
