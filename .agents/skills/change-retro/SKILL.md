# Change Retro

解释用户期望与实际结果的落差为何产生、为何未被及时纠正，并提出有证据支持的最小改进。

## 调查主线

- 先定位相关 unit、版本和会话，结合原始诉求、关键反馈及前后文重建问题：用户期望什么，实际发生什么，反馈针对局部结果、整体方案还是判断标准。用户举例不自动限定问题范围，重复的整体否定不能拆成互不相关的修补项。
- 在归因前梳理关键变化与纠正过程，再追查产生这些结果的决策、动作和当时依据。跨反馈查找共同机制，同时保留相互独立的问题；不强求单一根因，也不预设责任在某个角色或 Skill。
- 用原始证据检验解释：是否覆盖主要落差、问题分布及已发生的反复；哪些事实支持，哪些构成反证，其他合理解释能否排除。单个案例有证据不足以代表整体，无法解释的部分保留为未决，不用增加推断补齐故事。
- 最后区分需求/设计错误、实现偏离、验证不足和编排问题，以及规则缺口与已有规则未执行。建议针对已证实的机制，说明如何改变决策或验证；只有需要改 Skill 时才归并到对应角色，不默认以增加条款或人工门禁解决问题。

## 证据约束

- 原始动作和结果优先；DONE、旧 retro、旁人转述与摘要只是线索。区分用户原话、直接观察与分析推断，保留反证和无法确认项。
- 使用事发时适用的流程、需求和设计判断，不用当前 Skill 倒推历史违规。只读取线索涉及的角色规则，不加载全部 change Skills。
- 耗时/轮次/往返等数字说明采样与分母，区分 active 时间、等待和离线。异常计数是调查线索，不直接等于空转或因果证明。
- 调查中的进展更新区分事实与待验证解释；用户纠正后重新核对问题范围与原始证据，明确撤回错误归纳，不能只把新例子追加到旧结论。

## 产物与完成

按需用 [mine_jsonl.py](scripts/mine_jsonl.py) 提取线索，再核原文；工具与取证边界见 [取证参考](references/investigation.md)。

按 [output-template](references/output-template.md) 写新的 `retro-pipeline-rootcause.md`，不覆盖旧复盘。先呈现核心落差及原因，再给可追溯的时间线、证据与解释边界；结构服从问题，不机械为每条反馈或每个 Skill 建一节。

完成前核对主要反馈是否都被解释或明确列为未决、建议是否针对原因且遵循用户约束。证据足以回答核心困惑后结束，不以找到若干局部问题或填满模板为完成标准。按授权提交，未经要求不直接修改被复盘 Skills。
