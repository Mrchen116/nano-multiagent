# Frontend Experience Review

判断界面能否自明、视觉是否协调并延续产品风格，以及受影响流程是否便于辨认、阅读、比较、决定与操作。使用 caller 给定的用户目标、范围、平台、设计/产品版本及证据；作者自检与独立审查使用同一方法，但分别标明身份。

## 方法与证据

- 按 [共同判断标准](references/prototype-and-runbook.md#共同判断标准) 先独立阅读实际画面和操作，再核作者的功能清单、原型及解释。用接近日常的内容，说明具体视觉/操作事实如何帮助或妨碍目标；控件存在、分组齐全、保存成功不能证明整体体验成立。
- **Let the UI speak for itself。** 先看标题、布局、控件名称和状态能否直接表达用途；逐处判断说明文字是否增加决策所需的信息，指出重复标签、解释显而易见操作及暴露内部实现的文案。需要长解释才能用的地方，先检查命名和交互设计，不默认给每个输入框或按钮配说明；必要限制和后果仍须清楚。
- **把新增操作放回整页看。** 与改动前及相邻界面对照，检查按钮的位置、数量、主次、尺寸、对齐、间距和视觉样式是否协调，是否打断阅读或抢占主体。复用组件不等于整体和谐，能点击不等于设计成立；没有实际画面对照时，不宣称视觉一致性通过。
- 设计模式先按 [原型边界](references/prototype-and-runbook.md#原型的判断范围) 判断是否需要原型，再观察适用的原型或现有产品，判断内容关系和交互决定是否足以指导实施；不因使用本能力就要求新建原型。未实现部分只给设计判断，不要求提前起真实后端。
- 实施模式观察受审版本的真实客户端及连续操作，验证实际结果和方案本身是否合理。按 [平台与深度](references/prototype-and-runbook.md#验证平台与深度) 选择受影响平台，不默认双端矩阵；未实测的界面不写体验通过。
- 优先复用可信构建、现场与未失效画面，必要时补决定性操作。截图、viewport、状态和路径可复查；DOM、CSS 与测试只补充证据。只看静止状态不能证明交互完成。
- 涉及具体取舍再读 [纠正案例](references/ui-decision-gotchas.md) 的相关部分，不逐项套用。整体体验反馈检查共同成因，不能拆成一串“仍可点击”的 minor，也不扩大为全产品重设计。

## 判断与完成

返回实际观察、对用户的影响、证据定位与限制，按本次问题分别判 pass/fail/inconclusive。界面改动需明确自明性与视觉协调的判断及画面依据，不能用操作成功代替。缺必要画面/操作是 inconclusive；方案本身妨碍目标也需报告，符合原型不能豁免。纯风格偏好不阻断，但违反用户明确的设计要求、既有视觉语言或操作层级不属于纯偏好，须按实际影响处理；整体阅读/操作障碍应明确为阻塞。

只回答所选问题，不修改受审设计/实现、不自行派发或推送报告。与产品旅程共用证据时各自结论仍需成立，同一缺陷引用一次。相关问题及证据已充分就结束，修订后只补失效判断。

若本次启动或创建了验证资源，结束时按 [测试资源回收](../../../docs/development/worktree-runtime.md#测试资源回收) 处理，并返回回收结果或明确的保留交接。
