# Frontend Experience Review

判断受影响流程是否便于辨认、阅读、比较、决定与操作。使用 caller 给定的用户目标、范围、平台、设计/产品版本及证据；作者自检与独立审查使用同一方法，但分别标明身份。

## 方法与证据

- 按 [共同判断标准](references/prototype-and-runbook.md#共同判断标准) 先独立阅读实际画面和操作，再核作者的功能清单、原型及解释。用接近日常的内容，说明具体视觉/操作事实如何帮助或妨碍目标；控件存在、分组齐全、保存成功不能证明整体体验成立。
- 设计模式观察实际渲染原型及现有产品，判断内容关系和交互决定是否足以指导实施；原型范围与契约见 [原型方法](references/prototype-and-runbook.md#原型的判断范围)。未实现部分只给设计判断，不要求提前起真实后端。
- 实施模式观察受审版本的真实客户端及连续操作，验证实际结果和方案本身是否合理。按 [平台与深度](references/prototype-and-runbook.md#验证平台与深度) 选择受影响平台，不默认双端矩阵；未实测的界面不写体验通过。
- 优先复用可信构建、现场与未失效画面，必要时补决定性操作。截图、viewport、状态和路径可复查；DOM、CSS 与测试只补充证据。只看静止状态不能证明交互完成。
- 涉及具体取舍再读 [纠正案例](references/ui-decision-gotchas.md) 的相关部分，不逐项套用。整体体验反馈检查共同成因，不能拆成一串“仍可点击”的 minor，也不扩大为全产品重设计。

## 判断与完成

返回实际观察、对用户的影响、证据定位与限制，按本次问题分别判 pass/fail/inconclusive。缺必要画面/操作是 inconclusive；方案本身妨碍目标也需报告，符合原型不能豁免。纯风格偏好不阻断，整体阅读/操作障碍应明确为阻塞。

只回答所选问题，不修改受审设计/实现、不自行派发或推送报告。与产品旅程共用证据时各自结论仍需成立，同一缺陷引用一次。相关问题及证据已充分就结束，修订后只补失效判断。
