# 前端体验设计、原型与验收

## 共同判断标准

以受影响的使用过程为设计和验收单位：用户带着什么内容进入，要读懂什么、作出什么判断、完成什么动作。先决定信息如何组织、主次如何呈现、操作如何衔接，再映射到组件与接口；不要从已有字段或 API 返回形状直接推导页面。

设计时查看当前产品的真实入口和相邻界面，把布局、排版、密度、身份线索及交互方式作为可见的对照。说明本次沿用或改变的关系及原因；组件同名、颜色相同或使用原生控件本身不构成对照结论。

走查时先不借助测试数据含义、实现说明或旧通过结论，从实际画面辨认当前内容、阅读顺序、主要动作及其后果，再完成相关操作。使用接近日常任务的内容，实际触发承担关键选择或反馈的状态；静止画面只证明该状态。需要靠记住屏外内容、猜测字段含义或借测试标记才能完成判断时，记录具体位置和用户代价。

体验裁决写出“画面或操作中的事实 → 如何帮助或妨碍用户完成目标”，并链接对应证据。例如，比较任务要证明两侧内容的对应关系与提交含义可辨认；有两个分组、能滚到内容或保存成功只能证明各自的事实。功能、视觉与交互可共用证据，但通过结论各自需要成立；不要用三个同义段落重复功能成功。缺必要观察记未验证，已看到的问题按实际理解、阅读、操作或产品一致性影响处理，纯风格偏好不阻断。

先判断方案是否成立，再判断实现是否符合方案。设计有问题可直接提出修订，不必先把它实现或修复数轮。整体体验反馈按受影响流程检查共同成因，完成相关验证即停止，不扩为全产品重设计或另设 UI 审批。

## 验证平台与深度

按本次要证明的行为、平台特有风险和已有证据选择充分且成本最低的验证，不按改动文件的扩展名、客户端数量或角色数量扩大范围。共享业务链路优先在 Web 验证，不默认要求 Web 与 iOS 双端真实操作。

| 本次改动 | 默认验证 |
| --- | --- |
| 后端、工具配置、共享业务语义 | 窄测试与真实接口；需要用户旅程时优先 Web |
| Web 页面或交互 | Web 真实入口，覆盖受影响状态与必要宽度 |
| iOS 简单字段、默认值、设置项增删、已有控件绑定，或不影响排版的文案 | 编译与相关契约/回归测试；共享语义用 Web 验证，通常不启动模拟器 |
| iOS 布局、导航、手势、键盘、无障碍、权限或系统集成 | 在 iOS 真实客户端实测受影响流程 |
| 跨端交接、一致性本身是验收目标，或用户明确要求双端实测 | 两端实测对应结果；不将无关场景也复制到两端 |

design/runbook 和验收派发注明要证明的结果、所选平台、方法及可复用证据。must-match 只为依赖平台呈现的结果指定该端实测，不能把每个共享场景机械展开为双端。出现平台差异、相关回归失败或证据缺口时再扩大；修改 Swift 文件本身不是启动 iOS 实测的理由。未实测的平台界面不写体验 pass，也不因其不在本轮实测范围而自动阻塞。

实施者完成最窄自检，产品 reviewer 独立观察决定性用户结果；共享可信的构建、测试、环境与未失效证据，不要求双方各跑一遍完整平台矩阵。后续修订只复验失效范围。

## 原型的判断范围

仅前端 UI/交互变化需要原型。原型帮助用户判断本次产品决定，范围与改动相称；完整体验指受影响的使用过程，不要求每次重建整个产品。

作者在 design 中按受影响流程说明入口、内容关系、阅读与操作顺序及关键取舍，再选择足以评审这些决定的呈现方式。多端可以共享任务语义；布局或交互不同的端须呈现自己的关键流程，不能把另一端的缩窄截图当作该端设计。

| 需要判断的改动 | 合适的呈现方式 | 必须保留的上下文 |
| --- | --- | --- |
| 局部文案、样式或反馈 | 局部前后对照 | 实际容器宽度与相邻元素，例如输入框、错误提示和提交按钮；不孤立展示控件 |
| 一个组件的多种状态 | 同一组件的状态展示 | 触发动作、正常/处理中/失败及恢复，按本次影响选择 |
| 与页面布局或操作强耦合的增量 | 现有页面背景 + 可交互增量 | 真实入口、位置、空间占用、关闭/返回以及必要的周边状态 |
| 跨页面或跨设备的流程 | 可连续操作的旅程 | 各步入口、操作者、交接点、结果和恢复；不实现无关页面 |

局部改动不强制整页或端到端旅程；强耦合、多步改动不能用孤立卡片代替。`prototype.html` 可组织局部对照、状态展示和连续旅程，不要求所有页面都能点击。优先复用既有组件或样式；静态页面背景承载局部交互也可以，但必须注明背景用途，不把固定背景冒充响应式实现。

## 继承现有产品，明确增量

设计前查看受影响入口的实际界面或可核实截图，并走查相关操作，核对组件、路由和样式来源。在 design 中链接基线证据，说明哪些体验沿用、改善以及原因，不能只列组件名或相同配色。缺少画面或交互证据时明确缺口，不声称已完成对应对照。

复用现有设计系统与适用的平台约定，布局和导航服务本次目标；关键改变写入设计决定。不要为了串演示自行增加产品功能或入口，设计说明和模拟控制留在产品区域之外。

原型外层应简要标明“现有界面背景 / 本次新增或修改 / 仅演示”，不能只在 design 表格里区分。默认呈现正常使用状态；异常状态与模拟身份、本机动作等控制放在独立演示区。连续旅程通过产品操作走通，不要求用户借演示菜单拼接步骤。规则解释留在设计说明，产品区域只保留完成操作和作出决定所需的信息。

## 契约与交付前自检

`prototype.html` 可含演示 JS，不接真实后端、不代替产品实现。design 的“前端原型”段链接它，并用表说明：区域/状态、`must-match | may-adapt | out-of-scope`、真实产品入口、viewport/状态、milestone 退出标准。

- must-match 写出关键体验结果及支撑它的信息层级、视觉关系和交互约束，不能只写“有页面/按钮/字段”。
- may-adapt 标记已有体验方案中的可变形式，并指向该端的呈现依据；尚未决定的信息组织或交互不能以“平台适配”代填。out-of-scope 写清真实产品会呈现什么。
- 每个 must-match 都投影到 `[reviewer]` 用户结果与 `[worker]` 可复查的原型对照证据。

给用户作为可评审成果前，实际渲染并按共同判断标准走查，覆盖本次决定涉及的状态、适用 viewport 及容易挤压的宽度。原型依赖平台呈现的关键交互须在对应环境观察；模拟画面只证明设计意图，未观察部分保留为缺口。

留下足以复查的代表性截图及简短走查结果，证据放在 unit 内，不需要每种状态机械截图。脚本、DOM 和 CSS 检查只能补充，不能代替看实际画面。渲染工具不可用时可保留并展示明确标注的草稿，但必须写“视觉未验证”，不能宣称原型就绪或把必要视觉检查推迟到实施验收。先汇总问题、修正后按影响一次复查，不以主观审美偏好无限循环。

独立设计审查判断方案；实施者按上述平台与深度兑现并自检；产品 reviewer 在所选真实入口独立判断实际体验。接手既有设计时，先核对它是否足以指导本次流程；缺口补在原设计决定中，不把旧功能清单当作完整体验契约。原型通过不代表真实产品通过。

## 实施验收前置

Runbook for Reviewer 列出本 unit 相关服务的停止、启动/构建和健康检查命令，以及所选平台的入口驱动方式。不改客户端面时可用客户端实际调用的同一接口；客户端变化按上述平台与深度选择验证，只有需要证明的视觉、交互或平台能力才要求在对应真实客户端操作。

从必验旅程确定账号、凭据、测试租户、外部对象、权限或硬件的来源和可用性；没有则写“无”。未落实的必验资源阻塞 Gate 2；只有用户明确调整验收范围或授权替代验证后才能改变标准。运行隔离遵循 [worktree-runtime](../../../../docs/development/worktree-runtime.md)。
