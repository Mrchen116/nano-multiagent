# 复盘报告结构

在 `<unit_path>/retro-pipeline-rootcause.md` 写新的报告，不覆盖历史。按问题规模合并或展开以下结构；跨 unit 复盘明确各自版本，不要求完整列出无关阶段、会话或角色。

```markdown
# <范围> 根因复盘

## 核心问题与结论

用户原本希望得到什么、实际落差是什么、关键反馈针对什么层次。
给出证据支持的原因与解释边界；局部例子如何体现整体问题，独立问题如何区分。
不要用几条容易举证的缺陷替代用户的核心困惑。

## 范围、版本与关键经过

涉及的 unit、版本、会话和证据索引；区分事发规则与当前规则。
按时间记录改变判断的诉求、决策、结果、反馈和修订，保留必要原话与上下文。
时间线用于解释问题如何产生、延续或被纠正，不复述全部操作。

## 原因与证据

按有证据的原因组织，可覆盖多条反馈；无需一条反馈对应一个根因。
每项说明：
- 覆盖哪些现象与反馈，证据发生在哪个版本和时刻。
- 哪些决策或动作导致结果，哪些环节未能纠正；区分观察与推断。
- 支持证据、反证与其他合理解释，尚不能解释的部分。
- 原因属于方案、实现、验证、编排还是规则执行；不强行归到某个 Skill。

## 解释覆盖与未决项

核对主要落差与关键反馈是否得到解释；存在反复时说明为何修订后仍出现。
未覆盖部分写明证据缺口及对结论的影响，不强造统一根因。
调查中被证据或用户纠正推翻的结论，明确撤回并说明新依据。

## 改进建议

按实际收益与代价排序，关联原因，说明改变什么决策或验证、如何判断有效。
需要改 Skill 时再按角色归并；不为填表覆盖所有 Skill，不自动增加审批或检查清单。
```

报告质量取决于是否解释了用户的核心问题、因果证据是否充分、建议是否作用于原因。证据数量、篇幅和逐项齐全不等于解释完整；不要求固定数量的发现或改进。
