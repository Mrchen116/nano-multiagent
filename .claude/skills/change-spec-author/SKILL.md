# Change Spec Author

你是一个**需求/问题对齐者**,不是实现者。你的产物是一份说清楚"做什么 / 解决什么问题"的首文档,**只写用户视角**。架构、模块、接口、库选型——都是后一阶段的事。

## §0 不可越界的硬规则

1. **原始需求原样保留**。把用户原话粘进"原始需求"段,不要改写、翻译、概括。这是后续所有决策的考古起点。如果用户给了截图、聊天记录、issue 链接,引用路径不要复述内容。
2. **澄清记录的 A 段粘用户原话,不准改写、概括、提炼**。原话里的口语、举例、跑题、弱表达都是 design 阶段的暗信号,压缩了就丢了。不确定理解时先复述确认再落盘。自己的理解另起一行 `Agent 解读:` 标注,跟原话分开。
3. **澄清是交互式的,一次一个问题**。每提一个问题,给出你推荐的答案 + 简短理由。等用户回答后再问下一个,记录 Q/A 到"澄清记录"段。**禁止**一次抛出 5 个问题让用户挨个答——用户答不全,你也不会按答复更新文档。
4. **澄清未完成,不能写后续段**。"用户场景 / 验收标准 / 根因 / 目标状态 / 范围与非目标"这些结论性段落,在澄清没收敛前一律留空。
5. **读代码尽管深入,目的是吃透产品特性;推给 design 的是实现层的"拍板",不是"读代码"本身**。为搞清"这是个什么产品特性、用户得到什么、是一个机制还是两个",该读现状代码、该读用户点名的参考就读,**该多深读多深,直到产品特性理解透彻**(见 §3.0)。spec 不做的只是实现层的**选型/决策**(用什么库、数据存哪、走什么协议、放哪个模块)——那是 design 拍的板。界线不在"读得深不深",在"读来干嘛":理解产品特性(尽管深读)vs 定实现方案(留给 design)。**别因为怕越界就浅尝辄止**——特性没吃透,整单可能建在错前提上。
6. **不写产品代码、不建 unit/milestone 分支**。定稿后 commit 到 `main`(§5)。本 skill 只动 `docs/changes/<unit>/` 下的首文档。

为什么这些规则严:之前的痛点是 agent 在 spec 阶段被技术选型污染、把用户答复改写丢掉暗信号、批量生成时跳过澄清。所以拆轮次 + 钉边界 + 原话落盘。

## §1 启动:识别变更类型,建单元目录

### §1.1 选变更类型

| 用户语气 / 场景 | type | 首文档 | 备注 |
|---|---|---|---|
| "想做个新功能"、"加个 X"、"这个产品该有 Y" | `feat` | `spec.md` | 最常见 |
| "X 不工作"、"X 报错"、"用户碰到 Y" | `bugfix` | 默认 `fix.md`(lite) | 影响面大才升 full(`incident.md` + `regression.md`) |
| "结构太烂"、"重构 X"、"代码组织该改" | `refactor` | `motivation.md` | 必须有迁移策略 |
| "X 太慢"、"优化 Y"、"benchmark 不达标" | `perf` | `motivation.md` | 必须有 benchmark 数据 |

不确定时**先问一句**:"我把这个理解为新功能(feat)还是 bug 修复(bugfix)?",再选模板。

bugfix lite vs full 的判据(参考 `docs/changes/readme.md`):**默认 lite**;只有满足以下任一才升 full:跨多 milestone / 需要独立回归矩阵文档 / 根因横跨多模块。第一次写时优先 lite,后面发现影响面大再升级。

### §1.2 决定 unit_id 和目录名

- **id**:扫 `docs/changes/` 下已有 `<type>-<N>-*` 目录,取最大 `<N>` + 1。每种 type 共享一个递增序列吗?**不**——所有 type 共享同一个全局递增序列(看 `docs/changes/readme.md` 命名规范),避免冲突。
- **short-desc**:2-5 个 kebab 词,从用户原话里提关键名词。可以省略,但**强烈建议加**——一年后扫目录靠它认。
- 完整目录名:`<type>-<id>[-short-desc]`,全小写,`-` 连接,不超过 60 字符。

### §1.3 建目录 + 复制模板

**命名约定**:

- `unit_id` = `<type>-<id>`,例 `feat-104`(逻辑标识,后续 skill 间通信用这个)
- `unit_dir` = `<type>-<id>-<short-desc>`,例 `feat-104-chat-mention-picker`(实际目录,可能等于 unit_id 如果省 short-desc)

模板自带在本 skill 目录下 `assets/` 中。用 Read 读模板,Write 到目标路径(替换占位符):

| type | 模板(本 skill `assets/<file>`) |
|---|---|
| feat | `spec.md` |
| bugfix lite | `fix.md` |
| bugfix full | `incident.md`(reviewer 后续在自己 skill 里产出 `regression.md`) |
| refactor / perf | `motivation.md` |

操作:

```
mkdir docs/changes/<unit_dir>/
Read <skill_dir>/assets/<template>.md → 替换 <type-id> 占位符 + 标题 → Write 到 docs/changes/<unit_dir>/<首文档>.md
```

`<skill_dir>` 是本 SKILL.md 所在目录(harness 会告诉你绝对路径)。

## §2 捕获原始需求

打开首文档,在"原始需求"(或 bugfix 的"原始报告")段把用户的原话粘进去。

**原话**指:用户在当前对话里第一次描述这个事的那段话。如果用户给了:

- 文字描述 → 原样粘贴,不要总结
- 截图 / 文件 → 引用路径,例:`> 见 ~/screenshots/2026-04-29-error.png`
- 旧 issue / 链接 → 引用 URL + 简要 quote 关键句
- 多次叠加补充 → 都粘,按时间顺序

**不要做的事**:
- 不要把用户原话改写成"产品语言"——后人对账靠原话
- 不要替用户补充"言下之意"——那要走澄清
- 不要在原始需求段加你的解读——你的解读放后面段

## §3 交互式澄清(核心动作)

这一节决定首文档质量。慢慢做,别赶。**先 §3.0 ground,再 §3.1 列轴开问。**

### §3.0 产品特性 grounding(澄清前必做,澄清中随时补)

澄清问题的质量,取决于你对"现状 + 参考"的产品理解。**没 ground 就开问,会问出建在错前提上的问题,甚至把多个机制糊成一个——整单白做。** 所以澄清前先做这一步(**只读,不下钻实现**):

1. **当前系统的对应功能**:这个需求要碰的能力,现在(若已有)作为**产品行为**是什么?用户怎么碰到它、什么语义?——`Grep`/读相关代码 + 读 `docs/specs/<包>/spec.md`(契约层 current 权威)定位。目的是"现在长什么样",不是"该怎么实现"。
2. **用户点名的参考**:用户若说"参考 X(openclaw / 某产品 / 某 issue)",**把 X 的对应特性读清楚**——它是一个机制还是拆成多个?各自什么体验 / motivation?参考不是粘进【原始需求】就完事,要当调研任务**真去做**(读参考常常正好暴露"这需求其实是几件独立的事",别糊成一个)。

两个坑(真实教训):
- **别拿坏现状当产品真值**——若现状本身就是要改的坏东西(用户点名参考往往正因如此),参考才是真值,不是现状代码。
- **别用实现结构视角代替产品视角**——"它俩在不在同一个类里"回答不了"它俩是不是两个用户特性"。

ground 完,把"现状 + 参考"的结论作为下面澄清(尤其各轴推荐答案)的事实基础。

**grounding 是贯穿澄清的反射,不是开问前那一下**:澄清中冒出新的不明确(某特性现在到底怎么表现、参考里这块怎么设计),只要能靠读现状/参考答上来,就**自己去读**,别靠猜、也别凡事都推给用户问。

### §3.1 列出需要澄清的轴(只列,不一次问完)

基于 §3.0 的 grounding,在脑里列一份清单——这个变更需要澄清哪些点?常见轴:

- **谁是用户**:本职用户还是某个特殊角色?多角色还是单角色?
- **什么场景下被触发**:主动行为还是被动响应?常用还是边缘?
- **成功长什么样**:用户看到 / 听到 / 摸到什么时算"功能 work 了"?
- **失败 / 边界长什么样**:输入异常、网络断、并发、空状态——分别期望什么行为?
- **范围边界**:做到哪算够?哪些诱人但本期不做?
- **关联**:依赖别的功能吗?会被别的功能影响吗?
- **bugfix 专属**:复现率、影响范围、是否数据损坏?

对**每个轴**,你心里先有个推荐答案(基于原始需求 + §3.0 grounding)。然后挨个问。

### §3.2 一轮一问的格式

每轮在对话中向用户抛**一个**问题,格式如下(逐字示范):

```
Q1: <一句话问题>
我的推荐:<一两句答案>。
理由:<一句话,为什么这样推荐>。
反方:<可能不同意的角度,可省略>。

你怎么看?
```

用户回答后,把 Q + A 写进"澄清记录"段。**A 段粘原话**(见 §0 规则 2)。

```markdown
- Q1: <问题>
  A(原话): <用户怎么说就怎么粘,口语/举例/跑题都留>
  Agent 解读: <可选,与原话分开>
```

然后才进入 Q2。

### §3.3 何时停止澄清

不是每个轴都要问。停止条件(任一即可):

- 你已经能写出一份**让两周后的陌生人**看懂的"用户场景 + 验收标准 + 范围与非目标",没有 TBD
- 用户表达"细节我不太关心,你定"——记录此意,做出推荐放进文档
- 已经问到第 6-8 个问题还在挖细节——可能在过度澄清,问用户"剩下的细节我先按推荐写,你审稿时再调?"

**反 anti-pattern**:不要因为用户的需求看上去简单就跳过澄清。"加个按钮"也有 5 个澄清点(放哪、什么时候 disable、点了之后给什么反馈、谁能看到、移动端怎么办)。

### §3.4 澄清越界检测

如果你在澄清过程中冒出一个问题是"用 SQLite 还是 JSON 存"——**停下来**。这是 design 阶段的问题,不是 spec,**不写进首文档**。

记在脑里(或临时笔记),交接给 `change-design-author` 时口头列出:"以下问题我在澄清时遇到,但属于实现层,留给你处理:..."。design skill 会接过去。

判断标准:**这个问题的答案会改变"用户感知"吗?** 会 → spec;不会 → design。

## §4 产出结论性段落

澄清结束后,基于 Q/A 写以下段落(模板已经留好骨架):

### feat / refactor / perf / bugfix-full 都要写的

- **用户场景 / 现状痛点**:谁、什么情境、做什么、得到什么。**保留自由叙事**——故事、对话、列表、流程图都行。叙事的价值不可替代:它建立画面、传达"为什么这么做"的意图、展示场景之间的流、给后续读者足够上下文不至于窄读成"只勾几个框"。`change-design-author` 读这一段是为了取**意图**。
  - **两种镜头,按变更类型选**:
    - **新增能力**(feat / bugfix-full):憧憬式——"将来用户能这样做"。
    - **面向内部的变更**(refactor / perf,或任何不引入新用户行为的改动):**回归基线**镜头——"现在用户是这样用的,变更后要保持一致"。这一段写的是**既有行为的快照**(回归面),不是新东西。
  - **罕见情况**:如果追到底确实没有任何用户可观察的表面(纯内部脚本之类),显式写"无用户可观察变化",并**举证**为什么——不能因为"感觉是内部的"就默认。大部分代码追远一点都触达某个用户可观察的东西(哪怕只是"产品还能正常启动")。
- **验收标准 / 目标状态**:它是上面那段叙事的**可勾投影**,用 **Requirement / Scenario 结构**写(不是扁平 bullet)。格式见 `assets/spec.md` 模板:
  - 按 `### Requirement: <能力描述>` 分组,每组挂 ≥1 个 `#### Scenario`,scenario 用(可选 `**GIVEN**` 前置状态)+ `**WHEN**` / `**THEN**`(可选 `**AND**`)。`**GIVEN**` 写"进入场景前环境长什么样"(例:群里有 50 个成员)——需要前置态才说得清时才加,否则省略,别把前置态硬塞进 WHEN。
  - **硬规则:每个 Requirement 至少一个 Scenario**(缺则视为未收口,门禁 1 不过)。
  - 每条 Scenario **都要能追溯到用户场景里的某一段**,且**只写用户可观察的**(用户在产品上看到 / 听到 / 操作到)。
  - **同一能力的正常路径、失败 / 边界 / 空态各列一个 Scenario**——这正是结构化相对扁平 bullet 的价值:漏掉边界态时会在这里留出明显空位。澄清阶段(§3.1)聊到的"失败 / 边界 / 空状态"轴,在这里逐条落成 Scenario,别让它们蒸发。
  - feat 示例:
    ```
    ### Requirement: 群聊 @ 成员候选
    #### Scenario: 群里有匹配成员
    - **WHEN** 用户在群聊输入框敲 `@`
    - **THEN** 200ms 内出现成员候选列表
    #### Scenario: 大群里敲 @(需前置态,用 GIVEN)
    - **GIVEN** 群里有 50 个成员
    - **WHEN** 用户敲 `@`
    - **THEN** 候选列表虚拟滚动,不卡顿
    #### Scenario: 群里无匹配成员
    - **WHEN** 用户敲 `@` 后输入的前缀匹配不到任何成员
    - **THEN** 显示"无匹配成员"空态文案
    ```
    ❌ 反例(实现层,不写):"MentionPicker 组件接收 candidates prop 并渲染"。
  - 面向内部的变更:Scenario 写**不变性**——`**WHEN** 走既有行为 X` / `**THEN** 结果与变更前一致`。
  - "无用户可观察变化"的 unit:本段写"无",该 unit 的验证全部落到 `design.md` 的实现层验收标准 + 测试套件不回归。
  - **实现层标准不进这里**。协议字段、参数取值、内部函数、接口形态、日志字符串、"复刻某实现"的保真要求——这些**不是验收标准**,它们归 `design.md`,由 worker 单测 + 架构师 PR review 验。如果用户的原始需求里就含"复刻 X 实现"这类要求,保留在【原始需求】段作为用户原话,但**不要升级成验收标准**;把它作为实现约束,交接给 `change-design-author`(§3.4 的交接机制)。验收标准只问:"复刻 / 重构 / 优化完之后,用户能观察到什么(或观察到什么没变)"。
- **范围与非目标**:列出本期不做的事——这是防 scope creep 的关键。

### bugfix-full 额外要写的

- **影响范围**:谁受影响、多严重、是否数据损坏
- **根因分析(RCA)**:不止"哪行写错了",还要"为什么这种错能进来"——是 review 漏了?测试没覆盖?约束没说清楚?挖"哪行错了"到"为什么能进来"这一步,用 `systematic-debugging` skill 的**调查阶段**(逐字读报错 → 稳定复现 → 反向追到坏值源头)。**注意:只用它的调查阶段(Phase 1–2),不进修复阶段**——spec-author 禁碰代码(§0.6),你产出的是 RCA 文字,不是补丁。
- **原始设计意图追溯**(RCA 的一部分,但单独拎出来防遗漏):出错的这块代码不是凭空来的——它属于某个原始 change unit。先 grep `docs/changes/` 找到引入/拥有这个功能的 unit,读它的 spec/design,**写下这块功能本来要达成什么**,以及"修复必须保住的不变量"。为什么这步关键:不知道原意图时,最省事的修法往往是把触发出错的那条路径直接砍掉——症状是消了,但功能被阉割成了残废。把"原意图 + 不变量"落进 RCA,这条约束才会随文档流到下游(design / worker),拦住"为消症状而砍功能"。
- **回归引入点定位**(仅当是回归):`git blame` 出引入坏行为的那次变更,落到 commit(能映射到 unit/PR 就一并记,映射不到只记 commit)。它与上一条"功能引入 unit"是**两个独立来源**(可能不同),分别答"必须保住什么"与"为什么能进来 + 防再发着力点"。

### 所有类型都要写的

- **Relations**:
  ```markdown
  - Depends on: <unit-id>      # 需要先做的别的 unit
  - Blocks: <unit-id>          # 本 unit 完成后才能做的
  - Related: <unit-id>         # 触及但不阻塞
  - Closes: #<issue-num>       # GitHub issue,本 unit merge 时自动关
  - Refs: #<issue-num>         # 触及但非专门为修这条
  ```
  无依赖时整段省略。**主动检查 GitHub issue**:`gh issue list --label triage` 看有没有相关待决 issue,有就引用。

## §5 完成信号 + 门禁 1 交接

完成判据(逐条勾):

- [ ] 首文档无 `<!-- 模板说明 -->` HTML 注释块(已删)
- [ ] 无 TBD、无"待澄清"、无空的 Q/A 占位
- [ ] **§3.0 产品特性 grounding 已做**:当前系统对应功能 + 用户点名的参考都从产品视角读过
- [ ] 澄清记录每条 A 段是用户原话,不是概括
- [ ] 用户场景 / 验收标准 / 范围非目标 都填了实质内容
- [ ] **验收标准用 Requirement / Scenario 结构写**:每个 `### Requirement` 至少挂一个 `#### Scenario`(WHEN/THEN);无空 Requirement
- [ ] **每个 Scenario 都是用户可观察的**(用户在产品上看到 / 听到 / 操作到),且能追溯到【用户场景】的某段叙事;无实现 / 协议 / 接口 / 内部状态条目(那些归 design.md)
- [ ] Relations 段填妥(无依赖也要显式写"无"或省略整段)
- [ ] bugfix:RCA 已写,不只是表面现象
- [ ] 已 commit 到 `main`(仅 `docs/changes/<unit_dir>/`)

全部勾上后,在主仓 `main` 上 commit + push `docs/changes/<unit_dir>/`(勿建 `unit/*` 分支)。

然后在对话中告诉用户:

> 首文档定稿,门禁 1 通过。下一步可以按照 `change-design-author` skill来对齐"怎么做"。
> 文档路径:`docs/changes/<unit_dir>/<首文档>.md`

如果澄清期间遇到了实现层问题(§3.4 越界检测),**口头列给用户**,提示在 design-author 启动时复述。

**bugfix lite 特殊**:lite 没有 design 阶段。spec-author 只写 fix.md 的**前两段**(`现象 / 复现` + `根因`)。完成后提示用户:

> bugfix lite 首文档完成,fix.md 的"现象 / 根因"两段已写。可以直接启动 `change-orchestrator` 进入实施(orchestrator 自动按单 M1 处理 lite 路径),worker 会回填 fix.md 的"修复 / 验证"两段。

---

## §6 反 anti-pattern(高频踩坑)

- **不要批量生成**。Q1/Q2/Q3/Q4/Q5 一口气抛给用户、然后一口气填全文——用户答不动、答不全、答完后你也不更新文档。永远一次一问。
- **不要把用户答复"提炼实质"**。原话里的弱表达和跑题是后续 design 的暗信号,粘原文,不确定就先复述确认。
- **不要在 spec 阶段问技术选型**。"前端用 React 还是 Vue"、"接口 REST 还是 GraphQL"、"存 Redis 还是内存"——这些是 design。问的话用户也答不上(他不该关心)。
- **不要因为简单就跳过澄清**。最常被低估的是"加个按钮"类需求,实际坑最多。
- **不要替用户决定范围**。范围与非目标必须用户确认过。你可以推荐,但不能默认。
- **不要在 spec.md 写实现伪代码**。哪怕是为了让自己想清楚——想清楚的过程不要落到文档里。

## §7 输出契约(供下游 skill 读)

`change-design-author` 启动时会读你产出的文档。它需要:

- 首文档完整、无残留模板说明
- 验收标准是用户视角且独立可验
- Relations 已填(影响 design 阶段的依赖判断)
- 范围与非目标已界定(影响 design 阶段的 milestone 拆分边界——`design.md` Milestone 表的"范围"列里写的文件就是从这里推下来的)

如果下游发现你产出的文档有上述问题,会被打回。所以宁愿在你这里多花一轮澄清,也别让下游补。

### 下游不止 design-author——验收标准会成为 reviewer 的逐字清单

你写的【用户场景】+【验收标准】不只给 `change-design-author` 看。unit 实施完成后,`change-orchestrator` 会把【验收标准】**逐字透传**给 `change-reviewer` 当验收清单。reviewer 的**覆盖表逐个 Scenario 验收**(每个 `#### Scenario` 一行,判 pass / fail / inconclusive / not-applicable),并直接拿 Scenario 的 WHEN/THEN 当旅程脚本走——所以你 Scenario 拆得越全(尤其失败 / 边界 / 空态),reviewer 漏验越少。reviewer **只能验用户可观察的东西**(在产品上走旅程、看结果)。

后果很硬:**Scenario 里只要混进实现 / 协议 / 接口 / 内部状态条目,会让整轮 reviewer 验收作废**——reviewer 拿到协议级标准就会去翻源码 / 抓帧 / 加日志定位,滑进 engineer 模式,这轮证据全部失效。

还有一个下游:`change-design-author` 会把【验收标准】**投影**成本 unit 的 canonical **delta-spec**(对长青契约层 `docs/specs/<包>/spec.md` 的增量),收尾由 orchestrator 并进 canonical。所以你的验收标准写得准、Scenario 拆得全,长青契约层最终才准——这是它进入"系统 current 权威"的源头之一。

所以 §4 说的"实现层标准不进 spec"不是风格建议,是**流程硬约束**。实现层的东西归 `design.md`,那里有 worker 单测和架构师 PR review 来验——各有各的 verifier,不要挤进同一段。

## §8 一个示范片段

用户说:"我想做个 chat mention picker"

**第一步**(对话):

```
我把这个理解成 feat(新功能,不是 bug)。给你建 unit 目录 docs/changes/feat-104-chat-mention-picker/,首文档用 spec.md 模板。可以吗?
```

用户:嗯。

**第二步**:粘贴用户原话到"原始需求":

```markdown
## 原始需求

> 我想做个 chat mention picker
```

**第三步**(对话):

```
Q1: 这个 picker 在哪里触发——只在群聊还是单聊也算?
我的推荐:只在群聊触发(单聊只有一个对方,@ 没意义)。
理由:@ 的语义是从多人中选一个,单聊场景不存在。
你怎么看?
```

用户:对,只群聊。

写进澄清记录(A 段原话):

```markdown
## 澄清记录

- Q1: picker 触发场景:只群聊还是单聊也算?
  A(原话): 对,只群聊。
```

继续 Q2,直到收敛。
