# 产品试用

交付可供用户选择修复的发现：真实任务有没有做对，用户是否容易理解和控制，后台是否可靠、合理地完成，以及异常究竟发生在哪一层。最终成功不抵消过程中暴露的工具试错、无效审核、重复工作、事实失真或状态误导；一次异常也不能直接证明普遍故障或某个根因。

## 选择试用范围

- 用户指定场景、角色、入口、环境或限制时，以它们为范围；沿相关执行链向下检查，不借“全面”扩大为全产品巡检。
- 未指定时，先读仓库 `README.md`、`docs/product/` 与相关 current specs，把核心卖点转成少量有实际交付物的连续用户任务。说明为何选这些任务后直接开始，不要求用户替你列用例。
- 选能观察能力衔接的工作：发起任务 → 中途补充或更正 → 收到结果 → 后续继续或控制。按当前能力加入协作、持久化、提醒、恢复等环节，不强制每次覆盖所有模块。
- 用自然目标、真实约束和可核对的数据发起任务。不要在用户提示里教授工具参数、内部 ID 或正确调用顺序。测试专门能力时可以自然要求“请内部助手分别核算”，但不要替被测 Agent 完成编排。
- Nano 的场景设计和历史归因实例见 [场景与归因参考](references/scenarios-and-attribution.md)。历史发现只说明方法；当前版本是否仍有问题必须重新观察。

## 建立可信的试用现场

确认 checkout、branch、SHA、dirty 状态、模型和关键配置。保留已有修改，记录这次真正运行的代码和构建产物；不把 HEAD 当成 dirty tree 的完整基线。

遵循 [隔离运行契约](../../../docs/development/worktree-runtime.md)，优先用 `scripts/e2e-up.sh` / `scripts/e2e-down.sh`，隔离端口、数据、身份、配置、workspace 和 DSH home。通过真实界面与模型使用产品。临时测试身份及数据可在本轮隔离环境中创建和交互；不从试用请求推导向真实联系人外发、生产重启或部署授权。

起栈检查同时观察开发者首次运行的阻力。标准构建失败先保留命令和错误，再判断能否用明确标记的临时装配继续其他试用；绕过不能算原路径通过，也不能改变待验证的行为。若起栈始终不通，交付启动阻断及未覆盖面，不把静态阅读写成真实试用。

长时间运行的服务使用受控终端或 tmux；后续按实际进程、监听与新日志确认存活。网页创建、聊天、等待、查看结果等用户路径优先经真实界面；公开 API、日志和数据库用于核实，不能代替界面体验。无法使用某个真实入口时写清覆盖限制。

## 同时观察体验和后台执行

围绕同一任务维护简短时间线：输入和更正、首次可见反馈、关键工具与委派、结果落盘或投递、停止或恢复。记录 chat/session/turn/tool-call 等必要定位信息，供界面与后台对照。

| 观察面 | 要判断的具体问题 |
|---|---|
| 用户交付 | 结果、数值和事实是否正确；更正是否生效；是否交给正确的人和聊天；保存的文件、任务图等是否真的存在且一致 |
| 用户体验 | 等待时能否知道正在做什么；信息层级、状态、通知是否帮助判断；需要多少跳转和操作；失败、停止、完成是否说得清楚 |
| 模型与工具 | 首次调用是否正确；是否反复依靠报错补参数；结果是否被正确理解；审核、重试、空查询、重复创建是否有实际目的 |
| 委派与后台工作 | 交接是否保留事实和不确定性；更正是否到达原执行者；汇总是否夸大核实程度；后台复盘、自通知是否引起空转或污染后续判断 |
| 持久化与生命周期 | UI、工具返回、持久状态和实际效果是否一致；重启前的工作是否保留；停止是否真正生效；提醒是否按时且只送达应到的位置 |

不只查红色错误，也查“成功但绕了很多路”“没有异常但结果错了”“后台做了很多用户却不知道”。反复试错要保留失败次数、实际参数、错误和最终成功调用；最后一次成功不能覆盖前面的代价。发现明显耗时或重复工作时，尽量区分模型执行、等待子任务、审批和无效重试的贡献；没有计量就不编造 token、成本或延迟归因。

正常推进中的任务按事件或适当等待观察，不高频刷新制造负载。异常出现后先保存证据，继续不受影响的任务；不要过早沉入第一个问题，导致其余核心旅程没有试用。

## 沿证据链归因

每个候选发现先写“预期、实际、用户或运行代价”，再解释原因。预期来自用户原话和 current 契约；产品体验缺口也可来自完成目标的实际困难，不要求每个问题都有违约条文。

按异常需要追到对应层级，不能仅凭一条错误文案定责：

`用户输入 → 实发模型上下文/工具说明 → 模型输出或工具参数 → 审批/工具执行与业务结果 → 持久状态/事件 → 消息交付和界面`

- **追最早偏差。** 输入没有的条件首次在哪里被加进来？正确参数在哪里丢失或改变？下游重复错误信息不算独立证实，后续成功也不证明前一次执行成功。
- **核实模型实际看到什么。** 工具调用反复错误时，对照实发 schema/description、模型参数与服务端校验；源码里存在说明，不代表经过 SDK/协议转换后仍送给了模型。拿不到实发请求时保留这项限制。
- **区分状态层。** HTTP 成功、工具调用结束、业务成功、持久化完成和用户收到结果是不同事实。必须检查业务 payload 和实际展示，不能把底层 `completed` 直接等同于 UI 谎报成功。
- **区分责任来源。** 可能是本次模型行为、模型接口说明、审批/编排、服务端业务、持久化/投递、UI 表达、环境装配或测试方法；只按证据标注，可有多层原因，不强行单选，也不把“模型笨”“网络不稳”当解释。
- **做最小因果核验。** 围绕有证据的假设进行窄重放、对照输入输出、读取对应代码或日志；需要重复模型实验时用干净新会话，避免旧失败经验、Skill 或 memory 提供答案。保留原始失败，不用重试挑出的成功替代它。不要为每个发现开展全仓审计或固定轮数实验。
- **主动排除误报。** 检查当前契约、预置数据、临时端口/身份/产物装配，以及事件先后关系。提醒已送达后才重启，不能证明未到期提醒恢复；窄屏浏览器不能证明原生 iOS 可用。

分别标注“现象已证实”和“根因已证实／候选原因／未定位”。已证实根因要有能连接原因与现象的证据；只有相关性时列候选及缺少的核验，不编造确定性。模型输出问题说明本次模型、配置与样本范围，不凭单次运行宣称普遍失败率。

发现、核验和修复是不同工作。默认不改产品代码、提示词或工具说明来让本轮试用通过；先给用户可选择的结果。用户已授权修复时再按仓库变更流程推进，并保留修前证据。

## 交付与结束

保存一份本地可复查报告，Markdown 即可；截图和轨迹多时可用带证据链接的 HTML。原始日志、数据库、凭据和截图缓存不提交，报告脱敏；证据格式按 [Evidence](../../../docs/development/evidence.md)。

报告先给整体体验判断与主要影响，再列：

- 实际跑过的任务、基线、模型/配置、入口与覆盖边界；哪些能力有直接成功证据。
- 按影响排序的发现：稳定编号、类别、复现输入/步骤、预期与实际、影响、证据定位、归因结论及置信边界。建议针对已证实原因，或明确下一项核验；不让解决方案冒充根因。
- 已排除的可疑点及排除理由、尚未定位的问题、未覆盖范围和环境阻断。没有发现也如实报告，不凑固定问题数或严重级别。
- 清理状态：停止本轮启动的 IM/Node/DSH/Vite/预览服务，释放端口，移除临时配置与凭据；只操作本轮拥有的进程和文件。用户要求保留现场时记录运行入口、所有者及后续清理方式。

把同一原因造成的多个表象关联起来，保留不同影响但不凑成多个 bug。建议顺序考虑任务失败、数据/事实错误、用户控制、操作阻力和持续运行代价；不能只因为界面可用就降低后台问题的重要性。

在约定范围内取得足够的体验与执行证据、对高影响异常完成必要归因或明确限制后收尾，不追逐假想边界。最终回复链接报告，概括最重要发现与归因、未确定之处及清理结果，让用户决定下一步修复范围。
