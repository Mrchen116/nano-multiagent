## 一个有区分度的连续任务

最初试用围绕同一场朋友聚会推进，给定三个方案和明确报价，因此既能观察系统衔接，也能独立算出结果。

1. 网页创建全局助手，用默认模型和正常产品配置。单聊交办 10 人、预算 1200 元、14:00–18:00、不饮酒不爬山的活动；让内部助手分别核算预算和风险，保存“方案、确认人数、采购”计划。限定不联系真实商家，交付应能直接发给朋友。
2. 从另一聊天更正为 8 人、预算 900 元、2 人素食；要求复核原工作、更新原计划，结果回原单聊，群只回执。检查原 session、子执行和任务图是否延续，而非只看回答说“记住了”。
3. 确认部分步骤并要求保存文档，核对真实文件及任务状态。安排短提醒，看到它持久化后在未到期时重启隔离节点，随后核对实际投递时间、位置和内容。
4. 让它执行一个可控的等待任务，从另一聊天停止。核对实际执行、主/子轨迹和两处聊天反馈；再问之前更正过的条件，检查连续性。
5. 在真实委派点打开子执行范围，再返回父级；同时观察普通用户能否理解等待、错误、结果和后台维护通知。

原报价：A 场地 0 + 每人餐食 68、交通 20；B 场地 300 + 每人餐食 60、交通 15；C 场地 400 + 每人餐食 55、交通 10。8 人时分别为 704、900、920 元。报价并没有确认场地服务或包场时长。

可换成发布准备、旅行、资料整理等任务；保留可核对的事实、更正、交付与后续操作即可。不要把上次正确答案、内部调用语法或历史报错喂给新 Agent。

## 归因应达到什么程度

| 历史观察 | 当时如何归因或排除 | 可复用的判断方法 |
|---|---|---|
| 三步计划最终保存成功，途中连续三次工具失败 | 检查 create 带 operations、apply 缺 change_note、批内引用缺 `@` 的实际参数；对照模型可见规则与服务端校验。后续分析还发现当时 SDK 转换丢弃根级条件 schema | 既查首次调用，也查最终数据；区分说明缺失、转换损失与模型未遵循规则。不能从历史推断当前 SDK 仍有相同问题 |
| 审批提示“评审不可用” | 实际请求到达模型；响应耗尽预算且没有判定正文。后续分析另发现中文判定与解析器接受值不一致 | 查实发请求、响应、停止原因和解析路径，不把错误名称当网络根因，也不把不同失败机制混成一项 |
| 方案把“包场 4 小时”当事实 | 用户只给包场价格；主助手先在委派输入补出时长，子助手沿用，最终汇总再引用 | 找最早事实偏差，区分输入、假设和核实；子助手复述不是独立证据 |
| 聊天看不出工作是否在执行，后台通知很多 | 对照同一时刻聊天与 Work Running、首次可见反馈时间、自通知触发的额外轮次 | 同时解释用户理解成本和无意义后台工作，不只写“慢”或“文案不好” |
| 用户停止后，原聊天显示 failed | Work 为 interrupted、实际等待已停止、另一聊天收到停止回执 | 控制动作成功与界面状态误导可以同时成立，归因到正确层级 |
| 底层工具 completed，但 payload 为业务失败 | 工作页已把它显示为 Call failed | 不能仅凭底层状态举报“错误显示成功” |
| 被拒的 Skill 后来存在 | 时间线显示另一个后台 review 成功创建 | 后来的结果不能倒推前一操作绕过审批，须核对执行者、时间与来源 |
| 首次重启后看到了提醒 | 提醒在重启前已送达，重新安排未到期提醒才验证恢复 | 时间顺序是因果证据的一部分，避免拿错实验支持结论 |
| 标准构建失败，但单独 Vite 构建可运行 | 记录当时本机依赖和类型错误；后续才进一步查明类型来源 | 构建路径失败与网页运行结果分别成立，不扩大为所有环境或生产故障 |

报告中的原因可以停在“现象确定，根因待查”，但不能把猜测写成已确认。若要建议改系统提示词、工具描述、schema 或 UI，先说明实证把问题定位到哪里；不默认所有模型行为问题都靠加提示词解决。
