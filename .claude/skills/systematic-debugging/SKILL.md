# Systematic Debugging（系统化调试）

乱猜乱改最费时间,还会埋新 bug。快速补丁只盖住症状,根因还在。

## 核心铁律

> **没找到根因之前,不许动手修。修症状 = 失败。**

没完成阶段 1,就不准提修复方案。哪怕你"一眼看出来该改哪行"——看到症状 ≠ 理解根因。

## 何时该用、何时不用

**任何技术故障都用**:测试失败、运行时崩溃、构建失败、行为不符预期、性能异常、集成故障、flaky。

**越是这些时候越要用**(诱惑你跳过的时刻):
- 有时间压力 / 着急("先快修一下")——系统化比瞎试快,头一次就修对的概率远高。
- "就改一个地方试试"看起来很显然。
- 已经试过几次都没好 / 上一个修复没生效。
- 你其实没完全搞懂问题。

**不用**:常规预期内的失败(校验非法输入并正常报错,这是功能不是 bug);产品验收走查——那是另一种验收视角,不归调试纪律。

## 四个阶段(必须按顺序走完,不准跳)

### 阶段 1:根因调查

动手修**之前**:

1. **逐字读报错**。别扫一眼跳过——报错和 stack trace 经常直接写着答案。记下行号、文件路径、错误码、完整调用栈。

2. **稳定复现**。能不能可靠触发?确切步骤是什么?每次都发生吗?**不能稳定复现 → 先收集更多数据,不要猜**。

3. **查最近改动**。什么变了能导致这个?`git diff` / 近期 commit / 新依赖 / 配置变更 / 环境差异。

4. **多组件系统:先打边界日志定位是哪一层断的**。当系统有多层(CI → build → 签名、API → service → DB、前端 → 网关 → 内核),**在提任何修复前**,给每个组件边界加诊断:
   - 记录数据进入该组件时长什么样、离开时长什么样;
   - 核对环境/配置有没有正确透传;
   - 跑一次,拿到证据**指认是哪一层断的**(例:secrets→workflow ✓,workflow→build ✗),再去钻那一层。
   - 别一上来就猜某一层——先用证据缩小范围。

5. **反向追数据流**。错误深在调用栈里时:坏值最初从哪产生?谁用坏值调了它?一路往上追到源头,**在源头修,不在症状处修**。展开手法见 `references/root-cause-tracing.md`。

### 阶段 2:模式分析

修之前先找到"模式":

1. **找能跑的例子**。同一个 codebase 里有没有相似但正常工作的代码?
2. **对照参考实现**。如果在复刻某个模式,**完整读**参考实现的每一行,别跳读——半懂保证出 bug。
3. **逐条列差异**。能跑的 vs 坏的,每一处差异都列出来,再小也列。别预设"这个不可能有影响"。
4. **理清依赖**。这块代码还需要什么组件/配置/环境?它假设了什么前提?

### 阶段 3:假设与验证

科学方法,一次一个变量:

1. **写下单一假设**。明确表述:"我认为 X 是根因,因为 Y。"写下来,要具体不要含糊。
2. **最小验证**。做**能验证这个假设的最小改动**,一次只动一个变量,不要同时修好几处。
3. **验证后再继续**。生效了 → 进阶段 4。没生效 → 形成**新**假设,**不要**在旧的上面叠更多修复。
4. **不懂就说不懂**。"我不理解 X"——别装懂,去查、去问。

### 阶段 4:实施修复(回到三提交)

根因确认后才到这一步:

1. **先有复现测试**。最简复现,能自动化就自动化。
   - 在 change 工作流里,这一步**就是 worker 三提交的 C1(红测)**——回到 `change-impl-worker §5`,写复现该 bug 的失败测试再修。**本 skill 不另起一套提交流程**。
   - bugfix 尤其:测试要复现**用户报的那个症状**(真实入口),不是只复现你写的那段代码。
2. **只改根因这一处**。针对阶段 1 定位的根因,一次一个改动。不要"顺手"重构、不要"既然来了"附带改别的。
3. **验证修复**。测试现在过了吗?有没有弄坏别的测试?问题真的解决了吗?
4. **修完后考虑加固**。根因找到后,可在多个层次补校验防同类复发——见 `references/defense-in-depth.md`。
5. **flaky / 时序类**:别用写死的 `sleep`/timeout 蒙,用条件轮询——见 `references/condition-based-waiting.md`。

## 3 次失败 → 停手,质疑架构(不是再试第 4 次)

**这条在 worker 内、调单个 bug 的当下生效**,跟 `change-impl-worker §7.3`「同一 roadpoint 连续 6 次失败 → 回退重拆」是**两个并列的轴**:§7.3 是 roadpoint 级的机械重试上限;这里量的是**架构信号**——同一个 bug、试了 3 次修复、每次都在别处冒出新问题。

出现下列模式 = **架构错了,不是假设错了**:
- 每个修复都在不同地方暴露新的共享状态/耦合;
- 修复都需要"大动干戈的重构"才做得了;
- 每修一处就在别处冒新症状。

**停手,质疑根本**:这个模式本身站得住吗?是不是只因惯性在硬撑?该重构架构还是继续修症状?

然后**找 leader(orchestrator)谈**——走 `change-impl-worker §4 Pause-on-design-issue` / §7.3 既有上报通路。这不是"又一个失败的假设",这是"架构选错了"。

## Red Flags —— 抓到自己这样想,立刻停,回阶段 1

- "先快修一下,以后再查"
- "改个 X 试试看"
- "一次多改几处,跑下测试"
- "跳过测试,我手动验一下"
- "估计是 X,改了它"
- "没完全搞懂,但这样改可能行"
- "参考实现太长,我照着改改得了"
- 还没追数据流就开始提方案
- "再修一次就好"(已经试了 2 次以上)
- 每修一处就在别处冒新问题

**以上任意一条 = 停。回阶段 1。**(已 3 次失败 → 质疑架构,见上一节。)

合作者发出这些信号也是同理,回阶段 1:"是这样吗?"(你没验证就假设了)、"停止猜测"、"我们卡住了?"(你的路子不对了)。

## 常见自我开脱(都是错的)

| 借口 | 现实 |
|---|---|
| "问题简单,不用走流程" | 简单 bug 也有根因。流程对简单 bug 很快。 |
| "紧急,没时间走流程" | 系统化比瞎试快。 |
| "先试这个,再调查" | 第一个修法定了基调。一开始就做对。 |
| "确认能修好再补测试" | 没测试的修复不牢。测试先行才证明真修好了。 |
| "一次多修几个省时间" | 没法隔离是哪个生效,还引入新 bug。 |
| "参考太长,我改改模式" | 半懂保证出 bug。完整读。 |
| "我看出问题了,直接修" | 看到症状 ≠ 理解根因。 |
| "再修一次"(已失败 2+ 次) | 3+ 次失败 = 架构问题,质疑模式,别再修。 |

## 子技法(按需读 `references/`)

走到对应步骤、确实需要时再读,别一上来全拉进来:

- **`references/root-cause-tracing.md`** —— 反向追调用栈,把 bug 追到最初触发点(阶段 1.5)。
- **`references/defense-in-depth.md`** —— 找到根因后,在多个层次补校验防同类复发(阶段 4.4)。
- **`references/condition-based-waiting.md`** —— 用条件轮询替代写死的 timeout,根治 flaky(阶段 4.5)。

---

## 当调查真的得出"无根因"

如果系统化调查后确实是环境/时序/外部因素:

1. 你已经走完了流程(不是跳过);
2. 记录你查了什么;
3. 实施合适的处理(重试、超时、明确的报错);
4. 加监控/日志便于将来追查。

**但**:95% 的"查不到根因"其实是调查没做完。
