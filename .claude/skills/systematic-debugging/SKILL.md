# Systematic Debugging

用证据确定故障发生的边界与原因，再修复根因。调查、复现、比较和实验按实际线索选择，不要求固定阶段或每次读完整参考实现。

## 约束与完成

- 区分观察、假设和未知。复现不稳定时记录触发条件与已排除因素，收集能区分假设的证据，不把“尚未复现”当作原因已确认。
- 多组件问题优先核实际入口、数据流和运行配置；已有日志足够就不改代码加日志。只读任务或生产调查不因本 skill 自动获得修改/重启权限。
- 实验尽量隔离变量，避免同时堆多个猜测补丁。修复保留原功能及项目不变量，不顺手扩大范围。
- 确认根因后按所属任务的验证规则修复，以用户报告路径和适当回归保护证明症状消失。已有有效证据可复用；相关验证通过就结束。
- 多次有证据的修复却反复引出共享状态/耦合问题时，重新评估假设与设计，带证据向 owner 报告；失败次数本身不证明架构错误。

按问题选择参考：坏值源头不明用 [root-cause-tracing](references/root-cause-tracing.md)；真实独立边界需要额外保护时用 [defense-in-depth](references/defense-in-depth.md)；异步/flaky 用 [condition-based-waiting](references/condition-based-waiting.md)。

交付根因与证据、修复范围、实际验证及仍未解决的限制；环境阻塞时保留可恢复现场，不宣称已修复。
