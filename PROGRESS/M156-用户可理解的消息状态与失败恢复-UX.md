## 基线判断
- 现有消息状态已从裸枚举升级到简单标签，但仍不够解释性，用户不知道“Sent/Completed”分别意味着什么。
- 消息气泡里没有区分“用户消息未发出”和“Agent 处理失败”两类失败恢复动作。
- composer banner 已有 retry，但消息列表本身还缺少产品级状态说明。
- workspace 页已有比较完整的 SSE merge / usage refresh 链路，改动必须保持这条链路不变。

## 执行策略
1. 先在类型与 workspace 事件映射层补充恢复语义字段，避免只在 UI 临时拼接。
2. 再升级 message bubble 的状态 copy，让每个关键阶段都能说明当前发生了什么。
3. 最后补前端测试，覆盖 agent failure recovery copy，并更新 TASKS/PROGRESS。

## 进度

### R1 盘点现有状态与事件映射
- Context:
  - `message-pane.tsx` 负责最终状态展示；`chat-workspace-page.tsx` 负责 SSE 事件归并与前端消息模型更新。

- Rationale:

- Evidence:
  - `src/IM/frontend/src/features/chat/types.ts`

### R2 提升消息状态可理解度
- Context:
  - 原标签如 `Sent` / `Completed` 太短，无法帮助用户理解“消息到了哪一步”。
- Decision:
  - 将状态展示升级为“标签 + 解释 + 恢复动作”三层 copy：
    - 用户消息 sent -> `Sent to relay`
    - agent running -> `Agent is working`
    - agent completed -> `Agent replied`
    - 用户消息 failed -> `Didn't send`
    - agent failed -> `Agent couldn't finish`
  - 对失败态额外显示 recovery 文案，例如 `Recovery: Retry request`。
- Rationale:
  - 用户真正关心的是“现在发生了什么”和“下一步该做什么”，不只是底层状态码翻译。
- Evidence:
  - `src/IM/frontend/src/features/chat/components/message-pane.tsx`
  - `src/IM/frontend/src/features/chat/components/message-pane.test.tsx`

### R3 保持实时事件链路并补恢复测试
- Context:
  - `relay.failed` 与 `message_status` 更新都可能把消息推进到失败态；如果不在 merge 层写入 recovery metadata，UI 无法稳定区分失败类型。
- Decision:
  - 在 stream message builder、relay synthetic message builder、以及后续状态更新分支中统一注入 `recovery_action_label` / `recovery_hint`。
  - 保持 `shouldRefreshUsageForEvent`、`upsertMessage`、`mergeConversationDetail` 等逻辑不变。
- Rationale:
  - 只增强消息模型，不改变事件判定与刷新时机，能最大限度保持实时链路稳定。
- Evidence:
  - `src/IM/frontend/src/features/chat/chat-workspace-page.tsx`
  - `src/IM/frontend/src/features/chat/chat-workspace-page.test.ts`
