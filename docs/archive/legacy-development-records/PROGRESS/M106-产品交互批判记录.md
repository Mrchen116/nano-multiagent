# M106 — 产品交互批判记录

## 范围
- 仅覆盖 M106 要求的真实 IM↔Gateway 端到端验收与成熟产品视角批判。
- 不扩展到 M104 的全系统总验收，不对尚未要求的 UI/架构面做全面重构。

## 真实验收观察
- 绑定：实际 acceptance 已确认 `POST /im/v1/bind` 的 start/confirm HTTP 流程可跑通，节点 owner 归属会回写到 `/im/v1/me` 的 `owned_node_ids=["node-1"]`。
- 会话建立：Web IM 发消息后，Gateway 能基于 `conversation_id + user_id + agent_id` 建立本地 session 绑定，并创建 kernel session 与 run_id。
- 消息发送：IM 通过 `/im/v1/conversations/{id}/messages` 创建消息后，能经 `/im/ws/gateway` 下推 `relay.message` 给已连接 Gateway，且 Gateway pipeline 会回发 `assistant:hello from web im`。
- 回执：Gateway 回发 `node.delivery_receipt(sent/completed)` 后，IM 中 `relay_tasks` 状态会推进到 `status=completed`、`receipt_status=completed`，并记录 `receipt_detail=assistant:hello from web im`。
- 状态上报：Gateway 回发 `node.report` 后，IM 侧能记录包含 `run_id/conversation_id/message_id/summary/status` 的 report 快照；当前该信息仍停留在 handler snapshot，不进入用户可见消息流。
- SSE 可见性：实际事件流仍只有 `message.sent`、`message.delivered`，没有 `relay.sent`、`relay.completed` 等回执进度事件。

## 成熟产品视角批判

### 1. 绑定（Binding）
- 现状：链路能跑，但 start/confirm 是纯接口语义，缺少“当前设备是谁、为什么要绑定、绑定后影响哪些 Agent”的前置说明。
- 商业产品差距：成熟产品会在绑定前给出设备名称、节点能力、归属影响范围与风险提示，降低误绑成本。
- 影响：多设备用户在多个节点间切换时，容易对归属结果缺少心智模型。

### 2. 会话建立（Session Establishment）
- 现状：Gateway 能自动建 kernel session，但 IM 用户侧没有可见的“已连接到哪个节点/Agent/会话”的建立反馈。
- 商业产品差距：成熟产品会在消息送达后给出“已连接”“Agent 正在思考”“会话已恢复/已新建”等状态提示。
- 影响：用户无法区分“消息刚发出”“正在路由”“新会话创建较慢”三种阶段。

### 3. 消息发送（Message Sending）
- 现状：HTTP 写消息后，消息历史里马上可见，但这代表的是“IM 已持久化”，不是“Gateway 已接单”。
- 商业产品差距：成熟 IM 会区分本地发送成功、服务端接收、对端接收/已读等多阶段状态。
- 影响：当前 `message.delivered` 事件语义偏乐观，容易让人误判 Agent 已真正收到并开始执行。

### 4. 回执（Receipts）
- 现状：`relay_tasks` 内部状态能推进到 `sent/completed/failed`，但前端 SSE 目前仍只看到 `message.sent` / `message.delivered`。
- 商业产品差距：成熟产品会把接单、执行中、完成、失败反馈映射成可见状态，且与消息气泡/状态条绑定。
- 影响：真实中继状态已经存在，但没有进入用户界面；排障只能靠后端或数据库观察。

### 5. 失败反馈（Failure Feedback）
- 现状：若 `target_node_id` 未连接，HTTP 会直接返回 503；但对已经创建的消息与后续用户动作之间缺少更平滑的失败说明。
- 商业产品差距：成熟产品会把失败反馈落到消息上下文，提供重试、切换节点、检查连接等建议。
- 影响：用户只能看到请求失败，不能在会话上下文内理解失败原因，更缺少自助恢复入口。

### 6. 状态提示（Status Prompts）
- 现状：Heartbeat、node.report、delivery_receipt 都存在协议层语义，但没有统一映射到用户可见状态线。
- 商业产品差距：成熟产品通常会提供明确的节点在线/离线、Agent 忙碌、排队中、处理中、完成等提示。
- 影响：系统虽然具备协议能力，但产品层“感知透明度”不足，用户会觉得 Agent 响应是黑盒。

## 问题清单
1. `message.delivered` 当前更像“消息已入 IM 存储”，不是“已被 Gateway/Agent 真正处理完成”，语义与用户直觉不一致。
2. `node.delivery_receipt` 与 `node.report` 没有桥接到 `/im/v1/conversations/{id}/events` SSE，用户端看不到真实执行进展。
3. 节点断开后 `/im/v1/nodes` 很快回到 `offline`，但会话消息流里没有同步提示“节点已断开/结果来自刚刚完成的运行”。
4. 绑定流程缺少面向用户的节点能力与归属影响提示，设备心智模型弱。
5. 失败反馈停留在 API 错误层，没有消息级失败卡片或可执行建议。
6. `node.report` 目前只适合后端观测，不适合直接支撑产品级摘要/状态提示。

## 后续改进建议
1. 为 conversation SSE 增加 `relay.sent` / `relay.completed` / `relay.failed` 或等价事件，把真实回执映射到消息级状态流。
2. 重新定义 `message.delivered` 语义；若保留当前事件，应补充更准确的 `relay.*` / `agent.*` 阶段事件，避免误导。
3. 为绑定流程补一层“设备确认上下文”，至少包含 node_name、Agent 数量、归属影响说明。
4. 把 `node.report` 结构化为可前端消费的摘要事件，而不是只保留在 WebSocket handler 内存里。
5. 为目标节点未连接、执行失败、回发失败设计会话内可见失败卡片/提示文案，而不是只靠 HTTP 状态码。
6. 引入节点/会话状态提示线：`已发送 -> 已接单 -> 处理中 -> 已完成/失败`，并与真实回执绑定。
