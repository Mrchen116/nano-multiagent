## 基线判断
- 现有实现把 SSE 事件直接写入 `QueryClient` 中的 `conversation detail`。
- 当 `getConversation()` 仍在加载时，多处分支在 `previous === null` 时直接返回 `null`，会把已到达的 SSE 事件丢掉。
- 首次进入已有会话时，REST 历史与 SSE replay 先后顺序不稳定，因此会出现“只显示用户侧 / 只显示 Agent 侧”的前端观感缺陷。

## 进度

### R1 固定 race 缺陷
- Context:
  - 需要先用测试稳定复现，否则无法验证真正修复的是 race，而非偶然 UI 现象。
- Decision:
  - 在 `chat-workspace-page.test.ts` 增加 deferred `getConversation()` 场景，让 SSE 回放先到、历史后到。
- Rationale:
  - 该顺序最接近用户进入已有会话时的真实问题面。
- Evidence:
  - 新增测试：`reconciles replayed agent events that arrive before history loading completes`
  - 该场景验证：REST 历史返回前先收到 `relay.processing`，最终页面仍同时显示用户历史消息与 Agent 进度消息。

### R2 修复 history + SSE 合流
- Context:
  - 仅依赖 Query Cache 原地覆盖无法保证事件先于历史时不丢失。
- Decision:
  - 在 `chat-workspace-page.tsx` 增加统一 helper：`mergeMessages`、`mergeConversationDetail`、`upsertConversationMessage`。
  - `detailQuery` 在 `getConversation()` 返回后，与 Query Cache 中已累积的 SSE 消息做合并，而不是直接覆盖。
  - `message.sent`、`message_created`、`relay.*`、`message.delivered`、`text_delta` 在 `previous` 为空时会先建立 placeholder conversation，再写入消息，避免事件丢失。
  - `upsertMessage()` 改为保留更完整内容与已有附件，避免短 payload 把完整内容回退掉。
- Rationale:
  - 只有把“加载历史”和“实时事件”都视为 message source 再做 deterministic merge，才能彻底消除单边显示。
- Evidence:
  - `src/IM/frontend/src/features/chat/chat-workspace-page.tsx`
  - `src/IM/frontend/src/features/chat/chat-workspace-page.test.ts`
