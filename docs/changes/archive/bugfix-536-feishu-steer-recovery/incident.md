## 澄清记录

- Q1: 聊天进行中，你发出一条新消息时，机器人上一件事即使没能正常继续，期望这条消息如何被对待？
  A(原话): 问题我觉得是为什么上条消息没正常继续，如果是断网什么的停了，那应该当条消息按你说的，正常被接住，继续进行
  Agent 解读: 先诊断上一条未继续的原因；仅在它确实已停止时，将后来已收到的消息作为当前聊天的正常输入继续处理。验收只以用户是否收到该条消息的正常回应、会话是否可继续为准。
- Q2: 上一件事确实中途停下后，你后发的消息应当怎样继续？

  Agent 解读: 恢复后保留前序对话，并把后发消息作为当前工作的补充或调整继续完成；不得把它孤立为新问题处理。
- Q3: 这次发生在飞书；同一套聊天逻辑也服务 Web IM 和其他外部通道。修复范围要不要覆盖所有这些入口？

  Agent 解读: 所有经同一 Gateway 聊天链路进入的入口，都必须保持消息被接住、上下文不断、会话可继续的一致体验。
- Q4: 如果是你主动说“停止当前操作”或“开始新会话”，这次修复要不要保持它们现在的效果——停止就是停止，重开就是不再带旧上下文？

## 现象与复现

在飞书会话 `d195409657d74f0ebc60032d9fee2b10`，Agent 正在处理上一条工作时，用户发出补充消息。该消息没有收到回复；用户随后发送 `？`，该条也显示超时。

本次运行的可复核时间线如下（均为 2026-08-13 CST）：

1. 10:22:33，上一轮完成工具步骤后，自动压缩请求以 249,883 prompt tokens 开始。该 Agent 使用的 `codexOAuth:gpt-5.6-terra` 上下文窗口为 258,400 tokens，默认压缩余量为 20,480 tokens，触发阈值为 237,920 tokens，因此该轮必然进入自动压缩。
2. 10:23，用户在飞书发出补充消息；它被当前会话接收，等待进入下一次模型请求。
3. 压缩期间父会话没有新的 stream event；到 120 秒时 Gateway 以“无新事件”取消旧 run，并将该 Agent 气泡标为失败。
4. 随后的模型请求只含 8,756 prompt tokens，并包含用户补充消息，说明压缩已完成、消息也已进入后续上下文；但 Gateway 已停止该 run 的可见中继，结果没有回到飞书。

稳定复现应缩短 idle 窗口并构造：一轮达到自动压缩阈值 → 用户在压缩期间追加消息 → 压缩或后续请求超过 idle 窗口。修复前会出现旧气泡失败、已接收消息无回复；若内核创建后继 run，Gateway 也不会接管其可见交付。

## 目标状态与验收标准

### Requirement: 聊天中追加的消息在活跃但安静的阶段仍正常继续

#### Scenario: 自动压缩期间追加消息
- **GIVEN** Agent 正在为当前对话整理过长上下文，且用户随后发出补充消息
- **WHEN** 整理过程仍在正常进行
- **THEN** 用户不会看到上一条消息被误报失败
- **AND** 补充消息连同此前上下文进入后续对话，Agent 正常继续完成工作

### Requirement: 真正中断后，已接收的后续消息仍有一次可见的继续结果

#### Scenario: 中断前已接收补充消息
- **GIVEN** Agent 的上一件事确实中途停止，且用户已在停止前发出补充消息
- **WHEN** 系统恢复该会话
- **THEN** 用户在原聊天收到基于原有上下文和补充消息的继续结果
- **AND** 用户不需要重发该补充消息，也不会因它收到超时或重复回复

#### Scenario: 中断后的下一条正常消息
- **GIVEN** 上一件事已经停止且恢复流程已收口
- **WHEN** 用户继续在同一聊天发送消息
- **THEN** Agent 正常接住并回复，会话上下文不丢失

### Requirement: 所有 Gateway 聊天入口体验一致

#### Scenario: 从不同入口继续同一聊天
- **WHEN** 用户经飞书、Web IM 或其他使用同一 Gateway 聊天链路的入口发送上述补充消息
- **THEN** 各入口都满足消息被接住、上下文不断、可继续对话的同一行为

## 范围与非目标

**范围**：所有经 Gateway 进入的普通聊天消息，包括飞书、Web IM 和其他外部 channel；覆盖自动压缩期间的误取消，以及非用户中断后已接收普通消息的继续交付。

**非目标**：不改变精确 `/stop` 的停止语义或精确 `/new` 的重开语义；不把普通自然语言中的“停一下”“重新来”等文字擅自当作控制命令；不以延长或关闭 watchdog 作为绕开方式，真正失去进展的 run 仍必须可被回收。

## 影响范围

所有经过 Gateway 的聊天入口都受影响：飞书首先暴露了问题，Web IM 与其他外部 channel 共享相同的 session run coordinator 和内核 run stream，也可能出现相同的无回复/超时。没有证据表明用户内容或会话历史被删除；影响是已接收消息的可见回复丢失与会话暂时不可用。

## 根因分析（RCA）

根因有两个连续层次。

1. **上一条消息被误判为停住。** `AgentLoop` 在每轮下一次模型调用前先执行自动压缩。自动压缩的 summarizer 通过 sidechain 执行，并特意将该 sidechain 的 `session_event_publisher` 置为 no-op，避免摘要内部消息污染父会话。`bugfix-417` 为工具、主模型等待和权限等待补了 await-bound liveness 心跳，却遗漏了这条同样会等待模型的自动压缩路径。于是压缩正常进行时，父 run 在 Gateway 看来连续 120 秒“无事件”，被错误取消。

2. **取消后，已接收消息没有可见交付 owner。** Gateway 在 active run 上接受补充消息并把它记录为该 run 的 follower。idle 超时后，它立即取消旧 run、reconcile 气泡并把主消息和全部 follower 标为 failed。与此同时，Kernel 的 `RunsRegistry` 按 `bugfix-426` 的异常终止规则会保住未消费 pending message，另起 continuation run；但 Gateway 仍只监听旧 run id，且 `_on_other_event` 对 user origin 的后继事件直接忽略。因此内核“不丢输入”与用户“收到回复”之间断开。

这不是单一实现偏离：

- `bugfix-417` 的 liveness 设计把可合法安静的窗口列为工具、主模型等待、权限等待，漏掉自动压缩 sidechain；已有测试只验证这些已列窗口。
- `bugfix-426` 正确修复了正常路径“工具结束后、下一次模型请求前插话仍由同一 run 消费”，但将非用户终止后的 continuation 只验到 Kernel 队列层，没有验到 Gateway/IM/外部 channel 的可见交付。
- 当前 `test_real_stall_fails_and_releases_next_same_session_turn` 只验证失败**之后**才发的新消息能新建 run；它不覆盖“失败前已经接收的消息”。而 shutdown 测试还把已接收 follower 一律标失败当作当前行为锁定。

必须保持的原始设计意图：正常聊天中，旧 run 仍在工作时的新消息应在下一次模型请求前进入**同一个 run**；不得为了修复异常路径而退化成一条普通消息总要等旧任务结束，或丢失前序上下文。`/stop` 和 `/new` 的显式用户控制语义不属于本事故的恢复路径。

## 修复方向

1. 将自动压缩纳入父 run 的 await-bound liveness：压缩仍然不泄漏内部摘要内容和过程，但其正常进行会刷新父 run 的存活信号；真正卡死时，信号停止，watchdog 仍可回收。
2. 为非用户终止时的已接收消息建立端到端交付接管：Kernel 与 Gateway 明确关联旧 run 和恢复 run，Gateway 不得在恢复结果前把已接收 follower 宣告失败；它必须将恢复后的输出送回原聊天，并抑制旧 run 的迟到输出和重复投递。
3. 增加跨层组合回归，覆盖压缩、用户插话、watchdog、恢复 run、飞书/Web IM 的可见投递与之后继续聊天；保留正常同-run 插话、`/stop`、`/new` 的既有行为。
