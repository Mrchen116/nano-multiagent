# bugfix-647: 长期 Agent 轨迹同步重复读取冷历史

## 原始报告

> 解决生产 Agent 因轨迹同步产生的延迟问题，完成实现、验证、独立代码审查及 PR 提交。
> 避免只在返回值上过滤却仍逐次重读所有冷历史的表面优化；也不要另建庞大缓存框架或牺牲一致性。
> 本次授权范围是修复到提 PR，不包括合并或生产部署。

## 范围与澄清

按已授权范围修复轨迹同步和业务等待；模型审批、公网网络、睡眠策略不在范围。不修改生产 checkout 或服务。Full：运行时读取与 PA 业务等待两个模块需要独立回归验证。文档与代码均保存在本次隔离分支，遵守本次仅提 PR 的交付边界。

## 现象与复现

调查基线 8fa10d3；当前 236a4698 仍含相同路径。调查报告 `/tmp/nano-latency-20261023/findings.md` 中 Air 有 386/403 个直接子会话、约 387/342 MiB 压缩历史，task_graph 七次中位 45.9 秒。此为墙钟工具时间，不能直接认定为同步 CPU 时间；睡眠和审批独立。实验使用合成历史，禁止提交生产日志与会话内容。

## 根因分析

integration 的 session.descendants 忽略 cursors，先调用原生 listDescendants（逐子 observeSession 读目录），再 observeSession 读全部自有事件。原生 prepared cache 默认仅五条，长期父会话的两轮遍历反复淘汰与恢复冷历史。PA reconcile 同时承担根会话证据与子会话展示；task_graph/send_message 等待同一 drain，业务因此等待不相关历史。已有测试只验证完整返回和重启，没有保护无变化重复同步成本。

## Requirements

### Requirement: 未变化的冷历史不反复拖慢当前工作

#### Scenario: 长期父会话连续调用工具
- **GIVEN** 父会话已有数百个冷子会话
- **WHEN** 重复同步并查询任务或发送消息
- **THEN** 不重复读取、解压和投影全部未变化的子历史，业务不等待无关子历史同步
- **AND** 发送前重验、授权来源、Inbox 消费及持久化语义保留

### Requirement: 子轨迹保持完整与可恢复

#### Scenario: 新增、续写与重启
- **WHEN** 新子会话或孙会话出现、已有子会话续写、进程重启
- **THEN** 工作视图最终反映正确父子归属、工具调用与结果、耗时、模型和结束状态，不丢失游标之前的展示上下文
- **AND** 读取或持久化失败不推进成功游标，后续同步可恢复

## 修复方向

用 DSH 公开 API 的轻量版本检查复用子目录与游标，变化会话才读取事件；根会话证据与子轨迹同步独立排队。不改变审批或投递规则，不扩大上游缓存保留完整继承日志。
