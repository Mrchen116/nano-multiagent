# bugfix-669: Work 保留原始工具执行事实

## 原始报告

用户原话：

> 帮我按照快修模式解决#420。

来源：https://github.com/Mrchen116/nano-multiagent/issues/420；以下为收尾时读取的 issue 原文（历史“尚未实施”说明保留，不代表本次状态）：

```markdown
## 影响区域

个人助手与任务路由（PA）、IM 服务端、Work 工具执行展示。

## 实际现象

真实 PA 会话中，已完成的文件读取和 Bash 调用，在后续上下文裁剪后被展示为持续执行十几分钟。本次逐条核对的 7 条异常记录，都可以由“裁剪时刻减去原始工具开始时刻”精确解释。

这会误导用户对工具性能和任务卡顿原因的判断。原始执行已正常结束；这些记录不能作为工具实际执行缓慢的证据。

## 预期结果

工具耗时应由原始执行开始和完成事件确定。模型上下文中对历史结果的裁剪或替换，不应再次被当作工具执行完成，也不应覆盖用户可见的原始执行记录。

## 复现步骤与已核实证据

1. 运行长会话，产生较大的 read/Bash 输出，记录工具完成后的耗时。
2. 继续会话，直到上下文压力触发 DSH `compaction/prune`。
3. DSH 为历史工具结果追加同一 `toolCallId` 的 `tool/result`，携带 `surfaceOp: { op: 'replace', startSeq, endSeq }`，指向原始结果。
4. Nano 将该替换事件再次投影为 `tool_end`，Work 中对应调用的耗时被覆盖。

2026-10-27 的一条实际读取记录如下（北京时间，毫秒时间戳来自原生日志）：

| 事件 | seq | 时间 | 毫秒时间戳 |
| --- | --- | --- | --- |
| 原始 tool/call | 2653 | 19:55:28.951 | 1793102128951 |
| 原始 tool/result | 2656 | 19:55:29.049 | 1793102129049 |
| compaction/prune | 3078 | 20:14:01.282 | 1793103241282 |
| 替换 tool/result | 3079 | 20:14:01.282 | 1793103241282 |

替换结果携带 `surfaceOp: { op: 'replace', startSeq: 2656, endSeq: 2656 }`、`sourceEventSeqs: [2656]`。

- 正确耗时：`1793102129049 - 1793102128951 = 98 ms`。
- Work 保存的错误耗时：`1793103241282 - 1793102128951 = 1112331 ms`，即 18 分 32.331 秒。
- 另一个读取从实际 `67 ms` 变为 `1112235 ms`；一个 Bash 调用从实际 `5645 ms` 变为 `1196431 ms`。

原始完成事件及时间仍存在，没有被 DSH 改写。直接触发条件是上下文裁剪产生的 replacement，无须发生重启或恢复。

## 根因与责任边界

这是 Nano 的事件适配／展示投影问题，不是 DSH 工具执行或时间戳错误。

DSH 将不可变事件日志与模型可见上下文区分：原始事件保留执行事实，后续 replacement 调整模型下一次看到的历史内容。替换事件的时间表示替换发生时间。DSH 的 surface 实现明确说明，replacement copies 用于模型上下文，用户历史应使用 append-origin 事件。

Nano 当前链路忽略了该区别：

1. `packages/personal-assistant/src/presentation.ts:35-49` 对所有 `tool/result` 按同一 toolCallId 找原始调用，并使用 `event.time - call.time` 计算耗时，没有区分 `surfaceOp`。
2. `packages/personal-assistant/src/work-projection.ts:21-22` 将该结果转换成 `tool_end`。
3. `apps/im-server/src/work.ts:348-376` 按调用 ID 合并记录，后来的 `tool_end` 覆盖先前正确的 duration_ms 和展示 payload。
4. 前端展示收到的耗时，错误在展示数据进入前端之前已产生。

建议在本仓已有事件适配／投影边界正确区分执行事实与模型上下文替换。无需 patch DSH，也不应通过耗时上限、改成 0 或前端格式化掩盖问题；遵守现有包依赖边界。

## 环境与版本

- 观察时间：2026-10-27。
- 环境：macOS，隔离 worktree PA 真实运行及 Work 数据快照。
- 本次代码核查 checkout：`codex/pa-authorization-continuity`，HEAD `d76a7c6cd6629d671c64fd0bfbf884ff3a9f7143`。这是核查时版本，不据此推定原始运行的精确版本。
- 原始运行版本未在本次归因中独立确认；根因由原生日志、Work 保存值和当前代码链路共同核实。

## 修复验证

- 回归用例覆盖：同一调用依次出现开始、正常完成、compaction/prune、replacement tool/result；最终耗时仍为原始完成减去开始（上述样例为 98 ms），不产生第二次执行完成效果。
- 用户可见的原始执行结果不会因模型上下文裁剪而被替换；模型侧裁剪后的上下文仍正常生效。
- 在相同事件序列的实时消费和历史重放中，得到一致的工具执行记录。
- 保持普通成功／失败工具调用的展示行为正确。
- 真实长会话触发一次工具输出裁剪，确认已有工具耗时不跳增。

本 issue 仅记录已核实的缺陷与验收条件，尚未实施修复。

```

## 澄清与用户确认

- 用户亲自打开预览并询问裁剪次数；核对后澄清为“一批裁剪六条工具输出”，不是六轮摘要压缩；没有摘要压缩或换窗。
- 用户查看解释后原话“那提pr？”，同意进入 PR 交付。用户查看了预览；六文件自动验证由 Agent 执行，不记录为用户亲自重跑。
- 交付限提交、push、PR；不合并、不部署、不主动关闭 issue。

## 现象与复现

已完成工具结果在后续模型上下文裁剪后被重复当作完成记录，耗时与 payload 被覆盖。原始日志仍保留真实完成时间；实时消费即可触发，不依赖重启。

## 影响范围与非目标

影响 Work 对主/子执行事实的呈现与回看；不改变工具执行、模型裁剪策略或 DSH。已有中心历史污染不做回填迁移，本修复阻止新投影覆盖；不新增原生轨迹裁剪节点。

## 根因分析

投影把“模型可见历史替换”与“原始执行完成”混为一种事实；共享 RuntimeEvent 类型也未显式表达已被透传的顶层 surfaceOp，原有测试只覆盖普通结果，因此没有守住重复同 callId、不同时间语义的边界。

## 修复方向与验收

在工具展示投影边界忽略 replacement 完成效果，保留原始执行结果；原生事件和模型上下文不变。自动回归覆盖成功/失败、显式 append/旧缺字段、实时/持久重放；真实六文件压力测试及浏览器刷新验证见 [as-built design](design.md)。
