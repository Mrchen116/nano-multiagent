# bugfix-685 全局消息搜索事后设计

本文在实现后形成。基线为 `7e79e9b79`，代码和回归用例在 `8af1a2b44`。

## 数据流

1. 每次请求从登录主体的当前空间出发。按成员索引和公开群的部分索引取得候选 ID，保留仍有读取资格的解散群。对可能产生观察权的私聊，从属于该用户的 Agent 或 PA 绑定反查会话并成批读取成员。
2. 单会话详情、事件读者和全局搜索共享双 Agent 或 PA 与真人私聊的观察判定。双 Agent 仍按同空间及 owner 判断，PA 对真人私聊还需要 PA 当前能访问该空间。批量路径在一次请求内复用同一 PA 在同一空间的判断。
3. 共享消息查询收到可读 ID 集合。指定分类时，先按成员中的 Agent 数量判断类别，再按既有字面匹配、时间和消息 ID 排序与续页。`limit + 1` 的末项仅用于判断是否还有下一页。
4. 路由对真正返回的消息读取详情，同页同会话只装配一次。会话名、发送者、可读提及和片段沿用原投影。Agent Work 继续传自己的 targets，Web 权限只用于登录用户搜索。

## 数据与回滚

SQLite 在正常打开数据库时按现有 schema 创建三个索引，分别支持由用户查会话、仅扫描公开群、由可读会话查消息。无一次性迁移或历史数据回填。回退应用代码即可恢复旧查询，已有索引兼容。查询成本仍取决于该用户可读的会话、候选观察关系和要匹配的文本量。

## 验证

`apps/im-server/tests/conversation-search.test.ts` 通过真实路由和隔离内存 SQLite 验证，登录主体由 fixture 注入。用同一构造在修复前后对照。

| 基线装配的会话详情 | 10 | 10 |
| 修复后装配的会话详情 | 0 | 0 |

- 四种分类与全部分类逐一对照。覆盖相同时间戳时按 ID 排序、逐条翻页到末页，以及不同时间戳的最近优先排序。
- 覆盖可读提及、外部发送者回退、观察者会话名、公开空群、全 Agent 公开群和已解散的公开群历史。
- 覆盖已加入的私群、其他人的私群、跨个人空间、仅有公司管理员身份、两 Agent 的 owner、PA 与他人的私聊、三人私聊无观察权、PA 失效与公司资格撤销。既有用例还验证翻页时移除成员，以及搜索不推进未读。
- 用户授权自动对照后交付 PR。以上证据来自服务端测试，未进行用户亲测、生产流量测量或桌面端重新验收。
