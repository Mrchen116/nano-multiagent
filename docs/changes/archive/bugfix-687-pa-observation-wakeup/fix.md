# bugfix-687 修复 PA 重新启用后的重复空唤醒

## 原始报告

> 修复 PA 停用再启用后，旧生命周期 pending 观察每次节点心跳都会唤醒，实际读取却为空。实测 rev1 遗留一项、重新启用到 rev3，连续三次心跳唤醒三次、读取均零项。看 apps/im-server/src/{gateway,personal-agent,agent-lifecycle}.ts。优先对齐心跳候选与读取资格的代次条件，保留历史记录和当前代次暂时失败后的重试。验证同一 PA 新事件仍正常送达，其他主体和真实提醒不被误过滤，产品生命周期和授权语义不变。

## 现象与复现

在 IM 内存数据库中插入一条主人参与的聊天消息，观察表产生一条第 1 代 pending 事件。调用停用、报告已停止、重新启用，把同一 PA 推进到第 3 代。依次向 Gateway 送入三次在线心跳，每次统计中心发往节点的观察唤醒调用，再以该 PA 的绑定读取观察。

| 中心版本 | 三次心跳各自的唤醒数 | 三次读取各自的条数 |
| --- | --- | --- |
| 修前 `7e79e9b79` | 1、1、1 | 0、0、0 |
| 修后 `35d689c05` | 0、0、0 | 0、0、0 |

## 根因与修复

心跳重试由 `ed73cb9b8` 引入，用来接回暂时处理失败的观察。[feat-657](../feat-657-agent-disable-switch/design.md) 在 `701b6caa6` 为观察写入和读取增加了代次屏障。心跳仍按绑定和队列状态找候选。重新启用时绑定和旧记录都保留，因此旧事件足以触发唤醒，却永远不能被新代次读取。

`35d689c05` 将候选限定为该节点上具有当前启用代次待处理事件的绑定。完整条件与兼容边界见 [事后设计](design.md)。

## 验证

- 同一条长期回归用例先红后绿，可用 `pnpm exec vitest run apps/im-server/tests/personal-agent.test.ts -t 'enabled generation'` 复查。它也验证第 3 代新消息可读、标为 received 后仍会重试、处理完毕后停发。通过 PA 事件报告入口实际创建的安全提醒可单独触发心跳唤醒并读回对应 incident。最后查表仍有第 1 代 pending 行。
- 双主体隔离探针在同一个数据库建立两个 owner、两个节点、两个 PA，共享一条聊天来源，将两条观察的代次字段移除以模拟旧数据。第一个 PA 的第 3 代心跳无唤醒，第二个 PA 的第 1 代心跳只唤醒自身并读回该消息，使用第一主体的凭据读取第二绑定被拒。该一次性探针与 PA、生命周期回归一起运行，26 项通过。
- 以上为开发者在隔离 IM 服务组件中执行的自动化验证；发送边界被截获。未进行生产、真实节点、外部渠道或用户亲测。
