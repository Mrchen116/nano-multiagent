# IM conversations-messages Specification (delta for bugfix-697)

## MODIFIED Requirements

### Requirement: IM 托管聊天附件按会话成员关系读取

普通新上传和 Agent 图片均是受保护聊天资源；URL 不授予读取资格。IM 自身托管的旧公开上传在部署时按文档一次性转换其原消息关联与引用，新版本只提供目标格式的资源服务。

#### Scenario: 普通图片与文件上传
- **GIVEN** 用户已参与一个聊天
- **WHEN** 用户上传普通图片或文件并发送消息
- **THEN** 具有当前会话读取资格者可正常预览和下载；公开群对有效公司成员可读，私密群和普通私聊仅成员可读，恰含两个同空间 Agent 的私聊也允许双方有效 owner 按统一观察资格读取，未登录或无读取资格者持相同 URL 不能读取；全局 Work 可见不改变来源附件资格。

#### Scenario: 支持的图片编码与声明不一致
- **GIVEN** 上传请求声明为现有支持的图片类型，内容具有 PNG、JPEG、GIF 或 WebP 的受支持签名
- **WHEN** 实际图片编码与声明类型不一致
- **THEN** 按探测到的真实编码保存附件类型，并将文件名后缀校正为对应格式，正常预览和下载不要求用户手工改名或转码
- **AND** 未知图片内容和不支持的声明类型仍被拒绝，不放宽既有访问、大小、容量和限流边界

#### Scenario: 旧公开附件经部署转换后继续回看
- **GIVEN** 旧消息保存了本 IM 的公开上传 URL
- **WHEN** 部署 agent 按迁移文档转换历史引用并升级，有读取资格与无读取资格者分别打开同一历史附件
- **THEN** 有资格者从原聊天的新受保护引用读取同一字节，无资格者无法读取；旧关联文件不丢失，没有消息关联的历史文件不再公开。
- **AND** 单独保存的旧 `/im/uploads` URL 不再提供文件、别名或重定向服务。

#### Scenario: 引用与 fork 不产生访问旁路
- **GIVEN** 用户持有自己无权读取的聊天附件 URL
- **WHEN** 尝试将该 URL 关联到自己的会话
- **THEN** 不会因此取得附件访问权；有来源访问权的合法 fork 则保留独立附件关联，删除源聊天不破坏 fork 回看。

### Requirement: 上传与实时资源具有累计边界

#### Scenario: 上传累计超额与正常文件
- **WHEN** 用户或机器上传合法附件
- **THEN** 同时受单文件、账号累计和服务累计限制；并发及断流不能绕过配额或永久占用未完成预留，超额给出可恢复反馈。
- **AND** 合法会话成员可继续上传、发送和回看限额内附件；非成员不能借附件 ID/URL 绕过会话权限。

#### Scenario: 当前聊天草稿中的附件失败反馈
- **WHEN** 附件因单文件大小、格式、累计空间、限流或网络问题上传失败
- **THEN** 在当前聊天草稿区对应文件显示原因及移除/适用的重试动作，正文及其他已上传文件保留，不伪装成已发送消息。
- **AND** 不支持的格式与无法识别的图片内容分别说明，不将所有图片拒绝统一解释为格式不支持。
- **AND** 存在失败文件时不静默忽略文件发送；可明确选择仅发送文字并保留全部未发送附件，或移除失败项/重试成功后一起发送。限流按 Retry-After 等待；消息发送失败也保留待发内容，确认发送成功后才清理本次提交项。

#### Scenario: 容量告警由管理员处理
- **WHEN** 账号累计或服务累计容量触顶导致附件上传被拒绝
- **THEN** 普通聊天用户仅见“暂时无法上传附件”，正常文字消息继续可发，不要求用户清理附件或联系管理员。
- **AND** 管理员在现有“策略”页的存储状态区查看容量告警并处理；普通成员不可读取告警中的容量明细和相关账号。容量恢复后上传恢复，不新增附件管理或计费平台。

#### Scenario: 超大请求与慢实时客户端
- **WHEN** 请求体、WS 帧、连接数或待发送缓冲超过配置上限
- **THEN** 有界拒绝、限流或断开，不持续无限堆积；正常客户端重连沿用既有重放语义并重新验证资格。
