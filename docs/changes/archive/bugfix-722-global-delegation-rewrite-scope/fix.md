## 原始问题与本轮目标

用户报告：

主 Agent 曾把自己对截图的判断、重做方案和操作安排混入用户要求，同时没有交付执行者可读的原图。后续评测又暴露出交接夹带 IM 编号、复述默认限制、过早制定详细执行计划等问题。

本轮目标是让主 Agent 正确发现和委派工作、转发后续补充、处理子 Agent 的问题并向用户交付，同时保留其在现有授权内作决定的能力。

## 当前接受的分工

| 环节 | 当前规则 |
| --- | --- |
| 主 Agent 定位 | 负责理解、授权内判断、派工、接新消息、核对成果和用户沟通；日常问答与小事直接处理。 |
| 子 Agent 定位 | 完整事项交给后台可接续执行者，自主调查、选技术方案、执行、验证并组织必要助手。普通子 Agent 默认使用当前工作区及仓库指令，不继承主 Agent 的聊天和记忆，不能查询产品聊天、读取主 Inbox、公开发产品消息或与同级直接通信，只向父级汇报。 |
| 初次派工 | 照引相关用户原话，补齐必要背景和实际可读材料；交代目标、任务特有约束及交付物。用户陈述、主 Agent 的待验证判断和授权内决定分别标明，不将自己的判断冒充用户要求，不提前增设要求、详细执行计划或验收清单。 |
| 交接简洁性 | IM 会话、用户、消息 ID 留在主 Agent 的路由记录里；省略默认工作区、仓库指令和工具限制。 |
| 用户后续消息 | 相关补充、更正和答复回到原执行者，继续照引原话并提供可读附件；独立交付目标另派执行者，话题相近不自动合并。 |
| 子 Agent 提问 | 主 Agent 核对原话、现有授权和具体缺口；授权已覆盖的决定自行处理，缺少用户决定或新增授权时向用户提出具体问题，答复回到原执行者。 |
| 成果与进展 | 主 Agent 核对结果是否回应目标及证据是否可用，具体缺口交回执行者，不重做调查；普通进展内部消化，必要问题与可用成果送到正确会话，不重复交付。 |
| 主动推进 | 依据既有职责和授权主动发起或继续工作，不能把观察、外部资料或自己的判断变成新增用户授权。 |

## 已接受的限制

1. **原话、附件和续派正确性仍依赖模型遵守 Prompt。** 宿主尚未自动保证主 Agent 每次都传对原话、传齐材料和选对执行者；不能把写入规则等同于机制保证。
2. **主 Agent 的授权判断仍需要观察。** 分离原话与自己的决定有助于检查，但不是对越权扩写的确定性拦截；也不能为避免越权而把所有常规决定都交回用户。
3. **图片引用仍有理解成本。** 运行时可读图片可能使用无扩展名哈希路径；可读取不代表引用足够直观，已另记 [issue #477](https://github.com/Mrchen116/nano-multiagent/issues/477)。本轮不改附件存储或引用机制。

以上边界随当前方案一并接受，不通过继续追加针对单条 case 的 Prompt 来追求不存在的完整保证。

## 后续何时重新审视

出现下列具体事实时，保留用户原话、附件引用、主 Agent 的派工／续派正文及子 Agent 回报，再沿对应链路复审：

- 主 Agent 再次漏传原话或图片、夹带自定要求，或把自己的判断说成用户要求。
- 后续补充未到原执行者，造成重复派工、执行旧要求或相关工作丢失。
- 子 Agent 提出确需用户决定的问题却未传给用户，或已有授权内的常规决定反复要求用户确认。
- 在换窗、恢复或多个事项并行时，出现无法依靠现有工作记录稳定恢复的归属问题。
- Task／消息绑定机制落地，或者子 Agent 的上下文、工作区、通信能力及返回模式发生变化。

复审先区分 Prompt 遵循、工具／宿主机制和评测脚本的问题。以具体轨迹决定修 Prompt、调整机制或新增回归 case；没有新的事实时保留当前版本，不为了对齐参考项目而继续堆规则。
