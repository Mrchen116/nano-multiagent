# bugfix-741 Agent 停用和永久删除反馈

## 原始报告

> 为啥要有一个停止未确认。从商业产品设计来看，要么开着要么关了，为啥要搞个这个增加用户理解负担

用户认可「正在关闭…」「电脑离线，联网后会继续关闭」「关闭还没完成，重试」是操作反馈，并要求在测试服务实际试用。

试用后指出「关闭」的对象不明确。操作改为「停用 Agent」和「启用 Agent」，状态和过程提示统一使用「停用」。

## 现象与根因

Web 和 iOS 把节点的停止观察状态用作标题或徽标。用户要结合「停止未确认」和技术错误才能判断是否可以继续。重试请求被接受后，IM 仍返回之前的失败状态，直到节点再次上报。

## 修复

Agent 保留启用和已停用两种稳定状态。停用进度、离线提示和失败重试集中在详情操作处。确认停用后开放符合条件的永久删除。在线重试把同一次停用标为正在进行，继续等待节点确认。

工作区默认保留。能确认专属时允许单独勾选删除；无法确认时，确认框说明会保留文件。永久删除请求受理后，Web 以删除回执展示进度，确认成功后返回 Agent 列表。

## 验收

用隔离测试服务从 Web 实际关闭 Agent。观察关闭确认和永久删除入口，并验证执行电脑离线时的等待、重连后完成关闭及关闭失败的反馈。通过 iOS 编译与生命周期契约测试核对原生客户端。

### 本地预览结果

- Web 实测普通 Agent 正常关闭、打开删除确认并取消。重新开启后，旧版本缓存的删除入口立即消失。
- 暂停隔离的 DSH 子进程触发真正的关闭超时。页面显示关闭还没完成和重试。恢复子进程后，从页面重试进入已关闭。
- 停止隔离 Gateway 后从页面关闭 Global Agent。页面提示电脑离线，删除入口隐藏。Gateway 重连后自动确认关闭并开放删除入口。
- Web 相关 41 项测试和 Node、IM 相关 18 项测试通过。iOS Simulator 编译通过，本次定向测试过滤器未选中用例。
- 预览叠加在 PR #492 的节点修复上，用户试用后要求合并。
- 用户实测发现删除完成后详情页短暂显示列表加载失败。隔离服务真实删除后已能直接返回列表。回归覆盖生命周期先返回 404、联系人随后消失、最后收到删除回执的顺序；受理后持续显示删除进度，完成后返回列表并移除缓存中的旧条目。
