# bugfix-742 大量工作记录导致 Agent 删除收尾超时

## 原始报告

> 又摊上问题了呀

[关联排查](codex://threads/01a18c12-8a97-7783-a6c8-30aca57c6e05)记录，生产的已停用 Agent 在清掉执行文件后，两次卡在中心登记删除回执。74,397 条工作记录只登记了 9,750 条，界面显示清理失败。

## 现象 / 复现

一个节点的同一工作日志有约 196,000 条上传回执。删除会把目标 Agent 的工作记录按 250 条分批交给中心，每批需要在 10 秒内确认。重试沿用原删除请求，重新发送已登记的批次。使用合成数据复现大日志下处理单批的开销。

## 根因

中心同时按工作日志内的序号和事件 ID 查找可能冲突的上传回执，但查询只能用到现有索引中的节点和日志列。检查每条记录时都要扫描同一日志的大量回执，单批可能超过响应期限。即使已经登记的批次也要做同样的查找。

## 本次审查安排

验证同等规模下的批次确认、已有回执的重试与中心最终确认。保留序号、事件 ID、节点和所有者校验，仍清理可能存在的暂存数据，保留同节点其他 Agent 的工作记录和原工作区选择。没有对外契约变化。

## 修复

中心分别按日志序号和事件 ID 使用索引查找上传回执。启动时在旧库上创建缺少的事件 ID 索引。节点仍可使用现有协议重放已确认批次，中心仍校验每条回执并回收暂存文件。

## 验证

- 在同一台 Mac 使用独立磁盘 SQLite 与真实 IM 登记和最终确认逻辑。合成同一日志的 196,000 条上传回执与投影，其中 74,397 条属于删除目标。修复前前三批分别耗时 4,372、4,341、4,463 毫秒。修复后相同三批分别为 48、36、37 毫秒，298 批中最慢 67 毫秒。
- 从缺少新索引的已有数据库重启 IM，服务初始化耗时 221 毫秒。登记全部批次耗时约 9.4 秒，重放最早的 39 批耗时 423 毫秒，中心最终清理耗时 148 毫秒。目标成为已删除，同节点其他 Agent 的 121,603 条记录和上传回执均保留。计时不含真实网络或节点文件清理，合成投影不含生产消息和大正文。
- 36 项定向测试通过，覆盖按两个维度拒绝身份冲突、批次冲突回滚、活跃暂存上传、后续共享序号同步和删除状态回执。IM 类型检查通过。
