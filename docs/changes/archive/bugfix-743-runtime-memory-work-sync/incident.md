# bugfix-743：限制历史驻留内存和 Work 补传压力

## 原始报告

接手交办：“让历史审计数据增长不导致执行进程无界常驻；让Work同步真正按必要增量/有界批次传输，正确处理慢消费者，不再反复序列化整个历史。保留审计证据、Work完整呈现、游标/逻辑turn配对、重连恢复、取消关闭与权限边界，不能靠删用户历史、静默丢事件或仅抬高heap上限掩盖问题。”

原始只读取证：2026-11-09，`~/.codex/reports/nano-throughput-20261109/runtime-root-causes.md`（含样本、隔离复现和原始崩溃报告路径）。本 unit 不实现未完成子任务的持久续跑，不部署或重启生产。

## 现象与影响

17:55:40 和 18:29:59（上海时间）生产 DSH 执行进程发生 V8 heap OOM。同一进程承载多个 Agent；第二次崩溃打断了三个独立执行中的子任务。锁屏在 18:38:31，晚于崩溃；未观察到相关睡眠。重启后的空闲进程（35 个 Agent）堆仍约 2.02 GB，stdout/stderr 队列为空。

## 根因与证据边界

- 生产 `68e65a880` / DSH `0.2.1-alpha.1` 的 domain 在 open 时把所有记录读入常驻 Map。投影缓存 6,128 条、约 5.61 亿序列化字符；其中 3,210 个审批会话仅首条标题输入已约 5.12 亿字符。Reviewer 释放不会清除这些派生记录。工具展示另有约 1.75 亿字符。字符数不是 retained heap 字节数。复核 `origin/develop` 的相关生产实现未变。
- Work 的子会话游标只决定是否返回历史；有变化仍发送完整 own 历史，Node 收到后才裁剪。三个样本原始历史约 3.05 亿字符，主要是重复请求快照。隔离探针验证仅增 1 条却返回 100 条，且阻塞的输出仍持续排队。
- 崩溃栈在 V8 字符串展开和 stream 写出，与以上机制吻合；没有死亡进程 heap snapshot 或最终 RPC 帧追踪，无法唯一确定最后的触发帧。
- 同期一个公开 `send_message` 慢样本在 IM 入库前后均有长间隔。正常发送和处理回执时，Gateway 会分别读取并解析同一会话的完整本地事件账本，仅为定位一条工具调用。按会话和调用 ID 建索引后，一次定点读取供发送和回执复用。测量及内部 Agent 投递的取证边界见 [发信探针](M1-runtime-work/evidence/publication-latency.md)。

## 验收

### Requirement: 长期积累的历史仍可检查

#### Scenario: 大量历史后启动或继续运行

- **WHEN** 节点启动或继续累积历史，用户查询已完成 Work、原生轨迹或保留的审批证据
- **THEN** 历史仍能按现有权限读取，执行进程不因这些历史副本的累计体量常驻对应正文。

### Requirement: 主子 Work 从缺口继续补齐

#### Scenario: 长历史追加、慢消费或中断重连

- **WHEN** 父子执行追加记录、消费暂时变慢或进程重连后继续补齐
- **THEN** 工作记录按真实顺序补齐，主子归属、跨批次工具与逻辑轮配对、实际状态、完整正文及用量与原轨迹一致，不漏报或重复显示；未补齐的位置不标为完成。
- **AND** 历史补传不会无限堆积待发正文；实时控制、取消关闭和权限判断沿用现有边界。
