# bugfix-744：进程重启后让主 Agent 在下一轮看到子 Agent 中断

## 原始报告

> 我觉得不需要真的恢复子agent，只需要保证子agent挂了这个信息能传到主agent，他就能决策恢复

> 我觉得不是唤醒主agent，而是有新的触发的时候唤醒，这这是一条排队消息放着。理解不

## 现象 / 复现

共享 DSH 进程异常退出并重启后，Global 主 Agent 能继续使用原会话，Work 能读回中断的子执行，主 Agent 下一次因正常输入运行时却看不到这些子执行的中断通知。11 月 9 日生产现场的 714、716、720 均有未封口的子轮次，恢复后的 Work 已补齐显示，原父会话空闲。

重启时，把有持久证据的直接委派中断作为系统消息放进 Global 主会话的待处理队列。只有正常触发才能启动下一轮，届时主 Agent 一并读取通知并自行决定如何处理原委派。重复重启只保留同一中断的一份通知。正常结束、显式停止和缺少中断证据的会话不能被报告为进程中断。

## 根因

DSH 在在线子 Agent 结算时向在线直接父级发送 `subagent-settled`。进程级退出跳过该路径。SessionQuery 冷读会为未封口的轮次合成中断事件，Work 恢复只将事实同步到记录；Global Inbox 恢复以已存在的 Inbox 输入为依据，子执行中断没有进入主会话。应保留原生正常结算、Work 冷读和 Global 已有触发语义。

## 本次审查安排

| 必须回答的问题 | 能力 | 验证方法与已有证据 |
|---|---|---|
| 重启只排队，重启重复去重，原生触发时首次模型请求可读 | 代码审查、Agent Context | 锁定 DSH 的隔离子进程强杀重启，检查持久队列和模型实际输入 |

## 修复

启动恢复沿受信 Global 主会话的原生目录检查直属子执行。最新轮次以 DSH `interrupted` 结束时，用子会话 ID 和结束序号记一条系统通知。查询按直属子会话逐个观察，后续重启复用可验证的中断元数据；升级后的首次检查需读取缺少该元数据的已有子日志。

待交付通知单独持久化，正常步骤通过准入时才附加到模型输入。原生会话里有可持久确认的接收记录后，队列保留该子会话的去重位置。通知不占用原生 Inbox，不参与心跳和更新的忙碌判断，也不算 Task 自动执行的外部触发。永久删除主会话时清除对应队列。

恢复通知沿用 DSH 原生结算的异常结束与无结语文案，结束原因填入 `interrupted`。DSH 的格式化函数是私有实现，Nano 按原文构造内容并保留恢复通知的系统来源。

## 验证

锁定 DSH 的子进程夹具实际派出可继续子 Agent，等待请求写入原生日志后强杀进程。重启后磁盘队列中只有一条通知，子执行仍是未恢复状态。再次重启后原队列无重复，模型无请求，更新准备仍能通过。正常心跳通过空闲检查后，主 Agent 的首个请求收到子 ID 和中断状态，子 Agent 没有运行。消费后再次强杀和重启，新输入不重复摄取通知。正常失败和主动取消未被报告为进程中断。
