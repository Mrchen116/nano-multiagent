# bugfix-758 Dreaming Work 阶段标题

## 原始报告

[GitHub Issue #474](https://github.com/Mrchen116/nano-multiagent/issues/474)

> 同一轮整理可能出现两条都叫「Dreaming · 自动整理记忆」的记录。提取和整合的标题一样，尤其两条都显示失败时，看起来像同一个工具调用启动了两轮整理。
>
> 在 Work 列表和执行轨迹里给记录标出真实阶段。例如显示「Dreaming · 提取任务摘要」和「Dreaming · 整合长期记忆」。从已有阶段数据区分提取（extract）与整合（consolidate），每条继续展示自身状态和执行入口。

本轮请求原话「那做一下？微小的需求」。

## 现象与验收

在 Web IM 的 Work 查看一轮包含任务摘要提取与长期记忆整合的 Dreaming。两条记录按真实阶段分别显示标题。提取失败时，即使整合也失败，两个标题仍可区分，并保留各自的状态和轨迹入口。

## 根因

feat-676 将提取和整合保存为独立运行，Work 用会话链接保留各自的只读轨迹入口。运行已持久化 `stage`，但 `Dreaming.reviews()` 投影丢弃该字段，`KnowledgeUpdates` 将所有 Dreaming 链接写成同一标题。已同步的 Work 链接使用不可变事件，修复应保留会话身份、状态和原有回执。

## 审查安排

独立代码审查核对阶段来源、历史记录更新、状态和轨迹身份。用受控模型触发两阶段失败，验证运行时输出与 Work 链路。

## 修复

Dreaming 从已保存的阶段产生标题，供 Work 和新建的原生轨迹使用。Work 用独立链接事件更新已有会话标题。原生查看器读取运行保存的阶段名，历史轨迹继续使用原来保存的阶段措辞。

提取失败时，整合的 native 会话可能已经建立，虽然整合模型尚未调用。两个真实会话继续分别展示失败状态并提供入口。

## 验证

- Work 恢复用例在旧实现上复现同名，原生查看器的双失败回归也在旧渲染逻辑上复现同名。
- 隔离 IM 通过真实设备 WebSocket 和用户 HTTP 接口验证两条历史失败记录更新为两个阶段标题。列表只有原来的两个会话，状态均为失败，轨迹准备请求分别发往正确会话。
- Node 24.22.1 下，Dreaming 运行时、PA Work 投影、原生轨迹导航共 17 项通过。受控 DSH 运行复现了提取失败后两个会话均为 failed，原生轨迹查询保留两个不同的会话 ID、状态和阶段标题。
- 工作区构建、类型检查、iOS Runtime、文档检查、Python 135 项及 Ruff 检查通过。本机首次 Web 全量 1,155 通过、24 失败，IM 补充测试 16 通过、3 超时。并行检查存在多处等待超时，以 PR CI 的干净运行核对全量结果。
