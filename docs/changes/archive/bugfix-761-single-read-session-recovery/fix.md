## 原始报告

> 那怎么解决？我现在真正这台机子上就禅日常使用，而且才用了没多少天。后面一台机子要跑10个agent，并且长达一年的历史，不就完蛋了

> ok，先把恢复时同一份历史加载两次解决，开始做

本次处理已绑定主会话恢复时的重复读取，覆盖普通和全局 Agent、PA 以及 Schedule 对主会话的接入。按字节约束通用冷查询缓存、改变活跃历史表示，以及普通子会话独立恢复时的原生父子链核验，属于独立问题。

## 现象 / 复现

Air 的 DSH 在 Agent 空闲时约占 1,453 MiB，其中已用 V8 堆约 1,132 MiB。部署备份的隔离对照中，冷读 5 份历史后，再独立读取并准备其中 4 份主会话，回收临时对象后堆增加约 321 MiB。同一份历史的两次读取产生独立事件对象。

## 根因

Nano 在激活主会话前通过 DSH 冷观察读取正文，检查会话归属，并为全局主会话核验子执行中断。观察释放后，解压事件仍可能保留在 DSH 冷查询缓存。随后 DSH 的原生 Agent 恢复重新读取正文，建立活跃会话。Schedule 直接进入主会话时也会经过前置冷观察。

恢复必须校验原绑定、保持用户停用边界，在全局主会话接单前持久记录可信直属子会话中断证据。同一中断只通知一次；检查失败时不能发布可接单的 Agent。历史原文和 Work 仍按原规则可读。

## 本次审查安排

| 必须回答的问题 | 能力 | 验证方法 |
|---|---|---|
| 主会话接续是否去掉前置正文读取 | 性能、独立代码审查 | 真实 DSH 重启后，从普通入口和 Schedule 恢复，统计指定主会话的持久正文读取次数 |
| 身份、停用和全局中断通知是否保持 | 独立代码与 Agent Context 审查 | 真实 DSH 恢复已中断的直属子会话证据，核对主 Agent 看到的通知与重启去重，复用停用及恢复回归 |

## 修复

前置校验使用 DSH 的持久化会话头。原生恢复加载正文后，在发布 Agent 之前再次核对绑定身份，并从已加载会话的原生直属子目录取证和记录中断通知。缺少完整证据时，Agent 发布仍然失败；已证实的通知留待重试。Schedule 直接唤醒已绑定主会话时复用同一入口。

## 验证

真实 DSH 的 Global Relay、Schedule 唤醒和 Task 恢复三个场景中，激活主会话读取正文的次数均由两次降到一次。通知仍随恢复后的首次正常模型请求交付，重启去重通过。具体版本、检查结果与本机超时记录见 [审查与验证](review.md)。
