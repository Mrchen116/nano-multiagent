# bugfix-763: iOS 聊天连续体验

## 原始报告

Test User 按顺序报告：

1. “ios版本现在有个问题，页面老是弹connecting retry哪些，闪来闪去。体验不好，你给我说怎么改体验才好”
2. “一个商用IM，短暂重连连图标都不显示吧。不单单是聊天里，chats页也在闪。而且可能因为有生成的UI需要渲染，导致点进聊天内不是到最底下。你帮我把这些周边问题统一看下，告诉我每一个体验不好的地方，以及改法。”
3. “还有就是按右下角的那个跳到底部的按钮，有时候他不是跳到真正的底部，有时候点了没反应卡一下。”
4. “我想问下，当前在聊天内的消息，是不是已经存到本地库了。还是说要网络请求？是因为网络请求才卡卡的吗，大滚动都感觉卡卡的，不知道是网络请求的问题还是UI卡片的问题”
5. “好，现在是不是可以改了？开个unit改”。

## 澄清记录

- 用户选择：“从 Chats 重进就到最新”。该选择对应已展示的推荐：“从 Chats 重新打开聊天到最新；聊天内看详情返回或切后台回来保留当前阅读位置。”
- Agent 解读（不冒充用户原话）：短重连不显示任何文字、图标或 toast；连接展示与内容可用性分离；跟随最新与读历史是不同意图；主动点击最新后持续跟随，直到用户主动上翻。持续不可用、发送失败、登录失效仍按各自对象如实反馈。
- 本次建立新 unit。此前只读调查结束；本次不重开旧 unit，不部署、不合并、不操作用户手机。未决的体验阈值由设计作工程选择并以原生验证校正，不声称用户指定了秒数。

## 现象与复现

用户观察来自其 iOS 使用；手机安装 SHA 未取得，不能声称已复现原设备的帧停顿。前轮只读报告是调查线索，不是 App 内实测证据。本轮已核实 `origin/develop` 基线 `45babb2b49e314754c6ca390f4ca3da61fe9f107`，相关 current 契约为 `docs/specs/im/ios-client.md`。

- 打开 Chats 或会话、前后台切换/重连：Connecting / Retrying 随状态变化出现消失，打断阅读。现实现连接提示是条件插入的列表行/会话顶端内容行。
- 从 Chats 打开已缓存会话、末尾有异步高度卡片/图片、或点击最新：可能不到真实尾部。现实现仅监听消息数/末条正文、执行一次滚动；没有显式初始布局定位，动态高度未接入持续意图。
- 历史分页尚未完成时点击最新：已有迟到的历史锚点定位可以覆盖新操作。这是可由代码确定的竞争通路，用户现场是否经过此路径未知。
- 大幅滚动有卡顿感：用户已报告，但帧停顿、网络等待、异步长高、错位的贡献尚无测量结论。必须用同规模纯文字/卡片原生样本核实，不把 SQLite 或 WebKit 名称当作因果结论。

## 影响范围

iOS Chats、会话进入/返回、消息阅读、生成 UI/媒体增高、键盘与输入区变化、历史分页和回到最新。修复应保持本地优先、内容权限撤销、发送幂等、私人卡片状态与编辑语义。没有数据损坏证据。

不包含 Web 重设计、永久保存全部聊天历史、受保护媒体磁盘缓存、离线绕过卡片授权、模型质量或服务端架构改造。性能工作限定在这条实际阅读/跳转路径；仅修复经测量支持的代价，不做全仓优化或承诺真机无任何掉帧。

## 根因分析（RCA）

已在上述基线重新读取源码：

1. `ChatPhases.swift` 的连接文字直接映射原始连接状态；`ChatListView.swift`、`ConversationView.swift` 条件插拔内容行，没有稳定展示层。同类传输错误还写入 `listError` / `errors` 并重复显示。正常前台重连因此被当作需即时告知用户的内容变化。
2. `ChatStore.run()` 在 HTTP sync 成功后、WebSocket 建立前就置 online 并重置重试次数。HTTP 成功但 WS 失败的条件下，会有短周期 online/offline 摆动。这不是用户设备网络根因的已证实结论，但其状态/退避顺序是代码事实。
3. `ConversationView` 把几何接近底部同时当作『要跟随最新』，异步增高又会改变此几何值；没有把用户意图与布局结果分开。初始缓存数量不变没有明确初始定位；卡片测高 (`InteractiveWebView` / 随包 ResizeObserver) 和图片加载改高不进入定位仲裁。
4. 更早消息加载后无条件恢复 top、清理后的阅读恢复 center，与新点击最新没有先后仲裁。发出滚动调用不等于用户结果已到达；现有验证也没有覆盖这条异步连续旅程。
5. 性能因果仍未知：正文读取已是本地 SQLite 优先、UI 使用内存投影；跳最新 action 本身不等待网络。Markdown/日期/列表重算、可见已读回包、WebView/图片挂载是待比较的候选，不写成已确认瓶颈。

## 修复方向与验收

采用 Full：多个关联机制跨连接、会话定位与动态渲染，需要独立原生连续旅程与性能对照；不能用单个按钮补丁或静态检查完成。

### Requirement: 短暂重连不打断聊天阅读

#### Scenario: Chats 与聊天的短暂重连
- **GIVEN** 页面已经有可读内容
- **WHEN** 正常重连或短暂不可用随后恢复
- **THEN** 不显示连接文字、图标或 toast，不在内容内插入/移除连接行，列表、阅读位置、输入与键盘不被重建。

#### Scenario: 持续不可用与首次无缓存
- **WHEN** 连接持续不可用，或首次读取没有本地内容且失败
- **THEN** 在相应页面一处稳定、低干扰的反馈如实说明尚未更新/读取，并提供可理解的恢复入口；不反复轮播连接状态，不把未读取当成空会话。
- **AND** 确实未完成的发送和明确登录失效保留各自反馈，不被静默策略隐藏；离线内容不标为已同步。

### Requirement: 打开与回到最新表达可靠的持续意图

#### Scenario: 从 Chats 打开或重新打开
- **WHEN** 用户从 Chats 进入含本地消息的会话，包括本次已打开过且缓存未改变的会话
- **THEN** 默认显示最新消息尾部，不依赖网络条数变化才落底；不会为跳转读取全部历史。

#### Scenario: 动态内容与有效视口变化
- **GIVEN** 用户在跟随最新
- **WHEN** 流式正文、生成 UI、图片、键盘或输入区随后改变可用尺寸
- **THEN** 最新内容尾部仍在有效视口内，不要求反复点击最新，也不等待整段远程内容齐备才可阅读正文。

#### Scenario: 主动点击最新优先于旧定位
- **GIVEN** 用户正在读历史，且旧历史加载或恢复尚未结束
- **WHEN** 点击最新
- **THEN** 到达已取得的最新消息尾部并持续跟随，迟到的旧定位不能将其拉回；按钮有即时可辨认的响应，不制造长途滚动动画。

### Requirement: 用户读历史时不被异步更新抢位

#### Scenario: 主动上翻与详情/前后台返回
- **GIVEN** 用户主动上翻阅读历史
- **WHEN** 新消息、卡片/图片高度变化、历史分页、详情返回或前后台校正发生
- **THEN** 当前阅读上下文保持，不被自动拉到最新；回到最新保留明确入口。用户主动上翻也能终止尚未完成的跟随。
- **AND** 只有退出到 Chats 后再重新打开才按『到最新』处理，不新增跨会话持久阅读位置需求。

### Requirement: 用真实原生证据闭环卡顿与回归

#### Scenario: 相同历史规模的纯文字与卡片对照
- **WHEN** 在同一专用模拟器、相同合成历史规模中执行大幅滚动和跳最新，比较基线与修复版的冷暖进入
- **THEN** 记录可比较的点击/稳定尾部结果、原生滚动性能或主线程代价及相关请求时序，区分位置失效与实际停顿；只将有证据的代价作为优化结论。
- **AND** 以真实原生入口的连续操作和画面验证连接静默、动态尾部、历史不抢位；构建/单测不能替代体验结果。模拟器结果不冒充用户手机版本已核实或真机性能通过。
