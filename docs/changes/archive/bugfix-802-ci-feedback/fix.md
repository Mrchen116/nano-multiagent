# bugfix-802 提前报告 PR 归档状态并定位慢测试

用户在两周 CI 调查中选定独立的归档检查和两条测试的阶段计时，要求“快修模式走”。

## 现象与根因

[bugfix-511](../bugfix-511-unit-archive-ci-guard/incident.md) 负责保证 unit 分支交付时目录已唯一归档。提交 `aeccebccb8` 把检查放在后端测试之后，脚本只检查目录，却需要等构建和全套回归结束才能看到结果。两周内 35 次运行触发归档失败，其中 33 次仅此项失败。

[同提交重跑](https://github.com/Mrchen116/nano-multiagent/actions/runs/45853696252)中，插件测试从 120 秒超时变为约 80 秒通过，记忆维护用例从 30 秒超时变为约 20 秒通过。已有输出给出整个用例耗时，难以区分安装、重启和重复调用。基线已通过 `d1ee78b51` 调整超时预算。单个阶段或 runner 变慢的具体原因仍需基于日志判断。

## 修复和验收

归档检查在 PR 打开或更新时独立执行，沿用原脚本对分支及目录的识别规则。其他 job 并行运行。两条回归在结束时输出按执行顺序排列的阶段名和毫秒数。超时时最后一项对应当时正在执行的阶段。

核对独立 job 与归档脚本的契约测试、两条原始用例和外层超时探针。通过 PR 检查页观察反馈顺序。用户核对独立 job 的报错时间、本地回归与超时输出后确认符合预期，本单元已归档。

## 后续提速

用户要求在计时调查基础上缩短等待所有 PR 检查完成的时间。[初次验收](https://github.com/Mrchen116/nano-multiagent/actions/runs/45970278548)的后端回归占 9 分 49 秒，iOS 模拟器测试和设备归档依次占 8 分 47 秒和 5 分 14 秒。后续快修采用 Vitest 两路分片，并行执行 iOS 的两种构建模式。比较 GitHub 的 job 起止时间、整轮完成时间和测试文件覆盖。并行方案会重复少量环境准备，结果受 runner 排队和负载影响。
