# bugfix-809 桌面通知隐私与系统投递

## Relations

- [桌面通知与身份隔离契约](../../../specs/im/desktop-client.md)
- [feat-790 桌面宿主](../feat-790-desktop-client/review.md)

## 原始报告

> 宿主通知中心最近64条和 notifications.jsonl 消息预览跨登出/切账号/切服务残留，生产中存了标题正文。核实消费方，清理旧数据并避免继续留存无必要的内容，验证 A→B 和重启。macOS notifications.rs:1144 同时触发应用横幅和系统通知，验证后修双路和系统通知偏好问题，确保单次投递、尊重用户禁用和隐私，保留权限内的点击导航和现有 Windows 正常通知行为，不新增绕过系统选择的替代投递。

## 现象 / 复现

基线 `1bdc4646c` 的两个通知分类出口都调用 `record`，将标题、正文、路由写入桌面用户目录并复制进最近 64 条队列。仓内运行代码没有日志读者。只有受 reload token 保护的内部列表和按 ID 激活接口读取队列。两个平台真实原生点击入口直接使用系统通知携带的路由。日志跨重启保留，进程队列只在重启时销毁。

## 根因

feat-790 同时实现了后台系统投递、点击唤醒和内部诊断。诊断数据依附于进程和安装目录，账号及服务切换只更新 daemon session。提交 `810ff89c8` 的 macOS 路径同时调用独立置顶窗口和系统投递。系统无法将独立窗口纳入通知禁用、专注模式及隐藏预览设置。

## 本次审查安排

检查诊断副本的所有消费者、旧文件清理、身份切换前后的点击和投递，以及 macOS 和 Windows 的原生路径。用隔离宿主和合成消息回归，区分原生运行测试、系统设置和屏幕实测。

## 修复

- 移除宿主最近通知列表、按历史 ID 激活接口、日志写入及自绘弹窗。升级启动时仅删除原桌面用户目录的 `notifications.jsonl`。文件缺失可正常启动，删除失败会返回可诊断的启动错误。
- macOS 仅向系统通知中心投递。Windows 保留已有 AUMID、toast 和协议激活，系统投递失败时结束该次提醒。两端在服务或账号变化时撤回系统历史。启动时独立核对原生历史的归属，Windows 遇到无法按标签单独移除的旧 toast 时清除该应用的历史。
- 原生通知携带账号及服务的作用域和应用内路径。常驻与冷启动沿同一条身份校验路径导航，旧版无作用域通知无法触发导航。AppKit 的冷启动通知与常驻点击分别接入宿主。
- 会话切换同步清除待导航路由、未读计数和会话摘要。迟到的通知、会话更新和旧凭据刷新结果不能覆盖新身份。

## 验证

- 修前在 macOS 的独立测试 bundle 中送入一条合成 WebSocket 消息，实测宿主弹窗计数 1、系统提交计数 1。登出 A、登录 B 后，内部通知列表仍能读到 A 的正文。再次启动后队列为空，文件仍有正文。修后 macOS 26.5.2 arm64 的 `cargo test --locked --manifest-path apps/desktop/Cargo.toml --lib` 10/10 通过，含静音、回放、话题、审批路由及新加的跨身份回归。
- `6f68075ff` 的真实宿主进程连接两个回环测试 IM 服务。A 收到 WebSocket 消息后发生实际未读更新。验证 A 的通知可定位话题，切至 B、登出、切至另一服务的同名 B 后旧链接均失效，B 在当前服务的 Work 链接正常。多次终止并重启宿主，验证旧版无作用域链接与跨服务链接失效，同服务 B 的有效冷启动链接仍可用。旧文件被删除，新宿主目录内未发现合成标题或正文。
