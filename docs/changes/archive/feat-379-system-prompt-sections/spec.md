## 原始需求

> `/Users/czj/Repos/opensource-hub/claude-code/笔记/system_prompt.md` cc的system prompt是结构化的，一个个block的。有必须的，有每个特性自己控制的一段。这样很好管理。现在我们的个人助手的system prompt是这样的吗

> 对，要重构。但是重构成什么形式呢，我想内核肯定控制一些段，有固定的，有feature开关决定的。产品层也控制一些段，也有固定，有feature开关决定，有用户自定义。

> 这更像是feat，重构是一部分，但是关键是整个system prompt体系的构建

补充背景（Agent 调研，非用户原话）：现状 system prompt 是一整个 f-string 模板（`prompts.py:20` `PERSONAL_ASSISTANT_SYSTEM_PROMPT`）+ 4 个 `<RUNTIME_FILL:*>` 占位符 replace + 尾部按 toolset 条件追加几段常量（MEMORY_GUIDANCE / SKILLS_GUIDANCE / memory_block / BACKGROUND_TASK_PROMPT_BLOCK）。per-agent 自定义是整串 `session.system_prompt` 全量覆盖。对照 CC：CC 的 system prompt 是有序的命名 section 列表，每段一个 `string | null` 渲染函数，按 feature 门控自己决定出不出现。

## 澄清记录

- Q1: 这次变更定 feat 还是 refactor？
  A(原话): 这更像是feat，重构是一部分，但是关键是整个system prompt体系的构建
  Agent 解读: 核心价值是建立一套可分层、可门控、可被用户局部定制的 system prompt 段式体系，而非单纯重组现有文案。

- Q2: 段式化后 per-agent 的用户自定义怎么落？（选项：① 开关 + 自定义段；② 逐段覆盖 map；③ 保留整串覆盖）
  A(原话/选择): 「开关 + 自定义段(推荐)」。附选择时的预览：
  > [✓] 启用 Heartbeat 段
  > [✓] 启用 Skills 自进化段
  > [ ] 启用 Group 回复策略段
  >
  > 自定义补充(注入 pa.user_custom):
  > ┌────────────────────────┐
  > │ 你是我的私人法律顾问,    │
  > │ 回答时优先引用条款...    │
  > └────────────────────────┘
  > → 内核固定段 + 勾选的产品段 + 这段文本
  Agent 解读: 用户在 IM 里①勾选启用哪些可选段（feature 开关）；②填一段自由文本注入 `pa.user_custom`。内核固定段用户改不了。整串覆盖作为高级逃生舱可保留（待 Q 确认）。

- Q3: 适用范围——只个人助手，还是内核机制 + 两个产品（个人助手 + local_coding）一起？
  A(原话): 对
  Agent 解读: 内核段式机制 + 个人助手 + local_coding 都迁；"用户勾特性 + 自定义段"的用户面只在个人助手（IM）落地，coding CLI 只享内核段式化，不暴露勾选界面。

- Q4: 存量 agent 的整串自定义 prompt 怎么迁移？
  A(原话): 处于开发中。不考虑后向兼容
  Agent 解读: 段式是唯一机制，不为存量保留整串覆盖路径，无需迁移存量配置。

- Q5: 哪些段对用户暴露成可勾开关？内核 feature 段也给用户勾吗？
  A(原话): 内核feature，也要给用户勾吧，勾完更新到配置文件中。heartbeat，group 回复策略这种才是不用用户勾，因为必须要有的。不然群聊中的行为没法固定，heartbeat的行为没法固定。所以无论是内核还是产品，都应该有固定按场景必加的，有给用户勾的。
  Agent 解读: 区分轴不是"内核 vs 产品"，而是"固定按场景必加" vs "用户可勾"，且内核与产品两层都各含这两类。固定按场景必加（group 回复策略、heartbeat 等）由场景自动决定、用户不可关，以保证该场景行为确定；用户可勾（memory/skills 自进化指引等能力性特性）由用户开关、写回配置文件持久化。

- Q6: 用户勾的是 prompt 段还是特性本身？默认值怎么定？
  A(原话): 我明确下，我指的勾是值勾对应特性，比如，skills 自进化特性勾了，系统提示词就加。每个特性都有默认加不加的默认值了。不用重复澄清
  Agent 解读: 用户勾的是「特性」，特性开启则其对应 system prompt 段自动加入、关闭则移除。每个特性自带默认开/关值（新建 agent 按默认呈现）。没有独立的"prompt 段勾选"，段是特性的衍生结果。

- Q7: 段式化的同时，是否要把 core 段内容对齐 CC 的通用规范？
  A(原话): 以及现在我们的system prompt包含哪些内容？和CC一致的特性，或者一些常规的prompt应该跟他一致
  Agent 解读: 不只重组结构，还要让内核通用段（harness 不变量类）内容与 CC 真实文案对齐——补 `# Executing actions with care`（风险操作先确认）、`# Tone and style`（file_path:line_number / owner/repo#123 / emoji 按需 / tool 前不加冒号）、补全 `# System`（prompt-injection flag、被拒工具调用处理、system-reminder 说明、自动压缩说明）、修正工具使用（专用工具优先 + 并行调用）。不照搬 CC 的软件工程框架段 / CC 产品专属段（/help、/issue）/ 我们没有的特性门控段。属"与 CC 一致的通用特性"范畴，coding 专属内容归 coding_cli。

- Q8: agent 配置页要不要"完整系统提示词预览"？必做还是可选？
  A(原话): 折叠预览 是必做
  Agent 解读: 配置页必须提供可展开的只读预览，显示当前特性开关 + 自定义补充拼出的完整系统提示词（基线/单聊视角；群聊、记忆快照等运行时段不在预览内）；切换开关 / 改自定义文本时预览随之更新。

- Q9: 特性↔工具联动的三个方向哪些要？(a) 勾特性→自动加工具；(b) 移除工具→自动取消特性；(c) 取消特性→是否自动移除工具？
  A(原话): OK.
  Agent 解读: 采纳推荐——(a) 要、(b) 要、(c) 不要。即维持"特性开 ⇒ 其 requires_tool 必在 allowlist"这条不变量（靠 a+b 双向守住），但取消特性不回收工具（工具是更底层能力，用户可能为别的用途保留它，自动删会误伤）。

- Q10: 联动是"前端即时"还是"保存时校正"？
  A(原话): 对。
  Agent 解读: 采纳"前端即时联动"——勾特性时 memory 工具的勾立刻出现在 allowlist 区、取消工具时特性开关立刻取消，都在本地 draft 即时反映，点保存才一起落库；后端 PATCH 仍做一次一致性兜底，避免落库出现"特性开着但工具缺"的矛盾态。

- Q11: "可达性" AC 怎么界定"算可达"？
  A(原话): 新建 agent → 打开记忆自进化开关 → (Q1 的联动)memory 工具自动变绿 → 保存 → 对话中该特性行为生效
  Agent 解读: 以"从零可达"为口径——从一个全新建的 agent 出发，每个用户可勾特性都能在配置页被启用并最终生效，全程无需用户预先手动准备任何工具，不存在"开关灰着点不动"或"开了但工具不在所以段不出现"的死角。reviewer 须用全新 agent 验，不得用预置了工具的 agent（5 轮 review 漏掉缺陷 A 正因把"带 memory 工具的 agent"当成前提）。

- Q12: 新建 agent 页的预览口径？
  A(原话): 新建页的「完整系统提示词预览」必须能加载,且不依赖一个已存在的 agent
  Agent 解读: 新建页预览必须能加载，按当前 draft（特性 + 自定义补充 + 默认工具集）实时拼出提示词，不能因为 agent 尚未创建（现用 `__preview__` 占位 id）就 404 / 显示"无法加载预览"。把"新建时 agent 尚不存在"这一态正式纳入验收。

## 用户场景

配置 agent 的人（IM 中的 agent owner / 管理员）面对一个个 agent，希望按用途塑造它们的"人设与能力边界"，而塑造的载体就是 system prompt。今天他只能编辑一整串模板，改动哪一行都得对着一大坨文本，且每个 agent 各写各的、内核约束和产品规则混在用户文案里，难管难复用。

**场景 1 — 按用途裁剪能力指引。** 管理员新建一个"只读资料、不沉淀"的轻量问答 agent，把 "skills 自进化"特性关掉；又建一个会自己攒技能的助理，把它开上。每拨一个特性开关，该特性对应的行为指引就自动进/出这个 agent 的 system prompt，存回配置文件，重启 IM / Gateway 后保持。管理员不必再手抠文案。

**场景 2 — 注入私人定制人设。** 管理员给某 agent 填一段自定义补充（"你是我的私人法律顾问，回答优先引用条款"）。这段文本作为该 agent 专属段，和内核固定段、产品固定段、已开启的特性段一起拼成它完整的 system prompt。其它 agent 不受这段影响。

**场景 3 — 场景行为不可被关（确定性）。** 当某 agent 进入群聊，群聊回复策略指引必然在它的 system prompt 中；配置了 heartbeat 的 agent，heartbeat 行为指引必然在场。管理员无法关掉这些"场景必加"段——正因为关不掉，群聊与 heartbeat 的行为才能被固定、可预期。

**场景 4 — coding CLI 保持现状（回归基线）。** coding CLI 的 system prompt 同样由内核段式机制拼成，但 CLI 没有 IM 那种 per-agent 特性勾选界面，按默认特性集运行。对 CLI 用户而言，重构前后行为应当一致，无新增可观察变化。

**场景 5 — 特性与依赖工具的联动（从零可达）。** 管理员新建一个 agent，想让它会自己整理记忆，于是在配置页勾上「记忆自进化」。勾的一刻，该特性依赖的 memory 工具立刻在工具 allowlist 区变绿（自动加入）——管理员不必先去想"哦我得先把 memory 工具加上"。反过来，若管理员把 memory 工具从 allowlist 取消，「记忆自进化」开关也随即取消勾选，因为缺了工具这个特性无从谈起。这些变化在配置页即时可见，保存后落库。但取消「记忆自进化」本身不会把 memory 工具收回——工具是更底层的能力，管理员可能为别的用途保留它。整条路径不存在"开关点不动"或"开了却不生效"的死角：任何一个用户可勾特性，从一个全新 agent 出发都能被启用并最终在对话中生效。

**场景 6 — 新建 agent 时也能预览。** 管理员还在新建 agent 页（agent 尚未创建），边勾特性、边填自定义补充，展开「完整系统提示词预览」就能看到按当前选择拼出的提示词——而不是因为 agent 还不存在就显示"无法加载预览"。预览在新建页和已有 agent 的配置页表现一致。

## 验收标准

- [ ] 在 IM agent 配置里，每个"用户可勾"特性都有开关，新建 agent 时按各特性预置的默认值呈现（开/关）。
- [ ] 切换某可勾特性并保存后，重启 IM / Gateway，该 agent 的开关状态保持不变。
- [ ] 关闭某能力性特性（如 memory / skills 自进化）后，该 agent 在对话中不再表现该特性引导的行为；重新开启后恢复表现。
- [ ] 给某 agent 填写自定义补充文本并保存后，该 agent 表现出该文本描述的人设 / 约束，其它 agent 不受影响。
- [ ] 进入群聊的 agent 始终遵循群聊回复策略，配置了 heartbeat 的 agent 始终按 heartbeat 行为运行——这些行为无法通过 agent 配置关闭。
- [ ] coding CLI 的 agent 行为与重构前一致，无可观察变化。
- [ ] agent 在不可逆 / 影响他人的操作（发消息、删文件、git push 等）前会先与用户确认（对齐 CC「谨慎执行操作」规范）。
- [ ] agent 引用代码时用 `file_path:line_number`、引用 GitHub issue/PR 时用 `owner/repo#123`、非用户要求不滥用 emoji（对齐 CC 通用格式规范）。
- [ ] agent 配置页有可展开的只读「完整系统提示词预览」，显示当前特性 + 自定义补充拼出的提示词；切换特性开关或改自定义文本后预览随之更新。
- [ ] 勾选某个依赖工具的特性（如记忆自进化）后，该工具立即在 allowlist 区被勾上（变绿）；从 allowlist 取消该工具后，该特性开关随即取消勾选——这些变化在配置页即时可见，保存后保持。
- [ ] 取消某特性的勾选，不会把它依赖的工具从 allowlist 移除（工具保留）。
- [ ] 从一个全新建的 agent 出发，每个用户可勾特性都能被启用并最终在对话中生效，无需用户预先手动添加任何工具；不存在开关点不动、或开了却不生效的特性。
- [ ] 在新建 agent 页（agent 尚未创建）展开「完整系统提示词预览」能正常加载，按当前勾选的特性 + 自定义补充拼出提示词，不报"无法加载预览"。

## 范围与非目标

- 在范围：
  - 内核 system prompt 段式组装机制（分层归属：内核段 / 产品段；门控类型：固定无条件 / 固定按场景必加 / 用户可勾特性）。
  - 个人助手产品段迁移到段式 + IM 的「特性开关 + 自定义补充段」用户面（开关写回配置文件持久化）。
  - 特性↔依赖工具的前端即时联动（勾特性自动加工具 / 移除工具自动取消特性），与"从零可达"——每个可勾特性在全新 agent 上都能启用并生效。
  - 新建 agent 页的「完整系统提示词预览」可加载（不依赖已存在的 agent）。
  - local_coding 产品段迁移到段式（仅内核机制层面）。
  - 内核通用段内容对齐 CC 真实规范（谨慎执行操作 / 工具使用 / Tone & style / System 行为约束）。
- 非目标：
  - 后向兼容 / 存量 agent 整串 prompt 迁移（开发中，不考虑）。
  - 保留"整串 system_prompt 全量覆盖"作为用户面功能（废弃）。
  - coding CLI 的 per-agent 特性勾选界面（CLI 走默认特性集）。
