- Q2: v1 关键路径清单是否就锁定 issue 列的 7 条（发消息→回复 / bash 前台超时 / bash 后台通知 / subagent / /stop / cron / heartbeat）？

  Agent 解读: 7 条数量不变，但把路径 1 从「echo 式秒回」升级为「agent 先做真实工具调用、再回复」——理由是带工具调用的回复才是 agent 最常用旅程，能覆盖工具调用主循环这条最高频接缝（裸文本回复绕过了它）。其余 6 条沿用 Q2 表格定义。

- Q3: 「关键路径清单 + 归属」里「归属」指向谁，清单承载什么硬作用？（推荐：单一权威 catalog，每条登记四列「用户旅程 / 守护测试 / 归属子系统(包·契约层) / 引入 unit」；「归属」=所属产品子系统而非人名；硬纪律=新增关键特性必须登记一行 + 配一条 e2e，每条路径都必须有能跑的守护测试。）
  A(原话): 群聊也很关键，也需要有个关键路径
  Agent 解读: 用户未对「归属=子系统 + 四列 catalog + 登记纪律」提出异议，视为采纳（无反对）；同时追加一条关键路径——群聊。群聊考验的是单聊不存在的接缝：多成员消息广播 + @ 定向唤醒被点名的 agent + 未被点名的成员不抢话。故 v1 清单从 7 条增至 8 条。

- Q4: 群聊这条关键路径怎么定义最有代表性，清单是否锁 8 条？（推荐：双 agent 群 + 人定向 @A，验广播 / 定向唤醒 / B 不抢话。）
  A(原话): 群聊不单单要测试人能正确定向@，还要验证agent能定向@agent。
  Agent 解读: 群聊路径必须覆盖**两段定向 @**：①人 @ agent（人定向唤醒 agent）②agent @ agent（agent 在群里定向点名另一个 agent 并把它唤醒起来应答）——后者是多 agent 协作（feat-397 agent-team）的核心闭环，是这条路径的重点。完整链路：用户 @A → A 应答并在群里 @B → B 因被 A 点名而在群里应答。v1 清单仍为 8 条。

- Q5: 通读长青契约层后，对照已选 8 条，是否补充契约层已声明、关键、且只有端到端才暴露的路径？（推荐：补 A 权限审批 approve/deny、B 进程重启后会话续接、C 经 IM 创建 agent 并落地，其余断线重连/压缩恢复/附件/provider 切换/节点看板入 backlog；catalog 用「v1 必保活 + 已知缺口 backlog」两段式。）
  A(原话): 好，都收
  Agent 解读: A、B、C 三条全部纳入 v1，v1 关键路径清单从 8 增至 **11 条**。catalog 采两段式（v1 必保活=有守护测试；已知缺口 backlog=登记在册但暂无 e2e）。其余契约层路径（断线重连补发、上下文压缩恢复、附件透传、provider 切换、节点上下线看板）落入 backlog 段，诚实暴露「暂无 e2e 兜底」。

## 用户场景

这套 e2e 服务于一个开发者（本项目维护者）的核心焦虑：**产品功能越堆越多，关键用户旅程越来越多，改一处代码时单测全绿、心里很安，可真把进程起起来端到端一跑，某条用户链路其实已经断了——而且断了没人发现，直到某天真用户撞上。** #117（subagent 跨事件循环崩溃）就是活例：子 agent 这个核心特性完全不可用，仓库里却没有任何自动化拦住它，因为现有真 LLM e2e 全是「进程内拼装 runtime/组件」，恰好绕开了真正会崩的那段——进程编排、事件循环、IM↔Gateway 网络中继。

所以这次要建的，是一张**真正经真 Gateway 进程的端到端安全网**。它把自己完全当成一个真实 IM 用户：用 `scripts/e2e-up.sh` 起真 IM + 真 Gateway 进程（真子进程，不是进程内 new 一个对象）+ 真 LLM proxy，然后只通过 IM 的对外 HTTP/SSE 接口发消息、读回复/状态，断言只看「用户在 IM 上到底能不能观察到预期结果」。任何只有真起进程、真走网络中继才暴露的崩裂，都会在这里被拦下。

它平时不跑（真 LLM 烧 token），但**想测时一条命令全跑**，覆盖产品的关键用户旅程。开发者改完一处会牵动核心链路的代码，跑一遍这套，就知道有没有把某条用户路径端到端搞崩。

配套还有一份**单一权威的「关键路径清单」（catalog）**，把「哪些用户旅程必须保活、各由哪个 e2e 测试守护、归属哪个子系统、由哪个 unit 引入」一处对账，并显式登记「哪些关键路径目前还没有 e2e 兜底」。它补的是「关键基础功能坏了无人发现」的根：新增一个关键特性时，必须在清单登记一行并配一条 e2e；清单里每条「必保活」路径都必须有能跑的守护测试，缺口在 backlog 段一目了然。

**v1 必保活的 11 条关键用户旅程**（每条括号内是用户在 IM 上能观察到的成功信号）：

1. **工具调用后回复**——发一条需要 agent 调工具才能答的消息（如读文件/跑命令再汇总），收到带正确结果的回复（agent 最常用旅程，覆盖工具调用主循环）。
2. **bash 前台超时**——让 agent 跑一个会超时的前台 bash，session 不卡死、用户最终仍收到一条回复（工具徽标按超时收口）。
3. **bash 后台通知**——agent 把耗时 bash 丢后台，作业完成后用户**再**收到一条带结果的跟进消息。
4. **subagent**——agent 派一个前台子 agent，回复里带回子 agent 的产出；单个子 agent 失败被隔离、不拖垮常驻进程。
5. **/stop**——对正在跑的 run 发 `/stop`，运行被中止、状态可见为已停。
6. **cron**——到点的定时任务自动推一条消息到 IM 对话。
7. **heartbeat**——心跳在有可行动内容时主动冒泡一条消息（无内容时安静跳过）。
8. **群聊双向定向 @**——群里用户 `@A` 让 A 去 `@B` 办事：用户先看到 A 的应答且 A 定向 @了 B，接着看到 B 因被 A 点名而应答（人→agent、agent→agent 两段定向唤醒），未被点名者不抢话。
9. **权限审批 approve/deny**——agent 要调需许可的工具，用户在 IM 收到等待批准提示；批准则 run 继续并产出结果，拒绝则该工具不执行且 run 据此收口。
10. **进程重启后会话续接**——发消息建立上下文后**重启 Gateway 进程**，再发一条消息，agent 仍记得重启前的上文。
11. **经 IM 创建 agent 并落地可聊**——在 IM 配置中心新建一个 agent，它在节点落地 workspace 并上线，随后能跟它聊出回复。

## 验收标准

> 本 unit 的「用户」有两类：跑这套 e2e 的**开发者**（套件级 Requirement）、以及被守护旅程里的 **IM 端用户**（每条路径级 Requirement，Scenario 写 IM 端可观察的产品行为，由对应 e2e 黑盒断言）。

### Requirement: 一条命令按需全跑关键路径 e2e，平时不跑

#### Scenario: 默认测试运行不触发真 LLM e2e
- **GIVEN** 未设置 e2e 运行开关（env 关闭）
- **WHEN** 开发者跑常规测试（如 `pytest -m "not e2e"` 或默认收集）
- **THEN** 这套关键路径 e2e 全部被跳过，不消耗 LLM token、不依赖本地运行时

#### Scenario: 一条命令跑全部关键路径
- **GIVEN** 本地 LLM proxy 可用、设置了 e2e 运行开关
- **WHEN** 开发者执行那一条约定命令
- **THEN** 11 条关键路径 e2e 经真 IM + 真 Gateway 进程 + 真 LLM 依次跑完，每条给出 pass/fail
- **AND** 起停全栈与端口隔离自动完成，无需开发者手工配 IM/Gateway/端口

#### Scenario: 时间驱动路径可作为可单独跳过的子集
- **WHEN** 开发者只想跑非时间驱动的路径
- **THEN** cron / heartbeat 这类慢且时间驱动的路径可被单独筛掉，其余照常跑

### Requirement: 单一权威的关键路径清单 catalog 可对账

#### Scenario: 每条必保活路径都能对账到守护测试与归属
- **WHEN** 开发者打开关键路径 catalog 文档
- **THEN** 看到 11 条 v1 必保活路径，每条登记「用户旅程 / 守护它的 e2e 测试 / 归属子系统 / 引入 unit」四项，路径与测试一一对应

#### Scenario: 已知缺口在 backlog 段诚实登记
- **WHEN** 开发者查看 catalog 的「已知缺口 / backlog」段
- **THEN** 看到当前已知但尚无 e2e 兜底的关键路径（断线重连、压缩恢复、附件透传、provider 切换、节点上下线看板）被显式列出，而非被默认为已覆盖

### Requirement: e2e 失败时留下可诊断证据

#### Scenario: 某条路径失败可定位
- **WHEN** 某条关键路径 e2e 失败
- **THEN** 开发者能拿到该次运行的 IM / Gateway 日志等证据，定位是哪条路径、断在哪一段，而非只有一个红叉

### Requirement: 工具调用后回复旅程经真 Gateway 进程可用

#### Scenario: agent 调工具再回复
- **WHEN** 用户经 IM 发一条需要 agent 调用工具才能完成的消息
- **THEN** 用户在 IM 上收到一条带正确结果、非空、不含内部报错的 assistant 回复

### Requirement: bash 前台超时不卡死会话

#### Scenario: 前台 bash 超时后会话仍可用
- **WHEN** agent 执行一个会超时的前台 bash
- **THEN** session 不被卡死，用户最终仍收到一条回复，对应工具按超时收口

### Requirement: bash 后台任务完成后送达跟进通知

#### Scenario: 后台作业完成长出第二条回复
- **WHEN** agent 把一个耗时 bash 丢到后台执行
- **THEN** 作业完成后，用户在同一 IM 对话里**再**收到一条包含结果的跟进消息

### Requirement: 前台子 agent 可用且失败被隔离

#### Scenario: 派子 agent 并带回结果
- **WHEN** 用户的请求促使 agent 派一个前台子 agent 干活
- **THEN** 用户收到的回复里带回了子 agent 的产出（不出现跨事件循环之类的崩溃）

#### Scenario: 子 agent 失败不拖垮常驻进程
- **GIVEN** 一个会失败的子 agent 任务
- **WHEN** 该子 agent 执行失败
- **THEN** 失败被隔离在该次结果内，Gateway 进程存活，后续消息仍能正常处理

### Requirement: /stop 中止正在执行的运行

#### Scenario: 运行中发 /stop
- **GIVEN** 一个正在执行的 agent 运行
- **WHEN** 用户发送 `/stop`
- **THEN** 该运行被中止，用户可观察到它已停止（不再继续产出）

### Requirement: cron 定时任务自动推送

#### Scenario: 到点自动冒泡
- **GIVEN** 一个 agent 配了即将触发的 cron 任务
- **WHEN** 到达触发时刻
- **THEN** 用户在 IM 对话收到该 cron 任务自动推送的一条消息

### Requirement: heartbeat 有内容时主动冒泡

#### Scenario: 心跳带可行动内容时主动发言
- **GIVEN** 一个启用了 heartbeat 且有可行动内容的 agent
- **WHEN** 心跳触发
- **THEN** 用户在 IM 对话收到 agent 主动冒泡的一条消息

### Requirement: 群聊里人与 agent 的定向 @ 双向可用

#### Scenario: 人 @ agent 再由 agent @ agent
- **GIVEN** 一个群里有用户 + agent A + agent B
- **WHEN** 用户发 `@A 请 @B 让他做 X 并把结果带回来`（用户全程不直接 @B）
- **THEN** 用户先在群里看到 A 的应答，且 A 的消息定向 @了 B
- **AND** 用户接着在群里看到 B 因被 A 点名而作出的应答

#### Scenario: 未被点名的 agent 不抢话
- **GIVEN** 同一个含 A、B 两个 agent 的群
- **WHEN** 用户发一条只 @A 的消息
- **THEN** 只有 A 应答，B 不在群里发言

### Requirement: 工具权限审批人在回路可用

#### Scenario: 批准后运行继续
- **GIVEN** agent 即将调用一个需要人工许可的工具
- **WHEN** 用户在 IM 收到等待批准提示并批准
- **THEN** 该工具执行，用户最终收到带结果的回复

#### Scenario: 拒绝后工具不执行
- **GIVEN** agent 即将调用一个需要人工许可的工具
- **WHEN** 用户在 IM 收到等待批准提示并拒绝
- **THEN** 该工具不被执行，运行据此收口，用户可观察到被拒绝的结果

### Requirement: 进程重启后会话上下文不丢

#### Scenario: 重启 Gateway 后仍记得上文
- **GIVEN** 用户先发消息让 agent 记住一项上下文并收到确认回复
- **WHEN** Gateway 进程被重启后，用户再发一条依赖该上下文的消息
- **THEN** agent 的回复体现它仍记得重启前的上下文

### Requirement: 经 IM 创建的 agent 落地后可聊

#### Scenario: 新建 agent 上线并应答
- **GIVEN** 一个已绑定且在线的节点
- **WHEN** 用户经 IM 配置中心新建一个 agent
- **THEN** 该 agent 在节点落地工作区并上线，随后用户给它发消息能收到回复

## 范围与非目标

- 在范围：
  - 上述 **11 条关键路径**各建一条经真 Gateway 进程 + 真 LLM 的黑盒 e2e，断言只看 IM 端可观察结果。
  - 复用 `scripts/e2e-up.sh` / `e2e-down.sh` 全栈底座（真 IM + 真 Gateway 子进程 + 真 LLM proxy），端口隔离、起停、节点绑定自动化。
  - 统一 `@pytest.mark.e2e` + env 开关，**一条约定命令全跑**；cron/heartbeat 等时间驱动路径可作为可单独跳过的子集。
  - 一份**单一权威 catalog 文档**：v1 必保活段（四列：用户旅程 / 守护测试 / 归属子系统 / 引入 unit）+ 已知缺口 backlog 段；并写明「新增关键特性须登记一行 + 配 e2e」的纪律。
  - e2e 失败时留下 IM/Gateway 日志等可诊断证据。
- 非目标：
  - **不进常态 CI**：真 LLM 烧 token，按需手跑，不要求每次提交都跑。
  - **不为 backlog 路径建 e2e**（断线重连补发、上下文压缩恢复、附件透传、provider 切换、节点上下线看板）——仅在 catalog 登记在册，留待后续 unit。
  - **不改产品代码行为**：本 unit 只加测试 + 文档；若 e2e 跑出真实产品 bug，另开 bugfix unit，不在本 unit 顺手改产品逻辑。
  - **不迁移/删除既有测试**：现有进程内 live-proxy e2e 与单测继续并存，本套件是新增的产品层安全网，不替代它们。
  - **不追求 LLM 输出字面匹配**：断言走鲁棒判据（非空 / 不含报错 / 含关键信号 / 状态正确），不锁死模型具体措辞。
  - **不做前端 UI 自动化**（不驱动浏览器点界面）：以 IM 对外 HTTP/SSE 接口为「用户可观察面」，等价于真实前端所触达的契约。
