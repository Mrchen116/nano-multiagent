# feat-436: 每个模型可配置自己的上下文窗口

## Relations

无依赖。本 unit 触及内核压缩判定（`agent.core.agent.compaction`）与 LLM 模型配置链路（`agent.core.llm` / `agent.sdk` / Gateway config），不阻塞也不被其他 unit 阻塞。

## 原始需求

> 现在项目中配置的上下文最大窗口是多少
>
> 我需要让每个模型可以自己配自己的context_window

Agent 解读（与原话分开）：现状 `context_window` 全局硬编码 200_000（`compaction/types.py:22` 的 `CompactionSettings` 默认值），且全程无人覆盖，与"当前 run 用哪个模型"完全解耦。用户希望让每个模型在配置里声明自己的上下文窗口，压缩判定按当前模型的窗口走。

## 用户场景

运维者（部署个人助手 Gateway 的人）在 `~/.nano-assistant/config.yaml` 里维护一份模型目录，每个模型可带自己的参数（如 `extra_request_body` 的 thinking 设置）。不同模型的真实上下文容量差异很大——有的 128k、有的 200k、有的 1M。可现在系统对所有模型一律按写死的 200000 来判定何时压缩对话历史：窗口比 200k 大的模型白白浪费容量、提前压缩损失上下文；窗口比 200k 小的模型则可能在真实溢出前都不压缩，直接被上游拒绝。

运维者希望：在 config 里给每个模型声明它自己的 `context_window`，系统就按这个值来判定压缩边界。他不需要任何额外的可视化界面来"看"这个值——只要能在 config 里写、写了就生效即可。某个模型没声明 `context_window` 时（老 config、或临时加的模型条目忘了写），系统继续按 200000 兜底，行为和现在一模一样，不报错、不失效。

与此同时，运维者发现现在压缩留的安全余量（reserve）只有 4096 token 太小：压缩摘要本身的生成 + 下一轮回复都要消耗额度，留 4k 经常压完仍然贴着窗口上沿甚至溢出。希望把这个全局余量提到 20k，让压缩在更早、更安全的位置触发。这个余量是全局策略，对所有模型统一，不随模型变。

"生效"的可观察落点：当一个对话在某个模型下持续变长，系统会在"接近该模型配置的窗口减去余量"处触发一次压缩——把较早的历史折叠成摘要。换不同窗口配置的模型跑同样的长对话，触发压缩的时机随配置值前后移动。（既有的前端 token 占用显示会顺带把分母显示成配置值，但这不是本期要求交付的可见特性。）

## 验收标准

### Requirement: 每个模型可在配置中声明自己的上下文窗口

#### Scenario: 模型显式配置了 context_window
- **GIVEN** config 里某模型条目声明了 `context_window`（例如 1000000），且该值与全局默认 200000 不同
- **WHEN** 运维者用该模型跑对话，对话上下文增长到接近"配置窗口 − 全局余量"
- **THEN** 系统在该配置值对应的边界触发一次压缩（把较早历史折叠为摘要），而不是在写死的 200000 边界触发

#### Scenario: 不同窗口配置的模型，压缩时机随配置移动
- **GIVEN** 两个模型，一个配置窗口明显较小、一个明显较大
- **WHEN** 用同样的长对话分别在两个模型下推进
- **THEN** 窗口小的模型更早触发压缩，窗口大的模型能容纳更长的对话历史后才触发压缩

### Requirement: 未配置 context_window 的模型保持现有行为（向后兼容）

#### Scenario: 模型条目未声明 context_window
- **GIVEN** config 里某模型条目没有 `context_window` 字段（如沿用旧 config）
- **WHEN** 运维者用该模型跑对话
- **THEN** 系统按全局默认 200000 判定压缩边界，启动与运行行为与本特性引入前完全一致——不报错、不拒绝启动

#### Scenario: context_window 配成非法值
- **GIVEN** 某模型条目把 `context_window` 写成非正整数（0、负数或非整数）
- **WHEN** 运维者用该模型跑对话
- **THEN** 系统按"未配置"处理，回退到全局默认 200000，不崩溃

### Requirement: 压缩安全余量（reserve）的全局默认提高到 20k

#### Scenario: 默认余量生效
- **GIVEN** config 未对余量做任何特殊设置（沿用默认）
- **WHEN** 任意模型的对话上下文增长
- **THEN** 系统在"窗口 − 20480"处（而非旧的"窗口 − 4096"）触发压缩，给摘要生成与下一轮回复留出更充足余量

## 范围与非目标

- 在范围：
  - Gateway config.yaml 的 `llm.providers[].models[]` 条目支持 `context_window` 字段；该值贯通到压缩判定，按当前 run 所用模型生效。
  - 未配置 / 非法值回退全局默认 200000。
  - 全局压缩余量 reserve 默认值从 4096 提高到 20480。
  - Coding CLI 因共享同一套模型注册表自然受益（用同一目录配置时一致生效）。
- 非目标：
  - 不为 Coding CLI 单独设计 context_window 的配置入口 / UI。
  - 不做 per-model 的 reserve（余量保持全局单值）。
  - 不引入任何新的可视化界面来展示模型窗口值（沿用既有前端 token 显示，不在本期改动它）。
  - 不改变压缩的算法 / 摘要质量 / 触发判定公式本身（仍是 `窗口 − reserve` 阈值 + 溢出双条件），只让 `窗口` 来源变成 per-model、`reserve` 默认变大。
  - 不做窗口按比例（百分比）计算余量的方案。
