# feat-544: 群聊 Agent 发言前复核新消息

> 状态：核心需求及 Process/消息分段交互已对齐，技术方案见 [design.md](design.md)。不作为实施或部署授权。
> 日期：2026-09-09。类型：feat / Full。新增的是发言前复核能力；当前仅有代码证据，不把它写成已复现的生产事故。

## 阅读入口

本单希望解决：多个 Agent 同时思考时，后发言的 Agent 能先看到期间新增的群消息，再判断原来的话是否还值得说。目标是消除“不知情地发布旧草稿”的窗口，保持原有补充、分歧及静默规则，不承诺消灭所有语义重复或错误。

本期覆盖内置 Web IM 普通群聊，包含当前群运行的普通回复、同群 send_message 以及回到该群继续运行的后台结果。保留并行工作、既有触发策略和真人插话体验。本单在正式发言公开前增加复核；不把“失去正文逐字输出”当作已确认的体验代价。当前已核实 OpenAI-compatible 路径累积正文后整段交付，并非逐 token 展示。

已确认的核心约束：本单只补发言前的信息复核，保持原有回复方式、静默许可和触发策略；单聊排除。此前独立草案提出的三次冲突后暂停不再作为需求。设计沿用下文范围，不追加新的产品回复规则。

## 一、先拿 Raft 算这笔账：新机制有价值，但也确实能被标准化

### 从“一个人用一个 Agent”，变成“多人和多个 Agent 在同一个房间里工作”

假设一个群里有几个人、几个 Agent。用户提出问题后，两个 Agent 都决定响应：
```css
Agent A 读取群聊 → 开始思考
Agent B 读取群聊 → 开始思考
                  ↓
A 发出了答案，群聊状态已经变化
                  ↓
B 仍按之前读到的状态，发出重复或过时的答案
```

这里的关键不是 B 不够聪明，而是：**B 决策时掌握的信息，和它提交行动时的世界状态，不一致。**

Raft 为此设计了两个接口：收件箱让 Agent 按需拉取通知，而不是把所有消息直接塞进上下文；发送草稿时携带其依据的房间版本，如果期间有新消息，先保留草稿并返回变化，让 Agent 决定修改、放弃或继续发送。它把原本缺失的“行动前重新感知”变成了明确的交互能力。

**这是有意义的新探索：不是规定 Agent 应该怎么思考，而是改变它能够感知和采取行动的方式。**

| 首版范围 | 内置 Web IM 的普通 group 会话默认适用，包括仅一个 Agent 的群；排除外部渠道及其影子会话 | 真人也会在 Agent 思考中更新要求。外部群需要另行确认可见性与发送边界，首版不宣称覆盖 |

| 谁决定发言 | 系统发现按原策略应处理的新消息，Agent 在原有回复规则内重新判断 | 原本允许静默才可静默，原本要求回复仍需回复；不因 A 先发或发生冲突额外免除回复 |
| 哪些变化触发复核 | 当前先讨论 ALWAYS：目标群新增的真人与 Agent 正式消息，不要求 @当前 Agent；附件消息也算。MENTION 保留既有门控 | 人可能只补发图片或附件；不得只看纯文字。活动状态、思考和工具过程、已读等展示变化不算正式发言 |
| 正在做事与未启动 | 已在准备发言的 Agent 复核按原策略进入处理流程的新消息；空闲 Agent 仍服从原有提及/始终回复策略 | 将发言复核与唤醒分开，不因为别人发言就把所有空闲 Agent 拉起来 |
| 草稿保留与用户控制 | 当前任务内保留可继续处理的草稿；静默、失败、停止与运行限制沿用原有规则 | 不建草稿箱或编辑器，也不要求用户每条批准。首版不承诺进程重启后恢复未发草稿；恢复失败必须明确未发送 |

三种更省事的替代方案都不足以承载本意图：提示词要求“别重复”不能补上没看到的消息；全量插话仍可能晚于最后一次决策；固定串行发言会改变多人并行工作的体验。新增复核与已有插话互补，不取代它。

## 用户场景

### S1：没有插话时正常回答

用户在内置群 @A 提问，A 思考期间群里没有新发言。用户能看到 A 正在处理，随后看到完整答案，不用审批草稿，也不会被要求再次发送问题。群里即使只有一个 Agent，也有同样体验。

### S2：另一位 Agent 已经回答或补充事实

用户同时请采用 ALWAYS 策略的 A、B 讨论同一问题。A 先发出结论，B 正在准备回复。即使 A 没 @B，B 也先得到 A 新增的内容和发言身份，再决定如何处理自己的草稿。例如 A 说“会议已经改到周五”，B 应在正式发言前有机会改掉以周四为前提的建议。若 B 有独立证据不同意 A，仍可表达分歧；若发现自己只会重复，也只有原本允许静默时才能不发言；原本仍需回复时，继续按原有规则回应。

### S3：用户在等待中改了要求

B 正在写中文摘要，用户补充“改成英文，只保留三点”，或补发一张包含更正信息的图片。用户不想先看到旧摘要流出来再被撤回。B 应先结合补充重新处理，最终发布对应内容。过程中可以显示正在处理/结合新消息调整，但待修改正文可在 Process 的“原草稿 · 未发送”中查看，但不作为正式回复或混在无标记的工具结果里。当前已经执行的外部动作不因草稿复核自动撤销。

### S4：原文仍有价值，也可能再次过时

A 补充背景后，B 判断自己的结论仍成立，可以保留原文发出；不要求为了证明读过新消息而机械改写或添加套话。如果 B 复核期间 C 又发来新事实，B 要再考虑 C，不能把第一次复核当作永久通行证。新增消息在 B 正式发出之后才到达时，则留给之后的交互处理，不回溯撤掉 B 已发的消息。

### S5：复核不改变原有回复责任和结束方式

群持续讨论时，B 根据按原策略进入处理流程的新消息继续判断。原本允许静默的场景可以照常静默；原本需要回复的场景不能因复核或多次冲突变成静默、放弃或等待用户重新触发。网络、模型失败及运行限制沿用原有处理和可见反馈，不新增固定冲突次数后的暂停规则。用户 `/stop` 后不再出现这次未发的草稿，`/new` 后也不复活旧草稿。

### S6：当前群运行的发言出口一致

当前群运行的普通回复、同群 send_message，以及后台任务或 Workflow 结果回到该群后继续运行产生的回复，都复核该运行按既有策略已接收的新消息。跨群主动通知暂不增加另一套目标群复核机制。过程卡片中的原始工具结果仍是过程信息，不能被包装成绕过复核的正式结论。真人发言正常发送，其他群的活动不拖住当前群；单聊和外部聊天保持现有体验。

### S7：用户能看出哪一段工作已结合最新消息（交互已确认）

B 原消息块保留更早已经发生的 Process；当新消息被实际采纳时，旧块保留可展开的“原草稿 · 未发送”，并以“草稿未发送 · 转入后续处理”结束该段，用户可以定位后续块。复核本身从新消息下方的新 B 块开始，其 Process 提供已采纳新消息的引用，记录复核状态及实际已有的可展示过程。之后的工具调用和最终回复属于这段新工作，不再追加回旧块。原文仍适用时也在新块公开。原本允许静默时，新块可以仅保留已发生的 Process，不新增正文占位回复。再次采纳更新则再切段；一次采纳的多条消息合为一个新段，不按每条通知建块。旧块不移动，已发生的过程不复制。此处结束的是工作片段，不是宣称整个任务完成。

## 验收标准

以下是拟议产品行为，非已验收结果。除明确描述 MENTION 或单聊回归的场景外，群聊竞态场景均以 ALWAYS 为前提。真实验收通过聊天页面的正文、活动状态和历史观察；语义场景使用有明确更正关系的输入，不把“彻底没有重复”作为无法保证的目标。场景中的工作先后由可控长任务或并行任务建立，不以检查私有协议代替用户旅程。

### Requirement: 群聊发言在公开前结合期间新增的正式消息

#### Scenario: 没有新消息时正常发送（S1）
- **WHEN** 用户在覆盖范围内的群向 Agent 提问，准备回复期间没有其他正式消息
- **THEN** 用户先看到工作状态，随后收到完整回复，不需要批准草稿或重复提问

#### Scenario: A 未提及 B 的更正影响 B 的回复（S2）
- **GIVEN** A、B 同时准备关于会议日期的回复，B 原先依据周四安排
- **WHEN** A 在 B 发言前明确通知会议已改到周五，且没有 @B
- **THEN** B 后续公开的安排采用周五，或明确解释不采纳更正的依据，不继续无解释地按周四安排

#### Scenario: 真人更改输出要求（S3）
- **GIVEN** B 正在准备中文摘要
- **WHEN** 用户在 B 发言前补充“改成英文，只保留三点”
- **THEN** B 公开的摘要为英文三点，旧中文草稿未曾作为正式正文出现

#### Scenario: 附件形式的补充也被考虑（S3）
- **GIVEN** 使用支持图片理解的 Agent，正在按旧日期准备回复
- **WHEN** 用户在其发言前补发清楚写有更正日期的图片并说明以图片为准
- **THEN** Agent 后续回复依据图片更正；如果无法读取则明确说明，不能装作没有收到补充而直接确认旧日期

### Requirement: 复核结果遵守原有回复与静默规则

#### Scenario: 原本允许静默时继续允许（S2、S5）
- **GIVEN** 当前场景按原有设计允许静默，用户要求 A、B 回答同一事实问题，并明确“其他人已回答且没有补充就不用再发”
- **WHEN** A 先给出完整答案，B 没有新增信息
- **THEN** B 可结束而不发正式回复，群里不出现静默占位文字，B 不一直停在工作中

#### Scenario: 原本不允许静默时仍需回复（S2、S5）
- **GIVEN** 当前场景按原有设计不允许静默
- **WHEN** Agent 在发言前复核到新消息，即使其他 Agent 已回答或多次发生冲突
- **THEN** Agent 仍按原有规则回复，不新增静默、放弃或要求用户再次触发的结束方式

#### Scenario: 有不同意见仍能发言（S2）
- **GIVEN** 用户让两位 Agent 分别评估方案的收益和风险
- **WHEN** A 先发收益分析，B 随后完成风险分析
- **THEN** 用户仍能收到 B 有内容的风险意见，不因 A 抢先发言就被统一屏蔽

#### Scenario: 新消息不影响原结论时可原文发送（S4）
- **GIVEN** 用户要求 B 最终只回答一个确定的计算结果，A 期间补充无关背景
- **WHEN** B 完成复核并发言
- **THEN** B 可以仍只回答该结果，不被要求附带解释复核的套话

#### Scenario: 复核期间又出现更正（S4）
- **GIVEN** B 已开始根据“改到周五”调整日程建议
- **WHEN** 用户在 B 正式发言前再次明确“最终定周六”
- **THEN** B 的公开安排采用周六，不发布无解释的周五安排

### Requirement: 待复核草稿不提前成为公开发言

#### Scenario: 长回复调整时没有旧正文闪现（S3）
- **GIVEN** B 正在准备一篇长回复，期间收到要求改写的消息
- **WHEN** 用户持续观察聊天及可展开的过程展示，然后刷新历史
- **THEN** 未发送的旧草稿不作为正式正文或正式消息预览出现；可在所属块的 Process 中展开查看完整草稿，明确标注“未发送”，不留下先正式发布后撤回的旧答案
- **AND** 用户能区分 Agent 仍在处理与已正式发言；原始思考/工具过程不伪装成正式答案

#### Scenario: 同时完成时后发言仍衔接讨论（S2、S4）
- **GIVEN** 用户让 A、B 同时准备回答同一问题，并要求后发者只补充前者遗漏
- **WHEN** 两者在接近的时间完成准备
- **THEN** 群里后公开的回复体现对前一条已公开发言的补充，或在原有规则允许时后者静默；不把同时准备视为免复核条件

### Requirement: 复核保留原有失败与停止行为

#### Scenario: 无法复核时明确失败（S5）
- **GIVEN** 待发言因新消息需要调整
- **WHEN** 网络或模型失败导致无法继续处理
- **THEN** 沿用既有失败与重试反馈，不能将未公开的草稿显示为成功发言，也不新增冲突暂停交互

#### Scenario: 停止或重开后不补发旧稿（S5）
- **GIVEN** Agent 正在复核
- **WHEN** 用户停止该任务，或在群中执行新会话并收到相应确认
- **THEN** 此前未发的草稿此后不再作为正式回复补发；Process 中已经记录的草稿仍可查看，已发历史不因本机制被撤销

### Requirement: 发言来源一致且不扩大唤醒范围

#### Scenario: 当前群的工具发送和后台续跑也复核（S6）
- **GIVEN** 当前群运行将通过同群 send_message 或后台结果续跑报告旧安排
- **WHEN** 该运行在准备期间按既有策略接收到明确更正安排的新消息
- **THEN** 公开报告体现更正或解释分歧；只有原有规则允许时才能静默，失败仍走既有反馈；不会因发言来源不同就无解释地发布旧安排

#### Scenario: 空闲 Agent 不因复核能力被额外唤醒（S6）
- **GIVEN** B 采用仅被提及时回复的策略，当前空闲
- **WHEN** A 在群中发一条没有提及 B 的普通消息
- **THEN** B 不因此开始工作或发言；用户之后 @B 时，B 仍可利用此前讨论

#### Scenario: 其他聊天与真人发言不被拖住（S6）
- **GIVEN** 一个内置群中的 Agent 正在反复复核
- **WHEN** 真人继续发言，或用户在另一个群、单聊、外部渠道发起独立对话
- **THEN** 真人消息正常出现，其他聊天保持各自既有行为，不因该群的复核而被暂停

### Requirement: Open chat 单聊保持原有体验

#### Scenario: 从 Agent 详情页打开单聊（S6）
- **WHEN** 用户点击 Agent 详情页的 Open chat，进入新建会话并与该 Agent 对话
- **THEN** 这是用户与该 Agent 的单聊；正文仍按既有方式展示，运行中插话保持现有行为
- **AND** 不因本单引入群聊草稿保留、发言复核或连续冲突暂停

### Requirement: Process 保留原本生成的未发送草稿

#### Scenario: 查看未发送草稿（S7）
- **GIVEN** Agent 已生成草稿，并因采纳新消息进入复核
- **WHEN** 用户展开原消息块的 Process 和其中的草稿项
- **THEN** 可看到当时生成的完整草稿，明确标注未发送；刷新后仍可查看，不以新生成的摘要替代
- **AND** 草稿不作为正式回复正文，也不触发其他 Agent 接话；复核后正式回复仍在后续新块

### Requirement: 复核及后续工作对应最新消息分段展示（交互已确认）

#### Scenario: 复核与工具结果在更新下方（S7）
- **GIVEN** B 已有过程消息块，之后群里出现按既有策略进入处理流程的新消息
- **WHEN** B 采纳新消息并开始复核
- **THEN** 旧块保留原过程并说明草稿未发送、转入后续处理；更新下方的新 B 块展示复核 Process 与来源引用
- **AND** 后续工具调用和最终回复出现在新段，不追加回更新上方的旧块；刷新后顺序与归属一致

#### Scenario: 原文保留或原规则允许静默（S7）
- **WHEN** B 复核后保留原文，或按原有规则选择静默
- **THEN** 保留原文时在新段正式发布；允许静默时只保留实际发生的过程并结束运行态，不新增正文占位回复

#### Scenario: 成批采纳及再次更新（S7）
- **WHEN** B 一次采纳多条更新，或后续又采纳另一批更新
- **THEN** 每批从其最后一条已采纳消息下方的新段继续；不按每条通知建块，不移动旧块或复制原有过程

## 范围与非目标

在范围：内置 Web IM 普通群聊；目标群新增正式消息的发言前复核；当前任务内草稿保留及按原回复规则重新判断；当前群运行的普通回复、同群 send_message 与后台结果续跑回复；正文公开前的复核；原有回复、静默及失败行为的保留；既有提及、插话、停止、新会话和去重语义的保留。

非目标：

- 跨群主动通知的目标群复核、Gateway 尚未接收到的远端消息一致性；不建立 IM 房间版本仲裁。

- 飞书/Lark 等外部群及其影子会话的完整实时一致性；单聊、Coding CLI 的发言行为变化。
- 通用通知收件箱、注意力调度、自动主持人、固定轮流发言、任务认领或全局 Agent 协作规划。
- 改变原有回复和静默规则、按冲突次数新增暂停/继续交互、绕过复核强发、用户逐条审批、草稿箱/草稿编辑器、进程重启后的草稿恢复保证。
- 对所有语义重复或事实错误作保证；只要知情就可能合理保留原文或提出分歧。
- 撤销已经执行的工具或外部副作用；发言前复核不是任务执行锁，也不能防止两位 Agent 已经重复做了同一件事。
- 追溯撤回已经公开的发言、新增消息编辑/撤回能力、将所有展示事件都当成群讨论变化。

## 审稿与后续边界

用户后续澄清优先于独立草案建议。当前收口为补充发言前信息复核、保持原有回复与触发行为。

需求阶段收口，接下来进入设计对齐。版本表达、读过哪些消息的认定、发布的一致性保障、普通回复输出如何衔接以及失败后的恢复实现属于后续设计问题，本稿不指定协议、存储、模块或接口。尤其不能将“普通回复也适用”在设计时缩成只改主动发送工具。
