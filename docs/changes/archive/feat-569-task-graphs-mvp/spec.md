# feat-569：讨论驱动的任务图 MVP

> 需求版本：v1.2 · 2026-09-22。正式编号 feat-569 已由本地仓库分配器登记；独立 Gate 2 已通过，见 [design-review.md](design-review.md) Round 3。

## 原始需求

### 本轮明确的 MVP 范围（用户原话）

我觉得我们第一版先按照简单的来，先把这两种模式先能使用。包括用户界面上能看到图，以及agent能调用工具来创建，查询，更新task系统。什么预算，自动并行都不用。我只要跟他说我的大目标，然后跟agent讨论完，他能按两套之一给我拆分，至于多agent还是单agent做，我会跟agent说，然后再怎么把小任务细分，我也会跟agent讨论。他要讨论完能创建，做完任务要可以更新。我们第一版先做这些。你帮我按照我的仓库里的change-spec-author和change-design-author，写一版unit文档，包括prototype。然后我下载到我本地去让本地的code agent去做实现。

### 必须保留的双模式与嵌套要求（上一轮用户原话）

现在我们讨论的都是一个任务分成多个子任务，并按 DAG 运行。这种做法，确定性任务是可以这样做的。

最近我也跟你做了很多关于 AutoResearch 的研究学习。这里面会发现，一些偏研究方向的东西，没有确定性的分工。这时候讨论的是这个方向行不行、那个方向行不行。你可以从一个任务里拆分出多个子方向，在这些子方向上做了一些尝试之后，可能又会衍生出一个改进的子方向，所以它也是一棵树的形状。其实这两种，一种是确定性的树，一种是不确定性的探索树。我觉得我们这套任务系统里都应该支持。而且两者可以相互嵌套。比如一个确定性任务，可以拆分成 A、B、C，需要先做 A，再做 B，最后做 C。

其中，A 可能是一个探索性任务。在 A 内部，它是一棵探索树：先尝试 X 方向，再尝试 Y 方向；可能 X 方向后面更有前途，那就继续在 X 方向下面尝试一个衍生的 Z 方向。最后确定下来，可能 Z 方向是最好的，就相当于完成了 A 任务，然后继续完成 B、C、D。你理解吗？我们要把这个也囊盖

## 澄清记录

本轮用户已经主动收口，没有补造 Q/A。以下区分用户已决定事项与作者理解。

| 已有用户决定 | 本版采用的范围 |
|---|---|
| “第一版先按照简单的来” | 一个可读、可维护的任务记录系统，不建设自动编排平台。 |
| “两种模式先能使用”“两者可以相互嵌套” | 计划式依赖图、探索式衍生树；任一节点可进一步按任一模式细分。 |
| “用户界面上能看到图” | 在现有 nano IM 中查看图、节点详情、上下层关系和结果。 |
| “agent能调用工具来创建，查询，更新” | Agent 能按讨论结果持久建图、续查并更新，不止生成图片或聊天文本。 |
| “多agent还是单agent做，我会跟agent说” | 用户通过聊天决定执行方式；本功能不启动或调度执行者。 |
| “再怎么把小任务细分，我也会跟agent讨论” | 渐进拆分，讨论后增量修改，不一次性强行拆完。 |
| “什么预算，自动并行都不用” | 不做预算、自动并行、自动开工、决策收件箱或独立验收引擎。 |

**作者理解：**用户的确认发生在聊天里，不新增专门的审批按钮、审批状态机或强制门禁。用户要结束、继续修改、暂缓一个方向时，由 Agent 明确更新记录；记录不冒充经过系统独立验证的事实。此前讨论过的自动评审、资源治理等不属于本版。

### 本地评审后的权限收口（2026-09-22）

**用户原话：**“权限问题先怎么简单怎么来，自洽就行。”

**Agent 解读与采用方案：**沿用现有规则：任务图页面、任务查询和原聊天入口按当前聊天成员可见；Agent 已在 Work 中记录的任务内容继续按现有 Work 规则向登录用户展示。能看到这段工作记录，不代表能打开原图或原聊天。本版不增加任务专属的 Work 隐藏、脱敏或副本撤回机制。

### 本地评审后的工具入口澄清（2026-09-22）

**提问原文：**“第一版是否允许在飞书等外部聊天里，让 Agent 查询、更新任务图，并统一到 Web IM 查看图？”

**用户选择：**“允许，外部聊天也能操作，Web IM 负责看图（推荐）”。

**用户进一步纠正：**“外部内部都是输入user prompt，调用工具是agent内的事情，两者都无关”。

**Agent 解读与采用方案：**工具属于 Agent 能力；用户从 Web IM、飞书等入口输入指令，不参与任务工具的权限判定。创建、查询、更新沿用 Agent 的工具配置和真实身份，不额外按输入渠道划分任务专属权限。任务图仍持久存于 IM，关联的聊天只决定归属和成员可见性；Web IM 查看同一图，外部聊天不增加图形界面。任务记录不会因此自动启动或调度 Agent。

## 用户场景

### U1：讨论完，再把计划保存成可查看的图
用户通过现有 Web IM、飞书等单聊或群聊交代“大目标”。Agent 先讨论边界与拆分，用户说“就按这个建图”后，保存目标及 A→B→C。聊天能进入对应图；用户以后回来能继续看到同一份记录。只讨论、不要求保存时，不擅自建立和执行整套任务。

### U2：探索方向，而不是把所有候选都做成必做待办
用户与 Agent 先记录 X、Y，再根据 X 的结果提出 Z。图能说明 Z 来自 X，Y 可以保留“测过但不达标”的结论或标为不再探索。选定 Z 是一个明确记录，不自动把其他方向抹掉，也不自动宣告目标完成。

### U3：局部展开，不把三层工作混成一张大图
外层 A→B→C 中，A 是探索；打开 A，看 X、Y、Z；再打开 Z，看“原型→测量→记录结论”的验证步骤。面包屑可返回外层。探索根任务也可以在某个方向内部建立计划子图。局部修改不丢失其他层的结构。

### U4：工作由用户指挥，图由 Agent 持续维护
用户说“我先自己做 B”“让一个子 Agent 做 X”或“这个方案我不满意，继续改”。仍使用现有聊天与执行能力。Agent 能把对应节点标记为进行中、完成、暂缓或放弃，写结果和理由，再按反馈改回进行中。图上清楚标注这是记录状态，不是调度或验收结论。

### U5：查询、恢复和错误不能误导
用户可以查询可访问任务、定位某个节点、查看更新时间与最近修改者。刷新或 IM 重启不丢记录。保存失败不显示“已保存”；旧版本更新冲突不覆盖新记录；构成循环的错误修改不破坏原图。非成员不能通过任务入口看到该聊天的任务资料。手机可逐层查看图和详情。

## 验收标准

### Requirement: R1 用户能从现有聊天进入讨论后保存的任务图

#### Scenario: S01 讨论并保存计划（U1）
- **GIVEN** 用户和 Agent 已在聊天中讨论好目标与拆分。
- **WHEN** 用户要求按讨论结果创建任务记录。
- **THEN** 用户可从该聊天打开对应任务图，看到目标、任务名称及已讨论的依赖关系。
- **AND** Agent 只有在保存获得明确确认后才说创建成功。

#### Scenario: S02 只讨论，不自动开工（U1、U4）
- **WHEN** 用户只讨论拆分、查询或修改图。
- **THEN** 本功能不自动启动 Agent、执行命令、并行工作或创建定时任务。
- **AND** 用户仍通过原有聊天决定是否工作、由谁工作。

#### Scenario: S03 没有任务的聊天（U1）
- **WHEN** 用户打开一个尚未保存任何任务的聊天的任务入口。
- **THEN** 看到明确空态及“在聊天中讨论后创建”的指引，不出现演示任务或虚构进展。

### Requirement: R2 计划式图清楚表达前后依赖

#### Scenario: S04 查看计划结构（U1）
- **WHEN** 用户打开已保存的计划式图。
- **THEN** 能辨认各任务与依赖方向，并查看每个节点的说明、状态和结果。
- **AND** 图中的连线说明为前置依赖，不混用方向衍生的含义；分叉、汇合及跨过中间任务的直接依赖仍能辨认，详情可查直接前置和后续任务。

#### Scenario: S05 依赖不自动调度（U4）
- **WHEN** Agent 更新 A 的完成记录。
- **THEN** A 显示完成，B 和 C 原有状态不被自动修改，也不会因依赖满足就开始执行。

### Requirement: R3 探索式图保留方向来源与探索结论

#### Scenario: S06 从 X 衍生 Z（U2）
- **WHEN** 用户与 Agent 讨论后新增 X 的改进方向 Z。
- **THEN** 图保留 X、Y，并清楚表示 Z 从 X 衍生，而不是把 Z 当成 X 完成后必做的步骤。

#### Scenario: S07 负结果和暂缓方向（U2、U4）
- **WHEN** 一次尝试得到可信的负结果，或用户决定暂缓、放弃该方向。
- **THEN** 能保留实际结果及对应状态，不要求把负结果修成正结果，不删除其历史来源关系。

#### Scenario: S08 记录选定方向（U2）
- **WHEN** 用户决定当前采用 Z，Agent 记录该决定及理由。
- **THEN** Z 清楚标为当前选定方向，其他方向仍可查看。
- **AND** 外层 A 不因选择 Z 自动完成。

### Requirement: R4 两种模式可以逐层嵌套

#### Scenario: S09 计划内探索、探索内计划（U3）
- **GIVEN** 外层为 A→B→C，A 内有 X、Y、Z，Z 内有验证步骤。
- **WHEN** 用户依次打开 A、Z，再返回外层。
- **THEN** 每层显示正确模式、节点、连线与层级位置；B、C 不混入 A 的候选方向中。

#### Scenario: S10 叶子讨论后进一步细分（U3）
- **WHEN** 用户要求将一个尚未细分的节点按另一种模式细分。
- **THEN** Agent 可以保留节点身份、原说明与结果，并新增内部子图。
- **AND** 不要求用户重新建立整个大目标。

### Requirement: R5 Agent 可持续查询并修改同一份任务记录

#### Scenario: S11 查询已有任务（U5）
- **WHEN** 用户要求 Agent 找到之前讨论的任务并说明当前位置。
- **THEN** Agent 能查到有权限的目标、层级、节点及结果，并引用同一份任务图。

#### Scenario: S12 修改状态和结果（U4）
- **WHEN** 工作有进展，Agent 按实际情况更新节点说明、状态或结果。
- **THEN** 图中对应节点反映新内容，刷新后仍保留；其他节点不被无关覆盖。

#### Scenario: S13 不满意后继续改（U4）
- **WHEN** 用户要求已记录完成的任务继续修改。
- **THEN** 同一节点可重新记录为进行中，并说明继续修改的原因，不创建无关重复目标。
- **AND** 用户能辨认记录由谁、何时更新。

#### Scenario: S20 输入渠道不限制 Agent 的任务工具（U1、U4、U5）
- **GIVEN** Agent 已配置任务工具，且可访问目标图关联的聊天。
- **WHEN** 用户通过现有 Web IM 或外部聊天要求 Agent 创建、查询或更新任务记录。
- **THEN** Agent 使用同一工具与同一份持久记录；可用性不因输入渠道改变，用户可在 Web IM 查看对应图。
- **AND** 通过外部聊天输入指令不自动授予用户 Web IM 的成员身份；打开图仍使用既有登录和成员规则。

### Requirement: R6 图的结构修改失败时保留原记录

#### Scenario: S14 不合法的关系（U5）
- **WHEN** Agent 尝试建立循环依赖、循环衍生或把不在同一层的节点直接连线。
- **THEN** 修改被明确拒绝，已有图不被部分破坏，Agent 获得可供修正的原因。

#### Scenario: S15 同时修改冲突（U5）
- **GIVEN** 同一份图已被另一条更新修改。
- **WHEN** Agent 使用旧记录提交修改。
- **THEN** 不覆盖较新的内容；明确提示需重新读取后再调整。

### Requirement: R7 任务图真实持久，失败与未知不冒充成功

#### Scenario: S16 刷新和服务重启（U5）
- **WHEN** 用户刷新页面，或 IM 服务正常重启后再次进入任务。
- **THEN** 已保存的图、嵌套、选定方向和结果保持一致。

#### Scenario: S17 网络失败或保存结果未知（U5）
- **WHEN** 读取失败、连接中断，或写入后未收到确认。
- **THEN** 界面或 Agent 明确说明读取失败、保存失败或结果待核实，不声称已经更新。
- **AND** 能重试读取；有缓存时明确显示其可能不是最新状态。

### Requirement: R8 沿用聊天可见性与 nano 的基本体验

#### Scenario: S18 成员边界（U5）
- **WHEN** 用户或 Agent 通过任务入口或任务查询查看自己不可访问的聊天所关联的任务。
- **THEN** 这些入口不返回图、标题、结果及检索摘要，不因可查看某个 Agent 的 Work 就扩大任务访问权。
- **AND** 登录用户仍可按现有 Work 规则查看 Agent 已记录在工作轨迹里的任务内容；从中打开原任务图或原聊天时，仍按当前成员关系判定。

#### Scenario: S19 手机与桌面查看（U3、U5）
- **WHEN** 用户在桌面或手机上打开任务图。
- **THEN** 可以选择节点、进入子图、返回上层并读到完整详情；图内可滚动或缩放，操作按钮不被裁掉。
- **AND** 现有聊天、Agents 和 Work 入口不被任务功能替换。

## 范围与非目标

**在范围：**Agent 可按用户指令维护、在 Web IM 查看且关联既有 IM 聊天的任务图（包括已映射的外部聊天）；计划 DAG、探索衍生树及互相嵌套；Agent 创建、查询、增量修改；名称、说明、记录状态、结果和普通证据链接；显式记录一个当前选定方向；可浏览的图与节点详情；聊天入口、持久化、基本权限和错误反馈。

**非目标：**预算、Token 计费、自动并行、调度器、自动恢复执行、自动依赖放行、自动拆解或排序算法、自动创建/选择 Agent、决策 Mailbox、审批卡或审批引擎、强制独立验收、候选打分与排行榜、全局最优搜索、复杂事件溯源、跨节点离线同步、多父方向合并、跨层依赖、图形拖拽编辑器、后台任务状态自动映射、附件托管、CLI/外部 IM 的任务图 UI。普通现有工具与执行能力保持原样。

## 用户实测补充：S21 任务图特性开关

2026-09-22 用户要求 Agent 配置的“特性开关”中提供任务特性。沿用现有 Agent 设置入口与保存流程，默认开启；可关闭该 Agent 的任务图能力，并在下一轮回复生效。工具白名单仍限制能力，不因输入渠道改变；关闭不删除图、不阻止成员继续在 Web 看图。S21 验收覆盖显示、关闭保存/重读、下一轮工具关闭、重新开启和既有图仍可查看。此项加入同一未合并 PR 的 M1，不新建生命周期。
