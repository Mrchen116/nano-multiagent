## 优先处理的十项

P1 表示核心内容含义会改变；P2 表示频繁操作或阅读明显退步。排序是设计判断，可将相邻问题合并为小而可审的修复。

### U01 · P1 · 消息段落中的图文顺序改变

- 入口：聊天 → 含内联图片的 Agent 回复。
- 事实：`src/IM/ios/NanoIM/UI/MarkdownView.swift:61-67` 先渲染段落全部 inline 文字，再逐个追加该段所有直接图片；`:78` 在 inline 内容中删除图片。`文字 A ![图](合法资源地址) 文字 B` 因而呈现为“文字 A 文字 B，随后图片”。这是正常图文混排即可触发的内容变化。
- Web 基线：`docs/specs/im/web-chat-ux.md` 的“Agent 图片在正文中按顺序展示”要求保持引用位置。`src/IM/frontend/src/features/chat/components/message-pane.tsx:1833-1929` 的 Markdown 组件按原 AST 顺序渲染图片和相邻文本。
- 建议：原生段落按连续文字片段和图片顺序形成块流；不用复制网页组件，也不需要新渲染框架。对照一段中“说明 → 图 → 结论”和两张图之间有文字的实际回复。

### U02 · P2 · 待发送照片不可辨认

- 入口：聊天 → `+` → 照片，或粘贴图片 → 发送前检查。
- 事实：`ConversationView.swift:108-111` 的成功待发附件只有回形针、文件名和删除；`:116-135` 的上传状态也只有文件名；`:235-237` 将照片命名为随机 `photo-XXXXXXXX.jpg`。用户发多张截图时，发送前无法从缩略图检查或选择删除正确图片。
- Web 基线：`src/IM/frontend/src/features/chat/attachments/attachment-chip.tsx:17-34` 对 image 附件直接显示 `MessageImage` 和该项删除。目标 S10 也要求待发项可辨认。
- 建议：用本次照片/粘贴的现有数据显示原生小缩略图，上传中和失败叠加状态，成功后仍保留预览；点选可放大确认。无须增加离线媒体库或常驻缓存。

### U03 · P2 · 消息时间消失

- 入口：任意聊天历史、隔日回复、多人消息。
- 事实：`src/IM/ios/NanoIM/Features/Chat/ChatMessageView.swift:17-21` 只展示发送者和投递状态；`:49-57` 的耗时是执行时长，不能替代发送时间。整个 message body 没有展示 `created_at`；它只在 `startedAt` 中用于运行计时。
- Web 基线：`src/IM/frontend/src/features/chat/components/message-pane.tsx:1525` 计算消息时间，`:1790` 展示时间。原生列表也已有 `CommonViews.swift:111-118` 的本地时间格式组件。
- 建议：气泡末尾保留低层级的本地时间；跨日用日期分隔减少重复。不要常驻完整 ISO 时间戳，日期与执行耗时应可区分。

### U04 · P2 · 复制得到内部原文而非读到的正文

- 入口：聊天 → 长按 → 复制正文；代码块复制；任务引用复制。
- 事实：`ConversationView.swift:48` 直接将 `message.content` 写入剪贴板。消息显示经过 `ChatText.display`（`ChatMessageView.swift:27`），复制却未经过相同转换。因此可见 `@名字` 的消息复制后仍可能得到 `<mention type="user" target_id="…"/>`；Markdown 围栏等也原样保留。消息复制、`MarkdownView.swift:24` 代码复制和 `TasksView.swift:181` 引用复制均无本地成功反馈。
- Web 基线：current Web chat 要求复制可见正文、具名链接保留真实地址、排除头像/过程/指标。`message-pane.tsx:493-528` / `:1628-1635` 从正文或代码元素提取内容，`:1157-1165` 统一显示复制反馈；`task-graphs-page.tsx:228` 有引用复制结果。
- 建议：提供一个简单的正文文本提取，先转换 mention，再按已支持的 Markdown 类型生成结构可读的文字；具名链接保留 URL。用轻量“已复制”提示并保持阅读位置，代码仍只复制代码。

### U05 · P2 · 翻历史退化为反复点按钮

- 入口：聊天 → 向上翻一页以上历史。
- 事实：`ConversationView.swift:38-43` 只有“更早的消息”按钮；scroll geometry 的逻辑 `:62-66` 只检查底部跟随，没有顶部加载。按钮没有显示加载中、禁用并发状态或到底提示，`ChatStore.swift:146-167` 也无 per-chat 历史加载状态。
- Web 基线：`message-pane.tsx:822-827` 在接近顶部时加载；`:807-819` 恢复锚点；`:1009-1015` 区分加载中与历史结束。current Web chat 明确要求顶部自动分页并稳定保持位置。
- 建议：接近顶部时自动加载，保留原可见消息作为锚点；小字/进度指示区分加载和“没有更多消息”。按钮可作为可访问的重试入口，不应是每页唯一操作。

### U06 · P2 · 任务图的计划/探索语义不够可辨认

- 入口：任务 → 一个计划图或探索图。
- 事实：`TaskModels.swift:58-60` 已区分依赖和衍生数据，但 `TasksView.swift:94-100` 用相同实线/箭头；`:104-107` 节点只显示标题和状态，没有子图类型、当前选项标记；`:79-86` 图头没有计划/探索关系说明；`selected_candidate_id` 只在节点详情 `:173` 才可见，未在关系图强调。
- Web 基线：`task-graphs-page.tsx:85` 有关系含义，`:100-106` 用独立衍生线和标签，`:110-118` 有选中候选/节点模式，`:126-127` 展示当前选择与关系图例。current task spec 要求衍生不被误读为前置，以及负结果、方向与显式选项可辨认。
- 建议：图头说明“前置依赖”或“方向衍生”；探索线可虚线并标“衍生”；节点显示选定方向/已放弃及可进入的子模式，当前选择和理由可用紧凑摘要。原生可继续纵向分层，不必照抄桌面左到右布局。

### U07 · P2 · 子任务导航缺少祖先路径

- 入口：任务 → 节点详情 → 子图 → 子节点 → 再下层；或直接打开一个深层任务链接。
- 事实：`TasksView.swift:79-85` 只有当前 scope 标题，`:118` 一律为“任务图”；`:121-126` 节点详情以 sheet 承载，`:175` 在 sheet 的导航栈继续 push 子图。每层系统返回存在，但没有图根到当前位置的祖先线索；从深链打开时也无直接回父层/根目标入口。
- Web 基线：`task-graphs-page.tsx:177-178` 计算祖先，`:234-235` 每个祖先可点击。current task spec 和本 unit S14 均保留面包屑语义。
- 建议：在 scope 标题附近提供简短“根目标 › 当前层”的路径；深层可用路径菜单跳至任一祖先。详情采用 sheet 仍可，但路径应基于真实 container 层级，不依赖用户恰好经过的浏览历史。

### U08 · P2 · 建聊比 Web 多了不必要条件，也弱化联系人搜索

- 入口：聊天 → 新建聊天 → 创建群。
- 事实：`ChatListView.swift:97` 搜索仅匹配 display name，不匹配 Agent ID；`:110` 即使已经选择成员，空群名也不能创建；`:117` 未提供自动名称。建聊没有加载中/无匹配提示，联系人请求只有一次（`:111`）；这是源码可确定的状态呈现，不声称网络上已观察到卡住。
- Web 基线：`new-group-modal.tsx:37-46` 空群名使用已选姓名，`:91` 搜索显示名和 ID；`:112-134` 显示状态、ID、设备。私聊联系人 `new-chat-modal.tsx:27-28` 还有加载和空结果。
- 建议：选择成员即可创建，可编辑群名但不强制命名；保留 ID/设备作为次级识别信息，搜索涵盖名称和 Agent ID。顶部显示已选成员或人数，让原生多选时确认范围。不要将 Web 弹层布局原封照搬。

### U09 · P2 · 群里添加成员又丢失身份与多选能力

- 入口：群聊 → 聊天详情 → 添加成员。
- 事实：`ChatInfoView.swift:34-38` 只有单选 Picker 的姓名文字，再点击“添加”；没有候选头像、类型、设备或 ID，也不能一次选多名。群内已有成员行 `:27` 已有头像；同一任务切换到新增成员却只剩姓名，身份一致性未完整延续。
- Web 基线：`group-settings.tsx:225-233` 候选有头像及多选 checkbox，后续批量添加。Web 候选也仍可增强设备信息，因此不声称 Web 在这里已具备全部建议信息。
- 建议：单独的原生成员选择 sheet，沿用建聊候选组件的头像、名称、类型和必要设备信息；支持搜索和多选，一次明确提交。这是一个候选入口，不需“菜单 → 菜单 → 成员”的深链。

### U10 · P2 · Agent Work 有数据但失去人能扫读的工作摘要

- 入口：Agent → 全局 Agent → 工作轨迹 → 某轮/工具。
- 事实：`AgentWorkView.swift:122-124` 标题直接使用 description 或 scope，时间原样显示 ISO；`:109-110` origin 可直接 prettyPrinted JSON，触发详情再开 JSON；`:166` 工具折叠行只有工具名与调用状态。用户需要打开轮次和工具参数，才能判断“因什么唤醒、读了哪个聊天、把消息发给谁”。`:38` 关联执行也常显示 scope 与 session ID。
- Web 基线：`agent-work-panel.tsx:31-56` 区分 inbox/heartbeat/人工输入/cron 手动或定时/后台返回，`:78-79` 取得聊天和参与者名称；`agent-work-presenters.tsx:36-55` 显示“读取新消息/回查历史/发送到 + 真实目标”和业务状态。
- 建议：轮次标题使用现有 trigger/scope 的语义摘要，时间本地化；工具行摘要包含真实目标名称和关键业务状态。ID、完整参数/结果留在折叠详情中，保持可核实。可以先覆盖高频 inbox/conversations/send_message/agent，未知工具仍显示已有名称和原始详情，不新增万能解释框架。

## 审批和已读：单独列出的契约风险

以下不挤入十个可确认迁移退步，但在既有 S6/S13 的真实验收中应检查。

1. **审批首先要让用户知道正在允许什么。** `ChatMessageView.swift:139-155` 卡内只有工具名/问题，参数要 push 到“查看操作输入”；点选权限又打开一个新的提交 sheet。Web `permission-card.tsx:172-181` 直接给人类摘要与操作参数。建议卡内先显示可读动作/关键命令，完整 JSON 仍可展开；常用“允许一次”可直接提交，拒绝理由就近填写。是否减少一次确认是设计判断，不宣称所有确认都应去掉。
2. **聊天审批结果不确定处理与 Work 不一致。** `ChatMessageView.swift:163` 失败只写 error，409 才重读，`submitted` 未置 true，`busy` 结束后选项可再次操作；`AgentWorkView.swift:300-303` 对网络/未确认明确锁定为待确认。该分支可从源码确定，但未实际制造延迟/断网，不能写成已发生重复审批。Web 的 `permission-card.tsx:134-136` 对未确认也可能回到 error，因此这不是独属 iOS 的退步。目标 S13 已要求不能重复批准，应统一“已提交、等待核对”并仅提供刷新确认。
3. **`onAppear` 不是实际看见。** `ConversationView.swift:53` 每个 LazyVStack 消息 onAppear 即 markRead；`ChatStore.swift:169-174` 只检查 selectedID。源码没有消息级 viewport 可见边界。当前 `ConversationView.swift:61` 甚至已明确指出 Lazy row recycling 不能代表 viewport，只用于 bottom 修订。Web `message-pane.tsx:836-841` 至少依据当前可见页面/接近底部再推进。原生是否提前标记了预加载行需真实客户端复现；建议只推进实际可见的最后持久消息，避免按渲染生命周期推断看过。

## 修复与验收建议

可以先完成主实施线的输入候选和头像，再优先收口消息内容完整性（U01）、待发图片可辨认（U02）、时间和复制（U03/U04），随后任务语义/层级（U06/U07）。剩余 U05/U08/U09/U10 都属于现有入口内部的有限改进，不要求新增后端、统一跨端框架或新能力。

实际验收应使用真实数据：一条带交错图文的回复、两张待发截图、跨日消息、带可读 @ 的复制、两页以上历史；一张计划中嵌探索再嵌计划的图；多个不同设备的 Agent 建聊/加成员；至少一次 inbox、heartbeat 或 cron 触发及 send_message 的 Work。每条分别记录实际操作、截图/文字结果和是否通过，不用静态测试代替 iPhone 的阅读、键盘、缩放与辅助技术表现。

本轮没有修改产品代码，也没有更改任何验收状态。仅新增本报告。
