# feat-578 / feat-584：UI/UX 设计与评审失效复盘

> 2026-10-12；独立复盘。范围为 iOS 首版及其两次体验返工、Task 的需求与原型对齐，截至 feat-584 获准实施。本文不评价正在进行的 feat-584 产品实施，不修改技能或历史验收结论。
> 用户期望：Agent 能依据已有产品和使用场景主动完成产品设计，交付值得使用的完整界面，而不是把功能和数据各找一个控件放进去，再由用户逐项指出问题。

## 结论

两次工作都读取了 PR #314 的新规则，也有原型、截图和独立审查。失效发生在规则的实际解释和交付判据：**功能覆盖、入口可达、信息存在，持续替代了对页面目的、信息组织和操作体验的判断。**

iOS 第一版是整套产品设计不足。10 月 5 日用户随手查看登录和聊天就否定了整体质量，主 Agent 随后承认大量使用默认 Form/List、只盯功能和状态。10 月 6 日的提及菜单、头像只是第二次集中反馈的切入口；后续审视还发现内容阅读、待发附件、时间、任务路径、建聊、成员选择、Work 摘要和表单行为等成片问题。不能将这次事件归纳成“两个交互细节没做好”。

Task 则在设计阶段重现了同一倾向：状态列、筛选、详情、系统消息都做出来了，但整体布局是否服务“看清任务完成情况”没有先想透；用户不断要求收紧空间、补真实数据、回到真实聊天界面，最后才重构根任务总览。

主要责任在 author 和实施主 Agent；独立评审沿着同一套过窄判据检查，未充分形成纠偏。规则本身还存在跨阶段传递不足，但“再写一句重视 UI/UX”不能解决这次已有明确规则却被降格执行的问题。

## P0：iOS 用功能映射替代整套产品设计

### 证据

原始 `coverage.md` 的 C01–C34 将 Web 路由/功能映射到原生页面、IM 接口和 Scenario。例如 C05 将正文、提及、命令、草稿、粘贴集中映射到 Conversation/Composer；C14 将主子执行、统计、分页映射到 Work。这个表能防止功能漏项，但无法回答输入是否自然、Work 首屏是否可理解。

`76fe1d7e7` 的 design 将原型判断目标定义为“全量功能能否在四入口中自然找到……是否保留原语义”；P1–P5 主要约束入口、返回、功能路径和状态。字号和 UIKit 外观作为 may-adapt。虽有截图和 Web grounding，契约没有把现有体验的关键价值具体传给实现。

首轮验收版本 `b970e20a6` 可直接核查：

- `AuthView.swift:14–42` 将品牌、输入、登录/注册、连接设置分别放进 Form/Section，配另一层导航标题。系统 Form 本身无错，问题是这种组装没有落实该登录页应有的主次与空间设计。
- `ChatListView.swift` 使用导航大标题、searchable、分类 Section、列表按钮；`+` 又包新建与整理菜单。原生控件具备了功能，并不自动构成成熟 IM 的列表体验。
- `ConversationView.swift:93–110` 待发照片呈现为文件名；提及和命令位于附件 Menu 内的子 Menu。
- `TasksView.swift:101–104,161` 为通用“任务图/任务详情”标题、图中开 sheet、sheet 内继续导航。数据层级存在，用户当前位置和返回路径却没有得到同等设计。
- `AgentWorkView.swift:107–109,122` 可直接显示 turn ID、model ID、原始 origin JSON 或 scope；“能读到数据”没有转成“能读懂正在做什么”。

I:4528 的主 Agent 原话也确认：“我做了结构原型，但实现时大量直接套用默认 Form/List，后续又只盯功能和状态，没有认真对照你的 Web，也没有把实际页面的视觉质量作为验收门槛。”这与以上版本化源码相互印证。

### 根因与改法

**设计的基本单位选成了功能/字段/页面容器，缺少把它们组织成产品的工作。** 这发生在设计阶段，实施又以默认控件完成剩余选择。用户要求“全量原生”是完整范围，不是授权降低体验。

每个主要界面应先明确用户来做什么、最先需要知道什么、最高频动作在哪里、完成后去哪里，再决定布局与控件。功能覆盖表继续保留，但不能充当产品设计完成的依据。原生适配可以改变控件与导航形式，不能默许降低可辨认性、阅读顺序、操作效率和上下文连续性。

## P1：评审有实际操作，但判据围绕功能和结构

### 证据

iOS [设计审查](../archive/feat-578-ios-app/design-review.md) R1 实际比对 Web/原型，结论包括“四入口、浅色分组、青绿主操作”“未发现遮挡或拥挤到妨碍操作”。R2 通过。不是完全没看图，而是把视觉/体验判断落在很低的可用性底线上。

[产品验收 R1](../archive/feat-578-ios-app/M1-native-app/acceptance-r1.md) 明确实际使用“提及菜单”，P1 写“已走的结构 match”。该轮总体为 fail，原因包括照片选择器失效和未完成分支；**不能说它宣布整套产品通过**。但整套视觉与操作组织并未成为它叫停的主要发现，主线仍在继续跑功能，直到用户介入。

Task [设计审查](design-review.md) R1/R2 同样实际看图、操作并发现领取/冲突等真实问题。R3 于 21:46 通过，随后用户仍指出空间浪费、聊天脱离真实界面、信息重复和缺根任务总览。说明审查并非虚构，但检查充分性不足。

### 根因与改法

评审沿着设计已经列出的功能和场景证明“符合”，没有充分独立判断这些场景是否把产品设计对了。对错误或过窄设计的严格一致性检查，会把同一个缺口传下去。

在现有评审里加入一次普通用户目标走查：不先逐按钮核对，从“我要发一句带提及的话”“我要比较所有大任务进展”“我要知道哪项工作等我处理”出发，观察找入口、判断信息、执行和返回的成本。报告对功能正确、视觉组织、交互效率分别给出结论；有功能证据不能推定后两项。

## P2：第一次视觉返工没有覆盖整个 UX 问题

### 证据

10 月 5 日引入 P6，重做九页视觉并检查原生截图。相关视觉审查真实存在，也保留了尺寸、输入和真机限制。10 月 6 日用户仍明确表示“绝对不止这两处”。

随后 [Web 对照审视](../archive/feat-578-ios-app/M1-native-app/ux-audit-web-r1.md) 明确将正在修的提及/头像排除后，另列十项：图文顺序改变、待发图片不可辨认、消息时间缺失、复制内容与显示不一致、其他内容呈现问题、任务关系/层级、建聊、成员选择、Work 摘要等。[商业体验审视](../archive/feat-578-ios-app/M1-native-app/ux-audit-commercial-r1.md) 又指出草稿被无关保存覆盖、离开行为不一致、待处理工作不突出、主操作位置不一致、加载/空结果/零数据混用等。

这些报告部分是源码事实、部分是设计建议或待验证风险，不能将所有条目都称为已复现缺陷。但其广泛分布，足以否定“只剩提及和头像两个局部问题”的解释；[整体修正记录](../archive/feat-578-ios-app/M1-native-app/ux-correction-r1.md) 也实际覆盖了跨页面的一整批体验修正。

### 根因与改法

主 Agent 将第一次全局否定主要转译成视觉修订，缺少重新审视整个使用模型。用户的例子被当成待修清单，未及时作为同类问题广泛存在的信号。

遇到“随便两个页面都不行”“整个 UI/UX”“不止这两处”，主 Agent 应主动检查共同成因和相关界面，汇总后一次修正。范围以反馈揭示的产品问题为界，不要求无限发散、逐像素打磨或新增人工批准。

## P3：Task 把旧布局当约束，遗漏了新目标需要的信息架构

### 证据

用户最初要求看完成情况，随后说明多层拆解的特点。早期需求主要落成“每个任务层级展示直属子任务”。原型在旧左侧根名单、中心内容、右详情中加入状态列。

用户说布局重时，T:2298 的处理方向是缩小筛选、弱化列容器、详情按需展示；T:2329 确认删掉撑高整列的背景。随后仍有顶部占空间、列缺分组感等反馈。这是局部样式修补，尚未回答首屏到底应展示什么。

直到 Q40，T:3164 才明确承认：“现在默认钻进某个根任务，却没有‘所有根任务的完成情况’入口；左侧又把这些根任务当导航，导致你能点进去，却不能统一比较它们。”T:3197 才以“哪些大任务需要我关注”“下一层卡在哪里”推导总览、逐层深入、覆盖详情。

### 根因与改法

“继承现有 UI”被过度理解为保留旧空间结构，而不是保留已有体验价值、围绕新目标做必要改进。原始需求没有把“根总览必须是首屏”写成精确条款，不能倒推成违背一个已经明确的布局决定；但作者应主动识别这一信息架构问题并提出方案，而不是等用户看到原型后补出。

对结构性前端需求，先从用户问题推导信息架构，再决定哪些旧布局继承、哪些需要改变。Task 至少要区分：全部根目标、当前层直属任务、跨层负责人任务。是否需要保留某个侧栏，应由这三种使用方式决定。

## P4：基线与样例取证没有覆盖实际要判断的体验

### 证据

Task 有任务页 React 基线，但 T:2720 用户指出系统消息页面不搭真实页面；T:2725 主 Agent 承认旧聊天示意太简陋，随后读取 message-pane、global.css，并补真实聊天布局，形成 `54dd5dc21`。有一个页面的基线，不代表整个受影响范围都完成了 grounding。

T:2706 用户要求更多长短任务，T:2711 才补多树、长标题、多段描述和不同结果。贫乏数据使布局虽然可点击，却不能充分显露实际使用中的信息密度与层次问题。

系统消息又加入反复的“任务动态”标签、结果摘要和展开控件；用户质疑后，主 Agent 核对 Raft 并承认是自行增加，最终简化。这反映了将数据能力尽量呈现出来的倾向。

### 根因与改法

基线和渲染被当成做过就算的步骤，证据没有紧扣本次判断。原型应该能让用户判断实际体验，而不只是展示功能路径。

对受影响的每个界面核对相应基线；样例使用该场景正常会遇到的多对象、长短内容、不同状态。无需制造极端数据或固定截图数量。每个新增信息/动作都能说明它帮助用户作什么决定，不能因为字段存在就默认常驻显示。

## 按 skill 归并的最小改进建议

这些是供后续修改采用的建议，本轮未改 skill。

| 位置 | 建议 | 来源 |
|---|---|---|
| change-spec-author | 将关键用户目标转成可观察体验结果；功能迁移时记录应保留的关键使用方式，不只列功能名/API；不把常规控件选择逐个问用户 | P0、P3 |
| change-design-author / 原型参考 | 在既有原型段明确页面目的、信息优先级、主路径与返回；用当前产品对照保留/改善的体验，说明布局选择；真实感样例覆盖正常内容差异 | P0、P3、P4 |
| design 模板 / must-match | 契约保留辨认、阅读、操作成本和上下文；may-adapt 可变的是控件/平台形式，不能据此放弃体验要求 | P0、P1 |
| change-design-reviewer | 在功能/一致性检查外，独立判断方案是否解决原始用户目标；不把不溢出、入口存在、用了相同色彩当成充分体验证据 | P1、P3 |
| change-orchestrator-simple / worker | 实施主 Agent 对实际客户端的整体质量负责；默认控件不能自动替代设计；全局负面反馈触发共同成因检查，不逐句打补丁 | P0、P2 |
| change-reviewer | 在真实产品既有验收中对照基线操作和扫读效果，区分功能正确/视觉组织/交互效率；不能只核 Scenario 的狭义成功结果 | P1、P2 |

优先两项：**把设计完成标准从功能覆盖提升为有依据的完整界面与交互方案；让现有独立评审对方案本身作产品判断。** 不增加独立 UI 审批阶段，不机械要求多个竞品或多套方案，不把用户变成逐页设计师。
