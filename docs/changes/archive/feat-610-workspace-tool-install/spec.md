# feat-610: Agent 自建 DSH 插件与 workspace 插件管理

## 原始需求

> 没迁移到DSH之前，我可以让agent自己写python脚本到workspace固定目录下变成工具，现在呢，现在可以让agent怎么给自己加工具

> 那现在 Agent 能自己写插件并启用吗？还是得我手动加白名单、重启节点？我希望它能像以前一样自己给自己加工具。

> DSH本身不应该支持这个能力吗，我记得这是DSH宣传的卖点

> 那就复用 DSH 原生能力把这段接完整，让 Agent 能自己写工具、安装并启用，不用我手动加白名单和重启。保留 workspace 隔离，重启后也要能继续用。

> 但配置页目前只能查看自建工具的状态，还没有手动卸载按钮。也就是我点击，它不能卸载？为啥不能纳入管理，我理解这里所有工具都可以关掉，关掉就是等agent不忙时，重启了session。现在不是吗

> 而且我应该纠正下，改完之后，agent应该是不但可以做工具插件，而是可以用dsh的能力，做各种插件吧。那我们是否不应该在工具开关中管理，而是单独做一个插件开关，就类似工具开关一样，列出所有agent弄的插件

> 你给我构思吧，我睡觉了，转成更规范的change-spec，design模式来开发。自己思考清楚整个用户体验。最终提pr并别关测试服务，让我可以去看啥效果。

## 澄清记录与自主裁决

用户授权自主构思完整体验并按 Full spec/design 开发。前一轮以工具名 denylist 关闭自建工具的提案被本轮插件级管理取代；尚未实现的 denylist 不进入产品。

目标为 Agent 使用 DSH 原生扩展能力创作、安装和管理标准插件，工具只是插件的一种贡献。插件配置和安装资产以 workspace 为边界；同 workspace 的 Agent 共享插件选择，页面明确提示影响范围。插件管理独立于静态工具使用权限，关闭插件撤销整个插件的运行贡献，卸载另外执行。支持在 workspace preset 内可运行的标准插件（包括工具、提示词扩展、事件/服务贡献及组合）；不提供宿主级 runtime/provider 替换或跨 workspace 全局管理。

## 用户场景

用户让助手把每月报销统计做成可复用工具，并添加自动遵循报销报告格式的提示词插件。助手在既有聊天创建、安装并真实使用两种插件。用户进入该 Agent 设置的“插件”页签，能看到两个插件及说明，即使后一个没有工具也不会消失。关闭后，整个插件的行为停止；重新开启无需重装。用户可展开详情或单独卸载。忙碌时显示等待空闲，完成后更新状态；节点离线或失败不能伪装成功。整个过程保留聊天历史，重启后已完成的选择保留。

## 验收标准

### Requirement: Agent 可自助创作并使用标准 DSH 插件

#### Scenario: 工具和非工具插件在既有聊天生效
- **GIVEN** Agent 已获准管理插件并具备必要文件操作能力
- **WHEN** 用户要求增加可复用工具和不提供工具的行为扩展
- **THEN** Agent 能创作、安装并验证两类插件的真实效果
- **AND** 用户无需手改白名单或重启节点，历史保留

### Requirement: 插件安装与选择按 workspace 隔离并持久保存

#### Scenario: 同 workspace 共享，其他 workspace 隔离
- **WHEN** 一个 workspace 安装并开启插件
- **THEN** 该 workspace 的聊天获得插件贡献，其他 workspace 不能发现或使用该私有贡献
- **AND** 同 workspace 的 Agent 共享插件开关，页面清楚说明这一范围

#### Scenario: 已完成的选择跨重启保留
- **WHEN** 用户开启、停用或卸载插件后节点重启
- **THEN** 已完成的状态保持，既有聊天无需重新安装或创建
- **AND** 更新已停用的同名插件默认保持停用，显式开启才恢复

### Requirement: 插件管理有独立、完整的用户入口

#### Scenario: 查看全部已安装插件
- **WHEN** 用户打开 Agent 设置的插件页签
- **THEN** 列出当前 workspace 全部已安装插件包，包括停用、加载失败和不提供工具的包
- **AND** 名称、说明、版本、实际状态、开关与卸载操作可辨认，空列表说明可以在聊天中让助手创建
- **AND** 插件不作为工具开关中的只读卡片重复展示；静态工具权限保持原有逻辑

#### Scenario: 关闭与重新开启整个插件
- **WHEN** 用户点击插件开关
- **THEN** 无需点击表单保存，插件管理显示真实处理状态
- **AND** 停用后工具、提示词及其生命周期管理的事件/资源贡献一起撤销，重新开启恢复；安装包保留

#### Scenario: 卸载插件
- **WHEN** 用户选择卸载并确认具体插件及 workspace 影响范围
- **THEN** 插件停止并从已安装列表移除，其他插件继续运行，源码和用户工作文件保留

### Requirement: 运行中、失败和断线有准确反馈

#### Scenario: 忙碌时等待安全应用
- **GIVEN** workspace 的 Agent 正在执行请求
- **WHEN** 用户在网页停用或卸载插件
- **THEN** 页面显示等待空闲，不取消在途任务或重启 session
- **AND** 空闲后应用并显示最终状态；同 workspace 并发管理不会互相覆盖或死锁

#### Scenario: 安装失败可以修复
- **WHEN** Agent 安装无法加载的插件
- **THEN** 返回失败诊断，配置页可见异常；其他插件仍可使用
- **AND** 修改本地源码后可重新安装修复

#### Scenario: 离线或待应用期间重启
- **WHEN** 节点离线、请求结果未知或待应用时进程重启
- **THEN** 页面提示无法确认，重新连接或刷新后按原生持久状态展示，不把未完成操作当成成功
- **AND** 未完成操作允许用户重新发起

### Requirement: 自建插件不覆盖原有工具权限

#### Scenario: 安装新插件保留既有禁用选择
- **GIVEN** 用户关闭了一个已有静态工具或 Agent 工具集显式为空
- **WHEN** 同 workspace 安装插件
- **THEN** 既有静态工具不会被重新授权，显式空工具集与子任务限制仍有效
- **AND** plugin_manager 控制 Agent 的安装管理权限，网页管理权限来自可信用户身份

## 范围与非目标

在范围：标准 workspace 插件创建、安装、列表、开关、卸载、热生效、持久化、网页控制与真实工具/非工具演示。现有标准 plugins.json 静态扩展不自动迁入包管理列表。

非目标：宿主核心插件管理、进程沙箱、全局市场、任意插件类型兼容性保证、原生 iOS 新页、生产部署、安装器发布或 DSH fork。
