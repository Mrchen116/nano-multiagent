## 澄清记录

2026-10-15：Agent 提出 workspace 能力扩展方案，用户以上述第三条原话接受并要求建立 unit，随后以第四条原话授权继续完整设计、实施与交付。真实测试需使用常规自然语言任务，并观察 Agent 的实际轨迹与各种插件的业务效果；不能仅以模板测试或安装成功代替模型理解和创作能力。没有新增未回答的问题。

以下是对已接受方案的整理，不是新增的用户原话：

- Agent 可以扩展所在 workspace 的工作能力；Nano 继续负责身份、权限、消息交付、节点生命周期和客户端。
- 第一版整理已有工具、提示词、隔离服务、局部事件监听和压缩能力，提供随包开发 Skill、按需资料、可运行模板和当前接口发现路径。
- MCP 是后续支持方向，本 unit 不承诺新增 MCP 接入；先核实其实际挂载与权限链路，未核实前不发布可用承诺或照搬原生模板。
- 不开放任意客户端代码注入，不新增不可信插件沙箱，不另造 Agent Loop、插件运行时或通用后台调度器。
- 技术设计继续明确发现接口的具体形式、受支持事件清单与逐项验证，不将宿主全部公开 API 自动视为受支持扩展面。

## 用户场景

1. 用户希望助手处理一种新的业务文件或查询外部业务数据。Agent 判断现有能力不足后，读取适用于当前 Nano 版本的开发指导，创建并安装工具，在原聊天里实际使用并交付结果。
2. 用户希望报告遵循固定格式，或希望建立可持续更新的资料索引。Agent 可添加提示词贡献、插件私有索引服务及适用的局部监听。插件有明确的作用范围，停用后不继续影响后续工作。
3. 用户希望改变当前 workspace 的上下文压缩方式。Agent 按高级指导安装适用引擎，验证工作效果；停用后恢复默认行为，不影响其他 workspace。
4. 用户要求定时生成日报。插件负责所需业务能力，定时与结果交付继续使用已有产品入口。用户仍能通过既有产品方式管理任务和接收结果。
5. 用户希望给 iPhone、Web IM 增加按钮，修改权限或接管其他 Agent。Agent 能说明这些不属于当前 workspace 插件的受支持范围，按用户目标提供文件、报告或独立应用等适用交付形式，不谎称修改了客户端。
6. 用户更新、停用或重启插件；共享 workspace 的 Agent 看到一致的安装状态，其他 workspace 保持原状。加载失败时用户收到真实失败与恢复结果，而不是仅有“安装成功”。

## 开放能力与边界

| 能力 | 本 unit 的支持范围 | 边界 |
|---|---|---|
| 自定义工具 | 文件转换、数据查询、业务 API、调用脚本 | 新工具不覆盖既有受限工具，不把安装视为业务动作的额外授权 |
| 提示词与上下文贡献 | 格式约定、领域提示、适用上下文 | 不以插件重新定义产品身份、权限、交付规则 |
| 插件私有服务与状态 | 索引、缓存、业务数据、连接及资源管理 | 数据归属明确，资源随插件生命周期释放，不发布影响其他 workspace 的根服务 |
| 局部事件监听 | 适用的 workspace/preset 事件，例如索引更新和插件工作记录 | 只指导使用作用域已核实的扩展点，不承诺任意事件天然隔离；不旁路接管消息路由或交付 |
| 压缩引擎 | 保留现有高级扩展能力，提供开发与验证指导 | 限当前 workspace，停用恢复默认；不接管宿主整体运行时 |
| Cron / Workflow | 复用既有调度和编排入口，组合插件能力 | 不另起普通业务任务的常驻 Agent Loop 或重复调度体系 |
| 用户界面 | 按需要交付报告、文件或独立应用 | 不承诺 DSH UI 插件能修改 Web IM、iOS、飞书或轨迹查看器 |
| MCP | 说明当前支持边界及其后续方向 | 本次不新增接入承诺，不提供未经验证的模板 |

安装归属为 workspace。同一 workspace 的多个 Agent 会受到同一安装、配置及启停变更影响；运行时能力选择、子任务限制和既有权限仍按 current 契约执行。

宿主保留账号身份、workspace 归属、审批与凭据管理、Inbox 路由、消息投递与去重、用户收件状态、跨 Agent 会话管理和节点生命周期。宿主 profile、DSH 安装包及 Nano 源码修改不属于自建插件支持面。此处定义支持契约与 Agent 行为约束，不宣称现有机制已构成任意 JavaScript 的强安全隔离。

## Agent 如何获得开发知识

第一版采用已讨论的三层信息组织，具体装配及接口设计留给 design：

1. **工具入口**：管理工具简要说明作用范围、管理能力、生效结果及专门开发指导入口，不继续承担完整教程。
2. **专门 Skill**：随安装版本提供 `nano-plugin-development`，默认可发现；任务匹配时先读取指导，尊重用户明确的技能禁用选择。指导先区分现有工具、Skill、Workflow 与插件，避免普通任务都创建插件。
3. **按需资料与实例**：提供工具、提示词、隔离服务三类可运行模板，以及局部事件和高级压缩指导。资料解释创建、配置、更新、清理、验证和失败恢复，不引导操作 DSH 宿主或客户端槽位。

开发指导同时提供当前适用接口的查询路径，使 Agent 能获取当前运行时版本下的接口说明、配置约束和包文档位置，并区分可发现 API 与 Nano 支持的扩展点。优先复用公开能力，缺少或不适用时明确说明，不凭旧模板猜接口。具体查询工具、结果范围与技术验证由 design 确定。

标准开发旅程是：判断是否需要插件 → 读取指导 → 查适用接口 → 创建最小可用能力 → 安装并检查生效结果 → 实际使用 → 验证停用及恢复 → 向用户说明位置、影响范围和验证结果。知识资料本身需要随产品版本交付；不以模型预训练知识或联网找到的最新 DSH 文档代替当前版本依据。

## 验收标准

### Requirement: Agent 能获得适用当前 Nano 的插件开发指导

#### Scenario: 首次请求开发工具（用户场景 1）
- **GIVEN** 用户已开启插件管理与相应开发资料访问能力，workspace 没有目标工具
- **WHEN** 用户要求增加一种可复用的业务文件处理能力
- **THEN** Agent 能通过随包指导完成开发、安装和实际使用，交付正确的处理结果，无需用户另找教程或手动修改工具选择
- **AND** 开发说明及实际工作不依赖 DSH Web UI 或宿主 profile 修改

#### Scenario: 资料被禁用或所需接口不适用（用户场景 1、5）
- **WHEN** 用户禁用了开发 Skill，或请求依赖当前版本不可用的扩展点
- **THEN** Agent 尊重禁用选择，明确可验证的能力边界，不绕过选择、不编造接口或宣称未经验证的功能已可用

### Requirement: 开放能力覆盖工具以外的 workspace 工作需求

#### Scenario: 报告格式与资料索引（用户场景 2）
- **WHEN** 用户分别要求统一报告格式和建立能够跟随资料变化更新的索引
- **THEN** Agent 能依据对应指导交付可用的格式贡献及索引能力，更新后的资料能被后续查询使用
- **AND** 用户停用相应插件后，后续报告恢复原有格式，相关监听及受管服务停止产生新的工作；既有用户数据不被擅自删除

#### Scenario: 自定义压缩与恢复（用户场景 3）
- **WHEN** 用户启用适用的压缩插件并触发自动及人工压缩，随后停用该插件
- **THEN** 用户可继续对话并使用所选压缩方式；停用后恢复默认方式，其他 workspace 的行为保持不变

### Requirement: 插件遵守 Nano 产品责任边界

#### Scenario: 业务插件与已有调度交付组合（用户场景 4）
- **WHEN** 用户要求定时生成并接收依赖插件能力的日报
- **THEN** 用户可通过现有定时任务入口查看和管理任务，并通过既有聊天交付路径收到结果，不出现重复调度或插件另建的不可管理任务循环

#### Scenario: 请求客户端或宿主扩展（用户场景 5）
- **WHEN** 用户要求插件给 iOS/Web IM 增加按钮、改变审批身份规则或接管其他 workspace 的 Agent
- **THEN** Agent 说明当前插件支持范围，不将安装完成报告成客户端修改成功或权限变更成功；有适用替代交付时说明其实际位置和限制
- **AND** 用户仍能使用原有客户端、权限和消息交付流程

### Requirement: 插件变更有清晰的归属与可验证的生命周期

#### Scenario: 更新、重启及撤销（用户场景 6）
- **WHEN** 用户要求修改已创建插件，重启节点后再停用或移除
- **THEN** 更新后的能力在实际调用中生效，重启保留安装及启用选择，停用或移除后后续工作不再使用该贡献
- **AND** 同 workspace 的 Agent 可观察到一致的管理状态，其他 workspace 不受影响；用户能理解共享影响范围

#### Scenario: 加载或功能验证失败（用户场景 1、6）
- **WHEN** 插件无法加载，或安装后实际使用失败
- **THEN** Agent 明确报告未可用及可行动的诊断，能修正后重试；只有实际验证成功才报告该能力可用，原有管理入口仍可用于修复

#### Scenario: 管理关闭与原有工具限制（用户场景 5、6）
- **GIVEN** Agent 未开启管理能力、工具选择为空或已有工具被明确禁用
- **WHEN** 用户使用该 Agent，或共享 workspace 安装了插件
- **THEN** 既有能力选择按原契约保持，不因新插件而自动取消已禁用工具或子任务限制

### Requirement: 用户能准确理解插件信任与验证范围

#### Scenario: 查询插件隔离承诺（用户场景 5、6）
- **WHEN** 用户询问插件是否被严格限制在 workspace 内、是否可以安全运行任意来源的代码
- **THEN** Agent 和随包资料说明这是可信本地扩展，区分作用域与强安全沙箱，不把生命周期审计描述为任意代码的操作系统隔离

## 范围与非目标

在范围：明确支持矩阵与宿主边界；随版本交付的专门开发 Skill；工具入口精简；按需模板与参考；当前接口发现路径；已有插件能力的真实开发、更新、重启、停用、失败恢复与跨 workspace 回归验证。现有产品手册与开发资料职责要清楚，长期事实不重复维护；current spec 在实施验收后再归并。

非目标：新增插件市场、全局共享插件安装机制、任意客户端扩展系统、不可信代码沙箱、第二套运行时或 Agent Loop、独立调度器、权限系统重构，以及本次尚未承诺的 MCP 接入。不开启与实际需求无关的通用框架建设。

本首文档不预填 design、delta-spec、milestone 或验收结论。下一阶段为 `change-design-author`，将能力发现、实际事件作用域、模板与回归策略落实为技术方案。
