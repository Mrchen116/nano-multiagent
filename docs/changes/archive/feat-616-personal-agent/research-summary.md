# 个人助手：三方关系与消息机制研究（供设计对齐）

2026-10-16；Nano main `481467ac16f0eda4561fca5c8230050541600de9`。以下是推荐方案与证据，不是已实现功能，也不是已通过 Gate 2 的最终设计。

## 1. 角色：固定服务一个人，责任可以协助，身份不能混淆

用户负责目标、偏好和授权；个人助手持续理解这些目标、发现值得处理的变化、准备和执行已授权工作；外部人和专业 Agent 提供消息、请求、协作和结果。个人助手始终对自己的用户负责，但保留外部协作的真实责任与事实。

“我的任务”应进入助手的协助视野，不必先改派成“助手的任务”。例如张三负责周五交方案，个人助手可以整理材料、请已获授权的专业 Agent 做分析、形成草稿并提醒缺项；任务负责人仍是张三，实际分析的执行者仍如实记录。获得资料、发起协作、对外承诺、宣布完成分别有不同边界。

已有任务图仍是唯一进度事实源。既有 assignee、creator、真实 actor、结果和来源继续使用；不因新增个人助手就造另一套任务状态、必填交办人或验收人。个人助手的关注/协助只保存原任务引用、授权范围及必要的协助控制状态，不复制任务正文与状态成为第二份真相。

### 三类任务都要覆盖

- **你负责，助手协助**：负责人不变，助手推进已获准的可委托步骤；准备完材料不等于你已开始或完成原任务。
- **助手负责，你交办**：明确改派后，助手实际接手再开始；分配成功不冒充已运行。
- **别人负责，你关注**：助手关注依赖、风险与对你的影响，不能凭关注就替你催人、改对方状态或指挥其 Agent。

“停止助手跟进”“关闭原任务”“停止正在执行的工具”是不同操作。对方改派或取消后，迟到结果不应恢复旧授权；你已处理的事情应停止旧提醒。协助状态如果需要持久化，只表达等待你、等待外部、暂停等协助事实，不替代原任务状态。

当前任务通知也不是完整观察机制：结果通知面向创建者/直属父任务负责人，父任务关闭主要通知直属 Agent 负责人，不能保证真人背后的个人助手知晓。因此需要受授权的任务事件投影或按需复查，不能仅给原通知加一个名字。

经理/任务创建者的要求不自动成为本人助手的授权；本人授权也不能绕过组织规则。原任务改派、关闭或权限变化后，须重读并停止依赖旧授权的新副作用。

收到、接手、运行、提交结果、证据核验和业务接受是不同事实；外部 Agent 声称完成或任务标为 done，不等于已验证交付或本人已接受。

### 外部协作不能打开私人工作轨迹

你可与其他人共同推进一项任务，但个人助手的全局上下文可能同时包含其他私聊和私人资料。外部联络、公开名片、被提及或共享任务都不能顺带开放它的完整 Work、工具轨迹、记忆或子执行继承历史。应分享该任务允许披露的产物和验证摘要；当前“某一任务的轨迹选区”不是安全的数据过滤。

## 2. 消息应该立即给它吗？先区分六步

1. **读取资格**：候选来源取你当前的资源权限、组织/会话规则和明确协助授权范围的交集；跨空间须走专门受限通道，不能继承 owner 权限。
2. **持久收件**：符合范围的新事件及时保留引用和原始作者。它可以知道“有新消息”，无需复制全量正文和附件。
3. **唤醒处理**：本人请求、等待中的关键回复可优先；普通群更新可合并。入队不等于每条调用一次模型。
4. **按需取内容**：处理时再次核对权限、原消息和上下文；退出群或撤销协助后的旧队列不能继续取数。
5. **通知本人**：只有需要决定、有实质进展、紧急变化或重要阻碍时冒泡；你已处理的不再重复催促。
6. **对外行动**：草稿、Agent 身份回复、真人身份发送、接受承诺分别裁决。第三方消息即使被它读到，也不是你的新指令。读取委托不授予原任务写回、claim 或代发权限；行动与投递前须复核当前授权。

这让主动性和打扰成本分开：可以及时收集，但不必立刻打断你、立刻回应对方。助手消费消息也不应替你清除 IM 未读。

## 3. 推荐的三方通信默认（待产品确认）

| 通信 | 推荐行为 | 不随之获得的权限 |
|---|---|---|
| 你→个人助手 | 优先处理，沿用私人上下文；忙时保留新请求 | 不因换来源丢弃既有工作 |
| 同属你的专业 Agent→个人助手 | 已交办工作的结果/阻碍进入协作链，去重后处理 | 同 owner 不等于可冒充你批准动作 |
| 外部人/外部 Agent→个人助手 | 默认不开放私人主会话；若需要“联系我的助手”，用独立受控请求入口 | 不得看到私人记忆、跨聊天上下文、全部工作轨迹 |
| 外部人/Agent→你 | 在你启用的协助范围内记录观察事件；按相关性和待办条件处理 | 不能原样包装成你发给助手的命令 |
| 群聊普通更新 | 获准范围内作为背景或合并观察；提及、重要任务变化优先 | 不自动加入群，不因可读就可发言 |
| 个人助手→你 | 私聊交付建议、草稿、关键进展与决定 | 不能把所有机器事件逐条刷进聊天 |
| 个人助手→外部 | 使用明确身份、目标和任务授权；保留发送证据 | 读授权不等于发授权，超时也不等于同意 |

**建议产品第一次启用时一次讲清协助范围，日常按范围自动工作，而非每一条消息都询问。** 全量私信、选定聊天、群提及/关注任务三者的默认组合仍需与你对齐；当前原型只模拟显式选中消息，不代表最终默认只能手动转交。

## 4. 当前 Nano 的事实与关键缺口

- 首次引导已经创建 global Agent；但 `heartbeat`、`cron_scheduling` 明确关闭，而且恢复时有 `agents[0]` 回退。需要服务端唯一的个人身份绑定，不能靠名称或列表排序。
- 已有 global Inbox 会持久保存消息；普通未提及群更新可不唤醒，direct/ALWAYS/mention 可触发。现有 global 输入忙时持久入 Inbox，待主运行空闲再唤醒；拟新增观察流也应复用同一主运行。
- 目前人际私聊没有“收件真人→个人助手”的旁路。个人 Agent 也不能凭 owner_id 直接读真人的公司空间任务。
- 现有任务 claim 不允许助手抢占真人已负责的任务。协助要在原任务上保持责任，并通过真实 actor 和受委托范围工作。
- 现有幂等键防同一条重投，不防 A 新发→B 新回→A 新回。需要因果链、回合/时间/成本约束以及明确结束条件；速率限制仅抑制洪泛，不能终止慢循环。
- global 的精确 `/stop` 在普通真人输入路径上会取消主运行。现行共享 global 契约允许已触达的真人停止；拟新增观察流必须与本人控制事件分开，不能把第三方原文接成普通 direct user input。这是设计必须防止引入的风险，未将其宣称为已验证线上漏洞。
- 绑定个人助手的节点转交、离线、stale、旧 company Agent 和 single_thread Agent 的迁移都需要明确处理；不能连同硬件把个人身份和私密历史送给别人。

完整静态证据见 research/ 下 current-code 审计。没有用静态检查冒充真栈测试。

## 5. 开源项目具体借鉴什么

### OpenClaw：让“知道了”和“开一轮”“说出去”分开

当前源码快照的 `sessions_send` 支持 `mode=notify`，只排队上下文而不开轮；跨 session 信息保留 `isUser=false`，回复回到请求者一次，不自动感谢来回。Ambient room events 则是另一种选择：开安静轮次，但最后文本保持私有，必须显式发送才公开。这两种策略成本不同，不应混为一谈。

来源：[session tools](https://github.com/openclaw/openclaw/blob/d0c81f7ddabefc88bce6be9b72c00f1c40bfee5b/docs/concepts/session-tool.md)、[ambient room events](https://github.com/openclaw/openclaw/blob/d0c81f7ddabefc88bce6be9b72c00f1c40bfee5b/docs/channels/ambient-room-events.md)。已核对官方文档及选定实现，未运行该项目。

### Hermes：背景记录可以不调用模型

Telegram observe 模式可把未提及的群消息写入带来源的共享记录，不 dispatch Agent，后续被提及时再使用。Bot Chat 的队列接收、执行完成和向人投递也区分。适合借鉴低成本背景摄取，但不能照搬其所有 session 拓扑作为 Nano 的租户隔离保证。

来源：[observe mode](https://github.com/NousResearch/hermes-agent/blob/f57e46207d2adf267c9fec49e9ec6653d0e4aa1e/website/docs/user-guide/messaging/telegram.md)、[cron receipts](https://github.com/NousResearch/hermes-agent/blob/f57e46207d2adf267c9fec49e9ec6653d0e4aa1e/website/docs/user-guide/features/cron.md)。

### NanoClaw v2：可联系是有方向的授权关系

当前 mailbox 用 `trigger=0/1` 区分背景和唤醒。A2A 发送检查 source→target destination grant，可要求指定真人批准；等待批准后还会复核授权是否撤销。可以借鉴“能联系你”与“能看你历史/让你做任何事”分开；不是给全体 Agent 开一个无限互发群。

来源：[architecture](https://github.com/nanocoai/nanoclaw/blob/d61af17b541f52632c6194692a166184839a926f/docs/architecture.md)、[guard](https://github.com/nanocoai/nanoclaw/blob/d61af17b541f52632c6194692a166184839a926f/src/modules/agent-to-agent/guard.ts)、[approval replay](https://github.com/nanocoai/nanoclaw/blob/d61af17b541f52632c6194692a166184839a926f/src/modules/agent-to-agent/message-gate.ts)。不把仓库历史 v1 SPEC 当 current。

## 6. 论文给出的关键约束

- **Electric Elves** 曾为人提供持续运行的代理，并让代理协调、通知各自主人。实际部署出现超时后越权感、连续延迟和隐私泄漏。它支持研究个人代理协作，也说明“替我考虑”不能省略权限和停止条件。[部署教训作者稿](https://www.cs.cmu.edu/~pscerri/papers/Elves_lessons.pdf)
- **Adjustable Autonomy** 用控制权转移策略衡量等待、决策和协作成本。对 Nano 的启示是保留“等待本人”“询问其他协作者”“执行已有备用授权”的不同状态；没回复不自动扩大权力。[JAIR 论文](https://doi.org/10.1613/jair.1037)
- **Attention-Sensitive Alerting / BusyBody** 把消息紧迫性与打断人的代价分开。支持“立即收件、择机提醒”，但其小规模/特定环境评估不能证明现代 IM 的所有提醒都合适。[Attention-Sensitive Alerting](https://www.erichorvitz.com/priorities.pdf)、[BusyBody](https://www.microsoft.com/en-us/research/wp-content/uploads/2004/11/busybody_cscw.pdf)
- **Proactive Agent (2024, v2)** 将事件、候选任务、是否介入分开；报告的 F1 为 66.47%，precision 49.78%，不能仅用总体分数掩盖误打扰。合成环境和模型评判不是上线人群验证。[论文](https://arxiv.org/html/2410.12361v2)
- **Authenticated Delegation** 提议分开人的身份、Agent 身份与委托权限。适合指导三方事件里的 principal/actor/grant，但这是架构提案，不是已经证明万无一失的授权产品。[论文](https://arxiv.org/html/2501.09674v1)

## 7. 后续设计与验收

正式 spec/design 要把上面的选择投影到：首次设置、唯一身份与恢复、消息协助设置、原任务协助、外部协作请求、通知与离线反馈。原型 A/B 当前只比较入口，尚未完整表达全部机制。

验收至少包括：两端并发首次创建、重启恢复；本人负责的任务保持负责人而获得实际协助；原权限撤销后的旧消息；第三方伪造本人指令；Agent循环；本人已经回应后的停止提醒；等待确认不自行批准；草稿迟到不串会话；个人上下文不随外部联络开放；离线恢复不刷屏。模型相关性评分与真实越权必须分别计量，不能用整体成功率抵消越权。

状态：入口待用户看原型后决定；主动观察范围与对外协作默认待产品对齐；原型视觉核验目前受环境阻塞。尚未完成 Gate 1/2，不应进入实施。
