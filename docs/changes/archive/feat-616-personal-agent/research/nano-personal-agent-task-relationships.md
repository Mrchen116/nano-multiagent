# Personal Agent：真人任务、个人助手与外部协作者的关系设计

研究基线：`/workspace/shared/nano-personal-agent-design`，main，`481467ac16f0eda4561fca5c8230050541600de9`，2026-10-16。只读产品代码；未运行测试；已有 untracked `docs/changes/feat-616-personal-agent/` 未改动。本文为 proposed 设计研究，不是 current 契约，也不替用户决定持续读取范围。

## 1. 核心结论

个人助手服务的是“这个人要完成的事”，不是只管理 assignee=自己的任务。必须同时支持：

1. **本人负责，助手协助**：责任继续在本人。助手能在获准范围内理解、准备、执行具体步骤、组织证据、提示待决事项；“帮我推进”不能偷偷改派给助手。
2. **助手负责，本人交办**：原任务 assignee=助手；助手承担这项工作的交付协调，内部 subagent 不改变对用户的交付责任。是否接受、开始执行与任务分配是不同事实。
3. **他人负责，本人关心**：助手帮助本人了解影响、等待依赖、准备自己的下一步。关注不构成对他人或其 Agent 的指挥权，也不授予任务写权限。

这三类是可重叠、随时变化的查询关系，不是必须写进每个任务的三种新角色。继续使用现有 created_by、assignee、updated_by_actor；本人和个人助手的固定产品绑定另有权威。新增内容若需要持久化，应是“本人授权助手如何协助这个原任务”的有限关系，不是第二套任务状态、交办人、验收人或强制审批角色。

## 3. 三角关系与四个问题

三角中的顶点是本人、个人助手、外部人/独立 Agent。每条边分别回答：

- **谁负责结果**：原任务 assignee，不能由“最近谁操作”推断。
- **谁实际操作**：真实 actor；来源指令或授权引用是证据，不能改写 actor。
- **谁允许此动作**：已验证本人指令/明确站立授权，结合组织限制与工具审核；第三方消息只提供事实或请求。
- **谁可以看见**：源对象当前 ACL 与授权范围交集；能读不代表可向别的顶点披露。

例：经理把“交季度报告”分给小王；小王请个人助手先整理数据；助手请经明确授权的分析 Agent 计算某指标。季度报告负责人仍是小王，分析结果由真实分析 Agent 产出，助手负责所承诺的整理和回传。经理不会因为创建了任务而取得小王私人记忆；助手也不会因为了解经理需求而获得代表小王承诺交付日的权限。

不强制加“beneficiary、requester、executor、reviewer”到每个任务。实际交付预期可以存在任务描述/结果；特定审批或组织验收需要时使用具体流程，不能假装所有图任务都有一个系统强制验收人。

## 4. 动作权限矩阵（建议默认，须通过产品确认）

下列“可”均以源可访问、工具允许且动作被本人授权为前提。持续观察与主动唤醒范围尚待用户决定，不由此表授予。

| 动作 | 本人负责 | 助手负责 | 他人负责、本人关注 |
|---|---|---|---|
| 观察/解释 | 在批准范围读状态、依赖、证据 | 同左 | 同左；关注不增加可见性 |
| 私下准备 | 可准备本人要用的资料/草稿/建议 | 可准备完成任务的材料 | 可准备对本人的影响与下一步；不暗中接管他人产出 |
| 执行具体步骤 | 按本人批准范围执行可委托部分；人必须做的部分保留给人 | 按任务授权执行，不从分配事件推导无限许可 | 本人自己的工作可执行；他人的任务须另获明确协作/派工授权 |
| 更新原任务正文/结果 | 有真实写资格且获准时可写，actor=助手 | 同左 | 默认建议或汇报；共同编辑能力不等于主动改别人计划 |
| 改原任务状态 | 可记录本人明确开始/提交/完成事实；助手准备中不自动设本人 doing | 真正接手可 claim；提交结果偏向 in_review | 无特别授权不因观察推断改状态 |
| 改派/取消分配 | 与协助独立的明确操作，展示前后负责人 | 同左；分给外部 Agent 还需派工权限 | 不能由“帮我盯着”推出改派 |
| 对外沟通 | 明确接收方、目的和允许披露范围；以助手真实身份 | 相同；任务分给助手不自动授权任意外发 | 跟踪不默认允许催人、承诺或回复 |
| 接受结果/验收 | 可以汇集/核对证据；正式业务承诺须本人相应授权 | 可核验内部产出，不代本人接受未授权业务后果 | 可以报告“对方标为完成”；不擅自宣布本人已接受 |
| 关闭/删除 | 停协助、关闭任务、删除记录是三种不同操作 | 同左；删权限仍是创建者/真人管理员规则 | 关注可取消，源任务不随之关闭 |

“帮我推进”建议语义：建立针对该任务的协助意图、准备并推进已授权步骤、报告需要本人决策的下一步。它本身不包含改派、承诺新期限、发送第三方消息、接受交付或删记录。若用户所说推进明显包含具体对外动作，可按该原话授权处理，而非机械多问一次。

## 5. 最小持久模型：一个任务事实，有限协助状态

**图仍是任务唯一权威**：graph_id/node_id、title、status、assignee、result、父子/依赖均原处维护。个人入口实时读取投影，缓存标注版本/观察时间且不用于反向覆盖。

若产品需要可见、可取消且跨重启可靠的“帮我推进”，建议最小 owner-scoped assistance relation：

- `(owner_user_id, graph_id, node_id)` 唯一；当前个人助手从绑定解析，不复制固定角色身份。
- 当前授权的目的/范围、来源指令 ID、授予/撤销时间、可适用的动作类别；授权若已有统一存储，只保存引用，不能建第二套权限规则。
- 协助状态如 active / waiting_for_owner / waiting_for_external / suspended / ended，仅描述**助手的协助**，不冒充 task status。可与现有待办/运行跟踪设施合并，首版不要求另开一张表。
- 最后检查/提醒的 source event 或 revision、停止条件、必要的 operation/run 引用。仅为去重恢复和判断陈旧，不复制一份任务描述与结果数据库。
- “我负责”由原图 assignee 派生；“我关注/让助手跟进”由明确 relation 派生；“助手负责”由 assignee=个人助手派生。它们并非互斥角色枚举。

scope 默认只覆盖选中的节点，不自动包含未来新增子节点、所有后代或依赖图。用户要求整个项目时可明确扩大读取/跟踪范围；结构边不提供权限继承。若一次委托实际产生一个不同、可独立交付的工作项，可以在原图合适层创建真实子任务，非镜像父任务：例如真人负责报告、助手负责“汇总三个已授权数据源”。创建子任务必须符合用户的保存意图，子任务依旧默认不继承父负责人。

没有结构化协助设施的首版可用明确任务引用+现有主会话/执行记录，但必须诚实降低保证：不能承诺可靠跨会话同步、完整关注列表、严格去重和取消恢复。不要把自然语言备忘录冒充这些保证。

## 6. 生命周期与交接

### A. 本人任务由助手协助

1. 从原任务点“帮我推进”，带稳定任务 ID、当前 revision 和本人意图；读取失败不能用旧摘要假装同步。
2. 明确区分“我已接到协助请求”和“我已在原任务开始工作”。不 claim、不 set_assignee。
3. 分辨当前可准备、可执行、需本人完成/决定的步骤。只要授权足够即可先做独立部分，不要求每次全面填表。
4. 准备完成：给本人材料和证据，说明尚需谁做什么；原任务 todo 可以保持，即便助手准备状态已完成。
5. 要写回结果/提交待确认时，以真实助手 actor 写原任务；有权限但无写回意图时先提供建议。
6. 本人完成或别人改了任务：重读，结束过期催促；若还有明确后续，保留其独立原任务/协助关系而非把原任务重新打开。

### B. 真正转交助手

“交给助手负责”展示从本人到助手的改派。写资格、成员资格和工具审核通过后 set_assignee；分配保留既有状态，不宣称已经运行。助手评估目标、依赖、能力和授权后才接手/claim；离线显示已分配但尚未开始。原创建者不变，群内使用既有一条系统消息。

结果提交到原任务，不因为“已完成”自动接受结果或终止全部跟进。核对证据并按用户授权收尾；无需另造不可绕过的验收角色。改派给另一独立 Agent 同理，个人助手还需具备明确派工授权。

### C. 退回真人、换负责人、停止

- 助手不能做某步骤：请求本人处理具体步骤，保留已完成部分；“需要你登录/签署”不必把整任务改派回来。
- 真正改派回本人：明确改派，交接产物/已执行副作用/未完成项/等待对象；旧 run 不能继续用旧授权写回。
- 本人说“别跟了”：撤销协助关系及未来主动动作，原任务状态与 assignee 不变。
- 本人说“这任务取消”：核实指向，按授权关闭原任务；不伪装已停止在途工具。
- 本人说“暂停这个任务的执行”：定位相应 run/子执行，使用既有 runtime 控制，保留其他任务；原状态是否同步由这次意图决定，不靠状态更新暗中控制进程。
- 不可中断工具已开始：记录取消请求、阻止新的副作用，在可停止点停下，核实已发生的外部结果并回报。不能承诺撤回已发消息或已提交交易。

## 7. 本人与经理/外部人的冲突

权限分三层：组织/资源规则决定可做范围；本人授权决定个人助手为谁做哪些事；外部消息说明请求或事实。组织经理身份不会自动变成本人助手的授权者，产品绑定的 owner 也不赋予绕过组织 ACL 的能力。

- 经理让本人优先 A，本人让助手先准备 B：助手告知现实冲突和风险，不自行承诺经理、不自动替本人拒绝。本人可决定自己的协助优先级；原任务状态由真实保存的事实决定。
- 经理关闭/改派了原任务，本人仍让助手继续：暂停依赖旧任务授权的新副作用，重读并说明改变；不能覆盖经理新 revision 或悄悄改回。本人要求继续私人准备可在可访问且允许的范围内做，但不能谎称仍代表原任务负责人执行。
- 本人明确让助手停，经理继续催：停止本人委托的协助；经理新请求作为待处理信息，不恢复授权。
- 经理要求查看本人私有判断/其他私聊：不因与该任务有关就披露；仅分享该目的、受众已经允许的材料。
- 两人都能编辑：服务器仍按成员/revision 规则，不建“owner 永远胜过经理”的隐藏写优先级。助手应比较事实、说明冲突并请求决策，不能循环覆盖。
- 对方自称“我已经问过小王同意”：只有可验证的本人授权证据才改变权限；不能信消息里的自报身份。

## 8. 与独立 Agent 的协调和证据

现有群/私聊是沟通载体，任务仍是原图。不新增强制交接回执系统。一次协作尽量带以下可验证关联（可先为消息/工具 metadata，不要求新任务字段）：原 graph/node、目标与交付标准、有限输入/权限、真实发起/接收主体、授权引用、相关 run 或 request ID、correlation/root event ID、结果链接及源版本。

必须区分至少这些事实：发出请求、消息持久化/投递、对方实际接手、执行运行、提交结果、证据核对、业务接受。对方一句“收到”仅为确认收到；done 状态仅证明记录变化；测试通过只证明相应版本与环境。结果至少说明完成内容、未完成/限制、产物版本、验证方法及失败项，不能用“另一个 Agent 说好了”替代核实。

外部协作者自己的权限也要满足；转发本人可看的全部背景会造成泄漏。对方索要新数据/凭据/额外受众时回到原授权边界。中途改派后迟到结果可以保存为有来源的参考，不得用旧委托继续修改当前任务。

防循环：同一 root/cause ID 的确认/感谢不产生新任务；只有新增事实、明确问题或授权阶段推进才回复；设置有界重试/去重。不要把所有 Agent 消息当高优先级本人命令。重复投递共用 request/event 身份，不重复写状态、不重复催促。

## 9. UI：责任与协助在同一张卡上可辨认

保留现有任务列表/层级/负责人筛选，在个人入口给出三个可组合视角：“我负责”“助手负责”“我在跟进”。第三个视角不复制任务，只显示本人显式关注的引用；“我负责”包含跨层本人直接负责节点，不把父任务后代全算在内。

任务主信息保持标题、源会话、负责人、原任务状态。个人协助作为次级行，例如：

- 负责人：你；任务：待办；助手：已整理资料，等你选方案。
- 负责人：分析 Agent；任务：进行中；助手：关注其结果对周五报告的影响。

操作分开：

- “帮我推进”：负责人不变。可选/自然语言说明先帮什么，直接展示将做的可用范围。
- “交给助手负责”：明确旧→新负责人及所属会话；不把改派和开工合成已完成事实。
- “停止助手跟进”：取消个人协助。
- 原有“暂缓/关闭/改派/删除”：改变原任务，沿现有权限与危险范围提示。

若只有用户提供的快照：标“根据你转交的内容，未同步源任务”，不能显示假实时状态。权限失效：不泄漏旧标题/摘要/数量给已失权目标；私人历史保留与当前再次访问须另按安全政策处理，不能承诺历史物理遗忘。用户草稿回填保持人实际发送的身份，不能算助手代发。

## 10. 易漏边界与验收案例

| 场景 | 期望行为/证据 |
|---|---|
| 真人已分配，点帮我推进 | assignee/created_by不变；无 claim；actor可追溯 |
| 助手准备很充分，真人尚未开始 | 协助进度可推进，原任务不被虚报 doing/done |
| 同一任务本人负责又显式关注 | 唯一原图/关系去重，不出现两张独立真相 |
| 父负责本人，子负责他人 | 子任务不自动变本人义务；协助范围不默认跨层 |
| 任务被改派给本人但本人没接受 | 显示已分配；助手可按已准范围帮助评估，不替本人承诺 |
| task done但证据缺失 | 报告“标记完成，尚缺证据”，不自动接受/自动返工 |
| 本人已在源群回答 | 新事实消除旧待决/催促；不把本人发言触发为自答循环 |
| 原群解散 | 历史只读，未完成关闭按current；助手不得重建影子图继续写 |
| 原任务删除/失去访问 | 停止基于原任务的新动作；区分明确删除与无法访问，不无证据宣称删除 |
| 空间跨界：本人有公司任务，私人助手没有 | 受委托路径未设计前明确阻塞；不得放宽普通 canActorAccess |
| 读授权撤销，已有排队事件 | 取正文/行动/投递前再校验；不凭旧事件泄漏内容 |
| 根任务结果通知未@本人或助手 | 经批准的跟踪路径发现，不能依赖现有结果@规则作完整保证 |
| 人负责子节点，父被暂停 | 被授权观察机制识别；不因未@助手继续盲目行动 |
| 分配时接收 Agent 离线 | 保存成功且一条通知；未开工，不报告执行完成 |
| 发送未知/写入超时/重连重放 | 核实或同键重试；不重复交办/通知 |
| 撤销与在途工具竞态 | 阻止新副作用，报告已发生与未发生，不假称已撤回 |
| 他人更新同字段，旧 revision | 重读合并/问决策；不不断自动覆盖 |
| 外部 Agent 迟到结果 | 保留来源且核对当前范围，不恢复已结束授权 |
| 两个个人助手同时跟进同任务 | 同一图、各自owner-scoped协助；不互相继承授权或重复催群 |
| 管理员删父任务包含别人子任务 | 沿既有子树删除权限，不偷偷增加个人助手豁免或后代审批 |
| 转交含私人来源的结果到公共群 | 对每项披露重新检查受众，不能仅凭任务public就公开所有证据 |

测试应扩展 `apps/im-server/tests/task-collaboration.test.ts`、`tenancy.test.ts`、`e2e/conversation-tasks.test.ts`，以及 PA global/inbox/heartbeat、统一工具审核与 UI 测试。本文静态审查未执行这些测试。

## 11. 可先采用的安全默认，与待用户决定事项

### 不应再悬置的设计原则

- 真人任务是一等输入；不把个人助手产品缩成 Agent 自己的任务看板。
- 不新增 mandatory task roles；负责人、创建者、实际操作者语义保持。
- “帮我推进”不改派；协助完成不等于任务完成。
- 同一原任务一份真相；私有关注/协助只保存引用、意图与最小控制状态。
- 关注/分配/消息可见均不自动授予执行、外发、验收权限。
- 取消协助/原任务关闭/runtime停止明确分离。
- 实际身份、当前 ACL、授权证据、revision、幂等回执不能绕过。

### 必须与用户继续对齐的产品决定

1. **从哪里发现真人任务**：只手选引用，还是主动检查已授权任务/会话？范围是明确任务、指定会话，还是本人某类任务？这是持续读取决定，本文没有默认全量读取。
2. **“帮我推进”的默认深度**：只准备并提醒，还是允许某些常规执行/原图写回？哪些外发/改派/接受结果始终逐次问？可以按具体场景给默认，不应只问一个笼统“全自动开关”。
3. **公司任务跨空间的机制**：批准专门受委托只读通道，还是先限用户手选快照？如需写回/代发，分别设计身份、授权、审计，不把read grant扩为apply权限。
4. **跟踪与停止条件**：原任务完成即结束，还是等本人确认/下游结果？等待外部时提醒频率、静默/工作时段如何设置？不同停止条件必须明确，不能无限催促。
5. **外部人与 Agent 可否主动联系个人助手**：入口、来源验证、允许的信息、是否可派工、什么时候须转本人。默认能收请求不表示能替本人答应。
6. **对第三方任务的例行催办授权**：需要明确对象/目的/范围；“我关心”本身不足。是否只生成可审草稿是单独体验选择。

对话推荐先确认核心语义：“分给你的任务，助手也会帮你推进，负责人仍是你；只有你明确交给它负责时才改派。”然后只问当前阻塞实现的读取范围问题，避免一次把所有边界选择压给用户。

## 12. 补充边界：可联络/可协作不等于可看私人 Work

核对 `docs/specs/im/agent-work.md` 后，需要单独保护个人助手的主工作轨迹：current 的 Work 以 Agent 资源空间资格控制，允许有资格的非管理者查看公司 Agent 完整轨迹，已有内容不按原聊天逐项遮盖；子执行默认同样可检查继承历史。`apps/im-server/src/work.ts:168` 的更新广播也按 Agent 空间资格筛选。当前私人空间本来限制本人；以下是未来扩展的设计约束，**不是已发现现有未授权可读漏洞的断言**。

个人 Agent 即便以后可被外部人联系、加入某种协作入口、显示公开名片或承担公开任务，也不得因此把它的资源空间改成公司共享，或给所有协作者开放主 Work/原生轨迹。必须明确分开：

1. **身份可发现与联络入口**：可看到名称、必要能力、允许的联系方法；不暴露私人活跃事项、跨私聊列表、全局 token/执行摘要中的敏感任务名。
2. **共享任务及交付证据**：在原任务 ACL 下共享被允许的结果、产物、验证证据和必要操作事实。
3. **私人运行面**：个人主会话、完整工具参数/结果、system/context、私有记忆、fork 继承历史、后台整理和其他私聊资料，仅沿个人授权边界查看。

仅把轨迹时间轴缩到某次任务不够安全：current 派生视图是完整轨迹上的选区，不过滤记录；fork 可继承其他私人上下文。因此不得把“本次子执行链接”当天然可分享证据。需要分享时优先交付允许披露的产物/验证摘要；如未来需要共享任务级过程证明，应是明确、独立、最小化的结果投影，不是对私人全局轨迹的嵌入或链接授权。

技术验收须覆盖 Work总览、turns/items、原生历史流/订阅、关联子执行、工作区图片及附件、统计投影、浏览器深链和缓存，而不只隐藏一个 UI 按钮。角色/空间/授权变化后应停止新的读取和推送。源任务成员资格、可发消息、被@、自己创建了该任务，均不得推出私人主 Work 读取资格。向外部独立 Agent 交办时采用最小任务资料，不传 personal 全局 fork；内部 subagent 的私有执行仍不能被外部协作者通过任务链接顺带打开。
