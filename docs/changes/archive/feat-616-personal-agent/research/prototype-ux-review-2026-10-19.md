# feat-616：从 Personal Agent 定位出发的原型体验走查

日期：2026-10-19。结论：当前原型已经表达了来源、身份、受众和授权边界，但尚未建立“把目标交给它之后，它会持续负责”的体验。优先修订目标承接、跨渠道协调、持续跟进和有界自主能力，再处理局部按钮与布局。

## 判断标准

用户在本轮强调：“真正要站在 personal agent 的定位的角度去思考整个用户体验”。因此以四个问题判断：

1. 助手是否接住了我的目标，并让我知道它接下来负责什么？
2. 它是否主动消化信息和推进工作，使我需要操心的事情变少？
3. 只有需要我的判断、授权或新信息时，它才来找我吗？
4. 换聊天、等待他人、离线或暂停之后，它是否仍然说得清谁在跟进、何时再看、怎样算完成？

三种执行域可以是合理的内部保护机制；用户应感受到同一个助手在持续工作。技术隔离造成的能力限制需要如实说明，但不应默认让用户承担跨域搬运和协调责任。

## 实际连续旅程

以“周三做客户演示，帮我盯住材料准备和时间确认”为同一个目标：

1. 重置演示，选择新用户；起名“小航”，填写上述目标；阅读观察范围，创建并启用观察。
2. 进入私聊，目标成为草稿，再手动发送。注入真人来信，打开回复草稿，改为“周三 15:00 可以，演示材料我会提前发给你。”
3. 放入原聊天遇已有草稿，选择替换文字；原附件保留。发送后回到 PA，看到已回复、不再催回复的状态。
4. 打开公开资料搜索，先“核对本次内容”，再“确认这次搜索”；等待完成，返回私聊。
5. 打开页面制作任务，阅读专业能力、执行电脑与广权限说明；两步确认执行。完成后勾选结果并“提交选中内容”，再回到私聊。
6. 进入任务页，查看准备结果、预览写回并确认；原任务变为“待确认”，负责人仍为本人。
7. 切到林悦 DM，查看询问时间与日程的请求；回本人私聊，选择“这次不分享”；再查看外部 DM 的反馈。
8. 查看研究 Agent DM、群 @ 两种入口；回本人私聊，看到按来源分列的请求。编辑群回复为“周三 15:00 做产品演示，材料确认后会发到群里。”并完成模拟投递。
9. 查看个人助手设置、观察覆盖；暂停观察，再进入恢复面板，阅读两种恢复方式，选择补读并恢复。

原型正常的保护行为：取消/关闭不误发；替换草稿明确保留附件；本人已回复后不继续标为待回复；分享展示具体内容、身份和受众；写回保留原任务与负责人；暂停状态可辨认。应保留这些能力，但它们尚不足以证明个人助手的核心价值。

## 按产品影响排序的发现

### PA-UX-01：用户交的是目标，原型组织的是消息与单次动作

**观察：** 同一场演示被拆为本人来信提醒、搜索、页面制作、研究 Agent 请求、群分享和任务写回。私聊里没有“这件事目前进展到哪里、还缺什么、助手下一步会做什么”的统一承接。搜索和页面制作已完成后，主聊天仍显示原来的“可以补一份检查清单 / 查看页面制作任务”建议。首次填写的目标只被放入第一条消息草稿。

**影响：** 用户仍要记住这些碎片之间的关系，自己判断是否完成。固定入口和自定义名称提供身份连续性，尚未提供工作责任的连续性。

**归因与边界：** 原型现象已证实。`proactiveMessages`（prototype.html:115 起）按来源和动作拼消息；design 有合并承诺、任务唯一真相等意图，但缺少足以走通的目标级用户旅程。不能据静态无模型回复断言未来模型不会承接目标。

**建议：** 在现有私聊中用简洁的事情进展承接目标：已确认时间、材料进度、等待谁、下一次跟进、仅需本人决定的事项。已有任务作为事实源，不另造一套 Todo 数据库。来源和执行明细按需展开。先让一个目标从交办到完成连续成立。

证据：[完成工作后私聊仍是旧建议](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/07-completed-work-in-chat.png)、[最终本人视图](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/13-final-owner-view.png)。

### PA-UX-02：主动观察尚未转化为有分寸的持续跟进

**观察：** 原型能发现“有人等你回复”，也能停止已回复提醒；没有展示“今天 17 点前仍未确认怎么办”“用户稍后决定以后何时再问”“等待对方回复时谁继续盯着”。设置主要管理读取范围、历史覆盖、暂停和清理，没有体现提醒轻重、稍后提醒、这件事不再跟进等用户语义。

**影响：** 用户不知道不打开助手聊天会不会漏事，也不知道什么时候可以放心离开。助手可能成为另一条需要清理的信息流。

**归因与边界：** 属于当前设计与原型的体验契约不足，未实测后台定时能力。design:71 的 20 秒合并、批量引用和检查预算属于处理机制，不等于用户可理解的跟进节奏；design:231 也已承认重复打扰风险。

**建议：** 明确“正常工作安静推进；临近截止、被阻塞或需要用户决定时提醒”；每件持续事项说明等待对象和下一次检查。允许用户用“晚点说”“这件事不用跟”“今天只提醒紧急事项”调整行为，界面给出确认。上线前应演示离开、回来、跨天继续的一条旅程。

### PA-UX-03：单次授权颗粒度过细，用户成为操作调度员

**观察：** 一次公开搜索先展示完整查询词，再点“核对本次内容”，同一页没有新增关键决策信息，还要再点“确认这次搜索”。普通辅助回复需打开草稿、放入输入框、处理已有草稿、跳回原聊天、发送。专业任务还要求用户理解 shell、输入范围、节点和来源追踪。

**影响：** 助手发现得越多，用户要批准的动作可能越多。用户的目标是完成演示，却持续被询问执行手段，难以获得“它能帮我推进”的感受。

**归因：** 重复确认是原型中的确定事实；更深层的逐动作批准来自 design 的授权方案。不能用删除安全边界的方式解决，也不能默认搜索永远无隐私外传。

**建议：** 先移除无新增信息的重复确认；把明确的目标委托转换成产品可理解、边界清晰的行动许可，例如允许搜集指定主题的公开资料、整理本地草稿。涉及新增敏感数据、对外承诺或扩大受众时再请求具体确认。这是需要正式修订设计的有界授权能力，不是把本轮建议视为已获用户授权。原聊天发送可保留为选项，同时提供明确展示内容、收件人和发言身份的直接确认路径。

证据：[搜索第一步](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/03-search-approval.png)、[重复确认](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/04-search-double-confirm.png)、[专业任务权限](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/05-specialist-approval.png)。

### PA-UX-04：专业任务执行完，用户还要把结果搬回自己的助手

**观察：** 页面制作完成后显示“正文尚未交给 PA 自动处理”，要求勾选“作为新的本人输入提供给 PA”并提交。提交后回主聊天，也没有展示如何检查结果、关联原目标和继续跟进。

**影响：** 用户已经委托助手完成任务，却再次承担把成果交接给同一助手的工作；“执行完成”与“目标推进”断开。原型的搜索只展示完成回执，没有示例成果可用来完成演示准备。

**归因：** 结果手工重新提供是 design 明确规定的广权限任务边界（Gateway personal-agent delta:74），不是单纯漏了一个按钮。结果内容只是示例，不能据此断言真实搜索/制作能力失败。

**建议：** 日常工作优先提供能够安全返回结果的受控能力，自动把进度、可接受成果和下一步接回原目标。只有必须走广权限任务时，才明确说明能力例外与交接成本；不要把这种例外作为用户最先体验的默认路径。未知来源正文仍须保持隔离，不能为流畅而自动绕过。

证据：[结果需要人工重新提交](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/06-task-result-reimport.png)。

### PA-UX-05：外部请求能进来，但助手还没有承担协调与筛选责任

**观察：** 林悦、研究 Agent、群分别询问同一场演示，回到本人视角形成按来源分列的确认。本人已在源聊天回复 15:00，预置分享仍提供另一组时段；此处只能证明原型未演示跨来源统一，不能证明真实模型会产生同样冲突。选择“这次不分享”后，本人得到“没有向原聊天追加回复”，外部仍停留在“确认后在这里回复你”。

**影响：** 个人助手没有明显减少外界对本人的协调负担；别人可以把更多审批推给本人。拒绝隐私披露之后，正常业务请求也没有明确下一步，联系人继续等待，可能再次直接来找本人。

**建议：** 在本人私密视角把同一件事合并判断，清楚区分已经决定的事实、可对谁使用的资料和仍待决定的事项；外部上下文继续隔离，不跨受众泄漏。先替本人消化重复请求与不必要的问题。拒绝分享资料和放弃业务目标分开：可以提供不披露隐私的协调答复或替代方案，并按现有沟通授权决定是否发送。不要自动告诉外部“主人拒绝了你”。

证据：[分享决策](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/09-external-sharing.png)、[拒绝后对方仍等待](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/10-external-after-decline.png)。`declineRelease`（prototype.html:108）仅更新本地状态，没有对外闭环。

### PA-UX-06：责任交接用数据状态表达，用户难判断事情还归谁管

**观察：** 本人确认写回后任务变“待确认”，当前结果还包含“待你确认：采用哪组客户案例”，没有解释后续由谁决定、助手会否继续跟进。恢复观察的“仅从现在开始”同时写着“不继续旧的未处理建议”，没有先展示会放下哪些事项。暂停页解释消息覆盖，没有交代已有持续工作是否继续。

**影响：** 用户容易把确认写入误认为事情已完成，或在恢复数据观察时无意放下未处理事项。

**归因与边界：** 原型文案和路径已证实；`resumeObservation`（prototype.html:89）在 now 分支清空源 observed/pending，未处理建议不再显示。未证明会删除任务或中断真实后台工作，也不要求此 unit 重做整个既有任务系统。

**建议：** 明确区分“结果已保存”“等待谁确认”“这件事已完成”。暂停观察时解释已有任务/提醒是否继续；停止读取旧消息不应含混地等于放弃跟进。恢复时先给事项摘要，用户明确选择放下的事项，保持原任务真相。

证据：[任务写回状态](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/08-task-written.png)、[恢复观察选择](/Users/czj/.codex/visualizations/2026/10/19/feat-616-ux/12-resume-observation.png)。

## 建议下一版原型只先证明的一条完整价值链

用户说：“周三客户演示，帮我盯住。”

1. PA 明确承接：关联现有演示任务，说明将整理材料、核对时间；有一项需要本人判断的案例选择。
2. PA 在允许范围内整理并推进，把林悦、研究 Agent、群里的消息归到这件事，向本人展示一个可理解的当前结论。
3. PA 只在有实质决策时提问：给推荐方案和理由，展示具体内容与受众；不要求用户逐个批准同一许可内的准备动作。
4. 决策后继续负责：更新原任务、等待相关人的确认、在约定时间检查；用户不用逐页搬成果。
5. 用户离开再回来，看到完成了什么、还等谁、何时会再跟进。关键变化主动告知，普通过程保持安静。
6. 停止、暂停或完成时明确交接与结束，不留下“发送成功所以整个目标应该完成了”的误解。

以上是修订方向，不是本轮已经实现的能力，也不自动增加第二套任务系统。固定 PA 入口、原生 IM 联系与内部隔离可以保留，主要重做用户委托之后的连续工作体验。
