## 当前事实与参考边界

2026-10-19 检查 feat-616 工作区：`PersonalAgentIncidents` 查询 PA 专用 incidents API 并渲染固定标题、说明和两个固定业务按钮，由 PA collaboration 区域挂载。它不是普通消息中可由任意 Agent 组合的通用交互内容。现有消息契约支持正文、附件和若干专用投影，不能据此宣称已有通用交互回复。

OpenAI 的 [Intelligent UI 发布说明](https://openai.com/index/gpt-6-for-everyone/) 明确提到模型选择文字、视觉和交互的组合，使用原生可流式组件与增量处理界面的编译器，并针对设计判断进行训练。该资料未公开完整内部语法、编译器或点击执行协议，不能把以下 SDK 当作该内部实现的证明。

[ChatKit widgets](https://github.com/openai/chatkit-python/blob/main/docs/concepts/widgets.md) 公开了受约束的组件描述、结构化传输及客户端渲染；[交互与流式示例](https://github.com/openai/chatkit-python/blob/main/docs/guides/build-interactive-responses-with-widgets.md) 展示逐步更新；[Actions 文档](https://developers.openai.com/api/docs/guides/chatkit-actions) 展示按钮与表单回传、服务端处理，以及将用户动作加入模型上下文。这些是可借鉴的工程机制，不是本需求已选定的依赖。

[MCP UI 文档](https://developers.openai.com/plugins/build/chatgpt-ui) 另外展示隔离嵌入式界面、宿主通信，以及业务数据、临时界面状态和跨会话状态的分工。是否需要这种扩展路径留给技术设计。

## 用户场景

用户与任意 Agent 正常聊天，不需要先进入某个功能页或开启“交互模式”。简单问题直接得到简短文字；比较多个候选、调整条件、编辑草稿或理解动态关系时，Agent 可以在回复里给出合适的交互形式。用户既可操作界面，也可继续用自然语言修改要求。

例如用户请 Agent 安排西湖游览，回复可包含路线概览和可调整的时间、偏好。用户调整选项后可以比较结果，再说“就按这个继续准备”。理解和比较本身不会联系别人；当用户明确要求通知同行者时，才出现与具体对象和内容相符的发送行为。

隐私提醒是另一例：Agent 说明发生的事情，提供查看来源或处理联系人关系的操作。用户不处理也不会放行隐私；“这是误会”不会被解释成允许公开私人内容。提醒可以复用通用表达能力，但其业务事实与权限仍须可靠。

用户离开后再次打开聊天，能读懂交互回复、已经做出的选择和处理结果。移动端同样能阅读和操作，不因交互内容破坏现有聊天导航。

## 验收标准

### Requirement: Agent 可配置 Intelligent UI

#### Scenario: 默认启用并可关闭
- **WHEN** 用户打开 Agent 配置页的 Features
- **THEN** 显示默认勾选的 Intelligent UI，可取消勾选并保存；已有配置未指定时同样默认开启。
- **AND** 关闭后该 Agent 不再发布新的交互卡片，文字回复继续可用；重新勾选恢复能力，已有卡片与历史选择保留。

### Requirement: Agent 按任务需要选择表达形式

#### Scenario: 多种领域任务使用交互回复
- **WHEN** 用户分别提出方案比较、草稿修改、条件调整或信息提醒等任务
- **THEN** Agent 能选择有助于理解和操作的交互形式，不局限于 PA 或某一种预设业务卡片。
- **AND** 用户无需说明组件名称或先打开专用页面。

#### Scenario: 无交互提示的知识讲解
- **WHEN** 用户只说“给我讲解下冒泡排序”，没有要求按钮、动画或可视化
- **THEN** Agent 主动选择有助于理解过程的交互表达，用户能改变步骤或输入并看见有意义的内容变化，不能只给纯文字、静态装饰或无效按钮。
- **AND** 不在产品代码、模型提示词或随包 Skill 中写入冒泡排序专用组件、路由、规则或答案；另用不同领域的普通提问验证通用性。

#### Scenario: 保留通用界面能力
- **WHEN** Agent 根据内容组合布局、图表、输入、条件内容、重复列表和本地动作
- **THEN** 使用完整上游组件库与本地状态/计算机制，不强制所有输入进入表单，不强制只有一个提交按钮，不把所有点击转成模型请求。

#### Scenario: 简单回答与自然语言继续交流
- **WHEN** 简单文字足以回答，或用户选择直接打字而不点控件
- **THEN** Agent 仍能简洁回答或继续当前任务，不强迫用户填写表单。

### Requirement: 交互能衔接理解、选择与后续行动

#### Scenario: 调整方案后继续推进
- **WHEN** 用户调整候选条件、选择方案或修改草稿，再要求继续
- **THEN** Agent 理解实际选择及修改内容，继续对应事项，用户无需重复抄写。
- **AND** 单纯浏览、比较、试算不会被当成外发或执行承诺。

#### Scenario: 多次探索与继续提问
- **WHEN** 用户本地探索后请 Agent 解释当前结果，再继续改变条件
- **THEN** 原交互仍可探索；每次明确发给 Agent 的请求分别留有真实用户与当时状态，网络重试不会重复产生同一个请求。

#### Scenario: 执行有明确对象与实际结果
- **WHEN** 用户通过交互控件请求发送、保存或改变业务状态
- **THEN** 用户能辨认动作对象、含义和执行结果；失败不会显示成完成，重复点击不会产生重复业务效果。
- **AND** 控件不能绕过既有身份、会话权限或 PA 对外披露边界；不额外要求用户逐次批准普通展示和本地交互。

### Requirement: 交互回复是可持续阅读的聊天内容

#### Scenario: 离开、刷新与回看
- **WHEN** 用户刷新页面、换设备或回看历史
- **THEN** 仍能看到原回复的含义与已经确认的结果，不把旧选择误显示为新待办。
- **AND** 已过期或被后续事实替代的动作有可理解的状态，不能静默执行旧方案。

#### Scenario: 生成过程与失败
- **WHEN** 回复正在生成，或某段交互无法正常展示
- **THEN** 已可阅读的内容不会无故消失，用户能分辨尚未完成的内容，并能继续通过文字交流。

### Requirement: 延续现有 Web IM 体验

#### Scenario: 桌面与移动端
- **WHEN** 用户在桌面或手机打开包含交互内容的聊天
- **THEN** 内容可读、控件可操作，保留原有导航、聊天列表和输入入口；不会因卡片过大或持续堆叠而妨碍阅读主对话。

## 范围与非目标

- 在范围：独立研究并定义 Web IM 通用 Agent 交互式回复，兼顾 PA 和普通 Agent；按需呈现、用户操作回到任务、可读历史与现有权限边界。
- 本轮非目标：修改 feat-616，迁移现有专用卡片，替换 DSH 运行时或整套聊天客户端。
- 首版产品边界：Web IM 中的通用组件交互，普通 Agent 与 Global/Personal Agent 均可使用；其他客户端与外部 channel 保持可读文字。模型使用注册组件、函数和动作；不依赖生成任意 HTML/JavaScript 才实现通用性。保留上游 Query/Mutation 接入机制，通过本应用已提供且授权的工具工作；未接入的业务能力明确报不可用，不假装已经读写文件。生成期间沿用现有运行反馈，完成后交付可操作内容。跨回复增量编辑保留上游能力，通过新消息保存合并后的完整版本，保证历史可读。
- 不承诺复刻未公开的 OpenAI 内部实现。组件种类、复杂互动的承载方式、首版交付切片和其他客户端支持在后续设计中明确。


## 2026-10-19 自然上下文体验修订

用户原话：“那把侧聊反馈的两处体验也改了，去掉保存成功提示和选择附带横条，状态在后台保留，让 Agent 自己结合用户的话判断要不要用。”

### Requirement: 后台状态不成为用户需要管理的附件

#### Scenario: 正常探索与恢复
- **WHEN** 用户调整交互内容或重新打开会话
- **THEN** 本人状态自动保存、恢复；正常成功不显示保存成功提示、选择附带横条或Detach，不要求理解草稿/附带模式。
- **AND** 真正需要处理的保存失败、冲突、发送未知结果继续明确反馈。

#### Scenario: 自然追问、换题与状态冻结
- **WHEN** 用户问“为什么这一步要交换？”、换到无关话题，或发送后继续探索
- **THEN** Agent取得发问时准确的交互背景，结合用户原话决定使用、忽略或在指代不清时澄清；后续编辑不改变前一个问题的背景。
- **AND** 用户消息仍为原文，不被包装成确认选择或自动业务指令；后台状态不改变消息接收者，不公开为群成员的已提交选择，也不授予任何业务授权。

原生明确操作仍保留既有目标、身份、幂等与业务结果语义；不裁剪OpenUI能力。属于同一尚未合并PR的需求修订，重新开放当前unit并执行受影响设计与验收，保留此前崩溃修复与其CI结论。


用户进一步确认：“那就按这个边界改617：私聊后台保留状态，发消息时让 Agent 自己判断是否使用；群聊只有明确提交后才共享。把‘草稿已保存’和‘当前选择’的提示也去掉。”

本轮最终边界：后台上下文仅用于私聊发送；群聊普通文字不携带私人状态，所有Agent（包括卡片作者）均不能读取未提交状态。群聊只有卡片明确提交/提问动作才公开发问时快照；沿既有公开消息与群内Agent上下文语义。私聊背景只供相关性判断，不是确认、业务指令或授权。

作者解读：继续 feat-617 同一交付，改进消息及交互回复的空间利用；统一样式由宿主负责。本轮不改消息协议、生成内容或 Agent 权限，不扩展导航和整个组件库。

### Requirement: 消息宽度适配聊天面板与内容

#### Scenario: 桌面阅读交互回复
- **WHEN** 用户在宽聊天面板阅读交互回复
- **THEN** 图表、表格与交互区域使用面板可用宽度，不被普通窄气泡再次限制；外层不叠加一块重复灰底，发送者与时间仍可辨认。

#### Scenario: 短消息与长文字
- **WHEN** 同一聊天含短消息、长段落、代码与宽表格
- **THEN** 短消息按内容收缩；长文字在宽屏保留阅读上限；代码与表格在自身区域内处理必要横向滚动，不撑宽整个页面，消息操作仍可用。

#### Scenario: 窄面板与手机
- **WHEN** 面板变窄，或用户在手机上阅读与操作回复
- **THEN** 消息随可用空间缩小，头像、操作、输入框和内容保持可用；不因原有固定比例额外浪费窄屏宽度，不产生页面横向滚动。
