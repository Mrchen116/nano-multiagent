# PA 审核上下文膨胀复盘

调查日期：2026-10-20。只读核查代码、Git 历史、unit 文档及生产审计；本报告不代表已修复或部署。

## 核心落差

用户期望主 PA 和审批器正确理解真实主人、对话对象及相关背景，主会话压缩后仍能正常执行工具。实际生产主会话约 15 万 tokens 时，普通 write/bash 审批估算达到约 135 万，超过审核模型声明的 258400 窗口。

直接原因不是主会话压缩失效：Nano 新增的 `pa.authorization` 在审批时从 IM 数据库另取原始消息，绕过主会话有效历史。feat-623 将该接口扩展为所有可访问主人消息及这些消息所在聊天的完整历史，再以多个字段重复携带部分消息。

已查对齐记录没有用户要求新增这个内部接口，也没有要求每次审批全量重放聊天历史。用户确认消息身份、参与关系和背景处理语义，不等于指定了全量送审方案。接口与证据组织方式是实现方选择；不能把实现选择转述成用户要求。

## 用户要求与技术选择

[feat-616 spec](../feat-616-personal-agent/spec.md) 保存的要求是“通用能力就复用普通 Global Agent”“把之前给 PA 单独造的那些多余机制去掉”。[design](../feat-616-personal-agent/design.md) 随后选择以原始主人消息和提交选择作为授权证据，替代结构化目标许可。

[feat-623 spec](spec.md) 保存的要求是：主人身份与参与关系应分别说明；PA 收到的请求与主人收到的背景不同；观察背景十分钟合并；直接请求可提前读取背景。用户同时反对另造 mentions 等机制。上述要求需要相关上下文，但没有要求把所有历史放进每次审核请求。

[feat-623 design §5](design.md) 把 `owner_messages` 明确扩大为“所有当前可访问、可信主人身份的原文”，并要求保留原会话问答。这一步已经缺少任务相关性和模型窗口边界。实现再把“问答上下文”落实为每个相关聊天没有时间或条数限制的完整查询。

因此同时存在方案缺口和实现扩大：设计规定全量主人原文却未规定输入上限；实现将所涉聊天的全部正文一并加入。不能解释成单纯某个常量设置错误。

## 为什么评审和验收没有拦住

- [design-review R1-W3](design-review.md) 已明确指出“把所有主人聊天放进授权证据”，但关注的是 owner_messages 全量 digest 导致无关来信使外发许可失效。修订增加单独的 guard_messages，只缩小失效判定集合，完整送审上下文继续保留。
- [IM 实施证据](M1-context/im-identity-evidence.md) 将完整 owner 原文、conversations 问答和 guard 分离当作完成项；没有审核请求体积或长期数据规模验证。
- `apps/im-server/tests/personal-sources.test.ts` 的核心相关用例只有三条合成消息，验证“应该带的证据有没有”，未验证不相关旧消息是否大量进入、重复量或最终审核窗口。
- [code-review](code-review.md) 检查身份、guard、通知时序，发现并修复空批遗留 waitingForIdle；记录没有发现本次输入预算问题。这项有效修复不能覆盖另一条审核数据链。
- [acceptance](acceptance.md) 使用新建隔离 PA/session，记录真实身份、报价、十分钟批次和飞书旅程。它证明这些输入下的语义和交付，未提供生产长期历史规模下的审核输入验证。
- 原有超窗预检正常工作，所以没有把巨大请求发给模型；它是错误处理，不是使请求保持可用的预算方案。

本次证据支持“跨边界影响与规模验证遗漏”，不支持把原因归结为没有跑测试或没有独立审查，也不足以推断个别角色当时的主观动机。

最大单个聊天 845 条消息贡献估算 897325 tokens；报告问题的 `c_8wedfh29` 为 313 条、估算 42091。部分主人消息同时出现在 owner_messages、guard_messages 和 conversations。以上是稍后只读重建值，不声称与失败瞬间逐字节相同；失败瞬间输入总量来自审计原记录。估算器与主会话模型实际 usage 口径不同，不能把比例当精确分词对比。

## 与参考 CC / Codex 的关系

- 当时固定 CC 2.1.267 的[真实 compact 实验](../feat-552-global-auto-approval/evidence/cc-2.1.267-context-experiments.md) 中，审核改用压缩摘要和后续消息，旧消息与工具调用不再逐条出现。它仍可能因其他超长输入报错，不能泛称永不超限。
- feat-615 参考的 Codex 基线是 `806d9732c974bc8a51b8317c1bd8985544fe627c`。其 Guardian profile 对历史设保留预算，input_budget 对完整请求做预算处理及 checkpoint 恢复；不包含 Nano 的 IM 授权查询。
- Nano 的 CC 分支把 personalAuthorization 追加到 transcript；Codex 分支把同一数据放入 planned_action，而 planned_action 被要求完整保留。`reviewInput` 即使删掉全部历史也无法容纳该包时会抛 `Guardian budget cannot fit complete pending action`。因此切换策略不能解决这个共同输入问题；本次生产实际只验证了 CC 失败，Codex 影响是代码路径结论。

## 改进方向与边界

先重新对齐是否需要独立于有效会话的授权证据通道，不能默认保留现有接口、只给全量包加一个截断常量。若确需补证据，应明确它解决哪种缺失、取哪些相关原文、如何保留来源和缺失标记，以及如何受最终请求预算约束。许可失效的 guard 用途与模型需要阅读的上下文分开处理。

修复验证应复用本次已经证实的故障形状：长历史、多聊天、压缩后普通小动作；检查最终送审输入，既保留当前动作所需授权，又不重新灌入不相关全历史。相关撤销、更正、跨聊天真实授权仍须保持。

本报告未修改产品代码、生产配置、审批策略或运行服务。没有复盘其他未关联行为，也没有声称所有历史评审会话已穷尽；结论依据已保存的用户原话、unit 决策、精确提交 diff 和本次生产取证。
