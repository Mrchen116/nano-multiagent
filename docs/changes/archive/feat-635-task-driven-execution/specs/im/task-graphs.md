# im Task Graphs Specification (delta for feat-635)

## MODIFIED Requirements

### Requirement: 记录更新不等于执行或验收

#### Scenario: 更新状态、选项或结果
- **WHEN** 图记录被明确更新
- **THEN** 对应节点反映新内容，不自动改变无关节点或父目标；直接分配给 Agent 的节点进入 doing 后纳入该负责人的持续推进责任，其他记录修改不自动开工。
- **AND** 完成可继续修改，界面不将记录描述为已独立验收。
- **AND** 节点保留最近一次变更说明；从完成恢复进行中时必须附返工原因，可在详情查看，不形成历史版本系统。

### Requirement: 每个拆分层级提供结构与完成情况视图

保留现有计划依赖图、探索衍生树及二者嵌套。在同一层级切换结构图与完成情况视图，共用任务和状态；完成情况展示当前层的直属子任务，按待办、进行中、待确认、已完成、已关闭五组呈现；doing 与 waiting 合并为进行中组，卡片分别标为推进中、等待中；暂缓任务并入待办组，卡片仍标明“暂缓”，不更改其状态。 全局 Tasks 首屏提供根任务总览，只按可访问根节点的自身状态分组；进入某个任务后再展示其直属子任务。总览与各层使用有明确外框、列头和计数的五个状态分组，手机以对应纵向分组呈现。

#### Scenario: 比较根任务并进入下一层

- **WHEN** 用户打开全局 Tasks
- **THEN** 默认看到根任务总览，所有可访问根任务按自身状态分组，不自动选中第一棵任务树，也不混入深层任务。
- **AND** 卡片可打开详情，并通过独立子任务入口进入下一层；面包屑可回总览或任一祖先。
- **AND** 根任务及子任务的直属完成数量单独标明，不作为工作量百分比、不改变父任务自身状态；打开/关闭详情不挤窄看板或丢失当前浏览位置。


#### Scenario: Web 五列独立自然加载

- **WHEN** 总览或负责人结果中各状态数量悬殊，用户滚动其中一列
- **THEN** 每列从自己的完整匹配结果读取首批任务，滚动接近本列底部自动追加后续任务；没有整页上一页／下一页，不要求先翻完待办才能看到已完成。
- **AND** 列头显示该状态组的真实总数，待办包含暂缓，进行中包含 doing 与 waiting；加载、失败重试及到底反馈只影响该列，已有卡片与其他列的位置保持。
- **AND** 搜索或负责人变化同时重置五列；窄屏 Web 各状态组有有界滚动区，长待办不会无限推远后面的组。任务内已取得完整图的直属层不新增服务端分页。

#### Scenario: 查看大任务并逐层进入

- **WHEN** 用户进入大任务或其中一个可拆分节点并切换视图
- **THEN** 当前层的直属子任务按状态呈现，深层后代不会混入本层看板；可进入下一层并通过面包屑返回。
- **AND** 节点展示自身状态及直属子任务状态数量摘要，摘要标明范围，不显示未经定义的工作量完成百分比。

#### Scenario: 探索与计划嵌套

- **WHEN** 用户在探索方向及其验证计划间导航
- **THEN** 仍能辨认当前选择、方向结果和相应结构关系；关闭的方向不计为成功完成，未选方向不自动变成必做工作。

### Requirement: 人与 Agent 在相同权限原则下维护任务

Web、原生 iOS 提供创建大任务／当前层子任务、领取、调整负责人、编辑标题／描述／结果／状态和有权限删除等基础操作。Agent 工具提供对应能力，按实际调用主体鉴权。有所属会话写入资格的成员可共同维护，负责人不独占编辑。

#### Scenario: 人直接操作及成员共同维护

- **WHEN** 小王直接创建任务，或群内有写入资格的成员修改他人负责的任务
- **THEN** 操作按对应主体记账并反映到同一份任务；人直接创建记小王为创建者，修改者可辨认；不要求通过 Agent 才能完成基础操作。

#### Scenario: 先入群再分配

- **WHEN** 为任务选择负责人
- **THEN** 只能选择任务所属会话中的人或 Agent；非成员需先按群规则加入，分配操作不会自动拉人入群。

#### Scenario: 分配与领取分离

- **WHEN** 任务被分配或改派给某负责人
- **THEN** 分配不改变状态，todo 分配不代表已经开工，也不把通知投递当作进行中；领取会进入 doing，其他合法入口进入 doing 同样表示开始推进。doing 改派由新负责人接续，waiting 改派保留等待并核对安排，paused 改派不自动恢复。
- **AND** 其他主体不能通过领取直接抢占已有负责人任务，转交通过明确改派完成。

### Requirement: 原生任务流程保持统一的信息与编辑体验

iOS 任务总览、逐层浏览、详情和创建/编辑 SHALL 以任务正文、状态和负责人为主要信息，身份审计与危险操作为次级；编辑字段 SHALL 有持续标签和随内容增长的输入区。状态和负责人 SHALL 使用具名、可关闭、带选中反馈的选择面板，负责人可搜索并区分真人与 Agent。选择仅修改草稿，保存必须明确提交。

#### Scenario: 查看、编辑与离开
- **WHEN** 用户查看任务后编辑内容、选择状态或负责人并离开
- **THEN** 未提交修改不会自动保存；有修改时取消应可选择继续编辑或明确放弃，防止滑动关闭丢失草稿；保存成功回到更新后的详情。
- **AND** 保持所属会话成员资格、七状态（含 waiting）、层级、领取、删除、结果和通知契约，长内容/大字体仍可操作。

#### Scenario: 原生逐字段处理并发修改
- **WHEN** 原生编辑保存因 revision 过期失败，用户读取最新内容
- **THEN** 保留本地修改；远端独有修改纳入待保存稿，同字段不同修改具名比较并要求用户选择我的或最新；必须明确确认后才以最新 revision 保存。
- **AND** 再次冲突仍保留草稿重新比较，删除或失去权限不得覆盖或重建任务；新建子任务冲突保留输入，刷新父图后明确重试。

## REMOVED Requirements

### Requirement: 六种状态表达进展，验收采用引导而非强制门禁

## ADDED Requirements

### Requirement: 七种状态表达进展，验收采用引导而非强制门禁

状态为 todo、doing、waiting、in_review、done、paused、closed。doing 与 waiting 为并列持久状态，页面合并分组不改写状态。Agent 引导采用做完先提交待确认供人验证、确认后完成；系统仍允许直接完成，不增加必经审批、专属验收人或第三种任务权限角色。

#### Scenario: 提交结果

- **WHEN** Agent 完成工作并按协作引导提交结果
- **THEN** 可以标为待确认，展示结果并等待反馈；有资格的成员可调整状态，系统不强制每次完成都经过真人审批。

#### Scenario: 普通父子状态变化

- **WHEN** 子任务全部完成，或父任务被暂缓、关闭、重新打开
- **THEN** 未明确指定的其他节点状态保持，父任务不会因子任务完成自动完成；本人 doing 带来持续推进责任，waiting 满足有效安排时允许等待；父子关系不直接启动或停止对方 Agent。
- **AND** 显式调整整个子树时保留已完成节点的完成事实；普通父状态变化不等于整棵子树状态操作。

### Requirement: 等待信息 SHALL 与实际运行状态分别呈现

#### Scenario: 浏览等待任务
- **WHEN** 用户在 Web 或原生 iOS 查看 waiting 任务
- **THEN** 在进行中组看到等待中标记，详情可见等待原因、恢复条件与已安排检查时间。
- **AND** 负责人运行、空闲或离线单独表达，不能从任务状态推断正在运行；Global 与 single_thread 均读取真实原生状态。只读观察沿 Task 读权限从实际负责人解析，不返回其他聊天内容，连接或读取失败不沿用旧的运行状态。

#### Scenario: 安排失效或无法核实
- **WHEN** 用户打开详情且关联安排已失效或当前无法核实
- **THEN** 保留原业务等待原因及恢复条件，另外分别看到安排需要处理或暂无法核实，不把无法核实当作已确认有效，也不把保存的安排时间当成实际执行回执。

#### Scenario: 用户停止或恢复
- **WHEN** 有资格用户在详情暂缓任务或明确恢复推进
- **THEN** 分别保存 paused 或 doing 并清除 waiting 关联，返回列表后分组计数一致；正常消息不会自动恢复 paused。
- **AND** 用户无需手填原生 Schedule ID，界面不提供没有真实安排的直接 waiting 设置。
