## 原始需求

> 现在我们缺乏一个东西，就是显示的开关 agent。现有的/stop不能满足。我想说的是，真正把一个agent所有活动立刻停下来，并且不会被任何机制再唤醒的开关。停用该agent的开关。场景有两个，一种是紧急停止，比如说我发现Agent做了一个正在做一个高危的动作，那我想赶紧把它掐停，就这种场景，所以需要保证Agent以及它所开的Sub Agent，或者说它后台开的Bash任务，所有都要停。然后另一个是我这Agent这段时间希望不用它了，那就希望后面它都不会被其他什么机制唤醒，比如说Task机制啊，比如说群里面消息啊，都不能把它唤醒，就我希望它被停用。帮我理解一下，思考一下这个应该怎么设计。raft应该有类似的机制，可以学习

## 用户场景

1. 主人从 Agent 的工作视图发现危险动作，立即停用。跨聊天的主执行、各层 Sub Agent、普通后台 Bash 和终端一起停止，其他 Agent 继续工作。用户无需让模型理解停止意图，也无需等待普通任务排队完成。
2. 主人暂时不用一个 Agent。停用状态跨页面、节点重启和重连保留；私聊、群聊、Task、定时任务、Heartbeat、子任务回报等都不能唤醒它。
3. 主人在节点离线或清理失败时停用。系统保留停用意图，清楚说明尚未确认停止；恢复连接后继续处理。用户仍可查看历史和确认状态，不因超时误以为危险活动已经停止。
4. 主人重新启用 Agent。旧会话、文件和任务记录保留；新请求可正常处理，但被中断的旧任务、旧审批和积压执行不会自动恢复。用户需明确恢复具体旧任务。
5. 主人和其他成员看同一个 Agent 时，能区分设备在线与 Agent 是否启用。只有有权管理该 Agent 的真人可以改变开关；别人发消息或 Agent 自己调用工具不能解除停用。

## 验收标准

### Requirement: 管理者可以从明确入口立即停用 Agent

#### Scenario: 从工作视图紧急停用
- **GIVEN** 管理者正在查看 Agent 的工作过程
- **WHEN** 点击停用
- **THEN** 无需再经过确认弹窗或等待 Agent 回答即可提交停止，页面立即显示操作进度
- **AND** 停用独立于配置表单保存，不因未保存的其他设置而受阻或顺带保存这些设置

#### Scenario: 空闲 Agent 也能停用
- **WHEN** 管理者停用没有活动执行的 Agent
- **THEN** Agent 进入持久停用状态，而不是提示当前没有任务后仍允许被唤醒

### Requirement: 停用覆盖该 Agent 的全部受管执行

#### Scenario: 跨聊天、后代及后台工作一起停止
- **GIVEN** 同一 Agent 在多个聊天工作，拥有子 Agent、孙级 Agent、普通后台 Bash 和持久终端
- **WHEN** 管理者停用它
- **THEN** 这些执行全部收到停止并被终止，不需要逐一操作
- **AND** 只有确认全部受管活动已停止时才显示“已停用”，工作记录保留中断事实

#### Scenario: 其他 Agent 不受连带中断
- **GIVEN** 同一节点的另一个 Agent 正在独立工作
- **WHEN** 管理者停用目标 Agent
- **THEN** 另一个 Agent 继续工作，它的任务和会话不被暂停或重置

### Requirement: 停用期间任何自动机制均不能唤醒 Agent

#### Scenario: 消息与自动任务触发
- **GIVEN** Agent 已停用
- **WHEN** 到达私聊、群消息、提及、其他 Agent 的消息、Task 推进、Heartbeat、Schedule 或子任务回报
- **THEN** Agent 不开始执行、不调用模型或工具，也不发送旧结果
- **AND** 聊天历史仍可保存和查看，系统明确表达停用，不假装 Agent 已接手处理

#### Scenario: 重连、重启和重复操作
- **GIVEN** 管理者已经请求停用
- **WHEN** 节点或服务重启、连接恢复，或管理者再次提交停用
- **THEN** 停用意图持续有效，不因自动恢复、重试或重复操作而被撤销

### Requirement: 未确认停止时如实展示并保留停用意图

#### Scenario: 节点离线
- **WHEN** 管理者停用离线节点上的 Agent
- **THEN** 页面显示“已请求停用，等待节点确认”，不能显示已经停止
- **AND** 节点重连后先应用停用，再决定是否可以执行新工作

#### Scenario: 清理超时或失败
- **WHEN** 停用过程中无法确认执行与后台活动已经全部停止
- **THEN** 页面持续表明“停止未确认”及具体原因，提供重试停止入口
- **AND** 新工作仍被禁止，不把失败解释为重新启用

### Requirement: 重新启用只恢复新工作的执行资格

#### Scenario: 明确重新启用
- **GIVEN** Agent 已确认停用且保存着旧会话、任务和工作文件
- **WHEN** 有权管理的真人重新启用
- **THEN** Agent 可以处理新的请求，旧会话、任务、文件和历史仍可访问
- **AND** 不自动恢复被中断的任务、子 Agent、后台命令、旧审批或旧输出；停用期间错过的定时触发不补跑
- **AND** 独立周期计划只从未来触发点继续；服务于已暂停旧任务的计划不自行恢复

#### Scenario: 用户明确恢复旧任务
- **GIVEN** Agent 已重新启用，旧任务仍暂停
- **WHEN** 用户明确恢复某项旧任务
- **THEN** 只恢复被指定的工作，其他暂停任务保持暂停，已失效的审批不能直接作为新动作的放行依据

### Requirement: 开关遵守管理权限且不与在线状态混淆

#### Scenario: 非管理者与 Agent 自身不能改开关
- **WHEN** 无管理权限的成员查看或尝试操作开关，或 Agent 自身尝试重新启用
- **THEN** 可以按已有权限查看状态，但不能改变开关，也不能通过聊天、自动任务或普通 Agent 工具绕过

#### Scenario: 设备在线但 Agent 停用
- **WHEN** 用户查看运行在在线设备上的停用 Agent
- **THEN** 界面同时准确表达设备在线与 Agent 停用，不用绿色在线标识暗示它可接手工作

## 范围与非目标

- 在范围：普通与个人 Agent、global 与 single-thread；Agent 全部主会话及受管后代、Bash、终端、后台工作；所有唤醒与恢复入口；真人管理权限、持久停用、重新启用与旧任务显式恢复；Web 桌面/窄屏与 iOS 现有设置及工作入口；保留历史与旧数据的迁移。
- `/stop` 保留现有语义，不自动升级成永久停用；本次不新增聊天命令。
- 不扩展 DSH 在 macOS 等平台上的进程隔离保证，不新增虚拟机或容器。不承诺撤回外部系统已接受的动作，不接管通过 launchd、远端服务等另行启动的独立服务或主动逃逸受管范围的进程。
- 不把其他独立产品 Agent 当作 Sub Agent 连带停止；停用不删除 Agent、历史或用户文件。
- 不增加失联自动停机租约；离线请求须如实显示未确认。停止不是回滚已经发生的副作用。
