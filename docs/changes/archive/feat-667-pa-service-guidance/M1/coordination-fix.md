# 密集协调与重复通知修正

## 问题与范围

用户明确要求直接修复主/子 Agent 多轮密集往返，以及主 Agent 频繁向用户转述内部进展的问题。此修正属于 feat-667 的持续工作与安静服务反馈，基于 `7c23db0e9` 单独实施，不处理安全通知故障、耗时投影或确定性 E2E 改造，也不改变原生调度、消息协议、权限、子 Agent 生命周期或模型。

## 直接观察与原因

[交付耗时分析](delivery-latency-analysis.md) 的 21:29 CST 快照记录 PA 51 turns（44 次由 agent-message 触发）、同一 ongoing-work.md 54 次读取/57 次编辑，以及 62 次 send_message。次数不是净耗时，也不能据此判定每次通信都无用。

具体链路：根会话 `5524e22e-d1af-44f3-bd49-93350fa059e9` 的 turn 3 中，执行者已说明基线构建成功、发现 daily 模板差异且将使用基线支持的隔离栈继续。主 Agent 仍回传“收到”、重复既有限制，再向用户转述同一内部进展。turn 4 中执行者已说明对子进程环境变量做限定复核，主 Agent 再次回复收到和继续。后续记录有相同的进展→父级唤醒→重复指导/对外转述→工作笔记更新链路。

实际 provider 请求 `1793090824827829000.json` 证实主 Agent 消费到的 Global 指导要求长任务报告 meaningful findings / plan changes，并仅用“简短、避免重复”限制通知。子 Agent 指导允许主动回传 findings/drafts/results，却未区分需要父级行动与普通进展。已捕获的子 Agent 请求还包含 Task Feature 的“Report confirmed Task changes, actual progress, blockers and results”常驻指令，泛化要求回报实际进度。ongoing-work 要求收到新输入就找记录，缺少“上下文已经足够时不重读、状态未变不写”的条件。这些指导组合没有明确结束无需决策的往返；已确认实际重复行为，不将所有延迟归因于单条提示。

同时核对锁定 DSH 的实际任务注入与返回语义：continuable 明确要求结束前 send_message，完成通知也可能附收尾文本；fork 则完成返回。修正保留该模式，不用一条“只靠完成返回”覆盖两者。旧委派还显式要求“关键进展/过程里程碑主动回报”，因此新委派指导同时去掉这种默认泛化要求；已有明确汇报约定不能被当作无条件静默场景。

## 目标行为与最小修改

- 委派时约定成果、边界与何时需要上级介入；执行者在既定范围内持续工作，不逐步报进度等待批准继续。
- 普通进展、受理回执及可独立处理的问题不逐项触发内部消息；结果遵循原生模式：continuable 结束前内部发送一次完整结果再简短收尾，fork 通过完成返回；父级不因随后完成通知重复交付。真正阻塞、需要资料/决定、影响交付的重要变化及约定节点仍及时回传。
- 父级只发送能改变执行的新信息、更正或决定，不对纯进展回复“收到/继续”或重述原有要求。收到内部消息不自动等于需要对用户发消息。
- 工作记录保留可恢复的当前状态；仅在要求、执行者、成果或等待/阻塞状态发生实质变化时修改，上下文信息足够时不重复读文件。
- 保留首次真人交办确认、用户主动询问状态、真实阻塞、重要变化、停止/更正与最终交付；不设硬性限频、时间窗、关键词过滤或新的调度器。

修正同步收窄 Task Feature 的 child 常驻回报指导，保留其已确认等待/成果的反馈和固定会话路由；不改 Task 工具或状态回执逻辑。

## 验证范围

保留现有 Global/PA root 与 child、spawn/fork/冷恢复工具边界测试；指导文案不新增逐句快照断言。行为检查采用同一真实历史请求的限定重放，记录实际下一步选择与需要沟通的控制场景；重放不执行任何工具、不接续原运行中的 Agent，不替代完整产品长任务或独立验收。不执行回放响应里的工具调用。


## 实施与实际验证

最终产品改动仅三处：`global-mode.ts` 主/子角色指导、`features/task-graphs.ts` 子角色回报指导，以及随包 `nano-ongoing-work/SKILL.md`。没有改变工具注册、消息执行、持久化、审核或调度代码。默认 Persona 与用户自定义指令不回填。原生内部发送与 fork/continuable 返回语义保持；新委派明确不要求逐阶段或泛泛的“关键进展”回报。

## 交付边界

这是当前 unit 的有界修正，保存在独立 `codex/pa-coordination-quiet` 分支，基于 `7c23db0e9`；未改变主线程正在运行的服务、旧 PA 的委派或工作区。旧会话中已经给出的明确汇报要求及已加载正文仍可能影响行为，不能用源码已修改宣称旧实例实时生效。

此侧聊只实施并自验该修正，未做独立 code/context review 或完整长任务产品复验，也未归档 unit 或创建/合并/部署 PR。主线程集成后按实际 delta 完成现有独立审查与受影响验证；无需重跑无关的安全通知、审核重试全矩阵。现有 feat-667 完整交付状态不由本报告改写。

### 亲测修正：首次确认仅用于长任务

用户在新 PA 请求把既有解释改为交互图（主会话 `85c9210b-1add-4d89-bd07-21b57f30f03e`，turn 4）时，实际先收到回答预告，再收到图解。Global 常驻指导要求每次真人任务都先确认，Skill 也保留了无条件确认；交互 UI 协议并不要求分两次发送。原始工具顺序保存在本机 `coordination-fix/simple-request-before.json`。

按用户“只加一个定语”的纠正，Global 原句仅将 `a task` 改为 `a long-running task`，Skill 同步限定长任务；不再追加简单请求清单或另一套消息规则。对应 delta 保留长任务确认及用户不回复例外，并覆盖简单请求直接交付。

验证只覆盖本次两处指导：相关包构建通过，既有 Global/PA 原生 fixture 的一次性探针核对最终模型输入包含长任务限定、没有旧无条件句；不新增永久文案快照测试。原工具边界、原生返回和已通过测试继续保留。探针不证明真实模型一定采用新节奏，亲测运行中的 #420 工作不为加载此修正而强制中断。
