# 实施自检：搜索与容量

- 代码基线：实现基于 `6b95850a6`；证据对应本 unit 的实施提交，最终以该提交内容和审查时版本为准。
- 隔离环境：Air，本 unit worktree，Node v24.22.1；运行 `/tmp/nano-feat-680-e2e` 的独立 daily IM + Gateway，账号、消息、聊天和 workspace 均为合成测试数据。
- 真实模型：daily PA 使用 `codexOAuth:gpt-6-astra` / medium。测试主人在虚构蓝鸟项目群中依次记录周四计划和因测试未完改为周五，在 PA 私聊要求回溯。PA 调用 `conversations search`，参数为 `keywords: ["蓝鸟", "发布方案"]`、`limit: 30`；返回原始来源和真实消息，完整消息省略 `complete_message`，末页省略 `has_more` 与 `next_cursor`。PA 随后读取群历史，在原 PA 私聊发送周五结论和两条原消息链接。实际调用和交付可在隔离 IM 的 PA Work 记录中复核；本证据不证明所有模型和任务都能如此调用。
- 真实全栈高命中单样本：在同一隔离 IM 中写入 100 个合成聊天、100,000 条消息，其中 50,000 条包含“量测山雀”，测试写入事务 489 ms；PA 因自然语言请求调用 `conversations search`（`query: "量测山雀"`, `limit: 20`），Work 中记录工具耗时 465 ms，返回 20 条及 `next_cursor`。这是一条真实调用，不是 p95 或生产容量保证。
- 隔离磁盘微基准：Node v24.22.1，SQLite 文件库，100 聊天、100,000 消息、50,000 次字面匹配，取第一页 20 条；旧版 `Work.query` 3 次分别 5,459 / 5,900 / 7,003 ms，新版 10 次分别 199 / 203 / 211 / 224 / 232 / 253 / 256 / 289 / 291 / 426 ms。两版在同一进程顺序执行，进程 RSS 读数分别 860 / 933 MiB，包含此前执行和运行时保留，**不能**据此比较各版本独立内存；合成写入 100,000 条事务 1,429 ms，当前方案未新增消息写入钩子或索引。微基准直调 Work，不包含 RPC、模型、多个并发用户或真实磁盘压力；不宣称生产 SLA。
- 独立进程补测：相同规模和命中率、相同 Node 与隔离磁盘数据，各版本在单独进程创建同样的数据集后顺序运行。旧版查询 3 次 2,338 / 2,070 / 2,127 ms，RSS 起始 125 MiB、结束 890 MiB、峰值 890 MiB；新版查询 10 次 100 / 117 / 123 / 99 / 105 / 100 / 105 / 104 / 97 / 109 ms，RSS 起始 112 MiB、结束 251 MiB、峰值约 258 MiB。各进程各一次插入 100,000 条事务分别为 557 / 309 ms；写入路径没有变更，这种单次顺序比较受缓存和机器负载影响，不能当作精确写入增益或生产 SLA。进程 RSS 包含运行时与 SQLite；查询样本仅代表本机单用户、单请求。真实全栈单次 465 ms 见上一条，不等同这些直调样本。
