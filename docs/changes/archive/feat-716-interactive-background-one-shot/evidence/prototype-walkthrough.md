## 方法与边界

- **渲染方式**：headless Chrome `--headless=new`，逐状态打开 `file://…/prototype.html?state=<state>` 截图；桌面状态 `--window-size=1400,1000`，窄屏与 iOS 状态 `--window-size=520,1080`（520 是装载 390 面板的窗口宽度，面板本身固定 390）。
- **留证参数**：`?state=<state>` 选状态；冲突态加 `&diff=1` 展开只读对比；`&card=other` 让卡片显示另一台设备已保存的版本（周三 14:00、含李雷）；`?state=saved&card=other&note=adopted` 复现“改用最新草稿之后”的画面。
- **原型性质**：静态 HTML，全部样式与脚本内联，无外部字体/图标/CDN、不访问网络、不接后端。保存、发送、重试、冲突恢复都只在页面内模拟。
- **产品底色**：会话页外壳（会话列表、消息列表、交互卡片、composer、既有提示）按 `global.css` 与 `interactive-card.css` 的既有类名与 design token（`--im-accent:#0f766e`、`--im-danger:#c44747`、`--im-border` 等）复刻，不另建视觉体系。
- **真实产品基线**：本轮未启动 e2e 栈、未截真实产品图。基线取自代码事实——`message-pane.tsx:1259` 的 `interactive-selection`「是否送达尚未确认」行、`interactive-card.tsx:219-227` 的卡片内错误行、`global.css` 的 composer 尺寸与 danger 配色。真实产品对照留给 M2 `[reviewer]` 第 4/5 条。
- **演示控制**：状态切换、宽度切换、「重试保存」、「查看最新改动」→「改用最新草稿」可点；真实发送、卡片业务动作、会话切换不可操作。
- **像素与文案同步**：409 分支标题/正文改成“这个会话暂时不能发送”之后，用同一命令重渲染了受影响的五张本地截图（`conflict.png`、`conflict-diff.png`、`conflict-adopted.png`、`iosconflict.png`、`iosconflict-diff.png`），下表截图的文案与当前 HTML 一致。

## 事实 → 判断 → 修正

| 事实（渲染后看到的） | 判断 | 修正（原型里做了什么） |
|---|---|---|
| 卡片改动保存失败时，唯一的提示是卡片底部「草稿暂未保存。重试」；卡片此时可能已滚出视口，按下发送的位置看不到它 | 现有反馈在“发送瞬间”不可见，用户会发出缺背景的消息且毫不知情——这正是 D9 要堵的洞 | 把提示搬到输入框正上方（贴发送按钮的视线路径），并在保存成功前禁用发送 |
| 第一版提示标题只写「卡片改动尚未保存」 | 读起来像“再点一下重试就行”，没说明这次不会带上，也没说明消息没发出 | 标题改为「卡片改动尚未保存，这个会话暂时不能发送」，正文补“先保存再发送，否则这次不会带上你刚改的周四和参会人”；结论在前、原因在后 |
| 第一版正文写「这条消息没有发出」 | 实现上 flush 在 `commit()`/`ChatStore.send` 前进行，拦住的是**该会话此刻的所有发送**（包括与卡片无关的追问）；措辞把会话级代价说成了单条 | 标题改成“这个会话暂时不能发送”，正文补“同一会话的其他消息也要等它保存好”；Risks 表同步记这条代价 |
| 离线状态下「重试保存」一定失败 | 给一个不会成功的按钮等于假装有出口，但也不能提供“仍然发送”绕路（spec 非目标） | 保留按钮与失败态样式，正文明确“当前网络不可用，恢复后会自动放行”；不新增任何分支动作 |
| 409 冲突时若沿用 transient 的「重试保存」，只会用同一份旧 revision 再撞一次 409 | 唯一给出的补救路径不可实现 → 输入区永久卡住，用户既发不出也看不出是“另一台设备赢了” | 冲突单独一个 alert，**不给**「重试保存」；第一步只给只读的「查看最新改动」，点开后出现三列表（字段 / 另一台设备 / 我这台）与「改用最新草稿（会放弃本机这次改动）」 |
| 「改用最新草稿」一点就丢掉本机这次编辑 | 必须显式说明放弃，不能静默丢弃；合并也不能静默发生 | 按钮标签直接写“会放弃本机这次改动”，对比表 caption 写“只读对比 · 不会自动应用或合并”；放弃前的本机编辑与正文一直留在屏幕上 |
| 409 态的卡片底部仍画着现状那一行「重试」 | 真实产品在这张卡的 409 分支给的是冲突文案 + 「读取最新」（`interactive-card.tsx:219-227` / `InteractiveCardView.swift:24-29`）；原型若照抄会让读者以为本 unit 要改卡片内动作 | 保留现状那一行（它正是“卡片内提示不够、所以要搬到发送处”的对照物），并在 `?state=conflict` 的说明里写清这处差异不在本 unit 范围内 |
| iOS 冲突态第一版只有对比表与「改用最新草稿」 | `may-adapt` 只放宽形态，不放宽“明确放弃”这条语义 | iOS 的采用按钮补成「改用最新草稿（放弃本机这次改动）」，caption 补“不会自动合并”，与 Web 同义 |
| 第一版把卡片「地点」字段也画上，卡片过高，卡片内的既有错误行被 composer 盖住 | 看不到“现状提示在哪”，就无法对照这次搬走了什么 | 原型里去掉一项字段，让卡片与卡片内错误同时可见（这是原型的取景取舍，不改真实卡片结构） |
| 窄屏 390 上新增 alert 与既有「未确认」可能同时出现 | 两条都是整行提示，容易互相挤压，也容易被读成同一件事 | 固定顺序：拦截 alert 在上（红框 + danger 标题 + 动作），既有 status 在下（蓝底、无动作）；截图确认各自整行换行、不重叠、输入框仍可见可编辑 |
| 窄屏下 alert 折成多行，「重试保存」若垂直居中会浮在正文中段 | 唯一的推进动作不该飘 | 窄屏下按钮 `align-self:flex-start`，落在结论行右侧、仍在发送按钮的同一视线路径上 |
| iOS 版第一版把用户气泡「这样还能排得下吗？」画进了消息列表 | 与“这条消息因草稿没保存而没发出”自相矛盾，等于演示了一条已发出的消息 | 删掉该气泡，正文只留在输入框；列表最后一条仍是 Agent 的回复 |
| 保存成功后若再加一行“已保存”提示 | 违反既有“正常成功无保存提示”的约定，会让用户以为多了新机制 | 成功后 alert 与卡片内错误一起消失，不加任何成功提示；只用发送恢复可用表达“可以发了” |
| 点击「重试保存」后正文与卡片选择需要保留 | 提示消失后如果正文被清掉，用户要重打；卡片选择丢失则这次改动等于没保存 | 恢复态保留输入框正文与卡片当前选择（周四、参会人去掉李雷），只改提示与发送可用性 |

## 对设计提出问题的回答

- **提示是否在“按下发送”的位置被看见**：是。alert 位于 composer 顶部、输入框上方一行，与发送按钮同一垂直视线路径；卡片内既有错误保留，但不再承担拦截职责。
- **是否清楚表达“这次没带上去”**：标题先说后果，再说原因（改动没保存、这次不会带上），没有停留在“保存失败”这种技术描述；409 分支进一步说明是“另一台设备改过”。
- **失败原因不同是否有不同的出口**：有。网络/5xx 与离线只有「重试保存」（离线时明确它现在不会成功）；409 不给重试，先只读对比、再显式放弃本机改动并采用服务端草稿，两条路径都能回到“发送可用”。
- **拦截范围是否被说清**：是。标题与正文都说“这个会话”，并点明同一会话的其他消息也要等这张卡保存好；不提供“仍然发送”分支（spec 非目标不引入“附带开关/Detach”心智）。
- **窄屏是否挤压输入框或与“未确认”互相覆盖**：不会。两条整行提示在拦截态下并存，顺序固定为“拦截”在上；输入框仍可见可编辑（`evidence/screens/both.png`）。

## 未验证（留给 M2 验收）

- 真实网络失败与 409 冲突：原型只用状态开关演示两条分支（含“查看最新 → 改用最新草稿”的两步），没有真实的 `interaction-state` 请求、超时、旧 `expected_draft_revision` 与 409 响应；两步之间的服务端 revision 变化也未模拟。
- 真实产品的间距、字体度量与断点：原型复刻既有类名与 token，但用固定面板宽度（1180 / 390）代替真实断点与容器查询，不能当作像素级基线。
- 卡片是否真的已滚出视口、输入法组合输入、键盘弹出与 Safe Area、焦点顺序：均未实测。
- iOS 只对齐语义与组件形态（design 中标为 `may-adapt`），未做像素级或真机走查。
- 无后端，不能证明“发出后只携带一次”“切换会话清除”“换设备继续”“discard 水位只清 ≤ 那次改动”——这些只能由 M1/M2 的真栈与请求断言证明；原型里也看不到水位与 `discard(through)`。
- 辅助技术未实测：只有 `role="alert"` / `role="status"` 的结构与文案层级，未用 VoiceOver 或键盘遍历验证朗读与焦点顺序。
