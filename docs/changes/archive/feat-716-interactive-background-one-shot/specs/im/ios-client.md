# IM ios-client Specification (delta for feat-716)

## MODIFIED Requirements

### Requirement: 原生通用交互回复
客户端 SHALL 呈现当前 openui/nano-iui-1 通用交互回复，并保持与 Web 一致的组件、布局、绘图和动作语义；私人编辑、显式继续、只读历史和原聊天权限 SHALL 保持。私人背景是否随消息携带 SHALL 由中心按一次性语义判定，客户端 SHALL NOT 自行选择、缓存或上报背景。

#### Scenario: 跨端阅读同一回复
- **WHEN** 用户在 iPhone 打开含新版 Intelligent UI 的消息
- **THEN** 酒店照片卡片、看板图表/SVG 和会议选择使用同一源码呈现，正文仍独立可读；组件资源不要求在线 Web 页面。

#### Scenario: 本地探索与显式继续
- **WHEN** 用户操作回复中的输入、选择、计算或图表并明确请求继续
- **THEN** 本地探索即时更新而不触发 Agent；显式请求携带当时完整状态，只创建一次用户消息；私人草稿可恢复并保持原有冲突处理。

#### Scenario: 私人状态与历史
- **WHEN** 用户重新打开卡片、遇到其他设备的更新或查看只读历史
- **THEN** 恢复本人的选择，并发冲突可读取最新内容；历史可读但不能绕过权限提交。

#### Scenario: 私聊文字携带背景
- **WHEN** 用户在私聊改动 A、B 卡片的字段或选择后发送文字
- **THEN** 手写正文完整保留，这条消息携带两张各自最新状态并一起消费；紧接着不再改卡发出的下一条一张都不新带
- **AND** 后来只改 A，下一条只带 A；同卡多次编辑只携带最终状态一份
- **AND** 只打开、滚动、刷新或重载卡片不产生背景，只有用户的真实改动才算
- **AND** 重新打开 App 或换设备后，这次尚未发出的改动仍随该会话的下一条消息携带一次

#### Scenario: 发送前完成卡片保存
- **GIVEN** 私聊中有尚未保存的卡片改动
- **WHEN** 用户按普通发送按钮
- **THEN** 先尝试保存改动，保存成功后同一次点击继续发送；有效待发改动只随这条消息携带一次
- **AND** 保存因网络或临时故障失败时，使用普通发送失败反馈，保留正文和卡片改动。再次点击发送会重试保存，成功后继续发送。

#### Scenario: 自动同步同一账号的最新卡片草稿
- **GIVEN** 同一账号在另一端已保存较新的卡片草稿，当前端提交的旧版本被拒绝
- **THEN** 自动读取并显示服务端最新保存的卡片状态；用户已点击发送时，保留该次点击的正文并继续发送
- **AND** 读取失败时保留本机编辑和正文并沿用普通发送失败反馈，下一次发送重新读取最新版本。

#### Scenario: 多卡背景过大时恢复
- **WHEN** 普通发送的有效卡片背景整组超出总量边界
- **THEN** 沿用会话发送错误反馈，明确说明尚未发送及缩减卡片内容后重试、或在做过改动的设备上离开此聊天清除该端已保存待发背景的方式
- **AND** 正文、附件和卡片编辑保留，整组不消费、不静默少带，下一次发送重新按全部有效待发卡片判定

#### Scenario: 内容与宿主权限隔离
- **WHEN** 回复包含沙盒页面、查询、草稿采用或继续请求
- **THEN** 内容不能取得会话凭据或调用未注册 API；历史只读、访问撤销及退出登录后不能绕过原生权限发起业务请求。
