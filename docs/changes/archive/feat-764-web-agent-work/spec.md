## 原始需求

> 得重新设计work页的交互体验。滚动只能滚动左边，左边到底了就自动加载。所以右边永远看不到底。而且整个设计也不方便看。给我整体思考下，整个work页应该怎么合理的设计用户交互

> 我大概懂你的设计了，但是感觉还是怪怪的，而且还要考虑还有二级的subagent。
>
> 另外我还有一个需求，就是我希望work页能某个视图下，看到最近几天活跃的agent关系，比如类似我画的这个丑图，就能够看到一目了然，到底开了什么subagent。点进去能够看那个Agent的轨迹。

> 基本认可你整套设计，新建个unit做出来吧

## 澄清记录

- 连续阅读：“我觉得你这个太傻逼了，一轮没有什么信息量的啊。你每次都打开一轮，然后搞个查看轮次的下拉框，非常不舒服。而且，我对你工作记录里每次要点开进入轮次视图这个已经感觉很不舒服了。然后，主agent消耗了多少token为啥在派工关系中不体现”
- 数据和保真：“原本ui中提供的信息不要任何丢失”“保证出现在页面的东西要有来源，不是凭空做的”。用户后续澄清：“我说的有出处的意思是后端得有那个数据才能展示，不是让你关联现在的。”
- 聊天入口：“我觉得用户在聊天界面上点击某个agent头像应该能很方便看到他的工作进展（这个应该不用跳转页面，但是怎么设计好，得好好想想，私聊和群聊或许还需要不同的设计），并进而可以到他的配置页改配置。（假设这个用户有权限看这个agent的work）”
- 工作范围：“以及你把它分成本群以及全部工作。你怎么分呢？Agent一直在工作，他哪怕他读的是本群的，他可能在做的是其他的。”已对齐头像按 Agent 展示，不推断工作属于聊天会话。
- 头像卡：“点头像点进去，最好还能看到一些浓缩的信息，比如说现在正在跑多少个subagent。”“可以，相当于正在执行中则给的是最新的一次工具调用。那我觉得这种情况没必要搞个侧边栏吧。搞个头像旁边的浮窗就行了吧”。用户确认同步中用转圈后说：“好，这个定下来了，再回到work页的设计，重新给我一版”。
- Dreaming：“然后关于dreaming，原本没有设计在主agent工作记录中。你插进去，我觉得也合理但是，你没给跳转，跳转到dreaming实际的轨迹，其实这里类似subagent一样。然后也应该给工具次数，模型，token。”
- 工具：“我觉得关于怎么展示工具的详细信息，这个，你得有一套固定的设计，不要随机游走，有的是json有的又是语义化的。”原生轨迹：“我们不改原生轨迹的内部设计，现在做的挺好的，什么细节都在里面。”

- 单条回复入口：“然后每个agent消息下面有个work，点击进去跳转。这个work有点赘余，页面上看着很怪，你看这个怎么设计下”
- 性能：“你做具体实现设计要考虑性能问题，可以看过去我对work页面的性能优化上的努力。之前特别慢”

## 用户场景

用户平时从聊天判断 Agent 是否还在做事、最新做了什么、还有多少子执行。需要追查时从头像或聊天回复进入 Work，连续阅读真实记录、定位工具与消息、沿着委派追到二级执行。另一条入口从派工关系看近期全局和各执行的 token，用同一时间线查看明细。维护任务有独立身份，用户希望看真实阶段和轨迹。现有能力参考 [Agent Work](../../../specs/im/agent-work.md) 和 [Web Chat UX](../../../specs/im/web-chat-ux.md)。

## 验收标准

### Requirement: 主 Agent 和子 Agent 的 Work 可以连续阅读

#### Scenario: 在历史、发信轮次和嵌套子执行之间阅读
- **WHEN** 用户打开 Work、从一条回复定位 Work，或沿派工进入子执行和二级子执行
- **THEN** 可以在单一阅读区连续查看多轮记录，进入子执行后滚动能读到该执行末尾。
- **AND** 回复入口定位真实发信轮次并保留相邻历史；回到父执行时恢复发起位置和已展开详情。

#### Scenario: 较早记录和连接异常
- **WHEN** 用户读到已加载历史的末尾，或同步中断、历史或过程加载失败
- **THEN** 可以在原处继续加载或重试，仍能阅读已保存内容，当前阅读位置不会被刷新或分页抢走；状态未确认时给出对应反馈。

### Requirement: 派工关系可以检查多层执行与实际用量

#### Scenario: 从选定时段的关系进入真实执行
- **WHEN** 用户在「派工关系」查看最近数日或切换时间范围
- **THEN** 可辨认真实派工、嵌套层级和执行状态；同一子执行的多次唤醒从同一个节点可读，标题相同的独立执行可区分。
- **AND** 主节点和子节点各显示本身已报告的累计 token，子节点用量不会重复算入主节点；未报告或范围内统计不全时有清楚标识。
- **AND** 点节点进入相同的 Work 时间线，返回后恢复时段与节点。

### Requirement: 工具详情和 Dreaming 保持可读且可追溯

#### Scenario: 查看不同种类的工具
- **WHEN** 用户查看或展开终端、文件、消息、委派或其他工具
- **THEN** 从调用行能扫到工具名、已有描述、状态和耗时；详情按调用、结果、来源的顺序展示已保存事实。已支持的终端、文件、差异和消息呈现仍可用，其他结构化数据可逐项检查。
- **AND** 原消息和子执行入口与所属工具相邻。实际发信正文只显示一次，和请求不同才分别标识；调用完成、实际投递和子执行完成各据其真实状态展示。

#### Scenario: 检查一次 Dreaming
- **WHEN** 用户在主 Agent 工作记录查看 Dreaming 提取或整合
- **THEN** 能区分阶段、查看工具次数、模型及 token，并打开该次 Dreaming 的原生轨迹；无模型请求或未报告的值明确标识。

### Requirement: 聊天内可以就地查看 Agent 的工作状态

#### Scenario: 从私聊或群聊头像打开状态卡
- **WHEN** 有 Work 查看权限的用户在私聊或群聊点击 Agent 头像
- **THEN** 头像旁打开状态卡，聊天保持当前位置和草稿。卡片按 Agent 展示主执行状态、执行中的本轮最新工具和工具状态，以及正在运行、待授权的子 Agent 数量。
- **AND** 一、二级子 Agent 按真实身份去重，可展开名单并进入对应 Work。卡片提供完整 Work 入口，有编辑权限时显示独立配置入口。

#### Scenario: 同步中、离线或权限不满足
- **WHEN** 工作状态还在同步、节点离线或用户缺少权限
- **THEN** 同步中使用进度指示；状态无法确认时不将缺失用量或数量显示为零；用户只能查看和进入已授权内容。

### Requirement: 单条消息的 Work 入口归入消息操作

#### Scenario: 从一条回复追到它自己的记录
- **WHEN** 用户打开 Agent 回复的桌面工具条、右键菜单或触屏操作面板
- **THEN** 能选择「查看这条回复的执行记录」并定位真实发信轮次；聊天消息下方没有重复的常驻 Work 链接。
- **AND** 键盘和触屏都能进入；无可阅读消息正文、仅交互卡或附件的回复仍可在具备原访问资格时打开。不可用、待同步、已删除的目标继续如实反馈。

### Requirement: 大量历史和大结果不妨碍日常查看

#### Scenario: 长历史中的首屏、头像状态和旧回复
- **GIVEN** Agent 有大量历史轮次、关联执行和大工具结果
- **WHEN** 用户打开 Work、点开头像、从旧聊天回复进入或回看过去执行
- **THEN** 可以及时看到首批记录或状态，旧回复直接定位，后续历史和大结果按需可达。
- **AND** 回看时，新活动不会让已读历史反复重新加载或丢失阅读位置。

## 范围与非目标

- 在范围：Web IM 的 Work 记录、派工关系、Dreaming 入口、聊天头像状态卡及为其提供准确数据的后端能力。
- 非目标：重做原生轨迹内部设计、根据聊天读写推断工作归属、从自由文本生成任务进度、修改 iOS 客户端布局。
