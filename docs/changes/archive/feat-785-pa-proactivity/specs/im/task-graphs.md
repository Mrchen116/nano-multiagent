# im/task-graphs Specification (delta for feat-785)

## ADDED Requirements

### Requirement: 九种状态表达提议、推进、「先存着」留存与完结，验收采用引导而非强制门禁

状态为 `proposed`、`todo`、`doing`、`waiting`、`in_review`、`done`、`paused`、`backlog`、`closed`（界面状态徽章统一严格呈现对应的九个标准状态词：待拍板、待办、推进中、等待中、待确认、已完成、已暂缓、先存着、已关闭；等待原因、复查时间与负责人独立呈现于状态徽章旁，不混入状态框内）。`proposed` 表示尚未获拍板的候选提议，记录提议依据与获批后行动范围，在获批前不触发自动执行；`backlog`（界面呈现为「先存着」）表示暂不推进且免于催促的留存事项，与执行中途暂停的 `paused` 区分。`doing`、`waiting` 与 `todo` 为独立持久状态，可在「进行中」区域聚合呈现而不改写底层状态。Agent 引导采用做完先提交 `in_review` 供人验证、确认后 `done`；系统仍允许直接 `done`，不增加必经审批、专属验收人或第三种任务权限角色。

#### Scenario: 待拍板提议的界面或自然语言翻牌流转
- **WHEN** 有写入资格的成员在焦点台、目标全景或聊天活卡片对 `proposed` 节点选择批准、「先存着」或关闭，或在对话中明确表达同意、暂存或拒绝后由 Agent 更新状态
- **THEN** 批准操作在节点负责人为 Agent 且同层无未完成 `dag` 前置依赖时将状态置为 `doing`（触发单次事件唤醒），在负责人为真人、未分配或仍有未完成前置依赖时将状态置为 `todo`；「先存着」置为 `backlog`；关闭置为 `closed`
- **AND** 未经批准前，`proposed` 与 `backlog` 节点不触发 Agent 执行；当用户在顶部「先存着」页签或目标全景中对 `backlog` 节点点击「提上日程」时，节点状态恢复为 `todo` 并进入「进行中」列表，保留原归属会话与说明，并可继续按需展开为目标图

#### Scenario: 提交结果
- **WHEN** Agent 完成工作并按协作引导提交结果
- **THEN** 可以标为待确认，展示结果并等待反馈；有资格的成员可调整状态，系统不强制每次完成都经过真人审批。

#### Scenario: 普通父子状态变化
- **WHEN** 子任务全部完成，或父任务被暂缓、设为「先存着」（`backlog`）、关闭、重新打开
- **THEN** 未明确指定的其他节点状态保持，父任务不会因子任务完成自动完成；直接分配给 Agent 的节点进入 `doing` 时触发单次事件唤醒推进，`waiting` 记录等待原因与可选检查安排；父子关系不直接启动或停止对方 Agent。
- **AND** 显式调整整个子树时保留已完成节点的完成事实；普通父状态变化不等于整棵子树状态操作。

### Requirement: 聊天消息可内嵌与真实任务实时同源同步的行动卡片

Agent 与 PA 发出的聊天消息 MAY 在顶层 `task_cards` 字段附带同一可见权限范围内的真实任务节点引用列表。Web 与原生 iOS 客户端直接按真实任务节点当前状态渲染卡片，不将任务状态固化为静态消息文本快照；原生客户端本地消息缓存同步保存该引用并在连接与任务更新时刷新状态。

#### Scenario: 私聊卡片与任务面板双向实时同步及外部通道兼容
- **GIVEN** PA 在聊天消息中附带了待拍板提议卡或相关任务节点引用
- **WHEN** 用户在聊天卡片点击批准、「先存着」或关闭，或在任务页面、通过对话更新同一任务节点状态
- **THEN** 聊天消息中的任务卡片与任务行动焦点台、目标全景图实时呈现一致的最新状态，不出现一端已处理而另一端仍停留待拍板按钮的分叉
- **AND** 消息发往飞书等不支持原生活卡片的外部过渡通道时，自动退化附带可读的纯文本事项标题摘要而不静默丢失

#### Scenario: 无权读取或已删除任务的降级呈现
- **WHEN** 消息引用的任务节点已被删除，或当前查看者无该任务所属会话读取资格
- **THEN** 服务端不返回该任务正文或结构信息，界面仅显示简洁不可用占位，不泄漏受保护任务内容

## MODIFIED Requirements

### Requirement: 图节点可按任一模式继续细分

根节点与任意子节点均可按独立单卡（`mode: "none"`）、计划依赖图（`mode: "dag"`）或探索衍生树（`mode: "explore"`）建立。独立单卡在后续演变为长线目标或多步事项时，可在保留原图 ID、节点 ID、上下文说明与关联链接的前提下，原位升级为计划依赖图或探索衍生树并挂入子节点。

#### Scenario: 零摩擦建立单卡并原位生长为长线目标图
- **WHEN** 用户或 Agent 在私人空间或已加入的团队会话创建新任务而未预先指定复杂图容器
- **THEN** 默认建立为单张独立任务卡（根节点 `mode: "none"`），无需两步创建空容器；创建已知多阶段目标时也可一次原子提交根节点与初始子结构
- **AND** 当后续为该单卡补充阶段子任务或探索分支时，原卡原位展开为 `dag` 或 `explore` 目标图，原有标题、正文、结果与引用链接保持有效

#### Scenario: 两种模式嵌套
- **WHEN** 用户逐层打开计划节点里的探索，再打开方向里的验证计划
- **THEN** 每层展示对应关系、节点与面包屑，返回外层不丢结构。

### Requirement: 记录更新不等于执行或验收

#### Scenario: 更新状态、选项或结果
- **WHEN** 图记录被明确更新
- **THEN** 对应节点反映新内容，不自动改变无关节点或父目标；直接分配给 Agent 的节点新进入 `doing`（或在 `doing` 下改派给该 Agent）时触发单次事件唤醒推进，轮次自然结束后归于空闲，其他记录修改不自动开工。
- **AND** 完成可继续修改，界面不将记录描述为已独立验收。
- **AND** 节点保留最近一次变更说明；从完成恢复进行中时必须附返工原因，可在详情查看，不形成历史版本系统。

### Requirement: 每个拆分层级提供结构与完成情况视图

全局任务入口默认呈现聚焦「与我有关」范围的**行动焦点台**，替换原五列根看板；顶栏提供「当前行动」与「长线目标」双视角切换及「状态说明」流转图解，支持切换「按负责人」「团队全部」范围、选择归属会话快速创建私人或团队任务，并保留从群聊进入「本群任务」。点击任一具体任务卡片可打开按所处阶段呈现有效信息的详情抽屉/面板；点开任一多节点长线目标进入**北极星全景图**，保留计划依赖图、探索衍生树及多层嵌套语义。历史已保存的 `schema_version: 2` 任务图完整兼容可读可改。

#### Scenario: 默认进入「与我有关」双视角焦点台并支持并列查看「先存着」、阶段详情与范围切换
- **GIVEN** IM 中同时存在用户私人空间事项、本人牵头或直接负责的团队任务，以及他人在公开群推进的无关任务
- **WHEN** 用户在 Web 或原生 iOS 打开全局任务入口
- **THEN** 默认展示「与我有关」范围下的「当前行动」视角：顶部将「待你拍板」（本人私人空间 `proposed`、显式面向本人的团队 `proposed`、指定本人回答的 `waiting`、本人创建或父级归属本人的 `in_review`）与「先存着」（`backlog` / `paused`，支持一键「提上日程」或展开为目标图）并列切换呈现，中间主区展示「进行中」（私人空间活跃事项及团队中直接分配给本人的 `doing` / `waiting` / `todo` 节点），底部默认折叠「已完结」（`done` / `closed`）；切换至顶栏「长线目标」视角时专门展示私人或本人发起/直接负责根节点的未完结多节点目标概览（含目标自身标准状态徽章与阶段进度）
- **AND** 子任务卡片始终展示所属顶层北极星大目标与上级路径；点击任意任务卡片可打开详情面板，按任务当前状态自适应呈现提议依据与获批范围、等待原因、背景与具体要求、当前进展结果及前后置阶段（无对应内容时不堆砌空白占位文案）；本人发起的团队长线目标下由他人或其他数字员工负责的底层子任务收纳在该目标内页，无关公开群中他人的任务不进入默认焦点台；切换至「按负责人」或「团队全部」时顶栏「当前行动 / 长线目标」双视角同样一致生效，分别准确展示所选范围下的具体行动或长线目标，且桌面与手机窄屏均保留关键字搜索与新建单卡/多步目标入口
- **AND** 连续处理多张待拍板卡片时，瞬时确认反馈采用不挤动相邻待操作卡片坐标的轻量浮层；待拍板区清零时展示安静空态

#### Scenario: 桌面与手机按各自自然形态浏览北极星全景图与前沿新芽
- **GIVEN** 一个长线目标包含已完成阶段、当前推进前沿、探索试错分支以及 `proposed` 待拍板候选子节点
- **WHEN** 用户在桌面 Web、窄屏浏览器或原生 iOS 打开该长线目标
- **THEN** 视图顶部持续呈现该目标的顶层终局目标说明；用户能清晰辨认已完成阶段、当前推进前沿、探索选定方向与保留的负结果，以及尚未获批执行的待拍板新芽节点（提供批准、「先存着」与关闭入口），并可查看节点详情、负责人运行状态及新增/编辑子节点
- **AND** 桌面端支持结合脉络结构同屏查阅节点详情；手机窄屏与原生 iOS 采用适合竖屏单手阅读与点按的纵向阶段脉络呈现（前序已完成阶段可展开回看），不要求通过二维画布双指缩放平移才能完成浏览、编辑或拍板

#### Scenario: 多层子作用域逐级进入与面包屑返回
- **WHEN** 长线目标下某个阶段节点或探索分支内部继续拆分为多层子任务图，用户点击进入该子脉络
- **THEN** 界面保持顶层终局目标可见并展示当前层级的直属子结构与面包屑路径，深层后代不越层混入外层阶段；点击面包屑可逐级返回外层或焦点台且保留浏览上下文

#### Scenario: 焦点台各分区与列表视图的有界增量加载
- **WHEN** 焦点台分区、折叠的「已完结」列表、「按负责人」或「团队全部」匹配结果超出首屏批次上限
- **THEN** 首屏按有界批次返回并在用户展开或滚动接近底部时增量加载后续记录，加载中、失败重试与已到底状态可辨认且不影响其他分区已渲染卡片位置

#### Scenario: 探索与计划嵌套
- **WHEN** 用户在探索方向及其验证计划间导航
- **THEN** 仍能辨认当前选择、方向结果和相应结构关系；关闭的方向不计为成功完成，未选方向不自动变成必做工作。

### Requirement: 原生任务流程保持统一的信息与编辑体验

iOS 任务焦点台、长线目标脉络浏览、详情和创建/编辑 SHALL 以任务正文、所属顶层目标、状态和负责人为主要信息，身份审计与危险操作为次级；新建默认支持选择归属会话并零摩擦单卡起步，编辑字段 SHALL 有持续标签和随内容增长的输入区。状态和负责人 SHALL 使用具名、可关闭、带选中反馈的选择面板，负责人可搜索并区分真人与 Agent。编辑表单内的选择仅修改草稿，保存必须明确提交。

#### Scenario: 查看、编辑与离开
- **WHEN** 用户查看任务后编辑内容、选择状态或负责人并离开
- **THEN** 未提交修改不会自动保存；有修改时取消应可选择继续编辑或明确放弃，防止滑动关闭丢失草稿；保存成功回到更新后的详情。
- **AND** 保持所属会话成员资格、九种状态（含 `proposed`、`backlog` 与 `waiting`）、渐进式单卡与多层图结构、领取、删除、结果和通知契约，长内容仍可操作。

#### Scenario: 原生逐字段处理并发修改
- **WHEN** 原生编辑保存因 revision 过期失败，用户读取最新内容
- **THEN** 保留本地修改；远端独有修改纳入待保存稿，同字段不同修改具名比较并要求用户选择我的或最新；必须明确确认后才以最新 revision 保存。
- **AND** 再次冲突仍保留草稿重新比较，删除或失去权限不得覆盖或重建任务；新建子任务冲突保留输入，刷新父图后明确重试。

### Requirement: 等待信息 SHALL 与实际运行状态分别呈现

`waiting` 支持「关联跨天/定时复查安排」与「无定时器静默等待回复/决策」两类自然场景，并与负责人实时运行状态分开展示。

#### Scenario: 浏览定时复查等待与静默待人任务
- **WHEN** 用户在 Web 或原生 iOS 查看 `waiting` 任务
- **THEN** 状态徽章固定显示「等待中」，并在旁边及详情中展示等待原因；若关联了定时复查安排则同时展示下次复查时间（支持跨天及多周安排）；若指定了目标回答真人，则同时展示待决问题并在该目标用户的「待你拍板」区呈现，不要求绑定轮询闹钟
- **AND** 负责人运行、空闲或离线单独表达，有权限查看该 Agent Work 时可从运行状态直接跳往对应 Work 视图；连接或读取失败不沿用旧的运行状态。

#### Scenario: 安排失效或无法核实
- **WHEN** 用户打开关联了定时安排的 `waiting` 详情且该安排已失效或当前无法核实
- **THEN** 保留原业务等待原因，另外分别看到该定时安排已失效或暂无法核实；未关联定时器的静默等待任务不因无定时器而被标为安排失效。

#### Scenario: 用户停止或恢复
- **WHEN** 有资格用户在详情暂缓任务、设为「先存着」或明确恢复推进
- **THEN** 分别保存 `paused`、`backlog` 或 `doing` 并清除 `waiting` 关联，返回焦点台或全景后计数一致；正常消息不会自动恢复 `paused` 或 `backlog`。

### Requirement: 任务协作通知使用所属会话的一条系统消息

真实业务变化统一在任务固定所属会话表达。不引入任务专属讨论区、关注名单、重复私信或额外交接回执。消息对有资格成员可见，@ 为系统识别的有效成员提及；同一主体在一条消息中只提及一次。

| 事件 | 消息内容与重点关注对象 |
|---|---|
| 创建、首次分配、改派或取消分配 | 明确任务和变化，@ 实际涉及的原／新负责人 |
| 正文、要求、标题、结果或等待条件变化 | 明确更新内容类别，@ 当前负责人；要求更新须提示读取最新正文并给入口，不复制全部正文或只报技术版本 |
| 状态变化 | 明确九种标准状态中的新状态文案（含「待拍板」与「先存着」），@ 当前负责人；暂缓／关闭加直属下一层已分配 Agent，待确认／完成加创建者和直属父负责人 |
| 包含、依赖或替代关系变化 | 明确两端及业务含义，@ 直接受影响负责人；父级变化包括原／新直属父负责人 |
| 删除任务／子树／图 | 明确删除事实及原标识，@ 受影响原负责人及相关直属父负责人，不承诺已删除详情仍可读取 |
| 成员资格变化影响 Task 访问／处理 | 明确资格变化及受影响任务；不借通知扩大任何主体访问权限 |

#### Scenario: 改派双方获知
- **WHEN** 小王把「修复登录失败」从 A 改派给 B
- **THEN** 所属群出现一条说明从 @A 改派给 @B 的系统消息，其他有资格成员可见，不另发一份私下责任变化快照。

#### Scenario: 要求或关系更新
- **WHEN** 用户修改任务要求，或改变任务包含／依赖／替代关系
- **THEN** 消息说明具体任务发生的业务变化并 @ 需要处理的相关者；要求更新提示读最新正文，关系更新标明相关任务，不以 revision 变化代替含义。

#### Scenario: 暂缓／关闭逐层传达
- **GIVEN** 任务有 A → B → C 三层
- **WHEN** A 暂缓或关闭
- **THEN** 同一条系统消息 @ 当前负责人及 B 层已分配 Agent，不跨层主动 @ C；只有 B 的实际处理产生变化时，才继续通知下一层。
- **AND** 不自动修改 B／C 状态，不终止被通知 Agent 的无关工作。

#### Scenario: 结果向上反馈
- **WHEN** 子任务进入待确认或已完成
- **THEN** 同一条系统消息 @ 当前负责人、创建者及直属父负责人；相关者可查看结果并协调，但不因此成为系统强制验收角色，不自动修改父状态。
- **AND** 系统状态消息不能替代执行者向固定聊天实际交付成果。

#### Scenario: 成员失去任务处理资格
- **WHEN** 成员移除使 Agent 失去 Task 的访问或处理资格
- **THEN** 所属聊天保存这次变化，受影响 Agent 能获得必要的资格撤销事实并停止后续相关动作；对其不再暴露群正文、标题、成员列表或其他失权内容。
- **AND** 同群或同图不等于需要处理，通知不授予访问权；真人仍使用既有成员移除反馈，不新增任务私信。
- **AND** 已排入 Agent 上下文但尚未实际消费的失权内容须撤销，重启或消息重试不能重新注入；已经消费的历史仍按既有历史契约保留。

#### Scenario: 无业务变化与通知后的行动
- **WHEN** 读取、内部对象重建或无实际变化的提交发生
- **THEN** 不生成新的任务变化消息；真实变化的消息沿持久投递在离线后仍可消费，同一事件重试不重复保存或通知。
- **AND** 通知 `proposed`／`todo`／`backlog`／`paused`／`closed` 等状态变化不等于开工命令，且任务系统消息本身不通过聊天收件箱主动唤醒 Agent（无论负责人是人还是 Agent），仅同步被动任务上下文；真正的开工唤醒唯一由 `doing` 边沿责任事件、停止与授权边界驱动。
