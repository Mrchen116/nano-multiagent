## 现状痛点

2026-10-24 重新核对 origin/main `55376c1112ff870837a6ee65febf52e1f3686a9b`：NativeHistory 每个 nano turn/end 为该 session 新排完整导出；写出前 flush DSH，再读取所有事件，包括 fork 的继承前缀。两份 JSONL 每次都重新序列化并临时文件替换。启动按产品 bindings 重建；显式 fork 也等待导出。原始文件通过 `session.export` 提供给 ConversationHistory.distill；workspace 简化副本供人和工具读取。DSH 原生持久记录仍是恢复与 fork 的事实源。

隔离合成基线（Node 24.22.1，真实 NativeHistory + 真实临时文件，2048 条各 4096 字节工具内容，随后每轮 2 条消息及 turn/end）：初始化写 8,541,300 字节；连续 20 轮实际交给文件系统写 API 的 payload 为 171,262,920 字节、序列化 41,650 个原始事件；同时排入 20 轮为 172,492,300 字节、43,420 个事件。最终原始文件 2172 行、可读副本 82 行。具体方法与结果由 M1 evidence 留存。这些是应用写入字节，不是设备物理 I/O；旧 Air 样本不作为当前生产指标。

## 目标状态

在保证完整历史和来源保真前提下，使正常新增轮次的序列化、文件写入工作与新增事件及消息量相称；合并积压请求。连续 20 轮合成场景的增量写入量与原始事件序列化量均下降至少 95%；重启/故障时允许一次完整恢复，不引入另一份持久事实源。

## 用户侧验收标准（不变性）

### Requirement: 完整历史继续可供阅读和提炼

#### Scenario: 连续聊天后的完整副本
- **WHEN** 用户连续完成多轮聊天并读取已完成导出的 workspace 副本或请求历史导出
- **THEN** 既有文本、来源、图片占位与新增消息各出现一次；原始导出保留全部原生事件及格式头，提炼仍取得可读文件路径。

### Requirement: fork 保留继承边界且独立增长

#### Scenario: 从历史消息分支后继续聊天
- **WHEN** 用户从一条历史 assistant 消息 fork 并继续聊天
- **THEN** 分支导出包含继承到指定点的历史及分支新增内容，不包含原会话分支点后的消息，原会话保持可用。

### Requirement: 恢复不依赖派生副本

#### Scenario: 导出中断后恢复
- **WHEN** 导出失败或节点重启后继续导出
- **THEN** 从原生持久历史恢复完整副本，不重复、不遗失已持久事件；导出失败不伪报成功路径。

## 影响范围

仅 DSH integration 的派生导出策略、相关回归测试与契约说明。产品 RPC、PA 调用、事件格式与 DSH 依赖不变；无前端改动。

## 迁移与回滚策略

无需一次性迁移；启动仍从 DSH 重建绑定会话导出。旧导出保留，首次接管完整重建后才进行增量写入。回退旧版本同样完整重建；不清除任何生产历史。本次不部署。
