# perf-666: IM 热路径性能优化

## 原始诉求

> 那就按这个顺序把这三处性能问题优化掉，完成 review 后提交 PR。

用户确认的顺序：普通私聊流式 ACK 积压 → watchdog 历史规模成本 → 联系人查询。此前 review 指出逐片串行 ACK、全历史事件聚合、联系人全量装配与详情全量查；用户要求先核实真实性，再授权实施。

## 澄清记录

范围已在对话中确认，按原顺序优化并保持顺序、幂等、最终 flush、超时语义和联系人可见性。没有新 UI、生产部署、包发布或全仓性能重构要求。

## 现状痛点

基线 main `85910853ebe4a7a22c5b761029cf46da2f78cd5a`，干净工作树。静态核实：single-thread.ts 每片 text-delta 串行等 ACK，最终完成也等队列；gateway.ts 每片装配完整消息再追加全文；messaging.ts 联系人先全量装配再分页，详情也全量查。

2026-10-27 本机 Node 25.8.2 / SQLite 3.51.3 内存库，加载当前 schema，固定一条 running 消息；历史合成事件按每 100 条共享 message_id，执行原 watchdog 查询 5 次取中位数：1 万事件 0.76ms、10 万 7.82ms、50 万 42.04ms。EXPLAIN 包含 MATERIALIZE e、SCAN conversation_events、SCAN m。零 running 时该 SQLite 会跳过事件聚合。该实验隔离历史事件成本，不代表生产耗时，未声称已发生生产故障。

## 目标状态

慢 ACK 下流式传输按批次追平，不继续为每个碎片增加一次网络往返；持续输出仍渐进可见。watchdog 查找成本围绕 running 消息及其最新事件：同机合成 50 万事件、稀少活跃消息时目标查询中位数低于原查询的 20%。联系人单人读取定向完成，分页每次只装配有界候选并批量取得权限资料，不再全量装配及逐人补查。

## 用户侧验收标准（不变性）

### Requirement: 普通私聊回复保持完整且顺序正确
#### Scenario: 长回复逐步显示并完成
- **WHEN** 用户向普通私聊 Agent 请求一段较长回复
- **THEN** 文字渐进显示，最终正文完整无重复，完成状态正常收口。
#### Scenario: 群聊与显式回复维持原行为
- **WHEN** 用户在群聊中触发回复，或 Agent 已通过显式发送交付答案
- **THEN** 不额外泄漏未确认草稿或重复显示结束哨兵。

### Requirement: 聊天超时判断保持原语义
#### Scenario: 活跃和停滞回复
- **WHEN** 回复持续有活动，或回复超过现有超时时间且无新活动
- **THEN** 前者继续运行，后者显示既有失败反馈；已有正文保留。

### Requirement: 联系人搜索和访问边界不变
#### Scenario: 连续翻页与搜索
- **WHEN** 用户翻页、按类型筛选或搜索联系人并打开详情
- **THEN** 顺序和内容保持一致，静态数据下不重不漏，详情和列表相符。
#### Scenario: 不可见对象
- **WHEN** 用户查找或直接访问无资格的私人联系人或已停用的公司 Agent
- **THEN** 列表不显示，详情仍返回不可访问。

## 影响范围

packages/personal-assistant 普通 single_thread 输出；apps/im-server 流式接收、watchdog、contacts 列表和详情；相关现有测试与最小新增回归。无客户端源码变化，无 DSH 运行时改动。

## 迁移与回滚策略

数据和 API 保持兼容；新增查询索引，不转换历史记录。回滚应用代码即可恢复原路径，附加索引可保留。验证在隔离环境完成，不访问生产数据库。
