# perf-695：第二轮运行开销修复

## 来源与目标

用户要求完成三轮“独立检查 → 批量修复 → 工程验收/审查 → 合入 main”，下一轮必须从已合并主干开始，第三轮合入后复查最终主干。保持现有产品体验、权限、顺序、恢复与失败语义，控制实现复杂度。本次沿用用户仅针对这次后台优化的亲测豁免；不修改通用流程。

第二轮审计基线为第一轮 PR #448 合并后的 `9f2c73e0e40a81da05d0859719830b3a0089b6bb`。三路独立审计覆盖 IM、Node/PA/Channels、DSH 接入；主会话补查前端。修复已复现的问题，不把尚未证实的候选或理论泄漏列为结论。

## 已确认问题

| 场景 | 修复前证据 | 目标 |
|---|---|---|
| 300 会话恢复、1,000 条已完成控制 | 300,000 次旧控制解码 | 只恢复本 Agent 未交付控制，每 Agent 一次 |
| 首次确认 500 条 Task 原文 | 125,750 次解码、56.7 MB 重复 JSON | 每个凭证只重验对应原文 |
| 3,000 个外部聊天中搜索/锚点读一个聊天 | 3,001 次聊天解码 | 按 Agent/目标与来源查询 |
| 轨迹固定返回 1 条，10,000 个无关 run，30 次轮询 | 300,030 条遍历 | 单次建立关系索引，读取目标关系 |
| 无 Skill 手势，10,000 旧事件、25 步 | 25 次完整快照、250,325 次访问 | 没有手势则不读历史 |
| 配置快照每步寻找当前 turn | 25 次完整快照，只保存 1 次 | 使用公开 pre-step turn 参数 |
| 100,000 个 Work turn，返回 20 条 | 约 369 ms，并物化全部 payload | 顺序索引与惰性最新 usage 读取 |
| 100,000 附件、8 MiB/128 块上传 | 每次 256 次聚合，约 635–648 ms 聚合耗时 | 单写者派生合计，维持逐块并发预留 |
| 500,000 个历史事件、浏览器已在最新游标 | 约 13.6 ms 扫描旧时间前缀 | 已可判定的分支短路，时间索引服务其余查询 |
| 同聊天 100 条分类失败候选 | 初始与重连各 100 次查询 | 仅保留仍有效的最新候选 |

上传失败回归另外复现了文件异步 open 尚未完成即返回、清理目录后出现 ENOENT；修复释放边界，失败返回前等待文件关闭。

所有规模与时间来自隔离合成数据、真实方法/处理器调用，不代表生产数据规模或生产时延。未访问生产、未发真实模型请求；没有确认额外资源泄漏。Heartbeat 重复 ensure 的恢复语义尚未证明可删，继续保留。

## 成功标准

历史查询与模型可见内容保持一致；容量、并发、失败清理、恢复、权限及分页相关回归通过；独立 code/context review 与适用 CI 通过后合入 main，再启动第三轮。
