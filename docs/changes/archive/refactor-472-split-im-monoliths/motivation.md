# refactor-472: 拆分 IM 持久化与 Gateway 巨石模块

## Relations

- 无

  Agent 解读: 两个巨石模块均为本 unit 的必交付范围；实施时可分阶段推进，但不能只完成其中一个便关闭本 unit。

## 现状痛点

`src/IM/infra/repositories.py` 集中承载用户、策略、会话、消息、事件、Agent profile、节点、绑定和用量等多个持久化领域。它同时包含跨表读模型、消息写事务、事件写入、数据编解码和公共时间处理。不同变化原因被压在同一文件中，使局部修改需要理解远超目标领域的代码，并让事务边界与普通辅助逻辑难以一眼区分。

`src/IM/ws/gateway_handler.py` 同时承担 Gateway WebSocket 生命周期、注册与鉴权、连接替换、节点状态、下行推送、请求—响应关联、Channel 控制、relay 回执与群扇出、执行事件入库、Agent 间消息派发和协议字段解析。连接身份、并发状态与多类业务流程聚集在单个类中，主路径被大量互不相同的职责淹没，修改任一协议能力都容易误触其他状态机。

这两个文件已成为 IM 后端的集中变更热点。继续在其中叠加功能，会扩大代码审查范围、增加并行开发冲突，并让维护者难以判断一项改动应由哪个边界负责。仅把函数机械搬到更多文件也不能解决问题；如果事务、连接状态或请求关联的所有权被拆散，代码虽然变短，架构反而会更难理解、更容易出现行为回归。

## 目标状态

两个巨石模块均被拆除，IM 后端按稳定职责边界组织：持久化代码按领域与事务所有权归位，Gateway WebSocket 代码按连接生命周期、请求关联和独立业务流程归位。每个目标模块都有单一、清晰的变化原因，主要调用路径能从入口直接追踪到负责该行为的实现，不依赖通用转发层或隐式 service locator 才能理解。

拆分后的结构必须保住现有原子性和状态所有权：一次业务写入中不可分割的消息、事件和会话投影仍共同提交；连接注册、身份校验、连接替换与断连清理仍由同一状态所有者协调；请求等待与结果解除仍成对管理。具体模块、接口和迁移次序由 `design.md` 决定。

本 unit 完成时，两处目标均已迁移。所有生产装配、内部引用、测试引用和架构约束均指向最终结构；不为减少引用改动而强制保留旧文件。若旧入口没有明确边界价值，应删除；若保留，则只能作为有清晰公共职责的轻量入口，不能继续承载实现并重新长成巨石。

## 用户侧验收标准（不变性）

本次不增加新的产品能力。终端用户继续通过 Web IM 使用账号、会话、消息、Agent 和节点管理；Node Gateway 继续通过同一连接完成注册、状态上报、消息中继、配置与控制请求。重构后的可观察行为按以下回归基线保持。

### Requirement: 账号、租户与持久化数据行为保持稳定

#### Scenario: 用户登录后访问自己的 IM 数据
- **GIVEN** 两个用户各自拥有会话、Agent、节点和用量数据
- **WHEN** 任一用户登录并访问账号、会话、消息、Agent、节点、策略和用量相关页面
- **THEN** 页面正常返回该用户有权访问的数据，不能读取或修改另一用户的数据

#### Scenario: 用户刷新后继续看到完整会话历史
- **GIVEN** 用户已有包含普通消息、Agent 回复、工具过程和投递状态的会话
- **WHEN** 用户刷新页面并重新进入该会话
- **THEN** 消息顺序、内容、附件、发送者、过程信息和终态保持完整，不出现丢失、重复或错误的会话摘要

#### Scenario: 用户管理会话、Agent 与节点
- **WHEN** 用户创建或管理会话成员、修改 Agent 配置、创建 Agent、绑定节点或查看节点状态
- **THEN** 操作结果、权限边界、冲突提示、离线提示和刷新后的持久化结果均保持有效

### Requirement: Gateway 实时连接与消息中继行为保持稳定

#### Scenario: Gateway 注册后维持实时双向连接
- **GIVEN** 用户的 Gateway 已使用有效身份连接 IM
- **WHEN** Gateway 注册、持续心跳并与 IM 交换受支持的消息
- **THEN** 节点和 Agent 在线状态正确显示，连接可持续承载上行报告与下行请求

#### Scenario: Web IM 消息经 Gateway 获得实时回复
- **GIVEN** 用户的 Gateway 与目标 Agent 在线
- **WHEN** 用户在 Web IM 发送消息并等待 Agent 回复
- **THEN** 消息只被中继和处理一次，回复正文、流式过程、工具状态、权限状态及最终投递状态实时出现，刷新后与实时显示一致

#### Scenario: Gateway 重连或旧连接迟到断开
- **GIVEN** 同一节点建立了替代旧连接的新连接
- **WHEN** 旧连接随后结束或发送失败
- **THEN** 新连接仍保持可用，节点不会被旧连接的迟到清理错误标记为离线

#### Scenario: 非法或不支持的 Gateway 消息
- **WHEN** Gateway 发送非法消息或不支持的消息类型
- **THEN** Gateway 得到明确错误反馈，IM 服务不崩溃，其他已建立连接和用户会话不受影响

### Requirement: Gateway 配置控制与后台事件行为保持稳定

#### Scenario: 在线节点响应配置与控制操作
- **GIVEN** 目标节点在线
- **WHEN** 用户读取或修改 Agent 配置、创建 Agent、预览提示词、管理 heartbeat/cron、查看 skill 使用情况或管理外部 Channel
- **THEN** 操作通过当前在线节点得到对应结果，页面展示的成功、失败、超时和状态收敛语义保持有效

#### Scenario: 外部 Channel 与后台事件实时回流
- **WHEN** 外部 Channel 消息、群聊回复、后台 Agent 通知或执行过程事件到达 IM
- **THEN** 目标会话和在线浏览器及时显示对应内容，同一事件重试不产生重复气泡，其他租户收不到该事件

#### Scenario: Gateway 或目标节点离线
- **WHEN** 用户触发一项依赖在线 Gateway 的操作，而 Gateway 或目标节点不可用
- **THEN** 用户得到对应的离线、等待应用、空结果或失败反馈；IM 的账号、配置中心和历史浏览仍可继续使用

## 影响范围

- 直接目标：`src/IM/infra/repositories.py` 和 `src/IM/ws/gateway_handler.py` 中的全部职责。
- 必要联动：两个目标的生产装配点、API 与应用服务引用、Gateway 持久化协作者、WebSocket 路由、测试引用及架构契约。
- 数据影响：不改变数据库 schema，不要求用户迁移或重建既有数据；原有消息、事件、会话、Agent、节点、绑定、策略和用量数据继续可读写。
- 协议影响：不改变面向浏览器和 Node Gateway 的 HTTP、WebSocket、错误与事件语义。

非目标：

- 不新增或删除 IM、Gateway、Agent 或外部 Channel 的产品能力。
- 不借机重写 `db.py`、application services、API routes、`user_stream.py` 或其他相邻模块；仅在适配最终边界时做必要改动。
- 不改变数据库表结构、跨租户权限规则、消息投递语义、配置语义或前端交互。
- 不以“每个类一个文件”“每种消息一个 handler”或单纯限制行数作为成功标准；目标是清晰的职责和状态所有权，而非把巨石机械切碎。

## 迁移与回滚策略

实施必须分成可独立验证的小步，先完成持久化巨石拆分，再完成 Gateway handler 巨石拆分；每个阶段迁移对应实现、引用和测试后立即运行最窄回归，再进入下一阶段。两个目标都完成且完整非 e2e 测试树通过后，本 unit 才能收口。

迁移期间不得同时维护两套可独立演进的实现。若使用临时兼容入口，它只能短期转发到唯一实现，并应在最终阶段依据引用和边界价值决定删除或收敛；所有最终引用必须一致。每一步若出现用户行为、协议、持久化原子性或连接状态回归，应回退该步，而不是用兼容分支或静默降级掩盖问题。

数据库 schema 和持久化数据不迁移，因此代码回滚不依赖数据回滚。最终回滚单位以各个已验证的小步为准，确保任一阶段都可恢复到上一份通过测试的结构。
