## 1. 文档迁移有明确的授权边界

### 真实问题

早期整理过程中，Agent 为了让流程文档更“完整”，加入了原仓库并未强制的 spec review。用户随即指出：

> “我没改这个流程，你不要改。你只做文档整理，因文档整理而导致的相关修改当然可以改，但是这种把原本流程都改了就不要了。”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-27T10:38:19Z

后来全仓审计又发现许多 code、test、skill、active change 与文档之间的漂移。用户没有授权 Agent 顺手选择哪一方胜出，而是要求：

> “有一些漂移如果不是我期望的，我希望提issue后面解决掉。所以漂移的东西，你先用临时文件记录下来，我审核是否符合我期望。”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-30T06:24:29Z

### 通用机制

文档迁移天然会暴露语义冲突，也会诱使实施者为了“新体系自洽”而顺手统一政策。目录整理、引用迁移、事实纠错和政策重设计需要不同授权。

一套安全的迁移应先声明：

- 哪些行为、流程和产品语义保持不变；
- 哪些路径和结构允许调整；
- 哪些漂移可以由现有权威直接裁决；
- 哪些差异需要 owner 决定；
- 语义修改如何与机械移动分开审阅。

无法直接裁决的内容进入临时 drift queue。每项只记录现状、证据、影响、候选处理和 owner 决定。裁决结果可以是修文档、改代码、建 issue 或确认维持现状。queue 在全部裁决后删除或冻结，不能变成新的永久 backlog。

### 原文覆盖与缺口

原文在自动 Docs Agent 段落已经说它“不应自行发明新的权威或改变产品语义”，但这个警告出现得较晚，也容易被理解为只约束自动化清理机器人。真实迁移说明，它应成为所有文档迁移的首要安全边界。

### 建议写法

在“从已有仓库迁移”的步骤表之前增加一个短段落：

```text
先声明迁移不变量和授权范围
→ 将路径移动、结构调整和语义修改分开
→ 可由现有权威裁决的 drift 直接修正
→ 其余 drift 留证并交给 owner 决定
→ 再继续迁移与验证
```

这项建议值得写回原文，优先级最高。

## 2. 外部化知识前先做“增量信息测试”

### 真实问题一：文件清单式 index

迁移中先后创建了 active unit 表、research snapshot 清单等人工索引。用户的判断很直接：

> “docs/changes/README.md有## 活动区索引这个合理吗，我觉得这带来了额外无意义的文档维护。不符合我们的文章的精神吧”
>
> “压根没带来增量信息”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-30T13:03:25Z 至 13:03:50Z

在 research 目录中又出现同类问题：

> “这次重构文档体系，还有没有类似的问题，对于频繁更新的文档非要维护一个index这种愚蠢的做法”
>
> — `019fb322-eca1-71e2-a2fb-cc316a057f04`，2026-07-30T14:51:40Z

文件系统已经能回答“有哪些文件”。人工再抄一遍文件名，只增加一个会漏更新的副本。

### 真实问题二：重复的 `status.md`

为了跨 session 恢复，迁移一度给 active unit 增加 `status.md`。用户连续追问它从哪里来、何时更新，最后指出：

> “我觉得没必要吧，本身每个阶段完成，对应的文档都能看出来。”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-30T13:11:57Z

最终冷启动恢复没有依赖这份状态副本，而是读取首文档、design、milestone progress、验收报告，以及 Git、PR、worktree、进程和日志的实时状态。`status.md` 被删除。

但这不表示所有状态都不应持久化。code-review finding、轮次、未决决定或非显然暂停原因如果只存在于 Agent 内存，其他 durable artifact 和实时系统都无法恢复，就必须写入已有的阶段产物或专门证据文件。

### 通用判据

新建 index、catalog、status 或 summary 前，先问：

> 它是否保存了源目录、阶段产物、Git / PR / CI 或 runtime 无法直接给出的信息？

可用下面的区分：

| 产物 | 有增量信息 | 无增量信息 |
|---|---|---|
| index | 用途、读取时机、状态、权威、跨目录关系 | 抄一遍同目录文件名 |
| active work 索引 | 跨目录冲突、owner、无法从目录得知的状态 | 手工复制 active 目录 |
| status | 决定、非显然暂停原因、下一步、验证边界 | 重复“哪些阶段文件已存在” |
| count | 影响理解或导航，并由唯一源生成/校验 | 手工维护一个无实际用途的数字 |
| summary | 显著压缩跨多个来源的恢复成本 | 改写某个唯一来源的同一段内容 |

### 原文覆盖与缺口

原文已经写了“每增加一层索引，都应该证明它降低了定位成本”，也要求长任务保存可恢复状态。两条原则单独看都正确，但实施者很容易据此同时创建“每层 README”和“每个 unit 一份 status.md”。

值得补充的核心是：外部化不自动产生价值。应该保存不可推导的信息，可推导内容直接查询或生成。

### 建议落点

- 在“第二层是仓库地图”末尾增加“稳定语义地图与波动目录镜像”的反例。
- 在长任务恢复表之后增加一句：`durable state` 不等于固定创建 `status.md`，优先组合已有阶段产物和实时事实恢复。
- 在“可以生成的内容不要人工双写”中增加动态计数例子。

这项建议值得写回原文，优先级最高。

## 3. 机械保证必须逐层说清

### 真实问题

关键路径 E2E 文档写着清单与测试漂移时“门禁不过”，实际测试只检查了另一项 model catalog 行为。用户最初只看到计数错误，继续追问后发现真正问题是文档高估了机械保护：

> “等下，CI虽然没强制要求e2e测试，但是这13条e2e测试不存在？？是这个意思？”
>
> — `019fb322-eca1-71e2-a2fb-cc316a057f04`，2026-07-30T13:36:16Z

这件事至少包含四层不同事实：

1. catalog 中写了一个测试或用户旅程；
2. 对应测试符号真实存在并可被测试框架收集；
3. CI 或指定命令实际运行它；
4. 测试语义真正覆盖文档声称的用户旅程。

前几层可以机械检查，最后一层通常仍需要代码审查、真实 E2E 或任务级评测。文档只能声称已经实现的那一层，不能用“contract tests 会兜底”同时替代存在性、执行性和语义覆盖。

### 验证结论还绑定代码基线

同一轮迁移还发现，reviewer、verifier 和 code review 在旧 integration head 上通过后，如果 rebase 新 main，原结论不一定自动适用于最终 head。用户专门要求分析：

> “main rebase 后原门禁是否仍有效 你怎么分析”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-30T16:53:48Z

Git 没有冲突只能说明文本可以合并。main 的新增变化可能触及本 unit 的依赖、调用链、schema、用户旅程或测试假设。

因此，验证证据应保留：

- 它实际验证的 commit 或 tree；
- 后续基线发生了什么变化；
- 为什么原结论仍可 retained；
- 哪些受影响门禁需要局部或完整重跑。

旧报告的验证位置不能被改写成新 HEAD。验证结论是带适用范围的 evidence。

### 原文覆盖与缺口

原文已经把静态检查和真实任务评测分开，也说“文档写着必须、实际仍可绕过”表示机械执行不足。缺少的是机械承诺的精确粒度，以及验证 evidence 与最终代码基线的关系。

### 建议写法

在“验证这套体系是否真的有效”的自动检查表后增加两个短判据：

1. 文档中的每个机械承诺要对应真实检查层级：存在、可收集、实际运行、语义覆盖；
2. 每次验证结论都对应一个代码基线；merge、rebase 或最终修改后按影响范围 retained、局部复验或完整复验。

两点适合写在同一段，不必新增顶层章节。

## 4. 对强 Agent 使用最小充分契约

### 真实问题

迁移在修复并行 reviewer / verifier 竞态和 corrected-delta 对账时，一度加入专门 SHA、状态协议、固定报告段和 orchestrator 集中提交。用户反复要求简化：

> “其实agent的应变能力很强的，你简单点说，他能解决的。”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-30T15:35:57Z

> “为什么搞SHA，哪里来的思想？”
>
> “删掉！画蛇添足，没必要”
>
> — `019fb322-eca1-71e2-a2fb-cc316a057f04`，2026-07-30T16:21:12Z 至 16:22:38Z

但当流程被压缩为“其余按该 skill 的输入契约派发”时，用户又指出：

> “这里他知道‘该skill 的输入契约派发。’是啥吗”
>
> — `019fb322-eca1-71e2-a2fb-cc316a057f04`，2026-07-30T16:45:42Z

这组反馈划出了很清楚的边界。少写不等于省略跨角色接口，写全也不等于规定 Agent 的每一步局部手法。

### 通用原则

可概括为：

> 结果明确，手法自治。

跨角色、跨 worktree 或跨 session 的契约应明确：

- 当前 mode 和目标；
- 权威输入在哪里；
- 需要交付什么产物；
- 通过、失败和无法判断分别意味着什么；
- 谁负责接手和最终闭环；
- 何时必须升级或请求人类决策。

角色内部如何搜索、fetch、rebase、重试、组织临时文件和处理普通冲突，由强 Agent 自主决定。只有高后果不变量、反复出现的失败或不可逆操作才需要更细的控制。

这个原则同时防止两种错误：

- 用“Agent 很聪明”掩盖不存在的接口；
- 用“必须可恢复”给每一步增加 SHA、字段、schema 和重复报告。

### 原文覆盖与缺口

原文已经讨论根级指令与 skill / workflow 的分工，也引用研究说明更多指令可能只增加动作和成本。它尚未正面回答流程文档应该细到什么程度。

### 建议落点

在根级指令的 skill / workflow 分流之后，或“约束放进与其强度匹配的位置”附近增加一段“最小充分契约”。这是一条普适性很强的新原则，值得写回原文。

## 5. 流程顺序可以变化，闭环必须完成

### 真实问题

原文生命周期图天然从 current 进入 change proposal，再进入实施和 promotion。真实开发还有另一种常见入口：

> “docs/development/change-workflow.md 还有一种情况，是开发者vibe coding，用户一边说，agent一边改，改完之后再补unit的spec，design等文档。”
>
> “这叫快速开发模式”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-30T12:41:10Z 至 12:41:43Z

在这种模式中，用户通过连续体验和反馈完成部分产品验收，交付前再补 as-built spec/design、code review、current promotion 和历史记录。

### 通用机制

Agent-Native 变更可以有不同形成顺序：

- 高风险、多人协作或边界复杂的工作适合 spec/design-first；
- 边界清楚的 bug 可以走更轻的记录路径；
- 高频人机互动可能先形成实现，再补真实的 as-built 记录。

通用不变量是：

- 最终用户意图、范围和实际设计可追溯；
- review 与验证强度和真实风险相称；
- current 文档只在行为真正生效后归并；
- 过程和证据如实记录；
- 没有发生过的 milestone、review 和决策不能事后伪造。

具体是否需要 verifier、产品 reviewer 或用户再次确认，属于项目风险政策。文章不应把 nano-multiagent 的 gate 组合写成通用答案。

### 原文覆盖与缺口

原文当前只展示一条顺序固定的生命周期。它准确描述了知识闭环，但容易让读者把顺序当成唯一合法流程。

### 建议落点

在“把文档更新嵌入开发过程”的四个关键时刻之前增加一句：

> 这些阶段描述知识职责，不要求每次变更都以同样顺序形成；实施可以先发生，但交付前必须完成真实的验证、current promotion 和历史留存。

建议再给 docs-first 和 as-built 两条短路径，不需要扩写 nano 的具体 change 角色。

## 6. 兼容入口需要退出条件

### 真实问题

迁移过程中，旧路径一度被保留为 compatibility stub。用户指出迁移已经可以一步到位：

> “docs/IM前端蓝图.md，docs/需求.md 这些等等的旧文档，后续也不消费了的，都删了吧，不要留兼容入口了”
>
> — `019fa2f5-2fc5-76e0-890c-8ccc657b4935`，2026-07-30T16:33:34Z

旧入口即使只剩一行跳转，也会继续出现在 Agent 搜索结果中。它延长了双路径共存期，并让后续维护者误以为旧位置仍是稳定接口。

### 通用判据

保留 redirect 或兼容文件至少需要一个明确理由：

- 存在无法同步迁移的 live consumer；
- 对外暴露了稳定 URL 或路径；
- 有外部仓库、自动化或发布物依赖旧入口；
- 已定义过渡窗口和删除条件。

所有 live consumer 都已更新，Git 已保存历史，旧入口没有公共兼容责任时，直接删除通常更清楚。

兼容入口如果必须保留，应写明：

- 新权威位置；
- 保留原因；
- 仍存在的消费者；
- 删除条件或复审日期。

### 原文覆盖与缺口

原文同时提到 redirect、归档和删除，但没有给出选择标准。真实迁移说明，默认保留兼容入口也会制造知识噪声。

### 建议落点

在“从已有仓库迁移”的退役步骤中加入这组保留条件和退出条件。值得写回原文。

## 7. 只需加强，不必单独扩成新理论

### live consumer audit 要超出 Markdown

迁移实际发现旧术语和旧链接还存在于：

- code comment；
- test 文件名和模块说明；
- skill；
- script 提示与错误信息；
- paused active change；
- CI 和配置。

这些内容都会成为 Agent 搜索和判断的上下文。迁移审计不应只搜索 `.md`。这项内容适合在迁移 checklist 中补一行。

### 动态信息有价值时应生成或校验

用户并非反对所有计数。某个 spec index 的 Requirement 数量确实有导航价值，问题是它容易漏更新。适合写入原文的判断是：

- 无价值的动态摘要删除；
- 有价值的计数从唯一源生成；
- 暂时不能生成时，做窄而客观的结构检查。

这可以作为“可以生成的内容不要人工双写”的例子。

### runbook 应暴露当前证据入口

一次历史请求成功只说明某个时间点发生过什么，不能证明 model id、配置和服务现在仍可用。runbook 更有价值的内容是当前配置路径、健康检查、真实请求方法和日志入口。历史成功结果属于 Evidence 或 snapshot。

这项原则原文已有足够理论，只需要加入一个 operational 例子。
