## 3. 从原话归纳出的稳定思维模式

本节是分析，不是用户原话。每条均回指上面的证据。

### 3.1 先把“研究课题”对齐，再允许继续搜

稳定模式：

1. 从一个具体痛点出发，但不急于把痛点本身当课题。
2. 先把研究对象、时代背景、最终用途和排除项说清。
3. 一旦发现 Agent 连课题都没搞清楚，立即停下对齐，而不是让它继续堆材料。
4. 课题对齐后再授权深挖，并要求重要内容和链接同步记录。

证据：RW-001、RW-002、RW-007 至 RW-011。

这里的“对齐”不是礼貌性复述，而是一道真实的研究闸门。用户会检查：

- 是只改当前仓库，还是产出所有仓库可复用的方法？
- 是研究某个工具怎么写指令，还是研究 Agent 编码时代形成的文章与实践？
- 是传统文档管理的一般问题，还是 Agent-Native 生产方式下的新问题？

### 3.2 从具体案例提炼可迁移方法，但不能脱离具体证据

用户要的不是一份只对 nano-multiagent 有效的整改方案，而是：

`具体仓库问题 → 外部实践与一手材料 → 可复用方法论 → 回到具体仓库验证`

这不是单向抽象。研究成果还要回到实际案例、参考项目或真实运行中验证：

- 用 nano-multiagent 作为实例模板，但文章本身面向公共读者（RW-066、RW-067）。
- 从 Better Harness 的“反向检查流程”反推它隐含的“正向好 Harness 标准”，再实际运行一次审查（RW-031 至 RW-035）。
- 新研究结果先进入研究笔记，再归并进最终文章（RW-030、RW-041）。

### 3.3 资料不是越多越好；每类资料承担不同任务

从原话可以还原出一套资料选择逻辑：

| 资料类型 | 用户期待它回答什么 | 证据 |
|---|---|---|
| 官方文档 / 官方文章 | 产品机制、加载行为、边界等事实 | RW-006、RW-021 至 RW-023 |
| 社区文章与实践 | Agent 时代正在形成的仓库组织方法 | RW-007、RW-009 |
| 代表性开源项目 | 一套理论如何通过流程、规则和模型文件落地 | RW-031 至 RW-033、RW-041 |
| 实际运行结果 | 参考项目声称的流程在真实项目上如何表现 | RW-034、RW-035 |
| 论文或实验研究 | 支持一个窄而明确的经验命题 | RW-036、RW-038、RW-039 |
| 用户已有调研材料 | 扩展候选信息和线索，供重新核验与综合 | RW-012 |
| 当前仓库 | 作为问题现场、实例和落地验证场，而不是文章读者默认知道的背景 | RW-001、RW-066、RW-067 |

高频判断不是“这个来源权威吗”这么粗，而是：

1. 这个来源实际支持什么结论？
2. 它支持的是事实、经验观察，还是作者自己的综合框架？
3. 它的适用范围有多窄？
4. 这项证据在文章中应该出现在哪一层？

### 3.4 严格限制证据外推

最清楚的例子是 repository context file 研究。用户并不满足于“有两篇论文，所以文章更可信”，而是连续追问：

- 两项研究到底论证什么（RW-038）；
- 它们显然只涉及根级 `AGENTS.md` / `CLAUDE.md`（RW-039）；
- 因此不能拿它们支撑宏观 WHY。

由此可归纳出证据边界规则：

> 引用的位置由它能证明的最窄命题决定，不由它看起来多“学术”或多有说服力决定。

同理，“五个逻辑平面”“七个问题”“唯一事实来源按问题拆开”等框架一旦出现，用户会立即追问“从哪里来的”（RW-050、RW-060、RW-061）。如果它是 Agent 综合出来的，就必须明说推导过程，不能伪装成外部共识。

### 3.5 第一性原理在写作中的含义：每个设计都要接回问题和价值

用户明确把下面的结构称为“第一性原理思考”（RW-019、RW-020）：

1. 前文已经明确需要哪些文档。
2. 下一问是 Agent 怎样找到并消费这些文档。
3. 根据 Agent 的探索特点设计组织方式。
4. Agent 能用之后，再处理更新与腐败问题。

因此“第一性原理”在这里不是抽象口号，而是写作中的因果链：

`需求 / 问题 → 行为或约束 → 设计选择 → 产生的价值 → 后续生命周期问题`

这也是用户反感“上来列一堆三级标题”的原因：标题只是分类，不能替代推理。

### 3.6 文章结构由核心论证推进，不由搜到的材料分章

用户给出 WHY、WHAT、HOW、最佳实践作为这篇文章的主骨架（RW-014），但更稳定的偏好不是机械复用这四个英文标题，而是：

- 先解释为什么需要不同体系；
- 再定义管理对象和关键概念；
- 再从 Agent 的消费方式推到组织、更新和治理方式；
- 最后给出可落地实践。

新材料应放进既有论证链，而不是每发现一个概念就新开同级章节。RW-065 还展示了更细的顺序要求：理论和边界在前，常见长期文档作为推导后的总结在后。

### 3.7 用“三句话测试”暴露一段话真正的主张

RW-036 中，用户把完整段落贴出，要求“三句话内”解释它想表达什么。得到清楚解释后，用户指出原文完全没表达出来（RW-037）。

这是一种很有效的诊断方法：

1. 先暂时不改句子。
2. 用极少句子说出该段唯一核心命题及因果关系。
3. 比较“作者以为自己写了什么”和“读者实际读到了什么”。
4. 若两者不同，重写整段，而不是局部润色。

### 3.8 逐段审阅时连续追问四件事

从 RW-048 至 RW-065 可以抽出稳定的逐段审阅问题：

1. **概念是什么？**  
   “知识角色是啥”“生命周期和内容类型是两个维度想表达啥”。
2. **从哪里来？**  
   “五个逻辑平面从哪里学来”“长期文档内容哪里来”“七个问题哪里来”。
3. **它与相邻内容有什么区别？**  
   两张权威来源表是否在重复。
4. **它为什么出现在这里？**  
   长期文档清单应是前面理论推导后的 WHAT 总结；根级 context 论文不应放在宏观 WHY。

这四问比泛泛要求“写得更清晰”更可操作。

### 3.9 信息增量高于篇幅和“完整感”

用户多次删除三类低增量内容：

- 人人都知道的常识（RW-016、RW-017、RW-037）。
- 为一个没人持有的误解写的防御性反驳（RW-040、RW-052、RW-056）。
- 与邻近表格或段落表达同一信息的重复结构（RW-063）。

用户对文章长度没有预设偏好；RW-014 明确说“文字数量不是关键”。判断标准是：

- 是否推进核心论证；
- 是否带来新边界、新机制或新决策；
- 是否让读者更容易理解或检查；
- 是否只是为了看起来周全而写。

### 3.10 反感“先树一个没人相信的靶子，再说不是”

用户连续纠正如下表达：

- “Agent 时代真正被放大的不是文档数量太多……”
- “不要求物理上创建五个同名目录。”
- “这张表描述的是能力，不是要求每个仓库预先创建所有目录。”

问题不在“不是”这个字本身，而在于作者虚构了一个读者并未持有的误解，再花篇幅反驳它。可操作的改法是直接陈述真正主张、适用边界和因果机制。

### 3.11 抽象词必须能让读者立刻建立具体指代

“制品”“知识角色”“canonical owner”等词都会触发追问（RW-018、RW-049、RW-070）。用户更喜欢：

- 常用词；
- 第一次出现时就给出具体含义；
- 直接说来源支持的结论，而不是“回答的问题”这类二次抽象（RW-052）；
- 标题内的概念应语义同类，不能把“调研”和“联调”仅因都像入口就并在一起（RW-071）。

### 3.12 案例必须对公共读者自足

文章既“给自己看，也给别人看”（RW-013），因此：

- 不用个人整改故事开场（RW-014）。
- 可以用 nano-multiagent 做明确标注的实例模板（RW-066）。
- 不能写“当前内容”并假定外部读者知道指的是哪个仓库、哪个版本（RW-067）。

这里不是排斥个人经验，而是要求区分“论点正文”和“被介绍清楚的案例”。

### 3.13 图和表必须承担推理工作

用户接受并认可 Mermaid 图，是因为它把三层关系压缩为：

`仓库知识体系管理什么 → Repository Harness 支持什么 → Agent 得到什么工作结果`

随后又要求：

- 调整为合适宽高比，避免“超级大长条”（RW-043、RW-044）。
- 图旁必须有逻辑表述，不能只插图（RW-045）。
- 术语要与来源一致，不能遗漏“经验沉淀”等关键项（RW-046）。
- 图中的每项能力仍需文字解释（RW-047）。
- 生成图片不能只“看起来专业”，必须把复杂论证压缩成可检查的视觉结构（RW-068、RW-069）。

这意味着“一图胜千言”不是减少文字，而是让关系可见、可核对、可回到正文解释。

### 3.14 研究笔记与最终文章分层

RW-011 和 RW-030 明确形成两层：

- `docs/research/agent-era-repository-knowledge-system.md`：边研究边记的重要材料、链接、来源、推导过程和中间判断。
- `Agent-Native 代码仓文档体系.md`：给自己和别人看的最终结论沉淀。

新研究不是直接堆进文章，而是先进入研究层，经过筛选、核验和结构重组后，再更新最终结论。

### 3.15 排版服务于语义，不接受机械硬换行

这项偏好跨文章和仓库文档反复出现（RW-024、RW-073、RW-074）：

- 连续语义的一句话不要按固定列宽硬折行。
- 段落、列表、标题之间可以按结构换行。
- 同一份读者文档的语言保持一致（RW-035、RW-072）。

但 RW-075 又划出一个重要边界：不要因为某个 Agent 反复犯机械换行错误，就把“禁止机械换行”写成面向所有模型的仓库永久规则。更合适的落点是个性化写作 skill 或当次生成约束。

### 3.16 研究项目时沿真实执行链下钻，并审查证据上限

ChatGPT 的 Better Harness 会话补足了一条非常稳定的研究路径（RW-081 至 RW-084）：

```text
项目什么时候用
→ 它检查一次任务还是整个仓库
→ 代码和运行时如何触发
→ 分析对象和数据契约具体长什么样
→ 这些字段到底足以支持什么结论
```

用户不接受只讲模块职责或步骤名称。当文字概述难以建立模型时，会要求一个完整但最小的数据样例；看到输入信息量不足时，会继续追问分析者凭什么得出更深结论。

这项模式意味着，研究一个工具或项目时要区分：

- 项目宣传的目标；
- 静态代码和配置提供的能力；
- 运行时实际产生的输入；
- 单个分析者能直接观察的内容；
- 主系统跨多路证据综合后才能得到的判断。

“配置存在”不能自动证明“行为发生”，“字段缺失”通常也只能记为未知。只有把证据路径还原出来，才能评价项目真实能力及其上限。

## 4. 高频触发条件、失败模式与可操作修正

| 触发信号 | 用户识别出的失败模式 | 应采取的动作 | 主要证据 |
|---|---|---|---|
| Agent 开始大量搜索，但用户觉得“课题没搞清楚” | 研究对象、时代语境或最终用途错位 | 立刻停搜；用一句话重述研究问题、排除项和产物；得到确认再继续 | RW-007 至 RW-011 |
| 只围绕当前文件或仓库给整改建议 | 把局部实施当成研究结论 | 抽象成可复用问题；外部研究后再回到仓库验证 | RW-002、RW-008 |
| 研究某工具的指令细节 | 把工具说明当成时代实践 | 转向官方文章、社区实践和代表性项目的设计思想 | RW-006、RW-007、RW-009 |
| 看一个检查工具时照抄它的检查流程 | 学到“怎么检查”，没学到“什么是好” | 先解释其流程，再从每个检查动作反推出质量要求及证据 | RW-031 至 RW-033 |
| 研究项目时只讲组件和步骤名称 | 没有还原触发范围、运行时对象和证据上限 | 沿触发 → 作用域 → 代码/运行时 → 完整输入 → 可支持结论逐层下钻 | RW-081 至 RW-084 |
| 引用了论文或实验，但说不清作用 | 用“有研究”替代论证 | 逐条写明来源支持的最窄结论、限制和适合章节 | RW-036、RW-038、RW-039 |
| 出现“五个平面”“七个问题”等整齐框架 | Agent 综合被伪装成外部共识 | 给出处；若无直接出处，明确标为综合，并展示推导来源 | RW-050、RW-060、RW-061 |
| HOW 下堆出许多平级标题 | 分类清单替代因果推理 | 重排为问题 → Agent 特性 → 设计 → 更新与防腐败 | RW-019、RW-020 |
| 一段很长但读者说不出它表达什么 | 核心主张被材料和修辞淹没 | 先做“三句话测试”，再围绕唯一主张重写 | RW-036、RW-037 |
| 章节在反驳显而易见的误解 | 稻草人式“不是……而是……” | 删除虚构对照，直接写主张、机制和边界 | RW-040、RW-052、RW-056 |
| 章节读完只能得到常识 | 没有信息增量 | 删除，或补充真正有争议的边界、机制和取舍 | RW-016、RW-017、RW-037、RW-057 |
| 术语“很飘”或标题把不同概念并在一起 | 抽象词没有具体指代 | 换常用词；首次出现就定义；按语义重新分组 | RW-018、RW-049、RW-070、RW-071 |
| 两个表格都像在讲同一件事 | 结构重复制造虚假完整性 | 先写每张表独有的问题；无独有信息就合并或删除 | RW-063 |
| 理论、清单和案例顺序混乱 | 结论先于推导，读者不知道为何成立 | 先讲判据与边界，再总结常见类别，最后给明确引入的实例 | RW-065 至 RW-067 |
| 加图后正文没有改变 | 图是装饰，未进入论证 | 在正文解释图的层级、节点和因果；让图能被逐项检查 | RW-042、RW-045 至 RW-047 |
| 图片看起来专业但信息量低 | 视觉风格替代信息结构 | 删除或重做；只保留能压缩复杂关系的图 | RW-068、RW-069 |
| 图纵向过长 | 信息虽有，但扫描成本高 | 调整子图内部方向和整体纵横比 | RW-043、RW-044 |
| 文档按固定列宽硬折行 | 阅读被无意义断裂干扰 | 只按语义结构换行，不机械 wrap prose | RW-024、RW-073、RW-074 |
| 为纠正单个 Agent 的问题增加仓库规则 | 把模型特有失误变成全局维护负担 | 放入个性化 skill 或本次指令，不污染仓库权威文档 | RW-075 |

## 5. 可直接转成 skill 的检查点

本节仍是分析草案，供主代理设计 skill 时取用。

### 5.1 开始研究前

- [ ] 用一句话写清：这次到底研究什么？
- [ ] 写清“不研究什么”，避免研究对象滑到相邻问题。
- [ ] 写清最终产物：当前问题解法、可复用方法论，还是二者都要。
- [ ] 写清读者：只给自己、给当前团队，还是面向不知道上下文的公共读者。
- [ ] 先读取用户已有大纲或假设，将其视为待验证方向，不擅自换题。
- [ ] 如果无法准确复述课题，停下来对齐，不开始大规模搜索。

### 5.2 研究进行中

- [ ] 同步维护研究笔记，至少记录：链接、来源类型、关键原文、实际支持的结论、适用边界、待核问题。
- [ ] 官方材料用于确认机制事实；社区文章用于观察实践；代表性仓库用于观察理论如何落地。
- [ ] 对案例项目先讲清它实际怎么运作，再抽象它相信什么；不要只模仿表面流程。
- [ ] 明确项目检查的是一次任务、一个 session、整个仓库还是更大范围。
- [ ] 读到静态能力后继续核对运行时输入、数据契约和真实执行证据。
- [ ] 抽象说明难以理解时，展示一个完整但最小的输入/输出例子。
- [ ] 对结论反问：当前分析对象的信息量是否足够，缺失究竟表示不存在还是未知。
- [ ] 对关键候选方法，尽可能用真实运行、当前代码或具体案例验证。
- [ ] 用户提供的旧调研只作为参考输入，重新核验后再进入结论。
- [ ] 每个整齐的新框架都问：直接来源是什么？如果是综合，推导链是什么？

建议研究记录最小字段：

| 字段 | 要回答的问题 |
|---|---|
| Source | 链接、文件或项目在哪里？ |
| Type | 官方事实、社区实践、论文观察、案例实现，还是用户材料？ |
| Claim | 它实际支持哪一句结论？ |
| Limit | 它不能证明什么？ |
| Use | 放入文章哪一段，还是只留在研究笔记？ |
| Status | 已核验、待核验，还是与其他来源冲突？ |

### 5.3 从研究到文章

- [ ] 先写论证骨架，不按“搜到什么”排列章节。
- [ ] 每节都能补全一句：因为存在什么问题，所以要讨论什么设计，它带来什么价值。
- [ ] WHY 只回答课题层面的“为什么需要不同方法”，不把 HOW 的局部实验证据提前塞入。
- [ ] WHAT 中的分类来自前文判据；常见清单放在理论和边界之后。
- [ ] HOW 体现因果顺序：可发现 / 可消费 → 组织方式 → 更新与防腐败 → 落地门禁。
- [ ] 案例要明确介绍，不使用“当前内容”这类只有作者知道的指代。
- [ ] 研究笔记保存来源与推导；最终文章只保留经筛选后能推进结论的内容。

注意：用户这篇文章使用 WHY / WHAT / HOW / 最佳实践，不足以证明以后所有文章都必须套同一标题。可稳定迁移的是“问题和因果驱动结构”，不是标题模板本身。

### 5.4 段落级审阅

对每一节依次问：

1. 三句话内，这一节到底想表达什么？
2. 它解决的是哪个读者问题？
3. 每个关键事实或框架从哪里来？
4. 来源实际支持的是哪一句话，边界是什么？
5. 与前后段相比，有什么独有信息？
6. 有没有在反驳一个读者根本不会持有的误解？
7. 有没有“制品”“知识角色”这类不落地的抽象词？
8. 是不是可以用更短、更直接的句子表达同一逻辑？
9. 外部读者是否需要未提供的项目上下文才能看懂？

### 5.5 图表审阅

- [ ] 图是否表达了至少一个仅靠连续文字较难快速检查的关系？
- [ ] 图中的每层、每个节点和箭头是否有语义？
- [ ] 正文是否解释图的逻辑，而不是只说“如下图”？
- [ ] 术语是否与来源和正文一致，有无漏项？
- [ ] 宽高比是否适合实际阅读载体，是否出现“超级大长条”？
- [ ] 表格的每一列是否带来不同信息？相邻表格是否重复？
- [ ] 如果删掉图，文章损失什么？若答案只是“没那么好看”，图应删除。

### 5.6 排版和语言

- [ ] prose 不按固定列宽机械换行；只在段落、列表、引用、代码等语义边界换行。
- [ ] 同一读者文档保持主要语言一致。
- [ ] 标题下内容语义同类，不为了压缩目录而合并不相关概念。
- [ ] 不用“不是……而是……”制造无人持有的对立面。
- [ ] 不写向读者解释“本文为何这样组织”的低价值元话语，除非它确实帮助使用文档。
- [ ] 个别 Agent 的生成缺陷放进个性化 skill，不上升为仓库永久规则。

## 6. 证据强度与仍需主代理判断的边界

### 高置信、重复出现

- 先对齐研究问题，再研究。
- 研究项目时追到实际触发、运行时对象、完整输入和证据上限。
- 追问来源到底支持什么，而不满足于“有引用”。
- 因果链优先于标题清单。
- 删除常识、重复、防御性稻草人和无信息量图片。
- 面向公共读者时移除隐含的本仓上下文。
- 图必须压缩可检查的复杂论证。
- 不接受机械硬换行。

### 中等置信、应做成可调参数

- WHY / WHAT / HOW / 最佳实践是本篇已明确的大纲，不必固定为所有文章模板。
- 用户接受图、表、Mermaid 和生成图片，但是否使用取决于信息结构，不是每篇必备。
- 用户偏好中文输出在本组会话中成立；以后仍应跟随目标文章和读者语言。
- 可以使用当前项目做实例，但应显式引入；并非所有研究都必须含实例模板。

### 不应错误泛化

- 用户粘贴的 ChatGPT 调研内容、文章段落和 Mermaid 图不等于全部由用户原创；只能把“用户选择它做材料”和后续评价作为偏好证据。
- “不要无端换行”不应写回仓库规则；它适合进入个人写作 skill。
- 用户强烈批评时表达的措辞强度不需要被 skill 模仿，需提炼其背后的判断标准。
- 用户对本篇文章要求“不用个人叙事开场”，不代表所有个人文章都禁止叙事；稳定要求是开场服务于文章目标和读者。

## 7. 一句话总括

用户的稳定方法不是“搜很多资料，再写一篇完整文章”，而是：

> 先把可复用的研究问题对齐；边研究边记录每个来源真正支持的窄结论；用问题—机制—设计—价值的因果链组织文章；再以公共读者、信息增量和可检查性为标准，逐段删除常识、重复、伪对照、漂浮术语和装饰性图表。
