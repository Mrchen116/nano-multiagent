## 1. Research brief

### 实践触发

已知触发：一位大型 monorepo 的技术负责人正在评估，是否值得引入并长期维护一份 generated code ownership map。这个决策同时涉及错误编辑与评审路由的风险、跨团队排障效率，以及新增元数据的维护成本。

虚拟任务没有提供以下现场信息：

- “ownership”是只指审批人，还是还包含生成器维护者、源文件负责人、生成产物消费者和事故责任人；
- 当前仓库是否已有 CODEOWNERS、构建图、生成文件头、generator manifest 或服务目录；
- 当前是否已有错误编辑生成文件、找不到生成入口、评审误路由或事故升级失败；
- 代码生成跨多少语言、生成器和团队边界；
- 这份 map 预期由人手写、由现有权威数据生成，还是只作为查询视图存在。

按 skill 的“方向改变型假设先提出”规则，真实执行时我会先问一个阻塞性最强的问题：

> 你希望这份 map 首先回答“谁审批这个生成文件”，还是回答“这个产物由什么源和生成器产生、谁分别负责修源、修生成器和处理下游影响”？

本次 dry run 无法等待回答，暂按较宽且更有方法论价值的定义继续：

> generated code ownership map 是一项可查询的责任与溯源契约：对某个生成产物或路径，能解析出权威输入、生成器或再生成命令、生成器维护者、业务/消费者负责人，以及编辑、评审和事故路由。它不等同于只把路径映射到 reviewer 的 CODEOWNERS。

若用户实际只关心 reviewer 路由，研究范围应明显收窄。

### 可迁移研究问题

大型 monorepo 在什么条件下需要显式提供 generated-code ownership 能力？当需要时，它应由现有权威元数据按需查询、生成一个物化视图，还是维护一份独立 registry，才能让收益大于漂移与治理成本？

相应的子问题是：

1. generated code 引入了哪些普通路径 ownership 不能表达的责任关系？
2. 哪些失败确实来自这些关系不可见，而不是构建、文档或团队流程的其他缺陷？
3. 仓库现有机制已经能回答哪些问题，缺的只是发现入口还是事实本身？
4. 哪些规模、跨团队耦合、风险和自动化消费场景会使显式 map 有净收益？
5. 若建立 map，什么应是权威来源，如何生成、验证、消费、更新和退役？
6. 用什么结果指标证明它有用，而不是只证明字段覆盖率上升？

### 读者与用途

- 读者：拥有代码库治理、开发基础设施或工程效率决策权的技术负责人。
- 读完后应能：
  1. 判断自己的仓库到底缺不缺这项能力；
  2. 在“不新增 map / 暴露现有查询 / 自动生成 map / 狭窄手工 registry”之间选择；
  3. 设定一个可回滚的试点及成功、失败和停止判据；
  4. 识别重复权威、漂移和虚假 ownership 带来的风险。

### 范围

**In**

- generated code 的责任与溯源关系；
- 真实失败模式和适用条件；
- CODEOWNERS、构建图、generator metadata、服务目录等相邻机制的能力边界；
- map 的最小数据契约、权威来源、生成/校验和消费方式；
- 采用决策、试点指标、维护成本与反例。

**Out**

- 为某一个具体仓库选型或实施；
- 给出通用文件格式、数据库产品或 vendor 排名；
- 泛写 monorepo 治理、代码生成最佳实践或组织 ownership；
- 没有实证支撑时声称 map 能提高生产率、质量或事故指标；
- 把 coding agent 的需求当成引入 map 的唯一理由。

**Later**

- 面向 coding agent 的 tool/API 设计；
- 与软件目录、依赖图、数据血缘平台的统一模型；
- 跨仓库 generated artifact provenance；
- 某个真实 monorepo 的迁移方案。

## 2. 来源问题矩阵

这个矩阵在搜索前建立。它不是 source ledger 的替代品：矩阵负责定义“为什么搜、什么才算回答”，ledger 负责记录“实际读到了什么”。

| ID | 待回答问题 | 它服务的决策 | 优先证据 | 什么才算有效回答 | 不能从这类证据推出 |
|---|---|---|---|---|---|
| Q0 | `generated code`、`ownership`、`map` 在不同系统中具体指什么？ | 固定对象边界，避免把 CODEOWNERS 当成完整答案 | 官方规范、仓库约定、生成器输出契约、真实 schema | 能列出参与实体、字段语义和谁写入/读取 | 术语被使用不等于该机制有净收益 |
| Q1 | generated artifact 到 source、generator、owner 的真实解析链是什么？ | 判断现有事实是否已存在 | 构建规则、generator manifest、文件头、源码调用链、查询命令与测试 | 对最小案例能从产物走到权威输入、生成动作和责任方 | 某项目源码“支持”不证明所有产物覆盖或运行中被使用 |
| Q2 | ownership 不可见具体导致过哪些失败？ | 证明问题值得治理 | incident/postmortem、issue/PR、错误编辑被覆盖的记录、评审误路由、排障会话 | 有事件、机制、后果和替代解释；最好能定位发生路径 | 零散抱怨不能证明普遍频率或因果效应 |
| Q3 | 哪些仓库特征会放大这些失败？ | 形成采用阈值 | 当前仓库指标、跨团队依赖、生成器数量、所有权变更率、生成产物规模、自动化消费者 | 特征与失败之间有可解释机制，并能被本地测量 | “仓库很大”不能单独推出需要 map |
| Q4 | CODEOWNERS、构建图、服务目录、generator metadata 各能回答什么？ | 比较“不新增 / 查询 / 生成视图 / registry” | 各机制官方文档、schema、源码、测试和真实配置 | 逐问题比较 coverage、authority、freshness、queryability 和 consumer | 功能清单不能证明采用效果或维护成本 |
| Q5 | 显式 map 是否改善了实际结果？ | 判断收益而非功能存在 | 原始研究、前后对比、受控试点、长期运营指标 | 指标、基线、干预、时间窗、混杂因素和限制清楚 | 个案成功不能外推所有 monorepo；覆盖率不等于工程结果 |
| Q6 | map 会怎样漂移、误导或增加治理成本？ | 评估净收益 | 失败案例、staleness audit、owner 变更记录、CI 失败、弃用记录 | 能观察重复权威、过期频率、修复成本或错误信任的后果 | 有维护成本不自动推出“不应建立” |
| Q7 | 最小契约应包含哪些字段，谁是每个字段的权威？ | 设计可执行方案 | 成熟 schema、构建/生成器模型、真实查询需求、消费者代码 | 每个字段都有生产者、更新事件、校验、消费者和缺失语义 | 多个项目都含某字段不等于本项目也必须含 |
| Q8 | 哪些反例中 map 没有增量价值？ | 限定主张，防止统一最佳实践 | 小而同质的仓库、同 owner 的 source/output、已可完整查询的 build graph、从不直接触碰的产物 | 能说明现有机制已回答需求或风险低于维护成本 | 一个反例不能否定所有高耦合场景 |
| Q9 | 什么试点能区分“真实改善”与“多了一份清单”？ | 给技术负责人可逆决策 | 当前基线、历史事件、用户任务抽样、试点 telemetry | 有前置基线、目标 cohort、成功/停止阈值、漂移审计和回滚路径 | 短期满意度不能替代长期 freshness |
| Q10 | 公开证据在哪些问题上不足？ | 控制文章措辞和研究边界 | 对 source ledger 的缺口审计 | 明确哪些只能作为综合或作者判断，并指出所需本地证据 | “没有找到”不能写成“不存在” |

### 候选来源族

以下只是待搜索对象，不构成引用或证据：

1. **代码托管 ownership 机制**：GitHub/GitLab 等官方 CODEOWNERS 规范、匹配语义和限制。
2. **构建与 monorepo 系统**：Bazel、Buck2、Pants、Nx 等的官方文档、查询能力、规则模型、源码和测试。
3. **代码生成生态**：Protobuf、OpenAPI、Kubernetes code generator 等生成器的输入、输出、标记和再生成契约。
4. **大型开源 monorepo 实例**：实际 generated path、owner 配置、build rule、维护脚本、issue/PR 和事故记录；不能只读宣传博客。
5. **原始研究**：code ownership、socio-technical congruence、review routing、bus factor 或 generated-code maintenance 的原始论文；先核验研究对象是否真的覆盖本题。
6. **当前组织证据**：错误编辑被覆盖、找不到生成入口、评审重路由、事故升级、owner 变更、查询耗时和 map 漂移。这类证据对“是否在本仓采用”通常比公开最佳实践更关键。

### 暂定证据充分性与停止条件

skill 没有提供这一层，本次 dry run 需自行设定：

- 每个机制性核心命题至少需要一项权威机制证据；涉及真实失败时，再需要一项独立运行/事件证据。

- 若 Q5 的公开证据不足，不继续无限搜寻；把结论降级，并把本地试点作为决策方法的一部分。

## 3. 论证主链

### 待证主张

> 大型 monorepo 真正需要的是可权威解析的 generated-code 责任与溯源能力，不必然是一份额外的手工 map。只有当 generated artifact 跨越 source、generator、consumer 或团队边界，现有权威元数据又无法稳定回答编辑、评审和事故路由问题时，显式 map 才可能有净收益；能从权威事实生成时，应优先把它做成可校验的视图，而不是第二事实源。

这是本次 dry run 的 `[J]` 研究方向与候选 `[S]` 综合，不是已经被来源证明的结论。

### 因果主链

1. **现象或需求**  
   生成产物所在的路径并不天然说明谁能修改它、什么输入才是权威、哪个工具负责再生成、谁维护生成器、谁承担下游业务影响。

2. **过去的补偿机制**  
   在生成器少、团队关系稳定时，资深维护者、局部 README、评审转派和口头知识可以补全这些关系。

3. **环境变化**  
   monorepo 中语言、生成器、共享 schema、团队边界和自动化消费者增加；代码搜索、review bot 和 coding agent 更依赖仓库内可查询事实。

4. **补偿机制为何失效**  
   普通 path ownership 和 blame 把多种责任压成一个 owner；口头知识无法稳定进入自动化路径；团队或生成规则变化后，重复抄写的映射会漂移。

5. **执行后果**  
   可能出现直接修改随后被覆盖、修错 source/generator、评审送错团队、事故在 artifact owner 与平台 owner 之间往返、自动化在错误边界内修改等问题。每一种后果都必须由 Q2/Q3 验证，不能靠这条逻辑链直接断言其频率。

6. **必需能力**  
   对一个 generated artifact，应能解析：
   - 权威输入；
   - 生成器与再生成动作；
   - generator/platform 责任；
   - domain/consumer 责任；
   - 编辑、评审和事故路由；
   - 当前事实的来源、更新时间与缺失语义。

7. **决策分叉**  
   - 现有 build graph、generator metadata 和 ownership 系统已经可靠回答：提供统一查询或生成视图，不新建手工事实源。
   - 缺口存在但低频、低风险且局部知识足够：保留轻量约定并测量，不建立全仓 map。
   - 缺口反复造成高成本跨团队失败，且关系可从权威配置推导：自动生成 map，并在 CI 中校验。
   - 少数关键关系无法推导：只为缺失边建立狭窄 registry，给每项记录 owner、依据、审计和退役条件。

8. **落实与验证**  
   先做有限 cohort 的只读查询/视图试点，接入开发者检索、review routing 或事故分诊；用解析耗时、错误编辑、错误路由、升级跳数、缺失率和漂移率验证。若只有 coverage 上升而任务结果无改善，停止扩张。

### 核心论点与证据依赖

| 论点 | 命题 | 依赖问题 | 边界或反例 |
|---|---|---|---|
| C1 | generated code 把 source、generator、artifact、consumer 等责任拆成多层关系 | Q0, Q1, Q4 | 某些仓库这些角色由同一团队承担 |
| C2 | 关系不可见只在特定规模、耦合和风险条件下形成治理问题 | Q2, Q3 | 大型但生成规则高度统一的仓库未必需要新机制 |
| C3 | ownership 能力不等于一份额外文件；查询、生成视图和 registry 是不同方案 | Q1, Q4, Q8 | 消费者若只接受静态文件，物化视图仍可能必要 |
| C4 | 手工 map 的价值必须扣除重复权威、漂移和虚假确定性 | Q5, Q6 | 无法推导的少数责任边可能只能人工维护 |
| C5 | 最小契约应围绕真实解析任务，而非追求元数据完整 | Q2, Q7 | 合规场景可能要求额外审计字段 |
| C6 | 采用决策应以任务结果和 freshness 验证，不以 map 覆盖率自证 | Q5, Q9, Q10 | 长期事故指标低频时需使用代理指标，并明确限制 |

### 文章结构职责

这不是文章正文，只是 reader-layer 的结构决策：

| 章节 | 读者问题 | 本节结论 | 通往下一节 |
|---|---|---|---|
| 1. 先定义你要解决的 ownership | 我们说的 owner 到底是谁？ | 生成产物涉及多类责任，必须先定义查询任务 | 有了对象，才能判断现有机制哪里失灵 |
| 2. 哪些情况下问题值得治理 | 为什么不是每个 monorepo 都要建 map？ | 规模不是判据；跨边界失败、风险和查询缺口才是 | 进入方案选择 |
| 3. 四种方案，而非一个最佳实践 | 新增 map 是唯一答案吗？ | 不新增、暴露查询、生成视图、狭窄 registry 各有条件 | 选定方案后讨论如何避免新事实源 |
| 4. 把 map 做成可维护契约 | 需要时怎样设计？ | 字段必须有权威、生产者、消费者、校验和缺失语义 | 契约是否有效要由试点证明 |
| 5. 用试点决定扩张或停止 | 如何知道它值得长期维护？ | 以任务结果、漂移和维护成本作门禁 | 最后说明适用边界 |
| 6. 反例与限制 | 什么情况下不应照搬？ | 现有元数据充分、风险低或组织效果证据不足时应降级 | 收束为条件化决策方法 |

## 4. 是否需要图及 visual brief

### 决定

需要一张图，但只需要一张。题目的核心是条件化决策，至少包含“现有权威是否足够”“问题成本是否达到治理阈值”“缺失关系能否推导”三个连续分叉。把它只写成散文会迫使读者在多个段落之间保持状态；一张精确的决策流程图能同时显示路径和最终产物。

不需要生成式插图，也不需要再画一张装饰性的 monorepo 网络图。责任角色的定义可用正文中的紧凑表格承担。

### Visual brief

#### 论证职责

- 要压缩或证明的命题：需要的是可权威解析的 ownership 能力；是否建立 map、建立哪种 map，取决于现有事实、失败成本和可推导性。
- 为什么文字或短表格不够：这是三个有顺序的判断门，四个结果之间还有“不要创建第二事实源”的约束；流程图更容易检查是否走错分支。

#### 内容

- 实体：
  - 待解析的 generated artifact；
  - 所需答案：source、generator、responsible teams、regeneration/review/incident route；
  - 现有权威元数据；
  - build graph / generator config / ownership system；
  - 按需查询或自动生成视图；
  - 局部约定；
  - 自动生成并校验的 map；
  - 仅补缺失边的狭窄 registry；
  - CI/freshness 校验与试点结果。
- 关系：
  1. 先检查现有权威能否稳定回答全部必要问题；
  2. 若不能，判断缺口是否反复造成高成本或被自动化消费；
  3. 若需要治理，判断缺失关系能否从权威数据推导；
  4. 每条实施路径都回到结果与漂移验证。
- 阅读顺序：从左到右；主干最多三层判断，结果节点不交叉回线。
- 必须准确的标签：
  - “权威元数据”与“map/view”不能画成同一个事实源；
  - “无法推导”不等于“全量手写”，只登记缺失边；
  - “不建 map”仍可能需要统一查询入口；
  - “低成本问题”路径应包含继续测量，而非永久忽略。

#### 形式

- 媒介：Mermaid flowchart；最终发布环境若 Mermaid 渲染不稳定，再导出 SVG。
- 目标比例：横向约 16:9，避免高而窄的长条图。
- 放置章节：第 3 节“四种方案”开头，承接问题阈值并统领后续方法。
- 图注：

  > 图：先判断现有权威是否已经能回答责任与溯源问题，再按失败成本和可推导性选择查询、生成视图或狭窄 registry；map 是消费形态，不应自动成为第二事实源。

#### 渲染检查

- [ ] 每个判断节点只有可区分的 `是/否` 出边。
- [ ] 四种结果没有被视觉层级误画成成熟度阶梯。
- [ ] 权威事实到物化视图的箭头方向正确。
- [ ] “狭窄 registry”明确只补缺失关系。
- [ ] 图和正文使用同一组术语。
- [ ] 常见笔记宽度和移动端可读。
- [ ] 图产生决策路径压缩，而非复述一段定义。

本次 dry run 不生成或渲染该图。

## 5. Skill 中仍含糊、重复、过度流程化或可能诱发低价值产物的地方

### A. 冷启动研究的关键缺口

| 问题 | 具体表现 | 在本题中的风险 | 严重度 |
|---|---|---|---|
| 缺少“操作性定义/竞争含义”步骤 | brief 没有要求先列核心术语的多种含义 | 容易把 reviewer ownership、generator ownership、source provenance 和 consumer responsibility 混成一张 map | 高 |
| 缺少搜索前的 question-source matrix | skill 说“先列问题”，模板却直接从 brief 跳到按来源记账的 source ledger | 执行者可能按工具或项目收集资料，最后才发现没有证据回答效果和采用阈值 | 高 |
| 缺少证据充分性和停止条件 | 没说明一个问题何时算回答、何时停止扩搜 | “大型 monorepo + ownership”会扩张到大量构建系统、生成器、论文和项目，形成低密度资料堆 | 高 |
| 没有区分 authority、registry、index、cache、materialized view | “载体为什么由文档/代码/skill 承担”的提问仍太粗 | 可能直接推荐一份新 map，却没有先问现有 build graph 是否已经是事实源 | 高 |
| 没有明确的 missing-context 协议 | 只说方向改变型假设要先提出，但没说明何时必须停下来问、何时可带假设继续 | 本题的 `ownership map` 明显多义，执行结果高度依赖执行者个人判断 | 高 |

### B. 论证模板可能过度统一

`现象 → 过去补偿机制 → 环境变化 → 失效 → 后果 → 能力 → 实践` 对 Agent-Native、组织变迁一类文章很有效，但不是所有研究问题都有“过去补偿机制”和“环境变化”。本题可以使用这条链，但真正的中心其实是一个决策模型：

```text
待完成的任务
→ 当前系统能否回答
→ 缺口造成的风险与频率
→ 可选机制及总成本
→ 采用阈值
→ 试点与停止条件
```

如果把单一因果骨架当成必填模板，作者可能人为编造历史阶段，或让决策文章花大量篇幅讲“以前靠资深维护者”，反而延迟读者最关心的选择条件。

### C. 证据标签会把“来源声称”误写成“事实”

模板中的 `[F] 来源事实` 同时容纳：

- 官方文档声称某能力存在；
- 源码中直接观察到某个结构；
- 运行时日志证明某次执行发生；
- 论文在特定设计下报告某个结果。

它们的证据强度和外推边界不同。即使都直接来自来源，vendor 文档的陈述也不应自动获得“事实”语气。本题尤其容易把“某工具支持 ownership metadata”写成“该机制在实践中解决了 ownership 问题”。

### D. Source ledger 的字段不足以支撑版本化技术研究

当前模板没有显式记录：

- 它回答哪个 research question / claim；
- 版本、日期、commit 或观察环境；
- 证据是 source-stated claim 还是作者直接观察；
- 证据强度、代表性与适用范围；
- 下一步要用什么独立证据验证。

“来源及位置”可以承载其中一部分，但冷启动执行者未必会主动补全，最终 ledger 可追溯却不可比较。

### E. “标准文章/长程研究”的分界不明确

skill 一方面要求选择“最轻的充分工作集”，另一方面规定“标准文章至少保留研究笔记和读者稿两个层次”，长任务又要尽早建立持久工作区。这里没有说明：

- 两个“层次”是否必须是两个文件；
- 何种规模、来源数或轮次才算长程研究；
- 用户只要一篇短方法文时是否需要额外 working-set 文件。

这可能诱发为了合规创建 brief、ledger、map、feedback、backtest、visual 六份空壳文件。逻辑分层是必要的，物理文件不应成为默认。

### F. “还原真实范式”的提问过度偏向运行时软件

“触发—输入—状态/调用链—输出—验收”适合软件与 agent harness，却不完全覆盖组织治理机制。研究 ownership map 还需要：

- 谁拥有写权限和变更权；
- 什么事件触发 owner 更新；
- 冲突由谁裁决；
- 缺失、多人负责和无人负责分别怎样表达；
- 激励是否促使团队维护数据；
- 数据被哪些组织流程消费。

若只追调用链，文章可能准确描述工具，却漏掉 map 最容易失败的治理生命周期。

### G. 实践回测容易悄悄扩张任务

“尽量用真实实践或冷启动任务验证”方向正确，但没有明确：

- 何时只做只读审计；
- 何时可以创建迁移或 telemetry；
- 是否需要用户授权才能操作真实仓库；
- 文章研究与项目改造之间的停止线。

本题如果照字面推进，执行者可能为了“回测”去生成真实 ownership map 或修改 CI，超出研究写作任务。即使不修改，也可能投入大量仓库审计，偏离给技术负责人的一般方法。

### H. 视觉决策在总流程中偏晚

总流程把“设计并校验视觉”放在“写成读者稿”之后。对决策树、生命周期和多对多映射，视觉其实会反过来暴露 argument map 的缺口。本题的四种结果若等全文写完再画，容易沦为正文复刻。

更合理的是：

```text
argument map
→ 判断是否需要视觉并写 visual brief
→ 文章结构
→ 正文
→ 视觉制作与渲染校验
```

### I. 章节写法可能产生模板感

“每节开头说明问题、每节结尾说明如何通往下一节”如果逐节机械执行，会出现重复的元话语，尤其在短文章中降低信息密度。它适合作为结构审查问题，不宜成为每一节都必须显式写出的句式。

同样，“每个长段落或章节做三句话测试”是有效的编辑检查，但和“每节问题/结论/通往下一节”叠加后，容易让作者过度维护摘要而不是正文。

### J. 反馈 ledger 可能保留过多低价值或敏感原话

“原样记录关键反馈”应强调“只记录会改变决策或产物的最小必要片段”。长程研究中逐字保留所有反馈会制造恢复噪声，也可能无意持久化敏感上下文。当前模板没有区分当前用户约束、单次偏好和可泛化规则的证据门槛。

### K. 内容存在可压缩的重复

这些重复能提醒执行者，但也增加阅读和遵循成本：

- 证据边界在第 3 节、第 6 节和交付质检中重复；
- 视觉的信息增量与渲染检查在第 7 节、visual template 和质检中重复；
- “选择最轻工作集”和“长任务持久化”分散在工作强度、第 10 节及模板说明；
- “反馈应回写上游”同时出现在目标、第 8 节和 feedback template；
- 反例/回测分别出现在 argument map、实践回测和最终质检。

可以保留一处规范性规则，其余位置改成短链接或检查项，减少执行者在多处对同一状态重复记账。

### B1. `[SC]` 与 `[O]` 对论文实验结果的边界仍有歧义

当前文字把“论文直接声称”列为来源陈述，同时又把“从……实验结果直接看到”列为直接观察。冷启动执行者阅读论文结果表时，可能认为自己“直接看到了实验结果”，把作者报告的数字标为 `[O]`。这会削弱本 skill 最重要的证据边界：读到论文报告，与独立检查底层数据、复算指标或复现实验，不是同一种观察。

最小修订：

> `[SC]` 包含来源正文、表格和图中报告的结论或结果；只有代理直接检查源码、原始数据、日志、运行产物，或独立复算/复现实验时才标 `[O]`，并记录观察环境。读取论文中的结果表本身仍是 `[SC]`。

模板中的“直接陈述或观察”字段可以保留，但按这句话判定。

### B2. Artifact 角色判断没有写入可恢复的模板
