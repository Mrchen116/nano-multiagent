# 证据驱动的研究与写作

## 目标

把一个研究问题做成读者能独立理解、论证链完整、证据不越界的文章。保留研究过程中的来源、推导和用户反馈，但不要把研究日志直接拼成正文。

最终产物应同时满足：

- 问题与用户意图一致；
- 事实、推论和判断可区分；
- 关键现象、分类、转变或设计都能沿基础条件、目标、约束和机制还原；
- 外部读者不依赖会话上下文也能读懂；
- 结构、例子、表格和图都有信息增量；
- 新反馈能回写到整条论证链，而不是只做局部修辞修补。

## 工作强度

根据任务大小选择最轻的充分工作集：

- **短问题**：在上下文中维护 research brief、少量来源和论证链，不创建额外文件。
- **标准文章**：至少在逻辑上分开研究层与读者层；不要求物理拆成两个文件。
- **长程研究**：跨多次会话、多个独立来源族、需要 subagent/交接、预计会压缩上下文，或中间证据需要单独审计时，建立持久工作目录。使用 `references/working-set-templates.md` 中真正有恢复价值的模板。用户要求保留中间结果时，立即创建，不等到上下文将满。

不要为了流程完整而创建没有恢复价值的文件。能从其他权威事实直接恢复的状态，不再抄一份。

## 总流程

```text
研究对象与问题
→ 对齐研究问题与读者
→ 从基础能力、环境、目标与约束重建对象为何形成和演化
→ 按问题分配证据
→ 建立匹配题型的论证
→ 判断视觉是否能压缩关键关系
→ 设计文章结构
→ 写成读者稿
→ 制作并校验已获准的视觉
→ 用案例、反例、实践和反馈回测
```

## 第一性原理：重建“为什么会这样”

第一性原理不是一种研究题型，而是所有研究共用的分析方法。无论研究现状版图、历史演进、机制比较还是设计选择，都不要把现成术语、社区分类、时间线或流行结论当成研究终点。先说清楚要解释的现象或问题，再从对象最基本的能力与环境、参与者想完成的目标以及实际约束出发，重建它为何形成、分化或演进。

保持一条可以追溯的生成链：

```text
基础能力与环境
→ 目标
→ 暴露出的约束、困难或矛盾
→ 为此产生的机制、做法或分化
→ 获得的新能力与结果
→ 新机制暴露的限制
→ 下一阶段、其他分支或仍未解决的问题
```

这条链不要求所有研究都写成线性历史。研究当前版图时，从共同目标、约束和机制推出分类；研究历史时，解释每次转变为何发生；研究方案差异时，从各自目标和约束解释分化；研究设计时，从问题推出所需能力和选择。题型只决定文章怎样组织，第一性原理负责提供共同的因果解释。

每条箭头都要接受证据检验。时间先后、维护者叙事和技术上的可能性只能提供候选解释，不能自动证明因果；主动记录替代解释、反例和仍未知的环节。如果一个理论或分类只能靠事后编故事成立，或不能增加对现象、机制、边界或实践的理解，就删除、降为背景或留到 later。

## 1. 对齐研究契约

研究前先写出一个简短的 research brief：

1. **研究触发**：想理解什么现象、变化或未知，或者解决什么实践问题；
2. **要形成的理解或支持的决策**：最终要解释、梳理、比较或决定什么；
3. **操作性定义**：核心术语在本题中具体指什么，还有哪些竞争含义；
4. **可迁移问题**：这次研究最终要回答什么一般问题；
5. **读者与用途**：写给谁，读完要理解或决定什么；
6. **范围与非目标**：哪些相邻问题暂时不回答；
7. **已知、假设与未知**：哪些可直接采用，哪些必须先澄清；
8. **产物形态**：研究笔记、文章、图、方案或它们的组合；
9. **成功判据**：怎样才算研究到位、文章可用。

遵守这些对齐规则：

- 把用户明确给出的主结构、受众和写作目的视为约束，不静默换题。
- 具体观察或局部症状可以提升为一般问题，但要说明提升后的问题如何服务原始研究目的。
- 如果一个假设会改变研究方向，先显式提出；小的可逆假设可注明后继续。
- 如果一个未决术语会改变研究对象、来源族或结论选项，必须先问清；无法等待时只能带醒目标记的假设继续。
- 用户要求逐节对齐时，只推进当前章节，保留全文论证图但不提前大改后文。
- 发现相邻的大课题时，记入“later”，不要顺手扩张当前文章。

## 2. 先还原对象如何运作和演化，再抽象原则

研究软件、工作流或工程方法时，不从文档名词和表面目录直接归纳。先回答：

- 谁在什么时候触发它；
- 运行时实际读取什么输入；
- 经过哪些状态或调用链；
- 产生什么可观察输出；
- 用户或下游如何验收；
- 静态配置存在，是否真的意味着执行发生；
- 当前证据看不到什么。

研究 ownership、policy、目录或知识治理时，再回答：

- 谁有写入权和裁决权；
- 什么事件触发更新；
- 缺失、冲突和过期怎样表达；
- 谁实际消费这些信息；
- 如何审计和退役。

研究领域演进时，逐阶段回答：当时已有的基础能力和环境是什么，想完成什么目标，遇到了什么限制，新机制怎样回应这个限制，带来了什么能力，又暴露了什么新问题。时间线只负责定位事件，阶段之间的因果关系才是研究结论。

研究现状版图时，不直接照抄社区标签。先找共同目标、关键约束和实际机制，再据此推出类别与分支，并用反例检查分类边界。

推荐顺序：

```text
研究对象与所处环境
→ 目标与实际行为
→ 具体机制与数据
→ 观察到的能力、结果和限制
→ 分化、演进或可迁移设计要求
```

研究开源项目时，优先阅读入口、核心流程、数据契约、测试和真实示例。官方宣传只说明项目声称解决什么，不能代替运行机制。源码存在某能力，也不能证明某次任务实际使用了它。

当读者难以理解抽象说明时，展示一个完整但最小的输入/输出或执行例子，再概括机制。

## 3. 给不同问题匹配不同证据

不要按“找到什么就写什么”组织研究。搜索前先建立 evidence plan：列出待回答问题、候选命题、它服务的决策、优先证据、什么才算有效回答、不能推出什么，以及降级或停止条件。再为每个问题选择证据：

| 问题 | 优先证据 |
|---|---|
| 某产品或协议明确怎样工作 | 官方文档、规范、源码 |
| 运行时真实发生了什么 | 调用链、日志、测试、会话记录 |
| 某设计在实践中为何出现 | 维护者文章、issue、PR、成熟项目案例 |
| 某领域为何演进或分化 | 各阶段的论文、系统、版本、issue、PR 与同期实践记录 |
| 某因素产生了多大效果 | 原始论文、实验设计、数据 |
| 原则在当前项目是否可执行 | 当前仓库、真实迁移、冷启动任务 |

在 source ledger 中至少记录：

- 它回答的问题或命题；
- 来源及类型；
- 日期、版本、commit 或观察环境；
- 它研究或描述的对象；
- 可直接支持的命题；
- 不能支持的命题；
- 关键位置或链接；
- 与其他来源的张力。

对每个重要结论标记其性质：

- **来源陈述**：官方、维护者或论文正文、表格、图中直接报告的结论或结果；
- **直接观察**：Agent 直接检查源码、原始数据、日志、运行产物，或独立复算/复现实验得到；
- **受限推论**：从单个来源在其边界内推出；
- **跨来源综合**：由多个来源归纳出的框架；
- **作者判断**：基于目标与约束给出的取舍。

不必把这些标签机械地写进最终文章，但研究笔记中必须可追溯。来源直接声称某能力存在，不等于已观察到它在运行中生效。没有观察到某行为通常表示未知，不自动表示它不存在。

搜索前为核心问题规定最低充分证据。满足以下条件即可停止扩搜：

1. 决策所需命题已有类型匹配的证据；
2. 关键反例和替代解释已主动检查；
3. 新来源不再产生新的机制、边界或张力；
4. 无法解决的缺口已明确降级为未知或作者判断。

不要用来源数量代替充分性，也不要为了消灭所有未知无限延迟交付。

## 4. 建立因果论证，而不是目录堆砌

先写 argument map，再写目录。第一性原理生成链是共同的分析底座；下面的题型骨架只负责组织材料，不替代因果推导，也不要被填成形式作业。

现状版图型问题可以使用：

```text
共同对象与目标
→ 决定性的环境与约束
→ 可区分做法的机制维度
→ 由机制推出的类别与分支
→ 各类获得的能力、代价与适用条件
→ 尚未覆盖的空白与可能变化
```

历史演进型问题可以使用：

```text
阶段起点的能力与环境
→ 当时试图完成的目标
→ 暴露出的困难或矛盾
→ 出现的新机制
→ 新获得的能力
→ 新限制
→ 下一阶段为何出现
```

决策型问题可以使用：

```text
待完成的任务或风险
→ 当前机制能否满足
→ 缺口与后果
→ 备选方案
→ 收益、成本与采用阈值
→ 试点、停止与退役
```

机制比较型问题可以使用：

```text
共同目标
→ 各方案的权威来源与执行机制
→ 各自能解决和不能解决什么
→ 适用条件
→ 组合方式与边界
```

逐项追问：

- 这个概念、类别或阶段要解释什么现象、目标、困难或矛盾？
- 它由哪些基础条件与约束推出，而不是事后贴上的标签？
- 它通过什么机制产生观察到的能力、结果或转变？
- 哪些证据支持这条因果链，还有什么替代解释？
- 它的边界、代价和下一步限制是什么？

当结论涉及具体落地载体时，再追问为什么由这个载体承担，而不是代码、测试、文档、skill 或运行时事实中的其他载体。

删除只因“常见”“完整”“看起来专业”而存在的分类。若表格只是把正文换成格子，若标题只是并列名词，若原则没有失败机制，都应重写或删除。

如果文章建议新增 map、registry、index、catalog 或 summary，先判断：

- 它是权威事实源、人工补充 registry、派生索引、缓存还是物化视图；
- 同一事实是否已存在于代码、配置、构建图或运行时；
- 谁生产、谁能修改、什么事件触发更新；
- 能否由权威事实生成；
- 哪些消费者需要它，按需查询为什么不够；
- 缺失、冲突、过期和退役如何校验。

## 5. 分开维护研究层与读者层

### 研究笔记

保存：

- 来源、链接和关键位置；
- 直接观察与证据边界；
- 跨来源推导；
- 冲突、未知和待验证问题；
- 被放弃的解释及原因；
- 用户反馈及其影响面。

新增研究先回写研究笔记，再决定是否进入正文。

### 读者文章

只保留服务主论点的材料。默认按以下阅读逻辑组织，但服从用户已确定的主结构：

```text
研究对象与要解释的问题
→ 基础能力、环境与目标
→ 关键约束、困难或矛盾
→ 产生的机制、分支或阶段转变
→ 获得的能力、结果与新限制
→ 对理解、判断或实践的含义
```

在 outline 中为每节写清读者问题、唯一结论和逻辑去向。正文只在关系可能不清楚时显式过渡，避免机械重复“本节将……”之类元话语。

## 6. 写成外部读者能独立理解的文章

执行以下编辑规则：

- 先交代对象、背景、变化和后果，再进入分析。
- 例子必须自包含；移除只有当前仓库成员才懂的隐含上下文。
- 术语首次出现时用具体问题解释，避免用另一个抽象词定义它。
- 优先使用自然、准确的词，不为了显得专业发明标签。
- 删除读者本来不会产生的误解、常识性总结和虚构反方。
- 克制使用“不是……而是……”。只有读者确实可能持有前者，且对照能改变理解时才使用。
- 不用无语义的硬换行制造节奏。
- 引文只承担它实际支持的命题，紧邻相关句子。
- 研究来源不能替跨尺度命题背书；局部实验结果放在它能说明的 HOW 或限制中。
- 不把“来源很多”当作论证成立。来源与因果链必须逐项对齐。

若用户质疑“你到底研究了什么”，先说明读过的具体材料、得到的直接事实、综合推论和缺口，再讨论改文，不用笼统保证代替来源说明。

对每个长段落或章节做“三句话测试”：

1. 不看原句，用三句话以内说出它唯一的核心命题和因果关系；
2. 检查读者从现文中能否得到同一个命题；
3. 如果不能，围绕命题重写整段，不做局部同义改写。

## 7. 让视觉承担可检查的信息

只有当图比一段短文更清楚地表达下列关系时才作图：

- 三个以上节点的因果链或生命周期；
- 多对多映射；
- 层级、控制权或知识流；
- 多阶段迁移与状态变化；
- 两种系统在同一维度上的结构差异。

在 argument map 后判断是否需要视觉；需要时先写 visual brief，再用它反查论证结构。最终确定制作时再渲染和校验：

1. 这张图证明或压缩哪条命题；
2. 必须出现哪些实体；
3. 实体之间的关系是什么；
4. 阅读顺序是什么；
5. 读者看完能得到正文不易同时表达的什么；
6. 图注怎样把它接回论证。

媒介选择：

- 精确结构、流程和映射优先 Mermaid、SVG 或表格；
- 概念性场景才考虑生成式插图；
- 需要精确文本时，不依赖生成式图像模型排字。

生成后必须实际渲染并检查：标签、箭头、层级、纵横比、空白、字号和移动端可读性。避免高而窄的长条图、装饰性网络图和与正文重复的卡片拼贴。

## 8. 把用户纠正变成可复用规则

收到反馈时：

1. 记录会改变事实、范围、逻辑、读者假设或交付决策的最小必要反馈片段；
2. 判断它修正的是事实、范围、逻辑、读者假设、语言、版式还是视觉；
3. 找到受影响的上游假设和下游段落；
4. 先更新 brief、source ledger 或 argument map；
5. 再改正文及相关图；
6. 检查同类问题是否在其他位置重复出现。

不要只修用户点名的那一句。一次明确反馈足以成为当前任务约束；只有跨多个独立场景重复出现，才提升为通用写作规则。

## 9. 用案例、反例或实践回测理论

如果文章提出了一套工程方法、设计主张或因果解释，选择与主张风险相称的最小回测。默认只读；只有用户授权实施或任务本身包含迁移时，才修改真实仓库、配置或流程。一般研究可以用历史事件、对照案例、反例、最小沙盒任务或纸面 walk-through 检验。

先回答四个通用问题：

- 这项主张试图解释哪个现象、转变或差异，或者改善哪个真实任务或决策？
- 如果主张成立，应该还能观察到哪些事实、案例或结果？
- 哪个反例或替代解释必须主动检查？
- 什么证据会证伪主张、缩小适用范围或触发退役？

如果回测包含实践干预，再记录基线、干预后结果和维护成本怎样观察。

研究知识或文档体系时，还可以检查：

- 新代理能否找到正确入口和权威来源；
- 它能否区分 current、work、evidence、history 和 control；
- 它的探索轨迹是否合理，而不仅是最后碰巧答对；
- 实践是否暴露重复状态、漂移索引、虚假门禁或过度流程；
- 迁移是否偷偷改变了原有政策；
- 验证证据是否仍对应最终基线。

把回测结果分成：

- 真正新增的通用洞见；
- 文章已有原则的更强例证；
- 当前项目特例，不写入通用文章。

## 10. 长任务与 subagent 协作

长任务开始后尽早建立持久工作区。至少保存会话/来源索引、原始证据摘录和阶段综合，确保上下文压缩后能恢复。

只有在研究问题已对齐后，才把彼此独立的来源族或证据集交给 subagent。给每个 subagent 一个有边界的产物和持久文件；主代理负责：

- 统一问题与证据标准；
- 回查关键原文；
- 处理来源冲突；
- 完成跨来源综合；
- 决定最终结构和措辞。

不要让多个 subagent 各写一版全文后投票。不要持续轮询；并行处理其他工作，等完成或真实阻塞再接管。

## 11. 交付前质检

逐项检查：

### 问题

- 标题和正文回答的是同一个问题吗？
- 研究范围仍服务用户最初的实践目标吗？

### 证据

- 每条关键事实能定位到来源吗？
- 来源支持的是这句话，还是只支持一个更窄的命题？
- 事实、综合和判断有没有混写成“公认结论”？

### 逻辑

- 是否从基础能力、环境、目标与约束重建了现象为何形成、分化或演进？
- 分类和时间线是在承载解释，还是只罗列表面事实？
- 每条关键因果箭头是否有证据、边界与替代解释？
- 如果提出设计，所需能力、具体选择和价值是否由前文问题推出？
- 如果给出实践方法，是否回答了执行与维护问题，而不是重复原则？

### 读者

- 外部读者能理解例子、路径和术语吗？
- 是否存在只有作者知道的上下文？
- 是否有常识、重复解释或假想争论？

### 视觉与版式

- 每张图是否有独立信息价值并接回正文？
- 是否实际检查过渲染？
- 是否存在无语义硬换行、失控表格或过长列表？

### 反向验证

- 有没有真实案例或反例检验核心主张？
- 实践暴露的新问题是否被正确分成通用洞见、强化例证和领域特例？

交付时简要说明：完成了什么、主要研究边界、仍不确定什么，以及中间证据和最终产物分别位于哪里。
