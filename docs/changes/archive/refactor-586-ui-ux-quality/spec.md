## 范围与决定

按用户要求直接修改现有技能与模板。本记录保留需求和验证范围，不补造产品设计、产品验收或实施里程碑。关联 [PR #314](https://github.com/Mrchen116/nano-multiagent/pull/314) 的原型质量规则；本次把判断贯穿需求表达、设计、实施与验收，不加入历史事件的专用条款。

共同体验标准在 `change-design-author/references/prototype-and-runbook.md` 维护。各角色入口按职责引用；设计与验收模板承接相同标准。无产品代码、数据、部署或现有产品原型修改；不新增独立 UI 审批、不强制竞品数量或逐页人工确认。

## 成功标准

### Requirement: 设计从用户目标形成完整体验方案

#### Scenario: 设计与平台适配

- **WHEN** Agent 设计新增或迁移的界面
- **THEN** 根据用户目标组织信息、视觉层级与交互路径，说明关键取舍，并对照当前产品中有价值的体验。
- **AND** 功能清单与控件拼装不能证明设计完成；适配平台可以改变形式，但需保留关键体验质量。

### Requirement: 实施和验收独立判断体验质量

#### Scenario: 功能正常但体验不成立

- **WHEN** 功能和控件都存在，但实际使用中信息组织、视觉或操作体验妨碍用户目标
- **THEN** 实施者在真实客户端自检，评审者按实际用户代价报告问题；符合原型或场景未逐项列明不成为豁免。
- **AND** 功能、视觉组织、交互体验分别有证据；整体体验反馈推动检查共同成因，不只修正用户举出的例子。

### Requirement: 范围与证据相称

#### Scenario: 局部改动或缺少视觉条件

- **WHEN** 改动仅影响局部使用过程，或缺少必要真实画面
- **THEN** 检查覆盖相关上下文，不扩张成全产品重设计；明确未验证部分，不以 DOM、结构一致或功能通过推定体验通过。
- **AND** 不因纯个人风格偏好无限返工，不增加审批、规定截图数量或复制规则到各角色。

## 验证

验证技能结构、引用、模板与角色边界，并以独立的文档库批量标记设计、日历编辑器验收场景做有界前向试用。试用评价指令如何影响判断；没有真实客户端或当前产品画面的部分明确未验证，不宣称本修改保证未来产品体验。
