## 现状痛点

[跨 unit 复盘](retro-pipeline-rootcause.md)与[原话索引](feedback-evidence.md)显示：功能覆盖常代替信息组织；已有界面虽被读取却未被完整继承；独立 reviewer 也曾认可后来被用户否定的布局；整体反馈被局部修补。当前共同体验标准已经要求避免这些问题，因此重复增加同义原则不能直接解释或解决失效。

## 目标与不变性

目标是减少用户亲自纠正整体布局、信息架构和交互语义的负担，并保持现有开发流程轻量。一次试用只能检验可用性并提供有限效果线索，不把长期减少纠正次数承诺为本轮已证明结果。

### Requirement: 真实且可发现的判断案例

#### Scenario: 设计、实施或审查遇到相似问题

- **WHEN** 现有角色读取共同体验指导，并遇到案例覆盖的设计判断
- **THEN** 能按问题找到相应案例，理解真实情境、错误判断、改进依据、适用边界与观察办法；保留来源及证据缺口，不把历史建议冒充已交付结果。

### Requirement: 有界行为验证

#### Scenario: 验证新增资料

- **WHEN** 对新旧指导开展同模型、同输入和相同基线的任务试用
- **THEN** 被测上下文不含该任务标注答案或最终修复；检查实际读取、首稿渲染和关键操作，记录成本、结果和限制，未发现改善也如实交付。

### Requirement: 保持现有流程轻量

#### Scenario: 前端增量开发

- **WHEN** Agent 按现有 change 流程完成前端任务
- **THEN** 不因本次优化要求用户新增固定 UI 审批、增加额外 Reviewer 或重复提交一套设计文档。

### Requirement: 保持需求语义和产品范围

#### Scenario: 参考历史设计经验

- **WHEN** Agent 借鉴相似界面或用户历史纠正
- **THEN** 仍以当前需求与产品约束为准，不将经验变成一律隐藏按钮、禁止卡片、删除说明或禁止重新设计的规则。

### Requirement: 诚实区分建议与效果

#### Scenario: 有限试用后汇报

- **WHEN** 优化完成有限样本验证
- **THEN** 说明实际观察到的改善与剩余问题，不把材料存在、规则被读取或一次试用通过宣称为今后一次设计成功的保证。

## 影响范围

影响开发 Agent 的 UI 设计、自检与审查指导及其文档入口；不改变产品代码、当前产品交互、生产环境或运行时 Intelligent UI 提示词。

## 迁移与回滚边界

本轮没有运行数据或产品迁移。修改影响开发 Agent 读取的参考上下文，核对范围是既有入口、正文可读性、案例含义和实际消费结果。按用户要求直接实施，不补造事前门禁记录。使用现有文档权威与引用关系；若后续发现无收益或机械套用，回退对应指导变更，保留历史证据。
