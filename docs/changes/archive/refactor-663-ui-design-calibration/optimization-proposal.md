# 优化建议：按需使用少量设计取舍对照案例

日期：2026-10-26。本文保留实施前建议与来源核验；用户随后授权直接实施，最终改动和一次试用结果见事后 [design.md](design.md)，长期效果仍未证明。依据：[本次复盘](retro-pipeline-rootcause.md)、[用户指定 ChatGPT 对话](https://chatgpt.com/c/6adeb50a-d38c-83ec-b1cc-c3b7859b7f62)。参考聊天通过浏览器实际读取；聊天工具返回的回答引用占位符未当作正文。

## 推荐只做的一项改进

在现有共同 UI 设计指导旁，建立一份小而具体、按判断问题选择的对照案例资料。Agent 在作信息组织、交互模式和视觉权重决定时，读取相关例子，用其推理方法处理当前任务；现有自检和 reviewer 使用同一份资料进行校准。

不另建独立 Skill 或角色，不增加逐 unit 交付文件，不增加用户确认步骤。收益假设是用可观察的真实对照弥补抽象规则与实际判断之间的空白，而不是期待再写一遍“成熟、简洁、现代”就改善。

## 对 GPT 意见的取舍

GPT 最后一条建议是把历史纠正做成案例驱动的设计校准资料，接入 change-design-author，按需加载，并进行小规模对照验证。这个方向与本地证据吻合，但建议作四处调整：

| 建议 | 本次判断 |
| --- | --- |
| 选 10～15 个历史案例 | 不以数量为目标。先覆盖少量不同的决策机制，重复案例合并；优先有前后文、画面和已核实改进结果的案例。未完成的修复只能作为反例，不能冒充正确答案。 |
| 接入 design-author | 只接这里会漏掉实施时的设计决定和快速开发，也不能校准已出现误判的 reviewer。资料放在现有共同入口，由当前负责 UI 判断的角色按需读取；不复制到每个 Skill，不额外加一轮审查。 |
| 停用按钮是低频危险操作，应弱化 | 有条件成立。feat-657 原始需求包含紧急停止，工作详情必须容易找到。要校准的是列表浏览与紧急处置的不同任务，不能总结为危险操作一律藏进深层菜单。 |
| 用某历史 unit 原始需求验证 | 若该 unit 的最终方案已放进案例资料，测试会泄漏答案。验证任务应留出，且控制可见仓库快照、历史文档和提示；同时允许有证据的多种合理设计。 |

GPT 第一条长回答中的完整参考库、多工具链、额外专业 reviewer、多方案评测可作未来备选，但目前没有必要一起引入。引用论文和社区案例的结论未经本轮逐项核验，不当作本仓改善效果的证据。

## 资料应该教什么

每类只保留：用户正在完成什么 → 原做法为什么看似合理 → 实际代价 → 改变了哪个设计决定 → 哪些条件下应采用其他做法。配一对真实画面或可复查的现有页面/源码位置；无法取得改后实物时明确证据缺口，不编造“正确效果”。截图仍遵循本仓本地产物政策，不把图片批量提交到 Git。

建议首批关注四类：

| 判断问题 | 历史依据 | 希望学会的取舍 |
| --- | --- | --- |
| 操作应占多大权重 | 657 停用；636 PA Configure 行 | 浏览列表以身份和比较为主；当前工作中的紧急停止保持直接可达。同一操作可因所在任务不同采用不同呈现，不重复堆放同义控件。 |
| 哪些文字值得保留 | 652 Feature 说明；583 Work 冗余标题 | 删除不帮助判断的重复文字；保留用途、当前实际值及重要后果。简洁不能以用户猜测为代价。 |
| 新能力如何融入现有产品 | 616 导航/配置双入口；589 原生轨迹 | 优先沿用已形成的使用路径；存在明确任务收益时才改变结构。复用的对象是交互和阅读方式，不只是颜色。 |
| 内容与状态怎样影响布局 | 584 五列任务；645 Toast | 从用户需要同时比较的信息和状态变化决定结构；临时反馈不应挤动待操作内容，视觉分组不能掩盖数据分页造成的假空。 |

不能把这张表再当一组自动验收禁令。重点是具体画面如何体现取舍，以及当前场景是否满足同样前提。已有产品本身也可能不合理，保持一致性不等于复制旧缺陷。

## 如何嵌入已有工作

沿用共同体验标准这一权威入口，只替换其中缺乏操作支撑的部分，链接案例索引。遇到对应设计决定时选择最相关的案例，不默认加载整月复盘或全部用户原话。判断结论留在现有 design、自检或 review 的原位置，不增加一个“案例学习报告”。

Full 设计阶段在作决定时使用；直接实施或 lite 的实现者在自检时使用；现有 reviewer 用其校准判断，但仍先独立观察受审页面，不能先拿作者的理由作为答案。快速开发的改进需在实际实施之前可达，不能只挂到事后 change-fast-close。

是否必须改各 Skill 的入口，要以实际引用链核验；当前 design-author、简化实施与 product reviewer 已引用共同标准，优先利用这些接线，不为表面覆盖重复写规则。

## 验证应小而有区分力

这次优化本身做一次有界对照试用，不给以后每个 unit 加评测流程。选一个未进入案例资料的前端任务，在相同基线、模型和输入下比较现有指导与加入资料的首稿；既查看首次设计的实际画面，也操作最关键的交互。被测上下文不得含该任务最终修复方案或标注答案。

比较其是否保留交互语义、整页信息主次与产品连续性，以及是否仍需要重做结构。记录额外读取和耗时，避免以大量上下文换取微小收益。若两组都好或结果不一致，如实记录有限或未证明收益，不靠反复试到成功放行。

一次试用只能筛掉明显无效/有害方案；后续真实 unit 中用户纠正整体方案的次数，才是长期效果线索。不能以自行打分或“案例已读取”替代用户实际负担下降。

## 外部参考的有限用途

已读取 [Impeccable 官方仓库说明](https://github.com/pbakaus/impeccable)。其提供设计指导、critique/distill 等命令，并区分产品背景与视觉方向。这里只借鉴以层级、清晰度和删减组织设计讨论的方向；未核完各命令实现，不声称已移植其方法，也不建议目前安装整套工具链。它是否比本仓方法更有效，仍需实际对照。

## 补充核验：案例对照的社区依据

2026-10-26，用户转来 GPT 对“哪个社区实践是给 Agent 案例对照”的修正回答。本节读取原始来源后补充。上一轮推荐是依据本仓失败机制提出的工作假设，并非从 Impeccable 得出的已验证方法；以下材料支持存在类似实践，不能补成对本仓效果的证明。

| 来源 | 核验结果与边界 |
| --- | --- |
| [Reddit 作者原帖](https://www.reddit.com/r/ClaudeAI/comments/1t24gan/few_months_of_frontenddesign_uiuxpromaxskill/) | 作者确实称自己保存被拒绝版本、被接受的设计 token、带已交付示例的品牌表达规则，并按调用注入相关子集。这是个人实践自述，主要讨论客户品牌与跨会话偏好保持；不能证明复杂产品的信息架构或交互设计变好。本轮未取得其完整实现或对照数据，也未独立确认转述中的精确发帖日期。 |
| [shibroUI 的 composition.md](https://github.com/sshibro/shibroui/blob/main/shibroui/references/composition.md) | 实际文件包含正反例和检查方式，例如 SU-121 比较多个同等强调的操作与明确主次的操作。它证明这种材料形式可实现；其示例主要是设计规则的教学对照，不等同于保存用户真实迭代史。 |
| [Anthropic 的 Skill 经验文章](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/) | 确实建议从反复失败中积累 Gotchas，同时建议按需读取参考文件、给模型保留适应具体场景的空间。文章未证明 UI 前后截图有效，也没有提出“5 条”这个数量。它为材料组织方式提供经验依据。 |

“shibroUI 网页有 129 组交互对照”本轮没有核实。其 [README](https://github.com/sshibro/shibroui) 将组件案例来源指向 [TypeUI configurator](https://www.typeui.sh/ui-foundations/configurator)，后者页面确实有 Bad/Good 切换；不把上游展示页直接算成 shibroUI 自有网站。当前 README 的规则编号已延伸到 SU-361，也不宜用转述数量描述当前仓库规模。

尤其要保留 [shibroUI 自己的评测记录](https://github.com/sshibro/shibroui/blob/main/evals/RESULTS.md)中的反证：首轮三个任务的平均通过率只由 96.1% 到 97.8%，平均用时由 155 秒到 373 秒；后来一次管理页对照中，新版工具检查更好，盲评 Agent 却偏好旧版。作者同时披露单次运行、自有工具评分等限制。本轮没有重跑这些实验；它们是作者报告。更关键的是，版本间同时改变规则、工具与工作方式，无法从中分离出案例对照的因果效果。

因此对建议只作收紧：先从本仓已有四类问题中选少量真实 Gotchas，给出具体情境、错误判断、改进依据、适用边界和观察办法；不再增加泛泛的“保持一致、突出主次”原则。数字检查适合对齐、遮挡等可测问题；信息组织是否合理仍需看完整页面并操作，不能用数值达标替代。材料继续放在已有共同指导旁按需读取，不把全部案例塞进每个 Skill，也不引入检索系统。新任务试用和后续纠正次数用于检验收益；没有收益就调整或撤回。

## 当时的建议范围

提出本建议时仅创建 unit、保存复盘与反馈索引并评估参考意见，没有修改 Skill 或产品。后续按用户要求直接完成的工作以 [事后设计](design.md) 为准；本建议中的验证设想不冒充实际执行记录。
