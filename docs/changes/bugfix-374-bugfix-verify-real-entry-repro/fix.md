# bugfix-374: change-impl-worker 缺"按用户原始症状真实入口复现"的验收要求,后端 bug 修复可被纯单测蒙混

## Relations

- Related: bugfix-373（本缺陷的暴露案例：PR #38 在 openai_compat 改错 provider,单测全绿但运行时缺陷仍在,merge 后才发现）

## 原始报告

> 现在复盘一下刚刚一开始为什么完全没解决问题就提PR了

> change-impl-worker 是负责干活的，首先你明确下 change-impl-worker/SKILL.md 是否已经明确了修复后，要按照 fix.md 写的用户原始问题复现一遍，有没有这个过程

## 现象 / 复现

bugfix-373 走 lite 流程:spec 现象/根因正确、orchestrator 派发包甚至点对了 provider 目录,但 worker 把 round-trip 修复改到了 `openai_compat`(运行时实际走 `anthropic`),配套单测在 openai_compat 上红转绿、全绿,worker 据此回报 DONE,orchestrator 核对退出标准(分支合并、文档回填、单测过)后 merge(PR #38)。事后做 e2e 复现,**用户报的"工具调用后整轮停下、无文字总结"依然存在**——根本没修好。

复盘追问"skill 是否要求修完按 fix.md 的用户原始症状复现一遍"时,核对 `change-impl-worker/SKILL.md`:

- §6.0 lite"验证"段只写"修前能复现的步骤 → 修后不复现,给证据"——既没锚定到 fix.md【现象/复现】里那个用户症状,也没要求真实入口/运行时复现,一个红转绿的单测即可交差。
- §3.1 测试策略表把后端 bug 修复定义成"补能复现该 bug 的用例"(一个测试),主动认定"单测复现"合规。
- §0 第 3 条"单测全绿不算完成 + 真实入口验证"的强要求,适用范围只写了**新功能**和前端,**后端 bug 修复不在其中**。

结论:worker 基本踩着字面合规,skill 从没强制它"打开真实产品、按用户报的症状跑一遍"。

## 根因

change-impl-worker 对"修复是否真的解决了用户问题"缺一道和新功能对等的硬验收:

- 新功能有"至少一个真实入口验证";前端有"真实浏览器验收";**唯独后端 bug 修复只停在"补个能复现的单测"**。
- 单测复现的是"worker 写的那段代码",不是"用户报的那个现象"。当 worker 改错了位置(错 provider / 错模块),它写在错误位置上的单测照样红转绿,绿测于是给出虚假完成信号。
- 跨层/集成型缺陷(本例:provider 选择 + 历史 round-trip)无法被单一模块的单测捕获,而 lite 流程跳过 reviewer,绿单测就成了唯一关卡。

**为什么这种错能进来**:把"复现 bug"等同于"写一个能复现的测试用例",而没要求"回到用户报告的真实入口跑一遍原始症状"。验收语言的松动,让"代码能跑"冒充了"用户问题解决"。

## 修复

只动 `change-impl-worker/SKILL.md` 两处(克制,不动 §3.1 测试策略表):

1. **§0 第 3 条**:把"真实入口验证"适用范围从"新功能"扩到"新功能 + 修复用户报告的运行时缺陷",并点明 bug 修复要证明"用户报的那个症状真的消失";末句补"单测复现的是你写的那段代码,不是用户报的那个现象"。

2. **§6.0 lite 验证段**:从含糊的"修前能复现的步骤"改成锚定"**按 fix.md【现象/复现】里那个用户原始症状**,在真实入口(浏览器/CLI/HTTP endpoint)走一遍",并明确"单测红转绿是补充,不能替代真实入口复现"。

## 验证

本 change 是流程文档修订,验证即对照改后文本能否堵住 bugfix-373 那个洞:

- 改后 §6.0 要求 worker 的"验证"段必须是"按 fix.md 现象段的用户症状 + 真实入口复现",bugfix-373 worker 当时填的"openai_compat 单测红转绿"在新口径下**不合格**——会被退回补真实入口复现,而真实入口复现会立刻暴露"改错 provider、运行时症状仍在"。
- 改后 §0 第 3 条把后端 bug 修复纳入"真实入口验证 + 单测全绿不算完成",orchestrator 核对退出标准时有了明确依据,不再能拿绿单测放行。
- 范围克制:未改 §3.1 测试策略表(用户判定其表述可保留),无其它流程连带改动。
