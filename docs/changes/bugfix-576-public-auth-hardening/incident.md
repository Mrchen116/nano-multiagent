# bugfix-576: 公网认证可用性与浏览器会话加固

## Relations

- Related: feat-572-public-im-protection、feat-447、feat-554、feat-561
- Current: [认证与公司准入](../../specs/im/auth-tenancy.md)
- 路径：Full bugfix；跨认证、请求串行边界与浏览器会话，需要独立的并发和会话回归矩阵。

## 原始报告

用户引用先前审计结果：

> P2 可被定向锁登录 10 次错误密码后，正确密码也被拒绝约 15 分钟。
> P2 全局锁放大请求延迟 5 个并发错误登录，让无关读取从约 1 毫秒延迟到约 1 秒。
> P2 浏览器保护不足 缺少 CSP、防嵌入策略和 HSTS；访问及刷新令牌均存 localStorage。未复现 XSS。

用户约束：

> OK，然后同时我不希望整个系统引入过多的复杂性。就我要希望它是一个商业公司合理的安全事件，并且不要引入过多的维护复杂性。

实施与交付授权：

> OK，你新建一个Unit开始做吧。然后提交PR等我审核。

## 已确认范围与解释

沿用会话中已确认的方向：缩小公司锁的关键区间、限制昂贵认证计算、改进来源与目标账号限流、补浏览器安全响应头、短期 access 仅驻留内存且 refresh 通过 HttpOnly Cookie 保存。复用持久会话轮换与撤销，不重建认证系统。

Agent 解读：只为这三个已有风险引入必要代码，不增加 Redis、分布式锁、验证码平台、设备指纹或外部风控服务。保留一个 IM worker 的生产模型。提交可审核 PR，未经用户授权不合并、不部署、不修改 Cloudflare 或真实账号。

## 现象与复现

基线 `e1a4fbffc1beec0f0ce8f7e5ec1d2d162abe150c` 的相关实现与原审计基线 `499e118a3` 相同。原审计在 2026-10-02 通过临时隔离数据库和真实应用入口复现：

1. 一个已注册账号收到 10 次错误密码后，正确密码也返回 429，Retry-After 约 898 秒；已有合法会话未被注销。
2. 5 个并发错误登录让无关 `/im/v1/auth/me` 从约 0.7ms 延迟至约 979ms。该数据是隔离环境观察，不是生产容量承诺，也不是服务崩溃证据。
3. 公网页面未发 CSP、防嵌入与 HSTS；前端 `im_auth_v1` 存 access/refresh。没有复现 XSS 或真实登录态点击劫持。

原始本地证据位于仓库未跟踪 `output/security-public-20261002/README.md`、`isolated-probes.json`、`reproduce-isolated.py`；不提交运行数据或依赖本地文件作为最终交付依据。本 unit 用长期回归与隔离真栈重新建立可审核证据。

## 影响范围

- 认证尝试可跨用户放大请求等待；网络较慢的 Gateway RPC 同样可能阻塞无关公司请求。
- 知道账号名即可暂时阻断该账号的新登录；不构成密码绕过或账号接管证据。
- 浏览器长效令牌可被同源脚本读取，缺少额外防护会放大未来注入漏洞的后果；不能据此宣称已有 XSS。
- 2026-10-03 已完成的 HTTP→HTTPS 308 重定向不在本次修复范围内；HSTS 仍需补齐。

## 根因分析

- `CompanyBoundary` 在来源限流前取得全局 `company_gate`，并持有至路由响应开始；它同时承担共享 SQLite 操作串行、成员撤销与数据提交边界，却把 bcrypt 和远端等待一起包住。粗粒度串行保证被不必要地扩大到慢操作。
- 登录在验证密码前按单独的账号失败桶拒绝所有来源。匿名失败与合法用户的验证机会没有区分，导致防猜解措施成为账号拒绝服务入口。
- 浏览器直接沿用了程序客户端的 JSON token pair，并将两枚令牌持久化到 localStorage；没有浏览器专用的会话运输边界及与之配套的 CSRF 策略。响应头也没有统一的生产策略。

## 修复方向与非目标

在现有 IM 内完成：认证预算与短关键区、来源/账号组合限制、可被撤销的 Gateway 等待、统一响应头、Cookie 刷新和内存 access。保留已有数据库、JWT 签名、机器身份及原生 API 使用方式，任何浏览器会话迁移影响在设计与交付中明确说明。

非目标：全站抗 DDoS、分布式风控、MFA/密码重置产品、公司 RBAC 重构、工具记录脱敏、修补未复现的 XSS、扩展浏览器兼容层、生产容量压测或生产部署。

## 验收要求

### Requirement: 慢认证与远端等待不阻塞无关用户

#### Scenario: 并发错误登录与正常读取
- **WHEN** 隔离 IM 有多个密码校验尚未结束，同时另一已登录成员读取本人状态或公司资源
- **THEN** 正常读取无需等这些密码校验结束；超出认证预算的新请求得到有界、可重试的拒绝，不形成无界队列。

#### Scenario: Gateway 等待与成员撤销
- **WHEN** 一次 Gateway 控制请求已经发出、结果尚未返回，其他成员读取数据或管理员停用请求发起者
- **THEN** 无关读取和停用不必等远端结果；停用完成后旧请求不得继续提交新的受保护 IM 副作用或向该用户返回受保护结果；已经派发的远端动作不被伪称撤回。
- **AND** 同一 Agent 的并发配置操作保留冲突/待确认语义，不出现锁顺序死锁。

### Requirement: 防猜解不能形成跨来源的长时间账号封禁

#### Scenario: 错误来源受限、合法来源仍可尝试
- **WHEN** 一个来源连续对目标账号输入错误密码
- **THEN** 该来源及其账号组合会受到有界限流；另一正常来源不因这些失败继承约 15 分钟的账号封禁，短暂计算/目标节流须有明确重试时间。

#### Scenario: 分散猜测与重试
- **WHEN** 多个来源持续针对同一账号尝试，或者单个来源切换账号大量认证
- **THEN** 目标账号和来源均受实际执行预算约束，未识别账号与错误凭据使用相同拒绝语义，拒绝请求不无限续期；正常登录后仍保留成员准入检查。

### Requirement: 浏览器会话不在可读持久存储中保存令牌

#### Scenario: 登录、刷新页面与多标签续期
- **WHEN** 用户注册或登录并刷新页面，或两个标签同时需要续期
- **THEN** 页面通过受保护 Cookie 恢复会话，长期令牌不出现在 JSON 响应、localStorage、sessionStorage 或 document.cookie 中；access 只留内存，续期不因正常多标签并发永久退出登录。

#### Scenario: 登出、停用与失败恢复
- **WHEN** 用户登出、管理员停用成员、旧 refresh 被重放，或刷新请求临时网络失败
- **THEN** 登出/停用/重放不恢复有效公司访问；临时失败可重试且不伪装成成功，不用旧的持久 access 绕过验证；登录深链、pending 页面与公司缓存清理继续有效。

#### Scenario: Cookie 不能被第三方站点驱动
- **WHEN** 非许可 Origin 或缺少浏览器请求标记的第三方请求尝试刷新、登出或种入浏览器会话
- **THEN** Cookie 不被用于授权该请求，也不会向其返回凭据或修改浏览器会话；程序客户端继续使用明确提供的令牌。

### Requirement: 浏览器保护集中且不破坏现有产品

#### Scenario: 页面加载与嵌入
- **WHEN** 用户通过 HTTPS 打开 IM
- **THEN** 响应包含适配实际静态资源、附件和 WebSocket 的 CSP、防嵌入策略及仅当前主机的 HSTS；第三方不能嵌入该页面，正常登录、聊天页、图片与实时连接保持可用。

#### Scenario: 单机开发与维护边界
- **WHEN** 开发者运行既有 loopback 开发流程或维护安全策略
- **THEN** 开发环境仍可运行，策略在一个明确位置维护；无需增加外部服务，不将生产安全开关变成任意来源信任或全局脚本执行许可。
