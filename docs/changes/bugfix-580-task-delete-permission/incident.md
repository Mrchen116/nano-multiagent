# bugfix-580：任务删除重复授权导致反复确认

> 快速开发，事后记录；实现与自动验证完成后提交 PR，用户实际验收尚未发生，unit 保持 active。

## 原始报告与决定

用户提供生产会话 `c_kuthz6vx`，质疑删除任务时反复要求确认。调查确认用户先后说“删了这个任务。”“对”“直接删！”，工具仍要求输入“删除 tg_8b375dee”。

用户后续原话：

> 我日，怎么这样设计，不符合一般的agent实现，权限允许了，工具还拦截。还有其他工具也这样吗

> 这是个bug，快速改掉，并提pr

采用范围：删除任务的用户授权由现有统一工具权限流程负责，移除任务工具执行链路里的第二套消息授权检查。身份、工具能力、资源访问、来源真实性、版本冲突及幂等回执规则保留；不改其他工具、权限模式或生产配置。

## 现象与复现

1. 用户要求删除已明确的任务及其子任务。
2. Agent 说明范围，用户用自然语言确认，例如“对”或“直接删！”。
3. 删除执行链路仍返回 `confirmation_required`，要求固定的“删除 + 标题/ID”句式。

期望：统一权限允许后执行已确定范围，用户无需复述内部 ID；统一权限拒绝仍阻止执行。

影响：任务删除被迫多轮确认，无数据损坏证据。生产实例最终在用户输入精确口令后完成删除。

## 根因分析

Gateway 另行要求当轮真人消息来源，全局会话进一步依赖本轮完整消费的 Inbox 消息。IM 再读取消息正文，用正则全文匹配删除句式；它没有使用统一权限裁决，也无法理解上一轮说明与简短确认之间的关系。

feat-572 的设计允许用户确认已说明的范围，但实现将授权收紧成了固定措辞；历史验收将长自然语言失败记录为 minor 限制后放行。

## 修复方向与验收标准

- 获准删除不再依赖固定用户措辞或本轮真人消息的存在，普通会话与全局会话一致。
- 统一权限拒绝时，删除请求不发送。
- 仅删除指定图或子树；失效 Agent 仍不能删除，过时 revision 被拒，重试返回相同回执。
- 保留真实来源记录，不伪造用户。
