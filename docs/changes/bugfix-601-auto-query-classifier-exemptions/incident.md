# bugfix-601: Nano Auto 查询与会话计划记录免分类审核

## 原始报告与授权

2026-10-14，用户在主会话明确要求：

> 让subagent按快修模式，把这个第一批纳入免classifier

用户附件截图中的建议原文：

> 直接免 classifier。纯查询或会话计划记录，现有权限/作用域检查保留。

截图“第一批”范围由主会话转交：`skill_manage list`；`task_graph list/get`；`schedule_list/history`；`workflow list/read`；`get_goal / todo_write`。

## 已确认边界

- 仅在 Auto 开启且使用默认 Nano 规则时新增豁免。Auto 关闭时原人工审批路径保持；DSH 规则不继承本批豁免。
- 只跳过分类模型调用，保留工具可见集合、确定性拒绝、作用域、ACL、参数与执行约束。`todo_write` 只记录会话计划，不因此启动任务。
- 相邻写入/调度/编排/目标生命周期动作，以及 Bash、公开消息发送继续按原路径审核。
- 不扩大第二批范围，不修改审核模型、推理预算、故障处理或系统提示词。
- 用户已授权实施和可审 PR，尚未亲自体验验收。本 unit 保持 active，不将授权修改记成验收通过。

## 现象与复现

当前默认 Auto 将上述查询与会话计划记录送入分类器。分类器无结论时，即使动作没有需要分类审核的写入或外发效果，也会阻断查询；同时增加模型调用和等待。

在基线 `290652ada2bf5fafbd4ac9f27a1514680ff78ca9` 上，新增的真实 DSH RuntimeClient 回归向 9 种目标调用注入拒绝型审核响应，观察到了 18 次分类请求，查询被阻断，零调用断言失败。

## 根因

Nano 的既有确定性允许路径只包含原 safeTools、聊天查询及特定内部通信等情形。本批复合工具的查询 action 和会话计划工具未进入该路径，因而落入通用模型审核；审核本身的技术故障会成为查询的额外依赖。

审核预算/协议故障是独立问题。本修复只消除本批动作对分类器的依赖，不宣称解决其它动作上的审核故障。

## 实施结果与验收标准

在 Auto 开启、`rules:nano`、工具原约束允许的情况下，9 种目标调用不发出分类请求且继续执行；下游拒绝仍优先，工具禁用仍不可执行。相邻写动作、DSH 规则和 Auto 关闭路径不获得新增豁免。实施与自动化证据见 [as-built design](design.md)，独立审查状态见 [code review](code-review.md)。
