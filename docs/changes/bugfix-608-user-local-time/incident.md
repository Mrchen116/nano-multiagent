## 已确认范围

用户选择快速开发。浏览器/iOS 自动读取系统时区，在打开、回前台和发消息时刷新；IM 保存账号最近报告的时区并同步 Gateway，离线渠道和 Heartbeat 使用已保存值。每条消息固定发生时刻及当时时区，之后不重写历史。没有手动时区配置需求，不扩展会议、发布或其他原生定时工具行为。

## 现象与目标

| 问题 | 修复前 | 修复后 |
|---|---|---|
| iOS Heartbeat 设置 | 用户需填写 timezone | 去掉输入框，小字“按你所在地时间” |
| 模型侧消息时间 | UTC/缺少用户本地时间 | 已知用户时区时展示带 offset 的本地时间 |
| 全局飞书 Inbox | 原始 provider 时间未接入，可能 `time:null` | 使用飞书原发生时间和已保存的 owner 时区 |
| Heartbeat 活跃时段 | 依赖手工 active_hours.timezone | 使用账号最新系统时区 |
| HEARTBEAT.md cron | 按 UTC 判断 | 按同一用户时区判断 |
| Heartbeat 唤醒 | 缺少本次当前时间 | 附带当前本地时间及 timezone |

例：飞书原时间戳对应 UTC 01:00，用户时区 Asia/Shanghai，Inbox 返回 `time:"2026-10-14T09:00:00+08:00"`；Web IM 单线程模型输入也看到这一当地时间，聊天正文保持用户原文。

## 根因

客户端没有自动报告时区的完整链路；服务端、Gateway 缺少持久账号时区及逐消息快照。飞书毫秒时间没有进入 Inbox 的时间字段；Heartbeat active hours 与文件 cron 使用不同的时间来源，唤醒没有提供当前时间。

独立代码审查另外发现前台同步不能只比较客户端旧缓存：另一设备可能已经改变账号时区。因此每次前台激活都报告，由服务端按权威旧值抑制无变化写入与广播。
