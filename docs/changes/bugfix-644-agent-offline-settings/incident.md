# bugfix-644: Agent 配置页与外部渠道统一离线展示和操作边界

状态：首文档已收口，待设计；尚未实施。2026-10-23。

采用 Full bugfix：问题覆盖配置展示、能力目录、多个页面分区、配置提交与外部渠道生命周期，且改变现行渠道离线写入契约，需要独立设计及离线／掉线／恢复回归矩阵。本轮只建立首文档，不修改 current specs 或产品实现。

## 原始报告

用户在 `https://im.nanoim.win/settings/agents/nano-product` 提供离线 Agent 配置页截图，并报告：

> 好像只要不在线，都是有这个错误显示的问题，这个是bug吧

附件引用：本会话 `codex-clipboard-e1f0be3f-6ef0-497f-89f4-0cf9e09f5c4e.png`；原始本机位置 `/var/folders/mf/fxm1x6xs7pbf34h6rnmvjz1c0000gn/T/codex-clipboard-e1f0be3f-6ef0-497f-89f4-0cf9e09f5c4e.png`。附件只作用户报告证据，不复制截图缓存进仓库；临时文件不保证长期存在。

截图中 Agent 显示离线，模型仍显示 `codexOAuth:gpt-6.1-sol`；推理强度区域却显示“此模型不提供可配置的推理设置”“该模型已不接受当前保存的推理强度。请先移除它再保存。”和“移除不可用的推理设置”按钮。

## 澄清记录与用户决定

用户原话，按对齐顺序保留：

> IM 服务 只存模型，不存推理强度就很奇怪，两者配对的吧，也应显示吧

> 我觉得不合理吧？无论是模型还是推理强度，你没法去获取那台机子上真实有的哪些模型、哪些强度。那你就应该不让用户去选啊，你提示他掉线了，选不了不就好了吗？不是说搞一个默认啊？那你搞一个默认，用户要是选了又保存了，你还要去等他下次恢复了之后再去更新吗？是这个意思吗？

> OK，这个确定了。那其他的配置项呢？其他一大堆的什么feature啊、工具啊。那些在离线的时候应该怎么处理？现在是怎么处理？

> 现状是保存还是不保存不重要，重要的是你应该从这个产品实际的理念来看，从整个产品来审视，到底应该离线的时候怎么个情况。

> OK，就按这个原则，整个 Agent 配置页和外部渠道一起统一。先建个 bugfix，把离线展示、禁用操作和恢复在线的行为写清楚。

Agent 解读及已确认结论：

- 产品目标是长期拥有并管理助手。电脑失联不应让助手身份、配置和已同步信息消失；用户仍应能看懂这个助手及其最后确认的配置。
- 离线时配置只读，不能把最后确认的信息当成实时能力，也不能因拿不到能力而判断配置无效或补入默认值。
- 当前 IM 实际同时保存模型和推理强度；此前“是否保存”的讨论是排查现状，不构成目标设计限制。展示所需信息由产品体验决定，不能以当前没有存储为由省略已确认过的配置展示。
- 范围扩大到整个 Agent 配置页及外部渠道，统一禁用修改与执行操作，不再为渠道保留离线新增变更、上线后应用的入口。
- 恢复连接后自动刷新、确认后开放操作；未提交草稿不自动保存或应用。

## 现象与复现

调查基线：main `8fa10d3445f42f95e0316afb97600c2b8a37f35b`。证据来自用户截图和当前源码／既有测试检查；本轮未操作生产节点、未在真实页面重新制造断线，也未声称已完成产品复现或修复验证。

### 用户报告路径

1. Agent 已选择模型并保存非空推理强度。
2. 所属节点离线，打开或刷新 Agent 配置页。
3. 模型名称仍在，但缺少推理能力信息触发“不支持已保存强度”的错误和移除按钮，保存也可能被此错误阻断。

期望：显示最后确认的模型和强度，说明电脑离线并禁用修改，不把“无法验证”显示为“无效”。

### 同类现状与需要覆盖的路径

- 离线重新打开：Features 目录为空时整个区域消失；工具／Skills 用保存的名字充当候选目录，不能完整表达实际能力，却仍可操作。
- 在线打开后掉线：状态事件更新在线角标，但已有能力控件没有统一只读处理；旧目录可能继续留在页面供用户操作。
- 专属指令、审批策略、群聊策略、心跳、名称、描述及 PA 专属设置缺少统一离线禁用条件；配置提交才暴露失败或待确认。
- 定时任务离线查询降级为空数组，页面可能显示“没有任务”，混淆“没有取得信息”和“确实为空”。插件、统计和提示词预览分别处理请求失败，未形成统一体验。
- 渠道已有最后已知状态展示，但新增、编辑、启停、删除仍可写入期望配置，恢复后应用；这是现行契约明确允许的行为，本 unit 经用户确认将其改变。

## 影响范围

### 纳入

- Web IM `/settings/agents/:agentId` 的桌面及移动布局，适用于个人助手、普通 Agent 与 Global Agent。
- 配置表单全部字段：身份展示、专属指令、审批策略、群聊策略、Features、模型与备用模型、推理强度、工具、Skills、心跳及工作区信息；PA 专属设置与联系人限制管理入口同样只读。
- 页内 Skills 统计、插件管理、心跳文件、定时任务、工作信息等分区的离线展示，以及其中修改配置或需要节点执行的操作。
- 外部渠道页及其新增／编辑向导、启用／停用／删除确认、重连与删除重试；覆盖当前支持的所有渠道，不只飞书。
- 支撑上述体验的读取、提交与恢复行为。禁止离线提交是实际操作边界，不能仅把按钮置灰而仍接收相同离线写入。

### 非目标

- 不改造聊天发送、任务接单、节点安装绑定、账号管理及独立模型服务页面；不新增离线任务队列或消息补投递。
- 不要求节点断连后停止本地任务或断开外部渠道，不改变节点自治。
- 不扩展为全节点文件同步、完整可选能力目录的离线编辑器，或向 IM 复制凭据与私密文件的通用同步系统。
- 不新增原生 iOS 配置界面或其视觉改版；共享接口行为变化的兼容影响由后续设计核对。
- 不执行生产重启、部署或删除旧配置／待处理操作。

用户风险是误判配置失效、误删设置、无法知道按钮是否可用、将未知误认为空、把失联误当作已停止。本轮没有证据证明已有配置损坏或用户已执行误删，不推断生产数据丢失。

## 根因分析（RCA）

### 直接原因与代码依据

1. [im-agent-config-api.ts](../../../src/IM/frontend/src/features/settings/agents/im-agent-config-api.ts) 的 `getAgentDetailState` 在能力请求失败时，用配置中的模型、skills、tools 生成降级数据，不保留“实时能力未取得”这一独立语义；`toCapabilitySnapshot` 将缺失 Features 转为空列表。降级数据混入正常能力目录路径。
2. [model-reasoning-field.tsx](../../../src/IM/frontend/src/features/settings/agents/model-reasoning-field.tsx) 的 `isStaleReasoningEffort` 把缺失 descriptor 与真实不支持都判成 stale；组件据此展示错误和移除按钮。它无法区分“已取得当前目录且不支持”与“离线、尚未取得目录”。
3. [agent-detail-page.tsx](../../../src/IM/frontend/src/features/settings/agents/agent-detail-page.tsx) 根据目录决定 Features 是否渲染，多数编辑项和保存入口不使用统一的在线可用性条件；[agent-status-ws-consumer.ts](../../../src/IM/frontend/src/features/settings/agents/agent-status-ws-consumer.ts) 的状态事件只更新 config 的在线标记，不在该路径刷新能力或重新确认操作条件。
4. [control.ts](../../../apps/im-server/src/control.ts) 的配置更新先记录候选 operation，再向 Gateway 请求应用；离线无结果时进入待确认。能力、预览、插件等读取需节点 RPC，定时任务读取失败则返回空数组。缺少统一区分最后确认值、当前不可达和真实空结果的产品语义。
5. [agent-channels-panel.tsx](../../../src/IM/frontend/src/features/settings/agents/agent-channels-panel.tsx) 已区分部分 last-known 状态，但编辑、启停、删除等操作仍可使用；[channels.ts](../../../apps/im-server/src/channels.ts) 先保存期望变更再尝试推送，新增／编辑／删除不以节点可达为前提。渠道离线可写与配置页面的节点确认路径并存。
6. [personal-agent-settings.tsx](../../../src/IM/frontend/src/features/personal-agent/personal-agent-settings.tsx) 和 [personal-agent-blocked-contacts.tsx](../../../src/IM/frontend/src/features/personal-agent/personal-agent-blocked-contacts.tsx) 在同一配置页内独立提交设置，目前没有接入页面离线只读状态。

### 为什么现有保护未覆盖

- [agent-edit.test.tsx](../../../src/IM/frontend/src/features/settings/agents/agent-edit.test.tsx) 的 `keeps the settings form usable when live capabilities are unavailable` 用缺失推理强度的配置，mock 能力 503 但 PATCH 成功，刻意保护“能力失败仍可编辑保存”的旧行为，未覆盖截图中非空强度的场景。
- [model-reasoning-field.test.tsx](../../../src/IM/frontend/src/features/settings/agents/model-reasoning-field.test.tsx) 保护真实不支持时的错误与清除流程，但未区分离线导致的 descriptor 缺失。
- [agent-channels-panel.test.tsx](../../../src/IM/frontend/src/features/settings/agents/agent-channels-panel.test.tsx) 明确测试离线期望变更进入 pending，符合旧渠道契约；本次不能只新增禁用按钮测试而继续保留相反的提交行为。
- 综合根因是配置、能力与运行信息缺少一致的时效和可操作性契约，各区域各自降级。没有调查最初引入 commit 或历史审查过程，不归责于某次提交或审查。

### 与 current 文档的关系

- [产品定位](../../product/vision.md) 要求稳定 Agent 身份、本地执行与节点自治；[Web IM 原则](../../product/web-im-principles.md) 要求操作前说明可用性、保留未完成输入、不猜测能力及区分配置与运行状态。本 unit 将这些原则落实为一致的页面体验。
- [agents-nodes.md](../../specs/im/agents-nodes.md) 当前要求 runtime 能力按需解析且不持久化目录。本 unit 要求跨页面重新打开仍能展示最后确认的信息；如何满足、哪些展示信息需要保留由 design 决定，不能用旧实现约束否定需求，也不要求持久化全部候选目录。
- 同一 current 文档明确允许外部渠道离线修改并自动应用，且定时任务离线读取可返回空列表。本 unit 分别改为“禁止新离线变更”及“未知不冒充空”，必须在实施完成后归并对应契约，当前不提前覆盖。

## 修复方向与验收标准

页面以“最后确认的信息仍可阅读，电脑失联期间不可修改配置或执行操作”为统一原则。离线含节点无法联系；状态尚未确认或相关实时能力加载失败时，同样不能据此开放依赖该信息的操作，但提示必须如实区分离线、加载中和获取失败。

### Requirement: 离线时仍能完整理解助手的最后确认配置

#### Scenario: R1 离线首次打开、刷新或换一个浏览器
- **GIVEN** 助手曾在线并成功取得展示所需信息，之后所属电脑离线
- **WHEN** 用户打开配置页、刷新页面，或在同账号另一浏览器打开
- **THEN** 助手身份和最后确认的配置仍可阅读；模型／强度成对展示，Features 开关、工具和 Skills 的配置含义可理解，不因失联整块消失
- **AND** 页面明确提示“所属电脑已离线，显示最后确认的信息，暂时无法修改配置或获取最新运行状态”，最后同步的节点信息可辨认其时间；不依赖当前标签页曾访问过
- **AND** 不要求展示完整可选目录，不补入未经确认的默认值，不报配置无效、不提供移除无效推理设置的动作。

#### Scenario: R2 继承值、默认发现与从未取得的信息
- **WHEN** 某配置跟随节点、采用默认发现，或某分区从未取得过节点信息
- **THEN** 页面能区分“已明确配置”“跟随节点／默认发现”和“暂时无法获取”，已有最后确认的实际值仅以最后确认信息展示
- **AND** 无法确定的强度、Feature 默认开关或 Skills 完整名单不凭空生成；明确保存的 Skills 允许／禁用规则不能被误读成完整能力列表
- **AND** 未取得任务、插件或统计信息显示不可获取，不显示“没有任务／没有插件／零次使用”；确实取得过的空结果可作为注明时效的历史空结果展示。

### Requirement: 离线时整个配置页和外部渠道统一只读

#### Scenario: R3 所有配置字段和页内变更入口禁用
- **WHEN** 所属电脑离线，用户浏览配置页各分区
- **THEN** 配置表单包括名称、描述、专属指令、策略、Features、工具、Skills、模型、备用、推理强度、心跳和 PA 专属设置均不可修改或保存
- **AND** 插件启停／卸载、定时任务删除、需要节点执行的预览或其他变更操作不可提交；已有预览和记录仍可阅读
- **AND** 页面切换、展开收起、搜索已加载内容、复制、查看已有工作记录及历史链接仍可使用；重新检查连接和重试读取不视为配置变更。

#### Scenario: R4 外部渠道不再接受新离线变更
- **WHEN** 用户在电脑离线时进入渠道页，包括尚无渠道、已有渠道、已有删除记录，或已打开向导／确认框的情况
- **THEN** 新增、编辑、启用、停用、删除、重连、删除重试均不可提交，操作点说明需恢复连接
- **AND** 不出现“离线保存成功，等待上线应用”的新操作，不新建待上线的配置或执行请求；相同请求即使来自尚未更新状态的页面，也不能在已知离线时被接收为新变更
- **AND** 已有渠道配置与非敏感摘要仍可看，凭据仍按既有保护方式展示，不因离线快照扩大明文暴露。

### Requirement: 失联不等于本地停止，历史状态不冒充实时结果

#### Scenario: R5 节点仍可能在本地运行
- **GIVEN** 最后确认时 Agent 在工作，或外部渠道为已连接／连接受限／失败
- **WHEN** IM 失去与节点的联系
- **THEN** 页面说明无法确认当前运行状态，将之前的运行、连接和诊断结果标为最后已知
- **AND** 不把断连解释为任务停止、渠道断开或权限失效；不把历史连接状态显示为实时“已连接”，也不因失联宣称“已停用”或“已删除”。

### Requirement: 编辑中掉线不丢草稿，也不产生离线提交

#### Scenario: R6 表单、渠道向导或确认框中途掉线
- **GIVEN** 用户在线时正在编辑，尚未提交
- **WHEN** 所属电脑离线
- **THEN** 已输入内容保留，界面能区分未保存草稿与最后确认配置，编辑和提交立即转为不可用；确认框不能绕过禁用
- **AND** 用户可取消／关闭确认框或主动放弃草稿；恢复在线不自动执行保存、启停、删除、重连或其他之前准备的动作
- **AND** 不要求跨刷新持久保存未提交草稿或渠道密钥；离开页面遵循既有未保存提醒，自动状态刷新不覆盖当前草稿。

### Requirement: 已提交操作与新离线请求严格区分

#### Scenario: R7 提交瞬间断连，结果尚未确认
- **GIVEN** 用户在线时已提交操作，随后连接断开，尚不能判断是否生效
- **WHEN** 页面失去结果确认能力
- **THEN** 保留该操作的“结果待确认”信息，不伪称成功、失败、回滚或从未提交，不允许重复提交同一动作
- **AND** 恢复后确认该已提交操作的实际结果；结果确认不等于自动提交未保存草稿。

#### Scenario: R8 旧版本或掉线前已接受的待应用操作
- **GIVEN** 已存在被系统接受但未完成的配置、渠道变更或渠道删除记录
- **WHEN** 用户离线打开页面或升级后首次查看
- **THEN** 仍能看到待处理事实与最后确认进展，不丢弃、隐藏或自动当成已完成；离线不能新增重试动作
- **AND** 恢复后这些已接受操作仍按原有恢复契约收敛并展示真实结果，不把禁止新离线提交错误实现为取消既有操作。

### Requirement: 恢复连接后先刷新确认，再恢复操作

#### Scenario: R9 在线标记先到，能力或配置尚未刷新
- **WHEN** 节点从离线恢复，页面已收到上线状态，但相关当前配置／能力／操作结果仍在获取
- **THEN** 页面自动刷新并显示正在更新，依赖未确认信息的操作保持禁用；不直接用掉线前目录开放选择
- **AND** 刷新成功后自动恢复对应操作，无需手动刷新整个页面；某个统计区读取失败不阻断已具备有效信息的其他区域。

#### Scenario: R10 恢复后目录变化、配置变化或读取失败
- **WHEN** 新目录不再支持原模型／强度／工具／Skill，或其他地方已修改配置
- **THEN** 保留用户草稿，明确显示真实不兼容或配置冲突；用户确认调整后手动提交，不默默替换、清空或覆盖新配置
- **WHEN** 节点显示在线，但相关信息读取失败
- **THEN** 展示具体获取失败及重试入口，保留最后确认内容与受影响操作的禁用；不误报节点离线或能力不支持。

#### Scenario: R11 恢复后的正常配置和渠道操作
- **WHEN** 当前信息已刷新且没有未确认操作，用户主动修改并提交
- **THEN** 模型、强度、Features、工具、Skills 和其他配置按在线规则校验、保存；渠道新增／编辑／启停／删除／重连／重试正常工作
- **AND** 仍区分配置已接收、节点已应用和实际运行／连接结果；恢复在线本身不意味着所有渠道已连接或所有任务已完成。

## 回归覆盖与交接

后续设计和验收须覆盖上述 R1–R11，至少交叉检查：离线直接进入与在线后掉线；有／无历史信息；有／无草稿；有／无已提交未确认操作；普通／Global／个人助手；桌面／移动布局；配置／Skills／插件／渠道分区。旧的“能力请求失败仍可保存”和“新渠道离线变更进入 pending”用例必须随目标契约调整，在线正常行为继续受保护。

本首文档定义用户体验和变更边界，不选择快照存储、接口形式或组件组织方式。下一阶段由 `change-design-author` 形成 design、前端 prototype、current spec delta 和实施里程碑，并进行 Gate 2；本轮无实现、测试通过或生产上线声明。
