>

- 解释以下三个边界后，用户回复“对的”：未触顶时满 3 步清零；触顶后独立机制实际唤醒可清零；内部责任同步、停止上下文和配置刷新不自行解除停推，恢复资格仍受任务状态及审批屏障约束。

## 现象与复现

存在 doing 责任时，Agent 可能每次只执行一两步便结束。宿主在 idle 后仍发现同一责任，又安排下一轮；原有故障和拒绝屏障不能拦截正常结束的重复空转。

本次 native fixture 基线运行已观察到自动续推超过 256 次，断言期望 256、实际 260。该证据证明缺少连续短跑限制，不证明每个短跑都无业务进展。

## 影响范围

Task 自动执行的绑定主会话。连续重复消耗模型、事件存储与运行资源；上限按同一个产品 Agent 统计，不以单项任务为单位，不改 Task 业务状态。

## 根因分析（RCA）

`TaskExecutionDriver.poke()` 只核对责任、故障、审批与 native inbox 等现有条件，没有统计已经完成的自动续推长度。原 current spec 明确不增加 Task 专属轮数上限；本次用户决定为连续短跑增加一个窄例外。

## 修复方向

- 自动续推的一轮少于 3 个主会话原生执行步，连续计数加一；达到 256 后不再投递宿主自动续推。
- 未触顶时，同一 Agent 连续执行达到 3 步清零；短的外部执行不清零。
- 触顶后，独立输入实际进入执行时解除停推并清零；不要求这次执行满 3 步。
- 不修改任务状态、不制造等待安排、不越过用户停止或已有审批屏障。
