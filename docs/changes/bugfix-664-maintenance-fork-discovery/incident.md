# 系统维护 fork 与模型管理目录分离

## 原始需求

> 那就按这个源头方案改，系统维护 fork 不进 list_agents，历史和轨迹保留可回溯

> 快修模式

用户已经确认源头方案与保留证据的要求。本 unit 按快速开发实施；尚未把实现后的用户验收记为完成。

## 现象与根因

长期 E 的直接子会话目录包含 2513 个已结束的知识维护 fork。模型为了盘点自己管理的执行者调用 `list_agents(scope="descendants")` 时，DSH 先递归读取这些历史分支，再在工具返回时过滤 one-shot。历史积累本身正常，问题是系统维护运行进入了模型的管理目录。

Nano 的知识维护通过 `subagents.start('fork')` 启动。该委派服务在原生 provider 创建会话后显式追加 `subagent/catalog`，将宿主维护与模型委派混在同一目录。原生 fork 后端、持久化与目录发布是独立公开能力，维护不需要这一步发布。

## 范围与退出标准

- 新启动的 Memory、Skill、combined 与 F4 维护不进入原生子 Agent 管理目录；原版 `list_agents` 保持不变。
- 复用原生 fork 后端的上下文继承、策略、预算、取消、结果和释放，不新增执行循环或修改 DSH。
- 维护的用途、父会话、起止范围、状态及会话 ID 保存在原有轨迹索引；释放和重启后可查看继承历史、维护输入、工具调用/结果与结束事实，读取不恢复执行。
- 保留冻结的 system prompt、完整工具定义和执行白名单，保留失败、取消和维护周期规则。
- 本次只修正未来创建路径，不重写存量目录或删除旧历史；不部署、重启或发布生产服务。

## 验证

原始新断言在旧实现上复现：维护会话 ID 出现在父会话 `subagent/catalog`。实现后相关知识维护和轨迹回归通过；最终命令与独立审查见 `design.md`、`code-review.md`。用户实际验收仍待确认，unit 保留 active。
