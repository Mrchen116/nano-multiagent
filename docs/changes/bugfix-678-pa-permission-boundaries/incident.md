## 现象与证据

本次只读核对基线：`2b2c178616a62bf855bcabd3e642e5d229258a0f`，本地 main 与 fetch 后 origin/main 一致，开始时工作区干净。本轮没有运行故障注入或真实模型复现。

- [现行 PA 规范](../../specs/gateway/personal-agent.md)“已交办事项中的权限阻塞”已经要求主 Agent 核对原因、原始要求和限制，继续允许的独立部分；不因委派和跨轮次重新索要已有授权。该方向不是本 unit 新增。
- [审核实现](../../../packages/dsh-integration/src/policy/approval.ts)中，普通 Global 和子 Agent 使用 `return_to_agent`；有效拒绝返回 `NanoApprovalDenied / classifier_block`，审核异常在相应失败分流下也可返回 `NanoApprovalDenied / classifier_unavailable`。schedule/heartbeat 有自身无人值守分流，不能把所有路径概括为同一种处理。
- [Task 执行驱动](../../../packages/dsh-integration/src/task-execution.ts)监听工具结果，仅按 `NanoApprovalDenied` 名称或人工审批未获准记录进入 `denied()`；未能定位具体 Task 的普通工具会将当前 doing/repair 批次加入内部限制。
- 同文件 `runnable()` 排除这些任务；`poke()` 据此决定空闲后是否自动发起后续轮次。该限制没有直接结束当前 Agent 轮次，也没有把持久任务状态改成 paused。
- 内部限制可因任务版本改变或同动作成功等条件解除；审核服务恢复本身不是清除这份记录的条件。故障是否在实际运行中导致停滞还取决于后续 Agent 行为和其他唤醒，不能据静态代码声称每次故障都停工。

## 影响范围与根因

受到影响的是绑定 Task 执行驱动的会话后续自动续跑。当前机制为避免反复尝试被拒动作，将一次工具结果映射为任务级内部续跑限制；无法归属具体任务时又扩大到当前批次。任务目标是否仍可通过合法替代路径完成，本应由 Agent 结合上下文判断，调度器却提前作出任务级推断。

技术故障与真实拒绝共用错误名称是一个触发问题，但仅拆分名称仍保留用户已经否定的职责耦合。源码不能证明生产发生频率、模型自主更新任务状态的稳定性或最初引入该行为的提交；这些尚未实测。

## 已确认的修复方向

取消依据单次审批拒绝建立隐藏 Task 自动续跑限制的机制。审核仍约束具体动作并将准确原因交回执行 Agent；主 Agent 决定合法替代路径、继续独立工作或显式更新任务状态。不能把解除调度限制解释为允许执行原本被拒绝的动作。

### Requirement: 工具拒绝不代替 Agent 决定任务去留

#### Scenario: 被拒步骤存在合法替代路径
- **GIVEN** 用户已经授权目标，某个工具步骤被拒绝，但仍有获准路径或独立工作可做
- **WHEN** Agent 收到具体拒绝原因
- **THEN** Agent 可以继续推进这些工作，不因该拒绝被额外施加用户和 Agent 都不可通过正常 Task 状态理解的续跑限制
- **AND** 原权限规则继续生效，不允许换工具绕过同一被禁止的影响。

#### Scenario: Agent 判断任务需要暂停
- **WHEN** Agent 核对阻塞后判断当前任务无法继续，需要暂停
- **THEN** 通过正常任务状态表达暂停及原因，用户能够查看；调度依据明确状态处理后续推进，而不是从某一次工具拒绝猜测整个任务应停止。

#### Scenario: 审核临时故障
- **WHEN** 一次审核因服务故障未取得有效判定
- **THEN** Agent 获得准确故障原因，该结果不被另行转化为隐藏的任务暂停或整批续跑限制
- **AND** 是否等待、安排复查或请求必要帮助由 Agent 按既有任务规则处理；原审核与执行约束继续生效。

### Requirement: 长任务中的审核保持原授权与后续限制的语义

#### Scenario: 长对话或委派后的审核
- **WHEN** 已授权任务经历长对话或委派后继续执行
- **THEN** 审核证据保留原始授权及理解它所需的对话背景、来源和先后顺序；后续限制与撤回仍适用，不能将父 Agent 的转述升级为新的主人授权。

#### Scenario: 审核会话重建
- **WHEN** 审核会话因上下文预算等原因重建
- **THEN** 按实际可见历史补送需要保留的原始指令，不因旧会话曾收到它们就假定新会话仍可见。

#### Scenario: 原始指令无法完整提供
- **WHEN** 保留层因预算或来源不完整而无法提供整条指令
- **THEN** 明确说明证据缺失，不将残缺指令当作完整授权；保留层不通过截掉限制来留下半条许可。

### Requirement: 输入审核只影响当前消息

#### Scenario: 同群合法交办不受另一条拒绝影响
- **GIVEN** 群内主人交办已准入，另一条外部消息待审
- **WHEN** 外部消息被拒绝
- **THEN** 只结算被拒消息，原合法交办仍可读取和处理；重启不重复审核已拒消息，聊天来源权限不被撤销。

#### Scenario: 审核故障对 Agent 可见且不阻断其他输入
- **WHEN** 一条外部消息因超时、模型不可用或输入超限未取得有效判定
- **THEN** 该消息保持未准入，主 PA 收到具体故障和消息引用，决定是否重试、继续其他工作及必要时通知主人；系统不将故障当安全拒绝，不透明地自动重试，其他已准入消息仍可正常读取。

### Requirement: 输入审核具有确定范围的原始对话背景

#### Scenario: 连续对话与明确回复
- **WHEN** 审核当前外部消息
- **THEN** 按阶段设计提供当前消息、此前最近 20 条原始消息及窗口外的直接回复目标，保留身份与顺序，不通过另一模型筛选相关性。

#### Scenario: 恢复与长度限制
- **WHEN** 恢复审核或证据超出预算
- **THEN** 历史截止于待审消息的位置，不混入后来的消息；历史缺失明确标记，不将半条历史伪称完整，当前待审消息不能完整提供时明确报审核失败。

### Requirement: 主 PA 完成安全提醒和原聊天拒绝

#### Scenario: 输入审核发现风险
- **WHEN** 输入审核拒绝请求或标记需要处置的可疑行为
- **THEN** 系统将实际判定、来源和所需处置交给主 PA；PA 通过正常发送工具先提醒主人，再到原聊天拒绝，后端不直接以 PA 身份发送模板消息。
- **AND** 被标记内容仅作为风险证据，不作为可执行的新请求；对外拒绝仍受披露审核，只有真实发送回执才能表述为已送达，恢复时不重复已经确认发送的消息。

用户原话：

> 披露计数器：有并发一致性的目的，但目前实现与上下文机制不配套。根本没用，干掉！

**现状核查：** `apps/im-server/src/personal-actions.ts` 在受控动作提交时递增同一 PA 的 `disclosure_revision`，并在校验中将该版本变化与权限策略版本变化一并返回 `proposal_requires_review`。当前披露审核的历史依据来自 PA 有效上下文，不再通过该计数器自动补入其他动作的实际披露内容；参见 [bugfix-640 设计](../archive/bugfix-640-pa-disclosure-context/design.md)。计数器使其他提交令旧审核失效，但不保证重审时获得新增披露的实际内容。

**Agent 解读与已确认范围：** 删除以同一 PA 的全局披露次数为依据使待发审核失效的机制，不另建替代计数器、全局发送串行队列或累计披露账本。其他动作提交本身不再要求本次重审。外发仍独立核对完整动作与 PA 当前有效上下文，保留动作/审核证据绑定、实际权限及受众检查、生命周期和重复提交约束；不宣称并行审核总能看到其他刚提交动作的内容。

会影响 PA 决策的新消息、接收对象、内容或权限变化，应拦截并明确告知 PA 未发送及变化原因，由 PA 重新决定后续动作，不能被归入计数器删除后一并放行。具体错误分类与接线在完整设计收口时落实。60 秒许可期限是否删除尚未获用户明确确认，本次决定不包含它。

### Requirement: 其他披露提交不使当前审核自动失效

#### Scenario: 两条既定消息先后提交
- **GIVEN** 同一 PA 的两条待发消息各自经过独立审核
- **WHEN** 第一条先提交，第二条的内容、接收者、权限及其他实际发送条件未变
- **THEN** 第二条不因全局披露计数变化而失败或被迫重审；每条消息仍须满足自身的审核与提交条件。

#### Scenario: 决策条件变化仍交回 PA
- **WHEN** 待发动作遇到需要处理的新消息，或内容、受众、权限等实际条件变化
- **THEN** 旧动作不直接发送；向 PA 明确返回未发送及变化原因，由 PA 重新判断，不把删除披露计数器解释为取消相关检查。
