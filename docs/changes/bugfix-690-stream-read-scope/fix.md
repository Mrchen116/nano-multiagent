# bugfix-690 流式片段触发全量读取

## 原始报告

> 修复节点在每个流式文本片段上枚举会话绑定并重读旧输入。100 个会话、单聊天私聊 500 条历史输入，100 个片段读出约 2 万条绑定和 5 万条旧输入。入口在 packages/personal-assistant/src/{single-thread,global-agent,store}.ts。用真实流式通知验证读取规模下降，私聊片段顺序、合并展示、最终消息、群聊原有展示和发送前重验、断线恢复、Global 与单聊隔离不变。当前 main 上做，勿夹带或破坏 PR #438 的 Inbox 重启改动。

用户指定快速修复，交付到独立可审 PR。验证由执行者完成。

## 根因与原有行为

refactor-581 接入 DSH 后，单聊和 Global 监听同一个通知源。两者都先枚举节点绑定才判断是否处理通知。单聊复用整段输入历史来识别群聊，导致每次检查均加载并解析所有旧正文。perf-666 合并了等待 ACK 的文本，但合批发生在上述检查之后，且每批仍会读取整个会话来筛选本轮输入。

群草稿必须留待发送前重验。私聊依赖有序合批和持久发送状态恢复，Global 的工作过程只经显式发送进入聊天。此次修复遵循现有[路由与交付契约](../../specs/gateway/routing-delivery.md)和 [Global 契约](../../specs/gateway/global-agent.md)。

## 真实通知复现与对照

在 Node 24.22.1 下，为每次运行创建独立临时目录、SQLite 文件和本地 HTTP 端口。注册 100 条绑定，给一条私聊预置 500 条已经确认完成的旧输入，再通过 SingleThread.receive 提交一条新消息。受控 Anthropic SSE 端点每隔约 4 ms 发出一个四字符片段，编号从 000 到 099。锁定版本 DSH 子进程产生真实 session.stream 通知，经过 stdio 后交给同时注册的 SingleThread 和 GlobalAgent。

计数点为两个产品监听器同步处理 text-delta 期间 SQLite get/all 返回的行。绑定行按 binding 列计，历史输入按预置 input_id 计。另在 relay ACK 替身记录同一条消息的增量与最终正文。

| 100 个文本片段 | main 7e79e9b79 | 修复 b79f0d882 |
|---|---:|---:|
| SQLite 读取调用 | 300 | 200 |
| 返回绑定行 | 20,000 | 100 |
| 返回预置旧输入行 | 50,000 | 0 |
| 收到的增量批次 | 9 | 12 |
| 增量按序拼接等于原文 | 是 | 是 |
| 最终消息数 / 正文长度 | 1 / 400 | 1 / 400 |

批次数取决于定时器调度。计数不含异步批次发送、开始与结束对账，也不能换算成整轮耗时。修复后另查 SQLite 查询计划，绑定、群输入存在性、本轮输入各自走 sessions 主键、inputs_group_session、inputs_session_turn 索引。

## 修复与验证

实现及回滚见 [as-built design](design.md)。6 个 PA 测试文件覆盖单聊、群聊、模型回退和 ACK 丢失恢复、显式发送、Global、工作恢复和存储。慢 ACK 测试在私聊积压期间穿插一条 Global 片段，断言最终发布序列。群聊测试分别检查静默哨兵、扣留旧草稿及更正后发布。真实 DSH 对照只覆盖私聊，使用受控 provider 和 relay，未运行真实模型、浏览器或生产环境。上述结果为工程验证。
