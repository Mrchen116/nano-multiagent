# bugfix-697: As-built Design

> 本文在实现后形成，描述实际代码与验证；用户实际验收仍待完成。

## 最终结构

- `composer-draft-store.ts`：以 `uploads` 保存有稳定 id 的本地 File 和 queued/uploading/ready/failed 状态，属于原会话草稿；`pending` 继续承担可发送的服务端附件引用。
- `message-pane.tsx`：一次加入整批可见卡片，批内顺序上传，按卡片顺序构造 ready 引用；跨批完成顺序不改变发送顺序。本地文件身份参与草稿版本和空草稿判定，避免旧发送恢复覆盖新粘贴。移除立即生效，队列跳过已移除项，进行中的请求结果不能复活卡片。沿用订阅和撤权写入保护，让离开/重新进入聊天后的结果仍归属原会话。
- `composer-attachment-card.tsx`：使用本地 object URL 展示缩略图，组件卸载时释放；重试和完成保留同一卡片和 URL。蒙层/加载圈、可放大预览、独立移除按钮、卡片下方简短错误与重试/倒计时（详细原因保留 title 和可访问标签）；普通文件继续提供打开/下载动作。
- `chat-workspace-page.tsx`：去掉上传错误的全局 toast 通路，保留发送/权限错误；替换草稿时包含上传项冲突判断。
- `send-attempt-store.ts`：持久发送快照只保留上传后的引用，不保存 File 或临时预览信息；成功后只清除本次提交的 ready 卡片，文字单独发送继续保留附件。
- `media.ts`：对声明为已支持图片类型的请求，按已有签名检测确定实际编码；可识别且与声明不同时，以真实 MIME 和对应文件名后缀保存，未知内容继续 415。大小、容量、权限、并发等边界不变。
- `use-attachment-upload.ts`：读取现有结构化 HTTP 错误，区分未知图片内容和不支持的 MIME。

## 关键决定

- 上传前可见性只依赖本地 File，不依赖网络或服务端图片下载。
- 本地上传状态不进入消息流；发送仍等待当前草稿所有上传完成，失败不得静默忽略。保留明确的仅发送文字操作。
- 继续顺序上传同一批文件，不为预览新增服务端协议、并发调度器或持久草稿平台。
- 真实图片格式识别由服务端现有签名解析统一承担，不在多个客户端重复嗅探。
- 新增图片兼容不放宽为任意 MIME 或接受非图片内容，不进行转码。

## 失败、风险与回滚

移除上传中卡片不等待网络结束，晚到结果不加入草稿；已经完成但未被采用的服务端资源仍按原有上传资源语义处理。切换会话只恢复该会话自己的草稿，页面刷新不承诺恢复未发送本地 File。编码识别沿用原有签名能力，不声称进行完整图片解码。可回滚本 unit 的提交；无数据迁移。

## 与初始意图的差异

增加了用户后续报告触发的真实编码识别修复。未采用对话中曾提出、随后明确收回的消息流排队发送建议。
