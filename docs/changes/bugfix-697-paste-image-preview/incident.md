## 现象与复现

旧 `handleAdd` 等待每个请求完成才加入 pending 或 failed；上传中仅记录计数，草稿没有对应卡片。成功与失败项分组渲染，失败项退化为狭窄文档 chip，同时触发全局 toast。

用户最后附上的文件路径后缀是 PNG，但原始字节以 `ff d8 ff e0` 开始，为 JPEG。对隔离 IM 以 `image/png` 上传这份原文件，返回 415 `image content does not match content type`。另一个真实 PNG 附件在同一服务上传返回 201。以上证明本次提供的附件编码与声明不一致；原线上那次请求的原始字节/响应未取得，不能据此断言其数据完全相同或判断是哪一环改写了文件名。

## 根因

1. 草稿模型只保留完成后的附件或失败项，没有上传中的可见文件身份。
2. 失败反馈分组与窄 chip 排版放大了状态切换和长文案布局问题。
3. 服务端虽然支持 PNG，但要求声明 MIME 与探测到的图像签名严格相等；可识别的 JPEG 在标为 PNG 时被拒绝。前端把所有 415 归为不支持格式，掩盖了具体原因。
