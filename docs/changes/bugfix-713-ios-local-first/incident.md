- [`docs/specs/im/conversations-messages.md`](../../specs/im/conversations-messages.md)：聊天偏好与已读状态属于当前用户，已读不消费他人未读，同时到达且尚未展示的新消息仍保持未读。

## 现象与复现

环境：原生 iPhone 客户端（`src/IM/ios`）与 IM 服务端（`apps/im-server`）。下面是复现步骤；“实际”按当前实现确定，尚未在设备上逐条做运行时复现（见「原始报告」的证据边界）。

### A. 冷启动首绘要等整条网络链跑完

1. 杀掉 App 后重新打开（弱网更容易观察）。
2. 看首屏，再进入聊天页，直到列表出现。

期望：上次看到的内容先出现，新内容与未读在后台校正。

实际：先是整屏“恢复登录…”，之后聊天页只有“正在加载聊天…”，列表为空直到会话快照请求返回。启动链是串行的：恢复登录（一次续期往返）→ 账号状态 → 会话列表，列表首绘绑在第三段的返回之后。本地没有任何会话或消息快照可以先画。

### B. 断网冷启动只剩登录页

1. 打开飞行模式后冷启动。

期望：有有效会话时先显示本地内容并标明当前未连接。

实际：恢复登录失败被当成“没有有效用户”，界面停在登录页（密码表单）加一条错误提示；本地既没有列表也没有消息，用户被要求重新登录。这一次往返失败并不能证明会话已失效。

### C. 进入会话后未读不清零 / 会复活

1. 让别人给某会话发 2 条消息，回列表看到未读 2。
2. 点进会话，看到最新消息后向上翻历史。
3. 返回列表观察徽标。

期望：读完即清零，往上翻历史不改变未读。

实际：清零不可靠，往上翻历史后未读可能重新出现甚至变大。

当前的确定性机制（静态核对）：客户端只有“某一行进入视口”这一种读上报，并且对**任意**可见行上报该行的消息 id——包括往上翻到的旧消息；服务端 `/read` 无条件把读边界写成这条消息，并按“该消息之后的消息数”全量重算未读数。于是滚动历史等于把读边界往回推，未读随之复活。列表又会在每个 WS 事件后短时间内全量重读服务端列表并整体替换本地数组，服务端的非单调结果立刻覆盖界面。此外上报要求“当前仍停留在该会话”，离开后不再补报，失败被静默吞掉——因此“确实读完了”也不保证被服务端记住。没有任何读事件广播，另一台设备因此不会收敛。

### D. 发送期间输入区锁死、没有气泡

1. 在弱网、断网或服务超时（约 30 秒）下发送一条消息。
2. 尝试继续输入，并观察消息是否出现在时间线。

期望：消息立刻以自己的气泡出现并标出“发送中”；发送过程中仍能继续编辑；失败或未确认可在气泡上重试。

实际：点发送后输入框变为不可编辑，发送按钮与附件菜单同时不可用；正文与附件仍留在输入区，气泡要等响应回来才出现在时间线；失败只在顶部出现“等待核对发送结果 / 重试核对”，输入区依旧不可编辑，直到用户显式重试成功。

### E. 被丢弃的 Agent 占位消息在列表留下幽灵未读与空白预览

1. 让一个 Agent 走一次“先建运行中占位、再判定无需回复/失败/已由显式回复交付”的轮次（PA 单线程的 NO_REPLY、heartbeat 与自动轮次、模型失败、显式回复优先都走这条路径）。
2. 回到会话列表，观察该会话的未读数、预览与时间。

期望（既有契约 `gateway-relay.md`）：丢弃后会话投影恢复到该消息出现前。

实际：会话里的气泡按丢弃事件移除了，但列表的未读数、预览和时间仍是那条已不存在消息留下的值：未读被多算 1，预览可能显示被丢弃的正文，也可能是空字符串。原因是创建占位消息时就已经写了三项投影，丢弃时只删除了消息行。会话投影在 `last_message_at` 找不到对应消息时会回落到存储的预览字段，因此这条幽灵状态不会被自愈。

## 影响范围

- 受影响用户：所有使用原生 iOS 客户端的用户。A/B 每次冷启动都会遇到；C 每次点开会话都可能遇到；D 在弱网、断网或后台切换时必现；E 在 PA 与 Agent 聊天的自动轮次中反复发生。
- 严重度：属于第一眼体验与可信度问题，不涉及内容损坏。消息不丢——发送尝试在真正发送前已持久化，服务端按幂等键返回原消息，重试不会产生第二条；但未读与预览的错误会随下一次全量刷新继续存在，用户无法自行纠正。
- 契约影响：E 直接违反 `gateway-relay.md` 的既有 Requirement；C 与 `conversations-messages.md` 的已读语义需要一起看——修复不能让“尚未展示的新消息”被提前清零。
- 安全边界：本轮不新增越权面；但 A/B 引入本地快照后，必须守住既有“退出、切换服务/账号、被移出后不展示旧会话与受保护内容”的边界。

## 根因分析（RCA）

这些症状不是五个互不相关的 bug，而是同一个结构性缺口加两处契约缺口。

**R1：客户端没有“可先行、可对账”的本地状态层，界面状态直接等于某次网络往返的结果。**
启动时整屏只有一个“恢复登录…”，直到续期返回；聊天页的列表首绘只在会话快照 reconcile 末尾置真，因此被绑在“续期 → 账号状态 → 会话列表”这条串行链的最后一段。断网时恢复登录失败被当成没有有效会话，直接落到登录页。发送侧是同一模式的另一面：待发状态被直接当作“输入区可编辑/可发送”的开关。本地唯一持久化的聊天状态是“未确认发送尝试”，没有任何会话或消息快照，HTTP 层也明确禁用了 URL 缓存。所以“先画上次内容”在结构上不可能发生——这解释了 A、B、D 的空白、锁死和必须等待。

**R2：已读被表达成“行的可见性副作用”，而不是一次显式、可重试、单调的用户动作。**
客户端只在某行进入视口时上报，且对任意行（含历史行）上报；上报需要“仍停留在该会话”，离开后不再补报，失败静默吞掉。读完成这件事既没有明确触发点，也没有重试。服务端把读边界当普通字段无条件写回并全量重算，任何晚到或过期的上报都能把边界推回去，未读随之变大——这是“复活”的直接机制。同时没有读事件广播，多端不会收敛；列表又依赖 WS 触发的全量重读，服务端的旧值会立刻覆盖刚清零的显示。这解释了 C。

**R3：`message_discarded` 只实现了契约的一半。**
Gateway 先为回复建运行中占位消息，这条写入同时改了 preview 与 `last_message_at`，并给除发送者外的参与者未读加一；判定丢弃时只删除消息行并广播事件，既没有恢复投影，也没有把这些写入放进同一事务。契约明确要求同事务恢复三项投影。这条路径在真实使用中不罕见：NO_REPLY、heartbeat 与自动轮次、模型失败、显式回复优先都会发出丢弃。这解释了 E。

**为什么这种错能进来**：三个缺口都没有“用户旅程”级的回归基线。iOS 侧没有可先行的本地状态，“从冷启动、断网看列表”从未被当作验收对象；已读在实现里只是可见性副作用，没有“读完必须为零且只能往前走”的用例；丢弃的恢复半边只写在 spec 里，现有服务端测试覆盖不到它（删除气泡与幂等这一半也没有对应回归断言）。契约和用例都只覆盖了成功路径上看起来正确的部分，没有覆盖用户实际等待的那段时间。

**证据位置（均按当前 `main` 逐条静态核对）**：iOS 启动门控与聊天恢复链路的串行顺序、聊天列表首绘标志的置位点、本地仅持久化未确认发送尝试；iOS 读上报的唯一调用点与它的会话选中条件；服务端读端点对读边界的无条件写回与全量重算、会话投影对 `last_message_at` 的依赖；Gateway 流式丢弃分支只删除消息行；PA 单线程发出丢弃的四种原因。

**仍未知（本文不声称已证实）**：真实网络的往返耗时分布、各症状的实际发生频率、读上报被丢弃的具体比例，都需要运行时观测才能定量；本 unit 不基于这些数字做结论。

## 范围与非目标

### 本轮范围（用户决定先做的第①步，5 项）

1. 会话列表本地快照 + 启动首绘：先用上次的本地快照渲染列表，网络只在后台校正。
2. 输入区不再因待发状态只读；“能否再发”由发送守卫控制，而不是锁住编辑。
3. 发送乐观气泡：本地 id 加发送中/未确认状态，失败在气泡上重试。
4. 已读明确触发（不依赖行进入视口）+ 客户端与服务端读边界单调（未读清零后不被过期快照复活）。
5. `message_discarded` 恢复 `unread_count` / preview / `last_message_at`，对齐 `gateway-relay.md`。

### 非目标

- 不做 APNs、系统角标、远程推送、后台任务与深链（第②步）。
- 不做 `/sync` 增量与分页、会话投影去 N+1、keepAlive、ETag、事件回放上限（第③步）。
- 不做本地 delta 追加、Markdown 解析开销、图片缓存、上传进度、消息搜索、分页锚定、轮询页。
- 不改变重发与重试的幂等行为；不允许未确认草稿自动重发。
- 不做离线发送队列：离线时不保证消息能发出，只保证不丢用户已写下的内容、不假装已发送。
- 不新增跨端已读事件或已送达回执：多端只要求已读显示不倒退，不要求实时同步。
- 不重写聊天页信息架构与视觉，不改 Web 端信息架构；读边界单调化只要求不把 Web 现有行为改坏。

## 验收标准（用户可观察结果）

### Requirement: 冷启动先看到上次的内容

#### Scenario: 有本地快照时立即首绘
- **GIVEN** 用户上次正常使用过，本地留有该账号在该服务的会话快照
- **WHEN** 用户在可上网环境下重新打开 App
- **THEN** 打开后先看到上次的会话列表（会话、预览、时间、未读与上次一致），不再出现只有“恢复登录…”或“正在加载聊天…”的空屏
- **AND** 后台随后完成校正，列表的内容、顺序与未读按服务端更新，期间界面不整屏闪回加载态

#### Scenario: 校正结果与快照不同
- **GIVEN** 快照中的某个会话已被移出，或上次之后已有新消息
- **WHEN** 后台校正返回
- **THEN** 失去访问的会话从列表消失，其他会话的预览、时间与未读按服务端更新
- **AND** 被移除的旧内容不会在校正后重新闪回

#### Scenario: 首次安装或没有快照
- **GIVEN** 本地没有该账号的快照
- **WHEN** 用户首次打开聊天页
- **THEN** 显示加载状态直到首次结果返回，不把空列表当作“没有会话”展示

### Requirement: 弱网或断网时仍能看到已有内容并知道未连接

#### Scenario: 断网冷启动
- **GIVEN** 本地有有效会话与快照
- **WHEN** 用户在断网状态打开 App
- **THEN** 先显示快照中的会话列表，并明确标示当前未连接或正在重试
- **AND** 不把用户送回登录页，也不把此时的状态显示成已同步或已发送
- **AND** 网络恢复后自动校正，用户不需要重新登录

#### Scenario: 弱网下进入有快照的会话
- **GIVEN** 用户曾打开过该会话
- **WHEN** 弱网下再次进入
- **THEN** 已有内容先可阅读，补齐与校正只在后台进行
- **AND** 补齐失败时明确说明未完成，不静默显示为最新

### Requirement: 发送后立刻看到自己的消息

#### Scenario: 点发送即出现气泡
- **WHEN** 用户在可写会话点发送，且正文或附件合法
- **THEN** 立即出现自己的消息气泡，内容与刚发送的一致，并带有“发送中”一类可辨状态
- **AND** 用户能据此确认消息已经发出，不需要盯着顶部等待

#### Scenario: 确认后收敛为一条权威消息
- **GIVEN** 气泡处于发送中或未确认
- **WHEN** 服务端确认这条消息
- **THEN** 该气泡转为正常消息（身份、时间与状态和从服务端读到时一致），位置不跳变
- **AND** 会话列表的预览与时间按这条消息更新，且不出现两条相同消息

#### Scenario: 未确认时不自动重发、不产生重复
- **GIVEN** 一条消息处于未确认状态（超时、断网或结果未知）
- **WHEN** 用户重新打开 App、回到该会话或网络恢复
- **THEN** 这条消息不会被自动重发，也不会变成两条
- **AND** 只有用户显式重试才会推进，重复重试仍然只产生一条消息

### Requirement: 发送期间仍可继续输入

#### Scenario: 未确认时编辑不被锁死
- **GIVEN** 上一条消息还在发送中或未确认
- **WHEN** 用户继续输入、粘贴或调整待发附件
- **THEN** 输入区可正常编辑，已写下的正文不会丢失或被改写
- **AND** 此时点发送不会发出第二条重复消息，用户能看出上一条仍在核对

#### Scenario: 不可写会话仍不能发送
- **GIVEN** 会话为只读、已解散或用户已失去写权限
- **WHEN** 用户尝试发送
- **THEN** 与修复前一致：不能发送，并给出可理解的原因

### Requirement: 未确认消息在气泡上显式重试

#### Scenario: 失败就地在气泡上重试
- **GIVEN** 一条消息因网络失败或结果未知处于未确认
- **WHEN** 用户在气泡上发起重试
- **THEN** 重试针对同一条消息，成功后就地变为正常消息，不新增第二条
- **AND** 重试期间状态可见，失败后仍可再次重试，原始内容与附件保留

#### Scenario: 明确失败可辨认
- **WHEN** 发送明确失败（例如无权限或目标不可用）
- **THEN** 气泡显示失败与原因，不会停留在“发送中”，也不会进入已送达或已读的展示

### Requirement: 进入会话即清零未读，且不会被过期状态复活

#### Scenario: 打开会话后未读清零
- **GIVEN** 会话有 3 条未读
- **WHEN** 用户打开该会话并看到最新消息
- **THEN** 该会话未读变为 0，返回列表后不再显示徽标
- **AND** 清零不依赖“某一行恰好滚进视口”这类偶然条件

#### Scenario: 往上翻历史不会让未读变大
- **GIVEN** 用户已在会话内且未读为 0
- **WHEN** 用户向上滚动查看更早的历史
- **THEN** 未读仍为 0，列表不因滚动历史重新出现徽标

#### Scenario: 过期上报与过期快照不倒退
- **GIVEN** 用户已读完并清零，随后收到晚到的读结果或过期的列表快照
- **WHEN** 客户端应用这些过期结果
- **THEN** 显示仍为已读，未读数不回退

#### Scenario: 新到但未展示的消息仍算未读
- **GIVEN** 用户停留在会话内，期间又到达一条新消息
- **WHEN** 该消息尚未被展示
- **THEN** 它仍计为未读，不因为会话已打开而被提前清零

#### Scenario: 多端已读至少不倒退
- **GIVEN** 同一账号在两台设备上打开同一会话
- **WHEN** 一台设备读完后另一台刷新同一会话
- **THEN** 另一台不把已读显示回未读

### Requirement: 丢弃的消息不在列表留下痕迹

#### Scenario: 丢弃后列表未读与预览一致
- **GIVEN** 某条 Agent 占位消息随后被丢弃（静默回复、自动轮次、模型失败或已由显式回复交付）
- **WHEN** 用户查看会话列表
- **THEN** 该消息不贡献未读，列表不显示它的正文也不留空白预览，时间回到该消息出现前的最后一条真实消息
- **AND** 打开会话看不到这条消息，断线重连或重新拉取历史后也不重新出现

#### Scenario: 丢弃不影响其他真实未读
- **GIVEN** 该会话里另有真实未读消息
- **WHEN** 发生一次丢弃
- **THEN** 只有被丢弃消息造成的影响被回滚，其他消息的未读与预览保持

#### Scenario: 重复丢弃幂等
- **WHEN** 同一条消息被重复丢弃
- **THEN** 列表的未读与预览不会被重复回滚，也不产生额外变化

## 不得破坏的既有正确行为

- **重试重发不产生重复消息**：同一条未确认发送无论重试多少次、是否重启，都只对应一条消息。
- **未确认草稿不自动重发**：重启、重连、回到会话都不会自行发出，必须用户显式重试。
- **断线与重放不重复展示**：重连后增量事件不重复出现，历史补齐不回退；已丢弃的消息即使重放也不出现。
- **已读只属于当前用户**：不消费他人未读；同时到达且尚未展示的新消息仍保持未读。
- **权限与授权不变**：只读、观察者、已解散与已失去访问的会话仍不能写、不展示受保护内容；退出登录、切换服务或账号后，旧会话内容与本地快照不进入新会话。
- **列表既有行为不变**：置顶优先与按最后消息时间排序、搜索、分类筛选、静音、置顶与免打扰互不影响，公开群访客的只读浏览与加入路径可用。
- **发送前置校验不变**：不可写、已解散、附件仍在上传或失败等条件仍能阻止发送并给出可理解原因。
- **Agent 状态展示不变**：运行中、失败、权限确认等既有状态与操作保持。
- **丢弃的既有语义不变**：删除消息、广播 tombstone、重复丢弃幂等、刷新历史不复活。

## 修复方向（产品层；选型、接口与切片留 design）

- 给聊天状态加一层“本地先行 + 后台对账”：先画上次已知内容，再把网络结果当作校正；区分已确认、未确认与未连接，不把某次往返失败当作没有内容或没有会话。
- 把已读变成一次显式的、可重试的用户动作，并让读边界只向前推进；服务端接受上报时保持单调，同时保留“尚未展示的新消息仍未读”。
- 把发送表达为乐观气泡加发送守卫：气泡先出现，守卫负责“现在能不能再发”，编辑不再被待发状态锁住；重试沿用既有幂等身份。
- 补齐 `message_discarded` 契约的另一半（恢复会话投影），并让“丢弃不改变用户可见的未读与预览”成为可复核的用例。
- 边界要求：本地快照必须按服务与账号隔离并受既有授权约束，不能为了首绘更快而展示已失去访问的内容。
