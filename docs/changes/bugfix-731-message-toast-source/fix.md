## 现象 / 复现

- 用户截图位于 `/settings/agents/nano-manager?view=work`。左上角新消息弹窗标题显示 `ab3e25b7-c05e-4e8f-9524-88363180ab99`，下方有消息摘要与 `View message` 链接；用户无法通过标题辨认会话。
- 当前实现把发送者名称作为标题，没有使用会话标题。名称解析遗漏服务端实际使用的嵌套名称字段，Agent 完成提醒最终可回退为发送者内部 UUID。
- 代码取证基线：`0e7b7cb16`。未读取生产事件或数据库，截图中 UUID 的具体身份尚未通过生产数据核实；上述回退链路已由代码确认。
- Current 契约依据：`docs/specs/im/conversations-messages.md` 的“私聊可以按会话修改标题”和“普通人际私聊默认显示对方名称”说明会话名有独立语义；该文件与 `web-chat-ux.md` 当前未规定本弹窗的私聊/群聊标题组合。本次规则为用户明确的新要求。

### 已确认的目标

#### Requirement: 私聊提醒使用会话名

##### Scenario: 已改名的私聊收到消息
- **GIVEN** 用户和同一个 Agent 有多条私聊，其中一条已被用户改名
- **WHEN** 用户在其他页面收到该私聊的新消息弹窗
- **THEN** 弹窗显示该条会话的当前名称，用户可以辨认具体是哪条私聊。

##### Scenario: 真人私聊收到消息
- **WHEN** 用户在其他页面收到真人私聊的新消息弹窗
- **THEN** 弹窗使用与聊天列表一致的会话名。

#### Requirement: 群聊提醒同时说明群名和发送者

##### Scenario: 群聊中的真人或 Agent 发消息
- **WHEN** 用户在其他页面收到群聊的新消息弹窗
- **THEN** 弹窗同时显示群聊名和该消息发送者的可读名称，并保留消息摘要。
- **AND** 群聊身份按会话类型判断；只有两个成员的群仍显示群聊来源。

### Agent 提出的展示方案

沿用截图中的标题、摘要和查看入口三个层级，局部替换内容，不需要另建页面原型：

| 类型 | 标题 | 摘要示例 |
| --- | --- | --- |
| 私聊 | 周末出行计划 | 已整理好周六的行程…… |
| 群聊 | 产品讨论群 | 小陈：我补充了一版方案…… |
| 群聊中的 Agent | 产品讨论群 | 项目助手：整理结果如下…… |

- 会话名优先使用已保存的当前名称，包括用户自定义名称；群聊发送者使用该消息的展示身份，避免把代发身份一律替换为 Agent 配置名。
- 长会话名和长发送者名允许截断，不能挤掉所有消息摘要；群聊名和发送者仍能分别辨认。
- 名称暂不可用时使用当前语言的“新消息”“成员”或“Agent”等可读称谓，不把 UUID、逻辑 ID 当成面向用户的名称；名称数据可获取时应正常展示实际来源。
- 本轮范围为截图中的 Web 应用内新消息弹窗；系统桌面通知和原生 iOS 不在本轮已确认范围。
- 查看链接继续进入消息所属会话，关闭和自动消失行为沿用现状。`View message` 等英文动作文案属于已观察现状，本轮不另行扩展为通知整体改版。

## 根因

1. `src/IM/frontend/src/features/chat/components/in-app-toast.tsx` 直接把 `senderName` 渲染为标题；`hooks/use-global-message-toast.ts` 赋值时传入候选发送者名称，没有按会话类型组织会话名与发送者。
2. `features/notifications/agent-completion-accumulator.ts` 的名称解析只读取顶层 `sender_display_name` 等字段，最后回退为 `sender_user_id`。服务端 `apps/im-server/src/message-records.ts` 的消息投影实际提供 `sender.display_name`，创建事件通过展开消息投影发布。两边数据形状不一致导致可读名称被遗漏。普通用户消息的 `extractSenderName` 同样遗漏嵌套字段。
3. 现有 `use-global-message-toast.test.tsx` 的 Agent 完成测试人为提供顶层 `sender_display_name`，没有覆盖真实嵌套发送者形状，也没有用不同于发送者名的会话名断言来源，因此未能发现这两个问题。

历史定位：名称解析与 UUID 回退至少自 `c8db7c1c67`（`fix(refactor-460/M4/R4): 统一回复提醒生命周期`）引入该 accumulator 时即存在；当前直接透传发送者的赋值行来自 `f982d49673`。这说明问题存在于既有提醒链路，不据此推断截图部署版本或断言近期回归。

原功能意图与必须保留的不变量，依据 `docs/changes/archive/refactor-460-web-im-client-runtime/motivation.md` 的“会话列表、未读状态和应用内提醒保持一致”及相关通知要求：

- 非当前会话的新可见消息能实时提醒，会话预览、排序和未读反馈仍正常更新。
- 正在查看的会话和自己发出的普通消息不产生多余应用内提醒；外部渠道消息仍沿用既有身份判定。
- Agent 回复按完成生命周期提醒一次，断线恢复不重放已处理提醒，刷新跨越创建/完成时保留必要身份。
- 点击提醒进入实际消息所属会话，改展示名称不改变导航身份或访问资格。

## 修复

已在隔离分支 `codex/bugfix-731-message-toast-source` 实施：

- 私聊标题取当前会话名；群聊分别显示群名、发送者名、摘要。最终采用独立发送者行，使长发送者名不会挤掉消息摘要；名称行超长省略，摘要保留两行，窄屏不超出视口。
- 解析 canonical `sender.display_name`，缺名称时使用可读通用称谓，不再用逻辑 ID 或 UUID 作为新提醒的名称兜底。
- 优先复用已有会话缓存；在桌面设置页尚无聊天列表时，按会话 ID 获取单条会话，补齐标题与群聊类型。沿用已有鉴权和会话详情 query key。
- 未改变消息订阅、完成去重、自发消息抑制、未读和导航语义；桌面系统通知的名称解析复用 accumulator 的字段纠正，但未扩展其展示布局。
- 窄测试沿用原有通知 suite；新增 `message-toast-source.test.tsx` 从真实 canonical 发送者形状与空列表缓存观察实际弹窗，覆盖私聊、群聊 Agent 和群聊真人。原 hook 测试文件已超过 400 行，不继续堆积新的独立展示接线场景。
