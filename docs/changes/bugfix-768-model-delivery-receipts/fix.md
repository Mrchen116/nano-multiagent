# bugfix-768 按模型实际收到提醒推进送达回执

## 原始需求

> 我认为已送达的标准应该是那个Inbox提醒真正进到了模型，就是模型真正收到了，你理解吗？已读是模型真正的调了Inbox Read拿到了。

> 所以帮我解决这两个问题，一个是为什么会卡住了，新发消息也收不到。第二个问题是关于这个已送达的纠正

## 现象 / 复现

生产消息已持久进入节点 Inbox，仍 consumed=0 且没有新模型请求，界面却显示已送达。用户要求已送达对应本条消息的 Inbox 提醒真正进入模型，已读对应模型实际调用 Inbox Read 并成功取得内容。唤醒阻塞另行定位，此 unit 修正回执事实与展示时点。

消息仅入箱、原生队列接纳、等待调度、准备请求失败或取消时，均不得推进已送达。忙时提醒应到下一次真正消费该提醒的模型请求才推进；重试、恢复和同一请求多条提醒须按实际覆盖的消息幂等推进。已读保留成功工具结果与完整内容摄取的现有证据边界。传输接纳确认仍停止相同消息重投，不能与用户送达状态混用。

## 根因

GlobalAgent.receive 在 Inbox 持久化后立刻发 sent，Inbox.receive 同时建立待发送 sent receipt，中心把 sent 直接映射为已送达。原生唤醒 admission 与模型实际请求之间存在排队、恢复和失败环节，当前实现跳过了这些环节。

## 本次审查安排

独立代码与 Agent Context 审查合并检查。使用真实锁定 DSH 和受控 provider，读取实际出站请求及请求返回，验证本条提醒确实出现在模型消息里，配合产品 receipt 状态核对。覆盖忙时、取消／失败、重试、恢复、提醒批次冻结映射、成功 Inbox Read 与失败／部分读取。不能以 preview、turn/start 或仅进入 llm hook 代替真正模型接收证据。
