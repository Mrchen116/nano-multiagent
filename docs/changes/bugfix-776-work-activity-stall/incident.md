# bugfix-776 · 在线 Agent 的头像工作状态持续转圈

## 用户报告

> 我看到一直有收到包，但是一直显示记录同步中，帮我定位问题，很有必要做性能优化。
>
> 我前面告诉你的是，为什么它一直转圈圈，没有最终的结果。希望你优化性能，而不是说你去改整个UI。
>

用户截图分别显示 Mini 上的 Personal Agent 和 Air 上的 P2。P2 弹窗里的配置和打开工作记录入口已经出现，两行仍在转圈。用户希望打开时立即呈现现有弹窗，主 Agent 和子 Agent 各自在原位置转圈和显示结果。

## 现场与复现

11 月 19 日，在生产 Web 从聊天头像打开工作状态。以下时间从点击算到成功响应才会渲染的「打开工作记录」入口可见，包含浏览器自动化开销。每个 Agent 单次测量。

| 对象 | 实际观察 |
| --- | --- |
| Personal Agent（Mini） | 约 0.76 秒已显示入口，点击后 35 秒再次查看，主、子两行仍在转。派工图在早前复现时已经显示已保存的节点和用量。 |
| 禅（Air） | 约 0.76 秒已显示入口，随即读到「空闲」和「0 个执行中」。这次成功样本与用户此前长时间等待的观察可以同时成立。 |
| P2（Air） | 从完整弹窗和两个转圈开始，在点击后第 16 秒检查时已显示「空闲」和「0 个执行中」。实际结束时间早于检查时刻。 |

同日两次只读检查补充了浏览器无法给出的边界。

- Mini 较早样本中，本地产生、已确认与中心已保存序号均为 24546，没有未提交的分片和等待写入的事实。Personal Agent 是节点唯一的待恢复根会话。一个已完成的子执行原生序号达到 238，Work 检查点仍是 203，同一位置出现在 11 月 16 日和 18 日的备份。只读重放剩余 35 个事件能还原完成事实。生产库上连续四次直接调用摘要查询，活动查询用时 0.17 至 1.15 毫秒，派工图用时 0.26 至 2.55 毫秒。这些数值只覆盖数据库查询。
- Air 晚间样本中，本地生成和已确认序号均为 235571，待写事实为零。唯一待恢复根属于 P；P2 和禅属于同一节点的其他 Agent。稍后再查，节点的待恢复标记已经清零，此时从浏览器读到了禅和 P2 的状态。

## 根因与证据边界

1. Gateway 的 InboxStore 按根会话记录待恢复工作，WorkSync 上报时将全节点的待恢复与待写事实合并为一个布尔值。[本地进度](../../../packages/personal-assistant/src/inbox.ts) · [上报](../../../packages/personal-assistant/src/work-sync.ts)
2. IM 的 Work.recordSyncState 只接收节点身份。节点报告有待处理项，或者中心确认序号落后时，整个节点得到 catching_up。活动接口只有在节点在线且整机为 current 时才确认主状态和子执行计数。因此，即使待处理项只属于另一个 Agent，当前 Agent 的活动结果也会被挡住。[同步判断](../../../apps/im-server/src/work.ts) · [活动查询](../../../apps/im-server/src/work-summaries.ts)
3. 弹窗在首次发请求和成功收到 catching_up 时都渲染两个转圈，每 15 秒再查。只要后台持续返回这个值，每次 HTTP 读取都成功也可以一直没有结果。派工图同样使用整机同步状态。[头像弹窗](../../../src/IM/frontend/src/features/chat/components/agent-activity-popover.tsx) · [派工图](../../../src/IM/frontend/src/features/settings/agents/agent-work-delegation.tsx)

以上能解释长期转圈和跨 Agent 相互影响。Mini 的历史子执行长期停在 203 的具体线上调用仍缺少执行证据。离线重放覆盖了解码、分页与事实投影，未覆盖线上调度、运行时读取和提交。晚间 Mini SSH 连接被关闭，因此 Mini 数据库样本与晚间 UI 计时分开使用。

## 用户可观察的验收

### Requirement: 在线 Agent 的工作状态能够独立返回

- WHEN 用户打开在线 Agent 的头像，同时该电脑上的其他 Agent 正在补历史，THEN 当前 Agent 已可确认的主状态与子执行计数在现有弹窗显示，用户无需重开或刷新。
- WHEN 自身历史正在补齐，同时可以核实当前执行，THEN 已确认的当前状态能返回；真实未决的子执行数量保持未知。验证应包含真实运行中子执行，以防将未知写成零。
- WHEN 一次请求成功返回但尚待恢复，THEN 后台继续推进，恢复后已打开的弹窗与派工图自动显示对应结果。用 Mini 的历史缺口验证生产恢复链能走到结束事实。
- 从打开到拿到响应，以及从打开到两行均显示可信结果，分别计时。用同一组初始历史与活动状态对比修复前后，覆盖用户等待几十秒的场景。

修复保留现有布局和加载动画，保留历史记录、访问权限以及离线与未确认语义。相关当前契约见[头像工作状态](../../specs/im/web-chat-ux.md#requirement-web-聊天可从-agent-头像查看工作状态)和[工作记录](../../specs/im/agent-work.md)。
