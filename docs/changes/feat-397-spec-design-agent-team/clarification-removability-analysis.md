# Clarification Removability Analysis

基于 45 个 unit、222 条澄清记录的人工介入必要性分析。

---

## 1. 总览数字

| 分类 | 条数 | 占比 |
|---|---|---|
| **可剥离（合计）** | **54** | **24.3%** |
| 　repo（仓库代码 / 历史 unit / 既有实现模式） | 45 | 20.3% |
| 　docs（项目文档直接覆盖） | 1 | 0.5% |
| 　web（联网搜索 + 参考项目源码） | 8 | 3.6% |
| **不可剥离（合计）** | **168** | **75.7%** |
| 　value（产品方向 / UX 偏好 / 风险容忍 / 审美 / 命名约定） | 96 | 43.2% |
| 　scope（范围 / 优先级取舍） | 72 | 32.4% |
| **合计** | **222** | 100% |

**判定说明**：可剥离 vs 不可剥离的边界本身存在主观性。本分析以"一个没有维护者在场的 agent，是否能从现有 artifact 唯一推导出相同结论"为判据。对于维护者虽仅说"ok"/"对"但批准的是 agent 自主推导出的方案者，若该方案可完全由 repo/docs/web 推导，则归入可剥离；若方案本身包含价值判断，则归入不可剥离。

## 2. 可剥离部分的自动化机制

### 2.1 仓库 grep / 代码直读

最大的可剥离来源（45 条）。多数情况是维护者的答复本质上是"与既有实现一致"或"参照 X 已有约定"，agent 完全可以自己 grep/read 得到。

**例 1 — bugfix-348**（旧位置 session 文件是否迁移）
> 答复原话："不迁移。修复只改「今后新建/写入的落点」，旧文件留在原地（feat-330 已定调「开发态不兼容旧数据」）"

判据：`docs/changes/feat-330-session-context-storage/design.md` 第 7 行明确写"不考虑兼容旧数据，当前为开发态"，可直接读取。

**例 2 — refactor-345**（compact 发生时是否保留前端/REPL 提示）
> 答复原话："保留 compact boundary 提示信息。"

判据：`src/agent/core/agent/loop.py` 已有 `yield compacted_msg`（boundary 消息），保留是维持既有行为，读代码即得。

**例 3 — feat-393**（无直聊时是否自动新建）
> 答复原话："自动新建直聊并汇报(推荐)"

判据：`src/IM/ws/gateway_handler.py` 的 `_find_canonical_direct_conversation` 返回 None 时上层已有 `create_conversation` 逻辑，grep 可查。

### 2.2 历史 unit 检索

部分澄清仅是重新确认某个已在前序 unit 中决策的问题。

**例 1 — feat-385**（memory 闭环修复范围、USER.md 是否注入）
> 答复原话："这个之前引入hermes agent的自进化的时候对过了吧"

判据：`docs/changes/feat-349-self-evolving-skills-memory/spec.md` 的 Q1/Q3/Q5 澄清记录有完整记录，检索历史首文档即可。

**例 2 — refactor-360**（73 处测试迁移策略）
> 答复原话："按用途分流"

判据：分类逻辑（接通真实路径 / 平替 / 删）是标准死代码测试迁移模式，结合 `docs/TESTING_GUIDE.md` 的落层原则可推导，维护者只做了确认。

**例 3 — feat-347**（orchestrator"跳过 reviewer"的条件是否完整）
> 答复原话："没有——只覆盖了 lite 模式，漏了'零用户面 unit'。补进 orchestrator §5"

判据：读 `.claude/skills/change-orchestrator/SKILL.md` §5 即可核实条件列表，缺口客观存在，无需人的偏好。

### 2.3 参考项目源码查询（web 类）

8 条，主要来自本仓明确对标的参考实现（CC、openclaw）。

**例 1 — feat-333**（是否照抄 CC 的 allow/soft_deny/environment 配置模式）
> 答复原话："是。照抄 Claude Code 的模式"

判据：CC 的 `src/cli/handlers/autoMode.ts` 和 `yoloClassifier.ts` 公开可读，`grep soft_deny/allow/environment` 即可查到配置模式。

**例 2 — feat-394**（openclaw heartbeat/cron 的上下文分界线核实）
> 答复原话："你先去看 openclaw 源码，是不是这样的"

判据：纯事实核查，答案完全来自 `~/Repos/opensource-hub/openclaw` 源码，维护者无需输入。

**例 3 — refactor-345**（loop 内部触发策略：主动检查还是被动恢复）
> 答复原话："每次 LLM 调用前主动检查 token，超过阈值就 compact 后继续。"

判据：CC `query.ts` 的 `while(true)` 开头主动检查模式可直接读源码得到。

## 3. 不可剥离红线类目

168 条不可剥离澄清，按内容归纳为 6 个类目。

### 类目 A：产品方向与技术路线

**频次：约 30 条**

agent 无法自行决定本仓产品走哪个方向、选哪种技术范式。

- **feat-333**（是否引入 dangerously-skip-permissions 旁路）："默认体验是 auto；同时额外提供一个对标 Claude Code dangerously-skip-permissions 的危险旁路入口，语义是不进行任何权限管控"
- **feat-394**（heartbeat/cron 概念模型）："两套：主动脉冲 heartbeat + 显式 cron job……heartbeat是定期唤醒agent，保持当前的上下文记录……而定时任务，是不带你的上下文"
- **feat-387**（gateway 进程内化可接受性）："好"——但其背后是对"kernel 进程消失、gateway 生命周期即内核"这一运维模型变化的接受，属价值判断

### 类目 B：UX 偏好与交互设计

**频次：约 28 条**

界面布局、气泡合并规则、信息密度、错误呈现方式等。

- **bugfix-367**（工具-only 轮的泡边界合并规则）："我的预期是一轮 llm 工具调用和文字输出放在一个泡中，如果没有文本，只有工具调用则合并到上一个泡，不新增泡。直到有文本输出的一轮，新建泡泡。"
- **bugfix-380**（错误气泡归属身份）："还是挂在 agent 名下会比较好,因为群里 A agent 挂了,B agent 可能没挂,这样好知道是谁"
- **feat-379**（per-agent 用户自定义落地方式）："「开关 + 自定义段(推荐)」。附选择时的预览：[✓] 启用 Heartbeat 段…→ 内核固定段 + 勾选的产品段 + 这段文本"

### 类目 C：范围与优先级取舍

**频次：约 36 条**

本期做什么、不做什么、哪些拆 unit、哪些合并。这是最高频的红线类目。

- **bugfix-348**（修复范围：仅个人助手 vs 同时覆盖 Coding CLI）："一并覆盖。两个产品都受同一根因影响"
- **feat-388**（CI 门禁是否同时覆盖前端 vitest）："feat-388 的前端 CI 补充，你作为spec-author，顺便补一下"
- **refactor-395**（Q6: 扩范围）："就做这点有点少。再去看看报告，看有哪些是不需要讨论，毫无疑问是问题的"

### 类目 D：风险容忍度

**频次：约 18 条**

历史数据是否迁移、后向兼容策略、开发态豁免、fail-fast vs graceful-fallback。

- **bugfix-357**（已存错误数据是否回填）："对，开发态。不修过往"
- **feat-382**（config 缺 llm 段时处置策略）："不考虑后向兼容。"
- **feat-388**（存量违规处理）："存量要本unit修了"

### 类目 E：文档与代码审美

**频次：约 14 条**

注释详略、skill 篇幅、文字风格、结构取舍等。

- **bugfix-356**（SKILL.md 修订力度）："你写的太多了，就这么小一个需求，要讲这么多东西吗？……言简意赅的把核心的东西表达出来就行了。"
- **feat-398**（skill 文档是否太啰嗦）："写的太啰嗦了，不用这么啰嗦也能说明白。agent能很好遵循。"
- **feat-396**（skill 内容语言与写法）："要变成中文。其他的，你来考虑，原则就是效果优先，不用符合我现在的skill的写法，完全不需要。"

### 类目 F：命名约定与流程哲学

**频次：约 12 条**

unit 类型定性（feat/refactor/bugfix）、lite/full 模式选择、agent 角色哲学（目标驱动 vs 流程驱动）。

- **feat-379**（变更类型归属）："这更像是feat，重构是一部分，但是关键是整个system prompt体系的构建"
- **feat-391**（角色目标与职责关系）："目标，或者说是职责。都是一个意思 / 流程不可能面面俱到，所以关键还是目标"
- **feat-352**（trivial 不定义死分级）："我觉得这个问题很难定义清楚。就让 Agent 自己遇到情况自己来决策就行了吧"

## 4. 对 feat-397 的含义

### 真实占比结论

**维护者可以被剥离的比例约为 24%**，剩余 76% 是结构性不可剥离。这意味着：

- 即使系统具备完备的 repo 检索、文档查询、web 搜索能力，仍有约四分之三的澄清需要人工介入
- "可剥离"部分集中在事实核查类问题（现有代码怎么写、参考项目如何实现、历史 unit 已决策什么），而非判断类问题

### 必须留人的红线（escalate 触发条件）

按优先级排序，agent team 必须 escalate 给维护者的场景：

1. **范围与优先级取舍**（最高频，~36 条）：本期做什么 / 拆合 unit / 衍生功能是否纳入
2. **产品方向与技术路线**（~30 条）：选哪个架构范式、对标哪个参考实现到什么程度
3. **UX 偏好与交互设计**（~28 条）：界面布局、信息呈现、气泡 / 错误 / 状态的视觉规则
4. **风险容忍度**（~18 条）：历史数据迁移、后向兼容、fail-safe vs fail-open
5. **文档 / 代码审美**（~14 条）：注释详略、skill 篇幅、语言风格
6. **命名约定与流程哲学**（~12 条）：变更类型定性、agent 角色目标的表述方式

### 系统应具备的"自助查证"能力

为把 24% 可剥离部分真正自动化，系统需要：

1. **Repo 语义检索**：给定一个澄清问题，能自动检索相关源文件、历史首文档（`docs/changes/*/design.md` / `spec.md`）、skill 文本，提取已有约定或先例
2. **参考项目对照**：能 read/grep 本仓显式指定的参考实现（CC、openclaw、hermes-agent、opencode、codex），提取对应机制并构造"本仓是否已对齐"的判断
3. **历史 unit 索引**：能快速定位某个设计决策是在哪个 unit 的澄清中第一次确立，并检索后续 unit 是否复用了同一答案
4. **契约层文档查询**：能在 `docs/specs/<包>/spec.md` 中检索当前行为契约，对"这与既有契约一致吗"类问题给出有根据的回答

这四项能力只能覆盖可剥离的 24%。76% 的不可剥离部分是系统性的——它们不是信息缺失，而是**判断缺失**，必须由维护者提供。
