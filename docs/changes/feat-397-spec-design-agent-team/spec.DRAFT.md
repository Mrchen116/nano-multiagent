## 用户场景

**主角**：你——这套 change-* SDD 流水线的唯一维护者，同时扮演产品经理 / 架构师 / 前端品味的来源。

**现状痛点**：写代码环节（orchestrator → worker → reviewer）已基本全自动、趟通。但每个需求的**前两环——spec 对齐、design 对齐——仍要你详细地同步参与**：从用户视角想全局、从架构师视角想长期可演进、从前端视角想美观、遇到陌生领域还得自己上网查资料。这个对齐过程逐需求、同步、极耗你个人注意力，是你无法 scaling up、无法真正"简单沟通一下需求后全交出去"的瓶颈。

**憧憬中的旅程**：

> 你给一段**轻 brief**——一两句话，也许夹一个"参考某产品"的链接（D1）。系统的 spec/design team 接手：
>
> 能自己补的它自己补——通用最佳实践直接定、陌生领域自己上网查并附来源（D7），不拿这些来烦你。
>
> 你不在场，它就一直往前推，把**真正需要你品味的"价值岔路"**（多个合理选项且对产品/体验影响显著、与既定原则冲突、不可逆高成本、或它自己没把握）攒起来（D3）。
>
> 等你回来，在**门禁 1（spec）**看到的不是一篇要你通读的长文，而是：一份"已完成部分 + 待你裁决的 N 个岔路（每个带选项、取舍、系统推荐）"的决策包，经 IM 异步推给你（D2、D4）；产出还附一份**质量自评分**，把薄弱处高亮，把你的注意力引到该看的地方（D5）。
>
> 你做完少量裁决，系统据此把 spec 收口、继续推进到 **design 对齐**，同样在**门禁 2** 把设计决策里的岔路推给你。你每一次"不，我更想要 A，因为……"都被记进**品味库**，下次同类岔路它就按你的偏好自动决或直接推荐——**你越用越少被问**（D6）。
>
> 门禁 2 通过，产出就是现有 `docs/changes` 格式的 spec.md / design.md / milestone 拆分，你启动现有 `change-orchestrator`，它**零改动**接手后面已自动化的实施链（D8 范围交接）。

一句话：把你从"每个需求每个细节的同步对齐者"，变成"只在少数价值岔路上、异步、被引导着做裁决的人"。

## 验收标准

> 主角"用户"= 维护者你本人。所有 Scenario 都是你能在产品上观察到的行为。

### Requirement: 轻 brief 即可启动 spec/design 对齐 [D1]

#### Scenario: 一句话 brief + 一个参考链接
- **WHEN** 你给出一段自由文本需求（可含链接 / 截图路径 / "参考某产品"）
- **THEN** 系统无需你填任何模板即可启动，并回出第一版结构化需求草稿 + 一份"待你裁决项"清单

#### Scenario: brief 信息严重不足
- **WHEN** brief 不足以启动（连要解决谁的什么问题都说不清）
- **THEN** 系统回一个**最小**澄清集让你补，而不是空转、也不是凭空乱猜需求

### Requirement: 陌生领域自主研究，不为"这是什么"打扰你 [D7]

#### Scenario: 需求触及你不熟的领域
- **GIVEN** 需求涉及一个你和系统都不熟的领域
- **WHEN** 系统推进到需要该领域知识的地方
- **THEN** 系统自行上网检索 / 参考同类项目，并把调研结论与来源附在产出里，不就"这是什么"来问你

### Requirement: 只在价值岔路升级，常规决策自动化 [D3][D4]

#### Scenario: 遇到价值岔路
- **WHEN** 出现多个合理选项、且对产品/用户体验影响显著（或与既定原则冲突 / 不可逆高成本 / 系统低置信）
- **THEN** 你收到一个结构化决策请求：每个选项 + 各自取舍 + 系统推荐，由你裁决
- **AND** 系统**不**自行拍板替你做这个价值判断

#### Scenario: 常规决策
- **WHEN** 决策属于通用最佳实践或有既往先例
- **THEN** 系统自动决并记录理由，不打扰你

#### Scenario: 打扰频率受控
- **GIVEN** 已设定每个变更单元的升级次数上限
- **WHEN** 一个变更单元里待升级项超过上限
- **THEN** 系统合并 / 降噪后再呈现，你不会被高频逐条打断

### Requirement: 不在场也能推进，门禁处异步批量裁决 [D2][D4]

#### Scenario: 离场期间持续推进
- **GIVEN** 你不在场
- **WHEN** 系统遇到可自动决的部分
- **THEN** 它持续推进，把待你裁决项累积到门禁，不停在那里干等

#### Scenario: 回来一次过完
- **WHEN** 你回到 IM
- **THEN** 你在门禁 1 / 门禁 2 看到一份"已完成 + 待裁决 N 项"的汇总决策包，可一次性异步处理完

### Requirement: 产出带质量自评分，引导审查 [D5]

#### Scenario: 门禁处看到自评
- **WHEN** 系统在门禁 1 / 2 交出 spec 或 design
- **THEN** 产出附一份按既定维度（完整性 / 一致性 / 可演进性 等）的质量自评分
- **AND** 低分 / 薄弱处被高亮，把你的审查注意力引到该看的地方，而非让你通读全文

### Requirement: 品味沉淀，越用越少被问 [D6]

#### Scenario: 一次裁决，长期生效
- **GIVEN** 你曾在某类岔路上裁决并说明了偏好
- **WHEN** 后续出现同类岔路
- **THEN** 系统按你的偏好自动决（或直接把你上次的选择作为默认推荐），不再重复问你

#### Scenario: 品味可查可改
- **WHEN** 你想知道系统"以为你喜欢什么"
- **THEN** 你能查看并编辑已沉淀的品味条目

### Requirement: 与既有流水线无缝衔接 [B]

#### Scenario: 门禁 2 通过后交接
- **WHEN** design 对齐在门禁 2 通过
- **THEN** 产出为现有 `docs/changes` 格式（spec.md / design.md / milestone 目录），你启动现有 `change-orchestrator` 即可直接消费，无需任何手工格式转换

## 范围与非目标

**在范围**：
- spec 对齐 + design 对齐两环的自主化（探索→门禁1→设计→门禁2）
- 轻 brief 入口 / 自主澄清 / 自主研究
- 价值岔路 escalation + 打扰频率控制
- 离场异步推进 + 门禁处批量裁决（经 IM）
- 产出带质量自评分
- 单人品味库的沉淀与复用（含"设计/美观"作为其中一个偏好维度）
- 与现有实施链（orchestrator/worker/reviewer）的零改动衔接

**非目标**：
- 改动已自动化的实施 / 验收链（不在本 unit）
- 新建独立 agent 框架 / 群聊辩论拓扑 / 超过 3–4 角色的大 team（研究证据反对）
- 多人 / 团队品味对齐（仅单人）
- 训练式个性化模型（PReF/VPL 等，属后续阶段）
- **自动生成 UI / 视觉设计方案**（研究：跨页一致性尚不成熟；列为 related，后续单独立项）—— 本期只把"设计品味"作为偏好维度纳入，不产出视觉草案 ✅[D8 已确认]
- 对"可演进性"的全自动度量（研究空白；初期靠人工校准 LLM-as-judge）
