## 原始需求

> （第一次描述）
>
> .claude/skills/change-* 是我的一系列的 skill 来实现多 agent 的 SDD。但现在有个困难，就是每一个需求我都需要很详细的做 SDD 的流程去对齐需求对其 spec 对其 design。就很麻烦。所以我设想是 其实我自己去做这个对齐的工作，我也是从产品经理的角度，就实际上就从用户的角度去全局的思考这个产品。以及从架构师的角度去思考整个架构的长期的可演进。另外可能是从前端设计的角度看整体的美观性。遇到我陌生的，我也是上网找资料，或者参考同类的项目的设计。我觉得 SDD 的 Spec 跟 Design 这两个环节。是不是可以通过一个 Agent Team 来完成呢？我们不用局限于 Claude Code 这个框架。我们就非常开放的，认为可以群聊，可以单聊。反正就是我们有很强的OPUS 模型。我可以自己自由的做一个agent框架来实现。你帮我思考一下，应该怎么能做到把我给踢出去，就不用不停的 human in the loop。不然我没办法 scaling up。没法真正全自动做项目。最理想的状态就是我简单沟通一下需求，就后面所有步骤完全agent来做。首先不考虑实操，你讲这个哲学上是不是合理的？马化腾他自己也不可能去写代码，但是他也能把整个公司所有的产品。给下面的人给分配安排好。他也不用亲自去对需求，不用亲自写代码，去对齐代码， review 代码。

> （关键修正）
>
> 我也没有说我要完全把自己踢出去啊。我不是跟你说了，我要简单对需求吗？那马化腾他也不可能对需求对那么细啊。

## 澄清记录

- Q1: 这个 agent team 的产出边界，是只接管 spec + design 两个环节（到门禁 2 为止），实施/验收仍走现有 change-orchestrator + worker + reviewer？还是把后面也一起吞了？
  A(原话): 我明确一下，在写代码这个环节，现在是基本上是全自动的。 change-orchestrator + worker + reviewer基本上算是能趟通了。现在的主要，想做的就是前面的两个环节。
  Agent 解读: 范围锁定在 spec + design 两环（探索→门禁1→设计→门禁2），实施/验收链不在本 unit 范围内。

- Q2: "把自己踢出去"到什么程度——完全 out-of-the-loop，还是只在关键处保留人？
  A(原话): 我也没有说我要完全把自己踢出去啊。我不是跟你说了，我要简单对需求吗？那马化腾他也不可能对需求对那么细啊。
  Agent 解读: 目标是 human-on-the-loop（人只在价值岔路/门禁处异步裁决），不是 out-of-the-loop。"简单对需求"= 轻 brief 入口 + 只在少数关键岔路被打扰。深度研究亦独立印证：无人能把人完全踢出 spec/design 还拿到生产级质量（HC-1）。

- Q3-Q7（异步批量答 alignment-questions.md 的 D1/D2/D6/D7/D8）:
  A(原话): D1 对，肯定是不限制的。D2 通常直接IM发，但有时候有一些东西比较难表示，也可以用 markdown 文件，HTML 的形式放在目录里也行。这个都不太核心。关键还是能不能做到不用处处我决策。D6 只能是我一个人，我也没有团队啊。我现在的做法就是做feat SPEC的时候就让agent记录下所有我的原话，其实就有这个意思，想后面可以参考我现在的逻辑。D7 系统自己查.  D8 可以先不做。其他问题，我也没想好，我还在学习这个报告
  Agent 解读:
    - D1 brief 入口：不限制（自由文本，不强制模板）。✅
    - D2 升级通道：默认 IM 直发；难以在 IM 表达时可落 markdown/HTML 文件到目录。用户强调"通道不核心"——**真正的核心诉求是"不用处处都要我决策"**（这正是 D3/D4/D5 escalation + 品味编译要解的，且是本 unit 成败的关键判据）。
    - D6 品味库：仅单人。**重要线索**——用户现有"做 feat spec 时让 agent 记录所有原话"的做法，已是品味库的雏形：跨历史 unit 的原话语料 = 现成的"决策 + 理由"案例集，未来系统应参考/复用这套逻辑作为品味来源。
    - D7 陌生领域：系统自己查。✅
    - D8 美观/视觉：本期先不做（视觉自动化），仅作品味维度。✅
    - D3（价值岔路定义 + 红线）/ D4（打扰频率上限）/ D5（评测先行 + 自评分）：见下方 Q8/Q9 逐条收口。

- Q8（D3 价值岔路红线）: 推荐——6 类红线分两档（永远问你：范围优先级/产品方向；品味库预荐你确认：风险/UX/审美/命名）+ 可逆性闸门 + 可检索的永不问；并问"有无硬红线（删数据/对外API/权限安全）"。
  A(原话): D3，先拍脑袋按你说的吧，我没想清楚。
  Agent 解读: D3 **暂按推荐采纳，但标记为"未深思、provisional"**，design/实施阶段或用户想清楚后可回头改。硬红线（删数据/对外API/权限安全等不可逆）默认纳入"永远问你"，待用户确认时细化。

- Q9（D4 打扰频率上限）: 推荐——设 escalation rate 目标 15–25%，每单元 ~2-3 次。
  A(原话): D4，需要设定这么一个值吗，我觉得不应该，不同需求不同的。
  Agent 解读: **撤销固定频率值/配额**。escalation 频率不是设定值，是"价值岔路闸门（D3）在该需求上自然落出的结果"——复杂/陌生需求多问、常规需求少问。防打扰靠 D3 闸门质量（可检索自动 + 稳定品味降为确认 + 只真岔路升级）+ 门禁批量呈现，不靠百分比上限。spec.DRAFT 的"打扰频率受控"场景据此改写。

- Q10（D5 产出带自评分 / 高亮薄弱处）: 解释为"交法 B"——产出附自检、高亮薄弱处,让用户审查被引导而非通读。
  A(原话): 可以啊，Clowder ai也有这种机制是吧
  Agent 解读: D5 确认。**机制按 Clowder 的 shipped 形态落地**：确定性结构断言/风险检测标红（detectRisks 式：缺成功信号、混入实现层决策、缺 GIVEN/WHEN/THEN 等）+ 逐条 confidence（确信/中等/猜测）+ premortem（最可能翻车处），把用户引到薄弱处。**不强求 LLM-judge 数字总分**（避免 Critic 高方差误判）。"评测先行/怎么建"属 design 阶段,不进 spec。

- Q11（升级是否阻塞推进）: 硬红线一律升级对，但"一识别到就立刻提问、提问后就停下来"不好；应提问，但其他能继续开展的要继续。
  A(原话): 硬红线一律升级，这一点是对的，但是我希望他不是一识别到这种问题，就立刻提问了，提问之后就停下来了，这是不好的。他可以提问，但是其他能继续开展的，要继续开展。
  Agent 解读: **升级 = 非阻塞**。系统升级一个问题后，把它加入待裁决决策包，并继续推进所有不依赖该答案的工作；只有真正依赖该决策的那一小块挂起等答复，绝不因一个待决问题冻结整个 spec/design 流程。已落入验收标准「升级不阻塞推进」。


## 用户场景

**主角**：你——这套 change-* SDD 流水线的唯一维护者，同时是产品经理 / 架构师 / 前端品味的唯一来源。

**现状痛点**：写代码环节（orchestrator → worker → reviewer）已基本全自动、趟通。但每个需求的**前两环——spec 对齐、design 对齐——仍要你详细地同步参与**：从用户视角想全局、从架构师视角想长期可演进、从前端视角想美观、遇到陌生领域还得自己上网查。这个对齐逐需求、同步、极耗你个人注意力，是你无法 scaling up、无法"简单沟通一下需求就全交出去"的瓶颈。

**诚实前提**（来自本 unit 对 222 条历史澄清原话的实测，见 `clarification-removability-analysis.md`）：你的澄清里只有约 **1/4** 是"可检索的事实"（既有代码 / 文档 / 历史 unit / 参考项目能查到），约 **3/4** 是只有你能给的判断（范围优先级、产品方向、风险容忍、审美、命名）。所以本系统**不追求"全自动无人化"**（四轮研究证实在差异化产品上不可达），而是把人介入**重排**：可检索的自动掉、你的稳定品味沉淀后降为"确认"、只把真正的逐项目价值岔路留给你异步裁决。

**憧憬中的旅程**：

> 你给一段**轻 brief**——一两句话，也许夹一个"参考某产品"的链接。spec/design team 接手：
>
> 能自己查的它自己查——通用最佳实践直接定、陌生领域上网查并附来源、既有约定 / 历史决策自己 grep，不拿这些烦你。
>
> 遇到判断，它**分三档**处理：①「可检索 / 常规」→ 自动决并记理由；②「你的稳定品味」（风险容忍 / 审美 / UX 偏好 / 命名）→ 从**品味库**取你以往偏好、给出**预填推荐**，你一键确认或改；③「真正的逐项目价值岔路」（范围优先级 / 产品方向 / 技术路线）或「硬红线」（删数据 / 对外 API 契约 / 权限安全等不可逆）→ 攒成**结构化决策包**留给你。
>
> 你不在场它就一直往前推。回来时在**门禁**看到的不是要你通读的长文，而是：已完成部分 + 待你裁决的几个岔路（每个带选项 / 取舍 / 推荐）+ 系统把产出里的**薄弱处高亮**了（缺成功信号、混入实现层决策、它自己没把握的、最可能翻车处），你直接看这些地方。
>
> 打扰你几次，由**这个需求真实的岔路数**决定——常规小需求几乎不问，复杂陌生的多问几次；系统不设固定配额、也不为凑数硬问。
>
> 你每次"不，我更想要 A，因为……"都进品味库，下次同类岔路它就按你偏好预填或自动决——**你越用越少被问**。
>
> 门禁 2 通过，产出就是现有 `docs/changes` 格式的 spec.md / design.md / milestone，你启动现有 `change-orchestrator`，**零改动**接手已自动化的实施链。

一句话：把你从"每个需求每个细节的同步对齐者"，变成"只在少数真价值岔路上、异步、被引导着做裁决的人"。

## 验收标准

> 主角"用户"= 维护者你本人。所有 Scenario 均为你能在产品上观察到的行为。

### Requirement: 轻 brief 即可启动 [D1]

#### Scenario: 一句话 brief + 一个参考链接
- **WHEN** 你给出一段自由文本需求（可含链接 / 截图路径 / "参考某产品"）
- **THEN** 系统无需你填任何模板即可启动，回出第一版结构化需求草稿 + 一份"待你裁决项"清单

#### Scenario: brief 信息严重不足
- **WHEN** brief 不足以启动（连要解决谁的什么问题都说不清）
- **THEN** 系统回一个**最小**澄清集让你补，而不是空转、也不是凭空乱猜需求

### Requirement: 陌生领域 / 既有事实自主查证，不拿"可检索的事"打扰你 [D7]

#### Scenario: 需求触及不熟领域
- **GIVEN** 需求涉及一个你和系统都不熟的领域
- **WHEN** 系统推进到需要该领域知识处
- **THEN** 系统自行上网检索 / 参考同类项目，把结论与来源附在产出里，不就"这是什么"问你

#### Scenario: 答案在仓库 / 历史里
- **WHEN** 某个澄清的答案能从既有代码、项目文档、或历史 unit 决策中查到
- **THEN** 系统自己 grep / 读取得到并采用，记下出处，不把这种"复述既有约定"的问题抛给你

### Requirement: 判断分三档，只有真价值岔路与硬红线升级给你 [D3]

#### Scenario: 真·逐项目价值岔路
- **WHEN** 出现多个合理选项、且属于范围优先级 / 产品方向 / 技术路线，对产品或用户体验影响显著
- **THEN** 你收到结构化决策请求（每个选项 + 取舍 + 系统推荐），由你裁决
- **AND** 系统**不**自行拍板替你做这个价值判断

#### Scenario: 你的稳定品味（预填→确认，而非从零决策）
- **GIVEN** 你过去在这类判断（风险容忍 / 审美 / UX 偏好 / 命名约定）上表过态、已进品味库
- **WHEN** 再遇同类判断
- **THEN** 系统给出"按你以往偏好的预填推荐"，你一键确认或改，而不是被要求从零决策

#### Scenario: 硬红线一律升级
- **WHEN** 决策触及删数据 / 对外 API 契约 / 权限与安全等不可逆、高风险类别
- **THEN** 无论系统是否有把握，一律升级给你确认，不自动决
- **AND** 升级**不阻塞**其余工作——仅挂起依赖该决策的部分，其余继续推进（见「升级不阻塞推进」）

#### Scenario: 可检索 / 常规决策
- **WHEN** 决策能从既有代码 / 文档 / 历史 unit / 参考项目查到，或属通用最佳实践
- **THEN** 系统自动决并记录理由，不打扰你

### Requirement: 打扰频率随需求本身，无固定配额 [D4]

#### Scenario: 常规需求 vs 复杂需求
- **GIVEN** 一个常规小需求 和 一个复杂 / 陌生的需求
- **WHEN** 两者分别走完对齐
- **THEN** 前者几乎不打扰你，后者会多次升级——打扰次数由该需求真实的价值岔路数决定
- **AND** 系统**不**为了凑某个频率配额而硬问，也**不**为压低次数而把真岔路藏着不问

### Requirement: 不在场也能推进，门禁处异步批量裁决 [D2]

#### Scenario: 离场期间持续推进
- **GIVEN** 你不在场
- **WHEN** 系统遇到可自动决 / 可预填的部分
- **THEN** 它持续推进，把待你裁决项累积到门禁，不停在那里干等

#### Scenario: 升级不阻塞推进（提问 ≠ 停下）
- **GIVEN** 系统遇到一个必须升级给你的决策（硬红线 / 真价值岔路）
- **WHEN** 它把问题升级给你
- **THEN** 它把问题加入待裁决决策包，并**继续推进所有不依赖该答案的工作**，不停下来干等
- **AND** 只有**真正依赖这个决策**的那一小块工作被挂起、等你回答后再续；系统**不**因一个待决问题就冻结整个 spec/design 流程

#### Scenario: 回来一次过完
- **WHEN** 你回到 IM
- **THEN** 你在门禁看到一份"已完成 + 待裁决 N 项"的汇总决策包，可一次性异步处理完

### Requirement: 产出高亮薄弱处，引导审查（不是逐字通读）[D5]

#### Scenario: 门禁处看到被高亮的薄弱处
- **WHEN** 系统在门禁交出 spec 或 design
- **THEN** 产出附自检，把**薄弱 / 没把握处高亮**：可机械检出的结构硬伤（验收标准缺 GIVEN/WHEN/THEN、混入实现层决策、缺成功信号）、系统自评的低把握项、以及"最可能翻车处"（premortem）
- **AND** 你的注意力被引到这些地方，无需通读全文（是否再附一个数字总评分可选，非必需）

### Requirement: 品味沉淀，越用越少被问 [D6]

#### Scenario: 一次裁决，长期生效
- **GIVEN** 你曾在某类岔路上裁决并说明了偏好
- **WHEN** 后续出现同类岔路
- **THEN** 系统按你的偏好自动决或预填推荐，不再从零问你

#### Scenario: 品味可查可改
- **WHEN** 你想知道系统"以为你喜欢什么"
- **THEN** 你能查看并编辑已沉淀的品味条目

### Requirement: 与既有流水线无缝衔接

#### Scenario: 门禁 2 通过后交接
- **WHEN** design 对齐在门禁 2 通过
- **THEN** 产出为现有 `docs/changes` 格式（spec.md / design.md / milestone 目录），你启动现有 `change-orchestrator` 即可直接消费，无需任何手工格式转换

## 范围与非目标

**在范围**：
- spec 对齐 + design 对齐两环的自主化（探索→门禁1→设计→门禁2）
- 轻 brief 入口 / 自主澄清 / 自主查证（仓库 + 文档 + 历史 unit + web）
- 判断三档处理：可检索自动 / 稳定品味预填确认 / 真价值岔路与硬红线升级（含可逆性闸门）
- 打扰频率随需求本身（无固定配额）
- 离场异步推进 + 门禁处批量裁决（经 IM；难表达时可落 markdown/HTML 文件）
- 产出高亮薄弱处（确定性结构断言 + 逐条把握度 + premortem）
- 单人品味库的沉淀与复用（含"设计 / 美观"作为其中一个偏好维度；初始可挖历史原话语料 bootstrap）
- 与现有实施链（orchestrator/worker/reviewer）的零改动衔接

**非目标**：
- 改动已自动化的实施 / 验收链（不在本 unit）
- 新建独立 agent 框架 / 群聊辩论拓扑 / 超过 3–4 角色的大 team（四轮研究证据反对：同质 debate 帮倒忙、协调开销超收益）
- 多人 / 团队品味对齐（仅单人）
