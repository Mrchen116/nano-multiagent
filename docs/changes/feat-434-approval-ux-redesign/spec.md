## 澄清记录

- Q1: 待决审批卡（需要你点允许/拒绝的那张）视觉基调用深色还是全浅色？
  A（原话，来自选项确认）: 选「深色卡，更醒目（推荐）」。
  Agent 解读: 待决是唯一需要用户注意的东西，深色在浅色聊天里跳出来抓注意力；已决全部浅色收敛。

- Q2: 已决审批一堆厚卡太丑，怎么收敛？工具调用和授权能不能放一个气泡？
  A（原话）: 工具调用和授权不能放在一个泡泡中吗
  Agent 解读: 不止「放一个气泡」——核实后端发现：被拒绝的工具本身就会产出 `reason=denied` 的工具调用行，工具面板里已显示「已拒绝」。已决审批与工具调用本是同一条流，应让已决审批彻底变成工具列表里的一行，不再有独立卡片。

- Q3: 已决审批那行用什么标记？
  A（原话）: 我觉得不用🔒 ，你上一版那个文字的挺好的
  Agent 解读: 去掉锁图标，用纯文字「已授权 / 已拒绝」。

- Q4: 收起态怎么概括已决审批？
  A（原话）: 2 次授权 · 2 允许。我觉得你之前这个好点
  Agent 解读: 工具面板收起态后缀用分项计数「N 次授权 · X 允许 · Y 拒绝」（小圆点区分，仅显示非零分项）。

- Q5: 行尾「已授权/已拒绝」的位置，和工具出错的报错（退出码/超时/已中断）会不会撞在一起？
  A（原话）: ok，这次ok。有个问题是，你每个工具的这个"已授权"，"已拒绝"的位置，后面工具出错好像也是在这个位置报错，这个需要协同设计
  Agent 解读: 一个工具可能「授权了、但执行失败」，「已授权」与报错会抢同一位置。需分区：「是否授权」贴名称右侧（闸门区），「执行结果」在行尾（结果区），互不遮挡。

- Q6: 行尾失败文案为什么锁死英文（exit 1 / failed）？
  A（原话）: 不是i18n的吗，为啥要局限一个语言
  Agent 解读: 现状 reason 标签走了 i18n，但 failTag（exit/failed）漏接 i18n、硬编码英文。应把失败文案一并接入 i18n，跟随界面语言，不锁死任一语言。

- Q7: 「允许且执行成功」的工具要稳定显示「已授权」并计入「N 次授权」，需要后端把「某次授权」对应到「某条工具调用」（拒绝的能靠现有 reason=denied 自动对上，允许的需后端补标）。要含后端补标，还是退成纯前端（允许的不标、只处理拒绝）？
  A（原话）: 含后端
  Agent 解读: 采完整方案——允许成功的工具行也要显示「已授权」、计入授权计数。后端如何打标/用哪个字段是 design 的实现选型。

## 用户场景

一个用户在 IM 里和 agent（如「产品」）对话。agent 接到任务后会连续调用很多工具（读文件、跑命令、grep……），其中一部分命令触发了授权确认。

**现状的痛**：工具调用被收进气泡内的「130 次工具调用」胶囊里；但每一次授权确认在解决后，都在气泡**外面**留下一个独立的深色厚卡——「已允许 · bash」「已拒绝 · bash」。一轮跑下来好几个，竖排成一面黑墙，和浅色聊天撞色，还和上面的工具面板重复表达同一件事。用户嫌「这一堆堆着太丑」。

**重设计后用户体验**：所有技术动作收在**同一个 agent 消息气泡**里。

- agent 跑工具时，气泡内出现「N 次工具调用」面板，工具一条条累加。
- 碰到要授权的命令，气泡**最下方**滑入一张醒目的深色**待决卡**：显示工具名、要做什么、具体命令，和「允许 / 本会话内允许 / 拒绝」三个选项。这是唯一需要用户停下来看的东西。
- 用户点了允许或拒绝，待决卡当即消失，这次授权**并入工具调用列表里的一行**——允许的行在工具名旁标「已授权」，拒绝的标「已拒绝」。不再有任何飘在气泡外的独立审批卡。
- 如果之前已经决过几次，气泡里上方是已并入的工具列表（含已授权/已拒绝的行），下方才是新的待决卡，两者同时清楚可见——用户能看懂「我刚批过的」和「现在要批的」分别是什么。
- 工具面板收起时，标题后缀概括这轮授权：`N 次工具调用 · K 次授权 · X 允许 · Y 拒绝`（用小圆点区分允许/拒绝，没有的分项不显示）；展开能逐行看到每条批/拒了什么命令。

**一个关键边界**：用户允许了某条命令，但它**执行失败**了（退出码非零 / 超时 / 中断）。这时工具名旁的「已授权」和行尾的失败报错是两件事，要同时看得到、各占一侧——「是否授权」在名称旁，「执行结果」在行尾，不互相遮挡。被拒绝的命令则没有执行结果，行尾标「未执行」，且不重复出现两个「已拒绝」。

工具失败的报错文案（退出码 / 失败 / 超时 / 已中断等）跟随用户的界面语言，不锁死英文或中文。

## 验收标准

### Requirement: 技术动作收在同一个 agent 消息气泡内

#### Scenario: agent 调用工具并请求授权
- **WHEN** agent 在一条消息里既调用了工具、又请求了授权
- **THEN** 工具调用面板与（待决或已决的）审批呈现都在这条 agent 消息的同一个气泡内
- **AND** 气泡外不再出现任何独立的审批卡片

### Requirement: 待决审批醒目且可操作

#### Scenario: agent 请求授权
- **WHEN** agent 请求执行一条需要确认的命令
- **THEN** 气泡最下方出现一张醒目的待决审批卡，显示工具名、该命令要做什么、具体命令内容，以及「允许 / 本会话内允许 / 拒绝」选项

#### Scenario: 已有已决审批时又来新的待决审批
- **GIVEN** 本条消息里已经有用户决过的审批（已并入工具列表）
- **WHEN** agent 再次请求一条新的授权
- **THEN** 上方是已并入的工具列表、下方是新的待决卡，两者同时可见，用户能分清「已批过的」和「待批的」

### Requirement: 用户决定后待决卡即时折叠并并入工具列表

#### Scenario: 用户点允许
- **WHEN** 用户在待决卡上点「允许」（或「本会话内允许」）
- **THEN** 待决卡消失，对应工具作为一行进入工具调用列表，并在工具名旁标「已授权」

#### Scenario: 用户点拒绝
- **WHEN** 用户在待决卡上点「拒绝」
- **THEN** 待决卡消失，对应工具作为一行进入工具调用列表，标「已拒绝」，且行尾标明该命令未执行

### Requirement: 已决审批以工具行形态呈现，无独立卡片、无锁图标

#### Scenario: 展开工具列表查看已决审批
- **WHEN** 用户展开工具调用列表
- **THEN** 经用户授权的行在工具名旁以文字标「已授权」、被拒绝的标「已拒绝」，与普通工具行排在同一列表里
- **AND** 不出现独立的审批卡片，也不出现锁图标

#### Scenario: 收起工具面板看授权概况
- **GIVEN** 这轮里有过若干次授权（含允许与拒绝）
- **WHEN** 工具面板处于收起态
- **THEN** 面板标题后缀显示「N 次授权 · X 允许 · Y 拒绝」，且只显示非零的分项

#### Scenario: 本条消息没有任何授权（空态）
- **WHEN** 一条 agent 消息里的工具调用都无需授权
- **THEN** 工具面板不显示任何授权后缀，整条消息不出现任何审批相关呈现

### Requirement: 行内「是否授权」与「执行结果」分区，互不遮挡

#### Scenario: 授权后执行成功
- **WHEN** 用户允许的工具执行成功
- **THEN** 该行在工具名旁显示「已授权」，行尾显示执行耗时

#### Scenario: 授权后执行失败（关键边界）
- **WHEN** 用户允许的工具执行后失败
- **THEN** 该行同时显示「已授权」（工具名旁）与失败报错（行尾），两者都可见、互不覆盖

#### Scenario: 拒绝不重复呈现
- **WHEN** 用户拒绝某工具
- **THEN** 该行只在工具名旁出现一次「已拒绝」，行尾标「未执行」，不出现第二处「已拒绝」

### Requirement: 工具失败报错文案跟随界面语言

#### Scenario: 中文界面
- **GIVEN** 界面语言为中文
- **WHEN** 某工具调用失败
- **THEN** 行尾失败文案以中文显示

#### Scenario: 英文界面
- **GIVEN** 界面语言为英文
- **WHEN** 同样的工具调用失败
- **THEN** 行尾失败文案以英文显示

## 范围与非目标

- **在范围**：
  - 工具调用与审批在同一气泡内的协同呈现（合一）。
  - 待决审批形态（醒目深色卡、气泡最下方、允许/本会话允许/拒绝）。
  - 已决审批并入工具列表为一行（行内「已授权/已拒绝」+ 收起态「N 次授权·X 允许·Y 拒绝」分项计数），取消独立审批卡与锁图标。
  - 行内「闸门（是否授权）」与「结果（执行如何）」分区，覆盖「授权后失败」边界。
  - 工具失败报错文案跟随界面语言（修掉失败文案漏接 i18n 的现状缺口）。
  - 让「允许且执行成功」的工具行也能稳定显示「已授权」并计入授权计数（含后端为工具调用补「经用户授权」标识；具体机制属 design 实现选型）。

- **非目标**：
  - 不改审批的决策粒度与按钮语义（允许 / 本会话内允许 / 拒绝 照旧）。
  - 不改 auto_mode_gate「何时」触发审批的判定逻辑。
  - 不改「拒绝后 agent 的后续行为」（继续 / 停下）这一运行语义。
  - 不改工具详情展开卡（bash 终端块、diff 等）的内部呈现。
  - 不做审批历史的跨消息聚合（只在单条消息气泡内呈现）。
