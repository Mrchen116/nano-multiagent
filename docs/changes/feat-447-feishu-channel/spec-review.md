## Issues

按 CRITICAL > WARNING 排序。

### CRITICAL

1. **[CRITICAL] [验收标准 vs 范围：文件夹操作缺失]**
   范围与非目标写了「创建文件夹、移动文件」，Q4 Agent 解读也列了，但验收标准无任何文件夹/移动文件的 Scenario。
   **不改→下游坏事**：change-orchestrator 将验收标准透传给 reviewer，reviewer 的清单里没有文件夹操作，这部分功能做成什么算合格完全靠猜，要么漏验要么 reviewer 越权自行定义。

2. **[CRITICAL] [验收标准 vs 范围：文档读取操作缺失]**
   范围与非目标写了「读取」，Q4 解读列了「读取内容」，但验收标准无「读取文档」Scenario。创建和编辑有了，唯独读取蒸发。
   **不改→下游坏事**：design-author 不知道「读取」的预期行为是什么——是全文读取？选段读取？读取失败时怎样？会漏设计或过度设计。

### WARNING

3. **[WARNING] [S6「未 @ 消息作为上下文」：THEN 措辞模糊]**
   THEN 写「Bot 的回复能参考前 3 条消息的上下文内容」——「能参考」验收时难以判定。
   **不改→下游坏事**：reviewer 验收时不知道「参考」的判定标准，可能放过完全没用上下文的回复。建议改为更可观测的描述（如「Bot 的回复内容与前 3 条消息的话题相关」或拆一个具体示例）。

4. **[WARNING] [诉求「读取文档」/「创建文件夹」/「移动文件」：缺失败态 Scenario]**
   云文档操作有 S12（未授权）但缺其他异常：API 调用失败、文档不存在、无权限编辑他人文档等。
   **不改→下游坏事**：design 会漏掉错误处理路径，用户遇到异常时体验不确定。但作为 spec 层可以只列代表性失败态，不穷举——至少补一个「API 调用失败时用户看到什么」。

## Recommendations（不阻断门禁）

- 「合理时间内回复」可以量化（如「5 秒内」），让验收有明确阈值。不量化也行，下游 design 自行定义。
- 群聊 session 隔离的两种模式（群维度 vs 群+用户维度）在用户场景里提到了，但验收标准没有覆盖「可配置」行为——如果这是需求的一部分，建议补一条 Scenario。
- S8 只验证了 plato-bot，可以考虑补一条 GIVEN 描述泛化到所有 Bot。
