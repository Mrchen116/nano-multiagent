# feat-541: Agent 模型备用链

## 原始需求

> 当前一个agent只能配一个模型，如果那个模型欠费了，或者服务崩了就没得用了。看看Hermes agent，openclaw分别怎么设计的

> 立项，按openclaw的方式吧。

## 澄清记录

- Q1: 本期只做「Agent 主模型 + 有序备用模型，失败自动换模型」，还是连「同一家供应商多把钥匙轮换」一起做？
  A(原话): 对。「Agent 主模型 + 有序备用模型，失败自动换模型」
  Agent 解读: 本期不做同供应商多凭证轮换；产品能力就是每个 Agent 一个主模型加有序备用列表，失败时按序换模型。

- Q2: 主模型失败并切到备用之后，后面几轮还继续用备用，还是每条新消息都先再试一次主模型？
  A(原话): 好
  Agent 解读: 按 OpenClaw 粘在能用的备用上，直到用户 `/new` 开新会话，或在 Agent 配置里改模型列表。不把自动切换写回 Agent 保存的主模型。

- Q3: 备用模型列表在哪配？
  A(原话): 大概是在这个位置，但是要设计的有技巧点，默认可能得折叠，用户希望设置再展开之类的，不然太占位置了，而且这也不是重点
  Agent 解读: 入口仍在 Agent 新建/编辑页、紧挨现有主模型选择器；默认折叠，用户要点开才设置。备用链是次要配置，不能把表单撑满。

- Q4: 真切到备用之后，聊天里要不要让人看出来？
  A(原话): 要的，外部通道也要
  Agent 解读: Web IM 和飞书等外部通道都要有轻量提示：本轮因主模型不可用已改用备用。不弹窗、不要求确认；粘在备用后不必每条消息都重复喊。

- Q5: 什么失败才自动换模型？欠费、服务崩了之外，限流/过载/超时/认证失败算不算？上下文太长换不换？
  A(原话): 好
  Agent 解读: 欠费/额度、服务挂了或过载、超时、限流、认证失败都换。上下文太长不换模型，仍走既有压缩/失败路径。

- Q6: 心跳、定时任务这类没人盯着的回复，也走同一条备用链吗？（先说明 OpenClaw：心跳是会话里的一次普通 turn，cron 显式走同一套 failover，都用该 Agent 的 primary + fallbacks。）
  A(原话): 好
  Agent 解读: 人工聊天、心跳、cron 都走该 Agent 的同一条备用链。

- Q7: 用户没展开、没配备用列表时，主模型失败怎么办？
  A(原话): 好，没配就像现在一样，失败呈现
  Agent 解读: 没配备用列表时不偷偷用平台默认或其他 Agent 的模型顶上；主模型失败就按现状失败呈现。折叠默认等于没配。

- Q8: 剩下细节按推荐写进 spec；确认在范围 / 非目标（Agent 页折叠备用列表；欠费/额度、宕机过载、超时、限流、认证失败按序换，上下文超长不换；本轮继续回复并在 Web IM 与外部通道轻量提示，粘到 `/new` 或改配置；心跳与 cron 同链；没配或整链耗尽失败呈现与现在一样；不写回保存的主模型。非目标：多钥匙轮换、节点/全局默认备用链、Coding CLI、聊天 `/model`、辅助任务单独备用链、工具审批专用模型失败语义。）
  A(原话): dui
  Agent 解读: 按 Q8 列出的范围与非目标定稿。

- Q9: 主模型失败时，是先让用户看到失败再自动换，还是静默换？失败文案要不要带模型名？
  A(原话): 我说错了，应该是先让用户看到「⚠️ 模型调用失败:…」再换模型跑。而且这句错误提醒可能得换一下，得显示具体是哪个模型，否则如果切到备选还是失败，用户没法感知到
  Agent 解读: 可用性失败先投下带该模型名的失败气泡，然后同一轮自动改用下一候选继续跑，用户不必再发一条。备用也失败时，每条失败都带对应模型名。不是先失败然后等用户再发下一条才换。

## 用户场景

用户有一个日常助手 Agent，主模型选了常用的付费模型。某天这家欠费或服务挂了，现在：发出去的消息整轮失败，心跳和定时任务一起停，只能打开 Agent 编辑页手改模型，改完旧聊天才能再聊。备用方案要么没有，要么得占一整块表单，和「选哪个主模型」抢视线。

将来：主模型选择器还在原来的位置，是配置的重点。它旁边（或紧下方）有一个默认收起的次要入口，点开才看到有序备用列表——从该节点可用模型里按优先级往下加，不配就不占地方。保存后 Agent 页上显示的仍是原来选的主模型，不会因为某次自动切换被改掉。

用户照常在 Web IM 或飞书里发消息。这一轮主模型因欠费、额度、服务挂了/过载、超时、限流或认证失败用不了时，用户**先看到**一句带该模型名的失败提示（在今天「⚠️ 模型调用失败:…」上标明是哪个模型），然后系统按列表顺序改用下一个备用模型，**不必再发一条消息**，本轮仍然给出备用模型的回复，并在回复附近留一句轻量说明：已经改用某某模型，因为主模型不可用。不弹窗、不用点确认。飞书等外部通道同样看得到失败提示和这句说明。若备用也失败，用户能从下一条失败提示里看出是另一个模型挂了。之后在这个聊天里继续聊，默认接着用这个能用的备用，不再每条消息都提示一遍，也不再回头撞已经挂掉的主模型。用户发 `/new` 开新会话，或回去改了这个 Agent 的主模型/备用列表，这个聊天才重新从主模型试起。另一个聊天互不影响：那边仍先试主模型，自己失败了再走同一条备用链。

没展开、没加任何备用时，行为和今天一样：主模型失败就失败呈现（文案带上该模型名），不会偷偷拿节点平台默认或其他 Agent 的模型来顶。备用也全部失败时，每个失败的候选都留下带模型名的失败提示，没有伪装成功的回复。上下文太长走现在的压缩或失败路径，不换模型。心跳 tick 和 cron 任务用同一条链；它们若向用户发出可见内容，同样先有带模型名的失败提示（若发生了可用性失败），成功切换时再带那句轻量说明。

## 验收标准

### Requirement: Agent 配置页可设置有序备用模型，且默认不占地方

#### Scenario: 默认折叠，主模型选择仍是重点
- **WHEN** 打开 Agent 新建页或编辑页
- **THEN** 主模型选择器仍在原位置，可单独完成「这个 Agent 用哪个模型」
- **AND** 备用模型区域默认收起，不把表单撑高到需要滚动才能看到主模型以外的常用项

#### Scenario: 展开后按序添加备用并保存
- **GIVEN** 该 Agent 所在节点有多个可用模型
- **WHEN** 用户展开备用区域，按优先级加入一个或多个与主模型不同的模型并保存
- **THEN** 再次打开该 Agent 编辑页时，展开后仍看到同一顺序的备用列表
- **AND** 未展开时仍能看出「已配备用」（例如数量），不必先展开才能知道配没配

#### Scenario: 清空备用后与从未配置等价
- **GIVEN** 某 Agent 已保存过备用列表
- **WHEN** 用户把备用全部去掉并保存
- **THEN** 该 Agent 不再有备用链，之后主模型失败按现状失败呈现

### Requirement: 主模型因可用性失败时本轮改用备用并继续回复

#### Scenario: 欠费或服务不可用时本轮仍收到回复
- **GIVEN** Agent 保存了有序备用列表，且当前聊天尚未因失败粘在备用上
- **WHEN** 用户发一条消息，主模型因欠费、额度、服务挂了或过载、超时、限流或认证失败而无法完成本轮
- **THEN** 用户先看到带该主模型名的失败提示
- **AND** 不必再发一条消息，本轮按备用列表顺序改用下一个能用的模型，并收到该备用模型的回复

#### Scenario: 上下文太长不换模型
- **GIVEN** Agent 配备用列表
- **WHEN** 本轮失败原因是上下文太长
- **THEN** 不改用备用模型，仍走今天的压缩或失败呈现

#### Scenario: 没配备用时失败呈现与现在一样
- **GIVEN** Agent 没有备用列表（含默认从未展开过）
- **WHEN** 主模型本轮失败
- **THEN** 失败呈现与变更前一致，不改用节点平台默认模型，也不借用其他 Agent 的模型

#### Scenario: 整条备用链都失败时按现状失败呈现
- **GIVEN** Agent 配备用列表，且主模型与全部备用都因可用性失败
- **WHEN** 用户发一条消息
- **THEN** 每个失败的候选都留下带该模型名的失败提示，用户能区分是哪一个挂了
- **AND** 没有伪装成功的回复

### Requirement: 换到备用时 Web IM 与外部通道都有轻量说明，且不打扰后续轮次

#### Scenario: 首次切换时 Web IM 看到说明
- **WHEN** 某聊天本轮因主模型不可用改用了备用模型
- **THEN** Web IM 在该轮回复附近显示轻量说明：已改用该备用模型，因为主模型不可用
- **AND** 不出现必须确认的弹窗或按钮

#### Scenario: 外部通道同样看到说明
- **WHEN** 同一轮切换发生在飞书等外部通道触发的对话
- **THEN** 该通道里用户同样看得到等价的轻量说明，不必回 Web IM 才能知道已经换模型

#### Scenario: 粘在备用上之后不再每条都提示
- **GIVEN** 该聊天已经切到备用并继续用它
- **WHEN** 用户再发下一条普通消息且本轮没有再次换到另一个模型
- **THEN** 回复正常给出，不再重复那句切换说明

### Requirement: 切换粘在当前聊天，不改写 Agent 保存的主模型

#### Scenario: 编辑页仍显示原来保存的主模型和备用列表
- **GIVEN** 某聊天已经自动改用备用模型
- **WHEN** 用户打开该 Agent 的编辑页
- **THEN** 主模型选择器与备用列表仍是保存过的配置，没有被改成当前正在用的备用

#### Scenario: 同一聊天后续轮次继续用能用的备用
- **GIVEN** 某聊天本轮已改用备用模型 B
- **WHEN** 用户在同一聊天接着发消息，且用户没有 `/new`、也没有改该 Agent 的主模型或备用列表
- **THEN** 新回复继续使用 B，不再先撞已经失败的主模型

#### Scenario: `/new` 后重新从主模型试起
- **GIVEN** 某聊天已粘在备用模型上
- **WHEN** 用户在该聊天发送 `/new`
- **THEN** 之后的普通消息重新从保存的主模型试起；主模型再次因可用性失败时才再走备用链

#### Scenario: 改 Agent 模型配置后重新从主模型试起
- **GIVEN** 某聊天已粘在备用模型上
- **WHEN** 用户保存对该 Agent 主模型或备用列表的修改
- **THEN** 该聊天下一次新回复按刚保存的配置从主模型试起

#### Scenario: 另一个聊天互不影响
- **GIVEN** 同一 Agent 的聊天甲已粘在备用模型上
- **WHEN** 用户在该 Agent 的另一个尚未切换过的聊天乙发消息
- **THEN** 聊天乙仍先使用保存的主模型；它自己遇到可用性失败时才按同一条备用链切换

### Requirement: 心跳与定时任务走同一条备用链

#### Scenario: 心跳在主模型不可用时仍能完成 tick
- **GIVEN** Agent 配备用列表
- **WHEN** 一次心跳 tick 时主模型因可用性失败
- **THEN** 该 tick 按备用链改用能用的模型并完成，而不是整次心跳失败停住
- **AND** 若这次心跳向用户发出了可见内容，内容旁带与聊天相同的轻量切换说明

#### Scenario: 定时任务在主模型不可用时仍能跑完
- **GIVEN** Agent 配备用列表
- **WHEN** 一次 cron 任务执行时主模型因可用性失败
- **THEN** 该次执行按备用链改用能用的模型并完成
- **AND** 若这次任务向用户发出了可见内容，内容旁带与聊天相同的轻量切换说明

## 范围与非目标

- 在范围:
  - Agent 新建/编辑页、紧挨主模型选择器的折叠式有序备用列表；
  - 欠费/额度、服务挂了或过载、超时、限流、认证失败时按序换模型；先投下带模型名的失败提示，再在同一轮继续回复；
  - Web IM 与飞书等外部通道的轻量切换说明（首次切换提示，粘住后不每条重复）；
  - 按聊天粘在能用的备用上，直到该聊天 `/new` 或用户改该 Agent 的主模型/备用列表；不写回保存的主模型；
  - 心跳与 cron 走同一条链；
  - 没配备用或整条链耗尽时，失败呈现与现在一样。
- 非目标:
  - 同一家供应商多把钥匙 / 多账号轮换；
  - 节点级或全局默认备用链（没配的 Agent 不偷偷继承一条安全网）；
  - Coding CLI；
  - 聊天里 `/model` 手动切模型；
  - 生图、视觉、压缩等辅助任务的单独备用链；
  - 改变工具审批专用模型失败后不改用对话模型的既有语义。

## 移交 design 的说明

澄清中遇到、但属实现层或视觉层的问题，留给 change-design-author:

1. 折叠入口的具体控件形态（文案、是否显示已配数量、展开后如何增删排序）——用户要求「有技巧、默认折叠、不占位置」，spec 只锁这个体验，不锁组件样子；
2. 轻量切换说明在 Web IM 气泡旁、飞书卡片/正文里分别怎么呈现，具体措辞；
3. 候选链的执行落点（产品层在每轮开始前换模型，还是运行中换）以及与「已产出部分回复后不得原位重放」的既有恢复语义如何对齐；
4. 「粘在备用上」按聊天记住的方式，以及 `/new`、改 Agent 配置如何清掉；
5. 切到备用模型时推理强度怎么取（该备用模型自己的默认档，还是沿用会话里仍合法的 `/effort`）。
6. 失败提示如何带上模型名、以及换候选时如何避免 IM 里再出现一条重复的用户消息（Q9 已锁用户可见顺序）。
