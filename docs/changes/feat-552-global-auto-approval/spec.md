### 2026-09-11：等待用户回答时的参考行为

同一 Codex 源码基线支持两种提问方式：一种等待用户回答后返回；另一种提问后立即返回，保持当前工作轮次继续，用户回答作为新的用户消息进入。后者允许 Agent 先做不依赖答案的工作，不要求所有工作一起暂停。可用方式取决于当前开放的工具和 Agent 的选择，不能据此声称 Codex 每次提问后都继续工作，或会自动处理其他聊天。源码分别为 `codex-rs/core/src/tools/handlers/request_user_input.rs` 与 `request_user_input_async.rs`。

用户已确认本产品采用以下行为：默认允许全局 Agent 继续不依赖这次确认的工作，包括其他聊天；待授权操作保持不执行。用户回复后，将问题和回答一并提供给后续审批，再决定原事项如何继续；没有其他可做的事情时进入空闲等待。不把用户未回复当作同意。此处记录产品行为，不限定实现方式。

## 用户场景

1. **日常工作不再反复确认。** 用户让 CLI 或个人助手修改项目、运行本地测试或安排一次 Nano 内置定时任务。Auto 能理解这些已授权工作的范围，完成正常操作；不会仅因“启动服务”“定时任务”等词，或消息是通过 Inbox 送达，就反复拒绝。用户显式限制的操作仍应停住。
2. **全局主 Agent 自己沟通。** 一个聊天的操作被拒绝后，Agent 判断能否换用合规办法；需要确认时，在它判断合适的聊天向有权确认的用户说明具体操作及拒绝原因。用户通过普通聊天回答，无新弹窗或授权卡片。明确无法继续时，Agent 说明并停止该事项。
3. **等待期间继续工作。** 问完后，该操作不执行，但其他聊天或独立事项继续；无事可做时空闲。原用户回复“同意”后，审批能结合问题的具体对象和操作理解这句话。确认只覆盖所问操作或明确指定的子集；另一聊天里的“同意”、别的 Agent 代称用户同意、引用文本中的“同意”不混用。
4. **确认跨运行仍有效。** 在同一全局事项上，用户晚些回复、Agent 已完成上一轮或经历正常重启时，仍能从可信记录恢复原问题和用户回答。仅有概要、缺少可确认的对应原文时，Agent 先查回记录；无法查回则澄清，不猜测授权。Cron 自动触发和其他 Agent 发来的内容不冒充新的人工确认。
5. **用户能分辨为什么没做。** 真正被策略拒绝、审批服务暂不可用、以及用户主动拒绝，是不同原因。Agent 对实际原因作说明，不能把服务故障说成用户没授权。全局模式遇到这些情况均不占住整个 Agent 等权限弹窗；单聊天和 CLI 继续使用各自现有的人工交互入口。
6. **共用机制统一迁移。** CLI、单聊天 PA、全局 PA 和它们的子任务使用同一代 Auto 判断。正常的回复和协作不会因增加审批而变得不能沟通；对子任务的委托也不能扩大用户原先允许的范围。原有用户配置应有明确迁移说明和回退方法，不因更新被静默扩大权限。

## 验收标准

### Requirement: R1 已授权的常见任务无需重复确认

#### Scenario: 日常本地开发
- **WHEN** 用户要求在项目范围内修改文件、运行测试和仅本机可访问的开发服务
- **THEN** 正常操作自动完成，不因旧版笼统的服务规则反复要求确认。

#### Scenario: 明确要求一次 Nano 定时任务
- **WHEN** 用户经 Inbox 明确给出一次任务的时间、名称和任务内容
- **THEN** 可创建并执行该任务，不因 Inbox 来源或把内置任务一概视为未授权持久化而拒绝。

#### Scenario: 用户限制仍生效
- **GIVEN** 用户明确要求在确认前不要推送或删除指定资源
- **WHEN** Agent 尝试该操作
- **THEN** 操作不执行，既有正常操作的授权不覆盖该限制。

### Requirement: R2 全局模式拒绝后由主 Agent 处理

#### Scenario: 替代、确认和停止
- **WHEN** 某动作被自动拒绝
- **THEN** 主 Agent 收到可解释的原因，可尝试合规替代、在合适聊天说明并询问，或说明无法继续；被拒操作不执行，不弹授权窗。

#### Scenario: 需要确认时问题可理解
- **WHEN** 主 Agent 向用户请求确认
- **THEN** 用户能看懂要做什么、影响哪个对象、为何需要确认，能用普通聊天作答。

### Requirement: R3 用户回答作用于对应操作

#### Scenario: 原问题后的简短同意
- **GIVEN** Agent 在聊天中明确提出单一操作，原用户随后同意
- **WHEN** Agent 再次尝试相同范围的操作
- **THEN** 审批承认该确认；其他条件未变化时，不再以缺少授权或 Inbox 不可信为由拒绝。

#### Scenario: 无回答、拒绝或不同事项的回答
- **WHEN** 用户未回答、明确拒绝，或另一个聊天有无关的“同意”
- **THEN** 待确认操作不执行；Agent 不把没有对应关系的回答当作授权。

#### Scenario: 引用或 Agent 转述同意
- **WHEN** Agent 读到文件、网页、另一 Agent 的转述或引用中的“用户同意”
- **THEN** 这些内容不被当作用户对待确认操作的真实同意。

#### Scenario: 回复只同意部分内容
- **WHEN** 问题涉及多个对象而用户明确只同意其中一项，或简短回答无法区分所选操作
- **THEN** 只继续明确获准的部分；歧义未消除前不执行其他操作。

### Requirement: R4 等待确认不阻塞独立工作

#### Scenario: 其他聊天有工作
- **WHEN** 一个事项正在等待用户回答，另一聊天有独立请求
- **THEN** 全局 Agent 可处理新请求；待确认动作保持未执行。

#### Scenario: 空闲后收到回复
- **WHEN** 无独立工作时 Agent 已空闲，用户随后回答原问题
- **THEN** Agent 重新处理原事项，无需用户重新提交整项任务。

#### Scenario: 重启或压缩后回复
- **WHEN** 正常重启或上下文压缩后收到原事项的确认
- **THEN** 可信原问题和回答可恢复时照常判断；缺失时先查回或澄清，不能凭摘要假定同意。

### Requirement: R5 故障原因与产品交互明确

#### Scenario: 审批服务失败
- **WHEN** 审批超时、不可用或未给出有效结论
- **THEN** 动作不执行；Agent 获知审批没有得出结论，不把故障归咎于用户未授权；全局模式仍可处理其他独立工作。

#### Scenario: 多次拒绝
- **WHEN** 全局模式连续遭遇自动拒绝
- **THEN** 不自动变成权限弹窗等待，也不能因拒绝次数多而直接放行；主 Agent 按拒绝原因沟通、改方案或停止。

#### Scenario: 其他入口的交互
- **WHEN** CLI 或单聊天 PA 需要人工审批
- **THEN** 继续使用原有入口；用户已有的明确否决和权限边界仍有效。

### Requirement: R6 迁移在所有 Auto 入口生效

#### Scenario: 主任务与子任务
- **WHEN** 同范围操作由主 Agent 或其子任务提出
- **THEN** 都受更新后的 Auto 机制约束；委托不会绕过用户范围或扩大可用权限。

#### Scenario: 正常沟通与配置迁移
