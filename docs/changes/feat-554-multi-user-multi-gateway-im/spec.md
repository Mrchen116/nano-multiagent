# feat-554: 多人、多 Gateway 的人机协作 IM

状态：需求已确认，首文档定稿；下一步进入技术设计，尚未实施。

## Relations

- Related: feat-546
- Related: feat-552

沿用全局 Agent 的持续工作能力与分模式授权体验。本单元改变多人协作和聊天可见性，不重做 Agent 工作机制。

## 原始需求

> 我想把我们的系统变成多人多gateway的真正IM。但是我没想好gateway和人之间的关系，一个人肯定可以用多个gateway，多人可以在一个群里，一起控制agent。我想真正像公司里一样，人和agent一起做很多事情。

> 我想一开始简单点，不要搞太复杂的权限管理。

## 澄清记录

- Q1：你是否希望支持“团队共有的 Agent”，即由指定的人管理，但团队成员可以共同向它交办工作，它不会因为某个成员离开而被带走？
  当轮推荐（以用户回答为准）：支持个人 Agent 和团队 Agent；Gateway 的设备管理与 Agent 的协作使用分别表达。
  A（原话）：我想一开始简单点，不要搞太复杂的权限管理。
  Agent 解读：首期优先简化权限；尚未确认团队共有 Agent，不将此前推荐视为已接受。

- Q2：第一版采用“Gateway 和 Agent 各有一个管理者，Agent 入群后群成员都能交办工作，配置只由管理者修改”的规则是否符合预期？
  当轮推荐（以用户回答为准）：一个人可以管理多个 Gateway，Agent 随所属 Gateway 由同一人管理；暂不引入组织、角色或逐人授权配置。管理者将 Agent 加入群即允许群成员向它交办工作，不同时授予 Agent 配置或设备管理权限。
  A（原话）：好
  Agent 解读：确认 Q2 推荐；人无需拥有 Gateway 即可参与 IM 协作。此前 Q1 的个人／团队 Agent 分类不纳入首期。

- Q3：Agent 在群里请求某次工具执行批准时，是否允许群内任意人批准或拒绝？
  当轮推荐（以用户回答为准）：群成员均可决定本次执行，首个有效决定生效并向群内显示决定者；长期授权与 Agent 配置仍仅由管理者修改。
  A（原话）：首先，全局模式不会弹，单thread模式弹出来谁都可以按
  Agent 解读：全局模式不弹批准卡；单 Thread 模式弹出的批准卡，群内任何人都可以操作，不额外按卡片选项限制操作者。撤回此前“长期授权仅管理者可改”的推荐限制。Agent 配置的管理归属仍遵循 Q2；首个有效决定及处理人展示尚未作为用户确认项。

- Q4：除了在共同群里协作，其他用户是否也可以直接私聊你的 Agent？
  当轮推荐（以用户回答为准）：可以；Agent 作为 IM 联系人可以被其他用户找到并发起私聊，仍由原管理者管理配置。
  A（原话）：可以
  Agent 解读：其他用户可以直接私聊该 Agent；Agent 配置仍由原管理者管理。

- Q5：别人和你的 Agent 私聊时，你作为管理者是否也能在 IM 中查看这段私聊？
  当轮推荐（以用户回答为准）：IM 中聊天按参与关系可见，私聊只对参与者显示、群聊只对群成员显示；管理 Agent 不自动获得它参与的所有聊天的查看权。此处讨论 IM 产品内可见性，不承诺对 Gateway 所在机器的管理者隐藏本地运行数据。
  A（原话）：好
  Agent 解读：确认 IM 内聊天按成员关系可见。工作视图、搜索、附件等入口也不能绕过这项规则暴露非成员聊天；这是同一可见性规则的约束，不增设权限配置。

- Q6：第一版是否以“多人真正能在 IM 里沟通，并共同使用不同 Gateway 上的 Agent”为交付范围？
  当轮推荐（以用户回答为准）：包含注册登录、查找人和 Agent、人际私聊、人与 Agent 私聊、多人和多 Agent 群聊、一个人绑定多个 Gateway，以及 Q2–Q5 已确认的管理与可见性规则；暂不加入组织部门、团队资产归属、角色权限配置和独立任务看板。Agent 的既有工作能力继续使用。
  A（原话）：好
  Agent 解读：首期范围按上述推荐收口。以下场景与验收标准是 Q2–Q6 的可观察展开；此前未被接受或被撤回的推荐不构成要求。

## 现状与目标

当前 [账号与租户契约](../../specs/im/auth-tenancy.md)按 owner 隔离会话、Agent 和节点；[节点契约](../../specs/im/agents-nodes.md)将节点及其 Agent 归给绑定者。[群聊契约](../../specs/im/conversations-messages.md)也沿用 owner 隔离，不能直接表达不同账号参与同一个群的共同访问权。

目标保留个人对 Gateway 和 Agent 的管理归属，同时让人与 Agent 按 IM 联系人关系沟通，让聊天按成员关系可见。能找到、联系一个 Agent，不等于能修改它的配置或查看它参与的其他聊天。

当前[全局工作视图](../../specs/im/agent-work.md)展示跨聊天连续轨迹。目标中的聊天可见性也约束这类入口，不能从工作视图绕过聊天成员限制。本文定义目标行为，不将目标提前覆盖到 current specs。

## 用户场景

1. **没有机器也能成为同事。** 小李注册并登录 IM，没有绑定 Gateway，也能找到小陈、与他私聊，加入共同项目群。用户不用先部署 Agent 才能使用 IM；找不到联系人时能辨认空结果。

2. **一个人带来多台机器上的 Agent。** 小陈将 MacBook 和 Mini 两个 Gateway 绑定到自己账号，分别管理上面的开发 Agent 和资料 Agent。小王也有自己的 Gateway 和测试 Agent。每个 Gateway 及其 Agent 都有一个管理者；其他人能联系这些 Agent，但不能因此修改它们的配置。某个 Gateway 离线时，相关 Agent 显示不可用，不影响人与人、其他在线 Agent 的沟通。

3. **像联系人一样直接找 Agent。** 小李找到小陈的开发 Agent，直接私聊交办工作，无需小陈逐人授权。Agent 使用已有工作能力响应，小李能收到回复、刷新后回看历史。这个私聊的参与者是小李和开发 Agent，小陈不会因为管理该 Agent 就自动看到这段聊天。

4. **围绕项目共同做事。** 小陈、小李、小王建立项目群，各管理者把自己的 Agent 加进群。小李交办开发，小王补充测试要求，小陈补充背景，群成员都能向群内 Agent 交办工作并看到群内交付。Agent 位于不同 Gateway 不影响群内身份和交流，继续遵循既有提及、触发和工作模式。群支持既有改名、成员增减和解散操作，不新增组织角色配置；移出群的成员不能再读取或参与该群，解散权限沿用创建者规则。

5. **协作不反复找管理者审批。** 全局模式不弹批准卡，继续沿用既有自动审批及必要时主动聊天确认的体验。单 Thread 模式出现批准卡时，该聊天内的人都可操作卡片现有选项，包括不是 Agent 管理者、也不是原任务发起人的群成员。多人操作同一张卡时，不能让同一次执行因重复点击被重复执行。

6. **按聊天参与关系回看工作。** 小李只看到自己参与的私聊和群聊，收到这些聊天的新消息、过程及交付。小陈可以管理开发 Agent，但不能在 IM 的聊天列表、历史、实时通知、附件或工作轨迹中看到小李与它私聊的内容，除非自己也是该聊天的参与者。全局 Agent 仍能跨聊天工作，但产品展示不能把混合了其他私聊内容的整体轨迹直接公开给无权查看这些聊天的人。已有聊天和管理关系在升级后保留，不通过给所有人开放历史来实现多人协作。

## 验收标准

### Requirement: 用户无需 Gateway 即可注册登录并查找联系人

#### Scenario: 无 Gateway 的用户开始沟通
- **WHEN** 新用户注册并登录 IM，查找另一个人或 Agent
- **THEN** 能找到对应联系人，并辨认联系人是人还是 Agent
- **AND** 无需先绑定 Gateway 或创建自己的 Agent

#### Scenario: 没有匹配联系人
- **WHEN** 用户查找不存在的人或 Agent
- **THEN** 显示可辨认的空结果，不发起错误对象的聊天

### Requirement: 人与人可以跨账号私聊并持久回看

#### Scenario: 两个账号实时沟通
- **GIVEN** 两个人分别登录自己的账号
- **WHEN** 一方找到另一方并发起私聊，双方发送消息
- **THEN** 双方在同一私聊中看到彼此消息和真实发送者
- **AND** 刷新或重新登录后能回看已发送的历史，未参与者看不到该私聊

### Requirement: 一个人可以管理多个 Gateway 及其 Agent

#### Scenario: 同一人绑定多台设备
- **WHEN** 一个人绑定两个 Gateway 并查看各自的 Agent
- **THEN** 能辨认各 Agent 所属 Gateway，并管理自己名下的配置

#### Scenario: 协作者不能修改他人的设备或 Agent 配置
- **GIVEN** 用户可以私聊他人 Agent，或与该 Agent 同在一个群
- **WHEN** 用户尝试修改该 Agent 或其 Gateway 的配置
- **THEN** 无法保存修改；原管理者的配置保持不变

#### Scenario: 单台设备离线
- **WHEN** 一个 Gateway 离线
- **THEN** 用户能辨认其 Agent 不在线，不会看到尚未发生的执行被显示为完成
- **AND** 人与人的聊天和其他在线 Gateway 上的 Agent 仍可正常使用

### Requirement: 用户可以直接私聊其他人管理的 Agent

#### Scenario: 跨管理归属交办工作
- **GIVEN** 某 Agent 在线，由另一名用户管理
- **WHEN** 用户找到该 Agent 并直接发起私聊、交办工作
- **THEN** 不要求管理者先对该用户单独授权，Agent 能按既有工作能力处理并交付
- **AND** 双方身份与后续聊天历史保持稳定

### Requirement: 多人与不同 Gateway 上的 Agent 可以在同一群协作

#### Scenario: 建立混合成员项目群
- **WHEN** 多个账号加入同一群，各管理者把不同 Gateway 上的 Agent 加入该群
- **THEN** 所有人看到同一个群及一致的成员身份，群中可同时包含多人和多个 Agent
- **AND** 不要求人或 Agent 归属同一个 Gateway 管理者

#### Scenario: 不同群成员共同交办工作
- **GIVEN** 多人与多个在线 Agent 同在群内
- **WHEN** 不同的人按既有触发规则向群内 Agent 交办工作、补充要求
- **THEN** 这些人的消息均能作为相应 Agent 的用户输入，不限于管理者或最初发起人
- **AND** 群内正式回复向群成员实时呈现，刷新后仍可回看

#### Scenario: 群成员与群名变更
- **WHEN** 用户按既有群管理规则修改群名、增减成员或由创建者解散群
- **THEN** 群成员看到相应变化，不要求配置组织或角色权限表
- **AND** 移出的成员不能继续读取该群或向其交办工作；其他成员在群未解散时仍可继续协作

### Requirement: 工具批准遵循工作模式且不新增人员权限配置

#### Scenario: 全局模式不弹批准卡
- **WHEN** 全局 Agent 在多人协作中处理需要授权判断的操作
- **THEN** 不弹出工具批准卡，继续采用既有全局模式的自动审批及主动沟通行为
- **AND** 不因支持多人而绕过原有授权判断

#### Scenario: 单 Thread 模式的群成员可操作批准卡
- **GIVEN** 单 Thread Agent 在群中展示一张待处理批准卡
- **WHEN** 非 Agent 管理者且非原任务发起人的群成员操作卡片现有选项
- **THEN** 其决定可被接受，不因身份限制某个现有选项
- **AND** 生效结果在该聊天内一致呈现，不把卡片操作扩大为修改 Agent 配置的权限

#### Scenario: 同一张卡被多人操作
- **WHEN** 群成员先后或同时处理同一张批准卡
- **THEN** 该卡只有一个生效决定，后续界面反映实际状态，不因重复操作重复执行工具

### Requirement: IM 聊天内容按参与关系可见

#### Scenario: Agent 管理者不是私聊参与者
- **GIVEN** 小李与小陈管理的 Agent 私聊，小陈未参与该私聊
- **WHEN** 小陈在 IM 中浏览聊天、打开历史或尝试查看这段私聊的附件
- **THEN** 无法看到或读取该私聊内容，不因管理 Agent 获得查看权
- **AND** 小李可以正常读取自己的聊天和附件

#### Scenario: 群聊只向群成员开放
- **WHEN** 未入群用户尝试读取群聊历史、接收群内实时内容或访问聊天附件
- **THEN** 无法获得这些内容；当前群成员可以正常收发和回看

#### Scenario: 工作轨迹不绕过聊天可见性
- **GIVEN** 全局 Agent 已处理来自不同私聊和群的工作
- **WHEN** 用户查看 IM 中的工作轨迹、关联子执行或过程明细
- **THEN** 不向用户展示其未参与聊天的消息正文及承载该私聊内容的执行细节
- **AND** 不能通过链接跳转、刷新回看或实时事件绕过同一限制

### Requirement: 既有使用数据和工作能力在升级后保留

#### Scenario: 原用户继续使用
- **GIVEN** 原用户已有 Gateway、Agent、私聊、群聊和历史消息
- **WHEN** 系统升级支持多人协作，该用户重新登录
- **THEN** 原管理归属和既有聊天仍可使用，历史保持可回看
- **AND** 不向未参与的其他账号开放历史，Agent 的既有工作模式和能力继续可用

## 范围与非目标

- 在范围：注册登录与联系人查找、人际私聊、跨管理归属的 Agent 私聊、多人与多 Agent 群聊、多 Gateway 个人管理、已确认的分模式批准卡规则、基于聊天成员的可见性，以及既有数据与使用方式的承接。
- 非目标：组织部门体系、团队资产归属、角色权限表、逐人授权配置、独立任务看板；不重做 Agent 的既有工作机制。
- 可见性规则约束 IM 产品内访问与展示；本单元不承诺向 Gateway 所在机器的管理者隐藏机器上的本地运行数据，也不将聊天展示规则扩展为新的一套模型记忆隔离机制。

## 设计交接

设计需要落实管理归属与聊天参与关系的分离，并覆盖所有承载聊天内容的入口，尤其是当前跨聊天的全局工作视图。具体实现方案、数据承接方式及实施拆分由 design 阶段确定。不得通过隐藏所有既有工作能力或给管理者默认开放全部私聊来回避上述要求。
