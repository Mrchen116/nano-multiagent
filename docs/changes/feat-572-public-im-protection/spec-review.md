## W1 — 外部渠道发起人的公司资格适用规则未收口

**位置**：`spec.md:350-373`（尤其 351、357、372-373）；关联 `spec.md:188-201`、`333-346`、`107`。

**需求依据**：用户确认“所有用户属于一个公司，用户、agent共同协作”；正常注册后由管理员批准加入公司，待批准用户不能使用内部协作能力。Q12 最终决定（`spec.md:102`）是有效公司成员通过有效 Agent 共同维护公司任务，删除需要用户明确要求或确认；Q2 又要求“原本该怎么样就怎么样啊，原本就有一些设计了啊”。

**现有对外契约**：

- `docs/specs/gateway/task-graphs.md:39-42` 明确 Web IM 与外部聊天输入使用相同任务创建、查询和更新契约，不按输入渠道另建权限。
- `docs/specs/im/conversations-messages.md:148-158,358-360` 明确外部发送者保留独立外部身份，可以没有真实 IM 用户映射，不能自动当作 Gateway 管理者。
- `docs/specs/gateway/external-channels.md:18-26` 已有飞书私聊及群内交办入口。这是既有产品路径，不是新增假想渠道。

**遗漏与具体后果**：当前场景要求 Web IM 发起成员有效，也要求 Agent 及管理者有效，但没有规定：一位尚未取得有效公司资格、或没有 IM 身份映射的外部发送者，能否通过另一位有效成员的 Agent 查询、修改、明确要求删除公司任务。仅检查 Agent 及其管理者有效，和检查实际外部发起人有效，是不同的产品规则。设计者若沿用既有渠道能力，可以让公司准入限制之外的人借有效 Agent 操作全部公司任务；若自行要求外部发送者必须先绑定 IM 身份，又可能新增未经确认的登录或渠道限制并破坏既有外部交办体验。现有文字不足以选择其中一种；本审查没有证明实际实现存在访问旁路。

**建议**：在需求层明确“公司资格边界是否也约束外部渠道中向 Agent 交办公司任务的实际发起人”，并给出无 IM 身份映射、待批准或停用发起人在有效 Agent 上请求公司任务的可观察结果。可以明确外部交办沿用哪些既有授权，也可以要求核实有效公司资格；不要由设计者暗中选定。无需在首文档制定身份映射协议、字段、验证机制或新增审批角色。保持既有主动工作规则与外部聊天普通回复行为的范围清楚。
