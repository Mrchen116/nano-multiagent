- 用户明确的定位：所有用户属于同一公司，人和 Agent 共同协作；Gateway 可以运行在个人电脑或共用电脑上。
- Agent 解读：先以一套 IM 承载一家公司的协作为讨论基础，分别梳理成员资格、Agent 管理、Gateway 管理、资源使用与共同任务；不将上一轮评估中的建议视为已逐项确认的需求，也不自动扩大本 unit 的实施范围。
- Q3：正常注册后，新用户应如何取得公司内部的联系人、Agent 与共享 Work 访问资格？
  候选方案：正常注册后由管理员批准加入（推荐）；验证指定公司邮箱后自动加入；注册成功即自动加入。
  A（用户原话）：A
  最终决定：正常注册后由管理员批准加入公司。待批准用户可登录查看待批准状态，但不能访问公司联系人、Agent、共享 Work 或其他公司内部协作数据和能力；批准后按公司内部协作权限使用产品，不要求邀请码或额外 Cloudflare 登录。
- Q4：共用 Gateway 上的 Agent，是否可以由设备管理员以外的同事分别管理？例如你维护 Mini，小王和小李分别管理上面的开发 Agent 和运营 Agent。
  候选方案：允许设备管理员与 Agent 管理者不同（推荐，每个对象先保持一位管理者）；仍由设备管理员统一管理该 Gateway 上的全部 Agent，同事只参与使用。
  A（用户原话）：B吧，B不是更简单吗
  最终决定：选择 B，Gateway 及其上的全部 Agent 继续由同一位管理者统一维护。同事按既有协作规则联系 Agent、在群中交办工作，不因共同使用取得配置管理权；本 unit 不拆分 Gateway 与 Agent 管理归属，也不引入多人共同管理。
- Q5：群里共同交办工作后，产生的任务图应由谁查看并通过 Agent 继续推进？
  候选方案：参与该群的成员共享（推荐）；全公司成员共享；保持当前账号范围，只有 Agent 所属账号及其名下 Agent 可访问。
  A（用户原话）：A
  最终决定：群里共同交办工作后产生的任务图由该群成员共享；不同账号的群成员可查看任务图并通过 Agent 继续推进，不再因不是创建该图的 Agent 所属账号而被拒绝。本次明确调整这部分任务图访问契约，不将当前账号隔离视为目标要求。
- Q6：群任务图的访问资格是否随当前群成员变化？推荐加入群后可访问该群已有任务图，离开或被移出群后失去该群任务图的直接访问及继续推进资格；保留在公司共享 Work 中的已有内容仍遵循既有 Work 规则，不等于取得任务图访问权。
  A（用户原话）：好
  最终决定：权限跟随当前群成员。加入群后可查看该群已有任务图；退出或被移出群后失去直接访问和继续推进这些任务的资格。仍属于公司的用户可继续查看共享 Work 中按原规则可见的已有内容，这不授予任务图访问权。
- Q7：公司管理员是否可以停用成员，并立即收回该账号对公司内部数据与协作能力的访问资格，包括已登录设备和已建立的实时连接，同时保留其历史消息与任务记录供其他有权成员继续协作？
  Agent 推荐：允许停用，撤销后续访问、保留历史记录；恢复成员资格的规则及名下运行资源的处理不在本问题中预先决定。
  A（用户原话）：ok
  最终决定：管理员可停用成员，立即撤销该账号对公司内部数据和协作能力的访问资格，覆盖已登录设备及已建立的实时连接；保留其历史消息和任务记录，其他有权成员可继续访问和协作。
- Q8：停用成员时，其名下 Gateway 和 Agent 是否也同时停止接入公司 IM？
  Agent 推荐：同时停止接入，阻止通过已有机器连接或重新连接继续收发公司消息、读取公司数据和更新公司任务；保留已有配置与工作记录，不自动转移管理权，也不将该操作解释为远程关闭或接管成员电脑。
  A（用户原话）：好
  最终决定：停用成员时，其名下 Gateway 和 Agent 同时停止接入公司 IM；现有连接与重新连接均不能继续收发公司消息、读取公司数据或更新任务。已有配置和工作记录保留，不自动转移管理权，不远程关闭或接管电脑；其他同事也暂时不能使用这些 Agent，包括该成员管理的共用 Gateway 上的 Agent。
- Q9：私聊中产生的任务图，是否也按聊天成员访问，Agent 管理者不因管理该 Agent 自动取得其未参与私聊中的任务图访问权？
  Agent 推荐：与群任务和原聊天权限保持一致，按私聊参与者访问；公司共享 Work 中已经出现的内容仍按既有规则可见，但不扩大原聊天或任务图的直接访问权。
  A（用户原话）：好
  最终决定：私聊任务图与群任务统一按聊天成员访问；私聊的参与人和 Agent 可以访问，Agent 管理者不因管理该 Agent 而自动取得其未参与私聊中的任务图访问权。共享 Work 中已有内容保持原有可见性。
- 用户补充问题（原话）：但是gateway是不是可以换个账号绑定？
  现状核对：同一已绑定节点不能直接换成另一账号，`src/IM/infra/binding_store.py:74` 拒绝跨 owner 绑定，`src/IM/ws/gateway/sessions.py:290` 拒绝用不同 owner 注册同一节点。`docs/specs/im/agents-nodes.md:349` 同样规定不支持换绑，但其错误名与当前实现返回的 `node already bound to another owner` 不一致。
  Agent 最初建议（已撤回管理员审批部分）：将停止旧账号接入与合法设备交接分开；增加公司管理员批准、Gateway 本机确认的整台 Gateway 换绑，节点及其上 Agent 一起交接给有效公司成员，旧账号失去管理权。
  用户纠正（原话）：交接也需要管理员干？本来成员接入新gateway也没有管理员批准的过程啊
  已明确的约束：公司成员准入与设备管理分开；正常接入和换绑不额外增加公司管理员审批。
  Agent 修订建议：由有权操作 Gateway 本机的人发起并明确确认换绑，绑定目标为有效公司成员；节点及其上 Agent 统一交接，旧账号和旧连接失去相应管理与接入权。成员停用阻止旧身份继续接入，不永久封禁物理电脑；不能只凭节点 ID 在网页上抢占别人的 Gateway。本机确认的具体方式交给 design。
  A（用户原话）：好
  最终决定：本 unit 增加 Gateway 本机换绑能力，正常接入和换绑均不另设公司管理员审批。通过本机明确确认，Gateway 与其上的 Agent 一起交接给另一位有效公司成员，旧账号失去该节点及其上 Agent 的管理权，旧身份的机器连接不能继续使用；合法换绑后可按新成员身份恢复公司接入。保持每台 Gateway 及其上全部 Agent 同属一位管理者。
- Q10：来源聊天被删除或群被解散后，已有任务图由谁继续访问？
  现状依据：`docs/specs/im/task-graphs.md` 规定聊天删除不删除任务图，图的内容、ID 和后续读写保持；但现有账号归属不能直接解释新确认的聊天成员权限。
  Agent 原建议（已撤回）：继续保留任务，按删除前的聊天成员范围访问和推进。
  A（用户原话）：这个体验很奇怪其实，解散群聊要不直接把任务给删了？加个警告。
  最终决定：解散群聊前明确警告会同时删除群聊及归属该群的任务，用户确认后一起删除；取消确认不删除任何内容。不保留一套解散后仍可继续使用的群任务权限。退出或移除个别成员不触发共同任务删除，仅收回其访问资格。
- 跨群协作补充（用户原话）：其实可能有一个场景是，几个高层在A群讨论好了总task，做了一层任务分解，再在B群里一堆小兵一起做其中某个子任务
  Agent 解读：同一任务图可以跨多个聊天推进，不能再仅用唯一来源聊天表达整张图的协作范围。需要区分总任务和子任务的结构关系、各聊天承接的工作范围，以及删除聊天是否影响仍在其他聊天推进的任务。此前 Q5、Q6、Q9、Q10 的任务规则需结合此场景复核；不把“高层／小兵”直接转成新的系统角色或组织层级。
- Q11：B 群成员应仅访问被交办的子任务及其后续分解，还是也可以查看 A 群的完整总任务图？
  Agent 原建议（未采用）：B 群只取得被交办子任务及其后续分解的访问资格。
  A（用户原话）：是不是应该直接全员看到所有task，然后每个群里可以很方便看本群新建、编辑过的task？
  最新方向：采用公司共享任务模型，所有有效公司成员可查看所有任务；每个群提供本群新建、编辑过的任务视图。同一任务可关联多个群，不复制任务，也不因换群推进而从原群任务视图消失。
  Agent 解读：任务本身按公司资格可见，群任务视图只是工作入口，不作为任务访问权限；私聊创建和原本无来源聊天的任务也包含在“所有任务”中，原聊天及受保护附件仍按聊天成员访问。任务独立于群存在，解散群不再连带删除任务；具体修改、删除权限不能从“全员可见”自动推导。
- Q12：任务的新建、修改与删除是否也向所有有效公司成员开放，继续通过 Agent 执行？
  Agent 推荐：允许全员通过 Agent 共同维护任务，保留修改者与来源的可辨认信息，删除任务需要明确指令或确认；不额外引入任务负责人权限或审批角色。读取开放与修改开放分开确认。
  补充推荐：Agent 按交办或已有主动工作规则维护任务，不因为能看到就自行接单、改动；能辨认由哪个 Agent、在哪个聊天中做了修改，并发修改不能悄悄覆盖别人的更新。
  A（用户原话）：好
  最终决定：有效公司成员均可通过具备任务能力的有效 Agent 新建、修改和删除公司任务，不按任务创建者、账号归属或来源群设置额外写权限。Agent 沿用交办及既有主动工作规则；删除需要用户明确要求或确认。修改者与实际来源可辨认，并发更新不能静默覆盖；不新增任务管理员或逐项审批。
- 用户补充问题（原话）：然后你还要考虑agent 对task的可见性，agent也可以看到所有的task吗
  现状依据：`src/IM/application/task_graphs.py:113` 起按解析后的账号 owner 列出及读取图；`docs/specs/gateway/task-graphs.md` 还要求真实注册 PA 身份及已配置的任务工具。当前并非公司所有 Agent 都能读取所有任务。

## 用户场景

1. **本人手机访问**：用户在 iPhone 保持 Shadowrocket 开启，直接打开 `https://im.nanoim.win`，仅登录 Nano IM 即可聊天、上传附件、查看 Work 和收到实时回复，无需 Tailscale 或额外 Cloudflare 身份验证。
2. **朋友加入与协作**：朋友从正常注册页创建自己的账号，登录后看到待批准状态；管理员批准加入公司后，才可进入共享联系人与 Agent。用户和朋友可参加同一个群；聊天、附件和管理权限继续遵守既有成员／owner 规则，全局完整 Work 在公司成员范围内共享。
3. **认证遭遇滥用**：来源反复注册、尝试密码或轮换来源攻击同一账号时，系统在实际昂贵操作前限制滥用，并给正常用户可理解、可恢复的反馈。攻击者不能靠伪造来源声明绕过限制；共享网络下的合理少量使用仍可进行。
4. **会话退出、刷新与重启**：用户正常刷新登录，旧刷新凭据失效；用户退出后不能用已吊销的刷新凭据恢复会话。服务重启不会恢复这些失效凭据，仍有效的正常会话也不因无关重启被强制全部登出。
5. **附件与资源滥用**：成员上传的正常图片与文件可使用；伪造地址不能使 Agent 自动访问宿主机内网或读取非成员附件。反复上传、发送过大消息或建立过量实时连接时，服务拒绝超限请求并保持正常账号可用，不持续占满磁盘、内存或连接资源。
6. **管理与运维**：部署管理员可维护系统级设置，普通用户只能执行其获准的个人及资源管理操作。运维人员可确认当前保护生效、发现认证／资源拒绝异常，并在故障时关闭公网入口、恢复服务和已保存的数据，不公开登录凭据或宿主机其他服务。
7. **跨群任务协作**：A 群讨论总任务并分解，B 群继续处理其中某个子任务；所有有效公司成员均能查看完整任务图，A、B 群各自便捷展示本群新建或编辑过的任务。两群引用同一任务事实，不复制出两套任务。
8. **成员停用**：管理员停用一位公司成员后，该成员在已登录设备上也不能继续读取公司数据或发起协作，其名下 Gateway 和 Agent 同时停止接入公司 IM，其他同事暂时不能调用这些 Agent。已有配置和历史记录保留，其他有权成员仍可查看历史消息和任务记录、通过可用的协作方式继续工作；不自动转移机器管理权或远程关闭电脑。
9. **设备交接**：有权操作 Gateway 本机的人明确确认换绑到另一位有效公司成员，节点和其上的 Agent 一起交接，无需公司管理员另行审批；旧账号失去管理权，合法换绑后可恢复公司接入，包括原管理者已被停用的设备。
10. **任务与聊天分开访问**：有效公司成员可查看私聊中产生的任务，但不能因此打开未参与的私聊或受保护附件；任务正文属于公司共享内容。
11. **群的生命周期**：成员退群后仍可从公司任务入口查看任务，但不能访问原群；群解散后公司任务保留，其他群仍可查看相同任务。成员被停用后则失去公司任务访问资格。
12. **共同维护任务**：不同成员通过不同 Agent 更新同一公司任务，可辨认执行修改的 Agent 及实际来源；更新冲突明确反馈，不能覆盖别人已经保存的工作。删除由用户明确要求或确认后执行，不因 Agent 看见任务或群解散而自动发生。

## 验收标准

### Requirement: 正常用户只需 Nano IM 账号即可从公网访问

#### Scenario: 本机通过实际域名访问与实时使用
- **GIVEN** 已部署公开 Nano IM，用户已获准加入公司
- **WHEN** 从本机浏览器经实际 HTTPS 域名打开部署网址并登录自己的 Nano IM 账号
- **THEN** 可正常聊天、上传允许的附件、查看 Work 并收到实时回复，无需 Tailscale、Cloudflare 账号或额外身份登录
- **AND** 浏览器连接安全，不出现证书警告
- **AND** 本次按 Q15 不要求真实 iPhone 实测，不将本机窄屏验证描述为真实手机结果

#### Scenario: 朋友公开注册
- **WHEN** 一位未注册朋友打开注册页并提交符合现有规则的账号信息
- **THEN** 可创建自己的账号，登录后看到等待管理员批准加入公司的状态，不要求邀请链接或邀请凭据
- **AND** 重名、保留身份和不合规则的输入继续按现有规则拒绝

#### Scenario: 待批准账号不能进入公司内部协作
- **GIVEN** 用户已注册并登录，但尚未获准加入公司
- **WHEN** 用户访问公司联系人、Agent、Work、聊天、任务、附件或尝试使用协作及资源管理能力，包括直接请求这些入口
- **THEN** 访问被拒绝，不泄漏公司内部数据，也不能调用 Agent 或绑定、配置公司节点；页面明确显示待批准状态

#### Scenario: 管理员批准后进入公司协作空间
- **GIVEN** 一位新用户正在等待批准加入公司
- **WHEN** 管理员查看待批准用户并批准其加入
- **THEN** 该用户可在自己的 Nano IM 账号下进入公司协作空间，查看共享联系人、联系 Agent 和查看共享 Work
- **AND** 原聊天、附件和资源管理仍遵守各自权限，批准加入不授予系统管理权

#### Scenario: 普通用户不能批准自己或他人加入
- **WHEN** 待批准账号或普通公司成员尝试批准自己或其他用户加入公司
- **THEN** 操作被拒绝，目标用户的加入资格保持不变

#### Scenario: 匿名访客只能进入公开认证入口
- **WHEN** 未登录访客打开认证页面，或尝试直接读取聊天、附件、Work 和使用实时消息
- **THEN** 认证入口可正常使用，受保护内容及实时能力拒绝访问，不泄漏其正文

### Requirement: 管理员可停用成员并保留协作记录

#### Scenario: 停用后既有登录与实时连接不再提供公司访问
- **GIVEN** 公司成员已在一台或多台设备登录，并建立实时消息连接
- **WHEN** 管理员停用该成员
- **THEN** 停用生效后该账号立即失去公司聊天、任务、Work、附件及 Agent 调用等内部访问资格，现有连接不再接收新的公司数据或接受其协作操作
- **AND** 再次登录、刷新会话或重新建立连接不能绕过停用状态，页面明确显示账号已被停用

#### Scenario: 停用不删除历史协作记录
- **GIVEN** 被停用成员曾发送消息并参与任务
- **WHEN** 其他仍有相应访问资格的成员查看这些消息和任务
- **THEN** 历史消息、任务记录和既有署名仍保留，其他成员可在其权限内继续协作，不因停用而丢失共同工作记录

#### Scenario: 普通成员不能停用他人
- **WHEN** 非管理员尝试停用公司成员
- **THEN** 操作被拒绝，目标成员的资格和访问权限不变

#### Scenario: 停用成员同步撤销名下机器接入资格
- **GIVEN** 成员名下 Gateway 已连接公司 IM，承载一个或多个 Agent，包括同事共同使用的 Agent
- **WHEN** 管理员停用该成员
- **THEN** 停用生效后这些 Gateway 和 Agent 停止接入公司 IM，已有机器连接或重新连接均不能继续收发公司消息、读取公司数据或更新任务
- **AND** 其他同事调用这些 Agent 时得到明确的不可用反馈，不把无法派发的工作显示为已开始执行

#### Scenario: 停用接入保留资源记录且不改变机器归属
- **WHEN** 因管理者被停用而停止 Gateway 和 Agent 接入公司 IM
- **THEN** 已有配置、工作记录和管理归属保留，不自动转给其他成员
- **AND** 该操作不远程关机、不接管电脑，也不声称已经终止该电脑上的所有本地进程或外部通道

### Requirement: 注册与认证具有实际生效且可恢复的滥用防护

#### Scenario: 单一来源反复尝试被节流

- **THEN** 超限请求被暂时拒绝，页面明确提示稍后重试；被拒的注册不产生账号

- **THEN** 该账号的重复尝试受到临时限制，错误反馈不区分账号不存在与密码错误

- **WHEN** 部署指定的管理员修改系统级策略
- **THEN** 可保存并回看生效配置
- **AND** 普通登录用户执行相同修改被拒绝且不改变配置；页面明确显示其可操作范围

#### Scenario: 新注册不能自动获得系统管理权
- **WHEN** 普通用户注册账号或提交自称管理员的信息
- **THEN** 不因此取得系统级写权限，个人设置与已获准的聊天能力仍可使用

#### Scenario: 既有共享 Work 保持
- **WHEN** 已获准加入公司的朋友登录后查看共享联系人、全局 Agent Work 和已有子执行明细
- **THEN** 仍可查看 current 设计允许的完整工作轨迹，不新增按来源聊天过滤或邀请门禁

#### Scenario: 成员和 owner 边界保持
- **GIVEN** 两个独立账号拥有各自私聊、附件及资源，并参加一个共同群聊
- **WHEN** 两人分别读取与修改这些对象
- **THEN** 共同群成员可正常协作，非成员不能读取或写入原私聊及附件，非 owner 不能修改他人的 Agent／节点配置或读取其受限管理数据
- **AND** 从共享 Work 跳转原聊天或附件时仍按成员关系判定

#### Scenario: 共用 Gateway 统一管理、共同使用
- **GIVEN** 一位公司成员管理一台共用 Gateway 及其上的全部 Agent
- **WHEN** 其他公司成员联系这些 Agent，或在共同群聊中交办工作
- **THEN** 可按既有协作规则使用 Agent，无需共享管理者账号；Gateway 和 Agent 配置仍只由同一位管理者维护
- **AND** 共同使用不授予节点或 Agent 配置管理权

### Requirement: Gateway 可由本机确认整体换绑给有效公司成员

#### Scenario: 有效成员自行接入或换绑 Gateway
- **GIVEN** 操作者有权操作 Gateway 所在电脑，目标账号是有效公司成员
- **WHEN** 操作者在本机完成接入或明确确认换绑
- **THEN** Gateway 及其上的 Agent 统一归属该成员，无需公司管理员再次批准，始终保持一位管理者
- **AND** 换绑完成后旧账号不能再管理这些资源，旧身份的机器连接不能继续使用该节点身份访问公司 IM

#### Scenario: 仅知道节点标识不能远程抢绑
- **WHEN** 用户仅凭节点标识发起绑定或换绑，未完成对应 Gateway 本机的有效确认
- **THEN** 不能取得该节点及其上 Agent 的管理权，原有归属不变

#### Scenario: 不能换绑给尚无有效公司资格的账号
- **WHEN** 尝试将 Gateway 绑定给待批准或已停用的账号
- **THEN** 操作被拒绝，不能通过本机换绑绕过公司的成员资格要求

#### Scenario: 原管理者停用后设备可合法交接
- **GIVEN** 原管理者被停用，其 Gateway 和 Agent 已停止接入公司 IM
- **WHEN** 在 Gateway 本机明确确认，将节点及其上 Agent 整体换绑给另一位有效公司成员
- **THEN** 可以按新成员身份恢复公司接入，原账号仍保持停用，不因设备交接恢复其任何访问资格
- **AND** 保留原有 Agent 身份及已保存的配置与工作记录，不因换绑授予新管理者未参与聊天的访问权

### Requirement: 有效公司成员与具备任务能力的有效 Agent 可查看全部任务

#### Scenario: 公司任务跨账号与聊天可见
- **GIVEN** 一位有效公司成员未参与某任务最初产生的聊天，也不是执行 Agent 的管理者
- **WHEN** 该成员在公司任务入口浏览、搜索或打开任务
- **THEN** 可以查看完整任务图及其总任务、子任务，不因创建账号或来源聊天不同而被拒绝
- **AND** 私聊中创建和没有来源聊天的任务同样属于公司任务可见范围，待批准及停用账号仍不能访问

#### Scenario: 任务可见不授予原聊天与附件访问权
- **WHEN** 人或 Agent 从任务信息访问自己未参与的聊天或受保护附件
- **THEN** 原聊天及附件继续按成员关系判定访问，不因任务全员可见而开放其原文、受限来源信息或文件
- **AND** 无权访问的来源不显示为可用跳转，任务本身仍可查看

#### Scenario: 跨 Gateway 和账号的 Agent 可读取同一任务图
- **GIVEN** 两个具备任务能力、有效接入公司 IM 的 Agent 分别由不同有效公司成员管理，运行在不同 Gateway 上
- **WHEN** 任一 Agent 搜索、列出或读取另一 Agent 所创建的任务
- **THEN** 可读取同一公司任务及其总任务与子任务，不要求管理者相同或 Agent 加入相同聊天
- **AND** 不能由此修改其他 Agent 配置或访问未获准的机器资源

#### Scenario: 任务读取仍要求有效身份和已授予的工具能力
- **WHEN** 未注册身份、待批准或停用成员名下 Agent，或未启用任务能力的 Agent 尝试读取公司任务
- **THEN** 请求被拒绝，不能用模型自报身份、已知任务链接或旧机器连接绕过相应边界

#### Scenario: Agent 按需读取而非自动摄取全部任务
- **WHEN** Agent 处理工作并查询公司任务
- **THEN** 可按需取得任务摘要、搜索结果和具体任务内容，不因公司范围可见而自动将全部任务正文加入每轮上下文
- **AND** 读取任务不自动接单、唤醒其他 Agent 或开始执行，仍沿用交办与既有主动工作规则

#### Scenario: 飞书沿用现有主人识别与 Agent 公司资格
- **GIVEN** 飞书 channel 按既有 ownerOpenId 识别主人，其 Agent 有效接入公司 IM 且已获准任务工具能力
- **WHEN** Agent 按现有渠道交办规则查询公司任务
- **THEN** 使用同一 IM 任务服务，不要求外部发言人另行关联 IM 账号、不新增关联页面或确认码
- **AND** 未加入公司、待批准或停用管理者名下 Agent，以及失效机器身份或未启用任务能力的 Agent，均不能读取公司任务；飞书主人标识不替代 IM 的机器与管理者资格检查

### Requirement: 公司成员通过 Agent 共同维护任务且变更可辨认

#### Scenario: 跨账号和 Gateway 新建与修改任务
- **GIVEN** 有效公司成员通过具备任务能力、有效接入的 Agent 交办任务维护工作
- **WHEN** Agent 新建任务或修改其他成员、其他 Agent 创建的任务
- **THEN** 可维护同一份公司任务，不要求与创建者属于相同账号、同一 Gateway 或同一聊天，不新增任务管理员审批
- **AND** Agent 仍按交办及既有主动工作规则行动，不因任务可见而自行接单或任意改动

#### Scenario: 删除任务需要明确要求或确认
- **WHEN** 有效成员明确要求 Agent 删除指定任务，或在 Agent 说明删除对象与范围后明确确认
- **THEN** Agent 可删除所指任务，其他任务保持不变；被删除任务不再作为可用任务返回，旧链接明确反馈不可用
- **AND** 没有明确要求或确认时不执行删除，不能把解散群或笼统整理任务当作删除授权

#### Scenario: 修改者与来源真实可辨认
- **WHEN** 成员查看已更新任务的变更信息
- **THEN** 可辨认执行修改的 Agent 与实际来源聊天；能确认发起人的操作保留真实发起身份，没有来源或无法确认时不伪造
- **AND** 来源聊天及其信息的展示仍受聊天访问规则约束，不能通过变更信息读到无权访问的聊天正文或受限来源信息

#### Scenario: 并发修改不能静默覆盖
- **GIVEN** 多个 Agent 根据同一任务的旧状态准备更新，其中一个已经保存新进展
- **WHEN** 另一个 Agent 提交过时更新
- **THEN** 明确得到冲突反馈，不覆盖已保存的新进展；重新读取和核对后可按最新状态继续维护

#### Scenario: 任务写入保持有效身份与工具边界
- **WHEN** 待批准或停用成员、未有效接入或未获准任务工具能力的 Agent 尝试创建、修改或删除任务
- **THEN** 操作被拒绝，不因公司任务共享而绕过成员、机器身份或工具配置检查

#### Scenario: 外部渠道任务写入按 Agent 资格判定
- **WHEN** 飞书等渠道的 Agent 按交办请求创建、修改或明确删除公司任务
- **THEN** IM 按 Agent／Gateway 身份、管理者公司资格及任务能力决定是否允许，不要求逐个外部发言人先拥有或关联 IM 登录账号
- **AND** 保留真实来源和明确删除要求，不能伪造发起人为管理者；未获准 Agent 的写入不会因为已配置 ownerOpenId 而放行

### Requirement: 群内便捷查看本群新建或编辑过的任务

#### Scenario: 群任务入口展示本群工作
- **GIVEN** 成员正在查看一个有权访问的群聊
- **WHEN** 打开该群的任务入口
- **THEN** 可便捷查看在本群新建或编辑过的任务，并打开对应任务或子任务了解当前进展
- **AND** 群内列表是公司任务的一个视图，不创建副本或额外的任务权限

#### Scenario: 总任务与子任务跨群持续协作
- **GIVEN** A 群创建总任务并分解，B 群随后编辑其中一个子任务
- **WHEN** 成员分别在两个群的任务入口查看工作
- **THEN** A 群能继续找到自己创建或编辑过的任务，B 群能找到自己编辑过的子任务；打开后指向同一任务图中的实际节点
- **AND** B 群的有效更新在总图中可见，不复制任务，也不因最后一次编辑发生在 B 群而丢失 A 群与该任务的关联

### Requirement: 任务独立于群成员与群聊生命周期

#### Scenario: 退群不撤销公司任务读取资格
- **WHEN** 有效公司成员退出或被移出某群
- **THEN** 仍可从公司任务入口访问任务，但不能继续访问原群及其受保护聊天内容

#### Scenario: 解散群不删除公司任务
- **WHEN** 有权解散群的用户确认解散群聊
- **THEN** 群按既有规则删除，公司任务及其结构保留，其他群和公司任务入口仍可打开同一任务
- **AND** 解散操作不连带删除或伪称停止其他群正在推进的任务，已删除聊天不再作为可用跳转

### Requirement: 自动附件处理不能访问任意服务端目标

#### Scenario: 正常上传与 Agent 图片理解保持
- **WHEN** 成员上传允许的图片或文件并发送到有 Agent 的聊天
- **THEN** 成员可读取附件，Agent 可处理正常图片并回复；正常外部频道附件链路保持可用

#### Scenario: 伪造地址和附件引用被拒绝
- **WHEN** 客户端提交宿主机内部地址、其他未经允许的自动下载目标或非成员附件引用
- **THEN** 请求或附件处理被拒绝且给出明确失败反馈，不会借 IM／Gateway 自动访问该目标或读取无权附件
- **AND** 普通文本中的外链不会仅因这项防护失去原有展示能力

### Requirement: 公网滥用不能无界消耗服务的有限资源

#### Scenario: 超限上传和请求有明确拒绝
- **WHEN** 账号重复上传超过允许累计额度，或提交超过允许大小的消息／附件
- **THEN** 超限操作被拒绝并得到可理解的限制说明，不留下不完整的成功对象；额度内的正常使用可继续

#### Scenario: 附件空间不足不阻断文字聊天
- **WHEN** 上传因累计容量限制被拒绝
- **THEN** 普通用户看到“暂时无法上传附件”，可明确选择仅发送文字，附件仍保留在草稿，不要求先清理附件或联系管理员
- **AND** 管理员可看到容量告警并处理；拒绝上传不撤销正常文字聊天能力，不谎称附件已发送

#### Scenario: 实时连接受控且可恢复
- **WHEN** 同一主体建立过量实时连接、发送过大内容或高频重复操作
- **THEN** 超限行为受到限制，正常聊天连接继续可用；释放连接或限制期结束后可正常重新连接

### Requirement: 发布与恢复可验收，凭据不随运维证据公开

#### Scenario: 公网仅开放预定 IM 服务
- **WHEN** 运维完成上线并从外部检查公开入口
- **THEN** 可使用预定 Nano IM 入口，宿主机其他服务、内部控制入口与运行文件不因本次接入变得公开可访问
- **AND** 用户侧注册、登录、实时消息和附件均经过已生效的应用安全边界

#### Scenario: 运维证据不包含可复用凭据
- **WHEN** 运维核对认证拒绝、资源超限、服务健康或收集公开交付证据
- **THEN** 可辨认保护是否生效及故障类别，常规访问记录、错误反馈和交付材料不暴露密码、可复用会话凭据或 Tunnel 连接凭据

#### Scenario: 故障时可停止公开访问并恢复
- **GIVEN** 上线后发现故障或需要回退
- **WHEN** 运维按经验证的恢复流程操作
- **THEN** 可停止新的公网访问，恢复已保存的数据与原服务可用性，不因回退改变账号身份或覆盖无关配置

#### Scenario: 免费部署范围可核对
- **WHEN** 运维核对上线使用的 Cloudflare 功能与域名续费配置
- **THEN** 使用已确认的免费 Tunnel 方案，未新增付费附加功能；域名续费价格和自动续费状态可明确核对

## 范围与非目标

### 在范围

- 正常公开注册、Nano IM 登录、管理员批准加入公司与停用成员、待批准及停用账号的访问边界、停用时名下 Gateway／Agent 同步停止接入公司 IM、配置与历史记录保留，以及保护生效时的前端可理解反馈。
- 认证滥用限流、可信来源处理、持久刷新凭据吊销及并发轮换。
- 系统级策略管理权限，既有成员、owner、机器身份与共享 Work 边界回归。
- 有效成员自行接入 Gateway，以及 Gateway 本机明确确认后的整体换绑；节点和其上 Agent 保持单一管理归属，换绑后撤销旧身份管理与接入权。
- 有效公司成员及具备任务能力的有效 Agent 可查看全部公司任务；每个群便捷展示本群新建或编辑过的任务，保留跨群活动关联，原聊天与附件继续按各自成员访问。
- 有效成员通过 Agent 共同新建、修改与删除任务；删除须有用户明确要求或确认，修改者与来源可辨认，并发修改不静默覆盖。
- 保持任务独立生命周期和既有群解散权限；退群不撤销有效公司成员的任务读取资格，解散群不删除公司任务。
- IM／Gateway 自动图片与附件访问边界、资源大小与累计上传限制、实时连接及操作滥用保护。
- HTTPS 公网入口、只接入预定 IM 服务、常规诊断中的凭据保护、发布前验收和可执行恢复流程。
- 免费入口防护能力的选择与费用范围核对；所有本次文件位于仓库内。

### 非目标与边界

- 不做邀请注册，不增加 Cloudflare 账号登录，不重做共享 Work 或完整多租户产品模型。
- 不拆分 Gateway 与其上 Agent 的管理归属，不引入多人共同管理；共用设备继续由一位管理者统一维护。
- 不新增私聊删除、个人清空聊天记录、任务回收站或完整任务历史版本系统；不增加任务或子树级权限体系及任务管理员审批，不通过解散群连带删除公司任务。
- 不增加付费 Cloudflare 套餐或附加产品，不开放其他主机服务，不构建通用商业计费或配额平台。
- 不承诺任何规模的 DDoS 下都可用，也不把认证限流当作全网 DDoS 防护；公网入口与应用资源防护各自承担其可验证范围。
- 不把有限安全审查、mock 或通过既有回归当作“零漏洞”或生产公网验收证明。
- 不在首文档阶段选择存储结构、接口字段、限额数值、代理实现或 milestone 拆分；交给 design，并对照真实部署与既有能力作最小适当实现。
- 本次调用只完成首文档；实施、独立门禁、上线分别按后续生命周期执行。新建 unit 不表示已修复、已部署或已批准公网开放。
