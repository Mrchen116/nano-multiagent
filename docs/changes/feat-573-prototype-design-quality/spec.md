## 问题与范围

现有 skill 已要求继承当前 UX，但缺少选择原型呈现范围、区分产品与演示、实际渲染自检的明确要求；设计评审也缺少对应检查。结果是用户需要逐页指出布局、入口和范围问题，难以判断哪些内容会进入真实产品。

本次仅调整设计作者、设计模板、原型指南与设计评审 skill。按用户要求用本简短 spec 记录范围和成功标准；不修改产品或既有 change 的原型，不新增独立审批流程。规则变更的静态校验不代表后续原型效果已获真实验证。

## 用户场景与验收标准

### Requirement：按判断需要选择原型范围

用户评审局部反馈、组件状态、页面增量或跨页面流程时，由作者选择足够但不过量的上下文。

- **Scenario：局部变化。** WHEN 仅修改表单反馈等局部内容，THEN 可用局部对照或组件状态展示，保留真实容器和相邻元素，不要求重画整个产品。
- **Scenario：强耦合或多步交互。** WHEN 改动依赖页面布局或连续操作，THEN 展示现有页面与可交互增量，或可连续操作的旅程，使用户看清入口、结果和返回；不靠演示菜单拼接流程。

### Requirement：继承现有 UI，分清产品与演示

用户能判断改动在现有产品中如何出现，以及哪些内容真正属于本次范围。

- **Scenario：增量设计。** WHEN 原型呈现新增或修改的功能，THEN 以当前产品实际画面及组件样式为依据，沿用导航、信息层级和控件约定；未经确认不重做现有 UX。
- **Scenario：演示边界。** WHEN 使用示例数据、背景界面或异常状态控制，THEN 在产品区域之外说明用途，默认展示正常使用状态，不把设计解释、模拟控制或临时教程变成产品功能。

### Requirement：先完成视觉自检，再交付评审

用户收到原型前，作者主动发现并修正可见的布局与交互问题。

- **Scenario：交付前走查。** WHEN 原型作为可评审成果交付，THEN 已实际渲染并检查所覆盖的界面、关键状态和适用宽度，包括易挤压的中间宽度；修正重复信息、主次不清、按钮挤压、遮挡和反馈间距等问题，留下代表性截图和简短结果。
- **Scenario：无法渲染。** WHEN 缺少渲染条件，THEN 可展示标明“视觉未验证”的草稿，不能用 DOM 检查冒充视觉验收或宣称原型就绪。
- **Scenario：设计评审。** WHEN 评审前端设计，THEN 按同一范围对照当前 UI 与实际渲染结果，交互改动走查对应路径；可用性和范围混淆需修正，纯审美偏好不成为无限返工理由。

## 验证边界

本次验证两个 skill 的结构有效性、引用和模板一致性、差异格式及上述要求的覆盖。未运行新的产品原型实验，不声称已完成真实产品验收或独立设计审查。后续使用这些规则时，仍需在具体 unit 内提供实际视觉和交互证据。
