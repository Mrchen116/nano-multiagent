# 原生 iOS 日常交互独立审视 R1

日期：2026-10-06。审视基线：`5fde316f3c2d9e31984bfbbac41f5ce53af38b53` 加当前工作树；聊天输入候选与头像正在由主执行者修改，本报告不重复这两项。只读检查代码及 feat-578 spec/design/coverage，没有操作手机或 Simulator，没有以原型、截图或源码推演宣称真机体验验收通过。

## 判断与范围

四入口与全量功能覆盖已经形成，但连续工作路径存在明显成本：草稿保护不一致、等待状态缺少就近行动、任务浏览跨多层 sheet、管理主操作位置不一致。这里的“商业产品成熟度”指同一操作可预测、用户知道正在发生什么、常用动作可发现、退出不会无声丢工作；不要求逐像素继承 Web，也不虚构其他商业 App 的规则。

核对了 `docs/README.md`、feat-578 spec/design/coverage，以及 current 的 `conversations-messages.md`、`task-graphs.md`、`agents-nodes.md`。覆盖发现 Agent→建聊→多轮、历史/离线/发送等待、任务回聊、Work 与审批、Agent 创建/配置/通道、账号/设备/策略与返回保存。以下“事实”为源码可确认，“判断”为由事实推导的体验风险，仍需在实际 App 对路径验证。

| 优先级 | 问题 | 主要成本 |
|---|---|---|
| P1 | 改名草稿被置顶/静音回执覆盖 | 已输入内容无声丢失 |
| P1 | 账号、设备、策略、通道编辑离开保护不一致 | 用户不能预测返回后能否恢复 |
| P1 | 进行中与待授权工作缺少直接定位 | 必须逐个开聊/展开轮次找阻塞 |
| P2 | 创建与配置长表单缺少统一主操作和渐进披露 | 滚动、反复找保存、猜按钮为何不可用 |
| P2 | 任务层级藏在多层 sheet，回聊缺少来源返回 | 路径难记、回到原节点成本高 |
| P2 | 加载、无结果、真空数据被混用 | 不知道是等待、搜索失败还是没有数据 |
| P2 | Agent 详情的在线状态是旧快照 | 状态与真实可用性可能矛盾 |
| P2 | 未确认发送把正文留在锁定输入框 | 已发/待发难区分，下一段内容无法准备 |
| P2 | 新消息提醒没有聊天身份 | 多聊天工作时不能判断是否值得切换 |

## 1. P1：改名草稿被不相关偏好保存覆盖

- **当前入口与步骤**：聊天→右上详情→输入新名称，暂不点“保存名称”→切换置顶或静音。
- **事实**：名称使用独立 `title` 草稿；置顶/静音会立即提交各自 PATCH。任意 PATCH 成功后 `mutate` 都执行 `title = value.title`，把尚未提交的新名称替换成服务器旧名称。依据：`src/IM/ios/NanoIM/Features/Chat/ChatInfoView.swift:19-23,63-66`。
- **判断**：用户没有触发放弃改名，却丢掉输入。这是具体行为缺陷，优先于风格改动。
- **建议流程**：置顶/静音仍可即时保存，但仅更新该偏好及聊天权威快照；名称草稿在明确“保存名称”或“放弃”时改变。发送失败保留当前名称。
- **验收路径**：输入新名称后连续切换置顶/静音，名称原样保留；明确保存名称后再进页面回显新名称。

## 2. P1：显式保存页面的离开行为不一致

- **当前入口与步骤**：我的→个人资料修改名称/语言，或设备修改别名/开关，或管理员策略修改数值→直接返回；通道 sheet 修改 App ID 后下滑关闭。
- **事实**：账号、设备、策略均计算 dirty 并提供“保存/放弃修改”，但没有返回或 dismiss 的草稿保护。通道 editor 没有 dirty 判断或 `interactiveDismissDisabled`；关闭清除 secret。反之 Agent 配置会隐藏默认返回并询问放弃草稿，创建页也保护 dismissal。依据：`MeView.swift:76-118`、`SettingsNodesView.swift:73-115`、`SettingsPoliciesView.swift:35-62`、`AgentChannelsView.swift:107-158`、`AgentConfigView.swift:83-89`、`AgentsView.swift:178-183`（均位于 `src/IM/ios/NanoIM/Features/` 对应目录）。
- **判断**：同一 App 里“返回”一会儿保护、一会儿直接丢草稿，用户很难形成习惯。这里不要求跨重启持久化所有草稿。
- **建议流程**：需要显式保存的编辑页统一为“取消/返回 + 保存”；dirty 时离开提供“继续编辑/放弃修改”。通道只保护普通字段，秘密继续按既有生命周期清除，关闭时说明需重新输入；不为了草稿体验持久化凭据。
- **依据**：Apple 对 sheet 的建议是有未保存变更时确认下滑关闭；该建议适用于通道 sheet，账号 push 的一致行为是本报告的设计判断。[Apple Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets?changes=_1_1)。
- **验收路径**：对每类编辑页分别点返回、点取消、下滑关闭；无修改时不多一次确认，有修改时能继续编辑且值不丢。

## 3. P1：进行中与待授权工作不能从工作入口直接定位

- **当前入口与步骤**：发起 Agent 工作后返回聊天列表；或 Agent→详情→Work，寻找需要本人授权的轮次。
- **事实**：Conversation DTO 已有 `run_state`，列表只展示标题、预览、时间、未读和偏好。Work 的轮次默认 `expanded = false`，权限请求在展开后的 `ForEach(items)` 中；折叠标题只有描述/状态/时间，没有待处理数量或直接行动。聊天内审批卡本身是可见的，但只有进入对应聊天才可见。依据：`ChatModels.swift:18`、`ChatListView.swift:28-51`、`AgentWorkView.swift:89-125,150-154`、`ChatMessageView.swift:46-48`。
- **判断**：协作助手需要先告诉用户“哪项需要我”；现在返回总览后难以区分正在执行与普通旧聊天，Work 用户可能逐轮展开寻找审批。不能从已有 `run_state` 推断未报告的审批状态。
- **建议流程**：列表依据真实 `run_state` 给运行中聊天短状态；Work 基于已返回的未解决 permission item 在页首提供“待你处理”，点进对应轮次/请求。没有权威数据时保持未知，不发明计数；owner 才有处理按钮，其他成员仍可看轨迹。
- **验收路径**：准备两个并行聊天和一个真实待授权轮次，从总览能直接定位进行中工作；Work 不需逐个展开就能找到已报告的请求；非 owner 不获得审批能力。

## 4. P2：创建与配置长表单缺少统一主操作与信息收放

- **当前入口与步骤**：Agent→新建→选设备、ID、模式、workspace、名称、模型、能力→滚到底找创建。编辑已有 Agent 时保存却在导航栏；心跳时间需要手输 HH:mm 和时区。
- **事实**：创建按钮在 `AgentEditorFields` 后的最后一个 Section；禁用条件包含节点离线、能力未加载、缺名称等，但对应行没有逐项解释。创建完成只显示名称/workspace 和“完成”，没有发消息/配置下一步。备用模型直接全量展示，连空的“添加备用模型”也默认占一行；current spec 明确要求默认折叠并显示数量。依据：`AgentsView.swift:141-174`、`AgentConfigView.swift:83-86,147-173,262-267`；`docs/specs/im/agents-nodes.md` 首个 Requirement。
- **判断**：同一编辑任务的主按钮位置不一致；新用户可能先读完技术字段再发现不能创建。大字体/键盘下的真实可达性仍待真机验证。
- **建议流程**：创建主操作保持导航栏可见，与配置保存一致；首屏先身份/设备/名称/主模型，备用模型与高级能力按摘要展开，字段完整保留。缺前置时在对应字段给直接提示或绑定入口；成功提供“开始聊天/完成”。心跳时间用系统时间选择并保留服务端 HH:mm 语义，时区给当前值与选取帮助，不更改后端。
- **依据**：Apple 建议最可能使用的动作具有清楚的主操作层级；渐进披露方案是本报告判断，不声称 HIG 规定具体字段顺序。[Apple Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons?changes=latest_1__8)。
- **验收路径**：默认无备用模型不占展开列表空间；选择离线设备能直接知道为何不能创建；长表单和键盘可见时能找到提交；成功可直接进入真实新 Agent 聊天。

## 5. P2：任务层级与回聊分散在多层 sheet

- **当前入口与步骤**：任务→图→点节点弹 sheet→进入子图→再点节点弹另一个 sheet；之后“回到聊天并引用”。或从消息内任务链接打开图 sheet，再进入节点 sheet。
- **事实**：图的 selected node 用带 NavigationStack 的 sheet；Node 内进入子图又用 TaskGraphView，子图继续用节点 sheet；消息深链本身也用根 sheet。各层“任务图/任务详情”通用标题，没有路径面包屑；每个 Node 都有 `dismiss()` 的“完成”。回聊统一执行 reference，追加草稿并把聊天 navigation path 替换为 `[id]`。依据：`TasksView.swift:118-126,169-187`、`NanoIMApp.swift:150-154,177-180`。
- **判断**：用户需要记住 sheet 与 push 的层数；同名“完成”在不同层的退出效果难预测。回来继续检查任务，要先退到聊天列表再切任务入口，缺少显眼的原节点返回。现有任务 tab stack 可能保留，不等于有直接的来源返回操作。
- **建议流程**：任务图、节点、子层级使用一条可追溯的导航栈，显示“总目标 › 当前层级”；保留“引用到关联聊天”的现有草稿语义，再提供纯“查看关联聊天”作为次级动作，避免仅查看也改草稿。跨入口打开聊天时给明确“返回任务”来源动作，返回原节点与滚动位置。不新增直接编辑图权限。
- **依据**：Apple 提醒 modal 内多层导航可能让用户忘记如何原路返回。[Apple Modality](https://developer.apple.com/design/human-interface-guidelines/modality?changes=l_1_2)。纯查看动作与来源返回是本报告建议，需与现行 S14 引用语义一起确认。
- **验收路径**：计划→探索→验证计划三层浏览；始终能看出当前层级并一步退外层；回聊、引用、返回任务均保留原草稿和节点上下文。

## 6. P2：加载中、无搜索结果与没有数据被混用

- **当前入口与步骤**：刚登录进入聊天/任务，或打开新建聊天；输入不存在的聊天、Agent 或任务名称。
- **事实**：ChatStore 默认 conversations 为空且没有 initial-loading 状态，ChatList 根据 filtered 空直接显示“暂无聊天，使用 + 创建”；即便只是搜索/类别筛选无匹配也如此。Agents 只在原 contacts 空显示空态，搜索无结果时仅剩空列表。Tasks 初始 loading=false，可能先出现“暂无任务”；搜索无结果仍显示“在聊天中让 Agent 建立计划”。NewChat 请求联系人前没有 loading 或无结果提示。Conversation 请求历史时也缺少首次加载与真正空聊天的区分。依据：`ChatStore.swift:8,139-167`、`ChatListView.swift:53,81-111`、`AgentsView.swift:21,38`、`TasksView.swift:10,32,40-57`、`ConversationView.swift:35-59,87-89`。
- **判断**：用户不知道请求是否开始、搜索是否成功，甚至被引导去新建已经存在的数据。任务搜索同时由周期刷新和 submit 驱动，与其他列表即时本地筛选的反馈节奏不同。
- **建议流程**：首次读取显示加载；失败显示重试；真实零数据给创建/去聊天行动；搜索无结果显示查询词和“清除搜索/筛选”。任务搜索明确使用即时搜索或提交搜索的一种模式；避免当前查询与旧结果同时看似有效。
- **依据**：[Apple Loading](https://developer.apple.com/design/human-interface-guidelines/loading?changes=_4_8) 建议明确加载反馈；[Apple Search fields](https://developer.apple.com/design/human-interface-guidelines/search-fields?changes=_1) 建议在可行时输入即搜索；[Apple WWDC26 搜索](https://developer.apple.com/videos/play/wwdc2026/292/) 明确讨论无结果显示查询词。这里只引用相关原则，未宣称所有搜索必须同一技术实现。
- **验收路径**：慢网首次加载、合法零数据、查询无匹配、类别无匹配、请求失败分别显示不同状态；不会在请求仍进行时叫用户创建新对象。

## 7. P2：Agent 详情状态依赖进入时快照

- **当前入口与步骤**：Agent 列表点一个在线 Agent→停留详情；其节点断线或改名后继续看详情/发消息。
- **事实**：列表每 3 秒刷新，但 AgentProfileView 接收 `let contact` 且自身无按 agentID 重读；在线判断只有等于 online 与其余全部离线。详情发消息按钮只以 openingChat 禁用。对照 Web public profile 明确按 agentID 从每 3 秒刷新联系人结果取值。依据：`AgentsView.swift:44-46,64-88,112-118`；`Client/CommonModels.swift:24`；`src/IM/frontend/src/features/settings/agents/agent-profile-page.tsx:22-26`。
- **判断**：源码没有保证该页会得到最新身份和状态；不能据此断言所有 SwiftUI 重绘情况下都永久不更新。长停留后看“在线”，发消息却不能执行，会损害状态可信度。离线仍允许创建/进入聊天是合理的，但应说明回复条件。
- **建议流程**：详情按 agentID 获取当前公开联系人状态；请求失败区分“最后已知状态/状态未知”与真实离线。离线“发消息”仍打开历史/草稿，但就近提示“设备离线，Agent 回复需设备恢复”，不用把聊天入口一并禁掉。
- **验收路径**：停留详情时节点上线/离线、公开名更新，页面反映权威状态；暂时加载失败不把未知伪装离线；离线打开聊天可以阅读历史且清楚回复限制。

## 8. P2：未确认发送占据锁定输入区

- **当前入口与步骤**：输入长消息/附件→发送→响应超时或断线→想补充下一段。
- **事实**：pending 在请求前保存正文，确认响应前不清 drafts；composer 只要 pending 非空就不可编辑，附件移除和发送也禁用。异常后在顶部 ErrorNotice 和输入区显示“等待核对/重试核对”；时间线只有收到返回后才新增该消息，没有本地待确认项。依据：`ChatStore.swift:225-255`、`ConversationView.swift:104-111,150-159`。
- **判断**：可靠性约束是必要的，但正文留在输入框更像未发送草稿，等待数秒至重连期间也不能准备下一段。当前机制不会重发另一份消息，这一语义应保留。
- **建议流程**：把同一 pending 的内容显示为明确“发送中/待确认”的本地消息项，就近提供“核对结果”；保留同一幂等发送身份。下一段草稿可编辑但在上一条确认前不提交，不需要新增离线队列。若本轮不调整模型，至少明确显示待确认正文与锁定原因，避免看起来像输入控件失灵。
- **验收路径**：人工延迟响应与断网，用户能区分已确认消息、待确认内容和下一段草稿；核对不重复投递；恢复后只有一条服务器消息。

## 9. P2：前台提醒没有来源身份

- **当前入口与步骤**：在 Agent 配置/任务详情时，另一个聊天收到消息，顶部短暂出现“收到新消息”。
- **事实**：banner 存 conversationID，但 UI 始终显示通用“收到新消息”，3 秒后消失；点击即 `openChat`，会切 Tab 并替换聊天 path。依据：`ChatStore.swift:103-107`、`NanoIMApp.swift:162-165,177`。
- **判断**：用户不知道是哪位 Agent/哪个群需要注意；只能盲切或等返回列表查看。这不是要求展示正文或增加后台推送。
- **建议流程**：用当前已授权聊天名/身份头像 + “新消息”提供来源，正文继续隐藏；点击前即可判断是否值得打断当前工作。与第 2 项一起核对编辑页：不能由提醒跳转造成未保存内容无声丢失。
- **依据**：Apple 系统通知内容指南建议标题给上下文；这里对 App 内 banner 的应用是设计推论，并非 Apple 要求 App 内 banner 完全复制系统通知。[Apple Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications?changes=_4)。
- **验收路径**：两个聊天快速到消息时来源可辨识，点提醒打开正确聊天，不暴露正文；正在编辑配置时原草稿能恢复或明确处理离开。

## 建议收口与验证

先修 1/2/3 与 6，形成“输入不丢、状态可信、待办能找到”的基本工作闭环；随后统一长表单主操作与任务来源导航，再优化待确认消息与提醒。不要再用 coverage 每行“有页面/按钮”作为 UX 完成证据。

本报告只新增审视文档，未修改产品代码。上述提案未构成 spec/design 自动批准。实施后的最小真实路径：新 Agent→聊天→真实多轮→离线/确认→Work 审批→任务三层→回聊引用→回原任务→修改配置→返回/取消/保存→账号/设备/策略。用户在真机上的实际操作仍是最终体验证据。
