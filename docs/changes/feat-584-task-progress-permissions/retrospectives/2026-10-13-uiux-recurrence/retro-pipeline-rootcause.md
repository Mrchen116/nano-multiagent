## 核心问题与结论

用户希望获得能公开使用、与现有产品设计语言一致的 Web/iOS 任务体验：能比较进展、读懂任务、自然编辑和处理冲突，而不是字段和按钮齐全即可。10 月 12 日的原型已经因空间浪费、与真实聊天脱节、缺少根任务总览等问题多次修订。10 月 13 日真实实现又出现公开群裸弹层、五列共用分页和 iOS 冗长且信息不清的编辑页；交付后重新制作的设计稿，展开选择器时仍露出浏览器默认样式。

**PR #336 没有在这次工作中实现预期的防漏效果。首轮实施确实早于规则合并，但不能把后续失效归咎于旧规则：主 Agent 和产品 reviewer 后来均实际读取了新版完整体验标准。**

证据支持的主要机制是：原有设计契约仍以功能、数据语义和可达操作为主；实施把这些契约映射成通用表单与临时布局；验收虽实际操作、截图，并增加“视觉组织／交互成本”段落，判断仍围绕字段、分组、按钮和保存是否存在。后续定向复验继承了这些未充分成立的体验结论，直到用户指出具体画面，才触发真正的信息组织和交互设计。

最直接的证据：用户 11:42 指出“不清晰、没有美感”的截图，与 reviewer 用来关闭原生冲突问题的 `acceptance-r2-ios-compare.png` **字节完全相同**。问题画面已经进入验收视野，失败点在于如何判读和据此作出通过结论。

## 原因与证据

### 1. 新标准进入了会话，但旧设计的判定框架没有一起改变

原设计明确说明“本轮没有启动原生 App 取得当前截图”；手机 HTML 只表达信息和操作语义。P2 只列创建、编辑、改派、删除范围、冲突恢复等状态；`may-adapt` 允许原生 sheet/picker，要求“层级与可达操作不变”。R2 的主要退出条件是操作成功、事实一致、创建者不变、删除权限正确和草稿不丢。[原始 design](https://github.com/Mrchen116/nano-multiagent/blob/a3b2c8aa5/docs/changes/feat-584-task-progress-permissions/design.md#前端原型)

这些内容没有明确 iOS 正常编辑与冲突比较的阅读顺序、持久字段标签、信息密度、版本差异及提交含义如何呈现。作者把这部分留给“原生控件适配”，实施者便实际选择了 Form、Section、Picker 和一列 Text。这里的缺口不是要求每个平台都画全产品，而是本次新增的关键编辑流程缺少自己的体验方案。

00:29 主 Agent 读到新规则后，并未重新校准这组契约及其原生判据；可观察的后续工作是修复已经列出的 7 项问题、定向复验、保留其余证据。新标准作为原则进入上下文，旧 P/R 条目继续决定什么需要证明。

这只能说明本次应用过程的断点，不能证明任何正在运行的会话都必须全量重审。应重新核对的是受新标准直接影响、原先没有充分体验依据的判断。

### 2. 三种具体设计失败，被同一套“功能正确即可”的判断放行

**公开群发现：既有设计被实现偏离，验收又只核权限路径。** 原 design 已写“公开群发现嵌入现有新会话/群入口”。首批实现却在侧栏搜索上方添加独立按钮，并在聊天页面内直接拼出标题、关闭按钮、群名和 View group。CSS `inset:10% ...` 让弹层纵向固定占据约 80% 视窗；没有沿用既有聊天弹窗的布局和群头像列表。用户截图清楚显示少量内容撑满大块面板，与旁边已有会话行语言断裂。[首批弹层代码](https://github.com/Mrchen116/nano-multiagent/blob/51ce5e396/src/IM/frontend/src/features/chat/chat-workspace-page.tsx#L1211)；[CSS](https://github.com/Mrchen116/nano-multiagent/blob/51ce5e396/src/IM/frontend/src/features/tasks/task-graphs.css#L181)

Round 1 的 P4 对照项收缩成公开默认、私密可选、访客加入、范围切换和历史。其结论是“Web与历史读取 match”，证据是历史看板和原生建群，并未建立“发现入口及弹窗继承聊天体验”的对照。这里不是缺少一条“要用头像”的规则，而是从设计到实际验收时遗漏了整个发现入口的产品一致性。

**五列分页：列表 API 的取数方式主导了用户视图。** 原 design 直接决定“全局和负责人摘要沿用游标分页”。实现先取全局一页，再分进五列；首屏可能有很多待办，较早的完成任务却在下一页。静态审查 V4 已发现这种状态，却将修复限定为增加“本页／已加载”和局部空列提示。Round 2 又因 Previous/Next 可达、翻页可找到后续 Done 而判通过。[静态审查 V4 及闭环](https://github.com/Mrchen116/nano-multiagent/blob/c72ef882d/docs/changes/archive/feat-584-task-progress-permissions/code-review.md)

这修正了文案真实性，却没有回答原始目标“在同一总览比较哪些完成、哪些没完成”。在这种布局中，用户仍需翻过长待办所在页才能看到短完成列，五列也不拥有各自的浏览范围。直到用户指出，才改成按状态独立读取和自然追加。设计本身不合理与实现不准确是两类问题，不能只修后一类。

**iOS 编辑与冲突：数据字段直接成为页面结构。** `TaskEditorView` 用无持久标签的 TextField 承载已填写内容；描述、结果、变更说明分别最少占 3、4、2 行；负责人单独成组并重复标题；最新服务端版本在表单底部依次输出标题、状态、描述、结果和负责人，未显示字段名或差异关系。[交付代码第 27–85 行](https://github.com/Mrchen116/nano-multiagent/blob/c72ef882d/src/IM/ios/NanoIM/Features/Tasks/TaskEditorView.swift#L27)

于是系统确实保存了草稿、读到了远端、允许重试；用户却要跨长表单记住本地内容，再从无字段标签的一列值中推断对应关系。“Retry save”也只表示执行动作，没有在当前画面帮助用户判断本次会保存什么。这同时是阅读、比较与操作决策问题，不能归为纯审美偏好。

### 3. 有真实截图，但“视觉／交互通过”的结论没有得到相应证明

Round 2 写道：

> 冲突说明和恢复入口位于编辑表单顶部，草稿和服务端版本有独立分组。
>
> 服务端内容需一次正常的 Form 向下滚动即可比较。

但 reviewer 在同一轮保存的[比较截图](https://github.com/Mrchen116/nano-multiagent/blob/c72ef882d/docs/changes/archive/feat-584-task-progress-permissions/evidence/acceptance-r2-ios-compare.png)已经显示：大片固定多行留白、重复 Assignee、无标签的 `584777 / In progress / REMOTE584993 / 584123 / Test User`。用户后来发来的 `codex-clipboard-970099e3-d0d3-4dbd-bc00-f45b470a24c2.png` 与这张图的 SHA-256 同为：

`ff0d75577f537864f8a11c1fb5ddf47f13a93475747463a6827f5a10d0721f43`

这是比“截图没看”更具体的失败：**看到了画面，却用分组存在、内容可滚到、测试值可识别、重试成功，推导出用户能清楚阅读和比较。** 数字及 REMOTE 前缀有利于核对数据写入，却不足以考验正常用户面对真实标题、说明和结果时的理解成本。[Round 2 原始报告](https://github.com/Mrchen116/nano-multiagent/blob/c72ef882d/docs/changes/archive/feat-584-task-progress-permissions/acceptance.md#L123)

因此，增加“功能结果、视觉组织、交互成本”三个段落并未自动改变判断方式。报告的名称变了，其支持通过的证据仍主要是功能和结构存在。

### 4. 定向复验保留了未充分成立的体验结论

Round 2 关闭原生 F1/F2，仅留下分页尾部 inconclusive。Round 3 由用户实际拖动并点击 Load more，reviewer 独立确认 51/51，关闭最后证据缺口；原生代码未变，编辑页不再重新检查。Round 4 只关闭 Web 缓存重置及失败提示两项，继续继承原生结果，最终 PASS。

定向复验及证据复用本身合理，也确实发现并修复了实质功能问题。失败在于被继承的结论没有把“冲突数据恢复正确”和“冲突界面设计合理”分开。源码没变只能说明该画面没变，不能增强最初对它的错误体验判断。最终无遗留问题，实际只保证了既有发现列表清零。

### 5. 反馈后的设计稿仍只验证了选定路径，漏掉真实展开态

11:43 主 Agent 再次读取共同标准后，新稿确实改善了标题、属性、说明、结果和冲突比较关系，用户 11:54 的“大致方向对了”是直接反证，不能说没有产生任何设计进步。

但 11:46:39 写入的原稿中，状态和负责人使用普通 `<select>`。交付前可核对的 Playwright 路径覆盖详情→编辑、填写结果、模拟冲突、选择版本、保存、320/390 宽度和溢出检查；没有实际展开并查看两个 select 的弹出态。用户打开它们后看到浏览器默认菜单，与设计稿其他部分的移动端语言明显断裂。

这是前述机制在更小范围的再次出现：验证了已选定主路径以及静止画面，便把其中仍依赖浏览器默认呈现的交互也当成设计完成。它发生在明确读取新标准之后，不能再由旧 worktree 解释。不过用户已将这一轮限定为细节修整，不能据此否认整体方向的改善。

## 为什么我上次的修改和验证不足

PR #336 的标准方向是对的：已明确原生控件不等于设计完成、需要独立判断视觉与交互、设计本身有问题也要报告。本次读取记录证明，这些句子已到达执行者。

但我上次验证的是有界文字任务：设计试用没有真实现有画面；验收试用直接给出了“三屏后才能保存、切时区丢标题、返回位置丢失”等问题观察。它们能证明 Agent 会根据给定信息作合理判断，不能证明它会在未提示缺陷的实际界面上主动识别信息组织、组件语言与交互状态问题。[上次验证记录](../../../archive/refactor-586-ui-ux-quality/validation.md)

本次生产式任务包含旧设计、跨端适配、功能验收、问题清单和多轮证据继承；上次试用没有检验这条真实交付链。静态校验、引用检查、CI 全绿也不能补上这一缺口。更准确的评价应是“改进了规则表达并通过有限试用”，而不是问题机制已被验证解决。不能再仅以追加同义原则及同类文字试用宣布有效。

## 最小改进方向

1. **改变作出“体验通过”的证据标准。** 功能成功继续保留，但视觉/交互结论须解释实际内容如何被辨认、阅读、比较和操作；分组、按钮、截图数量不承担这种证明。对本次原生页，仅此一项就应阻止“存在最新内容区，因此可比较”的通过推断。
2. **将受影响的真实流程作为设计交付单位。** 双端共用数据语义，不代表新增原生编辑流程已设计；实现中的入口、表单、选择器及冲突状态须共同服务同一任务目标。现有 P/R 契约缺这一层时，补该流程的具体决定，不能以 may-adapt 直接降为控件选择。无需增加一套审批流程。
3. **用未标注缺陷的真实画面与操作验证 Skill。** 下一次验证应让独立执行者面对功能可用、但体验有已知问题的真实或冻结界面，自主发现并给出可追溯裁决；同时保留合理原生控件和已改善界面作反例，避免测试奖励“凡 Form 必批评”。通过标准是能在交付前拦住这类问题，而非能复述原则。

本次只形成复盘报告；未修改技能、产品代码或另一会话的工作，也未覆盖既有复盘。后续修订应依据上述机制另行验证，不能把本报告本身视为改进已经生效的证据。
