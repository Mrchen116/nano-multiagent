## 用户场景

1. **掌握分层进展**：用户先在总览比较所有根任务，再进入一个大任务，在结构图和完成情况之间切换；看清当前层哪些任务待办、进行中、待确认、完成、暂缓或关闭，点入子任务查看下一层，再沿面包屑返回。计划依赖和探索方向仍保留，完成数量不代替父任务结论。
2. **多人和 Agent 分工**：Agent A 创建大任务，将一个子任务分配给 Agent B，另一个交给真人。未分配节点等待明确安排，领取表示实际接手；人能在 Web／原生 iOS 操作，Agent 使用工具操作同一份任务。
3. **跨群协作但不复制任务**：B 群成员看见公开 A 群的任务，加入 A 群后领取或更新；B 群保留讨论入口，任务、进度和权限仍以 A 群归属为准。私密任务需要先邀请相关人员入群，或由有权者将群转公开。
4. **知道谁在负责、谁能改动**：任务显示创建者和负责人；有写入资格的群成员可共同维护，负责人承担交付责任但不独占编辑权。删除有独立资格，范围包含整棵子树时明确显示影响。
5. **在聊天中自然交接和反馈**：分配／改派、父任务暂缓／关闭、提交待确认／完成，都通过所属会话的一条系统消息及有效 @ 通知相关人或 Agent；Agent 按已有群消息配置接收和处理，不新增讨论区或额外通知通道。
6. **直接找到自己负责的工作**：用户按人或 Agent 筛选负责人，跨所有可访问任务树的层级查看匹配节点，结合所属群和父级路径理解上下文，点击回到原任务。
7. **保留已有成果**：升级时由部署 Agent 一次性整理旧任务；旧群默认私密。群解散后任务保留供历史回看，未完成工作关闭，已完成结果保持。

## 验收标准

### Requirement: 每个拆分层级提供结构与完成情况视图

保留现有计划依赖图、探索衍生树及二者嵌套。在同一层级切换结构图与完成情况视图，共用任务和状态；完成情况展示当前层的直属子任务，按待办、进行中、待确认、已完成、已关闭五组呈现；暂缓任务并入待办组，卡片仍标明“暂缓”，不更改其状态。 全局 Tasks 首屏提供根任务总览，只按可访问根节点的自身状态分组；进入某个任务后再展示其直属子任务。总览与各层使用有明确外框、列头和计数的五个状态分组，手机以对应纵向分组呈现。

#### Scenario: 比较根任务并进入下一层

- **WHEN** 用户打开全局 Tasks
- **THEN** 默认看到根任务总览，所有可访问根任务按自身状态分组，不自动选中第一棵任务树，也不混入深层任务。
- **AND** 卡片可打开详情，并通过独立子任务入口进入下一层；面包屑可回总览或任一祖先。
- **AND** 根任务及子任务的直属完成数量单独标明，不作为工作量百分比、不改变父任务自身状态；打开/关闭详情不挤窄看板或丢失当前浏览位置。

#### Scenario: 查看大任务并逐层进入

- **WHEN** 用户进入大任务或其中一个可拆分节点并切换视图
- **THEN** 当前层的直属子任务按状态呈现，深层后代不会混入本层看板；可进入下一层并通过面包屑返回。
- **AND** 节点展示自身状态及直属子任务状态数量摘要，摘要标明范围，不显示未经定义的工作量完成百分比。

#### Scenario: 探索与计划嵌套

- **WHEN** 用户在探索方向及其验证计划间导航
- **THEN** 仍能辨认当前选择、方向结果和相应结构关系；关闭的方向不计为成功完成，未选方向不自动变成必做工作。

### Requirement: 每个节点独立记录创建者与负责人

实际创建任务的人或 Agent 是创建者；负责人可以是人或 Agent，和创建者独立。新建子任务默认未分配，可在创建时指定，不继承父负责人。不新增交办人权限角色。

#### Scenario: 同一任务树由不同主体负责

- **WHEN** Agent A 创建父任务并把两个子任务分别分给 Agent B 和小王
- **THEN** 各节点显示各自创建者、负责人；未指定的子任务仍未分配，父负责人不被自动复制到后代。

#### Scenario: 经 Agent 创建及后续改派

- **WHEN** 小王让 A 创建任务，再将其负责人从 B 改为 C
- **THEN** 创建者仍为实际创建者 A，负责人变为 C；任务不会因真人交办、改派或最近修改者变化而改写创建者。

### Requirement: 人与 Agent 在相同权限原则下维护任务

Web、原生 iOS 提供创建大任务／当前层子任务、领取、调整负责人、编辑标题／描述／结果／状态和有权限删除等基础操作。Agent 工具提供对应能力，按实际调用主体鉴权。有所属会话写入资格的成员可共同维护，负责人不独占编辑。

#### Scenario: 人直接操作及成员共同维护

- **WHEN** 小王直接创建任务，或群内有写入资格的成员修改他人负责的任务
- **THEN** 操作按对应主体记账并反映到同一份任务；人直接创建记小王为创建者，修改者可辨认；不要求通过 Agent 才能完成基础操作。

#### Scenario: 先入群再分配

- **WHEN** 为任务选择负责人
- **THEN** 只能选择任务所属会话中的人或 Agent；非成员需先按群规则加入，分配操作不会自动拉人入群。

#### Scenario: 分配与领取分离

- **WHEN** 任务被分配或改派给某负责人
- **THEN** 分配本身不代表该负责人已经开工，也不把通知投递当作进行中；领取才表示接手开始推进。
- **AND** 其他主体不能通过领取直接抢占已有负责人任务，转交通过明确改派完成。

### Requirement: 任务可见范围跟随固定所属会话

公开群及其任务对公司内有资格的人和 Agent 可读；私密群及其任务仅成员可读；私聊任务仅参与者可读。公开不等于互联网匿名公开。领取、修改等写操作仍要求所属会话写入资格。

#### Scenario: 公开可读、加入后操作

- **WHEN** 公司内有资格的人或 Agent 尚未加入公开 A 群
- **THEN** 可读取公开群及其任务，自行加入后才能领取、修改；仅查看不会自动加入。

#### Scenario: 私密群和私聊

- **WHEN** 非成员尝试读取私密群或非参与者尝试读取私聊任务
- **THEN** 不因同公司、知道任务链接、管理某 Agent 或拥有公司管理员身份就取得读取资格；私密群参与需邀请。

#### Scenario: 在另一群讨论公开任务

- **WHEN** A 群任务在 B 群被引用、讨论或由具备 A 群写入资格的主体更新
- **THEN** 两处打开同一任务，任务归属和可见范围仍由 A 群决定；不复制任务、不按最后讨论群改变归属，也不产生局部子树共享权限。

### Requirement: 群类型具有明确默认值、加入方式与切换资格

新建群默认公开，可选私密；旧群升级时默认私密。公开群允许公司内有资格的人和 Agent 自行加入，私密群需邀请。公开／私密双向切换仅限已加入该群的公司管理员。

#### Scenario: 创建和加入

- **WHEN** 人或 Agent 新建群，或希望参与已有公开群
- **THEN** 新建时默认公开且能选择私密；公开群可自行加入，无需逐次邀请审批，私密群不提供自行加入；人有界面入口，Agent 有工具入口。

#### Scenario: 更改可见范围

- **WHEN** 已入群的公司管理员把群改为公开或私密
- **THEN** 群消息和所属任务一起采用新范围，已有成员与内容保留。
- **AND** 非管理员群创建者或普通成员不能仅凭创建／改名权限切换；未入群的公司管理员也不能直接切换。

### Requirement: 删除采用独立权限并包含所选节点整个子树

任务创建者或公司管理员可删除，仍须满足所属会话访问与写入条件。负责人身份本身不授予删除权。删除是真正移除记录，与关闭保留记录不同。

#### Scenario: 删除父任务

- **WHEN** 有删除资格的主体明确删除一个父任务
- **THEN** 删除范围包含该节点及整个下属子树，包括其他主体创建或负责的后代，界面／工具清楚呈现范围，不逐个请求子任务创建者审批。
- **AND** 沿用既有明确范围的删除授权及工具权限流程；范围已明确时不额外要求重复确认，不将笼统整理或普通状态更新当作删除授权。

#### Scenario: 只有编辑权或只有管理员身份

- **WHEN** 非创建者普通成员尝试删除，或公司管理员尝试删除其无访问／写入资格的会话任务
- **THEN** 删除被拒绝，任务及子树保持；管理员名下的 Agent 不自动继承管理员角色。

### Requirement: 六种状态表达进展，验收采用引导而非强制门禁

状态为待办、进行中、待确认、已完成、暂缓、已关闭。Agent 引导采用做完先提交待确认供人验证、确认后完成；系统仍允许直接完成，不增加必经审批、专属验收人或第三种任务权限角色。

#### Scenario: 提交结果

- **WHEN** Agent 完成工作并按协作引导提交结果
- **THEN** 可以标为待确认，展示结果并等待反馈；有资格的成员可调整状态，系统不强制每次完成都经过真人审批。

#### Scenario: 普通父子状态变化

- **WHEN** 子任务全部完成，或父任务被暂缓、关闭、重新打开
- **THEN** 未明确指定的其他节点状态保持，父任务不会因子任务完成自动完成；状态变化不直接启动或停止 Agent 执行。
- **AND** 显式调整整个子树时保留已完成节点的完成事实；普通父状态变化不等于整棵子树状态操作。

### Requirement: 任务协作通知使用所属会话的一条系统消息

不引入任务专属讨论区、关注名单、重复私信或额外交接回执。群内系统消息对全体成员可见，以下 @ 为系统识别的有效成员提及，不只是普通名字文本。

| 事件 | 同一条系统消息中的 @ 对象 |
|---|---|
| 首次分配 | 新负责人 |
| 改派 | 原负责人和新负责人 |
| 取消分配 | 原负责人 |
| 父任务暂缓／关闭 | 直属下一层子任务已分配的 Agent |
| 任务进入待确认／已完成 | 本任务创建者及直属父任务负责人（若有） |

同一主体在一条消息中只需提及一次；根任务没有父负责人，结果通知只提醒创建者。消息说明发生变化的任务及变化内容，能回到原任务查看结果和上下文。按 Q39，系统消息不重复显示“任务动态”标签，不附结果摘要或结果展开控件。接收资格沿用会话成员规则，不为通知授予额外访问权限。

#### Scenario: 改派双方获知

- **WHEN** 小王把「修复登录失败」从 A 改派给 B
- **THEN** 所属群出现一条类似“小王将「修复登录失败」从 @A 改派给了 @B”的系统消息，其他成员也可看见，不另发一轮通知。

#### Scenario: 暂缓／关闭逐层传达

- **GIVEN** 任务有 A → B → C 三层
- **WHEN** A 暂缓或关闭
- **THEN** 所属会话的一条系统消息 @ B 层已分配的 Agent，不跨层主动 @ C；只有 B 的实际处理形成相应变更时，才按同一规则继续通知下一层。
- **AND** 不自动修改 B／C 状态，不终止被通知 Agent 的其他无关工作。

#### Scenario: 结果向上反馈

- **WHEN** 子任务进入待确认或已完成
- **THEN** 一条系统消息 @ 该任务创建者及直属父任务负责人；他们能查看结果并继续协调，但不因此成为系统强制验收角色，也不自动修改父状态。

### Requirement: 通知遵循已有 Agent 群接收策略及忙闲处理

复用现有消息／Inbox 与执行机制，群内可见不等于所有 Agent 立即执行。分配通知是可由负责人接手的交办信息，读取并领取后才表示开始推进。

#### Scenario: always 与仅 @ 的 Agent 同群

- **WHEN** 改派消息 @ A 和 B，群里另有 always 模式的 C、仅 @ 模式的 D
- **THEN** A／B 因有效 @ 命中，C 按 always 命中，未被 @ 的 D 不因该消息主动运行，消息按已有背景／Inbox 机制保留。

#### Scenario: 空闲、忙碌、离线与取消当前执行

- **WHEN** 应处理通知的 Agent 空闲、忙碌或离线
- **THEN** 分别采用主动触发、排队等待合适处理时机、保留待处理通知；不等用户必须再次发话，也不把已投递显示成已开工。
- **AND** `/stop` 保持取消当前执行的语义；后续有效任务消息仍按既有群策略触发处理，不新增持久停止或等待真人恢复的状态。
- **AND** 不另开一个冲突执行，不把整张任务图或依赖关系自动变成任务调度器。

### Requirement: 负责人视图跨层汇总其直接负责的任务

#### Scenario: 一人负责多棵树的深层节点

- **WHEN** 用户在全局任务入口按某个人或 Agent 筛选负责人
- **THEN** 汇总所有可访问任务树、所有层级中该主体直接负责的节点，显示所属会话与父级路径，点击返回原节点所在层级。
- **AND** 父子同属该负责人时都可出现；不会将他负责的父节点全部后代都当作他的任务。此视图不改变每层完成情况仅展示直属子任务的规则。

### Requirement: 解散群关闭未完成工作并保留任务成果

#### Scenario: 群解散时仍有任务

- **WHEN** 有解散资格的主体解散群
- **THEN** 所属任务树及结果保留，待办／进行中／待确认／暂缓任务统一关闭，已完成／已关闭任务保持；按解散前的可见范围提供历史回看入口。
- **AND** 解散不是整群任务的永久删除授权，不恢复旧的公司共享权限，也不丢失不同创建者的工作成果。

### Requirement: Web、原生 iOS 和 Agent 工具操作一致

#### Scenario: 跨入口维护同一任务

- **WHEN** 用户在 Web／原生 iOS 或通过 Agent 创建、领取、修改、分配任务及管理相关群设置
- **THEN** 相应入口遵循同一权限、状态和通知规则，操作结果在其他入口可见；手机布局可适配屏幕，原生 iOS 不以网页容器代替内部页面。

### Requirement: 部署 Agent 一次性整理存量数据

#### Scenario: 旧群及旧任务升级

- **WHEN** 部署本 unit 并按 [迁移 guidance](migration-guidance.md) 整理存量数据
- **THEN** 旧群默认私密，任务归属得到整理且按新范围访问；任务内容、层级、依赖和探索结果保留，不因最后讨论位置直接改变归属，不伪造创建者或已有分配。
- **AND** 原放弃状态承接为已关闭；迁移不伪造开工或完成、不批量唤醒 Agent。确实无法判断的具体数据问题才提交用户，不建设长期人工整理产品。

## 范围与非目标

本次覆盖任务分层进度展示、节点创建者／负责人、会话归属及权限、公开／私密群的创建／加入／切换、基础任务界面与工具操作、六状态、上述系统消息通知、跨层负责人视图、群解散后的任务保留，以及存量迁移。Web 与原生 iOS 同步覆盖。

保留现有计划／探索结构和任务记录与执行分离的原则。其他已有能力保持 current 行为，例如已明确授权的工具操作流程、群消息接收配置、现有群解散资格；本 unit 只修改本文明确列出的产品行为。

不包含：

- 私密群子树局部共享、跨群复制任务或随讨论位置迁移归属。
- 新的交办人／验收人／群管理员权限角色，以及 Agent 自动继承其管理者身份。
- 任务专属讨论区、关注订阅机制、重复私信通知或强制交接确认。
- 强制真人验收门禁、任务树自动执行、按依赖自动调度、普通父子状态自动联动。
- 完整图形拖拽编排器、任务回收站或历史版本系统；基础操作不要求这些额外能力。
- 未在通知表中明确列出的新增自动 @ 规则；例如重新打开父任务不自动恢复或唤醒下属工作。
- 长期保留旧公司共享权限的兼容产品层。
- 持久停止整个 Agent 的开关、自动唤醒抑制位或新的恢复入口。

实现结构、公开 DSH 能力的具体承接、迁移命令与消息持久化方案交给设计；它们不得改变以上产品语义。当前文档完成不代表代码、部署或真实客户端验收已经完成。

## 原始需求

### Q6：跨群共享子任务（历史提案，Q10 已排除局部共享）

Agent 提出场景：A 群总任务含商业方案、开发功能、发布预算，将开发功能交给原本无权访问 A 群任务的 B 群；建议只共享开发功能及其下属拆分，不自动开放父任务或兄弟任务。

用户尚未选择，要求之后每个场景都同时说明：Raft 当前是否支持及具体逻辑、Nano 当前逻辑、Agent 推荐逻辑及取舍。此要求适用于本次后续对齐；不把此前单独提出的推荐记为用户决定。

本场景三方对照：

- Raft：普通 Task 绑定一个 Channel，当前任务模型没有 Nano 式父子任务图，也没有原生子树跨频道共享。公开频道任务按公开读取规则访问；私有频道任务按成员访问。在 B 群发送 A 群任务链接不会自动授予权限。若邀请 B 群相关成员加入私有 A 群，会开放 A 群相应内容；若在 B 群另建任务，则是独立任务，不自动同步 A 群原任务。
- Nano current：任务图具有嵌套结构，但所有有效公司成员及具备任务能力的有效 Agent 可读取同一完整图。B 群更新子任务后，该节点进入 B 群活动视图；A/B 使用同一份任务事实。群活动关联不是权限，只看开发功能的入口并不限制其读取商业方案、发布预算或父任务。
- Agent 建议（未确认）：显式共享开发功能子树给 B 群，A/B 维护同一份数据；B 群仅因这次共享取得该子树访问权，不取得父任务、兄弟任务或原 A 群聊天的访问权。代价是新增子树授权及受限图展示规则，超过 Raft 的频道权限模型；需要后续明确共享管理、成员变化和撤销等行为。

### Q7：先澄清频道类型与公开读取

用户指出 Q6 的“私有 A 群”前提混入了 Nano 尚无的频道分类。修正：Nano current 只有 direct/group 等既有会话形态，聊天按成员可见，没有 Raft 式公开／私密频道产品选项；当前公司共享任务的可见性则独立于聊天成员。

Raft 普通公开频道允许同服务器有访问资格但尚未加入的 Agent 读取消息与任务，写入还需频道成员／发言资格及动作约束；私密频道及 DM 则先要求参与资格才能读取。这是读取与参与操作的区别，不能简化成“所有频道任务只对频道成员可见”。源码依据为 `channelService.ts` 的 `canAgentAccessChannel`、`canAgentPostToChannel` 及 Agent Task 路由。

当前只确认私聊任务改为参与者可见。群任务是否保留公司范围可读、是否仅限成员操作、是否引入公开／私密群，以及子树共享均未决定。Q6 的局部共享仍是建议，不作为已确认范围。

最终决定：引入公开群与私密群，任务默认跟随所属群的可见范围。公开群面向公司内有访问资格的人和 Agent 可读，不要求先加入；私密群按参与成员可读。私聊任务继续采用 Q5 的参与者可见规则。公司内公开不等于匿名互联网公开。

此项将群可见性纳入本 unit 的需求范围，不仅是任务页筛选变化。是否能修改任务仍按后续动作权限讨论，不能由可读自动推出。群创建时默认类型、已有群／任务承接、公开与私密切换、加入方式等仍待对齐。

### Q9：基于群可见范围继续讨论子任务跨群（局部共享建议已被 Q10 排除）

需要区分两种情形：公开 A 群的任务可由有资格的 B 群成员读取，跨群讨论本身无需扩大读权限，但写权限仍待定；私密 A 群的子任务交给 B 群则涉及明确扩大局部可见范围。

三方对照基础保持 Q6：Raft 不原生支持任务子树跨频道共享；Nano current 依赖整张图公司共享及群活动入口，尚无子树授权；Agent 建议保留原任务及进度，明确共享指定子树给 B 群，原 A 群保留访问，不向 B 群自动开放父任务、兄弟任务或原聊天。公开 B 群意味着该共享子树将向公司内有访问资格的人和 Agent 可读，私密 B 群则限其成员；此为待用户判断的方案，不是已确认规则。

### Q10：排除私密群局部对外共享，聚焦公开群协作（已确认）

接下来只对齐公开 A 群任务在 B 群讨论与推进的行为。B 群成员可按公开范围读取同一图，但是否必须加入 A 群才能领取、更新等，仍未决定。

### Q11：公开群任务的读写资格（已确认）

### Q13：删除权限与父任务级联删除（历史提案，Q14／Q15 已收口）

Raft 当前：正常频道内先检查频道写入资格，再限制任务创建者或具备 `deleteAnyTask` 能力的管理员／Owner 等主体删除；负责人本身不自动获得删除权。Agent 删除入口也判断真实创建者或删除能力。普通任务无 Nano 式父子结构，不能据此推导级联删除授权。依据：`packages/server/src/routes/tasks.ts` 的 `DELETE /:taskId`、`packages/server/src/routes/internalAgentApi.ts` 的 Agent Task 删除路由。

Nano current：有效公司成员可经有任务能力的 Agent 明确删除图或子树，不按创建者、负责人限制；删除必须有用户明确要求或确认，并沿用统一工具权限。删除某节点会连带删除其下属拆分。依据：[当前任务契约](../../specs/im/task-graphs.md)及 `apps/im-server/src/task-graphs.ts` 的 delete 分支。

Agent 建议（未确认）：采用创建者或公司管理员可删除，仍须有任务所属群的写入资格；负责人和普通群成员不因编辑权自动取得删除权。删除父任务包含其整棵子树，按被删父任务的删除资格判断，不增加逐子节点审批；因此父任务创建者可能连带删除其他人或 Agent 创建／负责的子任务，必须把这个效果作为明确范围呈现。沿用已有明确删除授权，不把普通更新、完成、放弃或笼统整理当作删除授权；范围已明确时不重复要求确认。

管理员含义澄清：用户问“管理员是啥概念呢”。Raft 的 admin/owner 是服务器级角色，默认具备 `deleteAnyTask`，不是单个任务负责人或频道创建者。Nano current 已有真人账号的 `is_company_admin`，用于批准／停用公司成员、管理公司策略，且不自动授予他人私聊或设备管理权。Q13 的推荐指复用这个公司管理员身份，不新增群管理员或任务管理员，也不默认把管理员名下的 Agent 变为管理员；如何代表真人执行仍待对齐。公司管理员删除任务及级联范围仍为未确认建议。依据：[公司资格与管理员契约](../../specs/im/auth-tenancy.md)、`apps/im-server/src/schema.sql`、Raft `packages/shared/src/serverPermissions.ts`。

### Q14：复用公司管理员的删除资格（已确认）

用户答复：“可以，就复用公司管理员，但是还是要学raft那样，默认拥有删除他人任务的权限，仍要满足相应频道访问与写入条件。”

最终决定：采用创建者可删除自己任务、公司管理员默认可删除他人任务的角色规则；两者都仍须满足任务所属聊天的访问和写入条件。公司管理员身份不绕过私聊参与资格或私密群成员限制，公开群也仍需写入资格才能删除。复用已有公司管理员，不另设任务管理员。

本轮确认的是角色资格，不把它视为父任务级联删除授权规则已经收口。父任务删除是否允许连带其他创建者的下属任务、真人经 Agent 执行时如何核实授权主体，仍待对齐。

### Q15：级联范围及关闭／删除的区别（已由后续答复确认）

用户确认“删除父任务连带删除整个子树”，随即提出是否应对应 Raft 已关闭、保留记录，并追问“raft的删除是已关闭的意思吗”。不将这一答复理解为用户已无条件接受永久清除任务记录。

源码核实：Raft 的 closed 是任务状态，保留任务、事件历史，可按状态规则重新打开；delete 是另一个操作，`deleteTaskByOwner` 清除关联消息上的任务字段并删除 canonical tasks 行，task_events 随外键级联删除，但关联消息正文仍保留。依据为 `taskService.ts:530`、`:2343`、`:2378`、`:2925` 及 `schema.ts:3502`。

Nano current 的 delete 会移除图／子树，不是保留节点的 dropped 状态。Agent 建议：若目标是停止推进且保留回看，采用“关闭”这一名称与保留语义，不把“删除”与“关闭”混用。关闭是否覆盖整个子树、完成节点如何处理、关闭权限是否采用一般状态修改权限，以及是否仍提供永久删除，需基于用户保留记录的意图继续对齐，不能直接从此前删除权限推导。

后续用户明确纠正：“那我搞错了，删除父任务连带删除整个子树。不用混淆两个概念”。

最终决定：删除保留真正移除任务记录的语义，不改成关闭、软删除或回收站。删除父任务连带删除整个子树，按被删除父任务的删除资格判断，不要求逐个子任务创建者审批，即使下属任务由其他人或 Agent 创建／负责也在删除范围内。沿用 Q14 的创建者／公司管理员资格及所属聊天访问、写入条件，以及明确删除范围的用户授权。关闭与删除是独立概念，本次纠正不确认关闭的级联或恢复行为。

### Q16：经 Agent 创建任务时的创建者身份（已确认）

### Q18：看板状态与待确认语义（已确认）

- Raft 当前：todo / in_progress / in_review / done / closed，分别为待办、进行中、待确认、完成、不再做。待确认是协作状态，服务端允许进行中直接完成，不是强制真人验收门禁。
- Nano current：todo / doing / done / paused / dropped，分别为待办、进行中、完成、暂缓、放弃；没有独立待确认状态，父子状态不自动联动。
- Agent 建议（未确认）：采用待办、进行中、待确认、已完成、暂缓、已关闭六种状态；增加可选待确认，保留暂缓，将原放弃的用户可见名称统一为已关闭。待确认表示已提交结果等待反馈，不强制每个任务经过，也不新增专属验收角色；有编辑资格的成员仍按共同维护规则改状态。探索负结果保存在结果中，不因结果为负自动标为关闭；关闭不计为成功完成。状态集合及关闭对下属任务的影响分开对齐。

用户追问：“‘待确认’可选，允许进行中直接完成，不强制真人验收。那什么时候决定的是否需要真人验收？”（原话完整保留于原始需求。）

进一步核实：Raft 没有通用的“本任务必须真人验收”字段来控制该状态转换；其 Agent 指引 `packages/daemon/src/drivers/raftCliGuide.ts` 的 Workflow 第 4/5 步要求做完先 `in_review` 供人验证，批准后 `done`，而服务端仍允许直接 `in_progress → done`。因此“允许直接完成”是接口能力，不等于 Agent 指引默认允许自主跳过人工验证。Nano current 仅显式记录完成，不存在待确认状态或通用验收开关。

Agent 补充建议（未确认）：在讨论／创建任务时通过任务描述或明确指令约定验收方式；Agent 默认提交待确认，用户明确允许按约定标准自行验证完成时才直接完成；中途的新要求可更新该约定。未说明时采用待确认，不让 Agent 仅凭自认为做完就推定无需人确认。这是行为约定，不是新增不可绕过的审批门禁或身份字段。六状态方案及这一默认验收行为均待用户决定。

用户后续答复：“就学raft这种做法就行了。有引导，不用强制验收门禁。然后上一个问题：我同意，增加‘待确认’，保留‘暂缓’，把‘放弃’统一称为‘已关闭’，共六种状态。”（原始标点保留于原始需求。）

最终决定：六种状态为待办、进行中、待确认、已完成、暂缓、已关闭。增加待确认，保留暂缓，原放弃统一称为已关闭。沿用 Raft 的 Agent 行为引导：完成工作先提交待确认供人验证，确认后完成；系统仍允许进行中直接完成，不设置强制真人验收门禁、专属验收角色或必经审批步骤。上一段“必须先有明确允许自行验收”的建议不升级为额外系统授权条件；具体工作按用户指令与引导推进。

### Q19：父任务暂缓／关闭时是否联动子任务（已确认）

- Raft 当前：普通任务无父子结构，暂不提供这一层级联动规则；状态 closed 不代表自动终止 Agent 执行。

最终决定：状态默认不联动，只更新明确指定的节点或范围；父任务暂缓、关闭、重新打开均不自动改写下属状态，也不启动或停止 Agent 执行。整棵子树调整需明确指定范围，保留已完成节点的完成记录。删除整棵子树继续遵循 Q15，不能与状态更新混同。

### Q20：分配任务是否通知负责人（已确认）

- Raft 当前：分配与领取分离，分给别人不等于已开工。不同入口通知不完全一致：Agent 创建并分配时会持久保存带负责人定向提及的分配回执，再通过消息编排通知；Web 改派会向任务 thread 发布生命周期通知；Agent 单独 assign 路由本次核实到状态更新广播与动作记录，不能概括为所有 assign 都具有相同定向唤醒语义。参考 `internalAgentApi.ts:5965`、`:6055`、`:6496` 与 `routes/tasks.ts:712`、`:507`。
- Nano current：任务图是持久计划／进度记录，没有负责人或分配通知；任务工具不创建执行或调度工作，另在聊天中交办。
- Agent 建议（未确认）：创建时分配或后续改派给人／Agent，均向新负责人发送明确的任务通知。分配保留待办语义，负责人接手领取后才进入进行中；Agent 按既有消息处理能力读取任务、领取并推进，忙碌或离线不能被显示成已经开工。通知只针对明确分配的任务，不自动分配其子任务、不按依赖启动整张图，不另建任务调度器。是否把分配通知作为可直接接手的交办信号由用户本轮决定。

用户答复：明确要求“分配即通知，领取后才表示开始推进”，并追问 Raft 是立即触发 Agent 还是仅增加上下文、等待下一轮 LLM 请求。

最终决定：分配即通知新负责人，领取后才表示开始推进。消息已发出／已投递不能直接把任务标为进行中。具体忙闲唤醒策略尚未由此次答复确定。

本轮 Raft 源码追踪（非现场投递验收）：

- Agent 创建并分配：任务、分配回执、定向提及及 Inbox 事实持久保存；消息服务通过 Agent 编排层向 Daemon 推送。定向负责人通知可穿过其频道静音，前提仍是接收范围及频道访问资格有效。
- 正常托管 Agent 空闲且 runtime session 可接收：Daemon 将正文放入 Inbox，主动写入不含正文的收件箱更新提示，开始新一轮处理；提示要求 Agent 用 `raft message check/read` 读取消息。并非等待用户下一次发话，也非直接改写已经发出的 LLM 请求。
- Agent 忙碌：正文先排队。带追踪的定向提及路径等待 `turn_end` 后继续投递；普通通知还可按运行时能力发送忙时提示，如 Codex `turn/steer`、Claude 原生输入队列。不能统一称为每条通知都立刻中断当前推理。已发出的单次 LLM 请求不会因此被原地添加上下文。
- 正常闲置退出／允许自动运行但没有进程：服务端或 Daemon 尝试恢复／启动；显式 stopped 阻止自动唤醒。机器离线无法马上执行，持久消息和回执不等于运行成功。外部接入且不由 Raft 托管的 Agent 走 Inbox／wake-hint，由其桥接运行时处理，Raft 不直接启动它。
- 各分配入口的通知差异仍按上方记录，不把此定向通知路径推断成所有 assign 入口都有完全相同的保证。

定位：Raft `messageService.ts:3357,3535`、`agentOrchestrator.ts:10920,11180,11318`、`agentLifecycleReducer.ts:223`、Daemon `agentProcessManager.ts:4490,4600,7294`、`agentRuntimeInput.ts:198`、`drivers/codex.ts:1168`。

对 Nano 的建议（尚未确认）：复用既有消息／Inbox 与 DSH 执行入口实现负责人通知；空闲时触发处理，忙碌时排队至合适轮次，不并行启动第二个冲突执行；离线保留待处理通知，尊重手动停止。无需原样复制 Raft 的 stdin 或消息读取提示格式，具体内部承接交由 design 核对现有 PA/DSH 能力。

用户后续答复：“可以，就按这个来，然后我觉得父任务暂缓或关闭也应该以类似方式通知到子任务已分配的agent。”

最终决定：分配后持久通知新负责人，空闲 Agent 主动触发处理、忙碌 Agent 排队、离线保留待处理通知、尊重手动停止。读取任务并领取后才表示开始推进。复用现有 PA／DSH 消息处理能力，不另外建立任务调度器；具体运行时承接由 design 核对公开能力与现有机制，不要求照搬 Raft 内部协议。

### Q21：父任务暂缓／关闭通知直属子任务 Agent（已确认）

用户明确增加：父任务暂缓或关闭也采用类似方式，通知子任务已分配的 Agent。

三方对照：Raft 普通任务没有 Nano 的父子拆分结构，不提供此祖先状态到下属负责人的通知规则；Nano current 修改父节点状态不自动联动子节点，也没有此通知；本次增加父任务状态变化的下属负责人通知，复用 Q20 的持久通知及忙闲处理方式。

最终决定：父任务暂缓／关闭后，在任务所属会话发布一条系统消息，有效 @ 直属下一层子任务中已分配的 Agent，不逐个另发通知，不跨层 @ 整个下属子树。群会话内消息对全群可见，是否触发各 Agent 处理沿用 Q22 的现有 `always`／`mention_only` 策略；“仅下一层”限定本次任务通知主动 @ 的范围，不覆盖普通群消息接收配置。沿用 Q19，通知本身不自动改写子任务状态，也不等同于强制杀掉 Agent 进程或取消其所有工作；Agent 收到的是该父任务及相关子任务的协作信息，不能扩大为暂停其其他无关任务。手动停止的 Agent 不被擅自唤醒。

Agent 曾建议覆盖整个下属子树中尚未结束的任务。用户明确收窄：“通知范围，我觉得下一层就可以了吧，再下面的层根据这一层的处理而会间接收到。”因此不采用全子树直接通知。更深层依据直属负责人对本层任务的实际处理逐层收到信息；例如直属负责人显式将自己的任务暂缓／关闭时，再按同一规则通知其直属子任务负责人。收到祖先通知本身不会自动递归转发或改写后代状态。

用户在 Q22 明确会话系统消息及 Agent 既有群接收策略后，继续确认父任务状态通知也使用会话内系统消息。统一采用上述同一消息载体与有效 @ 机制；同一 Agent 负责多个直属子任务时，在这一条消息中提及一次即可，不因节点数重复发通知。

历史细化建议：曾提出按子节点状态过滤提醒、父任务恢复时另行提醒、人类子任务负责人对应提醒等扩展。本次不新增这些 @ 规则，按正文通知表实现；通知说明实际发生的父任务变化和相关子任务，后续工作由相应主体按用户指令处理，状态仍显式更新。

### Q22：改派／取消分配通过群系统消息告知（已确认）

场景：任务原由 Agent A 推进，成员将其改派给 B，或取消分配。Q20 已确认新负责人通知，但尚未明确原负责人是否收到定向通知，避免 A 不知情地继续工作。

- Raft 当前：Web 改派／取消分配会在任务 thread 发布生命周期系统消息，按 thread 接收范围分发；该入口未专门把原负责人列为定向提醒对象。Agent 单独 assign 入口更新任务、广播任务变化并记录动作，本轮未见等同于创建并分配路径的定向唤醒。不能把任务更新广播等同于原负责人必然收到可触发处理的通知。依据 `routes/tasks.ts:507,712`、`routes/internalAgentApi.ts:6496`。
- Nano current：无独立负责人字段及改派通知机制；任务记录更新不直接改变执行状态。
- Agent 建议（未确认）：改派时同时通知原负责人和新负责人；取消分配时通知原负责人。对 Agent 沿用 Q20 的持久通知和忙闲处理方式；原负责人收到不再负责的信息后，引导其停止继续推进该任务、补充已有进展及交接信息，不直接终止整个 Agent，也不要求等待原负责人确认后才允许改派。本问题仅确定通知与协作行为，不改变已确认的群内共同维护权限。

用户追问：“是不是可以参考raft的做法？”

补充核实：Raft Web 改派在任务自己的 thread 发布系统消息，经 `broadcastSystemMessageToLocalSurfaces` 记录 Inbox 事实并按讨论串接收范围投递；没有为原负责人单列定向提醒对象，也不等待其交接确认。任务事件另保存原／新负责人。此处是 Web 路径的实际行为，不扩展为所有 Agent assign 入口的统一保证。

调整后的建议（待确认）：参考 Raft，以任务关联讨论中的改派／取消分配系统消息告知参与者，沿用普通消息接收机制；不额外要求向原负责人单独定向唤醒或强制交接回执。已经确认的“分配即通知新负责人”继续保留。Nano 的讨论载体与现有聊天／任务活动入口如何衔接留给后续设计，不因参考本规则就默认引入完整 Raft thread 产品。此建议替代上一段对原负责人强制定向通知的建议，尚不作为用户已确认的结论。

用户继续追问讨论串含义及谁会收到消息。进一步核实：Raft 普通任务 thread 的持续通知由独立 `thread_follows` 关注名单决定，不是全群成员或任务角色名单。正常回复者自动关注；有人回复时，作为讨论起点的原消息作者也自动关注；在讨论中有效 @ 提及的所属群成员可被加入关注；用户可以手动关注。仅打开讨论面板不会自动关注，单独修改任务负责人也不写关注记录。原消息作者不能无条件等同于任务创建者。取消关注后普通后续消息不再按关注关系通知；再次回复、有效直接 @ 或手动关注可重新激活，访问资格仍需有效。Agent 的普通系统消息投递还遵守静音及运行时接收规则。

依据：`channelService.ts:6451,14118`（建立讨论不创建关注、关注写入规则），`messageService.ts:2732,8960`（回复／原消息作者及提及自动关注），`:249,309,3258`（合格关注者与系统消息投递）。因此前文“参与者会收到”应准确理解为“仍有访问资格的有效关注者进入通知范围”，不是看过任务或担任负责人就必然收到。Nano 尚无这套独立任务讨论及关注机制，是否引入属于产品范围决定，不能仅作内部技术映射默认纳入。

用户选择不引入任务讨论区及关注名单，而是在任务所属群发布系统消息，发送给群内所有成员。最终决定：本次不引入 Raft thread／follow 产品机制；改派／取消分配通过任务所属群的系统消息告知全体群成员，包括人和 Agent，不限于原／新负责人，不额外建立交接确认门禁。

用户随后质疑 Agent 所说的“同时保留已经确定的新负责人定向通知”是否存在于 Raft。澄清：Raft 的 Agent 创建并分配路径会在所属聊天保存一条带负责人有效 @ 的系统分配回执，并用同一条消息的 `personalAttentionTargets` 标记负责人；这不是另发一条私信。Web 后续改派是普通任务 thread 系统消息，Agent 单独 assign 入口也没有同等定向投递保证。不能将创建分配路径概括为所有分配操作的统一行为。依据 `taskService.ts:1824,1853`、`internalAgentApi.ts:6055,6068,6496`。此前 Q20 已确认分配通知及忙闲处理，但不等于必须在群系统消息之外重复发送一条通知；当前不把额外通知作为新增要求。群系统消息是否对新负责人附有效 @，需与最新简化方向继续明确，不擅自确认或取消。

用户最终确认：“那就在群系统消息里 @ 新负责人就行，不用额外发通知。”

用户进一步明确改派示例：“系统：小王将「修复登录失败」从 @Agent A 改派给了 @Agent B。”并说明“应该这样吧，两个都@了，同时整个设计很简单”。本次确认覆盖前述仅 @ 新负责人的方案。

最终决定：群任务分配／改派使用同一条群系统消息，在任务所属群内对全体成员可见，Agent 是否因此触发处理遵循其现有群消息策略。首次分配有效 @ 新负责人；改派有效 @ 原负责人和新负责人；取消分配有效 @ 原负责人。不另发私信或重复通知，不引入独立任务讨论区和关注名单。命中接收策略的 Agent 沿用 Q20 已确认的持久通知及忙闲处理语义；通知不等于已领取或已开工，也不直接终止 Agent 执行，不设置交接确认门禁。

用户提醒已有每个 Agent 的 `always`／仅 @ 配置。核实 current：`packages/personal-assistant/src/attention.ts` 的 `needsAttention` 对群消息检查 `groupReplyPolicy === 'always'`、结构化 `mentioned_agent_ids` 或 `reply_to_agent_id`；`context_only` 不触发处理。未命中时，single_thread 将消息放入群上下文缓冲，global 存入 Inbox 但不因该消息唤醒；见 `single-thread.ts:53`、`global-agent.ts:77` 和 [当前群路由契约](../../specs/gateway/routing-delivery.md)。因此“全群可见”不等于“所有 Agent 立即运行”。本次任务系统消息复用现有策略：`always` Agent 无需被 @ 也可触发处理；`mention_only` Agent 在该消息有效 @ 自己时触发，未被 @ 则仅保留可见／背景消息，不为任务通知绕过原门控。改派消息有效 @ 双方，使原、新负责人即使采用 `mention_only` 也能命中；其他 `always` Agent 仍按自身配置接收。这里的 @ 必须为现有系统能识别的成员提及，不是仅拼接显示名称。实际处理时机仍受忙闲、离线、手动停止等已确认规则约束。

### Q23：公开群是否允许人和 Agent 自行加入（已确认）

用户答复：“可以，就按raft这样，公开群人和Agent都可以自行加入，私密群需要邀请。继续下一个问题。”

### Q25：已有群升级后的类型（已确认）
