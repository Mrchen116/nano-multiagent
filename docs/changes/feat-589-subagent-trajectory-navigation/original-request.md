标题：feat: 从主轨迹发起点跳转子 Agent，并聚焦本次执行区间

## 问题与目标

当前 Work 原生轨迹可以通过顶部执行选择器切换主 Agent 和关联子执行，但所有关联执行平铺展示，后台维护会话直接显示 `nano-review:<UUID>`。用户难以知道某次子执行为什么启动、从主轨迹哪里分出去，以及本次真正执行了哪一段。

目标是打通 **主轨迹发起点 → 对应子 Agent 的本次执行区间 → 返回原发起点**。顶部执行选择器仅作为辅助导航，不承担发现子 Agent 和解释父子关系的主要职责。

本 issue 记录已对齐的产品方向，留待后续设计和实施；不在本次启动开发。这里补的是已有 subagent 的轨迹呈现，不是新增 subagent 调用能力。

## 已确认的交互方向

### 1. 主轨迹中显示可进入的发起记录

覆盖两类来源：
- 主 Agent 主动调用 subagent，明确是否 fork、用途及状态。
- 后台机制自动拉起的 subagent，例如记忆整理、技能复盘；即使没有模型工具调用，也应在真实发起位置显示对应入口。

点击发起记录直接进入对应子轨迹。后台记录显示可理解的用途，内部 UUID 留在详情中。并行子执行各自有明确的对应关系；工具启动调用返回，不代表子执行已经结束。

### 2. 进入子轨迹后自动聚焦“本次拉起”的完整执行区间

沿用原生时间概览的区间聚焦视觉：自动选中并清楚展示本次开始至本次结束的区间，关联下面的过程记录，提供直接定位起点和终点的方式，不要求用户手动拖选或翻找。

- fork 继承的父级历史仍可查看，但与本次子 Agent 新执行的记录清楚区分；不能把继承历史算成本次执行。
- 本次输入、模型请求、工具调用、输出及结束状态均处于可检查的执行范围。
- 运行中区间延伸至当前最新记录，并明确标为运行中；结束后使用真实结束边界。
- 同一子会话后续再次被唤起时，从不同发起点进入，应分别聚焦各自对应的执行区间，不能只打开同一个 Session 的全部历史。
- 完成、失败、取消等按真实事实呈现；数据不足时明确边界未知，不猜测结束点。

### 3. 保留父级来源和返回位置

子轨迹中显示来自哪个父执行、哪次发起，可一键返回该发起点；返回时恢复父轨迹原有的滚动、缩放和选择状态。嵌套子 Agent 同样遵循逐级进入与返回的关系。

顶部执行选择器保留为辅助入口，不用平铺名称列表替代以上路径。

## 验收场景

- [ ] 主 Agent 主动调用普通子 Agent：从发起记录进入正确子执行，直接看到本次起止与完整过程。
- [ ] 主 Agent 主动 fork：继承历史可查看，但默认聚焦本次新执行部分，起点清晰。
- [ ] 后台记忆整理／技能复盘：主轨迹存在对应发起入口，能辨认用途，不依赖顶部 UUID 列表寻找。
- [ ] 多个并行子执行及嵌套子执行：跳转对象和父级来源准确，不串线。
- [ ] 同一子会话多次唤起：每个发起入口定位到对应那一次执行区间。
- [ ] 运行中、正常完成、失败和取消：区间边界与状态来自真实记录；启动工具返回不会提前截断区间。
- [ ] 返回父轨迹恢复原发起位置、缩放和选择；刷新后仍可从持久记录重建关系与边界。
- [ ] 桌面与窄屏均可完成进入、检查和返回；沿用既有 Work 只读权限，浏览不启动、重跑或控制任务。

## 范围边界

本项完善轨迹导航与执行范围表达，不调整 subagent 调度、fork 上下文继承语义、后台复盘触发频率，也不清理或删除现有执行历史。
