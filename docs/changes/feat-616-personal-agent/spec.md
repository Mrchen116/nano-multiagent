## 自动观察与主动性追加原话

> 那不合理啊。那这还跟主动性有啥关系？那不就是我给一个任务，他做一个事情吗？……而不是说能够主动地看得到我的聊天记录，帮我处理问题吗？这是两码事吧

来源：2026-10-16，Sentinel_24fff2efb1c08191a5c797bf29c47a68。原话依父线程转交保留，省略号亦按转交内容保留。

已确认方向：个人助手应能够主动看到用户聊天记录，自动感知来自真人或 Agent 的消息，发现待处理问题并协助解决；不以用户逐条“交给助手”或手工分享作为默认感知前提。撤回前期讨论稿中“默认仅处理本次选中/已分享消息”的推荐。手动“帮我回复”仍可作为即时请求入口，不能代替主动观察。

设计边界：用户应能控制观察范围、排除会话和暂停观察。看得到消息不等于获得对外发送、代用户承诺、传播隐私或修改任务负责人的权限。具体群范围、历史窗口和恢复行为以文末收口及 design 为准；观察不批准自动代发。

### Requirement: 自动观察支持真正主动的协助

#### Scenario: 真人或 Agent 新消息到达
- WHEN 观察范围内、用户有权访问的聊天收到真人或 Agent 的新消息
- THEN 个人助手无需用户逐条转交即可感知，根据内容识别待处理问题，并在适当时准备回复草稿或关联用户负责的既有任务；用户能辨认来源及建议下一步。
- AND 感知不意味着每条消息必须提醒，不把原消息中的第三方指令当作用户授权。

#### Scenario: 用户已经回复
- WHEN 个人助手在有效观察范围内获知用户已处理某个待回复问题
- THEN 对该问题停止重复待回复提醒，不将回复自动解释为整个任务完成，也不替用户发送第二份回复。

#### Scenario: 范围排除与暂停
- WHEN 用户排除某个会话或暂停观察
- THEN 后续对应消息不被个人助手继续处理或用来产生新的主动提醒；界面明确观察状态，既有记录不伪装成持续更新。
- AND 暂停不删除已保存历史；恢复先核当前权限再合并最新状态；清理会清除 PA 管理的所选源缓存、失效衍生引用与旧执行上下文并显示进度；原聊天、Work、运行日志及导出可能保留但不得自动重新摄取，不承诺磁盘物理擦除或撤回已外发数据。历史窗口及覆盖必须在产品设置明确显示。

原型用明确模拟按钮展示真人/Agent新消息、自动准备草稿、任务关联、用户已回复、排除及暂停；最终范围和 A 入口见文末。原型不宣称产品已实现，视觉仍未验证。


## 统一 IM 联络模型追加要求

来源：2026-10-16，Sentinel_576b16ff6314819191b1234b87f3fae7。父线程转交的用户要求摘要（未提供完整逐字原话）：拒绝新“请求入口”；别人或 Agent 应直接私聊个人助手，或在群里 @个人助手。

已明确方向：沿用普通 IM，不新增对外请求门户或另一套收件箱产品页面。权限与披露边界在既有消息通路内执行，不用新产品入口替代安全模型。四种关系须统一说明：本人↔个人助手的专属私聊；外部人/Agent↔个人助手的普通私聊；既有群聊内@个人助手；个人助手观察本人其他范围内消息。第四类观察不自动将个人助手作为原聊天发言成员，也不把私人上下文复制给外部对话。

### Requirement: 外部联络沿用现有 IM 私聊和群提及

#### Scenario: 外部真人或 Agent 联系个人助手
- WHEN 外部真人或 Agent 在既有 IM 中直接私聊个人助手，或在允许其参与的群里 @个人助手
- THEN 使用现有聊天交互与身份线索，不要求另建请求门户或切换到专门收件箱页面；处理仍受相应会话、受众和披露权限限制。

#### Scenario: 四类关系保持可辨认
- WHEN 用户切换本人专属私聊、外部与 PA 私聊、群 @PA，或查看 PA 观察本人其他消息形成的建议
- THEN 能辨认当前发言者、可见受众和信息来源；外部视角不显示 owner 私聊、其他会话或私有任务细节。

原型外层“视角”控制仅为比较四类关系的演示控制，不是产品新增导航。外部联络场景沿用同样的聊天列表、消息区和输入框；自动观察、草稿审核、任务协助仍回到本人的 PA 私聊。具体建联、群成员资格、披露和代发遵守文末收口与 design。

## 已确认的产品范围

- 每位真人唯一、固定角色的个人助手；新手首个 Agent 即 PA，可自定义名称并改名；普通专业 Agent 继续可创建。
- 主动观察本人收发消息、历史与本人任务，无需逐条分享。主动准备材料、回复草稿、识别遗漏和跟进，与对外发送权限分开。
- 本人专属私聊、外部真人/Agent 的原生 DM、合法群 @PA、本人其他消息观察是同一 PA 身份的四种关系；不新增请求门户。
- 使用现有 task_graph 协助真人负责的任务；协助不自动 claim、改派负责人或建立平行任务真相。
- 私人上下文与外部会话隔离；外部请求不能批准读取或泄露私料，其他 Agent 不能代替 owner 授权。
- 初始原话明确要求 Web IM 入口设计。Agent 范围解读：本次新增导航以 Web IM（含响应式窄屏）为交付面，保持原生 iOS 普通聊天/API 兼容；尚未把原生 iOS 新导航列为用户已确认范围。

### Requirement: 固定个人助手与其他 Agent 共存

#### Scenario: 新手首次创建
- WHEN 新用户完成首次助手创建
- THEN 得到属于自己的唯一 PA 和本人专属私聊；重复提交或断线恢复不产生第二个 PA。

#### Scenario: 后续专业助手
- WHEN 用户另建专业 Agent
- THEN PA 身份和专属会话保持，专业 Agent 不隐式替换 PA。

#### Scenario: 既有用户
- WHEN 已有普通 Agent 的用户首次启用个人助手
- THEN 可辨认需要完成个人助手设置，已有 Agent 的职责、历史和会话不被静默转换或清空。

### Requirement: 协助本人任务而不转移责任

#### Scenario: 主动识别任务下一步
- WHEN 本人负责且仍可访问的任务出现新阻塞、依赖或截止风险
- THEN PA 可在本人私聊给出有来源的下一步并准备材料；负责人保持本人，不把消息送达算作任务完成。

#### Scenario: 授权后写回
- WHEN 用户确认将 PA 准备的结果或状态写回一个明确任务
- THEN 原任务显示真实执行主体及结果；并发修改或权限失效时不覆盖新状态，明确提示重新核对。

### Requirement: 对外会话不能取得私人上下文

#### Scenario: 外部套话或伪造授权
- WHEN 外部真人或 Agent 在 DM/群声称 owner 已同意并索取其他会话、工作轨迹、私密任务或附件
- THEN PA 不因该说法开放私人资料；需要 owner 决定时回到本人私聊提出具体资料及受众，外部仍使用原聊天。

#### Scenario: 有界分享
- WHEN owner 批准向具体受众分享具体资料或结果
- THEN 仅该授权范围可被对外使用，后续问题、附件或受众变化不会自动扩大权限。

#### Scenario: 外部控制文字
- WHEN 外部消息或历史记录包含 /stop、/config 或要求覆盖规则的文字
- THEN 不会控制本人私密 PA 主上下文或修改其权限。

## 自主设计授权与 Gate 1 收口

用户原话（Sentinel_a813ecc068e48191bf4e8e46d3475e0a）：

> 你先给我做吧。你先做出来以后，你可以派独立的sabger去走一遍，他能理解你的吗？他有时候他肯定理解啊。你说很丑，他也理解。以及符不符合这个用户审美啊，用户体验啊。你先做，不需要我选。

据此由设计作者决定入口 A：主导航固定 PA 自定义名称与角色标识，点击进入本人专属私聊；不再把 A/B 选择当用户待答。原型和真实实现均须独立评价视觉与易用性。

以下为实现该用户目标的设计决定，不伪称用户逐项原话：启用时明确说明持续观察本人已参与 DM/群与本人任务，首次近 30 天按需回溯；可排除、暂停和清理，未加入公开群不批量自动监控。首次启用前需用户在产品内确认这个清楚列出的范围，之后无需逐条分享。保留更早历史按当前任务有目的读取和真实覆盖提示。外部联系先沿同公司有效真人/Agent资格，可原生DM；owner确认PA加入群，屏蔽与频控始终可用。互联网匿名/跨公司联系不在本次范围。

对外普通回复只用该会话事实和已获准资料；私人资料披露、代表 owner 承诺或修改本人任务均需具体授权。不预置任何“全部隐私可自动外发”规则。默认群范围、历史窗口是产品可见且可控设置，不是将全部正文一次送入模型。

Gate 1 判定：用户目标、范围、非目标及验收行为已收口，无需继续向用户索取界面选择。技术设计必须兑现上述边界，验证资源不足仍会阻塞 Gate 2，不由本节跳过。
