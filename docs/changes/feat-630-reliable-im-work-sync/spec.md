## 澄清记录

- 用户要求从可供大量用户日常使用的 Web IM 考虑可靠性，而非仅恢复本次连接。
- 用户明确否定把多阶段内部状态铺到聊天界面。沿用正常聊天、必要失败提示及现有主动查看 Work 的体验；复杂度由系统承担。
- 本轮建立 feat 并完成设计；不实施产品代码，不部署或重启生产服务。

## Agent 对需求的解读

让消息收发、必要控制和工作记录同步具有独立的恢复边界。历史记录积压、同步慢或确认丢失时，用户仍能正常交办和收到回复；恢复后过程记录完整可查。保持授权、来源、发送前复核和执行去重，不以丢数据或放宽权限换取可用。

本轮解决当前单中心、多节点的可靠性与有界资源问题，并为后续扩容保留清楚边界；不把“大规模”解读为同时迁移中心数据库、引入消息中间件或交付多地域部署。

## 现状与问题依据

2026-10-21 的会话取证：18:57“如何了”和 19:02 的 @P 已存入 IM，目标节点为 macbook-air，六项目标投递没有接收回执；节点 Inbox 没有这两条消息。节点反复注册后发生业务请求十秒超时。

本机待同步的 100 个工作事件组成约 1,564,055 字节请求；本地确认位置 6643，中心为 6743。相同大小的无业务探针经公网 35 秒无回包，Mini 源站直连约 16 毫秒，Mini 经公网也超时。它们支持“公网大包请求不能在当前期限内完成”的结论，不足以归因到某个 Tunnel、运营商或 Cloudflare 内部环节。

源码基线 `11f599938d67f21398570009f1c7e9e0088b81a1`：`GlobalAgent.main/query/reconcile` 等待整个共享 Work 队列；新输入持久接收、聊天查询和回复准备因此受其影响。传输层业务确认串行，一项超时会拆连接，繁忙时还推迟心跳。详细责任与接口落在 design，以上只作为本次可靠性需求的来源。

## 用户场景

- U1 日常交办：Agent 昨天留下大量过程记录尚未同步，用户今天继续问进度；消息正常交给 Agent，回复回到原聊天。
- U2 暂时离线：节点不可达时用户发送一次消息；消息保留，节点恢复后自动处理，用户不必辨认内部状态或重复发送。
- U3 确认丢失与重启：网络中断或进程重启发生在消息已保存之后；同一消息不重复出现，不重复唤醒造成重复执行或重复发布。
- U4 忙碌控制：用户在 Agent 正在工作且记录补传缓慢时，按现有规则停止它、响应授权或补充新指令；旧记录不会挡住这些操作。
- U5 恢复回看：用户稍后打开现有 Work，可回看原有完整工作明细和真实归属，重复补传不会复制记录。
- U6 共享资源：同一中心有多个用户、节点及 Agent，其中一个持续补历史，其他人的正常沟通仍可继续。
- U7 保持安全：聊天成员关系、设备绑定或授权已经撤销时，恢复和重试不能让旧任务获得新的权限；新增纠正到达后仍须复核再发送。
- U8 简洁聊天：正常消息收发和暂时自动恢复不向聊天插入内部诊断说明，不要求用户管理上传与确认。

## 验收标准

### Requirement: 历史工作记录同步不阻塞当前沟通

#### Scenario: 有大量历史记录待同步时继续交办
- **GIVEN** 同一 Agent 有大量历史工作记录尚未同步，消息通路可用
- **WHEN** 用户在原聊天发出新的交办或进度询问
- **THEN** Agent 可以接收、处理并向原聊天回复，不必等历史过程全部上传。

#### Scenario: 工作记录同步暂时不可用时仍能查询并回复
- **GIVEN** 当前聊天和必要权限服务可用，工作记录同步服务持续失败
- **WHEN** 用户要求 Agent 查看有权访问的聊天并回复结果
- **THEN** 这次查询和回复不因无关历史记录未上传而失败。

### Requirement: 暂时不可达的消息自动恢复投递

#### Scenario: 节点离线期间发送消息
- **WHEN** 用户向暂时离线的 Agent 发送消息，中心已成功保存
- **THEN** 聊天保留该消息，不误报为未发送并要求用户重发
- **AND** 节点恢复后自动接收，用户无需再次发送。

#### Scenario: Agent 运行时尚未恢复
- **GIVEN** 节点能接收消息但 Agent 执行进程暂时不可用
- **WHEN** 用户发送交办，随后执行进程恢复
- **THEN** 交办保留并继续处理，不因等待执行进程而丢失。

### Requirement: 确认丢失与进程重启不造成重复处理或回复

#### Scenario: 已接收消息的确认丢失
- **WHEN** 同一条已保存的消息因确认丢失被重新投递
- **THEN** 用户只看到原消息及其应有回复，不因重投产生第二次相同交办或重复发布。

#### Scenario: 持久接收后节点重启
- **WHEN** 节点已接收用户消息，但在处理或返回确认前重启
- **THEN** 恢复后继续原交办；已完成的执行或外发不因重启被盲目再做一次。

### Requirement: 必要控制不等待旧工作记录

#### Scenario: 补传期间停止或回应授权
- **GIVEN** Agent 正在执行，历史记录补传缓慢，实时消息通路可用
- **WHEN** 用户按现有规则发送停止命令或提交权限决定
- **THEN** 对实际执行生效，不等待旧记录全部同步；权限决定确认迟到时沿用现有真实确认语义。

### Requirement: 工作过程在恢复后完整且不重复

#### Scenario: 大体积工具结果恢复回看
- **WHEN** 一次工具调用生成大体积结果，经历同步失败后恢复，用户重开现有 Work
- **THEN** 可以回看原有完整参数、结果、状态和父子归属，不因拆分、重传或刷新丢正文、乱归属或复制条目。

### Requirement: 一个节点的历史积压不拖住其他人的沟通

#### Scenario: 多用户和多 Agent 同时交办
- **GIVEN** 某节点持续上传大量历史记录
- **WHEN** 其他用户、节点及同节点的其他 Agent 收到正常交办
- **THEN** 仍能按原触发规则接收和回复，不等待该节点清空历史记录。

### Requirement: 恢复与重试保持原授权和纠正语义

#### Scenario: 排队期间失去访问资格
- **WHEN** 消息或记录尚在恢复队列中，相关设备或聊天访问资格已撤销
- **THEN** 重试不重新赋予访问或外发权限，不把撤销后的新内容交给失去资格的 Agent。

#### Scenario: 回复前收到新纠正
- **WHEN** Agent 准备回复，原聊天出现按其配置应处理的新纠正
- **THEN** 继续执行原有读取及发送前复核，不因同步隔离发布过时草稿。

### Requirement: 聊天保持简洁，不暴露同步实现

#### Scenario: 正常使用与自动恢复
- **WHEN** 用户正常聊天，或系统在后台自动重连、补传记录
- **THEN** 聊天不增加内部阶段标签、同步进度条或诊断消息，用户不需要管理节点、队列、确认与游标
- **AND** 原有必要失败提示、授权交互和主动打开 Work 的入口保持。

## 范围与非目标

- 在范围：内置 Web IM 到 global Agent/PA 的可靠接收、恢复与显式回复；共享传输上受影响的单 Thread 消息与必要控制回归；工作记录可靠补传；有界资源、公平调度与后台诊断；现有 Web 聊天体验保持。
- 非目标：更换 DSH、另建 Agent Loop、修改审批准入或群触发规则；新增用户可见内部状态面板；修改 Web/iOS/飞书布局；修复特定公网出口；中心数据库迁移、Kafka 等组件选型、多地域或具体人数容量承诺；自动合并、部署及生产数据迁移执行。
