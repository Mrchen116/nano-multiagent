## 已确认方向

本节与各题结论已按 Q15 最新决定统一：waiting 与 doing 并列，页面分栏不等于任务状态，两者都归入“进行中”栏；等待前的定时跟进纳入本期。早先原话与被替代的提案保留为讨论历史，不能覆盖最新结论。

- 本 feat 升级 Nano 现有 Task 体系，作为默认的目标与任务体系；Task 持续推进不依赖 DSH Goal。
- 所有现有及新建 Agent 默认关闭 DSH Goal 管理工具，仅在用户于配置页主动开启后暴露；这项可选开关不改变 Task 的独立执行责任，不做 Task/Goal 套壳或状态同步。
- 持续推进责任以进入 `doing` 为依据，不限于“领取”这一入口。存在 doing 时继续；没有 doing 且所有 waiting 均有有效后续安排时，Task 不要求立即续跑。waiting 的安排失效时须触发处理，不能静默失联。不能因一轮回复结束而遗失责任。
- Agent 自主安排多项进行中任务的推进顺序；续跑提示提供全部本人 `doing` 和 `waiting` 任务，分别标明待推进与等待中，不能只提供单一任务。助手按当前 Agent 负责的任务理解该列表范围，具体见 Q4。
- 确实没有可执行的下一步时，允许说明阻塞原因和恢复条件后等待；第一期即允许 Agent 根据相关用户答复、协作 Agent 交付或实际送达的外部结果自主判断恢复，不要求额外恢复指令。
- 在现有六种状态中新增 `waiting`，与 `doing` 并列；Agent 与持久化记录使用同一套状态。Tasks 页面将两者都放在“进行中”栏，分别标记推进中、等待中。等待条件满足后由 Agent 将 waiting 改回 doing 并继续；不维护另一套页面专用任务状态。
- 等待不设最少轮数。Agent 完成必要提问、交办或启动动作并核实实际状态后，若该任务没有可执行的下一步，可在建立有效 Schedule 后，将状态改为 waiting，并一并登记等待原因、安排关联及必要依据；其他 doing 任务继续。普通失败或困难本身不构成阻塞，第一期不增加阻塞审核模型。
- 用户主动暂缓后，须等用户表达恢复意图才能继续；普通新消息或外部条件变化不能自行解除暂缓，恢复不要求固定命令。
- 完成与验收按任务约定处理：达到要求并验证后，可直接完成或交付后进入待确认；两者均结束该项续跑，其他 doing 任务继续。需要返工时记录原因并恢复 doing，不新增必经真人审批。
- 当前 Agent 对直接分配给自己的任务承担推进责任。改派保留任务状态，责任转给新负责人；doing 由新负责人接续，waiting 保留并由新负责人核对阻塞条件及安排有效性，用户暂缓继续保留。能查看他人任务不等于承担该任务。
- 父负责人委派后继续对整体结果负责：有可执行工作时推进，只能等子结果时等待，结果到达后判断整合、验证或返工。保留父子逐层通知，子任务完成不自动完成父任务，第一期不增加按依赖图自动开工的调度器。
- `/stop` 停止当前执行并暂缓对应停止范围内的 doing 和 waiting 任务，避免被自动续跑重新拉起；范围外任务不受影响，恢复遵循 Q6。Global 与单 Thread 沿用各自停止范围，不将单聊天停止扩大为其他会话任务暂停。
- 重启或断连导致执行中断后，复用普通续跑判断：需推进的 doing 触发全部本人 doing 和 waiting 清单 prompt，waiting 状态及仍有效的等待安排保留，安排失效则触发处理；不因重启重复执行或跳过等待。正常上下文换窗与 Task 体系正交，不改变任务状态、不触发额外续跑。
- 第一期不设 Task 专属轮数上限，不另建 Task token 或费用预算体系；仍有有效下一步就继续，真实阻塞按 Q9 等待，用户停止及既有运行限制保持有效。运行故障如实展示，恢复后按 Q13 接续，不伪装成完成或用户暂缓。
- 续跑 prompt 参考 DSH 的原有提示词，将单个 Goal 改为当前 Agent 负责的全部 doing 和 waiting 任务，按状态区分待推进与等待中；任务完整正文和讨论按需读取，不每轮重复注入全部历史。具体适配遵守已确认的 Task 状态和无轮数上限规则，见 Q15。
- 等待前必须安排定时唤醒纳入本期，Agent 决定检查时间与下一次行动；没有安排时应提醒并继续，不能直接安静结束。关联及轻量有效性检查方向已在 Q15 确认，具体工具参数留给设计。
- 按没有旧 Task／Goal 数据处理，不做存量核对、迁移或历史 Goal 转换。具体工具参数与接口在设计阶段斟酌，不冻结讨论示例。

## 澄清记录

### Q1：什么动作表示任务开始持续执行？

问题：Task 在什么动作之后，才应该驱动 Agent 持续执行？

候选选项：

1. Agent 领取任务后持续执行。
2. 明确点击或要求“开始执行”后才持续执行。
3. 任务分配给 Agent 后自动开始执行。

助手当时推荐选项 1：复用现有领取语义，并保留“分配不等于开工”。用户随后以任务状态明确了更广的触发规则，见下方答复。

用户追问：

> 领取是进入待做状态，还是进行中状态？

现状核实：当前领取会设置负责人为领取者，并进入“进行中”；分配只改变负责人，不改变状态。依据：[Task 服务领取操作](../../../apps/im-server/src/task-graphs.ts)。当前领取不驱动自动持续执行，因此“进行中记录”与“实际持续工作”仍需在本 feat 对齐。此追问尚未构成对选项的选择。

用户最终答复：

> 明白，凡是进入了doing状态，都应该像DSH原本的goal那样保障推进，agent不能随便停下来了

结论：进入 `doing` 即纳入持续推进保障，不只覆盖领取动作；其他合法入口进入该状态也适用。Agent 一轮回复结束不等于任务完成，也不能作为放弃后续推进的理由。真实阻塞、用户暂停、执行成本及退出条件见后续各题结论；这项决定不等于无条件无限重试。

助手推荐允许：有可执行工作时继续推进；确实受阻时向用户说明，等待条件满足后接续，避免无效空转。当时尚未确定具体表达；最新结论见 Q5、Q15，恢复原则见 Q3。

用户答复：

> 类似 DSH 它允许吧？那我们也允许

结论：

允许 Agent 在确实没有可执行的下一步时，说明阻塞原因和恢复条件后进入等待；不能仅因困难、不确定或一轮回复结束就停止推进。等待转为 waiting，具体门禁按 Q9、Q15 的最新决定；恢复原则见 Q3。

参考核实：本地 DSH `packages/goal/tool-goal/src/index.ts` 要求 `blocked_reason`，自动 Goal 轮次调用还受默认 3 轮的门槛约束；提示词要求同一阻塞条件持续存在。`packages/goal/goal/src/index.ts` 将 Goal 转为 `blocked` 并解除自动续跑。允许阻塞不等于已经提供外部条件满足后的自动恢复；DSH 的具体轮次门槛也不因本次答复自动成为 Nano 的要求。

### Q3：等待条件满足后，是否自动恢复推进？

问题：因用户答复、子任务结果或外部结果而等待的任务，在所需条件满足后，是否应自动继续，无需用户再说一次“继续”？

助手推荐自动继续：任务已经开工，等待条件解除后继续履行推进承诺，减少用户重复催促。本题仅讨论因阻塞而等待，用户主动暂停的恢复规则另行对齐。

用户答复：

> 要用户明确/goal resume是DSH比较人参与的情况吧，我们第一期，也希望用户答复了他之后，他直接按自己的理解恢复。毕竟开启task，委派task，也不需要用户直接操作，对应的恢复也自然不用

结论：

第一期即支持 Agent 根据用户答复和任务上下文自主判断并恢复推进，不要求用户额外说“继续”、执行恢复命令或直接操作 Task。恢复与 Agent 自主开启、委派 Task 的原则一致，不沿用 DSH Goal 对恢复操作的直接真人请求限制。助手解读：收到答复后应判断是否已有可执行的下一步；答复仍不足以解除阻塞时，可以继续说明缺失条件并等待，不能将任意新消息一律当作解除阻塞。本结论不覆盖用户主动暂停后的恢复。按 Q15 最新决定，等待使用 waiting，条件满足后转回 doing，定时检查已纳入本期。

### Q4：同一 Agent 的多项进行中任务如何推进？

问题：同一 Agent 有多项 `doing` 任务时，是否允许它自主安排推进顺序，并在某项任务阻塞时转去推进其他可执行任务？

助手推荐允许：尊重用户明确的优先级，其余由 Agent 结合依赖、阻塞和已有进展选择下一项工作；某个 Task 等待不等于整个 Agent 都可以停止推进。只要仍有可执行的进行中任务，就应继续工作。这里讨论多项任务的持续责任与选择，不要求同时并发执行，也不要求频繁切换。

用户答复：

> 我理解允许它自由推进吧，但是只要有一项是doing状态，就不应该停下来。比如agent定下来了 DSH 的goal会给agent一段什么样的prompt？是把任务内容发给agent吗，如果是，我们就要把所有doing的任务列表发给agent

参考核实：DSH `packages/goal/goal-round-driver/src/prompt.ts` 的 `renderGoalRoundPrompt` 将目标原文和当前轮次写入 `<goal_round>`，要求在同一会话继续推进、检查当前工作区及工具结果和持久状态、验证整体目标完成后标记完成，未完成则保持 active。它提供一个 Goal 的目标，不是多任务列表。

### Q6：用户主动暂缓的任务如何恢复？

问题：用户主动要求“先停一下”而暂缓的任务，是否应等待用户表达恢复意图后再继续，而不能仅因收到普通答复或外部条件变化就自行恢复？

用户答复：

结论：

确认用户主动暂缓后，应等待用户表达恢复意图，不能仅凭普通新消息或外部条件变化自行恢复；自然语言表达即可，不要求固定命令或直接操作 Task。阻塞等待仍按 Q3、Q5 由 Agent 自主判断恢复。

### Q7：完成与待确认如何结束当前任务的持续推进？

现状依据：IM Task 契约引导做完先提交待确认，但允许直接完成，不设置必经真人审批；当前尚无与这些状态关联的持续执行机制。

## 用户场景

1. 用户通过聊天把工作交给 Agent，或 Agent 合法领取／开始已有 Task。任务进入 doing 后，用户无需反复发送“继续”；Agent 会持续推进当前由自己负责的全部任务。
2. Agent 需要用户确认预算。它先发出问题，再安排下一次检查，将 Task 改为 waiting 并登记等待信息。任务在页面上仍属于“进行中”，用户在 Tasks 页面能看见等待原因和下次检查时间。Agent 可继续其他工作；没有 doing 且全部 waiting 均有有效安排时才因等待空闲。
3. 用户在检查时间前回复预算，或协作 Agent 提前交付子任务。负责 Agent 读取最新消息，将对应 waiting 转回 doing、解除等待信息并继续；用户不必重新操作任务。若到期仍无结果，Agent 判断可做工作或调整下一次安排，不机械重复催促。
4. 父负责人将调研委派给另一个 Agent，自己先做可独立推进的部分。子任务交付后，父负责人整合、验证或要求返工；子任务完成不自动完成整体目标。
5. 用户要求暂缓某个任务，或通过 /stop 停止对应执行范围。受影响的任务停止自动推进，并在用户表达恢复意图前保持暂缓；其他范围的工作不受影响。
6. 节点重启或断连造成执行中断，运行恢复后重新遵循同一套推进／等待规则。waiting 及有效安排得到保留，失效安排触发处理；doing 不会因为一轮意外结束而被遗忘。正常换窗不改变 Task 生命周期。
7. 所有 Agent 默认使用 Task 体系而不暴露 DSH Goal 管理工具。用户若确有需要，可以在配置页为指定 Agent 开启 Goal；两套任务记录不自动相互转换。

## 验收标准

### Requirement: 进入 doing 后承担持续推进责任（Q1、Q4、Q10）

#### Scenario: 已开工任务不依赖用户反复催促
- **WHEN** 当前 Agent 负责的任务通过任意合法入口进入 doing，且仍有可执行工作
- **THEN** Agent 持续推进；一轮回复结束不使任务停滞，不要求用户再说“继续”。

#### Scenario: 多项任务由负责人自主安排
- **WHEN** 同一 Agent 直接负责多项 doing 和 waiting，其中包含不同任务树或不同层级的节点
- **THEN** Agent 能获知全部本人 doing 和 waiting，分别辨认待推进与等待中并自主选择下一步；可读但属于他人的任务不被当成自己的执行责任，一项等待不使其他可推进工作停止。

#### Scenario: 分配待办与开始执行保持区别
- **WHEN** 一个 todo 任务仅被分配或改派给 Agent
- **THEN** 它仍是待办；接手并进入 doing 后才承担持续推进责任，普通分配不伪装成已经执行。

### Requirement: waiting 与 doing 并列且具备有效后续安排（Q2、Q5、Q9、Q15）

#### Scenario: 等待预算答复
- **GIVEN** 必要询问已实际发送，该任务当前没有可执行的下一步
- **WHEN** Agent 说明原因并登记有效的定时检查安排
- **THEN** Task 转为 waiting，并保存等待原因与有效安排关联；页面仍归入“进行中”栏，不要求凑满固定轮数才能等待。

#### Scenario: 全部任务等待与部分任务可推进
- **WHEN** 当前 Agent 准备结束执行
- **THEN** 存在本人 doing 时继续推进；没有 doing 且所有本人 waiting 均有有效后续安排时，Task 不要求立即续跑；waiting 的安排失效时须触发处理。

#### Scenario: 无有效安排时拒绝转入 waiting
- **WHEN** Agent 请求将 Task 改为 waiting，但没有关联真实、有效且能唤醒适当执行主体的 Schedule
- **THEN** 转换被拒绝，任务保留原状态；Agent 获得具体问题并继续推进或补安排，用户不会看到虚假的等待或下次检查承诺。

#### Scenario: waiting 的安排后来失效
- **WHEN** Task 已为 waiting，但关联安排被删除、已消费后未建立下一次安排，或已不能唤醒适当执行主体
- **THEN** 系统触发处理并向 Agent 指出具体问题，由 Agent 补安排或转回 doing 推进；不能仅因状态为 waiting 就永久跳过该任务，也不能继续显示失效的下次检查承诺。

#### Scenario: 询问未送达
- **WHEN** 提问发送失败或投递结果尚不明确
- **THEN** 如实表达失败或未知，不把它记为用户没有回复；仍有可行的允许动作时继续，无法执行时明确实际障碍。

### Requirement: 消息与定时检查共同驱动再次行动（Q3、Q8、Q15）

#### Scenario: 相关答复提前到达
- **WHEN** waiting 收到足以继续的用户答复、协作交付或外部结果
- **THEN** Agent 读取来源与内容后自主继续，不要求用户额外发恢复命令，不必等定时检查到期；Task 从 waiting 转回 doing，等待信息解除。

#### Scenario: 定时到期但条件仍未满足
- **WHEN** 关联的检查时间到达，所需答复或结果仍未出现
- **THEN** Agent 重新判断下一步，可以推进则转回 doing；仍需等待则保持 waiting 并更新有效的下次安排；不默认每次都催问，也不把到期当作已收到答复或获得授权。

#### Scenario: 过期提醒不能重新开启已停止的工作
- **WHEN** Task 已完成、关闭、待确认或由用户暂缓后，旧提醒到达
- **THEN** Agent 核对最新任务情况，不因旧提醒把它重新开工；待确认返工和用户恢复仍遵守各自规则。

### Requirement: Tasks 页面区分进展、等待与实际执行（Q5、Q13、Q15）

#### Scenario: 进行中任务正在等待
- **WHEN** 用户查看 Tasks 页面上的 doing 与 waiting 任务
- **THEN** doing 和 waiting 都列在“进行中”栏，分别显示推进中、等待中；waiting 显示等待原因和有效安排的下次检查时间。waiting 转回 doing 后仍留在该栏，等待说明随之解除；页面分组不覆盖实际状态。

#### Scenario: 一个任务等待但 Agent 正在做别的工作
- **WHEN** Agent 等待任务 A 的结果，同时推进任务 B
- **THEN** A 的等待说明不会把整个 Agent 错标成未工作；任务进展与执行情况可区分。

#### Scenario: 节点离线
- **WHEN** 节点离线而 Task 仍为 doing
- **THEN** 用户能辨认执行不可用，不因 doing 状态就显示 Agent 正在实际执行。

### Requirement: 用户暂缓与停止命令有效（Q6、Q12）

#### Scenario: 暂缓指定任务
- **WHEN** 用户主动要求暂缓某项任务
- **THEN** 该任务停止后续推进，并等待用户表达恢复意图；普通消息或定时到期不能自行解除暂缓，其他任务仍按各自情况处理。

#### Scenario: /stop 暂缓对应范围
- **WHEN** 用户发送 /stop 并实际触达对应执行范围
- **THEN** 当前执行停止，该范围内本人负责的 doing 和 waiting 被暂缓，自动续跑不会立即拉起；Global 与单 Thread 沿用各自范围，不扩散到未触达的工作。
- **AND** 已发出的工具调用可能完成，已发生的外部效果不被描述为已撤销。

#### Scenario: 自然语言恢复
- **WHEN** 用户表达明确恢复意图
- **THEN** Agent 可以恢复对应任务，无需固定命令或直接操作 Task；恢复后继续遵守推进及有效等待规则。

### Requirement: 完成、待确认和返工保持真实（Q7）

#### Scenario: 按任务约定交付
- **WHEN** Agent 达成要求并验证结果
- **THEN** 不需要额外验收时可直接完成，需要验收时提交成果进入待确认；两者均结束该项续跑，其他可推进任务继续，不新增所有任务必经的真人审批。

#### Scenario: 返工继续原任务
- **WHEN** 已完成或待确认的工作收到需要返工的反馈
- **THEN** Agent 记录返工原因并恢复 doing，继续原任务；不能仅为结束续跑而宣称完成。

### Requirement: 改派转移责任并保留状态（Q10）

#### Scenario: 改派进行中的任务
- **WHEN** doing 从 Agent A 改派给有资格的 Agent B
- **THEN** A 停止该项后续工作，B 核对已有成果并接续，无需用户再次说“开始”；不得两边同时把责任交给对方。

#### Scenario: 改派等待或暂缓的任务
- **WHEN** waiting 或用户暂缓任务被改派
- **THEN** waiting 保留状态，新负责人读取并处理已有等待信息与后续安排，条件满足则转回 doing；用户暂缓仍保留，不因改派就解除。旧负责人留下的安排不能冒充新负责人已经接续工作。

### Requirement: 父负责人持续承担整体交付（Q11）

#### Scenario: 委派后继续或等待
- **WHEN** 父负责人委派子任务
- **THEN** 有独立工作时继续推进，确实只能等子结果时登记有效安排并转为 waiting；收到结果后判断整合、验证或返工，不因子任务全部完成而自动完成父任务。

#### Scenario: 父状态变化逐层通知
- **WHEN** 父任务普通暂缓或关闭
- **THEN** 沿用现有直属下一层通知，由接收 Agent 处理自己的工作；不自动整树改状态。明确要求整个子树操作时才按指定范围处理。

#### Scenario: 前置完成不机械启动所有后继
- **WHEN** 前置任务完成
- **THEN** 由负责人结合当前事实判断并启动后续工作，不因依赖图关系自动强制改变所有后继状态。

### Requirement: 中断接续与换窗保持正确边界（Q13）

#### Scenario: 重启或断连后恢复
- **WHEN** 重启或断连曾中断执行，随后运行恢复
- **THEN** 重新核对当前任务与安排，doing 自动接续，waiting 及有效安排继续保留，失效安排触发处理；暂缓、待确认、完成或关闭任务不重新开工，不要求用户再次催促。
- **AND** 核对可能已完成的动作，避免因恢复重复交付；未中断的执行不因重新连上而重复启动。

#### Scenario: 正常上下文换窗
- **WHEN** Agent 在工作中正常换窗
- **THEN** Task 状态和后续安排不因换窗改变，不额外创建任务恢复流程或重复启动执行。

### Requirement: 不以 Task 专属轮数终止持续责任（Q14）

#### Scenario: 多轮仍有有效下一步
- **WHEN** Task 经历多轮续跑，仍有可执行工作且运行条件允许
- **THEN** 继续推进，不因累计自动轮数达到固定阈值而停止，不另设本期 Task 专属 token 或费用预算。

#### Scenario: 运行条件不可用
- **WHEN** 模型、网络、额度或调度能力使当前执行无法继续
- **THEN** 如实显示实际原因，保留未完成责任，不伪装为完成或用户暂缓；遵循既有运行限制，条件恢复后按统一规则接续。

### Requirement: DSH Goal 默认关闭但允许用户主动开启（Q16）

#### Scenario: 现有及新建 Agent 的默认配置
- **WHEN** 用户使用本功能的默认配置，或新建一个 Agent
- **THEN** 所有 Agent 默认不向模型暴露 DSH Goal 管理工具；Task 持续推进不依赖开启 Goal。

#### Scenario: 配置页主动开启或关闭
- **WHEN** 用户在配置页明确为指定 Agent 开启 DSH Goal
- **THEN** 该 Agent 可按原有能力与权限使用 Goal 管理工具，其他 Agent 的默认关闭状态不受影响；用户再次关闭后，不再暴露这些工具。
- **AND** 开启不将 Task 转为 Goal，不建立 Task/Goal 双写或状态同步。

## 范围与非目标

本期覆盖具有既有 Task 工具资格的 Agent，包含消息驱动的 Global／Personal 入口及已有 single_thread 执行范围；不改变会话访问与身份权限。交付 doing 持续推进、waiting 等待及未完成责任、全部本人 doing／waiting 续跑输入、有效定时跟进、Tasks 页面将两者归入“进行中”栏并区分展示、相关消息自主接续、父子协作、责任改派、/stop 暂缓及统一中断接续。DSH Goal 默认关闭并保留用户在配置页主动开启的入口。

本期不做旧 Task／Goal 数据处理、存量核对或迁移；也不新增完整依赖图自动调度、独立阻塞／成果审核模型、Task 专属预算体系、通用跨节点运行迁移、资源清理回执或第二套 Agent Loop。原第二期定时跟进已并入本期，不再作为排除项。实现仍遵守仓库 DSH 公开接口边界。

工具调用示例不是最终契约；字段、操作组合、轻量检查接入点和界面布局由设计确定。现有生产配置和服务未在本次对齐中改动。
