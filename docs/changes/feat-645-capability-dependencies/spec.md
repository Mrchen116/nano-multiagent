# feat-645: Feature 联动与能力依赖完整性

## 原始需求

来源：配置设计聊天所收到的原聊天交接，引用用户原话：

> Schedule create 工具它都没有，它就没有办法跟我的 Task 系统紧密结合。不单是 Task，其他系统也可能需要绑定工具或 Skill，这种是不是不应该让用户能随便关掉？假如是一个特性，至少开启这个特性的时候不能关掉依赖；假如是默认的一些基础能力，就不能关。

本聊天只对齐需求与设计，不实施代码，不修改生产配置，不恢复 Task/Goal 双写。不是所有默认勾选的工具都属于不可关闭的基础能力。

## 澄清记录

### 1. Feature 与工具的优先级

来源：原聊天同步的用户已确认决定，非本聊天逐字原话。

- 工具开关决定工具是否实际可用；Feature 不能成为额外的 AND 门槛。
- 打开 Feature，自动打开关联工具，前端同步显示开启。
- 关闭 Feature，默认顺带关闭关联工具，前端同步显示关闭。
- 随后手动打开工具，工具真正可用，Feature 保持关闭，不反向打开 Feature。
- 底层服务须支持有效工具选择，不能出现工具已勾选但因 Feature 关闭而未加载。

### 2. 开启中的 Feature 保护必需工具

用户原话：

> 弹出可以消失的那种弹框，要求它不允许呗。就你自己想一段文字嘛，就要求用户先关闭某Feature才能单独调整。

用户随后纠正：

> 不是可关闭的提示框，是那种淡入淡出的提示框，不需要用户手动关闭，它过，比如说1秒或者2秒就关闭。你这个体验，你作为UIUX专业的人，你可以设计。

助手提出以下交互后，用户确认「可以，就这样。继续讨论下一个需要确认的点。」：

- 尝试关闭必需工具时，保持开启，开关不跳动。
- 操作区域附近显示 Toast：「请先关闭『{Feature 名称}』，再调整此工具」。
- 淡入，展示约 2 秒后淡出，不需要关闭按钮，不遮挡操作、不抢焦点。
- 连续点击延长当前提示时间，不叠加多个提示。

### 3. 多 Feature 共享依赖

用户原话：

> 还用想吗？那肯定是要保留呀。工具旁边不用标注什么鬼啊？你会不会做用户交互设计的？当然不用标注啊。

已确认：关闭一个 Feature 时，仍被其他已开启 Feature 必需的工具保持开启；最后一个依赖它的 Feature 关闭时，按默认联动关闭。工具旁不增加依赖归属标注。

### 4. Skill 联动

助手提案：仅对 Feature 正常工作必需的 Skill 使用相同规则；开启时保证可发现、可加载，正文仍按需读取；开启期间不得单独禁用，尝试时使用同类 Toast；关闭 Feature 默认联动关闭，但其他已开启 Feature 仍依赖时保留；用户之后可以单独重新启用 Skill。

用户答复原话：

> Of course.

### 5. Task 的定位

用户原话：

> Task 保留开关，开启的时候保证完整能力就行。

已确认：Task 属于可关闭的 Feature，开启后完整支持任务推进、等待与后续复查。早先助手提出的“不依赖 Cron Feature、只补齐调度工具”候选已被第 9 项替代：Task 明确依赖 Cron Feature，开启 Task 时应联动开启 Cron，不要求用户另行手动补开。

### 6. 现有配置升级

针对「已有 Feature 开启，但必需工具或 Skill 被关闭」的配置，用户原话：

> 保留 Feature 开启，自动补齐依赖。不然升级完功能反而关了。你这个用Agent来做吧。不用写到代码里面去。你写一个prompt在你的Units目录下，然后到时候我部署的时候，要求部署的Agent去根据你这个prompt去执行。

已确认：保留开启的 Feature，由部署 Agent 在升级时补齐依赖，不在产品代码中增加历史配置迁移逻辑。执行提示词见 [deployment-prompt.md](deployment-prompt.md)。当前只保存提示词，不执行生产操作。

### 7. 关闭 Task 时暂停已有责任（已被第 8 项替代）

助手提案：关闭某个 Agent 的 Task 开关时，所有由它负责、处于 doing 或 waiting 的任务转为 paused；其他 Agent 的任务及已完成、待审核等状态不变。重新开启 Task 仅恢复能力，不自动恢复这些任务，须明确要求继续。

用户核对原话：

> 你意思是所有正在执行的任务以及正在等待的任务全部变成暂停，是吧？

助手明确了上述负责人及状态范围后，用户确认原话：

> OK，我同意

这曾是用户确认的方案，随后由第 8 项明确替代，不再作为目标需求。助手后来提出的取消任务专用复查安排也未获确认，不纳入需求。

### 8. 存在进行中或等待中的任务时阻止关闭 Task（当前决定）

用户原话：

> 哎，我觉得这样好烦，要不简单一点，只要有在运行中或者在等待中的任务，这个特性就不能关，也是像刚刚那样给他一个提醒。

助手复述以下规则后，用户确认「好，继续」：

- 该 Agent 仍负责任一 doing 或 waiting 任务时，Task 开关保持开启，阻止本次关闭。
- 使用约 2 秒后淡出的 Toast：「还有进行中或等待中的任务，请先暂停或结束这些任务，再关闭 Task」。交互遵循第 2 项的轻提示规则。
- 被阻止的关闭操作不修改任务状态，不处理关联定时安排。
- 没有上述两类任务时才允许关闭；其他 Agent 的任务不构成该 Agent 的关闭阻碍。
- 不再通过配置关闭操作批量暂停任务，不引入配套的批量恢复或定时安排清理流程。

### 9. 单开工具的边界、Feature 依赖和统一关闭原则

用户原话：

> 单独打开工具，那就是只是那个工具可以用啊，其他不需要有啊。然后我回答你上一个问题。**Cron 定时调度的关闭条件，task 的feature就依赖这个cron的feature。所以task feature开了也不能关cron。有还生效的cron任务也不能关。你理解我的原则了，就不用问了。这种就很简单的逻辑，就是它需要被用到，那就不允许。**

已确认：

- 单独开启工具仅使该工具可用，不反向开启所属 Feature，不附带开启该 Feature 专属的额外提示词、后台复盘或其他自动行为。
- Task Feature 依赖 Cron Feature；开启 Task 时联动开启 Cron 及其必需依赖。即使当前没有 doing/waiting 任务，只要 Task Feature 开启，就不能关闭 Cron。
- 该 Agent 存在仍生效的 Cron 任务时，也不能关闭 Cron。
- 基础必需能力、已开启 Feature 的必需工具/Skill/Feature，以及仍被有效运行责任需要的能力，都不能被关闭。共享依赖只要仍有需要者就保留。
- 非基础能力在没有上述需要者时可关闭，遵循已确认的工具与 Skill 联动规则；默认勾选本身不构成关闭限制。
- 关闭受阻保持配置、任务和定时安排不变，使用既定 Toast 说明直接原因，不加依赖标注或确认弹窗。
- 按这条统一原则处理明确依赖，不再逐项要求用户重复确认。

助手的实现边界解释：工具的定义、参数说明及兑现其本身操作所必需的底层服务不等于额外开启 Feature 行为；不得通过裁掉工具必需执行条件，重新制造“工具勾选但不能用”。依赖细目由设计根据真实能力核实，不把这项解释扩大为新增其他工具或额外主动行为。

## 对齐状态

用户原则、Task/Cron 关系、关闭限制、交互和升级方式已收口，以下场景及验收标准据此整理，可交接设计。第 7 项及与第 9 项冲突的早期候选仅保留历史，不构成目标。具体依赖清单、工具与 Feature 的注册拆分、跨入口一致校验和运行状态读取方式交给设计依据真实实现完成，不再把同一原则的直接推论逐项交用户确认。尚未形成或审查技术设计，不授权实施或生产变更。

## 用户场景

1. 用户开启某个 Feature，希望相关工具、Skill 和依赖 Feature 同步可用，无需再猜测漏开了哪个开关；选择保存、重新打开和实际使用时一致。
2. 用户关闭某个 Feature 后，可以单独重新打开一个工具完成对应操作，不想同时恢复整套 Feature 的主动指导或后台工作。
3. 用户调整能力时，已开启功能不能被拆成残缺组合。需要保留的开关保持原状，短暂提示说明先关闭哪个依赖方即可，不增加常驻依赖标注。
4. 用户关闭 Task 时，如果该 Agent 仍负责执行中或等待中的任务，系统提示先处理任务；配置操作本身不批量暂停任务或清理安排。
5. 用户关闭 Cron 时，仍开启的 Task 或生效中的定时任务都会阻止关闭，避免运行责任失去调度能力；消除需要者后才可关闭。
6. 用户部署升级版本时，希望原先开启的功能继续可用。部署 Agent 按本 unit 提示词一次性补齐已有配置，而非关闭功能或让产品在每次启动时重写配置。

## 验收标准

### Requirement: Feature 开启 SHALL 保证完整依赖

#### Scenario: 开启功能时补齐依赖
- **GIVEN** 某 Feature 所需的部分工具或 Skill 尚未启用
- **WHEN** 用户开启该 Feature
- **THEN** 必需工具、Skill 和依赖 Feature 同步开启，界面显示真实选择，保存后实际功能完整可用
- **AND** 必需 Skill 可发现、可按需加载，不因启用而每轮全文注入

#### Scenario: 开启 Task
- **WHEN** 用户开启 Task Feature
- **THEN** Cron Feature 同步开启，并保证任务推进、等待及复查能力完整，不要求用户另行补开依赖

### Requirement: 单独工具选择 SHALL 真正生效且不附带启用 Feature

#### Scenario: Feature 关闭时单独打开工具
- **GIVEN** 所属 Feature 关闭
- **WHEN** 用户单独打开某工具并保存
- **THEN** Agent 可实际使用该工具，所属 Feature 保持关闭
- **AND** 不附带开启该 Feature 专属的额外提示词、后台复盘或其他自动行为

#### Scenario: 关闭 Feature 后重新打开工具或 Skill
- **WHEN** 用户关闭 Feature，随后手动重新打开其中某个工具或 Skill
- **THEN** 尊重最后一次手动选择，该工具或 Skill 实际可用，不因所属 Feature 仍关闭而被隐藏、拒用或再次关掉

### Requirement: 关闭 Feature SHALL 联动工具与 Skill 并保护共享依赖

#### Scenario: 允许关闭时联动关联选择
- **GIVEN** Feature 不属于基础必需能力，且没有其他已开启 Feature 或有效运行责任需要它
- **WHEN** 用户关闭该 Feature
- **THEN** 默认关闭其关联工具和必需 Skill，界面同步更新
- **AND** 基础固定能力、仍被其他已开启 Feature 必需的工具和 Skill 保持开启，不增加工具旁的依赖归属标注

#### Scenario: 默认工具仍可选择
- **GIVEN** 某工具默认勾选，但不属于基础必需能力，也未被开启的 Feature 或有效运行责任需要
- **WHEN** 用户关闭该工具
- **THEN** 可以保存并实际停用，不因默认勾选而被锁定

### Requirement: 仍被需要的能力 SHALL 阻止关闭并轻量提示

#### Scenario: 关闭已开启 Feature 的必需工具或 Skill
- **WHEN** 用户尝试单独关闭仍被开启的 Feature 必需的工具或 Skill
- **THEN** 开关保持开启，不跳动、不顺带关闭依赖方；显示「请先关闭『{Feature 名称}』，再调整此工具」或对应 Skill 文案
- **AND** 提示在操作附近淡入、展示约 2 秒后淡出，无关闭按钮，不遮挡操作或抢焦点；重复点击延长现有提示，不叠加多个提示

#### Scenario: Task 阻止关闭 Cron
- **GIVEN** Task Feature 开启，无论当前是否存在执行中任务
- **WHEN** 用户尝试关闭 Cron
- **THEN** Cron 保持开启，按同样 Toast 交互提示先关闭 Task，其他配置与业务状态不变

### Requirement: 有进行中或等待中的责任 SHALL 阻止关闭 Task

#### Scenario: 仍有责任时关闭受阻
- **GIVEN** 该 Agent 仍负责至少一项 doing 或 waiting 任务
- **WHEN** 用户尝试关闭 Task
- **THEN** Task 保持开启，显示「还有进行中或等待中的任务，请先暂停或结束这些任务，再关闭 Task」的 Toast
- **AND** 不修改任务状态，不取消或修改关联定时安排

#### Scenario: 不存在上述责任时允许关闭
- **GIVEN** 该 Agent 没有 doing 或 waiting 任务，也没有其他需要保留 Task 的依赖
- **WHEN** 用户关闭 Task
- **THEN** 允许关闭并保留已有任务记录；其他 Agent 的任务不阻碍这次关闭

### Requirement: 有生效中的定时任务 SHALL 阻止关闭 Cron

#### Scenario: 定时责任阻止关闭
- **GIVEN** 该 Agent 存在仍生效的定时任务
- **WHEN** 用户尝试关闭 Cron
- **THEN** Cron 保持开启，按同样 Toast 交互提示先停用或删除生效中的定时安排
- **AND** 定时任务的状态及安排不被本次关闭尝试修改

#### Scenario: 无依赖及定时责任时允许关闭
- **GIVEN** 没有已开启 Feature 依赖 Cron，且该 Agent 没有仍生效的定时任务
- **WHEN** 用户关闭 Cron
- **THEN** 允许关闭并按关联工具、Skill 的规则更新选择，保留历史记录

### Requirement: 各配置入口及真实执行 SHALL 遵循同一规则

#### Scenario: 保存与实际使用一致
- **WHEN** 用户通过 Web、iOS 或配置 API 保存上述能力选择，重新打开配置或查看有效能力
- **THEN** 选择和实际可用性一致；不能从其他入口绕过仍被需要的依赖保护，也不能保存成功后实际缺少能力
- **AND** 非界面入口返回可理解的关闭受阻原因，界面使用既定 Toast，不以界面置灰代替真实规则

### Requirement: 升级 SHALL 保留已开启 Feature 并由部署 Agent 补齐依赖

#### Scenario: 整理已有不完整配置
- **GIVEN** 升级前某 Feature 已开启但缺少必需依赖
- **WHEN** 部署 Agent 在已授权部署中执行本 unit 的部署提示词
- **THEN** 该 Feature 保持开启，缺失的必需工具、Skill 和依赖 Feature 补齐；已有 Task 开启时保证 Cron 开启
- **AND** 无关选择和业务记录保留，不关闭 Feature 来消除配置矛盾

#### Scenario: 后续合法选择不被迁移覆盖
- **GIVEN** 一次性配置整理已经完成，用户随后合法调整了能力
- **WHEN** 节点重启或再次部署
- **THEN** 不通过重放历史整理覆盖后续选择，不在产品代码中增加自动历史配置迁移逻辑

## 范围与非目标

- 在范围：基础必需能力、Feature 必需依赖及可选扩展的边界，配置联动与实际可用性，部署时补齐已有配置依赖的提示词。
- 非目标：本阶段实施代码或修改生产；替代另一聊天对 Global NO_REPLY、Task 空转及执行语义的讨论；恢复 Task/Goal 双写；把工具可用解释为操作已获授权；扩大既有审批与数据权限。
