## 原始需求

以下为用户原话；保留表述与编号，省略消息传输产生的转义符和多余空行。

> Let the UI speak for itself. 并且你做的雷霆大按钮巨丑。
>
> 让 UI 自己说话（Let the UI speak for itself）。
>
> 1. 不要用说明性文字解释界面已经表达清楚的功能、操作方法或页面用途。
> 2. 使用具体的动词和操作对象命名按钮，例如「连接仓库」，而不是「新建」或「开始」。
> 3. 如果标题、布局、图标、控件或状态已经传达了信息，就不要重复添加文字。
> 4. 优先用直接可操作的控件代替操作指引。例如提供「升级套餐」按钮，而不是写一段说明告诉用户去哪里升级。
> 5. 不要为了填充空间而添加副标题、辅助说明、功能介绍或占位文案。
> 6. 保留影响用户正确决策的必要信息，包括不可逆操作、费用、权限、数据删除和重要限制。
> 7. 使用清晰的信息层级、间距、分组和交互反馈让界面不言自明，不要牺牲可访问性。
> 8. 实现完成后审查每一处 UI 文案：如果删除这句话不会导致用户误解、犯错或遗漏重要信息，就删除它。
>
> 目标：让用户无需阅读功能说明，就能理解当前状态并完成操作。
>
> 现在整个agent配置的页面包括config和其他的，都需要进行一次重新的ui ux用户体验设计。然后，我特别指出一点，现在很少有网站会做这种红色的框的空位。
>
> ## 空间利用率与布局质量
>
> 设计现代、精致、高信息效率的 Web UI，避免传统企业后台常见的松散布局和过度卡片化。
>
> 核心原则：**留白必须有设计目的，而不是为了把页面撑开。追求高效的空间利用率，而不是单纯增加或减少间距。**
>
> 1. **消除无效留白**：不要让内容区域周围出现大块没有视觉或功能价值的空白。充分利用屏幕空间，合理调整内容宽度与布局结构。
> 2. **提高信息密度**：相关信息紧凑地组织在一起。简单配置不应需要大量滚动才能完成，但也不要将内容过度挤压。
> 3. **避免过度卡片化**：不要习惯性地将每组内容放进独立的大圆角卡片。优先通过排版、对齐、细分隔线和层级组织内容。
> 4. **减少过度内边距**：不要使用大面积 padding、margin 或空容器制造虚假的高级感。间距应具有一致的视觉节奏。
> 5. **根据内容选择布局**：短字段不需要横跨整个页面；相关字段可以排列为多列；简单状态和操作可以放在同一行。不要机械地把所有元素纵向堆叠。
> 6. **避免冗余说明**：不要在每个标题、字段和按钮下面都增加描述。仅保留帮助用户理解必要信息、重要操作后果的文字。
> 7. **建立清晰的视觉层级**：利用字体、大小、对齐、间距与分组建立界面秩序，而不是依赖大量灰底和白色卡片。
>
> **设计验收标准：**
>
> - 页面是否存在大块无意义的空白？
> - 是否有容器占据大量空间却只承载少量信息？
> - 是否能通过重组布局，而不只是缩小 padding，提高空间效率？
> - 每处留白是否有明确的分组、层级或阅读价值？
> - 界面是否呈现为一个经过整体设计的产品，而不是多张 UI 组件卡片的简单堆叠？
>
> 目标是现代、高品质 SaaS 产品的精致、克制、高效布局，而不是老式 Admin Dashboard 模板。
>
> 新建一个unit做这个事情吧

### Agent 解读与边界

- 类型为 feat，范围是跨多个页签的整体交互与视觉重设计；按用户本次明确要求，直接在真实代码与隔离运行环境中设计，不以原型或事前设计门禁阻塞迭代。
- “其他的”按附件六个页签及其所属内容理解，包含导航侧栏、Agent 页头、状态反馈，以及普通 Agent、Global Agent、本人 PA 在设置区内的适用差异。不是只修 Config 或单个离线横幅。
- “雷霆大按钮”视为对整页操作控件尺度和视觉权重的反馈，不擅自限定为某一个按钮。创建入口、打开聊天、刷新、保存及页签内操作均需审查。
- “高信息效率”要求重组信息关系与操作路径，不等于全局压小字号、点击区域或间距。具体布局、控件、视觉尺度和页签组织交给设计阶段决定；现有六个页面的能力必须仍然可找到。
- 本 unit 保留 bugfix-644 的离线可读、离线只读、未知不冒充空、刷新确认后恢复操作等行为；可替换其展示方式和文案。两者关联不表示 bugfix-644 已合并或部署。

## 用户场景

1. 用户从 Agent 导航切换助手，立即知道当前对象、连接状态和所在页面；六个页面呈现同一产品的层级与操作方式，名称或设备较长时仍能辨认对象。
2. 用户修改名称、说明、主模型、推理强度、备用模型、审批或能力配置，直接找到控件与提交动作。常用短字段紧凑排列，长文本有合适的阅读空间，不必越过大横幅、空白和功能介绍才能开始工作。
3. 节点离线或某部分读取失败时，用户仍能查看已有设置、上次确认时间和局部数据，并明确知道哪里不可改、哪里未知。恢复连接后能刷新确认，过程中不会误把历史信息当成当前结果。
4. 用户在 Channels、Skills、Plugins、Sessions 查看状态、查找条目并执行已有操作。空态、失败态、加载态与有数据的页面都保持适度密度，不出现只放一行内容的巨大容器或泛泛的功能介绍。
5. 用户调整本人 PA 的来源与联系限制，或执行删除、卸载等有后果的操作。界面简洁，但权限、影响范围、不可逆后果与失败结果仍清楚可见。
6. 用户用较窄窗口、移动浏览器、键盘或屏幕阅读器完成上述工作；视觉变紧凑不损害可读性、触达和焦点顺序。中英文界面均不靠说明段落补足交互含义。

## 验收标准

### Requirement: 整个 Agent 设置区具有统一、可辨认的信息层级

#### Scenario: 六个页面连续浏览
- **WHEN** 用户打开 Agent 并依次访问 Overview、Config、Channels、Skills、Plugins、Sessions 对应的页面
- **THEN** 能辨认当前 Agent、所在页面、主要内容和适用操作；六个页面的导航、标题、控件尺度和反馈风格一致
- **AND** 不出现只有 Config 更新而其余页面仍以另一套大卡片、说明和大按钮组织的割裂体验。

#### Scenario: 切换对象与长名称
- **GIVEN** 列表包含普通 Agent、Global Agent 和本人 PA，并有较长的名称或设备名称
- **WHEN** 用户搜索和切换 Agent
- **THEN** 能辨认当前对象及必要归属，侧栏不会挤占主要配置空间；加载或失败期间仍能导航
- **AND** 未保存的编辑沿用草稿保护，不因新导航交互丢失。

### Requirement: 布局通过内容组织提高空间效率

#### Scenario: 桌面 Config 首屏与常用编辑
- **WHEN** 用户在 1440×900、100% 缩放的桌面窗口进入 Config
- **THEN** 首屏能看到并开始操作基础身份与主要模型配置；没有大块提示或装饰性空白将常用控件推出首屏
- **AND** 短字段、相关配置与状态按内容关系组织，长文本保持可读宽度，不把全部字段机械堆成长列，也不把全部短字段拉满屏幕。

#### Scenario: 跨页面空间审查
- **WHEN** 用户在 1440×900 和 1920×1080 的桌面窗口查看六个页面的有数据状态
- **THEN** 内容两侧和分组之间的留白服务于对齐、阅读或层级，不重现附件中连续宽灰色边沟和只承载少量内容的大面积容器
- **AND** 相关内容主要通过排版、对齐与必要分隔组织，不把每组都包装为独立大圆角卡片；增加信息密度不依赖缩小正文到难以阅读。

### Requirement: 文案只保留会影响理解、决策或操作结果的信息

#### Scenario: 常规页面逐句审查
- **WHEN** 用户阅读六个页面中的标题、标签、状态、辅助文字和空态
- **THEN** 已被控件、标题或状态表达的功能与用法不再重复解释；不存在只为填空间添加的副标题、功能介绍或占位文案
- **AND** 每条保留的辅助说明都能指出删除后会导致的具体误解、误操作或重要信息遗漏。

#### Scenario: 操作名称直接表达动作对象
- **WHEN** 用户查看创建入口、打开聊天、保存、刷新、安装、删除等操作
- **THEN** 文字操作以明确的动作和对象命名，能够判断结果，不使用脱离上下文的“新建”“开始”等泛称
- **AND** 可直接完成的操作提供相应控件，不用一段去其他地方操作的说明代替；图标操作具有明确的可访问名称。

### Requirement: 按钮与操作反馈具有克制且明确的优先级

#### Scenario: 同屏多项操作
- **WHEN** 页头、侧栏与内容中同时出现保存、打开聊天、刷新和条目操作
- **THEN** 主次关系清楚，次要动作不会以超大尺寸或强烈底色争抢注意力；按钮大小与动作重要性和内容密度相称
- **AND** “无改动”、加载中、已保存等状态不会伪装成夸张的可点击主按钮，用户能区分状态与操作。

#### Scenario: 保存、失败与待确认
- **WHEN** 用户提交编辑并分别遇到成功、失败或结果待确认
- **THEN** 反馈简短明确且靠近相关操作；失败保留草稿，待确认不表示已保存，也不允许误触重复提交
- **AND** 下一轮采用等影响判断的生效限制仍可理解，不用常驻的大段文字解释每次操作。

### Requirement: 紧凑状态表达保留离线与数据时效的必要语义

#### Scenario: 离线且有历史内容
- **GIVEN** Agent 所在电脑离线，部分设置已有上次确认内容
- **WHEN** 用户查看各页面及展开备用模型、预览等只读内容
- **THEN** 可读历史仍可查看，离线与只读状态清楚，能找到对应内容的上次确认时间；写入操作不可用，且原因可理解
- **AND** 全页状态不占据大幅首屏空间，也不在每组中重复同一句离线说明；历史信息不呈现为已确认的实时状态。

#### Scenario: 未知、真实为空与局部失败
- **WHEN** 某区域从未成功读取、已确认没有条目，或再次读取失败但有历史内容
- **THEN** 用户能区分这三类情况；未知不显示为零项或全部关闭，局部失败不抹去其他区域
- **AND** 对可恢复的失败提供明确重试动作，恢复连接后先确认当前状态再允许编辑。

### Requirement: 六个页面及适用的 PA 内容均能直接完成原有工作

#### Scenario: 有数据的配置与管理旅程
- **WHEN** 用户查看 Overview、修改 Config、管理 Channels、浏览 Skills、管理 Plugins、查看 Sessions，并进入本人 PA 的适用设置
- **THEN** 原有信息与操作仍能找到并完成；列表中的名称、关键状态和相关动作易于对应，详情按需展开，不靠重复卡片说明完成导航
- **AND** 模型与备用顺序、能力选择、通道状态、会话入口及本人 PA 权限边界不因视觉简化改变。

#### Scenario: 能力依赖与占用反馈
- **WHEN** 用户选择 Feature、工具或 Skill，或尝试关闭存在依赖、固定要求或实际工作占用的能力
- **THEN** 保留既有依赖联动、关闭限制和其他草稿；受阻原因在操作附近清楚可见，提示不挤开控件、不遮挡目标、不抢焦点
- **AND** 不为说明依赖而添加常驻说明段落或新的宽大提示容器。

#### Scenario: 空态与加载态
- **WHEN** 上述页面处于加载中、搜索无结果或已确认无条目
- **THEN** 用户能辨认当前状态；有适用下一步时直接提供操作，没有时只保留必要的短状态
- **AND** 不出现大面积空卡片、无意义装饰、文件格式等内部实现说明或不适用于当前状态的操作入口。

### Requirement: 精简不隐藏重要后果或损害可访问性

#### Scenario: 重要后果与权限
- **WHEN** 用户准备删除、卸载、改变权限或执行具有不可逆后果、费用、数据删除影响的已有操作
- **THEN** 执行前能辨认对象、影响和适用限制；必要提醒不会因文案精简被删除或只靠颜色表达
- **AND** 取消操作保持原状态，失败明确表示未完成，不新增未经授权的能力或权限。

#### Scenario: 窄屏、键盘与应用语言
- **WHEN** 用户在 390×844 的移动浏览器、1280×800 的桌面窗口使用页面，或以键盘及屏幕阅读器访问主要操作，并切换中英文
- **THEN** 内容与操作可达、标签和焦点顺序清楚；窄屏合理重排，无整页横向溢出或按钮遮挡；紧凑按钮仍易于触达
- **AND** 图标、禁用态、选中态与反馈可被辨认，必要文字不被截断隐藏，中英文使用一致的简洁原则。

## 范围与非目标

在范围：Web Agent 设置区整体体验，包括六个页面及内部子视图、列表侧栏、Agent 页头、页内导航、适用的本人 PA 设置、表单分组、列表和详情、按钮层级、文案、空态/加载/失败/离线/待确认/成功反馈，以及桌面和移动 Web 的适配与可访问性。页签可以重新组织，但现有信息和能力不得因此遗漏。截图是具体问题起点，不是范围终点。

非目标：新增 Agent 运行能力、重定义模型或审批语义、修改权限边界、改变离线读写契约、扩展为全站视觉改版、原生 iOS 视觉重设计、重做电脑安装绑定流程、生产部署。创建入口与共用控件保持一致，但不扩展为新建 Agent 业务流程重构。

按本次明确授权直接交付可运行的真实页面供设计迭代；实现完成后按全部 Scenario 进行真实页面验收，并逐条审查保留文案的必要性。单张截图改善不等同于完成整个设置区的用户体验验收。
