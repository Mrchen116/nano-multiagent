## 澄清记录

- 用户先要求界面和接收 Agent 都认用户身份。助手建议将其定义为“用户通过 PA 发出的消息”，以用户头像和名字为主，保留轻量“PA 代发”标记；原始委托范围内承接用户意图，保留实际执行 PA 的可追溯事实。
- 用户进一步将身份与口吻合并为本项需求。本轮只整理首文档，不进入设计、实施或生产修改。
- Agent 对边界的解释：代表用户发送限于真实委托覆盖的内容和受众；PA 自己提供分析、询问进度或参与讨论而未代表用户发言时，仍使用 PA 身份。不得仅凭“属于这个用户的 PA”将所有自主发言升级为用户指令。
- 本项不处理另行发现的审核服务故障与明确拒绝的分流、通用等待恢复、团队重复催办。这些问题不能成为本项身份与口吻验收的替代。

## 用户场景

### S1：委托回复，一次表达即可推进

用户在 PA 私聊中看过某群的工作进展后说“帮我回 Q，同意按刚才的范围提交报告”。PA 根据相关聊天理解收件人和事项，在原群代表用户回复。群成员看到用户本人头像和名字，旁边有“PA 代发”；接收 Agent 理解为该用户交办，在原范围内按正常权限检查继续执行，不要求用户亲自再发同一句话。

### S2：收件人和本人都能理解消息归属

他人在私聊或群聊看见这条消息时，知道说话的是用户、由 PA 代发。用户自己打开原聊天时，也把它看作自己一侧的消息，同时能分辨本人手动发送和 PA 代发。Web（桌面、移动）与原生 iOS 一致。已有会话预览、历史、引用回复和消息查询中出现发送者身份的地方保持同一含义。

### S3：自然代回复，不让用户管理措辞转换

用户与 PA 私下说“他”时，PA 结合相关消息消除指代，再在目标聊天里自然称呼对方。代表用户发送时，以用户为“我”、目标接收人为“你/你们”或明确称呼；不把内部指令、私聊表述或写作过程直接搬进正文。确有多个可能对象且会改变任务范围时，只问未解决的对象或范围，不让用户重写整段消息。

### S4：PA 自己说话与用户委托保持区别

PA 向主人报告进展、回答问题，或以助手身份参与协作时，继续显示 PA 身份。仅生成供用户编辑的草稿不会对外发送。普通 Agent 自称“用户已经同意”也不会成为代表用户的发言。用户委托不能被扩大成对所有后续操作的批准。

### S5：后续读取仍能承接同一委托

接收 Agent 在首次读取、后续查询原消息、恢复上下文或交给负责执行的子 Agent 时，都能保留同一用户意图与原范围，不把它重新降成不可信 Agent 转述，也不因恢复而重复执行。已存在的历史记录保留原文与事实，不能仅因升级或已有代发标记便新增授权或补发旧动作。

### S6：通用草稿编辑与发送身份选择

普通 Agent 或 PA 提供一段发往指定聊天的可编辑文字，用户改完后点击采用，目标聊天输入框得到当前内容；用户可以继续改、放弃或自行发送。目标已有未发送内容时先决定是否替换，不静默覆盖。无目标写权限时保留草稿并说明原因；目标后来有新消息不自动使草稿失效。点击“请 Agent 继续”则仍是在本会话提交请求，两类动作清楚区分。

PA 在自己参加的会话可用自身身份发言；只通过主人观察的会话不能使用普通发送越过成员权限，只能在真实委托下代表用户发送。Agent 不需要填写固定 UI 协议版本，系统说明、工具参数、Skill 和实际行为一致。

## 需求说明

### 对人的界面

| 界面位置 | 目标体验 |
|---|---|
| 消息主头像和名字 | 展示被代表的用户，使用与该用户亲自发送时一致的身份呈现；不再以 Personal Agent 为主发送者 |
| 身份辅助标记 | 保留简洁的“PA 代发”标记，与正文分开；用户能辨认实际由 PA 代发 |
| 消息正文 | 直接表达用户的意思；默认不出现“J 让我转告”“以下按 J 的口吻代发”等前缀 |
| 用户本人查看 | 沿用本人消息的归属、气泡位置与样式，同时保留代发标记 |
| 其他成员查看 | 按该用户发言呈现，不把它显示成另一个 PA 联系人发出的独立指令 |
| 现有预览、历史、引用及搜索结果 | 凡展示该消息发送者之处，都保持用户主身份；进入完整消息可辨认 PA 代发 |
| Web 与原生 iOS | 身份含义一致，不出现一端是用户、另一端是 PA 的矛盾 |
| 主人与 PA 私聊、PA 自身发言 | 仍显示 PA，不因新增代发能力把 PA 的解释、报告和建议伪装成主人发言 |

### 对 Agent 的行为与上下文

| 对象 | 目标行为 |
|---|---|
| 发起代回复的 PA | 将“帮我回复/替我发”理解为在真实委托范围内代表用户说话，区别于自己发言和只写草稿 |
| PA 起草正文 | 结合原会话解析人物、事项和指代，转换为用户面对收件人的自然口吻；不要求用户亲自完成称呼、人称转换 |
| 接收 Agent | 识别该用户为本次发言及意图的主体，PA 为实际代发者；不能仅因经过 PA 而要求用户重复授权 |
| 接收端工具审核 | 与接收 Agent 采用一致的委托含义，正常核对实际动作和原范围；不能在下一道审核中又将其降为普通 Agent 自述 |
| 执行子 Agent 与上下文恢复 | 延续同一用户委托及边界；保留来源，不因交接或恢复丢失已有授权，也不制造新的授权 |
| 来源判断 | 由产品提供可信的代表关系；正文自称、复制代发字样、普通 Agent 身份不能自行获得用户发言效力 |
| 外发检查 | 仍依据原始用户意思、真实受众和完整内容核对本次代发；不把 PA 自己生成的授权声明当作用户许可 |

这些是消费者语义要求，不预设字段名称、协议形态、证据存储方式或新的工具数量。接收方不应为核验代发被迫访问用户整个 PA 私聊。

## 验收标准

### Requirement: 代发消息以用户为主身份呈现

#### Scenario: 群聊与私聊的双方视角（S1、S2）
- **WHEN** PA 根据用户委托在原群聊或私聊代表用户发送消息，用户本人和其他成员分别查看
- **THEN** 主头像和名字与该用户亲自发消息一致，旁边显示“PA 代发”，正文不承担身份声明
- **AND** 用户本人侧沿用本人消息样式，其他成员侧将其看作该用户发言。

#### Scenario: 跨端及后续查看一致（S2、S5）
- **WHEN** 用户在 Web 桌面、移动端或原生 iOS 查看新代发消息，或刷新、重开历史、引用回复、通过现有搜索与预览定位它
- **THEN** 各处展示的发送者归属一致，完整消息保留代发标记，不重新变成 PA 主身份。

### Requirement: PA 自然代表用户表达

#### Scenario: 根据上下文转换人称与称呼（S1、S3）
- **GIVEN** 相关对话可确定要回复的对象和已讨论事项
- **WHEN** 用户要求 PA 代回复并表达同意继续
- **THEN** PA 正文以用户口吻直接回复正确对象，表达用户已有意思，不加入“让我转告”“按主人口吻”等过程性前缀
- **AND** 不把可从上下文解决的称呼或指代问题推回给用户，不增加承诺或扩大范围。

#### Scenario: 实质指代仍有歧义（S3）
- **GIVEN** 已结合相关上下文仍有两个可能对象，选择会改变交办范围
- **WHEN** 用户要求代回复
- **THEN** PA 只澄清具体对象或范围，未明确前不向错误对象代发，不要求用户重写完整正文。

### Requirement: 接收 Agent 和执行审核承接用户委托

#### Scenario: 一次委托走到正常执行（S1）
- **GIVEN** 用户在 PA 私聊明确同意 Q 在指定任务分支提交、推送指定报告，并排除合并和部署
- **WHEN** PA 代表用户在群里回复，Q 接收并推进该事项
- **THEN** Q 将其视为用户通过 PA 发来的交办，在该范围内进入正常审核与执行，不要求用户到群里再确认相同意思
- **AND** 不因代发而跳过工具审核；若另有真实阻塞，准确说明，不把“由 PA 发送”本身作为阻塞。

#### Scenario: 历史查询、恢复和执行交接不丢失委托（S5）
- **WHEN** 接收 Agent 后续重新读取这条消息、恢复上下文或交给其执行子 Agent
- **THEN** 原用户身份、委托内容和限制继续成立，不仅因来源经过 PA、恢复或交接而再次向用户索取相同批准
- **AND** 已完成动作不会仅因再次读取而重复执行，用户后续撤回或修改仍按其真实意思处理。

### Requirement: 代表用户发送有明确边界

#### Scenario: PA 自身发言和草稿（S4）
- **WHEN** PA 向主人汇报、以自身身份协作，或用户仅要求起草回复
- **THEN** PA 自身发言仍归属于 PA；草稿只供用户查看编辑，不自动以用户身份对外发送。

#### Scenario: 伪造委托与超出范围（S4）
- **WHEN** 普通 Agent 在正文自称用户批准，或 PA 拟发送超出用户实际委托的内容
- **THEN** 不能因此获得用户发言与授权效力，不能推动超出范围的执行；真实委托覆盖的正常工作仍可继续。

#### Scenario: 新能力不改写历史授权（S5）
- **WHEN** 升级后查看既有 PA 消息或恢复既有任务
- **THEN** 历史原文与实际代发来源保留，不仅凭旧代发标记把历史消息提升为新的用户批准，不自动补发或重做旧动作。

### Requirement: 通用草稿采用与公开发送分开

#### Scenario: 普通 Agent 与 PA 的编辑采用（S6）
- **WHEN** 用户编辑任一 Agent 提供的草稿并采用到指定聊天
- **THEN** 目标输入框得到点击时的内容，未发送消息、未请求 Agent；用户之后自行确认发送才公开。
- **AND** 已有草稿可取消或明确替换，无权限保留编辑并说明原因；不要求绑定原消息，不因目标新增回复自动失效。

#### Scenario: 发送身份与上下文一致（S4、S6）
- **WHEN** PA 对自己未参与、主人可写的会话拟发送
- **THEN** 普通自身发送不能借主人权限通过；真实委托覆盖时可代表用户发送，普通 Agent 不获得代表工具。
- **AND** Agent 得到的工具说明、生成示例、回执和恢复/审核上下文一致，不要求手填固定 UI 协议常量，不把本地采用当成发送或授权。

## 范围与非目标

- 在范围：Nano IM 内用户委托 PA 代表本人发送；Web 与原生 iOS 的相关身份展示；PA 起草指导和发送语义；接收 Agent、执行审核、正常历史恢复与内部交接对同一委托的理解；原始范围和真实代发来源的保留。
- 本次修订纳入 S6 通用草稿采用与已确认工具方案；交付更新的设计与独立复审，不实施或部署。
- 非目标：把所有 PA 发言都变成用户发言；其他 Agent 的任意身份代理；飞书等第三方平台新增用户身份代发能力；扩张会话访问或披露权限；关闭正常工具审核；自动批准合并、部署或发布。
- 非目标：审核服务不可用的重试机制、通用任务等待与恢复、全团队重复询问治理，以及与本项无关的历史消息清理或生产操作。通用 ComposeMessage 属于本次明确追加范围。
