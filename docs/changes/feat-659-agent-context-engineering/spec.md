# feat-659: Agent Context Engineering 开发规范与审查机制

## 原始需求

完整原话保存在 [user-request.md](user-request.md)，包括用户指定的调查范围、规范与 Skill 设计、流程接入、三个真实 nano 试点和交付要求。下文是开发者视角的验收整理，不替代原话。

## 澄清记录

用户已明确：按现有 change-workflow 自主调查、设计、实施、测试并交付可审查 PR，不切换快速开发、不自动合并、不重构运行时。没有需要补充决定的范围问题。

## 用户场景

开发者修改 Agent 的提示词、工具、Skill 或动态上下文时，能够从仓库入口找到统一的设计标准，按实际影响设计其完整生命周期，并在已有设计和实现审查中发现模型无法正确消费的接口。与 Context 无关的工作维持原流程。维护者能区分方案推理、实际请求和模型行为证据，复查具体案例而不读取私人请求原件。

本 unit 改动开发方法和开发 Agent Skill；不改变 nano 终端产品行为，按 Full 零用户面执行 verifier 与 code review。真实 nano 案例是开发方法试点，不是新增产品功能验收。

## 验收标准

### Requirement: 开发者能使用统一且可发现的 Context 设计标准

#### Scenario: 修改模型可见内容或其生命周期
- **WHEN** 开发者改变信息的选择、交付、更新或恢复
- **THEN** 能从仓库入口找到唯一通用规范，以 LLM 消费者视角审查全部 Context 类型及组合关系，知道哪些事实必须由宿主保证。

#### Scenario: 修改无 Context 影响的界面样式
- **WHEN** 变更只影响展示样式且不改变模型输入、信息选择或消费链路
- **THEN** 沿用普通开发路径，不被要求做完整 Context Review。

### Requirement: 现有设计、实施、审查与验证自然覆盖 Context

#### Scenario: 设计与实施相关 change
- **WHEN** 设计或 diff 实际影响 Agent Context
- **THEN** 现有角色在原产物中完成相应设计说明、独立设计审查、交付验证、实现审查与一致性核对，不增加审批 Gate 或机械重复审查。

#### Scenario: 证据不足或出现接口设计缺陷
- **WHEN** 仅有源码、内部 API 或类型检查证据，或模型被要求提供不可获得的信息
- **THEN** 审查者区分设计缺陷、实现偏离及未验证行为，给出具体机制与证据状态，不把问题泛归模型能力。

### Requirement: 方法能通过真实 nano 案例复查

#### Scenario: 工具、动态消息和 Prompt/Skill 试点
- **WHEN** 维护者复查本次方法试运行
- **THEN** 能看到三个不同 Context 类型的实际审查结论、至少一个非触发反例，以及静态、最终请求与真实模型行为各自支持的范围。

#### Scenario: 环境或观测能力有缺口
- **WHEN** 无法获得某种实际模型输入或行为证据
- **THEN** 清楚记录缺口、影响和恢复验证入口；不提交私人原始数据，也不把静态验证当作模型验收。

## 范围与非目标

在范围：用户指定的规范、短 Review Skill（Design/Implementation 两模式）、现有 change-* 条件接入、索引与观测操作说明、现有能力调查及三个案例试运行。复用已有测试与日志，仅在证明实际观测盲区后考虑最小只读诊断。

非目标：重构 DSH/产品运行时、引入 MCP 协议、另建 Snapshot/观测平台、新 Gate/角色、全仓产品缺陷清扫、发布或部署。试点产品缺陷以带定位和证据的记录交回既有修复流程。
