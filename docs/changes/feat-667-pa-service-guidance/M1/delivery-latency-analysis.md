## 已证实的系统额外成本

1. 权限解释造成实质返工和停等。本轮必要合成证据检查、对齐 main 已改变的普通审核调用、正常调用现有模型 API 多次被拒。原授权存在，父级限制被扩大。授权问题、窄修订与恢复证据见 [authorization-fix.md](authorization-fix.md)；原始 Luna 输入、回放及主人干预记录保存在下述本地证据根目录的 `authorization-fix/`、`issue361-input-and-interventions/`。首次审计从18:12已报阻塞到19:39才取得；这一时间窗与其他工作重叠，不能声称净损失87分钟。第二次代理阻塞20:26到20:41实际恢复约15分钟。
2. 协调与记账明显放大。截至快照，PA主会话51个turn，44个由agent-message触发；54次读取同一个ongoing-work.md、57次编辑，62次send_message（28次回执行者、34次发给主人）。主会话累计活跃40.8分钟，其中多数与执行者并行，不能按40.8分钟净拖延计。执行者向PA回报55次，执行者会话共126次内部 send_message。七个工作角色合计93个turn、1749个工具调用；当前正在运行的turn尚未计入elapsed。这证实大量资源用在汇报与恢复记录，不证明每条消息都无价值。
3. 临时验收设施反复修理。执行者修改 .e2e-issue361-observe.mjs 18次、代理11次；真实故障含query路径错误（已到代理却日志漏记，误判成未到）、集成后的原生partition参数不匹配。另有安装矩阵初次收口才发现遗漏。计数不是缺陷次数；但这些具名故障和漏项确实造成了重新组织验证。应优先复用已验证的隔离启动/观测方式，开跑前明确覆盖矩阵，避免每轮临时发明设施。
4. 存在真实产品可用性故障，而非“只是验收慢”。R5-PA1中，非主人风险输入后固定安全通知/主人回执核对失败，合法主人DM的inbox check/read亦失败，回复held_for_revalidation。没有泄露，但正常服务被阻断。它与#361改动的因果关系尚未确定；不能据源码相同直接豁免，也不应无界扩大本次交付。

## 不能使用的耗时与归因

- Work中的某些工具duration_ms明显不能按串行执行时间相加：11:55:28 UTC的一次read标为1,112,331ms，却在后续秒级已经出现其他读取和动作；七个独立工具的“开始+duration”都落在12:14:01.280–.290 UTC。更像历史结果重建/投影时间被覆盖，需以原生持久事件进一步定因。本次不把统计出的read109分钟当真实磁盘或审核耗时。
- 目录列出23个维护关联session，但公开turns为空；不能据此写“23次维护已运行”或“维护耗时0”。维护对本轮关键路径的影响未证实。
- Token统计含大量重复cache-read。PA累计约1535万total、1517万cache-read；不能称为1535万新生成token或换算未经核实的费用。主会话末次context_used约10.2万，说明状态对话在增长。
- 没有证明Astra/Luna模型本身是主要瓶颈，也没有基准支持换模型即可解决。

## 处理顺序（建议，未额外实施）

1. 先收口原任务，只处理当前实际阻塞，不再对未受影响成果反复全审。
2. 缩减进度回传和账本写入：真正结果、阻塞、决定、执行者变动才需要父级处理；阶段性状态可合并，恢复笔记只保留当前态和证据链接。现有Skill虽要求简短/静默，实际仍出现大量读改；仅“写了规则”不足以说明行为达标。
3. 固定并复用验收入口和审计导出；同条件比较时避免把461提交的基线迁移混入纯开发效率。
4. 单独复现并修复安全通知失败阻断主人正常工作的可用性问题；先确认归因，不能放松安全规则换PASS。
5. 修正耗时观测可信度后，用同任务、同模型/门禁/基线比较直接Codex与PA。衡量实际交付时长、用户介入次数、重复执行与审核等待，而非单看最终测试是否通过。
