本轮修正：撤销先前“只有明确要求保存计划才建 Task”以及“未明确保存的完整委派不进入 Task”的边界。接下并委派的完整事项进入现有 Task，已有对应记录则沿用；日常小事若确实形成需要持续跟进的责任，也可按实际需要记录。普通倾诉、状态反馈或观察到的承诺不因此成为执行授权，不为每条日常消息机械建任务。

Agent 解读：本轮对齐需求和设计方向，不实施产品代码。适用对象是所有 Global Agent，包括 PA。主 Agent 承担连续对话、接单、来源核对、必要决策协调及全部用户沟通；日常小事直接处理，需要独立执行的完整事项交给一个内部执行者负责到底。内部执行者自行组织下级工作，主 Agent 不继续调查同一事项，也不把完整事项机械拆给多个直接执行者后亲自集成研究。Task 承担三项相连的责任：向用户呈现事项及真实流转、确保对应执行者在仍可推进时接续工作、让主 Agent 持续掌握事项变化以便统一沟通。Task 不是只关联一个执行者 ID 的静态备注。内部执行者不成为新的长期数字人或任务负责人。完整事项以可独立交付的用户目标识别，不按每条消息、一天、聊天或图中节点数量机械切分；不设置固定时长或工具步数门槛。

## 用户场景

### 一项完整工作由一个执行者负责

用户向“禅”交办“拉取 DeepSeek Super Agent，并与我们的 Global Agent 对比”。主 Agent 理解原始请求、实际来源和已有约束，确认后把完整目标交给一个内部执行者。执行者自行选择阅读顺序、调查方法、是否再安排下级及如何整合结果，负责交回完整比较成果和必要依据。主 Agent 不同时阅读两边代码重新做一遍研究，也不自行制定技术拆分和额外验收清单。

主 Agent 核对返回成果是否回应用户要求、是否有明确缺口及可用依据；内容矛盾或不足时交回原执行者补齐。需要用户选择、补充材料或处理权限时，执行者内部报告已有结论及具体问题，主 Agent 向用户沟通，收到答复后交回原执行者。接单回应、必要进度、问题和实际结果均由主 Agent 向用户发送，执行者不能绕过主 Agent 与用户对话，内部回传不是公开交付。

### 执行期间接新工作，补充仍回原事项

事项 A 在执行时，用户提出无关的事项 B、询问状态或纠正 A。主 Agent 及时接住这些输入：B 若需独立执行则另行委派，日常短问直接处理；A 的更正、答复和后续修改交给 A 的原执行者，而不是重开重复研究。仅仅话题相近的消息不自动并入 A；不能确定归属且会影响实际执行时才澄清。执行者仍能工作而无新决定时，不要求主 Agent 反复回复“继续”或检查进度。

### 贯穿一天的日常交流留在主 Agent

用户早上说精神不好，中午反馈分享材料做完，傍晚问“我还有什么 todo”，晚上说跑了两公里。PA 沿用同一人的上下文直接交流、查询相关信息和处理小事，把新的完成反馈用于后续回答，不把整天定义成一个持续运行的执行任务，也不为每句话创建执行者或持久 Task。确实接下需要后续跟进的小事时，可按实际需要记录或更新已有 Task，不要求用户额外说“创建任务”。已有获准定时关心仍通过现有安排发生，没有新帮助价值时保持安静。

日常交流中若出现“帮我整理一份完整分享材料”这样的独立交办，PA 将该事项交给一个执行者，同时继续其他日常对话。该事项的补充回原执行者；用户的倾诉、愿望、自述进展或对外承诺本身不自动成为新的执行授权。

### Task 展示所有已接下的完整执行事项

用户把一项工作交给 PA 或“禅”推进，没有使用“创建 Task”之类的固定说法。主 Agent 接下并委派后，该完整事项进入现有 Task；已有对应事项则沿用同一记录。用户在现有任务入口看到哪些在推进、哪些在等、等什么或等谁，以及可用成果和需要自己决定的问题。既有保存计划、业务分解和人工负责的任务继续保留，不把所有计划节点都当作已经交办的执行事项。

Task 仍由产品 Agent 对用户负责，完整事项有一个可辨认的内部执行者；用户不需要把负责人改成临时 subagent，也不需要重复保存成另一张工单。Task 与其执行者的创建和接续关联，不会发生已开始工作却从看板遗漏，或显示正在执行却没有真实执行安排且无人处理的情况。创建和派发发生故障或结果未知时保留真实进度，不重复生成 Task 或执行者。

执行者正在推进时，Task 保持真实的 doing，主 Agent 可以空闲或处理其他工作。系统不因主 Agent 空闲而误判事项无人推进，反复唤醒主 Agent、重复派工或要求用户给工作设置假的 waiting。Task 中的层级、依赖和探索结构继续表达业务关系，不能按每个节点机械创建执行者；同一完整事项也不能因父子节点同时在进行中而重复执行。

更正、回复和复查由主 Agent 协调原执行者接续。只有事项实际无可执行下一步、需要等人或外部条件时才采用 waiting，仍遵守已有有效安排及复查要求；执行者内部等待下级不直接转化为用户 Task 的业务等待。Task 结果提交后，主 Agent 向固定所属聊天交付真实成果；内部执行结束、报告已回传或主会话空闲均不单独意味着任务完成。

### Task 确保未完成的执行者继续，而不是反复催主 Agent

执行者一轮结束，但 Task 仍是 doing、没有真实阻塞、仍有合法有效下一步时，Task 推动原执行者接续，承接已有成果和上下文；不要求用户再说一次“继续”，也不先唤醒主 Agent 去重复调查或另派一人。执行者正在执行、已有待消费输入、或仍有有效下级和工具结果将唤回它时，正常等待对应执行，不并发重复启动同一执行者。

真实等待、用户暂停、完成、待确认、关闭及失去资格不自动续推。模型、工具或运行环境确实无法恢复时，保留实际故障与未完成状态，由主 Agent 说明需要什么处理；不能把意外停工自动描述成业务等待、成功完成或用户暂缓，也不能无效热循环。

### Global 掌握 Task 流转并承担唯一沟通入口

Task 的开始、等待、恢复、结果提交、完成、暂缓、关闭、改派和需要处理的执行异常都有可靠的当前记录，并进入负责 Global 的相关上下文。主 Agent 忙于其他对话时也能在后续处理该事项前取得已发生的变化；空闲时需沟通的问题、成果和故障能使它接续处理，不因为原执行者停止或 Task 已提交结果而丢失用户反馈。

用户随时问“现在在做什么、为什么还没好”，Global 能依据最新 Task 与执行结果回答，不依赖用户去逐一问 subagent 或让 subagent 各自发消息。普通工具步骤、无变化检查和可自行处理的恢复不逐条唤醒主 Agent 或发给用户；主 Agent 了解流转不等于介入每一步执行。

subagent 的提问、进度、阻塞和结果均先回到 Global，Global 决定需要向用户表达的内容并接收答复，再交回原执行者。看板和轨迹可以展示真实内部执行，但不另开用户与 subagent 的对话入口。

### 暂缓、恢复和运行故障不丢失归属

用户暂缓事项 A、改变负责人或撤回执行资格时，对应执行者及其受影响下级不继续发起 A 的新动作，独立事项 B 不被无条件停止。已经发生的动作按真实结果保留，不能声称已回滚。明确恢复后优先由原执行者承接有效要求与已有成果，不让用户重讲整个背景。

重启、换窗或执行者故障后，主 Agent 重新核实当前 Task、执行者和已完成成果，不仅凭 Task 仍是 doing 就复制一份工作。原执行者无法接续时说明具体原因和保留成果，再明确接手安排；暂停、关闭和撤销要求继续生效，不因定时消息、重启或晚到成果自动恢复。不能确认实际执行或交付时，如实说明，不伪报运行中或完成。

## 验收标准

### Requirement: Global 与 PA 将完整独立事项交给一个内部执行者负责

#### Scenario: 整项交办与内部再分工
- **WHEN** 用户交办需要独立调查或制作成果的完整事项
- **THEN** 用户在工作视图能辨认一个负责该完整事项的内部执行者，其下级分工由该执行者组织。
- **AND** 主 Agent 不把这项完整目标拆给多个直接执行者后同时亲自重复调查，也不替执行者预设技术实施方案或新增用户未要求的范围。

#### Scenario: 返回结果不足或执行能力不可用
- **WHEN** 返回成果遗漏原要求、依据不足或存在矛盾
- **THEN** 主 Agent 把具体缺口交给原执行者继续处理，不自行重做同项调查，也不将不完整成果描述为全部完成。
- **WHEN** 当前没有可用执行能力或原执行者确实无法继续
- **THEN** 用户得知具体受阻情况及已有成果，不因派发失败而收到完成声明，也不发生未说明的重复执行。

### Requirement: 委派期间主 Agent 继续处理独立输入并保留原事项归属

#### Scenario: 新工作与原事项更正
- **GIVEN** 事项 A 已由内部执行者承担
- **WHEN** 用户提出独立事项 B，或补充、更正 A 的要求
- **THEN** B 能被接住并按其性质直接处理或独立委派；A 的补充进入原执行者负责的事项，不重开同一份工作。
- **AND** 不能只因话题相近就把新交办并入 A，用户不需要为了内部委派重新复述已有背景或重复批准同一授权。

#### Scenario: 内部普通进展无需父级续令
- **WHEN** 执行者仍能在既有范围推进，只产生普通进展或受理回执
- **THEN** 工作继续，无需主 Agent 逐步批准；用户不会因此收到重复进度、重复成果或例行“收到、继续”转述。

### Requirement: 日常交流由主 Agent 直接延续

#### Scenario: 一天内的小事与状态变化
- **WHEN** 用户在一天的不同时段闲聊、反馈状态或完成情况、回顾经历、查询待办及交办几步可完成的小事
- **THEN** 主 Agent 直接处理并承接已有上下文，后续回答考虑新的完成反馈和当前状态。
- **AND** 不将整天包装成一个执行任务，不为每条消息创建执行者或持久 Task，也不把自述、倾诉和观察内容当作新的交办。

#### Scenario: 日常中出现独立交办
- **WHEN** 日常交流中用户另行交办一项需要独立调查或制作成果的完整工作
- **THEN** 该工作交给一个执行者负责，日常交流继续由主 Agent 接住；后续相关修改仍由原执行者承接。
- **AND** 已有定时关心和授权内日常安排继续使用，没有新帮助价值时不重复催问或播报。

#### Scenario: 小事形成持续跟进责任
- **WHEN** 主 Agent 接下的小事需要后续跟进或到时处理，确有持久记录需要，但无需独立调查或制作成果
- **THEN** 可以按实际需要记录或更新 Task 并沿用现有有效安排，不要求用户另说创建 Task，也不因为建立 Task 就强行创建 subagent。
- **AND** 普通倾诉、愿望、状态反馈和未经交办的观察内容不会因可记录而自动启动执行。

### Requirement: Task 自动记录已接下的完整执行事项并提供真实概览

#### Scenario: 无需明确要求保存与沿用已有 Task
- **WHEN** Global Agent 或 PA 接下并委派一个完整事项，用户没有明确说创建或保存 Task
- **THEN** 用户仍能在现有 Task 中找到该事项及当前进展，负责人仍是原产品 Agent；已有对应记录则沿用，不创建重复任务。
- **AND** 用户能辨认该事项对应的实际执行，不需要另建工单或把内部执行者配置成长期成员。
- **AND** 图中的父子、依赖或探索关系不被机械转成执行者数量，同一完整事项不因多个相关节点处于进行中而重复执行。

#### Scenario: 查看当前工作与等待
- **WHEN** 用户查看自己的 Global Agent 或 PA 当前承担的事项
- **THEN** 能区分正在推进、正在等待、已交成果及需要自己决定的事项，看到实际等待原因和可用结果，而不必阅读每个执行者的详细轨迹。
- **AND** 负责人或执行者暂时空闲不被当作任务完成；读取失败或执行事实未知时不显示为已确认运行。

#### Scenario: 创建和派发中断或结果未知
- **WHEN** Task 记录与对应执行者的建立、派发或接续只完成了一部分，或结果暂时无法确认
- **THEN** 用户看到真实的待处理或异常情况，后续核实并继续同一次交办；不会漏记已经接下的工作，也不产生重复 Task 或同项执行者。

### Requirement: 后台执行与业务等待按真实情况区分

#### Scenario: 执行者工作时主 Agent 可空闲
- **GIVEN** Task 为 doing，实际执行者正在承担该事项且暂无需主 Agent 处理的新事件
- **WHEN** 主 Agent 完成当前对话轮次
- **THEN** Task 仍保持进行中，实际工作继续；主 Agent 可以空闲或接其他请求，不重复调查、重复派发或仅为重述同一责任反复运行。
- **AND** 用户不会被要求把正常执行改成 waiting、paused 或完成来结束主会话轮次，也不会仅因主会话空闲被告知该事项已停止执行。

#### Scenario: 未完成的执行者意外结束一轮
- **GIVEN** Task 仍是 doing，执行者已经停止这一轮，没有真实等待或运行故障，仍有合法有效下一步，且没有其他正在承担该事项的执行
- **WHEN** 系统处理此次执行结束
- **THEN** 原执行者承接现有成果继续推进，无需用户再次要求继续，也不由主 Agent 重做调查或另开重复执行者。
- **AND** 正在运行、已有有效待处理输入或等待其下级与工具结果的执行者不会被并发重复启动；真实运行故障如实回到 Global 处理，不伪造等待或完成。

#### Scenario: 真正受阻、答复和复查
- **WHEN** 事项确实无可执行下一步并需要等待用户或外部条件
- **THEN** waiting 原因、实际已交付的问题及有效复查安排保持真实，继续遵守已有等待检查要求。
- **WHEN** 相关答复或复查到来且事项仍有效
- **THEN** 由主 Agent 协调原执行者核实并继续，不产生第二份同项执行；单纯等内部执行者工作不制造该业务等待。

### Requirement: 停止、恢复及故障处理作用于对应执行范围

#### Scenario: 单项暂停、撤销或改派
- **GIVEN** A、B 是两个独立执行事项
- **WHEN** 用户暂停、关闭或改派 A，或 A 失去执行资格
- **THEN** A 的实际执行及受影响下级在下一个可中断边界停止发起后续动作，B 继续按其有效要求推进。
- **AND** 原负责人不继续履行已转出的责任，已发生动作按真实结果保留，不宣称已经回滚。

#### Scenario: 明确恢复与运行恢复
- **WHEN** 用户明确恢复某事项，或未被停止的工作从重启、换窗或故障中恢复
- **THEN** 优先承接原执行者、当前要求和已完成成果，不重复从头执行；原执行者不可接续时，明确说明原因与接手安排。
- **AND** 用户停止、关闭、改派和权限撤销继续生效，旧通知、晚到结果和普通定时触发不能恢复已停止工作。

### Requirement: 主 Agent 处理必要决策并完成实际交付

#### Scenario: 决策与最终结果
- **WHEN** 执行者提出确需用户决定的具体问题，或交回可用完整成果
- **THEN** 主 Agent 在正确聊天提出必要问题或交付结果，用户答复回到原执行者；常规实施选择仍由执行者处理。
- **AND** Task 的结果交付回到固定所属聊天，不被最近一个聊天覆盖；内部回传、执行者空闲和状态通知不能代替公开交付。
- **AND** 完成与待确认依据实际成果及既有规则表达，不新增强制用户验收阶段；失败或未知回执不能声称已送达，也不重复已确认交付。

#### Scenario: subagent 始终通过 Global 与用户沟通
- **WHEN** subagent 需要向用户确认、汇报进展、解释阻塞或交付成果
- **THEN** 由 Global 在正确会话与用户沟通，用户的答复通过 Global 交回原执行者；subagent 不直接向用户发消息、另开会话或通过其他工具绕过这一入口。
- **AND** 用户无需管理内部执行者；查看 Task 和轨迹不产生另一个需要用户维护的对话入口。

### Requirement: Global 持续掌握自己负责的 Task 流转

#### Scenario: 执行期间的状态变化和用户问询
- **GIVEN** Global 正在处理别的对话，或暂时空闲
- **WHEN** 其 Task 开始、等待、恢复、提交成果、完成、暂缓、关闭、改派或发生需要处理的执行异常
- **THEN** 相关变化被保留，Global 在后续处理该事项前能取得当前事实；需要对用户沟通的问题、成果和异常不会因执行者空闲或事项结束而漏掉。
- **AND** 用户随后向 Global 询问当前工作或某项状态时，得到与最新任务事实及执行结果一致的回答，不需要自行询问 subagent。

#### Scenario: 普通内部步骤不构成外部打扰
- **WHEN** 执行者只有普通工具步骤、无变化检查或可自行恢复的问题
- **THEN** 它继续工作，Global 不因此逐项介入或对用户逐条播报；真正的流转、必要决定和最终结果仍正常进入 Global 的处理范围。

## 范围与非目标

- 在范围：普通 Global 与 PA 的主从职责、完整事项委派、内部进一步分工、同事项后续接续、日常小事直接处理；现有 Task 对已接事项的自动记录、概览、执行归属、对应执行者续推、等待、控制、恢复和交付的适配，以及 Global 对 Task 流转的持续知情与唯一用户沟通入口。
- 在范围：统一受影响的默认指导与相关随包工作方法，避免主从职责与持续工作指引相互冲突；保留用户已有自定义配置，设计须明确已有 Global/PA 会话怎样采用新分工。
- 非目标：新增 Ticket/Assignment 工单体系、第二套执行循环、按任务图依赖自动调度、为每条日常消息或每个下级执行者机械创建 Task、把临时 subagent 变成 IM 长期成员、复刻参考仓的 GitHub 事件订阅或全部 router 工具裁剪。
- 非目标：改变 SingleThread 的工作方式、Task 的既有业务状态和图结构语义；放开子 Agent 的产品聊天或主人代发权限；扩大原生委派深度、工具权限或用户授权。
- 本文收口需求；接下事项时 Task 与执行者如何联动、自动续推的判定、看板信息组织、Global 获取流转事实的时机与可靠性、模型可见指引和控制恢复链路的具体实现交给设计阶段。当前未实施、未部署，不能把本文件作为运行能力证明。
