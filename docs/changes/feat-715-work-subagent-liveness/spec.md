# feat-715: Work 页显示当前正在工作的一级 subagent

## Relations

- Related: #468

本 unit 只交付 Web。iOS 客户端 Work 页的同类能力随 issue #468 的 iOS 序列另行安排，不在本 unit 验收；理由与范围见「范围与非目标」。

## 原始需求

用户原话（保留）：

> 我觉得我们前端应在 work 页某个地方应该看得到当前到底有多少个一级 subagent 正在工作。否则现在只能看到主 agent 的工作，用户很迷茫，到底是不是在干活啊。

用户对拆分与实现方式的授权（原话，保留）：

> ios接下来的安排你自己推进

Agent 解读：这条授权用于「切多大、怎么拆」的判断，即由 Agent 决定本 unit 的范围与实施方式，不再逐条回问。它不追加本 unit 之外的能力授权——不表示允许改执行运行时、不表示 iOS 与 Web 必须同时做，也不改变下面已收口的口径。

## 澄清记录

- Q1: 「一级 subagent」的边界是什么？
  A: 已定口径：当前主 Agent 的直属子执行，即挂在当前主会话下、作为普通 subagent 注册的子执行。workflow 的子执行、cron 会话、已退休主会话下的历史执行都不计入。这与现行 [`agent-capabilities`](../../../specs/gateway/agent-capabilities.md) 中「一级执行者 = depth 1」的口径一致。
- Q2: 什么算「正在工作」？等待授权算不算？
  A: 已定口径：运行中与等待授权都算「在干活」，但必须分开显示——等待授权时 Agent 并没有推进，用户要能一眼看出是卡在等自己。无法确认的状态单列「状态未知」，不得并入空闲，也不得并入 0。
- Q3: 做到什么程度——只给数字，还是能看每一条？
  A: 已定口径：数字 + 可辨认的条目（标识与已工作时长），不做「它在做什么」的自然语言摘要。
- Q4: iOS 与跨端一致怎么处理？
  A: 已定口径：本 unit 只做 Web；iOS 归入 issue #468 的 iOS 序列另行安排。
- Q5: 是否需要改执行运行时或新增 RPC？
  A: 已定口径：不改运行时（DSH）、不新增 RPC。若实施中发现现有公开 API 确实不足以支撑，暂停并回报后再定。
- Q6: 以上口径是否与用户逐条确认过？
  A: 否。用户已把拆分与实现方式授权给 Agent；以上五条由 Agent 依据已有静态调研与现行 spec 收口，未再向用户逐条确认，不声称用户已逐条同意。

## 现状与证据

**为什么今天只看得到主 Agent。** 一级子执行的存在与它的轮次起止，整条链路上其实都被持久记录了，缺的是出口：

- IM 的工作视图只聚合主会话。`apps/im-server/src/work-records.ts` 的 `view()` 取「未退休的 global main」为主会话，只按主会话取轮次，主执行状态取自主会话最新一轮，`completed/failed/interrupted` 归为「空闲」；`other_executions` 只带身份字段，不带任何运行状态（`work-records.ts:469-508`，聚合出口在 `:490-505`）。外层 `apps/im-server/src/work.ts:88-96` 的离线降级也只作用于主执行。
- 前端只渲染主 Agent。`src/IM/frontend/src/features/settings/agents/agent-work-panel.tsx` 工具栏只有「主 Agent · 状态」一处运行态（`:168`）；关联执行是页面底部默认折叠的「关联执行 · N」，展开后只有名称与会话标识，没有状态（`:188`）。离线下把 `running/waiting_permission` 渲染成「状态未知」的范式已经存在，可直接复用。
- 单个子执行的状态今天查得到——点进某个关联执行时会读取该会话的轮次，返回里带状态。缺的不是可达性，而是主视图的一次性聚合：用户必须先点进去、逐个点，才知道有没有人在干活。
- 计数陷阱：`other_executions` 同时含 cron 会话、workflow 子执行与已退休主会话，直接拿它的长度当「N 个 subagent 在干活」是错的。

**运行时不需要改。** DSH 公开能力里已经有直属子执行列举、粗粒度活动态、由事件推导的开放轮次与 `agent/status`。本 unit 的缺口在下游产品侧，不在运行时。

**实时精度的上限（本 unit 不能假设它更高）。** 运行时对子执行也会发状态通知，但该通知不带根会话标识，PA 找不到对应绑定就丢弃（`packages/dsh-integration/src/index.ts` 的 `session.status` 通知与 `packages/personal-assistant/src/global-agent.ts` 的通知入口）。因此 IM 侧的子执行状态是「最后一个已同步事件」推导的结果，不是租约；「多久没动静」只能靠时间戳表达，不能靠实时心跳。

**必须同修的缺口：残留的运行中。** 服务端重启时会把残留的 `running/waiting_permission` 降级为未知（`work-records.ts:10-17`），但这覆盖不了「节点在轮次中途崩溃、没有留下结束记录」的情形——那会留下一个永真的运行中。主 Agent 今天已有同类缺口；一旦把「N 个在跑」显示给用户，这个缺口就从内部瑕疵变成用户看到的假状态，所以它是本 unit 的验收项，不是可选项。

**证据等级。** 以上均为对 `main`（`005a36057`）的**静态代码核对**：未启动 node / im-server，未运行前端，未做运行时复现，也没有真实并行派遣下的观测记录。据此仍属待验证、不能当既定事实的部分：

1. 真实并行派遣时，每个子执行是否都在 IM 侧落到「运行中」（取决于 PA 的同步时序与补传）；
2. 节点崩溃后残留运行中的实际发生率与形态（是永真，还是很快被后续事件覆盖）；
3. 节点离线 / 同步未知的降级扩展到子执行后的端到端表现；
4. 子执行起止触发前端刷新的实际时延。

本次静态调研的工作稿在 `/tmp/work-subagent-visibility-analysis.md`（临时路径，随主机重启消失，不入库）；上面每条结论都标注了仓库内的可复核位置，设计阶段应直接回到代码核对，不以工作稿替代。该工作稿还记录了两条被本次范围排除的精度方案：给运行时补由事件推导的开放轮次、给状态通知补根会话标识以做实时在场——两者都留待以后，见「范围与非目标」。

## 用户场景

用户打开某个全局 Agent 的 Work 页，最想知道的是「它现在到底在不在干活」。今天这一页只回答了一半：主 Agent 空闲、没有新轮次，页面就安静得像停了；实际上主 Agent 已经把三件事拆给三个子执行，它们正在跑，其中一个还卡在等用户授权。

目标状态下，用户在这一页直接读到「当前有 3 个子执行在工作」，旁边分开写着「2 个在运行 · 1 个等待授权」。展开能看见三条：谁是谁、各自从几点开始、已经跑了多久。他因此知道现在该做的事是去处理那个授权，而不是怀疑 Agent 掉线了。

过一会儿其中一个结束，数字自己变成 2，那条不再显示为运行中，不需要他手动刷新；再过一会儿全部结束，页面明确说「当前没有子执行在工作」，同时主 Agent 自己的状态照常显示——空不等于坏。他点进任意一条仍能回看那次的完整轨迹，与今天的行为一致。

另一种情况更重要：他把电脑合上了。回到页面时，页面说节点离线、状态未知，**不会**把离线前那个「2 个在运行」继续当作现状，也**不会**因为读不到就说「0 个」。如果节点是在某个子执行跑到一半时崩溃的，重连后那条不该继续显示为运行中——它会变成未知或已中断，页面上不会出现一个永远在转的假状态，也不会替它猜一个「已完成」。

还有一种小情况：某个子执行的明细此刻读不出来（比如权限或数据暂不可用）。他在总量里仍然看得到这一条并知道它的状态，只是点进去会看到明细暂不可读，而不是它凭空少了一个。

也要避免另一种误读：子 Agent 已经做完、会话仍驻留着，随时可以再被唤起——那不是「在干活」。同一项工作的先后两次唤起也不该被算成两个人。而如果页面本身读不到记录，它应该说读取失败，而不是淡定地显示「0 个」；换作一位没有该 Agent 访问资格的同事打开这个页面，他应该和今天一样被拒绝，看不到这份新数字。

## 验收标准

### Requirement: Work 页直接看到当前正在工作的一级子执行数量与条目

#### Scenario: 主 Agent 派发了多个子执行
- **GIVEN** 主 Agent 当前有三个直属子执行在运行
- **WHEN** 有该 Agent 空间访问权的用户打开 Work 页的工作记录视图
- **THEN** 不展开任何折叠区就能看到「当前有 3 个子执行在工作」这类可读结果
- **AND** 可以展开或平铺看到这三次执行各自的条目，与主 Agent 的轮次清楚区分

#### Scenario: 没有子执行在工作
- **GIVEN** 主 Agent 没有正在工作的直属子执行，且页面没有节点离线或正在补齐的提示
- **WHEN** 用户查看 Work 页
- **THEN** 明确显示当前没有子执行在工作，不是留白，也不只给一个孤立的数字 0
- **AND** 主 Agent 自身的运行状态照常显示

#### Scenario: 只有非直属执行在活动
- **GIVEN** 主 Agent 正在跑一个 workflow 且其子执行在活动，或有一个 cron 会话在运行
- **WHEN** 用户查看这一数量与条目
- **THEN** 这些执行不计入「正在工作的一级子执行」
- **AND** workflow 与 cron 的既有呈现不受影响

### Requirement: 运行中、等待授权与状态未知分开呈现

#### Scenario: 三个子执行里有一个在等授权
- **GIVEN** 两个直属子执行在运行，一个停在等待用户授权
- **WHEN** 用户查看 Work 页
- **THEN** 能看到在工作的总数，并能分辨其中「运行中」与「等待授权」各是几个
- **AND** 等待授权的那一项可被明确指认，用户知道现在卡在等自己

#### Scenario: 状态无法确认
- **GIVEN** 节点离线，或页面提示正在补齐 / 最新进度尚未确认
- **WHEN** 用户查看这一数量与条目
- **THEN** 状态显示为「状态未知」，既不显示成运行中，也不显示成空闲或 0
- **AND** 页面同时说明原因（节点离线 / 正在补齐 / 最新进度尚未确认）

#### Scenario: 单个子执行明细不可读
- **GIVEN** 用户在条目里能看到某个子执行，但它的明细当前不可读取
- **WHEN** 用户查看这一项
- **THEN** 该项仍按已确认的记录显示状态，并标明明细暂不可读
- **AND** 不因为读不到明细就把它算作不存在或已结束

### Requirement: 每个计入的子执行可辨认身份与已工作时长

#### Scenario: 辨认是哪一个、已经跑了多久
- **GIVEN** 两个直属子执行在运行
- **WHEN** 用户查看条目
- **THEN** 每个条目有可辨认的标识（有名称时用名称，没有名称时有可区分的标识）
- **AND** 能看到它开始工作的时间，或据此得出的已工作时长
- **AND** 不出现倒计时、剩余时间或伪造的进度

#### Scenario: 同一子会话的多次唤起
- **GIVEN** 同一个子会话先后被唤起两次，两次都已结束，当前没有在运行
- **WHEN** 用户查看「正在工作的一级子执行」
- **THEN** 历史唤起不出现在在跑的数量里；若仍在列表中保留，明确标为已结束
- **AND** 驻留但空闲、可再次续接的会话不算作在干活

### Requirement: 子执行结束后数量与条目按真实结束事实更新

#### Scenario: 其中一个正常完成
- **GIVEN** 三个直属子执行在运行
- **WHEN** 其中一个正常结束
- **THEN** 数量变为 2，该条目不再显示为运行中
- **AND** 用户不需要手动刷新才能看到变化；刷新后与变化前一致

#### Scenario: 子执行失败、取消或被中断
- **GIVEN** 一个直属子执行在运行
- **WHEN** 它以失败、取消或中断结束
- **THEN** 该条目不再计入在跑数量，并显示为已结束而不是已完成
- **AND** 主 Agent 的轮次、结果与既有统计不因此被改写

### Requirement: 连接中断、崩溃或读取不可用时如实降级，不长期显示假的运行状态

#### Scenario: 节点在子执行轮次中途崩溃
- **GIVEN** 一个直属子执行的轮次开始后节点崩溃，没有留下结束记录
- **WHEN** 节点重新连上，用户刷新或页面自动更新
- **THEN** 该项不再显示为运行中，而是状态未知或已中断
- **AND** 不显示为已完成，也不推测它的结果或耗时

#### Scenario: 节点离线期间
- **GIVEN** 节点在某个子执行进行中离线
- **WHEN** 用户查看 Work 页
- **THEN** 子执行状态整体标为未知并说明节点离线，不把离线前的旧数字当作现状
- **AND** 已保存的历史轮次与轨迹仍可回看

#### Scenario: 未知状态被后续真实记录纠正
- **GIVEN** 某项曾被标为状态未知
- **WHEN** 之后收到它真实的结束或真实的继续记录
- **THEN** 显示回到真实状态，未知标记不粘住
- **AND** 同一次执行不出现两条互相矛盾的结论

#### Scenario: 工作视图读取失败
- **GIVEN** 页面读取工作记录失败或超时
- **WHEN** 用户查看这一数量与条目
- **THEN** 显示读取失败与重试入口，不把 0 个或空列表当作已确认的事实
- **AND** 重试成功后按真实记录显示

### Requirement: 主 Agent 状态与既有 Work 能力保持原样

#### Scenario: 数量展示不覆盖主执行状态
- **GIVEN** 主 Agent 正在运行且有两个子执行在运行
- **WHEN** 用户查看 Work 页
- **THEN** 主 Agent 的状态仍按真实主执行显示，不被子执行状态顶替或合并成一个数
- **AND** 轮次明细、轮次统计、原生轨迹、任务图与 workflow 的既有呈现与之前一致

#### Scenario: 没有访问资格的用户
- **GIVEN** 用户对该 Agent 没有空间访问资格
- **WHEN** 他尝试查看 Work 页
- **THEN** 仍按现有权限被拒绝，新展示不提供绕过入口
- **AND** 新展示不带来发送指令、审批、取消或配置能力

## 范围与非目标

预期落在 `apps/im-server` 与 `src/IM/frontend` 两个包、约 1 个 milestone；具体切片由 design 决定。

- **在范围**：
  1. Web 内置 IM 的 Work 页「工作记录」视图：一级子执行的数量、状态三分（运行中 / 等待授权 / 未知）、条目身份与已工作时长、结束后的更新、空态、降级提示与读取失败提示。
  2. IM 对外工作视图需要能表达一级子执行的当前状态（今天只表达主执行）。「一级」的判定、未知与降级的判定在服务端收口，不把「什么叫在跑」复制到 UI。
  3. 节点崩溃 / 连接中断后残留的「运行中」必须降级。主 Agent 的同类残留与本项同源：是否在同一次改动里一并收口由 design 判断，但两个入口不得给出互相矛盾的结论。
  4. 相应 canonical spec 的 delta（见下节），归并前由独立一致性核对确认。
  5. 必要的中文文案与覆盖上述场景的测试。

- **非目标**：
  1. iOS 客户端不实现同类展示，归入 issue #468 的 iOS 序列；iOS 现有 Work 页行为不得被本 unit 破坏，也不要求两端同帧一致。
  2. 不改执行运行时（DSH）、不改 `dsh-integration` 对外的契约形状、不新增 RPC；若实施中发现现有公开能力不足，暂停并回报。
  3. 不把 workflow 子执行、cron 会话、已退休主会话的历史执行计入「一级子执行」。
  4. 不做「它在做什么」的自然语言摘要，不用模型生成状态描述。
  5. 不新增权限、不改审计；不新开节点到 IM 的独立实时状态 / 在场通道，也不在本次补运行时的开放轮次精度。
  6. 不改任务图语义、不改 workflow 呈现、不动聊天消息的投递与展示。
  7. 不做通知、推送或告警（例如「子执行卡住多久就提醒」），是否要做另行判断。
