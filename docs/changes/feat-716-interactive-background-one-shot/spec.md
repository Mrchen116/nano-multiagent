# feat-716: 交互卡片私人背景改为一次性携带

## Relations

- Related: feat-617（交互回复的原始设计，本 unit 修正其"会话内长期背景缓存"语义）

## 原始需求

> 以下为发起本次变更的产品负责人经派发方转述的已确认规则，逐条保留，不改写语义。原始对话在父对话中，本文件按其转述记录。

1. 用户触碰/编辑一张交互卡片后，该卡成为**唯一的待发背景**（只保留最近一张）。
2. **下一条出站用户消息**携带它；携带即**消费**。再下一条不带（除非用户又动了卡）。
3. 触碰另一张卡会**替换**待发背景（永不并存两张）。
4. 在以下情况清除待发背景：该卡被更新的卡取代、该卡变为只读、切换会话、会话是群聊（私人卡片背景永不进入群聊）。
5. 卡片内的显式提交（"继续"/"提交"）走既有的 `interaction_reply` 通道，该通道本身已携带这次提交；两条通道不得对同一张卡重复注入。
6. 失效只影响"是否携带"，不影响可观测性：注入背景在 Work 详情里按现状可见、可查原文；本 unit 不改变任何呈现。

负责人就"为什么"给出的判断（转述要点）：当前实现把背景当成"会话内长期存在的最近三张卡"，每条消息都重复注入同一批旧卡——每条消息固定多出约数百至一千 token；模型无法判断哪张卡才是当前背景。

## 现状与依据

以下均在 `origin/main`（`005a36057`）上逐条核对过代码。行号是本次核对的实际行号；括注的"旧引用"是派发前调查里与本轮不一致的行号，以本文为准。

**为什么每条消息都带同一批旧卡**

1. Web 把"被登记过的卡片"按会话长期缓存：`src/IM/frontend/src/features/chat/components/message-pane.tsx:287` 的 `backgrounds` 是内存级 `Record<会话, Record<消息, 选择>>`，唯一写入点是 `:296-304` 的 `chooseInteraction`，没有任何删除或过期路径。发送时 `:752-759` 对"当前已加载的消息"重新筛查（过滤掉只读/被取代/被替换的卡），按 `editedAt` 倒序、同值再按列表位置倒序取前 3 条。所以行为是"每次发送都重算最近 3 张"，不存在"已经带过"的判据。
2. Web 还会登记用户从未改过的卡：`src/IM/frontend/src/features/chat/interactive/interactive-card.tsx:89`，卡片挂载读到草稿后**无条件** `select(draft.state, lastEditedAt.current)`；没有草稿时 `draft.state` 是 `{}`、`lastEditedAt` 是 `0`（`:88`）。`:199-202` 在解析完成后又登记一次。（调查只提到 `:89`，`:199-202` 是本次补充的第二处登记点。）
3. 发送成功后只清"发送尝试"，不清背景：`message-pane.tsx:783-786`（`clearSendAttempt`）。刷新页面才会重置，因为 `backgrounds` 只在内存里。
4. iOS 同样"渲染即登记"：`src/IM/ios/NanoIM/Features/Chat/InteractiveRuntime.swift` 里 `select()`（唯一写 `ChatStore.interactionSelections` 的地方）有四个调用点——`:71`、`:82`（两条渲染路径的 `load()`）、`:100`（未触碰的渲染器状态推送）、`:286`（`changed()`）；没有草稿时 `editedAt` 为 `0`，有草稿时取服务端 `updated_at`，真实输入时取客户端 `Date()`。发送时同样"取最近 3 条且永不消费"：`ChatStore.swift:414-424`；只在卡片转只读（`InteractiveRuntime.swift:150-154`）和删除会话（`ChatStore.swift:497`）时清缓存。所以 iOS 表现为"把最近渲染过的 3 张卡附到我之后发出的每一条消息上，直到 App 重启"。
5. 服务端只做规范化，不判断该不该带：`apps/im-server/src/messaging.ts:512` → `apps/im-server/src/interactions.ts:59-70`（最多 3 条、按已保存 source 校验 state，**不**校验只读/被取代），再按"卡片作者"只投给该作者（`messaging.ts:609`，旧引用 616）。群聊带该字段直接 422（`messaging.ts:498`，旧引用 505）。

**注入文本如何进入模型输入（现状，本 unit 不改）**

6. PA 把背景**拼进模型输入文本**：`packages/product-contracts/src/interactive.ts:35` 在原话后追加 `\n\n[Private interactive background captured when this message was sent. …]` + JSON；该函数用于 `packages/personal-assistant/src/single-thread.ts:152` 与 `packages/personal-assistant/src/inbox.ts:347`。回复通道在同一函数的 `:31-34`，与背景块是两段独立追加——用户原话完整保留。
7. Work → 原生轨迹把这条输入按原生事实展示：`packages/trajectory-ui/src/client/trajectory-message-definitions.ts:157-189` 把人类 `user/message` 生成单条 `kind:'user'` 记录（`content` 原样带入），表格按 markdown 渲染（`packages/trajectory-ui/src/client/TrajectoryTable.tsx:1021`）；工作记录视图本来就不投影人类 `user/message`（`packages/personal-assistant/src/work-projection.ts:27-34`）。**注入背景在原生轨迹里可见是预期行为，也是本 unit 依赖的核查手段**，不是缺陷。

**重试与时间**

8. 请求指纹包含交互背景：`apps/im-server/src/message-attempts.ts:15-16`；同一键不同内容 409（`:32`）。Web 重试复用已冻结的 attempt（`message-pane.tsx:773-777`，指纹复用见 `send-attempt-store.ts:74-90`）；iOS 重试复用 `pending` 里的冻结草稿（`ChatStore.swift:326-338`）。
9. 卡片改动是 500ms 防抖保存（Web `interactive-card.tsx:204-212`；iOS `InteractiveRuntime.swift:284-289`），而发送路径不等待这次保存 —— 用户"拖完滑杆立刻发送"时，服务端可能还没收到这次改动。

**根因**

产品规则缺少"消费"语义。历史设计把背景定义成"屏幕上最近几张卡的样子"的会话级长期上下文，并明确写"成功发送不清除背景缓存"（`docs/changes/archive/feat-617-agent-interactive-responses/design.md:143`、`:145`），却没有任何"这条消息之后它就不该再带"的判据；两端各自缓存、服务端只转发，于是每条消息都复现同一批旧卡。同一份历史设计写的"不得强制解释卡片、覆盖手写正文"（`:155`）约束的是模型行为与用户原话，现状的字符串拼接已经满足（用户原话完整、背景是独立标记的数据块），本 unit 不改这段拼接。

**成本量级（估算，非实测）**

`interactive.ts:35` 的固定说明约 300 字符，加 3 条 context 的 JSON（`source_summary` 上游截断 160 字符，`interactions.ts:67`）；合计约 700–1,000 token / 条消息量级。这部分留在 DSH 会话历史里，每轮都在上下文中。

## 用户场景

**小周问一个跟进问题。** 小周在私聊里收到 Agent 的会议安排卡，把周三那场改成周四、又勾掉一个参会人，然后直接打字："这样还能排得下吗？" Agent 的回答显然基于周四那版安排。小周接着问"那谁负责订场地？"——这次 Agent 不会再收到一遍周四的安排，只按这句话回答；如果它需要那张卡，会自己回看会话。

**小周改了另一张卡。** 小周先去调预算表那张卡，又转头调会议卡，然后发一条消息。Agent 只看到会议卡（最近动的那张），不会同时收到预算表。小周不需要理解"带了几张"，他只需要知道"我刚动的那张会被看到"。

**小周只是看了一眼。** 小周打开会话、滚过几张卡、刷新页面、切到别的会话又回来，什么都没改，然后发消息。这条消息不该携带任何卡片内容——今天 Web 会把从未动过的卡（默认状态）当作背景带上。

**小周在群里。** 群里有人发了一张投票卡，小周勾了两个选项但没提交，然后发了一句普通的话。群里其他人和所有 Agent 都看不到他勾了什么；只有他明确点"提交"时，那次选择才作为提交消息公开。

**小周网络断了。** 小周发完消息界面没确认。他重试，最后只有一条消息、一次背景注入，不是两条，也没有变成"没有背景"的另一条。

**小周换了一台设备。** 他在手机上调完卡，回到电脑上发消息：电脑这边的消息带上了手机上那次改动（待发背景跟着"这个人在这个会话里的状态"走，不跟着某个客户端走）。

## 验收标准

以下每条都在产品上可观察。观察点主要是：消息在 Work → 原生轨迹里对应的模型输入、会话里其他人/其他 Agent 看到的公开消息、以及两端客户端的实际行为。**Web 与 iOS 必须对同一旅程给出相同结果**（见最后一节 Requirement「Web 与 iOS 行为一致」）。

### Requirement: 待发背景只有一张，且只来自用户自己的改动

#### Scenario: 改动一张卡后发消息
- **GIVEN** 私聊里已有一张可交互的卡片，用户此前没有改动过它
- **WHEN** 用户改变这张卡的一个字段或选项，随后发出一条普通文字消息
- **THEN** 这条消息的模型输入只包含**一条**该卡的背景，附在用户原话之后，带该卡来源、字段、选择与捕获时间
- **AND** 用户自己的文字完整保留，不被改写或摘要

#### Scenario: 连续改动两张卡
- **WHEN** 用户先改动卡片 A、不发送，再改动卡片 B，然后发出一条消息
- **THEN** 这条消息只携带 B
- **AND** A 不出现在该消息的任何注入内容里；之后的消息也不会补带 A

#### Scenario: 只渲染、不改动
- **WHEN** 用户打开或刷新会话、滚动经过若干卡片、切换会话后再回来，期间没有改变任何卡片内容，然后发出消息
- **THEN** 该消息不携带任何卡片背景
- **AND** Work 原生轨迹里这条输入只有用户原话（以及既有的时间等上下文），没有"私人交互背景"块

#### Scenario: 同一张卡再改一次
- **WHEN** 用户改动卡片 A 的一个字段，不发送，又改动 A 的另一个字段，然后发出一条消息
- **THEN** 该消息只携带 A，且内容是最后一次改动后的完整状态（不是两次各自一条）

### Requirement: 携带一次即消费

#### Scenario: 连续两条消息
- **WHEN** 用户改动卡片后发出消息 1，随后不改动任何卡片直接发出消息 2
- **THEN** 消息 1 的模型输入含该卡背景
- **AND** 消息 2 的模型输入不含任何卡片背景；再发第三条同样不含

#### Scenario: 改动后刷新或重开
- **GIVEN** 用户改动卡片后没有发送
- **WHEN** 用户刷新页面（Web）或重启 App（iOS），再次打开同一会话并发出消息
- **THEN** 该消息携带这次改动
- **AND** 该消息之后再发的消息不携带

#### Scenario: 换设备继续
- **GIVEN** 同一账号在另一台设备上登录同一私聊
- **WHEN** 用户在设备甲改动卡片但不发送，在设备乙（同一会话）发出消息
- **THEN** 设备乙这条消息携带设备甲的那次改动
- **AND** 设备乙之后再发的消息不携带

### Requirement: 失效条件只清除"携带"，不制造残影

#### Scenario: 卡片被更新版本取代
- **WHEN** 用户改动卡片后，Agent 发来同一张卡的更新版本，用户随后发出消息
- **THEN** 该消息不携带旧版本的背景

#### Scenario: 卡片变为只读
- **WHEN** 用户改动卡片后，该卡变为只读（历史/fork 副本或被取代），用户随后发出消息
- **THEN** 该消息不携带该卡背景
- **AND** 该卡在界面上仍可阅读，只是不再接受新的业务动作

#### Scenario: 改动后切换会话
- **WHEN** 用户在会话 A 改动卡片，切到会话 B，再回到会话 A 发出消息
- **THEN** 这条消息不携带该背景
- **AND** 清除由做过这次改动的那一端执行：另一台设备在同一会话打开又切走，不清除这台设备上尚未发送的改动（与「换设备继续」一致，优先级见 design §D4）

#### Scenario: 群聊永不携带私人背景
- **GIVEN** 会话是群聊
- **WHEN** 用户改动群内卡片后发出普通文字消息
- **THEN** 该消息不携带任何私人卡片背景，群内其他成员与其他 Agent 的模型输入里都没有它
- **AND** 只有明确提交动作才让本人当次选择以公开提交消息的形式出现

#### Scenario: 私聊背景不跨会话
- **WHEN** 用户在私聊 A 改动卡片，随后在私聊 B（同一 Agent 或其他 Agent）发出消息
- **THEN** 私聊 B 的消息不携带私聊 A 的卡片背景

### Requirement: 显式提交与私人背景是两条互不重复的通道

#### Scenario: 卡片内明确提交
- **WHEN** 用户改动卡片后点击卡内的"继续"/"提交"（或触发卡片发出的继续请求）
- **THEN** 产生的消息携带这次提交的选择（与今天一致的显式提交内容），且**不含**"私人交互背景"块
- **AND** 该卡在之后的消息里不再作为背景重复出现

#### Scenario: 提交与另一张卡的改动
- **GIVEN** 用户改动过卡片 A 但未发送
- **WHEN** 用户提交卡片 B
- **THEN** B 的提交消息只含 B 的提交内容
- **AND** A 的待发背景在这一步被消费：之后发消息不再携带 A

### Requirement: 失败与重试不重复消费、不改变已发出的内容

#### Scenario: 结果未知后重试
- **GIVEN** 用户发出携带背景的消息，界面未收到确认
- **WHEN** 用户重试，或刷新/重启后恢复这次发送
- **THEN** 最终只有一条消息、一次背景注入
- **AND** 重试后的消息内容与该次发送的原始内容一致（含当时携带的背景），不会变成"无背景"的另一条

#### Scenario: 重试成功后继续对话
- **WHEN** 上述重试成功，用户随后发出新消息
- **THEN** 新消息不携带那张已消费的卡

#### Scenario: 改动后立刻发送
- **WHEN** 用户改动卡片后立即发送（早于客户端把改动保存到后台）
- **THEN** 该消息仍然携带这次改动，不出现"刚改完却不带"的结果

### Requirement: Web 与 iOS 行为一致

#### Scenario: 同一旅程两端同结果
- **WHEN** 在 Web 与 iOS 上分别执行"改动一张卡 → 发送 → 再发送"
- **THEN** 两端都只在第一条消息携带该卡背景，第二条都不携带
- **AND** "只渲染不改动"、"改两张卡"、"切换会话"、"群聊"在两端得到相同的携带/不携带结论

## 范围校准（design 阶段确认）

本节记录设计阶段经派发方转达的负责人校准，只收敛范围，不改变上文已确认的携带/消费/失效规则。

- **Work 核查视图是现状，不是本 unit 的改动项。** 负责人明确：注入背景在 Work → 原生轨迹里可见、可查原文**本来就该如此**（可观测性要求），本 unit 要修的只是"每条消息都带同一批旧卡"。因此原 Requirement「Work 详情把注入背景与用户原话分开显示」及其三个 Scenario 已从本文件移除；其中属于数据边界的部分（私人背景不进入其他成员/其他 Agent 的视图、不进入公开消息）保留为「不得回归的既有行为」第 1 条。原始需求第 6 条按其字面执行：失效只影响"是否携带"，可观测性按现状保留，**本 unit 不改任何呈现**。
- **"Web 与 iOS 行为一致"的覆盖范围。** 一致的是**携带 / 消费 / 失效**这套语义（两端同结论），不含工作核查界面的呈现——呈现侧本 unit 不产生任何改动。可核实的现状是：iOS 没有轨迹／模型输入查看器（`grep -ril trajectory src/IM/ios/NanoIM` 为空），其 Work 页是 `src/IM/ios/NanoIM/Features/Agents/AgentWorkView.swift` 的原生摘要列表，从未展示模型输入；轨迹是 Web iframe（`agent-trajectory.tsx` → `packages/dsh-trajectory-viewer/dist`）。这里只说明"为什么没有 iOS 侧工作"，不推出"所以 Web 要改"。
- **前向约束。** 将来若 iOS 做出模型输入/轨迹查看器，须与 Web 现状一致地让注入背景可见、可查原文。

## 范围与非目标

**在范围**

- 私聊中"哪张卡的私人背景会被带进模型输入"的规则：单张、一次性消费、上述失效条件；
- Web 与原生 iOS 两个客户端的发送与失效行为；
- 中心服务对"该不该带"的权威判定（含对既有客户端仍发送背景数据的兼容处理）；
- 用户可见的抑制：卡片只是被渲染/恢复不再产生背景；
- 发送防抖与重试路径，使"刚改完立刻发"和"结果未知重发"都不丢、不重复、不复活过期背景。

**非目标**

- 不扩展交互卡片本身的渲染、组件、动作或查询能力；
- 不改 Work → 原生轨迹对注入背景的呈现：注入内容在模型输入里可见、可查原文是预期行为（见「范围校准（design 阶段确认）」）；本 unit 不新增、不改造、不拆分会话核查界面；
- 不新增用户可见的"附带开关""选择横条"或"Detach"（`docs/specs/im/web-chat-ux.md:629` 的既有契约保持）；
- 不改卡片内显式提交的消息语义、幂等键与冲突处理；
- 不改私人草稿的保存、CAS 冲突与只读规则；
- 不改消息投递、relay、离线重放与未读的既有语义（除背景来源）；
- 不改写历史会话里已经注入的文本（那是历史输入的真实记录）；
- 不为待发背景引入时间过期（TTL）——它不在已确认的清除条件里，属于新的产品规则；
- 不把背景变成公开字段、消息正文或对其他成员可见的内容；
- 不改动"背景只交付卡片作者 Agent"的路由与私密边界。

## 不得回归的既有行为

1. 私聊背景只交付卡片作者 Agent，不进入公开消息、不进入其他成员或其他 Agent 的视图；只有该 Agent 的 Work 核查视图能看到它进入过模型输入（`docs/specs/im/conversations-messages.md:577-579`；`messaging.ts:609`）。
2. 群聊普通文字不携带；越权客户端在群聊带背景仍被拒绝；群聊只有明确提交才共享快照（`messaging.ts:498`；`conversations-messages.md:569`、`:579`）。
3. 同一幂等键 + 同一内容返回原消息与原投递，不重复入队；同键不同内容仍 409（`messaging.ts:509-510`；`message-attempts.ts:32`；`conversations-messages.md:583-585`、`:600-602`）。
4. 显式提交的消息内容、提交记录、草稿 revision 递增与 `submission_message_id` 语义不变（`interactions.ts:146-151`）。
5. 私人草稿的 CAS 冲突、跨设备冲突提示、只读卡片不接受提交（`interactions.ts:98-112`、`:141-142`）。
6. 卡片渲染失败、加载失败、保存失败、未知结果重试、ComposeMessage 采用等路径的现有反馈不变（`interactive-card.tsx:67-79`、`:184-228`）。
7. 模型输入中背景仍然是"数据、非指令、非授权"，用户原话完整（现有断言见 `packages/personal-assistant/tests/interactive-replies.test.ts:87-101`）。
8. 原生轨迹"按原生事实显示、保留原文"的检查能力不变（`docs/specs/im/agent-work.md:80-84`）——本 unit 完全不改模型输入文本，也不改它的任何呈现。
9. 工作记录视图的投影规则不变：人类消息本来就不投影（`work-projection.ts:27-34`）。
10. 消息列表、时间线、未读、流式确认、附件与引用校验等既有展示与行为不变。

## 交给 design 的决策点（不改变上文验收）

1. **待发背景由谁判定。** 验收里的「改动后刷新或重开」「换设备继续」与「只渲染、不改动」三条把"同一账号同一会话内的待发状态必须跨客户端一致"写成了验收条件，因此实现需要中心侧的权威判定，或与之等价的跨端一致性方案。推荐：由中心从"该用户在该会话的最后一张私人草稿编辑时间"与"该用户在该会话的最后一条本人消息"的关系派生待发状态，客户端不再自行决定；需要核实的细节是：这条判据对"用户自己发的消息"的界定（PA 代表用户发出的消息，`apps/im-server/src/personal-actions.ts:241-246`，也以用户身份落为 `user` 类型消息，会把待发状态消费掉）、外部渠道同步进来的本人消息（`messaging.ts:396`）以及消息时间与草稿时间是否同一时钟口径（两者当前都是服务端 ISO 字符串：`context.ts:27`、`interactions.ts:108`）。
2. **「改动后切换会话」如何落地。** 这条无法从"草稿时间 vs 消息时间"自然派生（切换会话不产生消息），需要显式信号或等价的记录方式。若设计判断显式信号不可靠，必须回到负责人确认把该条收窄为"背景按会话隔离、切换只保证不串到别的会话"，不能静默改语义。
3. **旧客户端的兼容路径。** 推荐：中心以自己派生的结果为准，继续接受但不再采信客户端送来的背景数据；旧版 Web/iOS 因此立即收敛到正确行为（可能仍会在"改动后切换会话"这一条上与新版不同，直到客户端更新）。需要明确的是：请求指纹是否继续包含客户端送来的背景数据（影响跨版本重试的 409 判定），以及新旧客户端混用时的验收口径。
4. **"触碰"的判定落点。** 现有两端已有"真实输入事件"信号（Web `interactive-card.tsx:184-192` 的捕获处理器决定是否保存草稿；iOS 只在 `changed()` 里登记）。推荐复用该信号并去掉"挂载/解析即登记"（`interactive-card.tsx:89`、`:199-202`），而不是新造一套。
5. **捕获时间与来源摘要的取值。** 建议改由中心用草稿的保存时间填充（修掉客户端 `Date.now()` 与 `date.parse(draft.updated_at)` 混用两套时钟的问题，`interactive-card.tsx:63-66`、`:88`；`InteractiveRuntime.swift:286`），验收只要求"显示的捕获时间与用户实际改动时间一致、跨设备一致"。
6. **防抖 flush 的失败处理。** 「改动后立刻发送」要求发送前等到这次改动落地；如果等待失败（网络/冲突），需要明确用户看到什么、以及该消息是否仍携带。推荐：明确告知"这次改动尚未保存"，不静默发出无背景消息。
