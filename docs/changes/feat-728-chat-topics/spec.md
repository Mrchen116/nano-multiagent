# feat-728: 聊天内话题

## 原始需求

> 现在有个具体的需求，我想让本IM还是要支持thread能力，类似slack，飞书都支持。就是一个群一个聊天内，应该有thread展开一个话题，而不是都堆在聊天一个串里。跟我对齐需求

> 关于thread的设计可以参考slack等，关于thread 内的agent相关，可以参考raft，我理解大概就是agent参与的thread，收到的消息也作为特殊消息，类似@agent，不过我不确定。

## 澄清记录

- Q1: Agent 何时被 thread 消息叫醒？
  A(原话): 唤醒用 follow 模型，跟 Raft 一样。
  Agent 解读: 话题里的一条新消息，只叫醒已经关注这条话题的 Agent，不把话题里的每条消息都当成 @。关注的来法对齐 Raft 文档：发出被挂话题的那条消息、在话题里回复过、在话题里被 @。人还可以主动关注或取消关注。[Raft：Channels and DMs](https://docs.raft.build/features/messaging/channels/) 写明，thread 挂在一条消息上，写出那条消息、在其中回复、被 @ 或选择 Follow thread 的人会 follow，只有 follower 收到回复；Unfollow 停止。[Raft：Agents](https://docs.raft.build/features/agents/) 写明，叫醒包括 joined channel 的新消息、私聊、@、所 follow 的 thread 里的回复。Raft 也允许 Agent 做完后自己 unfollow。第一版不验收这种自动离开：Agent 一旦因上面的条件关注，就保持关注，用户才能在同一话题里纠正；人取消的是自己的提醒。本仓群里「回复所有群消息」继续只作用于主时间线，不把未关注话题里的每条回复都变成叫醒。

- Q2: 是否支持 Slack 式“同时发到聊天”？
  A(原话): 不做同时发到聊天。
  Agent 解读: 话题里的回复只留在话题中。不做 Slack 的 “Also send to the channel / DM”，也不做飞书帮助中心里回复话题时的「同时发送到群 / 同时发送到会话」。主时间线上只保留原消息和进入话题的入口。

- Q3: 第一版做哪些端？飞书话题呢？
  A(原话): 第一版做 Web 和 iOS，飞书话题映射放二期。
  Agent 解读: 第一版在浏览器 Web IM（含窄屏）和原生 iPhone 客户端提供本 IM 私聊、群聊里的话题。不把飞书话题同步进来，也不把本 IM 话题同步到飞书。外部通道在本 IM 里的影子会话第一版仍是一条时间线，不能在那里创建话题。

- Q4: 回复某条消息时，用 Raft/Slack 的「回复即进 thread」，还是飞书的「普通回复是可多层的引用、留在主时间线，只有『在话题中回复』才开话题」？
  A(原话): 我不是特别同意。我其实更喜欢飞书那种玩法。我觉得可以先试着用飞书这套玩法。
  Agent 解读: 同一条消息上有两件不同的事。一件是引用回复：新消息留在主时间线，能看出回的是哪一条；对一条本身也是引用回复的消息再回复，仍然留在主时间线，并能回到更早的那条。另一件是在话题中回复：第一条发送出去才出现话题，之后的讨论只在话题里。飞书帮助中心把后者写成：为某条消息创建话题，讨论聚合在话题下，未参与的成员不会频繁收到提醒；回复过会自动订阅，也可以另外订阅或取消订阅（[使用话题回复](https://www.feishu.cn/hc/zh-CN/articles/423295624296-%E4%BD%BF%E7%94%A8%E8%AF%9D%E9%A2%98%E5%9B%9E%E5%A4%8D)）。同一页还提供「同时发送到群」，该项已由 Q2 排除。飞书英文帮助写过群内引用回复会在输入框自动加上对原发送者的 @（[Reply to messages](https://www.feishu.cn/hc/en-US/articles/360024608614-reply-to-messages)）。用户确认的是回复落在哪里，没有确认自动 @。第一版不自动替用户插入 @；引用回复就是主时间线上的一条新消息，未读和 Agent 叫醒沿用主时间线规则，用户仍可自己 @。回复到某条 Agent 消息时，沿用现在「回复该 Agent 会叫醒它」。

- Q5: Agent 多步任务是否默认挂到请求消息的 thread？
  A(原话): 可以啊，就按raft的做法。
  Agent 解读: 按 Raft 现在的交办说明：Agent 接下一件要做的事时，在你那条消息的 thread 里确认要做什么；做的过程在这件事自己的任务对话里；做完后把结果发回你那条消息的 thread（[Your first task](https://docs.raft.build/hand-off-your-first-task/)、[Tasks](https://docs.raft.build/features/collaboration/tasks/)）。本仓已经有任务和工作视图，第一版不另做一套任务对话。用户要在聊天里看到的确认、追问和结果，都在这条请求的话题里，不复制到主时间线。随口一句能答完的，仍直接出现在主时间线，不为此单开话题。过程展示跟着那条回复走；本来就在工作视图里看的执行轨迹仍留在那里。

- Q6: 私聊里的 thread 回复是否像 Slack 那样全部通知，群聊则按 follow？
  A(原话): 可以啊，没毛病。那其实就是应用于私聊的逻辑嘘。没有变化。
  Agent 解读: 「嘘」按笔误理解为“是”。私聊话题回复的提醒与现在这条私聊来了新消息一样，双方都会知道，不套用群的关注过滤。群里只有关注的人被提醒。Slack 的帮助与此同向：一对一私聊里，thread 的新回复默认都通知；频道或多人会话里，发起人、回复过的人和被提及的人会收到通知，也可以单独打开或关掉某一条 thread 的通知（[Use threads to organize discussions](https://slack.com/help/articles/115000769927-Use-threads-to-organize-discussions)）。

- Q7: Agent 回复时看多少上下文？
  A(原话): 没懂啥意思，回复不就是send_message吗，和看上下文有啥关系。
  Agent 解读: 不产生需求，也不在本文提问。用户把「回复」理解成把消息发到该去的地方。上下文取多少留给 design。

- Q8: 内核会话是否按 thread 拆？
  A(原话): 不懂你说啥，感觉你没有理解我的代码一样。
  Agent 解读: 不产生需求，也不在本文提问。会话如何划分、消息发往哪个内部目标，留给 design。本文只规定用户看得到的落点。

## 现状

本 IM 的一个私聊或群聊现在只有一条消息流。新消息接在末尾。消息上能做的是复制整条，以及在单聊里对一条已完成的 Agent 回复「从此处分支」：那会另开一段带着历史的单聊，不是在原聊天里展开话题。依据：[会话与消息](../../specs/im/conversations-messages.md)、[Web 聊天体验](../../specs/im/web-chat-ux.md)。

群里的 Agent 默认只在被 @，或这条消息是在回复它时才接话；也可以设成「回复所有群消息」。没接话时，用户看不到一条写着内部拒绝词的消息。依据：[群路由](../../specs/gateway/routing-delivery.md)。界面文案是「仅被提及时回复」「回复所有群消息」「不回复群消息」。

未读和免打扰按人和聊天分开记。活跃的 iPhone 客户端对其他未静音聊天给出可关掉的轻提示。依据：[会话与消息](../../specs/im/conversations-messages.md)、[iOS 客户端](../../specs/im/ios-client.md)。

飞书等外部聊天在本 IM 里是影子会话，现在也是一条消息流。产品愿景把 Web IM 和原生 iPhone 当作日常协作入口，飞书是延伸触达。依据：[产品愿景](../../product/vision.md)。

## 参考

这些产品只说明用户已经点名的玩法，不把它们的界面或实现当成要照搬的契约。

- Slack：thread 挂在一条消息上；一对一私聊的 thread 回复默认都通知；群里发起、回复过或被提及才通知；可以单独关注或取消。勾选后可以把回复同时发回频道或私聊的主视图。本需求不做这最后一项。
- 飞书：普通回复留在会话里并带引用，可以再回复一条引用；「创建话题 / 在话题中回复」把讨论收进话题，未参与的人不频繁被提醒，回复过自动订阅，也可以手动订阅或取消。帮助中心允许回复话题时「同时发送到群」，本需求不做。话题群（整个群只能以话题形式发言）不是本需求。
- Raft：能读这个频道或私聊的人就能读其中的 thread；只有 follower 收到回复。Agent 接工作后，在请求消息的 thread 里确认，过程放在任务自己的对话，结果发回请求消息的 thread。

## 用户场景

项目群里，投放结论、闲聊和一张截图堆在同一条时间线上。小李想只接住「下周三的评审要补哪三页」，又不想让每句讨论都刷过所有人。

她把指针放到那条消息上，能分清两件事。选「回复」，她的话留在群的主时间线上，上面能看出引用的是哪一条；别人再引用她这条，仍然留在主时间线，并且能点回更早的那条。选「在话题中回复」并发送之后，这句话不出现在主时间线上。原消息上出现话题入口。群里的人都能打开，按时间看完，也能继续说。没参与的人不会因为这些回复多出一个未读；发出原消息的人、在话题里说过话的人、被 @ 的人会知道有新回复。小李也可以对一条自己没参与的话题主动关注，或在看完后取消关注。

私聊不是这套过滤。小王和同事的一对一里，对方在某条消息下展开话题，提醒和未读与现在这条私聊来了新消息一样。

同一条群消息也可以交给 Agent。随口问「用一句话回答这个时间对不对」，Agent 的那一句仍出现在主时间线上，不单开话题。把「先说你准备怎么补这三页，做完把提纲发回来」交给它时，主时间线不再接上它的确认和提纲；打开原消息的话题才能看到。小李在这个话题里说「第二页不用了」，Agent 接上，后续仍发在同一话题里。别人另开一个与它无关的话题时，它不插话；有人在那个话题里 @ 它，它才加入。加入之后，这条话题的新回复会继续叫到它，结果发出后也不自动离开，这样还能在同一话题里改。

手机上打开同一个群，能做同样的选择：引用留在主时间线，话题单独展开，关注与否和在电脑上一致。飞书里的那个群，第一版仍然是照原来的一条消息看，不在这里映射话题。

## 验收标准

### Requirement: 引用回复留在主时间线，并可一层层回到被引用的消息

#### Scenario: 回复一条普通消息
- **GIVEN** 用户可以在这个私聊或群里发消息，时间线上有一条普通人或 Agent 发出的消息
- **WHEN** 用户选择把回复留在主时间线并发送
- **THEN** 新消息按发送时间出现在主时间线，能看出它在回复哪一条，并能回到那一条
- **AND** 原消息上不因此出现话题

#### Scenario: 再回复一条引用
- **GIVEN** 主时间线上已有一条引用回复
- **WHEN** 用户再引用这一条并发送
- **THEN** 这条仍在主时间线，能看出直接回复的是哪一条，并能继续回到更早的那条
- **AND** 仍然不产生话题

#### Scenario: 不能引用系统行
- **WHEN** 用户查看时间线上的系统提示或 Agent 配置分界
- **THEN** 不能对它做引用回复

#### Scenario: 不能发或发送失败
- **GIVEN** 用户只能看这个聊天，或者发送时失败
- **WHEN** 用户尝试发出一条引用回复
- **THEN** 不能发时不出现可发送的回复；失败时用户知道没发出去，已经写好的内容还在
- **AND** 时间线上不增加一条失败的半截消息

### Requirement: 一条消息可以展开一个话题，话题内容不进入主时间线

#### Scenario: 发出第一条话题回复
- **GIVEN** 一条普通人或 Agent 的消息还没有话题
- **WHEN** 有发送资格的用户选择在话题中回复并发送文字、@、图片或这个聊天本来允许的文件
- **THEN** 这条回复不出现在主时间线
- **AND** 原消息上出现话题入口，能看出已有回复；打开后能看到刚发送的内容

#### Scenario: 打开但没发送
- **WHEN** 用户选择在话题中回复后离开，没有发送
- **THEN** 原消息上不出现话题

#### Scenario: 阅读、接上和同时看到新回复
- **GIVEN** 一条消息已有多条话题回复
- **WHEN** 能读这个聊天的人打开话题
- **THEN** 回复按时间排列，更早的可以继续往前看
- **AND** 有发送资格的人可以继续回复，新回复只追加在这个话题里
- **AND** 正在看这个话题时，新回复出现，不需要退出再进；人在往上翻更早的回复时，新回复不把阅读位置拉走

#### Scenario: 主时间线只更新入口
- **GIVEN** 用户正看这条聊天的主时间线
- **WHEN** 话题里来了新回复
- **THEN** 原消息上的话题入口更新，能进入并读完
- **AND** 这条回复本身不插入主时间线

#### Scenario: 话题不套话题，也不串到别的消息下
- **GIVEN** 同一聊天里有两条各自带话题的消息
- **WHEN** 用户在其中一个话题里继续发送，或试图对话题里的某条再开一个话题
- **THEN** 内容仍留在原来那一个话题
- **AND** 另一个话题的内容不变，没有第二层话题

#### Scenario: 旧消息和自己的消息也能开
- **WHEN** 用户对一条更早的消息，或自己刚发出的普通消息，发送第一条话题回复
- **THEN** 话题挂在被选中的那条消息上，规则与挂在最新一条上相同

#### Scenario: 重新进入后仍在话题里
- **WHEN** 用户离开这个聊天后再次进入，或在 Web 与 iPhone 之间查看同一条消息
- **THEN** 话题回复仍只在话题里，主时间线不把它们补成普通消息

#### Scenario: 不能对话题使用的消息
- **WHEN** 用户查看系统提示或 Agent 配置分界
- **THEN** 不能把它展开成话题

#### Scenario: 只能看，或发送失败
- **GIVEN** 用户只能读这个聊天，或者话题回复发送失败
- **WHEN** 用户打开话题或尝试发送
- **THEN** 能读的人可以读完；不能发的人看不到可发送的入口
- **AND** 失败时用户知道没发出去，写好的内容还在，话题里不增加半截消息

### Requirement: 群里按关注提醒，私聊仍按现在的私聊提醒

#### Scenario: 发出原消息的人
- **GIVEN** 用户发出的一条群消息下有了话题
- **WHEN** 别人在话题里回复
- **THEN** 这个群为该用户增加未读；聊天未免打扰时，提示方式与现在这条群里来了新消息相同

#### Scenario: 回复过或被 @
- **GIVEN** 用户在这条群话题里回复过，或某条话题回复 @ 了该用户
- **WHEN** 之后又有新的话题回复
- **THEN** 该用户被提醒，规则与发出原消息的人相同

#### Scenario: 没参与的群成员
- **GIVEN** 用户能读这个群，但没发原消息、没在话题里回复、没被 @，也没主动关注
- **WHEN** 话题里来了新回复
- **THEN** 不因此增加该用户的未读，也不提示
- **AND** 打开群后仍能从原消息进入话题并读完

#### Scenario: 主动关注和取消
- **GIVEN** 一条已有话题的群消息
- **WHEN** 用户主动关注，之后来了新回复；再取消关注，之后又来了新回复
- **THEN** 关注期间的新回复提醒该用户
- **AND** 取消后的新回复不再提醒；用户能看出自己现在是否还关注
- **AND** 取消之后又在话题里回复、被 @，或重新关注，则之后的新回复再次提醒

#### Scenario: 私聊没有这层过滤
- **GIVEN** 一对一私聊里某条消息已有话题
- **WHEN** 对方发送一条话题回复
- **THEN** 未读和提示与现在这条私聊来了新消息一样

#### Scenario: 免打扰和各自的已读
- **GIVEN** 一个会收到这条话题提醒的人把该聊天设成免打扰，另一位也会收到提醒的人没有
- **WHEN** 话题里来了新回复，然后第一个人打开并看到它
- **THEN** 免打扰继续按现在的方式压住提示
- **AND** 只清除看到的这个人的未读，另一个人的未读还在

#### Scenario: 引用回复不是话题提醒
- **WHEN** 用户在群的主时间线发出一条引用回复
- **THEN** 它按一条普通的主时间线新消息提醒本来会收到这个群新消息的人
- **AND** 不因为没人「关注」就消失

### Requirement: 话题里的 Agent 按关注被叫醒

#### Scenario: 与它无关的话题
- **GIVEN** 群里的 Agent 现在是「仅被提及时回复」，一条话题挂在别人的消息上，它没有在其中被 @，也没有回复过
- **WHEN** 人们在话题里继续讨论
- **THEN** 它不开始回复，也不出现正在处理这条话题的状态

#### Scenario: 在话题里被 @
- **GIVEN** 同一个 Agent 在主时间线被 @ 时现在会被叫醒
- **WHEN** 有人在话题里 @ 它
- **THEN** 它被叫醒，并开始关注这条话题
- **AND** 之后这条话题的新回复继续叫醒它
- **AND** 它没有要说的话时，不留下空消息，也不出现内部拒绝词

#### Scenario: 它发出的消息被展开
- **WHEN** 别人把话题开在这个 Agent 自己发出的一条消息上并回复
- **THEN** 这些回复叫醒它

#### Scenario: 它已经在话题里说过话
- **GIVEN** Agent 已在这条话题里回复
- **WHEN** 用户在同一话题里补充或纠正
- **THEN** 它被叫醒，后续要用户看到的话仍发在这个话题里

#### Scenario: 「回复所有群消息」不吞下别人的话题
- **GIVEN** Agent 被设成「回复所有群消息」，但没有关注某条别人的话题
- **WHEN** 主时间线来了一条普通新消息，同时那条未关注的话题里也有新回复
- **THEN** 主时间线的消息仍按现在的方式叫醒它
- **AND** 那条话题回复不叫醒它

#### Scenario: 主时间线上的引用回复
- **GIVEN** Agent 现在是「仅被提及时回复」
- **WHEN** 用户在主时间线引用这个 Agent 的一条消息并发送，没有另外 @ 别人
- **THEN** 这个 Agent 被叫醒
- **AND** 用户引用的是别人的消息、又没有 @ 这个 Agent 时，不因此叫醒它

#### Scenario: 关注一旦成立就保持
- **GIVEN** Agent 因为发出原消息、在话题里回复过或在话题里被 @ 而关注这条话题
- **WHEN** 之后又来了没有再次 @ 它的话题回复
- **THEN** 它仍然被叫醒
- **AND** 不因为结果已经发出就自动不再关注

#### Scenario: 私聊里的 Agent 仍收到话题
- **GIVEN** 用户与一个 Agent 的私聊
- **WHEN** 用户在某条消息的话题里回复
- **THEN** 这条回复会到达该 Agent，和现在私聊里发来一条新消息一样

#### Scenario: 设成不回复群消息
- **GIVEN** Agent 被设成「不回复群消息」
- **WHEN** 人们在群话题里说话，或在话题里 @ 它
- **THEN** 结果与现在在主时间线做同样的事一致，不因为话题多出一个接话途径

### Requirement: 要持续做完的事，确认和结果在请求消息的话题里

#### Scenario: 交给 Agent 一件要做完的事
- **GIVEN** 用户在主时间线把一件需要先确认、再交付结果的事交给 Agent
- **WHEN** Agent 接过这件事
- **THEN** 主时间线不新增它的确认和结果
- **AND** 打开这条请求的话题，能看到确认和最终要给用户看的结果
- **AND** 这些内容不会再被复制到主时间线

#### Scenario: 在话题里纠正
- **GIVEN** 结果已经发在这条请求的话题里，Agent 仍关注它
- **WHEN** 用户在该话题里指出要改的地方
- **THEN** Agent 接上，改完后用户仍在同一话题里看到

#### Scenario: 一句能答完
- **WHEN** 用户要求 Agent 只用一句话回答，Agent 也只发来这一句
- **THEN** 这一句出现在主时间线
- **AND** 不为此创建话题

#### Scenario: 过程不铺到主时间线
- **GIVEN** Agent 的这条回复今天在主时间线上会带着正文、图片、交互或过程
- **WHEN** 这条回复按本需求发在话题里
- **THEN** 这些内容跟着出现在话题里的这条回复上
- **AND** 本来要去工作视图或任务里看的执行轨迹仍在原处，不新灌进主时间线

#### Scenario: 人自己开的话题
- **WHEN** 用户对一条与当前交办无关的消息使用「在话题中回复」
- **THEN** 话题照常出现
- **AND** 不因为这件事不是多步工作就拒绝

### Requirement: Web 和 iPhone 都能完成同一件事

#### Scenario: 浏览器
- **WHEN** 用户在桌面或窄屏浏览器里做引用回复、展开话题、继续回复、关注和取消关注
- **THEN** 每一件都能做完，并能分清回复会留在主时间线还是进入话题

#### Scenario: iPhone
- **WHEN** 用户在原生 iPhone 客户端做同样的操作
- **THEN** 消息在不在主时间线、谁被提醒、Agent 有没有被叫醒，与浏览器一致
- **AND** 具体版式可以按手机重组，不要求与桌面同一套布局

### Requirement: 现有聊天不被话题改掉

#### Scenario: 不用新入口
- **WHEN** 用户像现在一样直接发送，不引用、不开话题
- **THEN** 消息仍进主时间线，未读、免打扰、@ 和群回复策略与现在一致

#### Scenario: 分支仍是另一段单聊
- **GIVEN** 一条今天可以「从此处分支」的、已完成的 Agent 回复
- **WHEN** 用户分支，或这条回复已经挂着话题
- **THEN** 分支仍另开一段带着历史的单聊
- **AND** 原聊天里的话题还在，分支聊天不是那个话题

#### Scenario: 搜索找得到话题里的话
- **GIVEN** 话题回复里有一段主时间线上没有的文字
- **WHEN** 用户用现有聊天搜索找这段文字
- **THEN** 能找到，并打开到话题中的那一条
- **AND** 搜索本身不改变未读

#### Scenario: 飞书影子会话第一版不变
- **WHEN** 用户打开一条外部通道影子会话
- **THEN** 仍然是一条时间线
- **AND** 不能在这里创建本 IM 话题，也看不到飞书话题映射

## 范围与非目标

- 在范围：本 IM 的私聊和群聊；浏览器 Web IM（含窄屏）与原生 iPhone；引用回复；一条消息下一层话题；群按关注提醒、私聊按现有私聊提醒；Agent 按同样的关注被话题叫醒；要做完的事，其确认和结果进入请求消息的话题。
- 非目标：把话题回复同时发回主时间线；话题里再开话题；把整个群改成只能发话题；飞书或其他外部通道的话题映射；在影子会话里创建话题；单独的跨聊天话题收件箱；给话题另起标题、标记结束、撤回或编辑消息；只引用消息中的一段文字；替换现有分支单聊、任务或工作视图；Agent 做完后自动取消关注；规定 Agent 看多少上下文、会话如何划分或内部发送目标。
