# feat-780: 聊天内话题

## Relations

- Related: feat-730, feat-779

## 原始需求

> 现在有个具体的需求，我想让本IM还是要支持thread能力，类似slack，飞书都支持。就是一个群一个聊天内，应该有thread展开一个话题，而不是都堆在聊天一个串里。跟我对齐需求

> 关于thread的设计可以参考slack等，关于thread 内的agent相关，可以参考raft，我理解大概就是agent参与的thread，收到的消息也作为特殊消息，类似@agent，不过我不确定。

> feat 730不是已经做完了吗，我现在就是让你基于最新的develop继续做我们讨论的这个新版本啊

## 澄清记录

- Q1: Agent 何时被 thread 消息叫醒？
  A(原话): 唤醒用 follow 模型，跟 Raft 一样。
  Agent 解读: 话题里的新消息只及时叫醒已经关注这条话题的 Agent，不把每条话题消息都当成 @。关注来自：发出被挂话题的那条消息、在话题里回复过、在话题里被 @ 或被引用。[Raft：Channels and DMs](https://docs.raft.build/features/messaging/channels/) 写明，thread 挂在一条消息上，写出那条消息、在其中回复、被 @ 或选择 Follow thread 才会 follow，只有 follower 收到回复。[Raft：Agents](https://docs.raft.build/features/agents/) 写明，叫醒包括所加入频道的新消息、私聊、@，以及所 follow 的 thread 回复。人可以主动关注或取消自己的提醒。Raft 允许 Agent 做完后自己 unfollow；第一版不验收这种自动离开，否则用户无法在同一话题里纠正。本仓现在的「普通群消息大约十分钟才带上」只适用于主时间线。未关注的话题回复不进入这批背景，否则没参与的 Agent 仍会被周期叫醒。

- Q2: 是否支持 Slack 式“同时发到聊天”？
  A(原话): 不做同时发到聊天。
  Agent 解读: 话题回复只留在话题里。不做 Slack 的 “Also send to the channel / DM”，也不做飞书帮助中心的「同时发送到群 / 同时发送到会话」。主时间线只保留原消息和话题入口。

- Q3: 第一版做哪些端？飞书话题呢？
  A(原话): 第一版做 Web 和 iOS，飞书话题映射放二期。
  Agent 解读: 浏览器 Web IM（含窄屏）和原生 iPhone 都能展开、阅读和回复话题。不把飞书话题同步进来，也不把本 IM 话题同步到飞书。外部通道影子会话第一版仍是一条时间线。

- Q4: 回复某条消息时，用「回复即进 thread」，还是飞书的「普通回复留在主时间线，只有『在话题中回复』才开话题」？
  A(原话): 我不是特别同意。我其实更喜欢飞书那种玩法。我觉得可以先试着用飞书这套玩法。
  Agent 解读: 两件事分开。已有的「回复」留在主时间线；新的「在话题中回复」才打开话题。飞书帮助中心把后者写成创建话题、讨论收在话题下、未参与的人不频繁被提醒，回复过自动订阅，也可以另外订阅或取消（[使用话题回复](https://www.feishu.cn/hc/zh-CN/articles/423295624296-%E4%BD%BF%E7%94%A8%E8%AF%9D%E9%A2%98%E5%9B%9E%E5%A4%8D)）。同一页的「同时发送到群」已由 Q2 排除。用户当时还把普通回复理解成可以一层层引用。develop 上 feat-730 已经做成单层快照加点击定位，见下方现状。本 unit 不把这条已完成能力改成多层链；话题不依赖多层引用。飞书英文帮助里「群内回复会自动 @ 原发送者」也没有被确认，本 unit 不新增强制 @。

- Q5: Agent 多步任务是否默认挂到请求消息的 thread？
  A(原话): 可以啊，就按raft的做法。
  Agent 解读: Raft 现在的交办是：在请求消息的 thread 里确认，过程放在这件事自己的任务对话，结果发回同一条 thread（[Your first task](https://docs.raft.build/hand-off-your-first-task/)、[Tasks](https://docs.raft.build/features/collaboration/tasks/)）。本仓已有任务和工作视图，不另做一套任务对话。用户要在聊天里看到的确认、追问和结果进入该请求的话题，不复制到主时间线。一句能答完的仍留在主时间线。

- Q6: 私聊话题是否全部通知，群聊则按 follow？
  A(原话): 可以啊，没毛病。那其实就是应用于私聊的逻辑嘘。没有变化。
  Agent 解读: 「嘘」按笔误理解为“是”。私聊话题回复的未读和提示与现在这条私聊来了新消息一样。群里只有关注的人被提醒。Slack 帮助与此同向：一对一私聊的 thread 回复默认都通知；频道里发起人、回复过的人和被提及的人会收到通知，也可以单独开关（[Use threads to organize discussions](https://slack.com/help/articles/115000769927-Use-threads-to-organize-discussions)）。

- Q7: Agent 回复时看多少上下文？
  A(原话): 没懂啥意思，回复不就是send_message吗，和看上下文有啥关系。
  Agent 解读: 不产生需求。上下文取多少留给 design。

- Q8: 内核会话是否按 thread 拆？
  A(原话): 不懂你说啥，感觉你没有理解我的代码一样。
  Agent 解读: 不产生需求。会话如何划分、消息发往哪个内部目标，留给 design。本文只规定用户看得到的落点。

- Q9: feat-730 的引用回复还要不要重做？
  A(原话): feat 730不是已经做完了吗，我现在就是让你基于最新的develop继续做我们讨论的这个新版本啊
  Agent 解读: 引用回复是已完成的现有能力。本 unit 不改 feat-730 的文件，也不替它收口。话题是另一个功能。

## 与 feat-730 的关系

feat-730 负责主时间线上的「回复」：新消息留在主时间线，带上被回复那一条的单层快照，点击后定位到原消息。本 unit 不改变这个结果，也不把它升级成一层层点回去的引用链。

两条入口必须能分开：

- 主时间线上，已有「回复」仍只产生主时间线消息。新的「在话题中回复」才把内容放进话题。对一条已经带话题的消息使用「回复」，仍然留在主时间线，不写进话题。
- 话题里可以引用其中某一条。这条新消息使用和主时间线相同的单层引用与点击定位，但仍留在同一个话题里，不回到主时间线，也不另开话题。
- 话题里不再提供「在话题中回复」。没有第二层话题。
- 原生 iPhone 今天还没有「回复」。把它补到手机上属于 feat-779 的能力对齐，不属于本 unit。本 unit 在 iPhone 上增加话题；两端将来都有「回复」时，它和话题入口仍然是两件事。

## 现状

依据是 `origin/develop` 的当前 specs 与代码。长青 spec 还没有单独的引用回复 Requirement；feat-730 的行为在 Web 和消息服务里，unit 仍留在活动区。本文不改那份记录。

一个私聊或群聊仍然只有一条主时间线。消息上没有话题。能读这个聊天的人按时间看消息；未读按人和聊天分开记，看到的人只清自己的未读。免打扰是这个人自己的偏好。依据：[会话与消息](../../specs/im/conversations-messages.md)。活跃的 iPhone 客户端对其他未静音聊天给出可关掉的轻提示。依据：[iOS 客户端](../../specs/im/ios-client.md)。

Web 的消息菜单有「回复」。选中后，输入区显示可取消的引用摘要；发送后的新消息仍在主时间线末尾，卡片上是那一条原消息的发送者、正文、附件和已发布卡片，点击卡片定位到原消息。原消息不在当前已加载的历史里时，沿现有分页补出来再定位。只能引用本聊天里已可阅读的人或 Agent 消息，不能引用系统提示、配置分界、未完成的 Agent 消息或别的聊天。引用只保存被点的那一条，不带它自己更早的引用。Agent 发到本 IM 时也可以指定引用本聊天的一条消息；发到外部通道或内部执行者的消息不能带这个引用。原生 iPhone 的消息菜单仍是复制和分支，不提供「回复」，也不显示引用卡片。feat-779 已要求手机补齐引用回复，该要求不在本 unit。

群里的 Agent 不再使用「仅被提及时回复 / 回复所有群消息 / 不回复群消息」。现在的选择是「团队协作」或「仅限本人」，新建默认团队协作。团队协作时，私聊、真正的 @、回复或引用该 Agent 会及时叫醒它；没点名的普通群消息先攒着，下次被点名或大约十分钟再一起带上，Agent 仍可以不说话。仅限本人时，只接收创建者亲自发来的一对一私聊。依据：[群路由](../../specs/gateway/routing-delivery.md)、[Agent 协作范围](../../specs/im/agents-nodes.md)。

single_thread Agent 和每个私聊、每个群各自延续一段记忆，`/new` 在原聊天重开这段记忆，已有消息还在。Global Agent 跨聊天共用一段工作记忆；没被及时点名的群消息进入它的收件，不自动变成聊天里的回复；它要出现在聊天里，得自己把话发到那个聊天。过程在 single_thread 上跟着那条聊天回复，Global 的执行轨迹在工作视图。这些是现在的落点，不是要求按话题拆开或合并记忆。

单聊里仍可以把一条已完成的 Agent 回复「从此处分支」，得到另一段带着历史的单聊。那不是话题。

飞书等外部聊天在本 IM 里仍是影子会话，一条时间线。依据：[产品愿景](../../product/vision.md)。

## 参考

这些产品只说明已经点名的玩法，不把它们的界面或实现当成要照搬的契约。

- Slack：thread 挂在一条消息上；一对一私聊的 thread 回复默认都通知；群里发起、回复过或被提及才通知；可以单独关注或取消。勾选后可以把回复同时发回主视图。本需求不做这最后一项。
- 飞书：普通回复和话题回复是两个动作。话题聚合讨论，未参与的人不频繁被提醒。本需求不采用「同时发送到群」，也不把整个群改成话题群。
- Raft：能读这个频道或私聊的人就能读其中的 thread；只有 follower 被通知。Agent 在请求消息的 thread 里确认并交付结果。

## 用户场景

项目群里，评审、闲聊和截图还是堆在一条时间线上。小李只想接住「下周三要补哪三页」。

她在 Web 上能看见两个不同的动作。选已有的「回复」，话留在主时间线上，并带上那一条的引用卡片，点一下能回到原消息。选「在话题中回复」并发送后，这句话不出现在主时间线上。原消息上出现话题入口。群里的人都能打开并按时间读完。没参与的人不会因此多一个未读；发出原消息的人、在话题里说过话的人、被 @ 的人会知道。她也可以关注一条自己没参与的话题，或看完后取消。

私聊不是这套过滤。对方在某条消息下展开话题，未读和提示与现在这条私聊来了新消息一样。

把「先说你怎么补，做完把提纲发回来」交给 Agent 时，主时间线不接上它的确认和提纲；这些在那条请求的话题里。小李在话题里说「第二页不用了」，Agent 仍在同一话题里接上。随口一句能答完的，仍直接出现在主时间线。别人另开一个与它无关的话题时，它不马上插话，这条讨论也不混进它大约十分钟才看的普通群消息。有人在话题里 @ 它或引用它，它才加入，之后这条话题的新回复会继续叫到它。

iPhone 上可以打开同一个话题、读完并继续回复。手机上今天还没有「回复」，本需求不补那一个动作。飞书影子会话仍然是一条时间线。

## 验收标准

### Requirement: 话题挂在一条消息上，内容不进入主时间线

#### Scenario: 发出第一条话题回复
- **GIVEN** 一条本聊天里已可阅读的人或 Agent 消息还没有话题，用户可以在这个聊天发消息
- **WHEN** 用户选择在话题中回复，并发送文字、@、图片或这个聊天本来允许的文件
- **THEN** 这条回复不出现在主时间线
- **AND** 原消息上出现话题入口；打开后能看到刚发送的内容

#### Scenario: 打开但没发送
- **WHEN** 用户选择在话题中回复后离开，没有发送
- **THEN** 原消息上不出现话题

#### Scenario: 阅读和接上
- **GIVEN** 一条消息已有多条话题回复
- **WHEN** 能读这个聊天的人打开话题
- **THEN** 回复按时间排列，更早的可以继续往前看
- **AND** 有发送资格的人可以继续回复，新回复只追加在这个话题里
- **AND** 正在看这个话题时，新回复出现，不需要退出再进；往上翻更早回复时，新回复不把阅读位置拉走

#### Scenario: 主时间线只更新入口
- **GIVEN** 用户正看主时间线
- **WHEN** 话题里来了新回复
- **THEN** 原消息上的话题入口更新
- **AND** 这条回复本身不插入主时间线，也不会同时再出现一份

#### Scenario: 不套话题，也不串话题
- **GIVEN** 同一聊天里两条消息各自有话题
- **WHEN** 用户在其中一个话题里继续发送，或试图对话题里的消息再开一个话题
- **THEN** 内容仍留在原来那一个话题
- **AND** 没有第二层话题，另一个话题不变

#### Scenario: 旧消息和自己的消息
- **WHEN** 用户对一条更早的消息，或自己刚发出的普通消息，发送第一条话题回复
- **THEN** 话题挂在被选中的那条消息上

#### Scenario: 重新进入后仍在话题里
- **WHEN** 用户离开后再进入，或在 Web 与 iPhone 之间查看同一条消息
- **THEN** 话题回复仍只在话题里

#### Scenario: 不能展开的消息
- **WHEN** 用户查看系统提示或 Agent 配置分界
- **THEN** 不能把它展开成话题

#### Scenario: 只能看，或发送失败
- **GIVEN** 用户只能读这个聊天，或者话题回复发送失败
- **WHEN** 用户打开话题或尝试发送
- **THEN** 能读的人可以读完；不能发的人没有可发送的入口
- **AND** 失败时用户知道没发出去，写好的内容还在，话题里不增加半截消息

### Requirement: 已有引用回复和话题入口互不替代

#### Scenario: Web 上两个动作都在
- **GIVEN** 用户在 Web 查看一条可以回复的主时间线消息
- **WHEN** 用户分别选择「回复」和「在话题中回复」
- **THEN** 「回复」仍按现在的方式在主时间线发出带单层引用的消息，点击引用能回到那一条
- **AND** 「在话题中回复」不产生这种主时间线消息

#### Scenario: 已有话题时仍可引用到主时间线
- **GIVEN** 一条主时间线消息已经有话题
- **WHEN** 用户在 Web 上对它使用「回复」并发送
- **THEN** 新消息在主时间线，并引用这一条
- **AND** 它不出现在话题里

#### Scenario: 话题内引用留在话题里
- **GIVEN** 用户正在一个话题里
- **WHEN** 用户引用其中某一条并发送
- **THEN** 新消息留在这个话题，带上和主时间线相同的单层引用，点击后能在话题里回到那一条
- **AND** 不回到主时间线，也不创建新话题

#### Scenario: 不改已有引用的层数
- **WHEN** 用户在主时间线上引用一条本身已经引用了别人的消息
- **THEN** 新的引用卡片仍然只呈现直接被点的那一条，和现在一样
- **AND** 本需求不新增一层层展开的引用链

### Requirement: 群里按关注提醒，私聊仍按现在的私聊提醒

#### Scenario: 发出原消息、回复过或被 @
- **GIVEN** 用户发出了被挂话题的群消息，或在该话题里回复过，或被话题回复 @
- **WHEN** 话题里又有新回复
- **THEN** 这个群为该用户增加未读；未免打扰时，提示方式与现在这条群里来了新消息相同

#### Scenario: 没参与的群成员
- **GIVEN** 用户能读这个群，但没发原消息、没在话题里回复、没被 @，也没主动关注
- **WHEN** 话题里来了新回复
- **THEN** 不因此增加该用户的未读，也不提示
- **AND** 打开群后仍能从原消息进入话题并读完

#### Scenario: 主动关注和取消
- **GIVEN** 一条已有话题的群消息
- **WHEN** 用户主动关注后收到新回复，再取消关注后又有新回复
- **THEN** 关注期间提醒该用户，并能看出自己是否还关注
- **AND** 取消后不再提醒，直到再次回复、被 @ 或重新关注

#### Scenario: 私聊没有这层过滤
- **GIVEN** 一对一私聊里某条消息已有话题
- **WHEN** 对方发送一条话题回复
- **THEN** 未读和提示与现在这条私聊来了新消息一样

#### Scenario: 免打扰和各自的已读
- **GIVEN** 一个会收到提醒的人把该聊天设成免打扰，另一位也会收到提醒的人没有
- **WHEN** 话题里来了新回复，然后第一个人打开并看到它
- **THEN** 免打扰继续按现在的方式压住提示
- **AND** 只清除看到的这个人的未读

#### Scenario: 主时间线引用不是话题提醒
- **WHEN** 用户在群的主时间线发出一条引用回复
- **THEN** 它按一条普通的主时间线新消息提醒本来会收到这个群新消息的人

### Requirement: 话题里的 Agent 按关注被叫醒

#### Scenario: 与它无关的话题
- **GIVEN** 群里一个团队协作的 Agent 没有关注某条别人的话题
- **WHEN** 人们在话题里继续讨论，没有 @ 它，也没有引用它
- **THEN** 它不被及时叫醒，也不出现正在处理这条话题的状态
- **AND** 这些话题回复不混进它主时间线上大约十分钟才带上的普通群消息

#### Scenario: 在话题里被 @ 或被引用
- **GIVEN** 这个 Agent 现在在主时间线上被 @ 或被引用时会被及时叫醒
- **WHEN** 有人在话题里 @ 它，或引用它已经发出的一条消息
- **THEN** 它被及时叫醒，并开始关注这条话题
- **AND** 之后这条话题的新回复继续及时叫醒它
- **AND** 它没有要说的话时，不留下空消息，也不出现内部拒绝词

#### Scenario: 它发出的消息或它已经说过的话题
- **WHEN** 别人把话题开在这个 Agent 自己的消息上并回复，或它已经在这条话题里回复后又有新回复
- **THEN** 这些回复及时叫醒它
- **AND** 不因为结果已经发出就自动不再关注

#### Scenario: 主时间线规则不变
- **GIVEN** 一个团队协作的 Agent
- **WHEN** 主时间线来了没点名的普通消息，同时一条它未关注的话题里也有新回复
- **THEN** 主时间线的消息仍按现在的方式先攒着，下次被点名或大约十分钟再带上
- **AND** 那条话题回复不参与这次积压

#### Scenario: 仅限本人
- **GIVEN** Agent 被设成仅限本人
- **WHEN** 群话题里有人 @ 它，或创建者在和它的私聊话题里回复
- **THEN** 群话题不把它叫进来
- **AND** 创建者的私聊话题回复会到达它，和现在这条私聊新消息一样

#### Scenario: 私聊里的 Agent
- **GIVEN** 用户与一个能接收该私聊的 Agent 对话
- **WHEN** 用户在某条消息的话题里回复
- **THEN** 这条回复会到达该 Agent

### Requirement: 要持续做完的事，确认和结果在请求消息的话题里

#### Scenario: 交给 Agent 一件要做完的事
- **GIVEN** 用户在主时间线把一件需要先确认、再交付结果的事交给 Agent
- **WHEN** Agent 接过这件事
- **THEN** 主时间线不新增它的确认和结果
- **AND** 打开这条请求的话题，能看到确认和最终要给用户看的结果
- **AND** 这些内容不会再被复制到主时间线

#### Scenario: 在话题里纠正
- **GIVEN** 结果已经发在这条请求的话题里
- **WHEN** 用户在该话题里指出要改的地方
- **THEN** Agent 接上，改完后用户仍在同一话题里看到

#### Scenario: 一句能答完
- **WHEN** 用户要求 Agent 只用一句话回答，Agent 也只发来这一句
- **THEN** 这一句出现在主时间线
- **AND** 不为此创建话题

#### Scenario: 过程不铺到主时间线
- **GIVEN** 今天这条回复若在主时间线上，会带着正文、图片、交互或过程
- **WHEN** 这条回复按本需求发在话题里
- **THEN** 这些内容跟着出现在话题里的这条回复上
- **AND** 本来要去工作视图或任务里看的执行轨迹仍在原处

#### Scenario: 人自己开的话题
- **WHEN** 用户对一条与当前交办无关的消息使用「在话题中回复」
- **THEN** 话题照常出现

### Requirement: Web 和 iPhone 都能处理话题

#### Scenario: 浏览器
- **WHEN** 用户在桌面或窄屏浏览器里展开话题、继续回复、在话题里引用、关注和取消关注
- **THEN** 每一件都能做完，并能分清「回复」会留在主时间线、「在话题中回复」会进入话题

#### Scenario: iPhone
- **WHEN** 用户在原生 iPhone 客户端阅读话题、继续回复、关注和取消关注
- **THEN** 消息在不在主时间线、谁被提醒、Agent 有没有被叫醒，与浏览器一致
- **AND** 具体版式可以按手机重组
- **AND** 本需求不要求手机先补上主时间线「回复」

### Requirement: 现有聊天不被话题改掉

#### Scenario: 不用新入口
- **WHEN** 用户像现在一样直接发送，不引用、不开话题
- **THEN** 消息仍进主时间线，未读、免打扰、@、协作范围和群里积压与现在一致

#### Scenario: 分支仍是另一段单聊
- **GIVEN** 一条今天可以「从此处分支」的、已完成的 Agent 回复
- **WHEN** 用户分支，或这条回复已经挂着话题
- **THEN** 分支仍另开一段带着历史的单聊
- **AND** 原聊天里的话题还在

#### Scenario: 搜索找得到话题里的话
- **GIVEN** 话题回复里有一段主时间线上没有的文字
- **WHEN** 用户用现有聊天搜索找这段文字
- **THEN** 能找到，并打开到话题中的那一条
- **AND** 搜索本身不改变未读

#### Scenario: 飞书影子会话第一版不变
- **WHEN** 用户打开一条外部通道影子会话
- **THEN** 仍然是一条时间线
- **AND** 不能在这里创建本 IM 话题

## 范围与非目标

- 在范围：本 IM 的私聊和群聊；浏览器 Web IM（含窄屏）与原生 iPhone 上的一层话题；与已有「回复」分开的「在话题中回复」；话题内沿用单层引用且不离开该话题；群按关注提醒，私聊按现有私聊提醒；Agent 按关注被话题及时叫醒；要做完的事，其确认和结果进入请求消息的话题。
- 非目标：修改 feat-730 已完成的主时间线引用回复，或把它改成多层引用链；替 feat-730 收口；实现 feat-779 里的 iPhone 引用回复；把话题回复同时发回主时间线；话题里再开话题；话题群；飞书或其他外部通道的话题映射；在影子会话里创建话题；单独的跨聊天话题收件箱；给话题另起标题、标记结束、撤回或编辑消息；只引用消息中的一段文字；替换分支单聊、任务或工作视图；Agent 做完后自动取消关注；规定 Agent 看多少上下文、会话如何划分或内部发送目标。
