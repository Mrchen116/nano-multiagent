# im/conversations-messages Specification (delta for feat-780)

## ADDED Requirements

### Requirement: 一条主时间线消息可以挂一层话题

话题回复仍是该聊天的消息，但不进入主时间线。根必须是同一聊天里已可阅读的人或 Agent 消息。系统提示、配置分界、未完成的 Agent 消息、别的聊天、以及已经属于话题的消息不能当根。没有发送出第一条回复之前，不出现话题。

#### Scenario: 话题回复不进入主时间线
- **WHEN** 有发送资格的成员向一条合格消息发送话题回复
- **THEN** 主时间线的历史、游标和实时插入都不出现这条回复
- **AND** 打开该根能按时间读到它。正在看该话题且已经离开底部时，新回复加在末尾，阅读位置不动。正在看主时间线的人只看到根上的入口更新

#### Scenario: 非法的话题根被拒绝
- **WHEN** 请求把话题根设成系统行、未完成消息、别的聊天或另一条话题回复
- **THEN** 不创建消息，已输入的内容仍可重发

#### Scenario: 搜索能打开话题里的原文
- **WHEN** 用户搜索只存在于话题回复中的文字
- **THEN** 结果指向该话题里的那一条，而不是一条新的主时间线消息
- **AND** 搜索不改变未读

#### Scenario: 分支不带走话题
- **WHEN** 用户把一条已挂话题的、今天允许分支的 Agent 回复分成新单聊
- **THEN** 新单聊只带主时间线历史；原聊天的话题仍在，不在新单聊里出现

### Requirement: 群话题按关注计未读，私聊话题仍算普通新消息

#### Scenario: 群里的关注者
- **GIVEN** 用户是该话题根的发送者、已在话题中回复、被 @、被引用，或主动关注且未取消
- **WHEN** 别人在该群话题中回复
- **THEN** 该用户的这个聊天未读增加
- **AND** 打开主时间线并读到主时间线消息，不会清掉还没打开的该话题未读

#### Scenario: 没关注的群成员
- **WHEN** 能读该群但未关注的成员遇到话题新回复
- **THEN** 不增加其未读；打开群仍可从根进入并读完

#### Scenario: 取消后恢复
- **WHEN** 用户取消关注后又有回复，之后自己回复、被 @、被引用或重新关注
- **THEN** 取消期间不计未读；恢复之后的新回复重新计入

#### Scenario: 私聊
- **WHEN** 一对一私聊中出现话题回复
- **THEN** 未读、已读和提示与现在这条私聊的新消息相同

### Requirement: 引用与话题互不替代

#### Scenario: 主时间线引用
- **WHEN** 用户对主时间线消息使用现有引用回复
- **THEN** 新消息留在主时间线，仍是那一条的单层引用
- **AND** 即使该消息已有话题，这条引用也不写入话题

#### Scenario: 话题内引用
- **WHEN** 用户在话题中引用该根或该话题里的一条消息
- **THEN** 新消息留在同一话题，并带单层引用
- **AND** 不创建第二层话题

## MODIFIED Requirements

### Requirement: 会话消息与时间线条目响应字段稳定且按消息游标分页

前端经会话 endpoints 创建和读取消息；消息继续使用 Actor 语义并暴露 delivery status、sender type 与 attachments。历史读取的 `items` 是 typed timeline union，可包含普通 message 与独立 config boundary；`next_before_message_id` 继续作为消息游标。未知会话保持稳定 404。主时间线只包含没有话题根的消息；话题回复由话题读取返回。

#### Scenario: 创建会话指定参与者 Actor
- **WHEN** 前端创建带参与者的会话
- **THEN** 返回会话 id，后续可据此读写消息

#### Scenario: 创建消息回显既有消息字段
- **WHEN** 前端创建用户或 Agent 消息
- **THEN** 响应继续包含既有 message id、conversation id、delivery status、sender type 与 attachments

#### Scenario: 并发创建会话
- **WHEN** 同一用户同时提交多个合法的创建会话请求
- **THEN** 对同一对联系人的普通私聊发起返回同一个会话；显式新建群或 fork 仍分别建立独立会话，所有会话均保留完整参与者列表

#### Scenario: 列时间线走 items 与消息游标信封
- **WHEN** 前端读取会话历史
- **THEN** 响应含 `items` 与 `next_before_message_id`
- **AND** 每个 item 由 type 明确区分 message 与 Agent 配置边界，面向浏览器的 boundary 只含定位与展示所需字段
- **AND** 话题回复不在这些 items 中，也不占据消息游标；已有话题的根消息带回复数和最后一条摘录

#### Scenario: 未知会话相关读写返回稳定 404
- **WHEN** 前端对不存在的 conversation id 读写消息或时间线
- **THEN** 返回既有 conversation not found 语义

#### Scenario: conversation 列表与 sync 暴露通用运行态
- **WHEN** 浏览器前端请求 conversation 列表或 sync 数据
- **THEN** 每个 conversation item 包含通用字段 `run_state`，取值至少支持 `"idle"` 与 `"running"`
- **AND** 该字段不带 distill 命名，可被其他功能复用

#### Scenario: 普通浏览器消息使用本人身份
- **GIVEN** 当前用户是该聊天成员
- **WHEN** 浏览器提交消息并尝试声明其他人的发送者身份
- **THEN** 消息不能冒充其他人、Agent 或 system；正常用户消息展示当前登录者。

#### Scenario: 纯人聊天不需要 Gateway
- **WHEN** 两个用户创建私聊或只有真人成员的群并收发消息
- **THEN** 消息正常持久化和实时呈现，不要求存在 Agent 或在线 Gateway。

#### Scenario: 群类型不由人数推断
- **WHEN** 用户明确新建只有本人和一个 Agent 的群
- **THEN** 仍创建群会话，可按群操作添加成员。

#### Scenario: 普通人际私聊默认显示对方名称
- **GIVEN** 两个真人的普通私聊尚未被明确改名
- **WHEN** 任一成员读取列表、详情或同步结果
- **THEN** 默认聊天名显示该查看者的对方；明确设置的共享名称继续对双方一致，fork 与 Skill 蒸馏聊天保留自己的标题。

#### Scenario: 聊天历史摘要与完整过程读取
- **WHEN** 客户端选择摘要视图读取聊天历史，随后展开某条已结束回复的过程
- **THEN** 历史先返回消息、审批状态和过程概况，按需读取同一消息的完整过程；普通客户端仍可按原方式读取完整历史。
- **AND** 过程详情必须符合当前会话读取资格，消息与会话不匹配或当前不可读时不能取到详情。

### Requirement: 聊天偏好与已读状态属于当前用户

#### Scenario: 置顶与免打扰各自独立
- **GIVEN** alice 与 bob 同在一群
- **WHEN** alice 设置置顶或免打扰
- **THEN** 仅改变 alice 的聊天列表与通知偏好，bob 的偏好不变。

#### Scenario: 已读不消费他人的未读
- **GIVEN** 两人均有该群未读消息，其中包含一人尚未打开的群话题
- **WHEN** alice 打开聊天并读到当前主时间线消息
- **THEN** 只清除 alice 已看到的主时间线未读；她尚未打开的群话题未读还在，bob 的未读保留；同时到达、尚未展示的新主时间线消息仍保持未读。

#### Scenario: 旧状态随升级承接
- **GIVEN** 原用户已有聊天偏好和未读数量
- **WHEN** 部署 agent 按 unit 的迁移文档完成存量转换，升级并重新登录
- **THEN** 原用户的既有偏好和未读数量保留，其他用户的个人状态独立初始化；旧聊天、历史与 fork 链接继续可用。

### Requirement: 真人发送的普通聊天消息提供逐人回执

#### Scenario: 聚合展示私聊与群聊回执
- **WHEN** 真人在 Nano 私聊向真人或 Global Agent 发送消息，或在群聊中发送普通消息
- **THEN** 消息发送者可辨认待送达、已送达和已读，并按收件人查看状态
- **AND** 群聊主时间线以发送时其他有收件资格的成员为范围；群话题回复只把当时关注该话题的人计入范围。因 Agent 协作范围排除的目标不占分母，全部计入范围内的人送达后才显示已送达，全部已读后才显示已读

#### Scenario: 各收件人的状态独立推进
- **WHEN** 部分收件人确认收件或已读
- **THEN** 发送者可以查看这些人的最新状态，其他收件人维持最近一次已确认状态
- **AND** 对 Global Agent，已送达以本条消息的 Inbox 提醒实际进入模型请求、且该请求返回有效模型内容为准；仅持久入箱、进入调度队列或开始请求不能推进已送达。已读以模型调用 Inbox read 成功取得完整消息且读取事实已持久化为准

#### Scenario: Agent 忙碌或离线时不提前显示送达
- **GIVEN** 新消息已持久进入 Agent Inbox，但其提醒仍排队、请求未发出，或请求未返回有效模型内容
- **THEN** 该 Agent 的回执保持待送达；节点在线或传输确认不改变这一状态
- **WHEN** 包含该条消息提醒的模型请求返回有效内容
- **THEN** 仅推进该提醒实际覆盖的消息，不把稍后到达或按范围取消的消息一起标记已送达；重试与恢复重复证据不重复推进
- **AND** Inbox check、读取失败或只取得部分内容不产生已读回执
