# perf-784 降低 IM 流式消息的同步数据库开销

## 原始诉求

> 我在做性能检查，希望在体验不变的情况下，优化性能。上面是agent给我找到的性能问题。你帮我审视下，包括周边的能力。是否确实存在性能问题。如果是，则新开unit帮我修复。

## 现状与目标

在 6e387616f、Node 24.22.1、本机文件 SQLite WAL 上运行真实 Gateway.streaming、Messaging 和 Gateway.broadcast，socket 只计数。每帧写 100 个 ASCII 字符及一个新 key。12 帧预热后用一帧统计 get/all/run，随后每组 20 帧、共五组计时。99 名真人和一个 Agent 在群，1000 个浏览器中 99 个有权接收，共 1124 条语句/帧，五组均值 10.77–12.13 ms。1 真人、1 Agent、无浏览器是 39 条/帧。目标为同条件群聊至多 150 条、耗时中位数至少降低一半，小群也减少同步开销。历史、投递与设置状态的新鲜度沿用现有体验。

### Requirement: 实时投递与撤权
#### Scenario: 成员、观察者及退出者
- **WHEN** 群成员或有权观察私聊的主人在多个浏览器接收消息，其中一个会话被撤销，或用户被移出群。
- **THEN** 每个仍有效的接收端按原顺序收到应有事件，失去资格的接收端收不到后续正文；成员变更通知仍可到达原收件人。

### Requirement: 流式正文、重试与历史
#### Scenario: 运行中刷新及终态
- **WHEN** 运行中收到重复增量、刷新历史、断线重连、正常结束或中断。
- **THEN** 已提交文字即时可读、只出现一次；补发与历史一致，终态后迟到的增量不改变正文，禁用或旧代次的写入仍被拒绝。

## 范围与回滚

仅调整 IM 服务端的 SQL 执行、广播和幂等键生命周期。上游批量发送、客户端显示与轮询节奏按现状。回退可切回旧实现继续读取原表、正文及事件。
