## 现状痛点

总量调解群里先经 conversations.list 获得四名成员，再额外执行20次 Bash。当前成员使用 IM user_id，Inbox Agent 发送者常用 agent_id，mention 又要求 agent_id。单 Thread 会注入 mention 格式，全局模式没有同等说明。发送模型参数叫 to，查询叫 target。模型要自己拼接这些接口知识。用户要求改善工具，不以封禁 Bash 或添加任务推进规则代替设计。

用户现有操作基线：在多个群与同一 Agent 交流，查询参与者、私信、在群里提及；两种工作模式能按既有群回复策略响应；会话名与历史保持，刷新和重启后继续使用。

## 目标状态

人和 Agent 在聊天中各有一个全局稳定的短身份，同一对象在所有群和主上下文中一致。查群成员后可以直接私信或提及，不需寻找另一套身份。Inbox 与历史表达一致，工具说明足以走通查询到发送。部署 Agent 依迁移文档一次性更新已有数据，保持历史与会话连续性。

## 用户侧验收标准

### Requirement: 跨群聊天身份稳定且可直接联系
#### Scenario: 同一成员出现在多个群
- **WHEN** Agent 查询两个群的成员并联系同一个人或 Agent
- **THEN** 两处身份一致，私信到达正确对象，没有另建或误认参与者
#### Scenario: 查询指定群成员
- **WHEN** Agent 已知某个群并查询它的成员
- **THEN** 得到完整成员名单与名称，包含未发言成员；空结果和无权访问明确区分

### Requirement: 两种模式保持群内提及体验
#### Scenario: 在群内提及 Agent 或人
- **WHEN** 用户或 Agent 在群内提及另一位成员
- **THEN** 正文显示正确名字，目标 Agent 按既有提及回复策略处理；不把群发改成私信
- **AND** 单 Thread 和全局模式均可使用，普通名字文本不冒充有效提及

### Requirement: 消息查询与发送语义清晰一致
#### Scenario: 从未读或历史辨认发送者
- **WHEN** Agent 读取 Inbox 或同一聊天历史
- **THEN** 能一致辨认发送者和聊天类型，消息内容、顺序与附件保持；只有 Inbox 摄取推进本 Agent 未读
#### Scenario: 查询并发送
- **WHEN** Agent 使用查到的聊天或成员身份发送消息
- **THEN** 正确目标收到消息；失败或暂扣明确表示尚未发送，成功回执不重复整段正文

### Requirement: 一次性迁移保留现有使用状态
#### Scenario: 迁移后继续已有聊天
- **WHEN** 部署 Agent 按迁移文档完成备份、迁移与启动
- **THEN** 已有账号、群成员、消息、手动会话名与 Agent 上下文保留，私信及提及继续到达原对象
- **AND** 重启后身份与会话仍保持；新代码不依赖旧 ID 别名或旧 mention 格式

## 影响范围

IM 用户/会话 ID 生成、聊天成员查询、提及路由与前端渲染；Gateway 工具、Inbox 身份、两种模式的通信提示；部署迁移文档。agent_id 仍整个 IM 唯一，内部调度保留 agent_id。消息/执行/工具调用 ID 不纳入缩短。无权限模型改造、Bash封禁、调解策略改写、生产部署或 PR 合并。

## 迁移与回滚策略

部署时停相关写入，备份 IM 与全部连接 Gateway 的持久状态、配置和上下文。一次性改写 user_id/conversation_id 及引用，旧 Agent mention 改为统一 user mention；必要时重封装绑定旧 owner_id 的渠道凭据。使用迁移映射文件进行核对与备份回滚，但该映射不被新代码加载。完整操作由 migration-prompt.md 交给部署 Agent；本轮先在复制数据上验证，不对生产执行。旧外部书签需使用迁移后的地址，不保留旧地址解析接口。
