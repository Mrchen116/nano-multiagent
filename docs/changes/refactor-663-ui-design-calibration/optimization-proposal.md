# 优化建议：按需使用少量设计取舍对照案例

日期：2026-10-26。状态：供讨论的推荐方案，未实施、未证明有效。依据：[本次复盘](retro-pipeline-rootcause.md)、[用户指定 ChatGPT 对话](https://chatgpt.com/c/6adeb50a-d38c-83ec-b1cc-c3b7859b7f62)。参考聊天通过浏览器实际读取；聊天工具返回的回答引用占位符未当作正文。

## 推荐只做的一项改进

在现有共同 UI 设计指导旁，建立一份小而具体、按判断问题选择的对照案例资料。Agent 在作信息组织、交互模式和视觉权重决定时，读取相关例子，用其推理方法处理当前任务；现有自检和 reviewer 使用同一份资料进行校准。

不另建独立 Skill 或角色，不增加逐 unit 交付文件，不增加用户确认步骤。收益假设是用可观察的真实对照弥补抽象规则与实际判断之间的空白，而不是期待再写一遍“成熟、简洁、现代”就改善。

## 对 GPT 意见的取舍

GPT 最后一条建议是把历史纠正做成案例驱动的设计校准资料，接入 change-design-author，按需加载，并进行小规模对照验证。这个方向与本地证据吻合，但建议作四处调整：

| 建议 | 本次判断 |
| --- | --- |
| 选 10～15 个历史案例 | 不以数量为目标。先覆盖少量不同的决策机制，重复案例合并；优先有前后文、画面和已核实改进结果的案例。未完成的修复只能作为反例，不能冒充正确答案。 |
| 接入 design-author | 只接这里会漏掉实施时的设计决定和快速开发，也不能校准已出现误判的 reviewer。资料放在现有共同入口，由当前负责 UI 判断的角色按需读取；不复制到每个 Skill，不额外加一轮审查。 |
| 停用按钮是低频危险操作，应弱化 | 有条件成立。feat-657 原始需求包含紧急停止，工作详情必须容易找到。要校准的是列表浏览与紧急处置的不同任务，不能总结为危险操作一律藏进深层菜单。 |
| 用某历史 unit 原始需求验证 | 若该 unit 的最终方案已放进案例资料，测试会泄漏答案。验证任务应留出，且控制可见仓库快照、历史文档和提示；同时允许有证据的多种合理设计。 |

GPT 第一条长回答中的完整参考库、多工具链、额外专业 reviewer、多方案评测可作未来备选，但目前没有必要一起引入。引用论文和社区案例的结论未经本轮逐项核验，不当作本仓改善效果的证据。

## 资料应该教什么

每类只保留：用户正在完成什么 → 原做法为什么看似合理 → 实际代价 → 改变了哪个设计决定 → 哪些条件下应采用其他做法。配一对真实画面或可复查的现有页面/源码位置；无法取得改后实物时明确证据缺口，不编造“正确效果”。截图仍遵循本仓本地产物政策，不把图片批量提交到 Git。

建议首批关注四类：

| 判断问题 | 历史依据 | 希望学会的取舍 |
| --- | --- | --- |
| 操作应占多大权重 | 657 停用；636 PA Configure 行 | 浏览列表以身份和比较为主；当前工作中的紧急停止保持直接可达。同一操作可因所在任务不同采用不同呈现，不重复堆放同义控件。 |
| 哪些文字值得保留 | 652 Feature 说明；583 Work 冗余标题 | 删除不帮助判断的重复文字；保留用途、当前实际值及重要后果。简洁不能以用户猜测为代价。 |
| 新能力如何融入现有产品 | 616 导航/配置双入口；589 原生轨迹 | 优先沿用已形成的使用路径；存在明确任务收益时才改变结构。复用的对象是交互和阅读方式，不只是颜色。 |
| 内容与状态怎样影响布局 | 584 五列任务；645 Toast | 从用户需要同时比较的信息和状态变化决定结构；临时反馈不应挤动待操作内容，视觉分组不能掩盖数据分页造成的假空。 |

不能把这张表再当一组自动验收禁令。重点是具体画面如何体现取舍，以及当前场景是否满足同样前提。已有产品本身也可能不合理，保持一致性不等于复制旧缺陷。

## 如何嵌入已有工作

沿用共同体验标准这一权威入口，只替换其中缺乏操作支撑的部分，链接案例索引。遇到对应设计决定时选择最相关的案例，不默认加载整月复盘或全部用户原话。判断结论留在现有 design、自检或 review 的原位置，不增加一个“案例学习报告”。

Full 设计阶段在作决定时使用；直接实施或 lite 的实现者在自检时使用；现有 reviewer 用其校准判断，但仍先独立观察受审页面，不能先拿作者的理由作为答案。快速开发的改进需在实际实施之前可达，不能只挂到事后 change-fast-close。

是否必须改各 Skill 的入口，要以实际引用链核验；当前 design-author、简化实施与 product reviewer 已引用共同标准，优先利用这些接线，不为表面覆盖重复写规则。

## 验证应小而有区分力

这次优化本身做一次有界对照试用，不给以后每个 unit 加评测流程。选一个未进入案例资料的前端任务，在相同基线、模型和输入下比较现有指导与加入资料的首稿；既查看首次设计的实际画面，也操作最关键的交互。被测上下文不得含该任务最终修复方案或标注答案。

比较其是否保留交互语义、整页信息主次与产品连续性，以及是否仍需要重做结构。记录额外读取和耗时，避免以大量上下文换取微小收益。若两组都好或结果不一致，如实记录有限或未证明收益，不靠反复试到成功放行。

一次试用只能筛掉明显无效/有害方案；后续真实 unit 中用户纠正整体方案的次数，才是长期效果线索。不能以自行打分或“案例已读取”替代用户实际负担下降。
