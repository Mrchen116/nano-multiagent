# 最近一个月新 unit 的 UI/UX 纠正与根因复盘

调查范围：2026-09-26—2026-10-26（Asia/Shanghai），截至本次调查。仓库：nano-multiagent。调查时主仓 main 干净；原调查未修改产品、Skill、历史 unit 或 memory。本报告随后按用户要求收入 refactor-663；入库仅调整证据链接及本说明，后续建议见 optimization-proposal.md。

## 核心结论

用户的感受有实质证据：多个新 unit 在原型、真实实现甚至独立验收通过以后，仍需用户纠正基本的信息组织、视觉层级、产品一致性和交互路径。问题不局限于颜色、字号或个人风格偏好。用户反复承担的是产品设计者和最终体验验收者的工作。

最稳定的共同机制是：**Agent 将需求转成字段、入口、状态和按钮，完成接线后，再以“能看到、能点击、能保存、没有遮挡”证明体验成立。** 原型和审查文件可以很完整，但信息优先级、操作频率、内容关系与整页构图仍没有真正决定。新增控件因此常被直接加到现有页面上；用户指出后，又按局部例子修补，容易留下相邻入口或造成另一端问题。

当前 Skill 已明确反对这些做法。历史上也已在 9 月 30 日、10 月 12 日和 10 月 13 日连续改进过。对 10 月下旬案例，再解释成“缺一条 UI 要求”不成立。需要同时处理设计方法的执行、判断质量，以及 Skill 验证不能代表真实产出的局限。

## 调查口径与边界

- 从 Git 的 unit 文件新增历史建立候选清单，检查 archive/retired 的迁移与别名；不能把旧 unit 重归档当作本月新建，也不能把后续修复 unit 再算一遍失败。
- 对本机可读取、工作目录关联本仓且最近一个月更新过的 121 条主聊天做文字筛查；时间窗口内有 1,546 条候选用户消息。该数包括范围外话题、授权、测试协助等，不是 UI 反馈数，也不是 unit 总数。
- 针对相关聊天读用户诉求、连续反馈与前后回应，并核对设计、验收报告、Git 版本。保留了 [82 条反馈定位及原话](feedback-evidence.md)，其中包括正面反馈、范围澄清与反证，不将它们全部计为缺陷。
- 直接目视复核了 feat-645 用户所发 Toast 截图、feat-657 iOS 原型截图、10 月 26 日生产 Agent 列表截图。其余案例主要使用原话、前后文及版本化产物，不声称全部历史画面都已重新渲染。

## 为什么做不好：有证据的机制

### 1. 功能组织代替了产品设计，交付时才发现整页不成立

578 用默认 Form/List 承接大量需求；584 全局分页后再分五个状态列；589 为满足技术扩展能力另建默认视图；657 将同一开关铺到各入口。共同点不是组件不会写，而是先满足字段/操作覆盖，再把它拼成页面。

这会系统性地产生大按钮、默认表单、大卡片、冗余标签、低信息密度。它们都很容易证明“存在且能用”，但没有回答：用户此刻最需要读什么、哪些操作高频、哪些信息只应在异常时出现。

584 的五列分页尤其能区分设计与美化：用户要同时比较任务进展，后端整页切片却让某列出现假空。调间距、补“本页”标签都无法满足这个目标。589 的轨迹过滤也一样：选中一段与删掉其他历史是不同的产品动作。

### 2. 对既有产品的继承停在局部相似，没有守住整条路径

572 字体/成员身份、578 头像与输入交互、616 主导航、644 Skill 状态、636 PA 配置行、657 列表操作，都出现过“新功能在，产品连续性不在”。

不能笼统断言 Agent 从未看旧页面：657 的 reviewer 明确实际打开了基线，645 也对照过现有配置页面。更准确的结论是：**读取过基线、复用过颜色或组件，并未转化为对入口、信息权重、列表节奏和完整交互的约束。**

此外，“UI 做完整”还会被误执行为“把这个 unit 的所有状态和说明画出来”。657 原型直接把“配置页用开关；详情和工作页用按钮”的设计说明放进卡片，正是把设计文档内容当成产品内容。

### 3. 独立审查存在，但各角色使用了同一种不足的判断依据

最直接的原始产物证据：

- [feat-645 design-review:41](../archive/feat-645-capability-dependencies/design-review.md)：首轮认为提示紧跟条目、未盖住开关、能消失，未发现需阻断的视觉问题；第二轮沿用并 Approved。用户随后指出工具被挤动，[149 行起](../archive/feat-645-capability-dependencies/design-review.md)记录撤回该体验判断。这里“没有覆盖控件”不等于“反馈不扰动布局”。
- [feat-657 design-review:63](../archive/feat-657-agent-disable-switch/design-review.md)：第一轮将身份→设备→Toggle/状态→按钮判断为足以指导实施。第二轮 [111 行](../archive/feat-657-agent-disable-switch/design-review.md)明确承认旧卡片将 Toggle 和同义按钮拼在一起，撤回正面判断。这不是没截图，而是看过后判断不成立。
- feat-572 在用户指出整体布局后，Agent 给出“独立复验 8 项通过”，紧接着用户仍指出大刷新按钮和错位；feat-596 的功能录像和独立验收通过后，用户仍要求整页重做。

因此增加审查次数或再分一个同类 reviewer，不能自然解决问题。独立身份能够减少作者自证，却不能自动补齐共同缺失的设计判断。

反证也需要保留：584 reviewer 抓到了真实 iOS 建群与冲突恢复缺陷；645 后续拦住浮层越界；657 reviewer 抓到停用聊天仍显示在线、用户不知为何不回复。这些审查有价值。问题是对可操作故障较敏感，对整体信息组织和视觉权重的判断不稳定。

### 4. 用户的整体否定被缩成局部补丁，甚至过度纠偏

578 用户明确说“绝对不止这两处”；584 多次否定整体布局；652 最后要求“不要让我一个一个指出来”。这些反馈针对设计方法和覆盖范围，而不是再列一个待修 bug。

652 给出最清楚的反向例子：用户要求删除无效说明，但 Agent 连 Feature 用途也删了；用户不得不补充“别人怎么知道这个特性是干什么的”。这是没有以“帮助判断是否开启”作为删留标准。先多写无效信息、再机械删光，都没有完成信息设计。

同样，新增 PA 配置入口不等于设计了配置路径：616 产生两套入口，636 又产生更高的特殊行与 Configure 按钮。局部功能修好，没有对新结果与相邻区域重新判断。

### 5. 原型能解释方案，却没有稳定约束真实布局；但原型不是唯一根因

HTML 原型、iOS 原生页面和实际 Web 组件之间，仍可能留下“原生适配”或“局部样式”的判断空白。578 的结构原型不能替代原生 UI 设计；657 的一张示意卡甚至把三个页面混在一起。真实产品中的多条数据又会放大原型中不明显的重复操作——10/26 的红色停用按钮阵列就是这种整页效果。

但不能推出“取消原型就会好”：652 已按用户要求直接在 worktree 改代码、看真实页面，仍出现删错说明、遗漏创建页。真实画面是必要证据，最终仍取决于如何组织和判断它。

当前 [共同体验标准](../../../.claude/skills/change-design-author/references/prototype-and-runbook.md) 甚至直接写了“不要从已有字段或 API 返回形状直接推导页面”“先判断方案是否成立，再判断实现是否符合方案”。[产品 reviewer](../../../.claude/skills/change-reviewer/SKILL.md) 也要求先判断整体可交付性。这里有明显的规则执行/判断失败，不能只往 Skill 再加同义句。

同时，现有体系规定了该做什么、不能凭什么放行，仍将具体构图、信息优先级、模式选择和质量校准留给模型临场决定。这是目前可以支持的能力与工作方法缺口；并非证明需要增加一个角色或更长的 prompt。

10/13 [skill-validation.md](../archive/feat-584-task-progress-permissions/retrospectives/2026-10-13-uiux-recurrence/skill-validation.md) 已如实记录：第一次图像试用仍把整体问题拆成 minor，修改后才改善；末尾明确没有验证完整多轮交付链，也没有旧 Skill 对照组。不能把这次有限改善理解为对未来 UI 交付的保证。

## 最小改进方向（本次未实施）

1. **把设计工作的首个结果从控件清单变成整页方案。** 在既有 design 阶段先确定这个页面的核心判断、阅读顺序、主要动作与频率，再给出放在真实上下文中的完整画面；简单控件无需增加文档。这样能在添加停用按钮、配置卡片前判断它应该处于什么权重。
2. **把现有成熟页面和高质量组合做法作为可执行的设计参照。** 复用列表行、页头、配置表单、轻提示和导航方式，说明本次为什么需要偏离。先检查已有组件能否直接承担，避免仅抄配色后重造整个壳。无需建立庞大新设计系统。
3. **让已有 reviewer 真正做不依赖作者说明的阅读与操作。** 用正常数量和长度的内容，看整页、展开关键状态、完成核心判断，再核契约；反馈要说清画面事实及用户代价。比如 Toast 前/中/后的布局，20 个 Agent 下动作权重，默认字号的真实消息密度。不是要求用户多确认，也不是新增一个审批 Gate。
4. **把 Skill 验证推进到未提前指出问题的新任务交付。** 原有冻结图保留作回归样本，另选小型真实增量验证从设计到实现的首稿。记录用户是否还需纠正整体结构、审查漏检了什么、复用是否保住旧体验；不要以文件齐全、截图数、CI 或 reviewer 自报通过替代。没有对照和多个样本之前，不宣布根因已被解决。

改动落点应优先是 design-author 的实际设计方法与参考材料、design-reviewer/product-reviewer 的判断校准及现有 Skill 验证方式。仅加“你是专业 UI/UX 设计师”“必须现代漂亮”，或继续加轮次、截图、审批，无法针对已证实的失败机制。

## 未决项与结论限制

- 没有针对所有角色逐一重放全部工具与模型上下文，因此不能声称每次失败都因没读 Skill、上下文太长、模型型号或消息截断。
- 不能从用户说“丑”推断所有细节都是错误；本报告靠具体目标、相邻回应和产物定位问题，并保留明确的正常迭代与正面反馈。
- feat-617 的运行时生成 UI 与本仓开发 Agent 设计 UI 分开归因；其历史组件/提示词解释需要另做当前源码及对照试验，不能用它解释全部设置页问题。
- 原调查仅形成报告；随后按用户要求收入 refactor-663 并补充优化建议，仍未改变 Skill，未认定 10/26 正在处理的界面已经修复。
