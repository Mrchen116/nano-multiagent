### Task 提醒机制逐项对齐

| 机制 | 对齐进度 |
|---|---|
| 一：初次执行／恢复时的任务责任同步 | 不保留独立额外提醒；真实变化同步由机制二承接 |
| 二：任务变化时的责任更新 | 已确认通过所属聊天系统消息统一表达、@ 相关人或 Agent |
| 三：一轮结束后的自动续跑 | 已确认必要续跑规则＋全部本人 doing／waiting 任务概要＋详情入口 |
| 四：waiting 的定时复查与安排修复 | 已对齐：保留正常复查；Schedule 用户删除通知与具体 Task 无有效安排提醒分别需要，后者不区分删除操作者 |
| 五：Task 操作成功后的交付提醒 | 已确认保留，围绕本次任务、固定所属聊天及必要交付规则精简，已确认交付不重复 |

#### 机制一已确认：内部对象生命周期不触发额外提醒

- 内部对象释放、重建或宿主“上次展示快照”记录丢失，本身不能触发额外的模型可见 Task 提醒；内部生命周期不构成 Agent 可观察任务事实的变化。
- 宿主可以重新核对任务状态，但“重新核对”与“向 Agent 注入提醒”必须区分。不能仅因内部没有 previous/shown 就认定 Agent 没有相应信息，或认定任务责任发生变化。
- Agent 当前可见的任务信息仍然有效、真实任务事实也未改变时，不因内部对象重建再发送相同快照或完整续跑规则。
- 保留用户最初要求：执行确实因重启、断连或意外结束而中断，且仍有可推进 doing 时，按原本统一续跑逻辑接续；这不授权无任务时或正常工作未中断时因内部重建而额外催促。真实任务变化由机制二同步，不再保留仅以首次执行／内部恢复为由的独立提醒机制。
- 首次会话所需信息和有效上下文的完整性仍须满足本 unit 的信息保真要求；具体组织方式在五个机制全部对齐后的整体设计中统一处理，不用内部对象生命周期替代模型可见信息的判断。

原意与偏差追溯：[`feat-635 Q13`](../archive/feat-635-task-driven-execution/spec.md#q13重启或断连导致执行中断后如何接续) 明确“doing 的还是按原本的方式发 prompt”及上下文换窗与 Task 正交；其设计要求比较已展示责任并移除无变化提示。后续 [`bugfix-646 用户复核续修`](../archive/bugfix-646-task-continuation/design.md#用户复核续修停止不唤醒与变更同步审计2026-10-24) 将“任务实际变化后需同步”扩大为冷恢复时只要 shown 缺失就附快照；提交 `503498e1f` 又在该路径复用完整续跑 prompt。该扩大是设计和实现推导，不是用户要求内部释放重建后追加提醒。

#### 机制二已确认：真实任务变化统一通过所属聊天系统消息表达

- 任务真正发生业务变化时，在任务固定所属聊天产生系统消息。沿用现有会话及消息能力，不再为同一变化维护一份平行的、仅对 Agent 可见的责任变化提醒；原有任务协作消息与本机制统一考虑。
- 消息说明哪个任务发生什么变化；需要重点关注的人或 Agent 用 @ 明确标出。相关者按实际职责和协作关系判断，包括原／新负责人、需要接收子任务结果的父负责人等；同图、同群或能够查看不等于需要被要求处理。
- 对正文／要求更新，消息明确说明要求已更新、需要读取最新正文，并保留可定位任务的入口；不只传技术版本或更新时间，也不重复注入全部正文。关系或方向变化同样表达可理解的业务含义，不用“revision 变了”代替。
- 补齐成员资格变化导致任务访问／处理资格变化的通知，使 Agent 获知真实责任边界变化，不能只依赖后续工具被拒。消息仍遵守实际会话访问边界；失去原会话资格的相关主体如何获知必要的撤销事实，留到整体设计处理，不通过 @ 扩大访问权限。
- 复用持久聊天消息承接离线和稍后读取：真正发生的变化有对应消息，已知且没有变化的事实不因内部重建重新生成消息；同一事件的重试／重放不重复发一份。停止、恢复等必要来源事实仍须保真。
- 任务事实通知与是否开工分开：通知不因任务尚为 todo 或处于暂停等状态就自动变成开工指令，既有停止和授权边界继续有效。具体提醒与唤醒组合在五个机制全部对齐后统一设计，不在本轮另造算法或消息通道。

本轮源码核对的范围：常规 create/apply/delete、PA 委托写入、/stop、明确恢复、群解散和 Agent 停用已有通知入口；当前 changeHint 收件范围为整图所有 Agent 负责人，责任比较又包含整图 revision，导致无关变更可能形成多余提醒。成员移除入口仅发布会话成员变化，缺少直接的任务责任更新接线；责任快照未表达正文及关系变化的具体含义。以上是现状证据，用户已确认的目标以上述群消息原则为准，不把现有私下快照路径固化为目标设计。

#### 机制三已确认约束：续跑 prompt 保留必要行为规则

- 用户明确否定“仅补任务清单，稳定规则全部交给其他上下文”的简化。自动续跑需要必要的行为规则，不能将规则去重理解为删除续跑所需的行动指导。
- 回到 [`feat-635 Q15`](../archive/feat-635-task-driven-execution/spec.md#q15agent-看到什么用户看到什么) 的用户原话：“Agent 的续跑 prompt 要参考DSH的prompt，改变就是DSH只有一个goal，我们的是全部doing 任务。任务详情 Agent 按需读取完整正文和讨论，不每轮重复注入全部历史。”后续对齐增加 waiting 分类，不能因此丢掉原始行为目的。
- 历史文档已确认的核心是：在同一会话继续，核对当前工作区／工具结果／持久状态，取得具体进展并验证，完成前核对整个目标及证据，未完成的责任继续保留；按需读取详情。`bugfix-646` 又对真实阻塞、授权内替代路径、等待和实际交付作了产品适配。
- 已确认续跑内容由必要行为规则、全部本人 doing／waiting 任务概要及按需读取详情入口组成；必须区分无意义的规则重复与续跑触发点所需的必要重申。具体措辞及与常驻说明、等待和交付提示的分工，在五个机制全部收口后统一设计；本段不冻结最终英文 prompt，也不将第四、第五机制提前定案。

#### 机制四已确认：Schedule 删除通知与具体 Task 无有效安排提醒各自成立

- 正常定时复查沿用既有契约：读取当前 Task 与外部事实，能推进则继续，仍需等待则建立有效的下次检查，间隔由 Agent 按任务判断且不超过一小时；相关回复可提前恢复。用户要求继续下一项，本轮不重开这些已确认规则或新增独立的重复催促。
- Schedule 被用户删除后，需要给相关 Agent 发 reminder，说明这项 Schedule 的删除事实。这是 Schedule 自身的变化通知，与是否关联 Task 无关；没有 Task 也需要通知。
- 若 Task 仍为 waiting，而其关联 Schedule 已不存在，还需要独立的 Task reminder，明确是哪项任务失去了有效后续安排、无法按原计划唤醒，并给出检查当前任务、继续推进或重新安排检查的行动指导。该条件与删除操作者无关：用户删除和 Agent 自己主动删除都必须触发，不能因 Agent 自己调用了删除工具、已经知道删除事实而省略。Schedule 删除通知或删除工具回执不能替代这项 Task 提醒；不能因为两者源于同一次删除就认为是同义冗余。
- Reminder 必须明确到具体 Task。至少包含可识别的任务标题、唯一定位信息（如 graph_id/node_id）和任务入口；多个任务受影响时逐项列明，不只给一句泛泛的“Task 无有效 Schedule”。具体格式留给整体设计。
- 用户给出的内容方向：“Task未有关联的schedule，无法按原计划唤醒，请检查任务当前是否结束；能继续就推进，仍需等待则建立新的有效检查安排。”最终措辞遵循本 unit 自有提示统一英文的决定，保留这些事实与行动要求。
- 删除 Schedule 后，Task 此时仍为 waiting；Agent 读取最新事实后按实际进展处理 Task 或建立新的有效安排。提醒本身不伪造状态变更，也不自动把任务当成已结束。
- 此前“类似报错”的表述以本轮用户明确的 Task reminder 为准。Agent 曾进一步建议“拒绝删除并保留原安排”，这不是用户要求，不作为本 unit 的目标或替代上述 reminder 的方案。具体接线在五项收口后的整体设计中处理。
- 当前核实：删除并非仅由 Agent 控制，设置页也有用户删除入口。Agent 使用原生 Schedule 工具；用户经 `control-routes.ts` 的 cron 删除路由、Node 转发与 `CronOwners.command` 删除。Task 进入／变更 waiting 时已有有效 Schedule 校验。
- 证据边界：前述“关联安排被删除”最初是解释用例，未提供实际故障证据；现已成为用户明确要求覆盖的场景。当前 `schedule.wait.inspect` 对不存在、不活跃或过期返回合并原因，不能宣称它已准确判定“被删除”并只是遗漏传给模型。

#### 机制五已确认：具体任务的操作结果与实际交付衔接

- 保留 Task 操作成功后的交付提醒：成功进入 waiting 时应向固定所属聊天解释必要进展与阻塞；提交 in_review／done 结果时应实际交付经过核验的成果。任务记录变更、系统协作消息、私有结束语与实际交付各有不同作用。
- Reminder 围绕本次具体任务及实际交付组织，明确任务标题与定位、固定所属聊天、此次已确认的状态或结果，以及必要行动规则；不再次附完整工具结果，也不完整复述所有常驻 Task 规则。
- waiting 保留说明实际进展、具体阻塞、已尝试路径、需要谁提供什么及下次检查的必要指导；in_review／done 提醒交付核验后的成果。Global 仍以 send_message 实际发送，内部子 Agent 向父 Agent 报告，由主 Agent 负责公开交付。
- 先核对较新状态与消息，已确认交付的相同内容不重复发送；回执重放、没有新内容的等待续期不要求刷屏。失败／未知不能声称已送达，也不回退已保存的 waiting 或删除其有效 Schedule；其他可执行责任继续。
- 本机制与机制二分工：群系统消息让相关者知道任务事实变化；本提醒让执行者完成成果或阻塞的实际沟通。不能仅因存在状态变更消息就删除必要的交付提醒。

### 1. 自有提示语言混搭、段落职责不清

PA 默认指导是中文，Global/PA 固定规则、Task 和 Feature 指导大多英文；来源规则甚至在英文段落内穿插中文解释。Global 与 PA 段各有四千余字符的长段，身份、来源、权限、沟通、工具操作、失败处理混杂，难以审查遗漏或冲突。

来源入口：[`personal-agent-defaults.ts`](../../../apps/im-server/src/personal-agent-defaults.ts)、[`global-mode.ts`](../../../packages/dsh-integration/src/global-mode.ts)、[`personal-security.ts`](../../../packages/dsh-integration/src/personal-security.ts)、[`policy/sources.ts`](../../../packages/dsh-integration/src/policy/sources.ts)。

语言混用本身不能证明模型错误；主要风险是职责交叠、重复规则掩盖关键约束。不能以全部翻译替代结构整理。

### 2. 相同约束在多层反复解释

| 重复主题 | 当前分布与问题 |
|---|---|
| 来源与授权 | 默认 PA 指导、Global、来源规则、PA 固定规则多次解释观察不等于交办、主人身份不等于授权、其他 Agent 发言不构成新授权 |
| 实际交付 | Global 段内多次强调私有回复不等于公开交付，来源、UI、Task 段又重复实际发送要求 |
| 反馈与安静 | 多处要求有变化才汇报、不得重复发送已交付结果；相同规则缺少清楚的唯一归属 |
| 持续推进与等待 | Task 常驻说明与动态续跑消息都完整解释等待、复查、恢复及反馈流程 |

补充入口：[`features/task-graphs.ts`](../../../packages/dsh-integration/src/features/task-graphs.ts)、[`features/intelligent-ui.ts`](../../../packages/dsh-integration/src/features/intelligent-ui.ts)、[`task-execution.ts`](../../../packages/dsh-integration/src/task-execution.ts)。重复的安全边界仍然有效，去重不能误删其唯一生效位置。

### 3. 常驻细节与按需指导重叠

Task 等待及复查包含长篇操作细节；Skill 创建指导一面要求加载 Skill，一面已在常驻提示中展开创建细则。需要区分常驻必要边界、能力发现入口、按需操作方法和本轮任务事实，避免同一指导在多种载体反复出现。

来源入口：[`features/skill-creation.ts`](../../../packages/dsh-integration/src/features/skill-creation.ts)、[`agent-config.ts`](../../../packages/dsh-integration/src/agent-config.ts) 及上述 Task 入口。不能仅因存在 Skill 就删除模型发现它所必需的信息。

### 4. 首次环境和能力信息排列在唤醒之后，轨迹难以理解

已观察的排列为：初始系统提示 → Inbox 唤醒 → Task 提醒 → 当前运行状态 → Skill 目录 → 模型响应。用户预期先具备环境和能力上下文，再追加唤醒事件。

前轮对本机 DSH 依赖的检查表明，这些动态信息在第一次模型调用前准备；该排列不代表模型先处理 Inbox、执行后才得到环境与 Skill。运行快照在变化或旧快照缺失时提供；Skill 目录在首次、变化或当前上下文缺失时补充，并非每条新消息都注入全部 Skill 正文。

待优化的是首次上下文与后续更新的职责及可理解性。调整模型实际顺序和调整轨迹展示是不同方案，设计时应根据实际请求验证；不能仅为视觉顺序修改 DSH 私有运行时。DSH 接入红线仍以 [`SPEC.md`](../../../SPEC.md) 为准。

### 5. Task 动态提醒过长，注入条件与当前责任不充分匹配

用户观察到新消息后反复出现完整续跑提醒，质疑每次追加是否必要。当前 main 的 `TaskExecutionDriver` 在 `agent/pre-step` 读取责任快照；首次或责任指纹变化时补充提示，显式自动续跑时注入完整 `prompt()`，后续责任变化通常使用 `delta()`。因此不能将“每条新消息无条件追加”写成已证实结论。

已确认两个具体问题：

1. 首次尚无 `previous` 且有普通输入时，即使没有可推进任务，非 runnable 分支仍可能调用完整 `prompt()`。其中“Continue working on your owned Tasks”与空责任状态不匹配，纯观察或普通问答也可能看到这类指令。
2. 自动续跑仍携带整段稳定规则，而不仅是此次责任、变化和下一步所需事实；与系统 Task 指导重复。需要核对连续新消息、真实状态变化、自动续跑、恢复后的实际注入次数与内容。

本问题不主张取消持续推进、停止事实或有效等待复查。应避免无变化、无责任时堆叠长篇继续工作命令，同时确保关键状态变化及时可见。

## 目标状态（后续设计输入）

- 自有常驻规则有清晰职责，来源、授权、交付、任务责任各有权威定义；其他段只补充特有约束。
- 自有提示统一英文并整理结构风格，保留工具名、字段名等必要原名，不修改用户自定义文本来追求一致。
- 常驻规则、动态事实、Skill 目录与按需正文分工明确，实际消费链可验证。
- 首次环境/能力上下文与后续唤醒、状态更新容易区分；具体排列与组织方式按仓库 Agent Context 原则设计，保留现有信息，不将固定排列或仅调整轨迹显示预设为方案。
- Task 机制一不保留独立额外提醒，内部对象释放重建不能触发提醒；真实变化按机制二统一通过所属聊天系统消息表达并 @ 相关人或 Agent；机制三保留必要续跑规则、本人任务概要及详情入口。机制四保留正常复查，Schedule 用户删除事实与具体 waiting Task 无有效安排分别需要提醒，后者不区分删除操作者；机制五保留面向具体任务的必要交付提醒，已确认交付不重复发送。
- 用实际组装请求及代表性行为验证优化，消除明显重复冗余，不把字符数降低或源码整理单独视为成功；不设置字符数、token 或降幅指标。

## 用户与 Agent 消费者验收标准

以下包含已确认的行为改进和必须保留的既有能力。提示结构、重复注入和请求顺序的实现层验证在 design 中补充，不冒充已完成验收。

### Requirement: Agent SHALL 获得职责清晰且信息完整的 Context

#### Scenario: 首次接收用户请求
- **WHEN** PA 或普通 Agent 在当前能力配置下首次处理请求
- **THEN** 在决策前能获得有效身份、行为边界、运行环境和可用 Skill 入口，并区分初始环境／能力信息与触发本轮的消息；Nano 自有提示使用英文，用户自定义指导保留。

#### Scenario: 内部对象重建但任务事实未变
- **WHEN** 内部对象释放重建后，Agent 已有的任务信息仍有效且任务事实没有变化
- **THEN** 不仅因内部对象重建收到额外的 Task 责任提醒；实际执行中断且仍有可推进任务时，沿用正常续跑规则。

### Requirement: 真实任务变化 SHALL 在所属聊天以系统消息通知相关者

#### Scenario: 正文、责任或关系发生变化
- **WHEN** 任务被创建、修改要求、改派、改变状态／关系、删除，或成员资格变化影响任务处理
- **THEN** 所属聊天产生说明实际业务变化的系统消息，并 @ 需要重点关注的人或 Agent；正文修改明确要求读取最新正文并提供任务入口，不只报告更新时间或技术版本。
- **AND** 不为同一变化维护一份平行的 Agent 私下责任变更提醒；访问撤销事实仍须到达受影响主体，不能借通知泄露其已无权读取的聊天内容。

#### Scenario: 相关 Agent 离线后恢复
- **WHEN** 真实任务变化发生时 Agent 离线，之后恢复并处理新输入
- **THEN** 能获知尚未消费的变化，已知且未变化的事实不重复生成系统消息；暂停和恢复等必要来源事实保留，todo 或暂停任务的变更通知不等于开工指令。

### Requirement: 普通问答和观察消息不凭空产生任务或授权

#### Scenario: 没有本人进行中任务时收到消息
- **WHEN** 用户发来当轮可回答的问题，或 PA 仅观察到其他聊天的消息
- **THEN** 与现有授权契约一致，Agent 回答实际问题或按观察规则处理，不把无关消息变成新任务，不擅自代表主人发言。

### Requirement: 已接受的长期任务持续推进并真实交付

#### Scenario: 进行中任务跨轮次推进
- **WHEN** 本人 doing 任务仍有可执行工作，一轮回复结束或用户补充信息
- **THEN** Agent 保持原有持续推进责任，结合最新信息推进并核验成果，向任务固定聊天实际交付，不以私有结束语或接单代替完成，不重复发送已确认结果。

### Requirement: Task 操作成功后 SHALL 提醒具体任务的实际交付

#### Scenario: 跨聊天等待或提交成果
- **WHEN** Agent 在聊天 B 处理属于聊天 A 的 Task，并成功登记 waiting 或提交 in_review／done 结果
- **THEN** Reminder 明确具体任务和固定聊天 A，指导交付必要等待说明或核验后的成果；实际交付回到 A，不误发到最近聊天 B 或假定的人类主人。

#### Scenario: 已交付、等待续期或发送未确认
- **WHEN** 相同反馈已确认送达、等待无新内容续期，或一次发送失败／结果未知
- **THEN** 已确认内容不重复发送；未确认发送如实处理，真实任务状态和有效安排不因反馈失败而被伪造或撤销，其他独立工作继续。

### Requirement: 有效等待与复查不因提示精简失效

#### Scenario: 确需等待外部条件
- **WHEN** 已授权任务确认阻塞，其他可做部分已核对，需要后续复查
- **THEN** 按现有 Task 契约建立真实且有效的复查安排，告知必要进展与阻塞；复查时依据最新事实继续或更新等待，不向用户反复汇报无变化状态。

### Requirement: Schedule 用户删除事实与 Task 无有效安排 SHALL 分别提醒

#### Scenario: 用户删除未关联 Task 的 Schedule
- **WHEN** 用户删除某 Agent 的 Schedule，且没有 Task 引用该安排
- **THEN** 该 Agent 仍收到 Schedule 删除事实的 reminder，不以没有 Task 为由省略通知。

#### Scenario: 用户删除 waiting Task 的关联 Schedule
- **WHEN** Schedule 被用户删除后，Task 仍为 waiting 且没有有效的关联安排
- **THEN** Agent 获知 Schedule 删除事实，并收到独立的 Task reminder，指出该任务无法按原计划唤醒，要求检查当前是否已结束、能推进则继续、仍需等待则建立新的有效检查安排。
- **AND** 不以 Schedule 删除通知替代 Task 提醒；Task 不因提醒发出而自动完成或改变状态。

#### Scenario: Agent 自己删除 waiting Task 的关联 Schedule
- **WHEN** Agent 主动删除关联 Schedule 后，Task 仍为 waiting 且没有有效的关联安排
- **THEN** 该 Agent 同样收到 Task reminder，指出任务无法按原计划唤醒，并要求检查任务当前是否已结束、能推进则继续、仍需等待则建立新的有效检查安排。
- **AND** 不因删除由 Agent 自己发起或删除工具已返回成功而省略这条 Task 提醒。

#### Scenario: 多项 waiting Task 失去有效关联安排
- **WHEN** 一次检查发现多项 waiting Task 没有有效关联 Schedule
- **THEN** Reminder 对每项受影响任务列出标题、唯一定位信息和入口，使 Agent 明确要检查和处理哪些任务，不以泛化提醒代替具体任务信息。

### Requirement: 暂停和授权限制 SHALL 保留

#### Scenario: 任务暂停或动作被拒绝后又收到新消息
- **WHEN** 用户已暂停任务或工具动作被拒绝，随后到来无关消息或定时事件
- **THEN** 与现有停止和授权契约一致，不擅自恢复该任务、不绕过拒绝，也不妨碍独立的已授权工作。

### Requirement: 首次运行和恢复后仍能使用当前可用能力

#### Scenario: 新会话或正常换窗后继续工作
- **WHEN** 用户提出适合当前已启用 Skill 的请求，或在恢复后继续已有事项
- **THEN** Agent 仍能发现并按需加载可用 Skill、依据最新任务状态继续；不使用禁用能力，不把旧快照当新授权，不要求用户无故重复背景。

## 影响范围与契约入口

范围覆盖 Nano 自有的 PA/Global 提示、来源规则、相关 Feature 指导、Task 动态提醒，以及首次/后续运行状态和 Skill 目录的注入边界。以 PA 样本发现问题，但共享规则调整须回归受影响的 Global/普通 Agent。

current 契约：[`personal-agent.md`](../../specs/gateway/personal-agent.md)、[`global-agent.md`](../../specs/gateway/global-agent.md)、[`task-graphs.md`](../../specs/gateway/task-graphs.md)、[`agent-capabilities.md`](../../specs/gateway/agent-capabilities.md)。方法遵循 [`Agent Context Engineering`](../../development/agent-context-engineering.md)。本轮不修改 current spec，不以活动 unit 代替当前行为。

非目标：重做 Task 调度或权限模型、改变 Dreaming/记忆写入归属、新增 Agent Loop、批量改写用户自定义指导、为整理文案 fork/patch DSH、在生产发送测试消息。

## 迁移与回滚策略

保留任务状态、历史来源、已交付事实、用户配置和有效授权边界；不清空历史来制造干净的上下文效果，不覆盖已有 Agent 的自定义指导。首次运行、已有会话下一次执行及换窗恢复均应保留回归基线。是否需要一次性迁移由实际设计决定，本问题登记不引入迁移或兼容层。

后续实现若造成漏掉真实任务、遗漏停止事实、丢失能力发现或错误扩大授权，应停止推广并回退相关提示/注入变更；不通过叠加另一层通用提醒修补。新请求验证和行为回归通过后才能宣称优化完成。
