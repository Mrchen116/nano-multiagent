# IM Task Graphs Specification (delta for refactor-679)

## MODIFIED Requirements

### Requirement: 任务协作通知使用所属会话的一条系统消息

真实业务变化统一在任务固定所属会话表达。不引入任务专属讨论区、关注名单、重复私信或额外交接回执。消息对有资格成员可见，@ 为系统识别的有效成员提及；同一主体在一条消息中只提及一次。

| 事件 | 消息内容与重点关注对象 |
|---|---|
| 创建、首次分配、改派或取消分配 | 明确任务和变化，@ 实际涉及的原／新负责人 |
| 正文、要求、标题、结果或等待条件变化 | 明确更新内容类别，@ 当前负责人；要求更新须提示读取最新正文并给入口，不复制全部正文或只报技术版本 |
| 状态变化 | 明确新状态，@ 当前负责人；暂缓／关闭加直属下一层已分配 Agent，待确认／完成加创建者和直属父负责人 |
| 包含、依赖或替代关系变化 | 明确两端及业务含义，@ 直接受影响负责人；父级变化包括原／新直属父负责人 |
| 删除任务／子树／图 | 明确删除事实及原标识，@ 受影响原负责人及相关直属父负责人，不承诺已删除详情仍可读取 |
| 成员资格变化影响 Task 访问／处理 | 明确资格变化及受影响任务；不借通知扩大任何主体访问权限 |

#### Scenario: 改派双方获知
- WHEN 小王把「修复登录失败」从 A 改派给 B
- THEN 所属群出现一条说明从 @A 改派给 @B 的系统消息，其他有资格成员可见，不另发一份私下责任变化快照。

#### Scenario: 要求或关系更新
- WHEN 用户修改任务要求，或改变任务包含／依赖／替代关系
- THEN 消息说明具体任务发生的业务变化并 @ 需要处理的相关者；要求更新提示读最新正文，关系更新标明相关任务，不以 revision 变化代替含义。

#### Scenario: 暂缓／关闭逐层传达
- GIVEN 任务有 A → B → C 三层
- WHEN A 暂缓或关闭
- THEN 同一条系统消息 @ 当前负责人及 B 层已分配 Agent，不跨层主动 @ C；只有 B 的实际处理产生变化时，才继续通知下一层。
- AND 不自动修改 B／C 状态，不终止被通知 Agent 的无关工作。

#### Scenario: 结果向上反馈
- WHEN 子任务进入待确认或已完成
- THEN 同一条系统消息 @ 当前负责人、创建者及直属父负责人；相关者可查看结果并协调，但不因此成为系统强制验收角色，不自动修改父状态。
- AND 系统状态消息不能替代执行者向固定聊天实际交付成果。

#### Scenario: 成员失去任务处理资格
- WHEN 成员移除使 Agent 失去 Task 的访问或处理资格
- THEN 所属聊天保存这次变化，受影响 Agent 能获得必要的资格撤销事实并停止后续相关动作；对其不再暴露群正文、标题、成员列表或其他失权内容。
- AND 同群或同图不等于需要处理，通知不授予访问权；真人仍使用既有成员移除反馈，不新增任务私信。
- AND 已排入 Agent 上下文但尚未实际消费的失权内容须撤销，重启或消息重试不能重新注入；已经消费的历史仍按既有历史契约保留。

#### Scenario: 无业务变化与通知后的行动
- WHEN 读取、内部对象重建或无实际变化的提交发生
- THEN 不生成新的任务变化消息；真实变化的消息沿持久投递在离线后仍可消费，同一事件重试不重复保存或通知。
- AND 通知 todo／paused 等状态变化不等于开工命令，正常续跑、停止和授权边界仍适用。
