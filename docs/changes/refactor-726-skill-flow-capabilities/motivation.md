# refactor-726: 分离开发流程与可组合能力

## Relations

- Related: refactor-565, refactor-679, feat-703

## 原始诉求

> 然后skill体系整体怎么构建，怎么把能力和流程分开，每个流程按照当前的需求，适配不同的能力

> 你新开个worktree，按照你的规划来做

> 你的这个分支很特别，叫develop分支，后面我要再上面做几个需求测一下是否真的可靠，我觉得可靠后，我再合入到main

## 已确认范围

沿用对话确认的方案：流程负责阶段、选择、派发与收口；能力负责专业方法和证据判断；项目规范负责事实和操作入口。任务依据目标、影响和已有证据选择具体问题与能力，能力不绑定固定 subagent。保留独立审查，合并重复的 verification 职责和报告，拆出产品旅程与前端体验，Context 默认阅读实际运行输入。

本 unit 在独立 worktree 的 `develop` 分支实施、提交并推送，作为后续需求试验基线；不创建 main PR、不合并、不部署。用户通过后续实际需求判断可靠性；本轮静态校验和有界演练不冒充自然任务验收。

## 现状痛点

- refactor-565 已合并静态执行者，但当前 workflow 仍要求分别写 code review 与 verification；feat-703 的 verification 重复维护同一缺陷并等待产品报告后再开一轮对账。
- change-reviewer 混合旅程、界面判断与报告/同步流程；Context 与前端方法同时出现在多个角色入口。
- design 模板仍固定“一律走端到端真栈”，限制按实际问题选择证据。

## 目标状态

每个流程在已有任务记录中选择有限、具体的审查问题和证据。按共享材料、工作量和独立性组合能力；每个问题只有一处结论和缺陷记录。修复和版本变化只使受影响判断失效。

## 消费者验收标准

本次不改 Nano 运行时、产品界面或部署配置。消费者是使用仓库 skills 的开发 Agent；以下验证流程使用行为，不启动产品栈。

### Requirement: 需求决定能力组合

#### Scenario: 有界修复
- WHEN 一个 Bugfix lite 只改变工具返回的状态表达
- THEN 保留修复流程与独立代码审查，选择受影响的 Context 问题，不补 Full 设计、无关 UI 或产品全旅程。

#### Scenario: 跨组件界面需求
- WHEN Full 需求同时改变界面交互和模型输入
- THEN 在设计中明确各自问题和证据，按需要组合前端体验、Context、产品旅程，不固定每项一个 Agent。

### Requirement: 独立判断与交付边界保持

#### Scenario: 复用证据与收口
- WHEN 一项审查已完成而另一项仍在执行，或只更新报告
- THEN 流程保留等待状态与有效结论，不重复制造缺陷、重跑或唤醒审查；必要证据缺失时仍不能宣布整体通过。

#### Scenario: 快速开发和生产操作
- WHEN 已有用户验收进入快速开发收尾，或执行获授权部署
- THEN 前者复用用户验收并补必要独立审查；后者只在既有生产授权和范围内验证，不因能力选择自动增加生产写入或新门禁。

## 迁移与回滚

新任务使用新入口；活动任务接手时保留旧报告和证据定位，迁移尚未完成的问题，不重写历史。退役旧 reviewer/verifier 入口及不再使用的模板，现行引用全部更新。归档历史引用保持可解释，文档校验不把历史快照当现行接线。回退本次提交即可；无产品数据迁移。
