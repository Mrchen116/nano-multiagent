# Nano 前端体验与验收

前端设计以 [Crewden 视觉风格和 Web IM 原则](../product/web-im-principles.md) 为准。通用的设计判断、原型范围、对照和自检见 [frontend-experience-review](https://github.com/Mrchen116/dev-workflow-skills/blob/main/skills/frontend-experience-review/SKILL.md) 及其参考。结合实际入口选读 [Nano 真实纠正案例](frontend-experience-cases.md) 中有关操作权重、文字删留、阅读路径和状态布局的经验。

## 验证平台与深度

按本次要证明的行为、平台特有风险和已有证据选择充分且成本最低的验证，不按改动文件的扩展名、客户端数量或角色数量扩大范围。共享业务链路优先在 Web 验证，不默认要求 Web 与 iOS 双端真实操作。

| 本次改动 | 默认验证 |
| --- | --- |
| 后端、工具配置、共享业务语义 | 窄测试与真实接口；需要用户旅程时优先 Web |
| Web 页面或交互 | Web 真实入口，覆盖受影响状态与必要宽度 |
| iOS 简单字段、默认值、设置项增删、已有控件绑定，或不影响排版的文案 | 编译与相关契约/回归测试；共享语义用 Web 验证，通常不启动模拟器 |
| iOS 布局、导航、手势、键盘、无障碍、权限或系统集成 | 在 iOS 真实客户端实测受影响流程 |
| 跨端交接、一致性本身是验收目标，或用户明确要求双端实测 | 两端实测对应结果；不将无关场景也复制到两端 |

design/runbook 和验收派发注明要证明的结果、所选平台、方法及可复用证据，并在 Full unit `design.md` 中按 [五端对齐矩阵](change-workflow.md#五端对齐矩阵) 逐端声明 `shared`、`native-sync` 或 `platform-exempt`。must-match 只为依赖平台呈现的结果指定该端实测，不能把每个共享场景机械展开为双端。出现平台差异、相关回归失败或证据缺口时再扩大；修改 Swift 文件本身不是启动 iOS 实测的理由。未实测的平台界面不写体验 pass，也不因其不在本轮实测范围而自动阻塞。

实施者完成最窄自检，产品 reviewer 独立观察决定性用户结果；共享可信的构建、测试、环境与未失效证据，不要求双方各跑一遍完整平台矩阵。后续修订只复验失效范围。

## 实施验收前置

Runbook for Reviewer 列出本 unit 相关服务的停止、启动/构建和健康检查命令，以及所选平台的入口驱动方式。不改客户端面时可用客户端实际调用的同一接口；客户端变化按上述平台与深度选择验证，只有需要证明的视觉、交互或平台能力才要求在对应真实客户端操作。

常规真实产品验收复用 [固定日常模板](worktree-runtime.md#固定日常验收模板)（`--profile daily`），每个需求独立启动。runbook 只列本次需补充的角色、数据、权限或专项 profile，固定阵容、模型和审核配置以模板及本轮 `.e2e-daily.json` 为准，不复制生产配置或每次重写一套基线。

从必验旅程确定账号、凭据、测试租户、外部对象、权限或硬件的来源和可用性；没有则写“无”。未落实的必验资源阻塞 Gate 2；只有用户明确调整验收范围或授权替代验证后才能改变标准。运行隔离遵循 [worktree-runtime](worktree-runtime.md)。
