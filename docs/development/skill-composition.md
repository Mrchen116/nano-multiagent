# 流程与能力组合

流程决定何时做、为何做和何时结束；能力提供解决某类问题的方法；项目规范提供事实、约束和操作入口。按本次目标选择能力，不把 skill 数量当作阶段或 Agent 数量。

## 职责与加载

| 部分 | 负责 | 不负责 |
|---|---|---|
| 流程 skill | 阶段、选择能力、派发、处理发现、交付与恢复 | 重复编写专项判断方法 |
| 能力 skill | 适用问题、必要输入、专业方法、证据边界、结束条件 | 自行新增阶段、派 Agent、扩大授权或决定交付 |
| 项目规范与参考 | 架构、current 行为、环境、工具和取证入口 | 复制流程与能力正文 |

先读取当前流程和任务材料，只加载选中的能力；参考按具体问题读取。不把所有能力嵌入流程正文，也不要求每项任务建立全能力清单。能力可以供作者自检和独立审查复用，执行身份决定证据性质；作者换上下文或加载审查 skill 不会成为独立审查者。

## 从需求选择问题

在已有任务记录中说明：要实现的结果、可能使结果不成立的实际影响、需要的观察及可复用证据。用简短叙述或下表即可，不另建能力计划文件。

| 本次必须回答的问题 | 能力与使用阶段 | 证据方法、范围与已有定位 |
|---|---|---|
| <具体理解、行为或边界> | <所需方法；设计/自检/审查> | <能直接判断的证据；已有或待取得> |

先保证重要目标、关键设计决定及实际影响都有充分的判断方法，再删除没有对应问题的能力。独立审查者检查遗漏，不受作者只挑容易通过项的限制；发现新增影响时通知流程补问题和必要范围，不自动扩大为全量检查。

| 能力入口 | 选择依据 | 主要证据 |
|---|---|---|
| [代码正确性](../../.agents/skills/change-code-review/SKILL.md) | 实现审查、需求遗漏、设计一致性、最终 delta 校对 | diff、调用链、相关契约与针对性测试 |
| [Agent Context](../../.agents/skills/agent-context-review/SKILL.md) | 改变模型可见内容及选择、加载、注入、更新或恢复 | 设计样例；实际交付输入与后续行动 |
| [前端体验](../../.agents/skills/frontend-experience-review/SKILL.md) | 信息组织、视觉或交互影响用户理解和操作 | 实际原型/产品画面、连续操作与受影响平台 |
| [产品旅程](../../.agents/skills/product-journey-review/SKILL.md) | 需要跨组件证明用户从真实入口完成目标 | 实际入口、交付结果与关键恢复过程 |
| [性能](../../.agents/skills/performance-review/SKILL.md) | 性能是目标，或有具体运行代价需要判定 | 同条件基线/候选测量、行为不变量 |
| [架构设计](../../.agents/skills/codebase-design/SKILL.md) | 实质模块职责、接口、依赖或测试边界决定 | 真实调用方、约束、可复用机制与取舍 |

这是选择入口，不是固定套餐。权限、迁移、并发等问题先落到相关能力及项目规范，不为每个关键词创建新 skill。阶段尚无实现时审样例和验证方案；已有实现时用对应运行产物，不混淆两类结论。

## 组合执行

流程根据共享材料、工作量、观察视角和独立性组合任务。例如代码正确性与实现覆盖一次完成；前端体验与产品旅程共用一次操作；小范围 Context 可与代码审查合并，复杂多轮加载/恢复可单独执行。不同能力之间不默认要求人员隔离；独立审查者必须未参与受审对象的创作。

派发提供目标与预期、受审版本/范围、本次问题、所需能力、证据位置及缺口、现场授权和输出位置。不继承整段作者会话或用作者成功叙述替代原始材料。能力指出缺口和新增影响，编排者决定调整范围与人员。

环境与运行证据尽量一次准备，版本、输入、方法和限制明确。共享证据不等于共享判断；审查者亲自阅读决定性原始产物，必要时独立补跑关键条件。无需因为换人重新起栈或重复完整矩阵。

## 结果与收口

能力返回：本次问题、执行者/模式、实际版本与范围、判断、决定性证据及限制、问题或未验证项。没有发现也说明实际覆盖，不能只凭空 findings 宣布整体完成。能力不自行提交报告、push 或制造新报告文件；按 caller 指定位置返回。

change unit 的实施审查统一由流程归集到 `review.md`，保留执行者归属和原始结论。并行执行者返回结果，由 owner 串行写入，避免互相覆盖。设计审查继续使用 `design-review.md`。独立任务没有 unit 时直接返回，不强制建立 unit 或报告。

同一缺陷只有一个 ID 和一份关闭记录，其他问题引用它。结果区分：

- 已看到具体缺陷：记录触发条件、影响与证据，交 owner 判真修复。
- 检查尚在运行：流程记录 pending，不生成另一个审查 finding。
- 必要观察无法取得：记录 inconclusive 和明确缺口，不能宣布相关目标通过。
- 未受影响的结论：引用原版本和证据，说明保留理由；不能冒充本轮重跑。

流程收口只核目标覆盖、阻塞问题、必要证据及最终版本有效性，不重做所有能力。统一模板和复验细节见 [validation](../../.agents/skills/change-orchestrator/references/validation.md)；各生命周期何时选择、何时结束见 [change-workflow](change-workflow.md)。

## 其他流程与历史接手

故障调查按待验证假设选择能力，已足够的日志不必重跑任务；部署按目标版本、迁移和运行入口选择核对方法，始终遵循原授权与生产边界；探索性试用按用户目标选择观察面，不自动成为开发交付门禁。

旧 `change-verifier` 的需求/设计一致性与 corrected-delta 判断已归代码审查，证据齐备检查归流程；旧 `change-reviewer` 的方法归产品旅程与前端体验。接手旧 unit 保留 verification/acceptance/regression/code-review 报告，引用有效结论和未关闭问题，后续结果写 review.md。不回写历史，不仅因入口或格式变化重新验收。
