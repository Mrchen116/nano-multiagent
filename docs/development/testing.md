# Testing

目标：让 worker 写出**保护真实回归风险、且不腐烂**的测试。测试的价值在“每次改动被它挡一次”，不在数量。写之前先问“它要防什么失败、能从哪里观察、谁已经在保护”，而不是想到什么测什么。

> 适用面：本指南适用于本仓所有新增、修改、删除的自动化测试与测试门禁。

## 1) 永久测试的准入与停止条件（核心）

一项测试只有同时满足以下条件，才值得进入长期套件：

1. 它保护一个明确、稳定的**产品、公开接口、运维或架构边界**回归风险；
2. 它从有意义的可观察 seam 断言结果，而非窥探当前内部做法；
3. 它位于能暴露该失败原因的最低层；
4. 没有已有测试已经承担同一失败原因；
5. 它有明确的归属文件和长期运行门禁。

- 首文档/design 的退出标准是主要来源，但不是“每一条文档句子对应一个测试函数”。一个连贯的风险链可以由一个测试保护；已有覆盖足够时不新增。
- 实现中发现首文档遗漏的真实、稳定风险时，先交回对应 owner 补充需求/design 决策；仅属于
  测试实现取舍时，在实际存在的实施记录或 DONE 回报中说明来源和边界，再建立保护。不要因为
  原文没写就忽略风险，也不要把假想边界当永久契约。
- 断言稳定、可观察的结果：用户可见输出、公开 API/协议、持久状态、跨模块边界、进程/运维结果或明确的架构依赖。mock 调用次数、内部调用顺序、私有状态、文案细节和文件布局，只有它们本身就是已声明的公开协议或契约时才可断言。
- MUST NOT 测：私有函数/实现细节、框架本身、语言特性（如 getter 返回了它该返回的）。改个内部写法就变红的测试是**负债**——删掉或重写为行为保护。

### 受影响的既有测试是持续维护资产

当 milestone 改变实现路径、公开/架构 seam、测试层级、fixture/harness，或发现旧测试前提失效时，
必须先定位受影响的既有覆盖并形成可审查的处置结论。只审本 milestone 影响的测试，不建全仓台账；
复杂 milestone 可写入 `tasks.md`，简单情况在 DONE 回报中概括，没有受影响覆盖时说明搜索范围和理由。

| 处置 | 适用条件 |
|---|---|
| `keep` | 直接经过当前的用户、公开接口、运维或架构 seam，保护仍存在的风险，且处于最低合适层 |
| `rewrite-merge` | 风险仍在，但测试断言旧内部步骤、跨层重复，或把可由同一 seam 覆盖的风险拆成重复测试；改为从当前 seam 观察结果 |
| `delete` | 只守历史文本/布局、私有符号、退役路径、一次迁移或临时证据，且没有当前风险需要长期保护 |

若风险仍在，删除旧测试前必须先确认保留保护，或建立并跑通最低层替代保护；只有没有当前风险时才可无替代删除。精确文本断言只用于协议、schema、序列化格式或写入 current 契约的用户可见文本，不能因为实现或文档曾出现某句话就固定它。

## 2) 先定位，再决定新建（对治文件爆炸）

写任何测试前 MUST 先回答：**“这个失败原因现在由哪个文件保护？”**

- 已有测试承担**同一失败原因** → 扩展、参数化、合并或直接保留；不要新建一份平行保护。
- 新风险有不同的语义 owner、落层或运行门禁时才新建文件；不能为了避免新文件而把无关行为继续
  堆进旧文件。新建理由应能从实施记录、commit 或 DONE 回报复查。
- 默认动作是先找到风险 owner，而不是新建 `test_<milestone>.py`；milestone 不是长期测试分类。
- 新测试完整替代旧测试的保护 → 删旧的；不能仅因名称相近就删掉仍覆盖不同失败原因的测试。

## 3) 命名与落层

**命名**：文件名/函数名描述**被测行为**。
- ✅ `test_loop_compact.py` / `test_mark_stale_for_node`
- ❌ MUST NOT 用流水号：`test_m170_*` / `test_bugfix358_*` / `test_refactor353_corrigendum` / `*_rerun_acceptance`。milestone 编号是"写的时候"的上下文，半年后无人能解读。

**落层**：目录即分层，按“能暴露该失败原因的最低层”选：

| 测什么 | 目录 | marker |
|---|---|---|
| 纯逻辑、单模块 | `tests/unit/` | — |
| 跨模块/真实入口(HTTP/CLI 子进程,本地无浏览器) | `tests/integration/` | — |
| 架构边界/契约(依赖方向、事件 schema) | `tests/contract/` | — |
| 起真进程 / 真浏览器 / 真 LLM / 重外部依赖 | `tests/e2e/` | `@pytest.mark.e2e` |

- 浏览器(playwright)、真实 LLM、真实长驻进程的测试 **MUST 放 `tests/e2e/`**。`tests/e2e/conftest.py` 会按路径统一添加 `e2e` marker，不要求每个文件重复声明；放错目录会让 `pytest -m "not e2e"` 误跑它。

## 4) 跨层不重复

- 同一**失败原因**只在能暴露它的最低层保留一份永久保护，不是把同一产品行为机械限制为一层。
- unit 已覆盖的逻辑，integration 只验证接线、跨边界、真实配置或进程协作等 unit 测不到的风险；e2e 只验证真实入口和用户旅程特有的风险。
- 不要为同一个 milestone 在 unit + integration + e2e 各写一遍同样的断言；高层测试若保留，必须能说清它与低层测试不同的失败原因。

## 5) 可选/重依赖必须优雅跳过

外部或可选依赖(playwright、需要起服务的库等)**MUST NOT 在模块顶层裸 import**——否则缺依赖时整个 `pytest --co` 收集中断，全套测试一个都跑不了。

```python
import pytest
playwright = pytest.importorskip("playwright")   # 缺依赖 → skip 本文件，不炸收集
```

## 6) 临时验收证据 ≠ 永久回归测试

TDD 过程里产生两种东西，去向不同：

- **一次性验收证据**(手动验收脚本、截图、"这次交付时验一下"的清单)：路径/结论记进实际存在的
  `progress.md`、DONE 回报或 PR Validation Summary，**MUST NOT 作为 `test_*.py` 提交进测试套件**。
  milestone 收尾删掉一次性脚本。
- **永久回归测试**（在其固定质量门禁中长期运行、有持续回归价值的断言）：才进 `tests/` 套件。

判据：问自己“半年后它是否仍应在自己的固定质量门禁中运行，并在风险回归时失败？”——否 → 它是验收证据，不是回归测试。

一次性证据的 Claim/Baseline/Method/Result/Locator/Limit 记录方式、保存位置和 promotion 规则见 [`evidence.md`](evidence.md)。

**被测逻辑 MUST 住在 `src/`，不靠 `importlib` exec 一次性脚本取用。** 反模式:把有回归价值的纯逻辑(DB 读取、解析、状态判定)留在 `ACCEPTANCE/*.py` 这类一次性验收脚本里，测试用 `importlib.util.spec_from_file_location` 把整个脚本 exec 进来取函数。后果:① 脚本的顶层依赖(playwright 等)会连坐进收集，缺依赖就炸；② 被测逻辑不在产品代码里，等于没真正落地。正确做法:有长期价值的逻辑提进 `src/`，测试直接 `import`；一次性脚本不作为被测对象。

## 7) 结构与上限

- AAA 结构(Arrange-Act-Assert)，一个测试一个清晰主题。
- 新增测试文件不得超过 **400 行**，超出时按行为拆分；扩展既有超长文件时，不继续向其中堆积新的独立行为。
- MUST NOT 用无条件 `skip`/`xfail` 蒙混过关。测试该绿就让它绿，该删就删。第 5 节的 `importorskip` 和已有的环境能力门禁用于“依赖/能力确实不可用”的场景，不是隐藏产品失败。**唯一合规的产品 xfail 例外**：已知产品回归（测试正确、产品有 bug）可打 `@pytest.mark.xfail(strict=True, reason="<现象>; tracked in #<N>")`，条件：① 必须附 issue 编号；② `strict=True`（修好后转 xpass 自动报错，强制摘标）；③ 该测试不得删除（删除=掩盖 bug）。无 issue 编号的 xfail 视同蒙混，审查拒绝。
- 复用现有 fixture/helper，不重复造。

## 8) 测试策略必须可复查

已派发 worker 固定创建简短 `tasks.md` / `progress.md`，但不必把完整测试策略台账填进 `tasks.md`。
复杂 milestone 可在其中展开；简单 milestone 只保留实际实施块、验证和必要结论。直接闭环或简化流程
可以在 commit/DONE 回报中留下同样可复查的信息：

```markdown
## 测试策略

- 保护的回归风险与可观察 seam: <行为/边界；失败时能看到什么>
- 已有保护与处置: `<file>`(keep / rewrite-merge / delete) / 无；同一失败原因为什么未被重复保护: ___
- 落层/目录/marker: tests/<unit|integration|contract|e2e>/ , marker: <e2e|无>；为什么这是最低能暴露该失败原因的一层: ___
- 文件归属: 扩展 `<file>` / 新建 `<file>`，理由: ___
- 可选依赖 importorskip: <有,哪些> / 无
- 本 milestone 产生的一次性验收证据(收尾删除,不进套件): <列出> / 无

### 受影响的既有测试处置

| 风险 / 行为 | 既有测试 | 处置 | 理由与保留或替代保护 | 验证 |
|---|---|---|---|---|
| <当前应防的回归> | `<path::test>` / 无（附搜索范围） | keep / rewrite-merge / delete | <为何这样处置；若风险仍在，最低层保护在哪里> | <命令或证据> |
```
