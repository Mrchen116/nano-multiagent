# Web IM Principles

Web IM 是用户理解 Agent 团队、发起协作和管理节点配置的默认界面。以下原则约束跨版本体验取舍；具体页面行为由 [`docs/specs/im/`](../specs/im/spec.md) 定义。

## 对话优先

主路径始终围绕“找到会话、读懂上下文、发送消息、看到结果”。配置、诊断和运行信息服务于这条路径，不应让用户先理解内部架构才能开始聊天。

## 高信息密度，但保持清晰层级

会话、消息、工具过程、响应指标和状态可以同时存在，但主要对话内容优先。次要过程按层级和需要展开，避免把运行遥测与用户可见回复混成同一种信息。

## 桌面与手机使用各自自然的导航

桌面端可以同时呈现会话列表和当前消息流；手机竖屏以列表与详情之间的单栏切换为主。响应式设计围绕设备上的实际任务重组信息，而不是把桌面页面等比缩小。

## 在用户操作前说明当前是否可用

节点未绑定、Gateway 离线、数据加载失败或配置尚未应用时，界面应在对应操作点显示状态和下一步。输入区、保存按钮或危险动作的可用性与真实后端状态一致，提交失败时尽可能保留用户尚未完成的内容。

## 历史与实时事件组成一条连续时间线

刷新、分页、断线重连和配置切换不能让用户误以为消息消失、重复或属于另一段会话。实时事件最终与持久历史收敛；用户上滚阅读历史时，新事件不应无故夺走阅读位置。

## 会话身份必须可辨认

用户与 Agent 单聊、Agent 间会话、群聊、系统 feed 和外部通道影子会话具有不同语义。列表、标题、参与者和操作入口帮助用户理解“谁在和谁说话”以及回复会去哪里。

## 配置展示期望状态，也展示实际运行状态

用户通过 Web IM 管理 Agent、节点和外部通道时，保存成功只说明期望配置已经提交；节点是否在线、能力是否可用、通道是否真正连接需要独立呈现。前端不猜测节点本地能力，以节点当前上报和校验结果为准。

## 动效和视觉装饰服从阅读效率

消息出现、页面切换和状态变化可以使用克制的过渡，但不干扰文本选择、滚动、复制或连续阅读。视觉差异用于表达发送者、层级和状态，而不是增加无含义的装饰。
