概述

本次评审对 nano-multiagent 应用 /codebase-design 词汇（module、interface、depth、seam、adapter、leverage、locality）进行深模块扫描。发现两类主要摩擦：一类是删除后复杂度直接消失的死 shim；另一类是表面入口很窄、但真实 interface 通过私有字段接线、共享状态和穿透式测试泄漏到调用方的大型 module。文件行数和 implementation 宽度本身不是问题；判据是调用方必须掌握多少隐含不变量，以及状态与生命周期是否有单一 owner。

1. Platform Tool Registry 透传 shim

src/agent/platform/tools/registry.py（5 行）

Strong

Problem

该文件只是 agent.core.tools.registry.ToolRegistry 的纯 re-export；生产代码没有调用方，只有旧测试仍依赖这条兼容路径。删除测试很明确：删掉它不会让复杂度转移，而是直接消失。

Solution

删除这个 shim，并把测试导入迁到 canonical agent.core.tools.registry。工具加载与 SDK 装配若要收敛，应单独治理现有 platform.tools.loader 与 sdk.kernel 的策略重复，不把这个死路径改造成第二个 factory。

Benefits

  • Leverage: 调用方只需学一个概念，而不是两个完全相同的东西。
  • Locality: ToolRegistry 的 identity 与测试锚点只留在 canonical module。

2. SDK Kernel facade 混合装配、API 与 DTO 映射

src/agent/sdk/kernel.py（1,870 行）

Worth exploring

Problem

build_kernel() 与 Kernel 位于同一文件。该文件同时承担模型注册表初始化、LLM client 工厂装配、hook registry 装配、tool registry 装配、workspace 工具扫描、self-evolution 配置读取、权限 broker 绑定以及 DTO 翻译。Kernel 暴露了 20 多个公共方法，interface 过宽。

Solution

拆分为三个 deep module：KernelAssembler（窄 interface assemble(config) -> components）、Kernel（仅暴露 session/run/stream/permission 语义），以及一个边界映射模块，统一拥有 SDK-to-internal 的 DTO 转换。

Benefits

  • Locality: 装配 bug 留在 assembler，而不是公共 API 文件里。
  • Leverage: 测试公共 Kernel 只需了解语义层面，无需掌握 wiring graph。

3. 权限请求闭包缺乏 locality

src/agent/core/agent/runtime.py（2,177 行）

Worth exploring

Problem

AgentEngine._build_hook_context() 在运行时现场构造了一个巨大的 async 闭包 _permission_requester，其中混合了 PermissionBroker future 注册、事件发送、can_use_tool callback 与 broker future 的 race、权限等待期间的 liveness ticker、响应对象 duck-typing 构造以及取消/超时/异常回退。真正的 bug 不在某条纯函数里，而在「怎么被构造、怎么被调用、怎么与 run lifecycle 交互」。

Solution

把权限请求流程抽象成一个注入式的 PermissionRequester adapter，窄 interface 大致为 request(req) -> response。AgentEngine 只负责把它注入 HookContext；具体的 broker/publisher/ticker/race 逻辑封装在 platform 层的 deep module 里。

Benefits

  • Locality: 权限 race 逻辑集中在一个 adapter，不再散落在 engine runtime 各处。
  • Testability: engine 单元测试注入 fake requester；requester 测试独立演练真实 race 条件。

4. InboundPipeline 的真实 interface 与状态所有权泄漏

src/personal_assistant/gateway/inbound_pipeline.py · src/personal_assistant/main.py · gateway/runtime_delivery/

Worth exploring

Problem

窄 handle_inbound() 隐藏宽 implementation 本身是 depth；真正的摩擦是其真实 interface 被藏在 18 个构造参数、main.py 对 6 个私有字段的事后接线、其他运行时对 _agents/_session_store 的直接读取，以及大量测试对私有状态的穿透中。active run、steer、/stop、terminal reconcile、附件预处理和 background subscriber 还拥有不同的状态生命周期。

Solution

保留 InboundPipeline 作为稳定 facade，按状态 owner 深化为 LiveAgentCatalog/SessionBinder、SessionRunCoordinator、ImageAttachmentResolver 与 BackgroundSubscriptionManager。/stop 必须与 steer、active-run marker、stream terminal 和 reconcile 一起归 SessionRunCoordinator；relay lifecycle 继续复用现有 runtime_delivery.lifecycle seam，不重复提取 emitter。

Benefits

  • Locality: stop、steer 与 terminal 不变量集中在一个 run module。
  • Leverage: composition root、运行时与测试只跨显式 interface。
  • Testability: 测试不再修改 pipeline 私有状态。

5. Kernel event observer 是巨型事件翻译闭包

src/personal_assistant/gateway/runtime_delivery/observer.py（1,191 行）

Worth exploring

Problem

build_kernel_event_observer() 返回的闭包是一条超长的 if/elif 链，覆盖 run_status、assistant_message、turn_end、tool_start/tool_end、permission_request/permission_resolved、injection_consumed、run_terminal_reconcile、run_heartbeat、thinking_segment 等。路由逻辑与每种 event 的具体翻译压在一个函数里，新增 event 还得改同一个 1,191 行的文件。

Solution

把 observer 改成 event name → handler 的注册表/dispatcher。每个 handler 是一个独立 deep module，只暴露 handle(event, run_context, manager)。build_kernel_event_observer 变成 narrow seam：负责 context lookup、dispatcher 调用、公共错误 swallow。

Benefits

  • Leverage: 新增 event type 只需写新 handler，不必让中央闭包继续膨胀。
  • Locality: heartbeat lazy bubble、reasoning deduplication、external reply mirroring 各自独立成模块。

6. IM GatewayHandler 是 WS/RPC/streaming god class

src/IM/ws/gateway_handler.py（2,306 行）

Speculative

Problem

GatewayHandler 同时持有连接表、9 种 request/response waiter dict、node/agent 状态广播、streaming_delta 翻译、agent.message 持久化、delivery receipt 处理。handle_message() 是超长 if/elif 链，_handle_streaming_delta() 内部又是按 kind 的巨型 switch。request_agent_config、request_agent_create、request_agent_capabilities、request_fork_session 等方法大量重复「生成 request_id → 建 future → push_downstream → wait_for → cleanup」的样板。

Solution

抽出 GatewayConnectionManager（只负责 WS 连接注册/断开）、GatewayRPCHandler（把 request/response waiter 模式封装成统一 RPC seam）、StreamingDeltaTranslator（与 observer.py 对应，按 kind 分发成 handler 注册表）。GatewayHandler 只保留协议顶层路由。

Benefits

  • Leverage: RPC 样板只写一次，所有 request type 复用。
  • Locality: streaming 翻译改动只影响 translator，不影响 connection manager。

7. IM repositories 是单体持久化层

src/IM/infra/repositories.py（3,959 行）

Worth exploring

Problem

一个文件里塞了 UserRepository、ConversationRepository、MessageRepository、EventRepository，以及大量 SQL、row-to-model 映射和辅助查询。find_or_create_external_conversation()、create_message()、update_runtime_state() 等方法包含大量分支和特殊 case。新增查询要编辑一个近 4,000 行的文件，locality 差；测试也难以针对单一 repository 进行。

Solution

Benefits

  • Locality: 消息持久化改动留在 message 模块。
  • Testability: 每个 repository seam 都可通过专注的 in-memory adapter 测试。

8. Gateway main.py 混合产品装配与进程生命周期

与 REFACTOR-461 重叠

src/personal_assistant/main.py（4,376 行）

Skip

本次评审忽略: 该候选与正在推进的单元 refactor-461-dead-kernel-subprocess-seam 直接重叠，后者已在重塑 Gateway composition root、service lifecycle 和配置所有权。请勿在此处并行启动重构。

Problem

Gateway 入口同时承担参数解析、子进程启动/守护、kernel/SDK 装配、channel/scheduler/IM connection/heartbeat/cron 生命周期、内部 HTTP dispatch server、信号处理、capability 上报。虽然已经在使用 ProcessLike、ProcessFactory、ReadyWaiter、AsyncConnect 等可注入 seam，但它们都住在同一个文件里，composition graph 与进程生命周期仍然耦合。

Solution

将 build_runtime(config) 提升为独立的产品 composition root，输出 GatewayRuntime。引入 LaunchMode adapter seam 处理 foreground、daemon、attach 模式。main.py 退化为只做 argparse 并调用 composition root 的薄入口。

Benefits

  • Leverage: 同一 runtime 可通过切换 launch adapter 在测试、前台、守护模式下启动。
  • Locality: 进程启动 bug 与产品装配 bug 分离。
