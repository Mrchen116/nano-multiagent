Change Review Gates

速读版 讨论原话 核心模型 Change 类型 Verification Plan 330 / 重构 视觉 Gate Skill Set 评测

核心结论

不要把所有 change 都塞进产品验收。

reviewer 应该按 design 里的 Verification Plan 执行 gate。用户侧功能走产品验收,平台能力走技术契约验收,内部重构主要看回归和工程证据。

保留一个通用 reviewer skill,不要拆一堆 reviewer。复杂度前移到 design 的 gate 设计。

讨论原话

“对于这种软件内部的改动，好像产品侧不需要验收……有的需求是完全是重构代码相关的，完全没有用户侧变化。”

设计约束:不是所有 change 都有 product acceptance。

“我们参考传统的人类的开发流程，应该怎么设计，是否需要多个不同的类型的reviewer，根据需求而定，还是如何。”

设计约束:先按风险决定需要哪些 verification gates。

“可以合起来就是一个skill，然后在design阶段，明确当前需求需要哪些类型的review，具体review什么，然后在review阶段去读design的要求。”

设计约束:一个 reviewer skill + design 阶段 Verification Plan。

“改了之后我应该怎么验呢？应该拿我过去做过的一些需求来测试新的skill集合是否ok对吧。”

设计约束:skill set 本身要有 regression/eval。

核心模型

Spec

说明目标、用户/外部 actor、范围和非目标。

Design

写 Verification Plan:这次要过哪些 gate,谁负责,证据是什么。

Worker / CI

实现代码,留下工程 gate 的测试和证据。

Reviewer

只执行 owner=reviewer 的 gate,并检查其他 owner 的证据是否存在。

Change 类型

类型 例子 主要风险 常见 gate
User-facing feature 新页面、新 CLI 命令、新交互 用户不能完成任务,体验偏离设计 product visual regression
Developer/platform feature API、CLI 契约、文件格式、事件流、session 存储 外部契约不稳定,下游无法使用 technical engineering
Internal refactor 模块拆分、依赖方向调整、内部存储替换 行为回归,模块边界破坏,测试缺口 regression engineering
Bugfix 修复已知验收问题或线上问题 复现未闭环,同类场景回归 regression
Performance / security 缓存、批处理、鉴权、权限隔离 指标无改善、越权、泄露、边界不清 benchmark boundary

Verification Plan

design.md 里建议新增强制段。reviewer 以后读这个执行,不是自己猜。

Gate Type Owner Scope Evidence
V1 product_acceptance reviewer 用户能完成主路径 真实浏览器/CLI 截图、录屏、终端 transcript
V2 technical_acceptance reviewer 外部 API / CLI / 文件契约可用 命令输出、JSON、文件片段
V3 engineering_verification worker / CI 内部算法、边界、并发、性能假设正确 pytest、CI、benchmark、contract test
V4 regression reviewer / CI 已知 bug 不复现,相邻路径不坏 复现步骤闭环、测试输出
V5 visual_reference reviewer 当前实现对齐原型 / 设计稿 / reference repo 内 reference + actual 截图和对照结论

例子

330: session context storage

它不是普通产品功能,而是 developer/platform feature + internal architecture change。

  • Reviewer 验:CLI/API 多轮历史连续、重启 resume、不丢历史、JSONL 文件可解析。
  • Worker/CI 验:warm turn 零磁盘读、compact/fork/load 算法、并发锁、flush 语义。
  • 不应强行要求普通用户 UI 产品验收。

纯重构

可以没有 owner=reviewer 的 product gate。

  • 必须有 regression evidence:相关单测、集成、contract 全绿。
  • 可以有 engineering review:模块边界、依赖方向、复杂度下降。
  • 如果公开文档受影响,加 doc_acceptance。

视觉 / Reference Gate

  • reference 和 actual evidence 要落到 repo 内或长期可访问位置,不能只放 /tmp。
  • 最终 pass 前必须用当前实现重新跑 reference gate,不能只继承旧轮分级。
  • 如果 spec 写“像素级对齐”,就不能默认把“近”当 pass;阈值必须由 design 先定义。
  • 功能 gate 和视觉 gate 分开。功能修通不等于视觉通过。

Skill Set 评测

改 skill 后,要拿历史需求做 workflow regression suite。目标不是重测业务代码,而是看 skill 是否能稳定做正确流程决策。

Eval 样本
样本 来源 评测重点
E1 UI feat-340-agent-native-im product + visual_reference;最终 pass 前必须有 reference + actual evidence。
E2 Platform feat-330-session-context-storage technical + engineering;跳过普通产品验收。
E3 Bugfix bugfix-331 / bugfix-339 原始复现步骤闭环,同类场景不回归。
E4 Mixed feat-334-tool-result-budget 用户可见输出 + 内部预算策略测试。
E5 Refactor 造一个 fixture 无 product gate 也能合法流转,但不能缺 regression evidence。
关键反例
  • 视觉缺证据:只有组件测试和实际截图,没有 reference 对照,必须 fail。
  • 平台能力误派产品验收:330 类需求不应被要求普通 UI 用户旅程。
  • 纯重构无用户变化:可以跳过 product gate,但缺 regression evidence 不能进 PR。
  • 历史结论继承:上一轮 near 不能替代本轮当前实现的 reference gate。
  • 工程 gate 伪装用户验收:多轮聊天成功不能证明 warm turn 零磁盘读。
通过门槛
  • 6 个 eval 样本里,核心 gate 类型和 owner routing 至少 5 个正确。
  • 所有关键反例都不能被错误 pass。
  • UI 样本必须要求真实入口截图和 reference 对照。
  • platform/internal 样本不能被强行要求普通产品验收。
  • reviewer 报告中的每个结论都能追溯到 Verification Plan 的 gate ID。
