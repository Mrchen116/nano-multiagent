# gateway (personal_assistant) - Global Agent Specification

> 对齐: feat-805
> 上级: [gateway (personal_assistant) Specification](spec.md)

## Purpose

全局 Agent 跨聊天持续工作、Inbox 摄取、内部委派、显式投递、群聊及私聊发送前复核和主上下文控制的 Gateway 契约。

## Requirements

### Requirement: 全局 Agent 跨聊天保持连续的工作认知

#### Scenario: 使用另一个聊天中已读取的相关条件
- **GIVEN** 全局 Agent 已在 A 聊天读取并确认一项工作约束
- **WHEN** 它在 B 聊天处理与该约束相关的事项
- **THEN** 它能沿用该约束，用户不必仅因换了聊天而重新说明

### Requirement: 依据配置接收信号，并自主安排读取

#### Scenario: 忙碌期间有其他聊天的新请求
- **GIVEN** 全局主 Agent 正在处理工作
- **WHEN** 其他聊天发来符合接收条件的新请求
- **THEN** 新请求保留供其读取，不因收到请求就强制中断当前工作
- **AND** 范围内直接找 Agent 的新输入或已到期的普通消息在主 Agent 下一次模型请求前提供 Inbox 系统提醒，不必等当前任务结束；已开始的模型请求和工具执行不被硬中断
- **AND** 下一次模型请求前积累的多条应提醒的新输入合并为至多一条新的 Inbox 系统提醒；各条消息正文仍完整保留供 Inbox 读取
- **AND** 合并提醒直接提供各未读会话的名称、私聊/群聊类型、可读取引用、未读消息数和实际 @ 本 Agent 的消息数；计数来自未读消息元数据，不把私聊、回复或找主人的消息等同于 @ 本 Agent
- **AND** 提醒与主动 check 逐会话展示本次可见未读消息中最晚的原始发送时间，时间明确时按新到旧排列，未知时间不冒充新消息。
- **AND** 提醒进入模型上下文后，再到达的新输入可以在后续模型请求中触发新提醒
- **AND** 提醒不包含新消息正文或代表真人授权，正文与来源仍通过 Inbox 主动读取；原发送前复核继续生效
- **AND** Agent 可直接使用提醒中的会话引用按需 read，或继续当前工作；check 仅在需要刷新摘要时主动调用，不是读取正文的前置要求
- **AND** 用户能在工作视图中查看其后续读取和处理过程

#### Scenario: 空闲时收到符合触发条件的输入
- **GIVEN** 全局主 Agent 空闲
- **WHEN** 收到符合该 Agent 触发配置的输入
- **THEN** 它能开始处理，不要求用户额外操作才能唤醒

#### Scenario: 普通群聊更新遵循各 Agent 配置
- **WHEN** 群内有未提及某个全局 Agent 的普通更新
- **THEN** 「团队公开」（`team`）下在所参与群内立即可读，「项目级」（`project`）下在所参与的未解散私密群内立即可读，遇到下一条高优消息或自首条积压起十分钟，先到者触发一次合并提醒；无新增不唤醒，持续来信不延后期限。「私有」（`owner_only`）下仅接收同主人私密专属群（仅含主人本人及同主人名下 Agent）的更新，不接收含外部成员群聊的消息
- **AND** PA 自己作为成员参与的群聊同样遵守其所选两档规则。

#### Scenario: PA 通过主人观察未参与聊天
- **WHEN** PA（无论处于「团队公开」还是「私有」）通过主人权限接收自己未参与且未被排除聊天的更新
- **THEN** 它们按 [personal-agent](personal-agent.md) 的主人目标和背景规则保存和通知，保留旁观身份；主人直接请求仍及时通知且可读取相关背景。

### Requirement: 全局模式向目标群或私聊发言前复核应处理的新消息

#### Scenario: 没有新消息时正常发言
- **GIVEN** 全局 Agent 准备向内置 Web IM 群或已有私聊发送消息
- **WHEN** 目标会话没有它尚未读取、按其配置需要处理的新消息
- **THEN** 可以正常发言，不需要用户批准或额外触发

#### Scenario: 目标群的新更正被考虑
- **GIVEN** 全局 Agent 正准备向内置 Web IM 群回答一项安排
- **WHEN** Gateway 在发言前收到该群按 Agent 配置需要处理的新更正
- **THEN** 旧草稿不先公开，Agent 读取新信息后重新判断再交付
- **AND** 新信息不影响原结论时可保留原文；是否允许静默仍遵循原有规则

#### Scenario: 复核期间又收到适用的新消息
- **GIVEN** 全局 Agent 已因目标群更正开始复核
- **WHEN** Gateway 在其正式发言前再次收到该群按配置需要处理的新更正
- **THEN** 后续发言继续考虑新更正，不把第一次复核当作永久通行证

#### Scenario: 其他群及仅作背景的更新不阻塞发送
- **GIVEN** 全局 Agent 准备向 A 群发送消息
- **WHEN** 只有 B 群的新消息，或 A 群按其配置仅作背景的普通更新
- **THEN** 这些消息不阻塞本次向 A 群发言，也不因复核改变它们原有的处理与唤醒规则

#### Scenario: 草稿和复核归属员工工作视图
- **WHEN** 用户查看全局 Agent 的工作视图
- **THEN** 可以展开查看真实未发送草稿、所涉目标会话与复核过程
- **AND** 未发送草稿不作为目标会话的正式发言出现，也不触发其他 Agent 接话

#### Scenario: 私聊补充在旧答发送前到达
- **GIVEN** 全局 Agent 正准备向 Web 或飞书私聊回答
- **WHEN** 该目标出现它尚未读取且按配置需要处理的新补充
- **THEN** 旧稿不先公开，Agent 读取补充后重新判断再交付
- **AND** 飞书真实会话和 Web 镜像定位到同一目标时，两侧接收的新输入均参与复核
- **AND** 正在执行的工具不被硬中断，其他聊天与仅作背景的输入不阻塞该私聊

#### Scenario: 私聊复核后再次有补充
- **WHEN** Agent 读取新输入后重新发言前，该私聊又出现需处理的新输入
- **THEN** 新发言继续复核，不复活已拦截的旧发送调用

#### Scenario: 外部群聊与真实投递回执保持
- **WHEN** 全局 Agent 向外部群聊发送，或私聊发言已经进入投递
- **THEN** 外部群聊保持原有规则，已投递消息不因后到输入被撤回
- **AND** 外部回复经原 Channel 投递，不能仅保存 Web IM 镜像就确认已发送

### Requirement: 全局模式不通过聊天命令重置工作上下文

#### Scenario: 全局 Agent 收到重置命令
- **GIVEN** Agent 使用全局模式
- **WHEN** 用户在群聊或单聊中向它发送被识别为控制命令的 `/new`
- **THEN** 它明确提示“全局模式不支持按聊天重置”
- **AND** 不清空或切换全局工作上下文，不因该命令中断正在推进的工作

#### Scenario: 单 Thread 模式继续使用重置命令
- **GIVEN** Agent 使用单 Thread 模式
- **WHEN** 用户发送符合现有规则的 `/new`
- **THEN** 继续按现有规则重置对应聊天的工作上下文，不因新增全局模式改变其行为

### Requirement: 停止命令强制停止实际触达的 Agent

#### Scenario: 从一个聊天停止跨聊天工作的 Agent
- **GIVEN** 全局 Agent 正在处理来自其他聊天的工作
- **WHEN** 用户的 `/stop` 按现有命令寻址规则触达该 Agent
- **THEN** 该 Agent 的当前主执行被强制停止，不等待它主动读取收件箱或自行决定是否停止
- **AND** 保留已有全局上下文与未读消息，停止结果沿命令来源反馈

#### Scenario: 停止范围由既有路由决定
- **WHEN** 一个群中的 `/stop` 按既有规则触达一组 Agent
- **THEN** 各被触达 Agent 分别按自身模式处理停止，不将命令扩散到未被触达的其他 Agent
- **AND** 无活动执行时保留现有的空闲反馈规则

#### Scenario: subagent 停止规则不因全局模式改变
- **GIVEN** 被停止的全局 Agent 已委派 subagent
- **WHEN** `/stop` 强制停止该 Agent
- **THEN** subagent 是否停止以及其后续通知，继续遵循既有停止机制，不新增统一级联停止规则

### Requirement: 全局模式的压缩命令作用于主工作上下文

#### Scenario: 从聊天压缩全局主上下文
- **GIVEN** Agent 使用全局模式
- **WHEN** 用户向它发送符合现有寻址规则的 `/compact` 或 `/compact <关注点>`
- **THEN** 按现有手动压缩规则压缩该 Agent 的全局主上下文，并向命令来源说明结果
- **AND** subagent 上下文继续遵循各自原有机制，不随本命令统一压缩

### Requirement: Inbox 读取与聊天历史读取具有不同的消费语义

全局 Agent 可以依据提醒中已交付的待读来源快照直接选择摄取消息，也可主动 check 刷新；只有完整内容进入可恢复的主上下文才清除对应待读。聊天发现／历史查询不修改 Agent Inbox 或人的聊天已读状态。

#### Scenario: 只查看摘要或历史
- **WHEN** 全局 Agent 查看 Inbox 摘要或回查某聊天历史
- **THEN** 本 Agent 待读数量和人的聊天已读状态不因该查看推进

#### Scenario: 分页、分段及失败
- **WHEN** 一次读取只返回部分内容，或正文持久摄取失败
- **THEN** 未完整摄取的部分仍可重读，不因页面最大序号被跨过
- **AND** 图片与附件来源不被替换成已完整摄取的虚假声明
- **AND** 续页保持原查询快照；IM 断连导致在线历史暂不可续读时，原游标可在恢复后重试；缓存历史明确标出仅含已接收记录及权限确认时间
- **AND** 普通文件附件按其描述和读取入口摄取，不因误认图片而持续阻塞向来源群回复

#### Scenario: 受限的聊天访问
- **WHEN** Agent 查询它不可访问的聊天，或子 Agent 尝试消费全局主 Inbox
- **THEN** 请求被拒绝，不扩大访问权限或改变消费位置

#### Scenario: 模型读取简洁且可操作的 Inbox 结果
- **WHEN** 全局 Agent 查看或读取 Inbox
- **THEN** 来源摘要为所有 Global（包括 PA）提供真实可读名称、私聊/群聊类型、待读数量和实际 @ 本 Agent 的未读消息数；普通 check 在输出预算内列全，超过预算时可继续读取且不遗漏来源
- **AND** read 保留消息与发送者稳定身份、真实名字、秒级 UTC 时间和有序正文／多模态内容；内部回执、分片及重复路由字段不进入模型上下文
- **AND** 只有存在后续页、不完整内容或读取错误时才附相应信息；精简展示不影响持久摄取确认、用户请求的权限识别或人的聊天已读状态

### Requirement: Inbox 与会话查询使用同一查看者视角的名称

来源命名遵循 [IM 私聊名称投影](../im/conversations-messages.md#requirement-私聊名称按实际查看者投影)，以实际 Agent 为查看者；PA 的主人读取权限不替代 PA 的展示视角。

#### Scenario: 私聊被用户改名后读取
- **WHEN** 用户修改私聊会话名后 Agent 再查询或读取该会话
- **THEN** Inbox 显示同一个新标题，身份和回复目标不变

### Requirement: 聊天工具提供连续的查询到发送路径
#### Scenario: 已知群聊查询成员并沟通
- **WHEN** 全局Agent查询指定聊天信息并使用返回身份私信或群内提及
- **THEN** 得到完整成员及可直接使用的身份，消息到达选定对象
#### Scenario: 未读与历史辨认同一发送者
- **WHEN** Agent读取同一聊天的未读和历史
- **THEN** 发送者身份、聊天类型与内容表达一致，历史查询不消费Inbox

#### Scenario: 外部聊天发送者没有 IM 身份映射
- **WHEN** 读取外部来源消息，现有记录未关联真实 IM 用户
- **THEN** 明确显示外部来源身份，不将代记账号作为可私信发送者；平台身份已知时保留该身份，未知历史只保留已知显示名，回复仍发往原聊天

### Requirement: 全局未获准动作由主 Agent 继续处理

#### Scenario: 自动拒绝或审核故障
- **WHEN** 全局消息驱动的主 Agent 或其普通 child 动作未获准
- **THEN** 不弹权限卡片、不挂权限 Future；原因交回主 Agent，由其选择合规替代、普通聊天询问或说明停止；故障不归咎于用户未授权。
- **AND** 工具失败或单项动作被拒绝不代表事项完成；主 Agent 检查执行错误并选择有用的允许动作，或向原用户说明具体阻塞和所需决定，不直接静默放弃。替代方案不得通过更换工具、通道、身份或伪装相同动作绕过拒绝。

#### Scenario: 正常发送询问
- **WHEN** Agent 在发起事项的合适聊天中澄清具体操作
- **THEN** 宿主确认是绑定本人私聊时不调用 LLM 审核；其他收件人和群聊按完整目标和正文审核，正常询问适用协作/回复例外；结果中的 accepted、held_for_revalidation 或错误按实际状态保留，不把受理或暂缓描述为已送达。
- **AND** 某条公开消息被拒绝不等于禁止所有澄清；向原用户说明阻塞或询问的独立消息按收件人适用审核或本人私聊免审，不夹带被拒绝发布的内容。结果或问题实际送达后可安静等待；无待办的后台轮次仍可不发送公开消息，并按内部收尾要求结束。

#### Scenario: 只向绑定本人私聊免 LLM 审核
- **WHEN** Agent 公开 send_message 的真实收件人由产品绑定及平台身份解析为本人，且目标为私聊
- **THEN** 不调用 LLM 分类器，仍遵守工具限制、平台身份和可写权限，并按实际投递结果记录状态。
- **AND** 其他人、其他公开 Agent 和任何群聊仍审核；不因群由本人创建、本人参与或原群有来信而免审，也不因正文自称“给本人”或通用工具白名单而免审。未知身份不获得本人豁免。
- **AND** 飞书使用当前 app/ownerOpenId 与真实私聊身份，不以影子会话归属替代实际收件人。分类器获得固定消息投递语义及宿主解析的发送者/收件人事实，独立审核正文是否适合受众，不把工具形式的正常回复本身判成未经授权发布。

#### Scenario: 主会话创建、恢复与运行配置刷新
- **WHEN** 全局主 session 新建，或既有/恢复主 session 在空闲后继续接收事项、刷新运行配置
- **THEN** 保留未获准动作返回主 Agent 的交互选择；仅读取已有绑定不替换忙碌运行的配置，后续接续在提交前沿共享运行配置入口应用该选择。
- **AND** 该会话被 Heartbeat 复用时仍按实际自动入口的原 fallback 处理，不改变普通 global wake 和普通 child 的返回路由。

### Requirement: Inbox 保留工具形态与多来源授权语义

#### Scenario: 同页包含真人与 Agent
- **WHEN** Agent 读取实际 Inbox 消息
- **THEN** 审批获得工具调用、带 target/channel/sender/id/text/partial 及实际 reply 字段的宿主附加上下文，并保留真人、Agent、系统及未知来源；只有明确真人原话可表达人工意图，Agent 转述、自动事件与引用不升级。
- **AND** 主 Agent 与审批模型收到同一份应用来源说明；外部真人身份只沿 Gateway 已有 user 映射，不根据名称或正文推断。

#### Scenario: 多聊天提议与简短回复
- **WHEN** Agent 已通过 send_message 对不同聊天提出不同问题，某一用户回复
- **THEN** 历史发送目标/正文和该回复来源共同交给模型判断；同范围明确同意可继续，无关回复不凭全局时间邻近扩大授权；不要求新建专用确认实体。

#### Scenario: Inbox wake
- **WHEN** Gateway 因有未读消息唤醒全局主 session
- **THEN** wake 是系统通知；实际发送者身份与原话通过后续 Inbox read 提供，不能凭运行 origin=HUMAN 把通知当确认。

### Requirement: 等待确认可继续独立事项并按原来源恢复

#### Scenario: 其他聊天有工作
- **WHEN** 当前事项在等待用户回复
- **THEN** 待确认动作保持未执行，Agent 可完成独立工作，无事则 idle，回复到来后重新处理原事项。

#### Scenario: 普通跨轮或重启压缩后回复
- **WHEN** 用户回答旧问题
- **THEN** 根据当前可见问答与 CC 实时/恢复规则判断；必要时通过 conversations 查询背景后重述确认，查询旧消息不产生新的 live Inbox 投影，不复认证旧授权，也不要求用户重提完整任务。

#### Scenario: 连续拒绝
- **WHEN** 普通 global wake 或 global child 的拒绝次数达到阈值
- **THEN** 不变成弹窗等待、不因计数放行，后续新动作仍能接受分类；Heartbeat（包括复用全局主 session）和独立 Cron 按各自自动入口继续原有 fallback；普通 global child 仍返回主 Agent，不因 BACKGROUND_TASK 调度值切到该 fallback。

### Requirement: Inbox 保留真人消息原发生时间和已知用户时区

#### Scenario: owner 从飞书发来早间消息
- **GIVEN** 可信映射的 owner 时区为 Asia/Shanghai，飞书消息原时间为 UTC 01:00
- **WHEN** 全局 Agent 从 Inbox 读取消息
- **THEN** time 为该日 09:00:00+08:00，包含 offset，保留实际消息来源；不会因飞书原时间字段未映射而返回 null。

#### Scenario: 历史消息不随当前时区变化
- **GIVEN** 消息接收时固定了原发生时间及用户时区
- **WHEN** 用户换时区后 Agent 再读历史
- **THEN** 该消息仍使用原时间快照。

### Requirement: 全局轮次区分内部收尾与公开交付

#### Scenario: 模型空返回
- **WHEN** 全局 Agent 的模型请求返回空响应错误
- **THEN** 使用运行时既有重试策略恢复，耗尽后报告失败，不因全局模式把错误当作成功结束。

#### Scenario: 已交付或无需公开更新
- **WHEN** Global 已通过 send_message 实际交付文字或卡片，或本轮没有值得公开的新信息
- **THEN** 使用简短非空的私有结语说明已交付、已沟通的阻塞或无需公开回复的原因，不要求 NO_REPLY，也不重复公开发送收尾。
- **AND** Task 自动续跑与 shared 交互卡片引导遵循同一规则；SingleThread 保留其静默交付协议。

### Requirement: 全局 Agent 在任务执行期间主动沟通

#### Scenario: 简单请求直接交付
- **WHEN** 用户提出简单请求
- **THEN** 直接发送结果，不单独发送受理确认或回答预告。

#### Scenario: 接到真人任务
- **WHEN** 全局 Agent 读取到真人交办的长任务，且用户未要求不回复
- **THEN** 系统要求它在开始或委派主要工作前，向原会话简短说明具体事项与预期结果；已授权的工作不因这次告知等待再次批准。

#### Scenario: 职责内主动开展工作
- **WHEN** 全局 Agent 准备在既有职责和权限内主动开展较大事项，且用户或既定指引未要求静默
- **THEN** 主 Agent 在开始或委派前，向相关工作会话简短说明具体事项与预期结果，再继续已授权的工作，不将告知变成额外审批。
- **AND** 消息受众与私有信息边界保持，日常小事直接处理，执行中的普通进展不逐条外发。

#### Scenario: 长任务过程更新
- **WHEN** 全局 Agent 处理长任务或多步骤任务
- **THEN** 系统要求它通过显式消息发送对用户有用的成果、影响交付的重要变化、需其介入的阻塞或约定节点更新，合并内部阶段进展；用户主动询问状态或明确要求汇报频率时及时回应并遵守约定。
- **AND** 确认和进度通常为一两句话，避免重复状态、工具日志或空闲播报；用户明确不回复的要求仍受尊重。
- **AND** 确认和进度不代表最终结果已交付，内部草稿不算向用户更新。

#### Scenario: 内部进展无需父级介入
- **GIVEN** 主 Agent 已委派工作，执行者可按当前授权和要求继续
- **WHEN** 收到普通进展或受理回执，且没有新决定、更正或需要持久保存的状态变化
- **THEN** 不回复“收到/继续”、不重复交办，不因这条消息自动重读或改写工作笔记，也不逐条转述给用户；可按现有规则私有收尾。
- **AND** 执行者自行完成常规步骤和可恢复问题，将发现汇总在成果中；不逐步汇报等待批准继续，按原生模式报告成果，主 Agent 不因随后完成通知重复回复或向用户交付。

#### Scenario: 必要沟通和最终交付保持
- **WHEN** 用户首次交办、主动询问状态、提出更正/停止/接续，或工作出现需上级处理的阻塞、影响交付的重要变化、约定汇报节点或最终成果
- **THEN** 按实际来源及时处理、联系原执行者或向用户反馈，保留所需授权、状态和真实投递检查；普通进展的静默不吞掉这些必要行动。
- **AND** 内部阶段进展合并到用户有价值的更新，执行者所需的新资料或决定由父级明确返回；不增加固定限频或消息丢弃规则。

### Requirement: PA 跨渠道主人交办一致性

主人 Web 私聊和已绑定主人飞书私聊均作为主人直接交办来源，原始授权由服务端持久身份事实确认。主会话继续使用同一个 Inbox、工具和调度，按来信渠道回复；其他会话中的主人消息作为背景事实，不自动获得私聊授权。

#### Scenario: 主人飞书交办可引用原始授权
- WHEN 主人在已绑定飞书单聊发起需要主人授权的操作
- THEN PA 可引用该条原始消息执行授权范围内的操作，不要求主人转到 Web 重复交办

#### Scenario: 单一接入
- WHEN 一条飞书消息镜像进入持久来源事件并经历重试或重启
- THEN PA 主会话只接入一次，保留原渠道、发送者和时间

### Requirement: 全局输入的持久接收与工作记录上传独立

#### Scenario: 旧记录未同步仍接收新交办
- **GIVEN** 工作记录补传失败或积压，节点仍能持久接收消息
- **WHEN** 用户向全局 Agent 或 PA 发送符合原触发规则的交办
- **THEN** 输入持久保留并可唤醒处理，不等待旧记录完成中心同步。

#### Scenario: 执行运行时暂不可用
- **WHEN** 节点已持久接收输入而执行进程暂不可用，随后执行进程恢复
- **THEN** 自动继续原输入，回执暂不可达不阻止待办恢复；重复投递和重启不重复执行已接受的相同输入。

#### Scenario: 持久通知在冷重启时中断
- **WHEN** 运行时已接受通知但该轮因进程结束而中断，Inbox 中仍有对应的未读交办
- **THEN** 保留原消息与通知身份并自动继续未读交办；部分来源已消费时仍按实际通知边界恢复
- **AND** 已消费内容不重新交办，用户主动停止不会被当成进程中断自动继续。

#### Scenario: 主及各级子会话在进程恢复后自动继续
- **WHEN** 原执行进程退出或失去文件系统进展，主会话或各级 continuable 子会话的最近执行被原生恢复标记为 interrupted
- **THEN** 按原会话身份、原生子会话组合、当前权限与持久历史自动续原任务；原消息已被 Inbox Read 消费也不需要真人重新发消息。
- **AND** 恢复系统通知明确原授权不扩大、保留已完成工具结果，并列出已恢复的直接子会话，避免重新派工；结果未知的外部动作须先核实实际状态，不能盲目重放。
- **AND** 已完成、明确失败、用户取消或停止范围内的旧任务不因进程恢复重开；停止后的新任务按其自己的执行时间判断，不被旧停止记录永久阻断。
- **AND** 一次性 fork 缺少原生可恢复组合时，保留异常结束事实并通知父会话，自动唤醒负责的主会话继续原任务、核实后处理，不伪造同一 fork 已恢复执行。
- **AND** 其他 Agent 的接单不等待该会话检查历史。

### Requirement: 查询回复与必要控制不受无关轨迹积压阻塞

#### Scenario: 查询聊天并向原目标回复
- **GIVEN** 目标访问与必要权威事实可用，历史工作记录同步失败
- **WHEN** Agent 查询聊天并准备发送回复
- **THEN** 不等待无关历史同步，仍按原权限、来源证据与新消息复核处理；旧草稿被要求重读时不会自动发布。

#### Scenario: 停止与权限决定
- **WHEN** 用户按现有规则停止 Agent 或响应权限请求，且实时通路可用
- **THEN** 控制作用于真实执行，不等待历史过程全部上传，不因重试绕过撤销或审批边界。

### Requirement: Global 主 Agent 专属产品聊天工具

#### Scenario: 内部执行者需要资料或交付
- **GIVEN** 普通 Global Agent 或 PA 使用内部一级或二级执行者
- **WHEN** 执行者需要产品聊天资料、公开汇报或交付成果
- **THEN** 通过原生内部通信向父级请求或回传，由主 Agent 使用现有权限查询并决定发送。
- **AND** 子 Agent 的工具列表没有 inbox、conversations、download_attachment、send_user_message 或 send_message 的 target/text 公开分支；保留 agent_id/message 的原生内部通信，直接调用受限产品入口（含 `download_attachment`）也不能越过主 Agent 身份限制。Global/PA 根主 Agent 将 `download_attachment` 纳入固定产品工具面，并免审批直接执行受控下载（下载产物不视作人类授权来源）。

#### Scenario: 新建、fork 和恢复角色一致
- **WHEN** Global 子 Agent 被创建、fork 或恢复到原会话
- **THEN** 使用同一主/子工具边界，不因旧历史或配置继承恢复产品聊天权限；当前提示不要求子 Agent 消费主 Inbox 或向用户公开回复。
- **AND** 主 Agent 的产品读取/发送、来源权限与真实投递检查保持，主 PA 的代表发送仍为主 PA 专属。

### Requirement: Agent 可搜索并回查允许访问的聊天历史

主 Agent 能在当前可访问的 IM 已同步消息历史中，按精确文本或多个字面线索搜索，并组合聊天、发送人和时间范围；可按相关性或最新时间排序，未指定时间不默认排除旧历史。结果保留实际发送者、来源、时间和可继续读取的定位，权限与 Inbox 消费语义沿用现有规则。

#### Scenario: 多线索和准确文本
- **WHEN** Agent 根据用户的中文关键词或准确编号回溯历史
- **THEN** 它可以查到含多个分散线索的消息，也可以按完整准确文本查找；结果按相关性优先展示，较新弱匹配不会仅凭时间压过较早的明确匹配
- **AND** 卡片初始视图中的公开文字参与匹配。命中后返回完整卡片及其来源。

#### Scenario: 最近和筛选
- **WHEN** Agent 按聊天、发送人和时间组合条件搜索并选择最新优先
- **THEN** 返回符合全部条件的消息，较新结果在前；不指定时间时较旧匹配仍可查到

#### Scenario: 来源和前后文
- **WHEN** Agent 找到相关消息并按结果定位回查
- **THEN** 它能辨认真正的发送者和来源、取得原消息及同一聊天的前后文，并保留个人助手的可读来源和主人可读性事实

#### Scenario: 分页与当前权限
- **WHEN** 结果需要继续读取，或结果来源的权限在续页前被撤销
- **THEN** Agent 可继续查看允许访问的快照结果；不可再访问的内容不再返回，权限变化不使其他仍可访问结果被误认为已查完

#### Scenario: 完整与分段消息
- **WHEN** 搜索或回查返回完整消息，或因结果预算只返回消息的一部分
- **THEN** 完整内容无需重复的完整状态标记；部分内容能被辨认，并能判断是否需要继续读取以及前面是否还有未获得的部分
- **AND** 同一页收到的同一消息正文和附件描述保持顺序，完整取得附件描述不等同已读取附件内容
- **AND** 纯 UI 消息作为一条完整消息返回卡片内容与来源，正文和附件可为空

#### Scenario: 结果为空或历史不可用
- **WHEN** 已同步 IM 范围内没有匹配，或查询/所需来源不可用
- **THEN** Agent 能区分空结果与未查全或查询失败；已同步范围不被表述为外部平台全部历史

### Requirement: 聊天工具结果准确说明续查与完整性

#### Scenario: 会话列表和历史结果的续查
- **WHEN** Agent 成功列出聊天、搜索或读取历史
- **THEN** 只有存在后续结果时才提供续查信息；没有后续信息表示当前结果范围没有下一页，不表示未同步的外部历史已经查全

#### Scenario: 外部本地缓存完整性未知
- **WHEN** Agent 读取外部来源的本地缓存，而某条消息的完整性无法确认
- **THEN** 结果明确标示缓存范围及完整性未知，不将其冒充完整消息或编造分段；能够定位已同步原文时可继续回查，不能定位时可如实说明限制

### Requirement: 主 Agent 将完整独立事项交给单一内部执行者负责

主 Agent 与其 subagent 共同构成 IM 中一个独立、负责的角色，内部委派不转移对外的工作和交付责任。它与人和其他 IM Agent 平等协作，持续承担配置中的职责与目标，结合相关聊天、记忆与执行结果，在职责和权限内主动开展有价值的工作并接续已有事项；主会话是这个角色的对外表达与内部委派入口。普通 Global 与 PA 使用同一分工，具体服务对象和职责由各自角色配置确定，不因使用 Global 执行模式统一变成组织专家。

#### Scenario: 完整交办与内部再分工
- **WHEN** 用户向 Global 交办需要独立调查、制作成果或持续执行的完整事项，或 Global 根据既有职责和权限开展这类事项
- **THEN** 主 Agent 将整项目标及有效约束交给一个内部执行者负责到底，该执行者自行组织必要下级并整合成果。
- **AND** 主 Agent 不同时重复调查或替执行者预设实施方案；返回有缺口时交回原执行者补齐，不将派发当作完成。

#### Scenario: 派工与续派保留原话和可读材料
- **WHEN** 主 Agent 委派用户事项或向原执行者转发后续补充
- **THEN** 指引要求照引相关用户原话，补齐必要背景，并提供执行者实际可读的附件路径；缺少必要材料时说明缺口，由执行者向父级索取，不以文字描述代替看图。
- **AND** 普通子 Agent 默认使用当前工作区及其仓库指令，不继承主 Agent 的聊天和记忆；主 Agent 明确其不能查产品聊天、读主 Inbox、公开发产品消息或直接联系同级，只向父级汇报。
- **AND** 交接省略 IM 会话、用户、消息编号以及重复的默认工作区、仓库规则和工具限制；必要说话人用自然语言区分，路由编号仍由主 Agent 内部保存。
- **AND** 本轮由 Prompt 与 Skill 指导上述行为，不新增宿主自动绑定原始消息、自动传附件或自动路由话题消息的机制。

#### Scenario: 主 Agent 的判断与用户要求分开
- **WHEN** 主 Agent 对用户反馈形成自己的解读，或子 Agent 需要其作决定
- **THEN** 指引要求分别标明用户陈述、主 Agent 的待验证判断和现有授权内决定，不把自己的结论、额外要求、执行计划或验收清单冒充用户要求。
- **AND** 主 Agent 保留现有授权内的决策职责；下一步超出范围或确需用户选择时才询问用户，有效决定交回原执行者。执行者对疑似超范围或必要来源缺失的部分向父级澄清，可独立推进的部分继续。

#### Scenario: 日常交流和小事直接处理
- **WHEN** 用户闲聊、反馈状态或进展、回顾日常、查询待办或交办适合直接完成的小事
- **THEN** 主 Agent 直接承接上下文并处理，不因跨一天、跨消息或全局模式就强制创建 subagent。
- **AND** 日常中另有完整独立交办时只将该事项委派，不把整天包装成持续执行任务；倾诉和观察不自动成为交办。

#### Scenario: 多项独立工作与原事项更正
- **GIVEN** A 已由一个内部执行者承担
- **WHEN** 用户补充 A 或提出独立事项 B
- **THEN** A 的有效补充交回原执行者，B 可直接处理或由自己的执行者推进；主 Agent 继续接新输入，不为 A 重开重复工作。
- **AND** 用户可在现有工作视图辨认各事项的委派、结果和执行范围；普通内部进展不需要主 Agent 逐步批准或逐条转发。

#### Scenario: 必要问题与交付
- **WHEN** 执行者需要用户决定或交回完整成果
- **THEN** 由主 Agent 在正确原聊天提出问题或交付可用结果，有效答复回到原执行者；内部受理和完成通知不能替代实际交付，也不导致重复发言。
- **AND** subagent 始终通过主 Agent 与用户沟通，不另开用户对话或通过其他工具绕过该入口。

#### Scenario: 原执行者更正、停止与明确接续
- **WHEN** 用户在聊天内更正、停止或明确接续一个委派事项
- **THEN** 主 Agent 按创建时的框架处理原执行者和对应范围，保持其他独立工作；不把中断受理描述为已经停止，不把晚到成果当恢复授权。
- **AND** 原执行者不可接续或当前能力不足时说明真实原因与保留成果，不冒充已执行、不静默复制工作；已发生副作用按真实结果保留。

#### Scenario: 机器级派工与中断恢复
- **WHEN** 本机普通 Global 或 PA 派出新事项
- **THEN** 使用节点配置的 DSH、Codex CLI、Claude Code 或 Antigravity CLI，默认 DSH。框架及会话随该事项固定，追加与结果归原委派。
- **AND** 宿主恢复时将丢失的外部执行标为中断，携原 worker ID 向所属父 Agent 投递可重放、去重的中断通知；已保存的终局回报优先交付。用户明确续做时恢复原 CLI 会话。正常轮次结束时保留 worker 原文，由父级根据内容判断成果或待补问题。

#### Scenario: 外部通信能力不等于派工权限
- **GIVEN** 用户未授予对其他 IM Agent 的任务分配权限
- **WHEN** 用户要求该数字人完成一项工作
- **THEN** 它可处理日常小事或内部委派，不因能够向其他 IM Agent 发消息就默认将工作分派给对方。

### Requirement: Global 的话题按一等 target 独立收发，未关注的话题不进 Inbox

Global/PA 不按话题新建主 session，但 Agent 工具侧将话题作为一等 `target`（`<chat_id>:<8位短消息id>`），Inbox 按 `target` 拆行且不带正文 preview；原聊天发现、只读查/搜、话题关注与受保护附件下载分别由 `conversations`、`read_messages`、`search_messages`、`threads`、`download_attachment` 承担，所有需由 Agent 填写的原子编号长度不超过 8 位（其中原生附件在保留原 `url` 以兼容内联图片、PA 转发与前端展示的同时，附加 `<= 8` 字符 `attachment_id` 如 `a_xxxxxx`）。

#### Scenario: 未关注的群话题没有 Inbox 行
- **GIVEN** Global Agent 没有关注该群话题，消息也没有 @ 或引用它
- **WHEN** 话题里出现新回复
- **THEN** Inbox 不增加这条消息，十分钟背景里也没有它

#### Scenario: 话题在 Inbox 中按独立 target 呈现与消费
- **GIVEN** 同一群的主时间线和已关注话题各自有未读消息
- **WHEN** Global Agent 收到唤醒通知或调用 `inbox(check)`
- **THEN** 主时间线 `c_xxx` 与该话题 `c_xxx:yyyyyyyy` 各占一行，均不带消息正文 preview，可分别独立调用 `inbox(read, target=...)`
- **AND** `inbox(read)` 按三维预算分页（单页最多 20 条、文本 8000 字符、图片 4 张，始终至少返回第 1 条），避免高频纯文本群聊被迫逐页空翻
- **AND** 仅首次进入陌生话题（或压缩后首次回来）时附带一次根消息、有限条最近回复与显式截断标志；持续跟进时只交付新消息本身

#### Scenario: 显式 target 落点与话题级复核
- **WHEN** Global 接下一件需要确认和结果的请求，并以 `send_message(target="c_xxx:yyyyyyyy")` 发出确认和结果
- **THEN** 这些消息只出现在该话题；传入主时间线 `target="c_xxx"` 则发往主时间线，宿主不静默改写目标
- **AND** 向话题发送前的 `held_for_revalidation` 复核仅检查该话题自身是否存在未读高优消息，不被主时间线或兄弟话题的新消息误拦
- **AND** Global Agent 通过 `read_messages` 持久读到且已完整返回的纯文本、已核准、无风控提示的未读消息，同步核销对应 `inbox` 未读条目，不再触发重复 `held_for_revalidation`（含图片附件、多片拆段、私密交互背景或 PA 风控警示的消息仍须走 `inbox(read)`）

#### Scenario: 历史读取与搜索透出话题地址，Agent 可管理关注
- **WHEN** Agent 调用 `read_messages(target="c_xxx")` 读主时间线、调用 `read_messages(target="c_xxx:yyyyyyyy")` 读话题、或调用 `search_messages` 命中话题回复
- **THEN** 主时间线有回复的根消息带 `thread: { target, reply_count, latest_at }`；读话题返回根消息与回复；搜索命中话题直接返回话题 `target`
- **AND** Agent 可通过 `threads(list/follow/unfollow)` 查看或管理关注；取消关注时话题内留一行人类可见提示，后续再被 @ 或引用自动恢复关注并附带提醒

### Requirement: 全局数字员工围绕岗位职责执行两阶段静默运转、原会话归属与低噪触达

对工作模式为 `global`、非个人助手（`!personal`）且启用 `proactive_planning` 的数字员工，宿主复用同一主会话执行平时对话安静后的轻量记账与凌晨标准 `Dreaming` 之后的每日一次岗位深度筹划，不拆脱离主会话上下文的孤立短期小会话，也不授予个人助手专属的跨人私密会话旁观或代表用户发言权限；新建全局模式数字员工（含配置页、REST 接口省略技能列表及 PA 聊天创建）默认启用内置 `nano-proactive-care` 供根主会话按需加载，当关闭 `proactive_planning` 或用户显式禁用该 Skill 时同步隐藏该 Skill 及其加载提示。日常协作与主动唤醒全程遵守常驻 `MEMORY.md` 中「主动性与介入偏好」四档校准（含岗位通用准则与带协作者/会话范围限定的局部触发边界，命中链接后按需读取 `entities/` 或 `projects/` 详情页），且不读取后台观察池 `knowledge/proactivity-signals.md`。

#### Scenario: 平时对话安静后按来源会话原位轻量记账，零自激循环
- **GIVEN** 全局数字员工启用了主动筹划且未处于停用状态
- **WHEN** 其在参与的群聊、话题或 1 对 1 私聊中收到范围内的新增真人消息或需关注的同级 Agent 协作消息，随后进入安静空闲期
- **THEN** 宿主在安静满静默窗口时向其主会话提交轻量记账隐藏唤醒 `proactive_review`（主会话忙碌时保留水位待空闲重试；主动唤醒自身回合、被动 `task_graph` 系统通知、定时与记忆维护轮次不推进活动水位，全天无新增协作动态时保持零唤醒）
- **AND** 主会话仅将已明确达成的事项进展或具体检查时间原位更新至各自事项所属会话（`conversation_id`）的 `task_graph` 与原生 `schedule` 中，对常驻免打扰禁区（含特定协作者或会话禁区）保持零记账，不做发散立项；除有效非安静时段内发现约一小时内紧急阻塞/冲突可向原会话简短提示一句外，保持静默结束

#### Scenario: 凌晨紧随标准夜间 Dreaming 之后围绕岗位职责与原会话建立待拍板提议
- **GIVEN** 全局数字员工启用了主动筹划且未处于停用状态
- **WHEN** 进入有效时区凌晨休息窗口（默认 `03:00–06:00`），自上次夜间筹划以来存在新增协作活动且距最近活动已满夜间安静门禁
- **THEN** 若该数字员工启用了自动 `dreaming` 且当夜自然日槽位的标准 `Dreaming` 尚未完成，在连续失败未达上限且重试时间未越过凌晨窗口截止前，宿主非阻塞等待当夜 `Dreaming` 先行吸收当日对话与人类任务面板拍板反馈并更新 `MEMORY.md`（关闭 `dreaming` 或重试越界时直接降级放行），随后提交每日最多一次的 `proactive_nightly` 唤醒并在尾部附带较窗口首轮快照有更新的最新 `MEMORY.md` 正文
- **AND** 主会话结合已确认 `ROLE.md`、最新 `MEMORY.md` 与活跃目标图做无外部副作用的只读核查与工作区备料，先收起已解决或过时的旧 `proposed` 卡（不伪造人类未采纳反馈），再按事项来源原路建立有界数量的 `proposed` 待拍板提议卡：源自项目群目标或群讨论的候选卡绑定回该群及对应目标图并指向相关业务负责人（`proposed_for_user_id`）；源自与某成员 1 对 1 私聊的独立事项严格绑定在该私聊而不外溢至群聊；无前序对话、纯依据 `ROLE.md` 长期职责识别的新事项绑定至该职责服务的目标业务群，仅当该职责或该数字员工未关联任何协作群聊时归属与绑定管理者的私聊；当日仅有日常寒暄而无职责缺口时建立零张提议卡，夜间全程不调用 `send_message`

#### Scenario: 团队低噪次日触达与已有周期汇报顺路合并
- **GIVEN** 全局数字员工完成了夜间深度筹划
- **WHEN** 目标会话已存在固定周期汇报定时任务，或目标会话未设置固定周期汇报定时任务
- **THEN** 若目标会话已有固定周期汇报 `schedule`，主会话不另建提醒闹钟，而是将夜间准备好的要点摘要、工作区文件路径与 `task_cards` 引用按目标会话记入持久 `notes` 交接项，在该周期汇报触发时顺路合入同一条消息发出并清理交接项
- **AND** 若目标会话无固定周期汇报安排，常规 `proposed` 待拍板提议卡仅静默挂在对应会话的任务面板等待相关负责人翻牌（不发送个人式早安问候或例行早报消息刷屏）；仅当产出了近期活跃任务急需的实质准备成果或发现职责内明确时效风险与阻塞时，才创建工作时段一次性 `schedule` 发往原会话（群聊优先回到原讨论话题 `<chat_id>:<root_id>`）

#### Scenario: 定时触达前核实未读收件箱与任务最新状态，避免马后炮提醒
- **GIVEN** 全局数字员工的主会话由原生 `schedule` 定时唤醒准备发送跟进或风险提醒
- **WHEN** 团队成员此前已在原群聊、话题、私聊（含尚未到达十分钟普通群合并提醒窗口的新消息）或任务面板中先行修复、回复或完结了该事项
- **THEN** 宿主在进入模型首步前刷新本地未读收件箱摘要，并在存在未读会话或话题时提示主会话先读取相关未读内容；配合目标会话/话题自身的发送前复核（`held_for_revalidation`），主会话核实最新进展后原位收口对应任务并静默结束，不发送滞后的马后炮提醒
