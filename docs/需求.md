# 通用 Multi-Agent 智能框架需求文档
从用户侧反馈的原始需求。
## 一、文档目标与边界
本文档将需求拆分为两个对象，避免“内核能力”和“Agent 助手产品能力”混杂：

1. **内核（Kernel）需求**
   - 面向通用运行时能力，强调与具体IM平台、具体产品形态解耦
   - 提供可复用的 Agent 执行、工具、记忆、扩展等基础设施

2. **Agent 助手（基于 SDK 的上层应用）需求**
   - 面向最终用户协作体验，强调多Agent团队编排、人机交互、IM接入
   - 通过内核与SDK提供的接口落地产品能力

## 二、内核（Kernel）需求
内核是框架基础执行层，负责“单Agent可运行 + 可扩展 + 可持久化 + 可观测”，且不仅要支撑个人助手场景，也要支撑本地 coding 场景；两类场景在运行时基础设施上复用同一套内核能力，但允许在工具集合、Hook 体系与配置目录结构上按场景分化。

0. **多场景复用与隔离**
   - 内核必须同时支持至少两类上层使用场景：个人助手场景、本地 coding 场景
   - 两类场景复用同一套底层基础设施，包括 Agent 运行时、工具注册中心、记忆机制、任务/子Agent机制、观测与持久化能力
   - 场景层可在复用基础设施之上定义各自独立的工具白名单/默认工具集、Hook 配置、System Reminder、权限策略与默认行为
   - 不同场景需支持各自独立的配置目录或命名空间，避免个人助手配置与 coding 配置相互污染
   - 未来若新增其他 Agent 产品形态，也应能够在不复制内核实现的前提下，基于同一内核快速装配新的配置目录、工具集与 Hook 体系
   - 内核需对上层产品扩展开放：新增产品时优先通过配置装配与标准扩展点完成接入，而非派生/复制一套专用 Runtime
   - 外部若对 Agent loop 设计、调度策略或执行核心有更新，原则上应可直接在 core 层统一演进，并自动惠及各上层 Agent 产品，避免每个产品分别重复改造
   - 场景差异应通过标准化配置装配完成，而非复制两套内核实现，保证能力复用、统一演进与后续维护成本可控

1. **MCP 工具扩展能力**
   - 兼容标准化MCP工具协议，支持第三方/自定义工具扩展
   - 统一工具调用入口、权限管控、执行状态管理与日志留存
   - 无需修改Agent核心代码，即可完成工具扩展
   - ~~动态注册、卸载、热加载~~（V1 暂不实现，工具变更需重启生效，参见 `docs/内核设计SPEC.md` §6）

2. **Skill 技能体系**
   - 支持标准化Skill定义，绑定适用场景、Prompt模板、依赖工具、输出格式与异常处理策略
   - 支持任务触发的Skill自动匹配、多Skill组合执行
   - Skill可配置、可扩展、可启用/禁用，支持执行后反思校准

3. **内置基础工具（5个）**
   - 内置五个核心工具：`read`、`write`、`edit`、`bash`、`task`
   - `read/write/edit/bash` 默认启用工作区安全约束，统一经工具注册中心执行
   - `bash` 支持Shell命令沙箱执行、标准输出/标准错误获取、超时控制、安全隔离
   - `task` 仅用于在当前节点内拉起临时子Agent（subagent），不承担跨机器调度

4. **`task` 临时子Agent机制（上下文减负）**
   - 子Agent由主Agent通过 `task` 工具按需创建，生命周期随任务结束而终止
   - 子Agent继承主Agent的人格设定与同一份记忆（共享主Agent的 `MEMORY.md`）
   - 子Agent是内部执行单元，不作为IM可直接对话对象，不参与团队长期角色编组
   - 支持双模式执行调度：
     - 阻塞模式：主Agent等待子Agent完成后继续
     - 非阻塞模式：主Agent不等待，子Agent异步执行

5. **独立私有记忆（Memory）机制**
   - 每个配置级Agent拥有独立私有Memory，不与其他配置级Agent共享
   - Memory以Markdown文件形式持久化存储
   - 存储路径为Agent专属配置目录
   - 采用按需读取机制，Agent仅在需要时加载记忆文件
   - `task` 临时子Agent不单独持久化记忆，直接共享其主Agent记忆
   - **每个配置级Agent全量聊天记录必须持续归档落盘**，保留完整原始记录（非仅摘要）；Agent可自主在文件系统中检索、定位、调取任意历史聊天的原始完整数据
   - **系统需定期执行信息抽取任务**：按可配置周期扫描该Agent历史聊天记录，抽取稳定事实、偏好、约束、长期上下文，并进行去重与冲突处理
   - **抽取结果需沉淀到一个或多个固定记忆文档**（固定文件集合），禁止按会话无限新增记忆文件，保证长期可维护性
   - 记忆文档中的关键条目需保留来源索引（如会话ID/时间戳/原始记录路径），支持回溯核验与纠错更新

6. **Hook 事件自定义能力**
   - 开放Agent全生命周期/执行链路全节点Hook挂载点，覆盖任务接收、思考、工具调用、异常、超时等关键事件
   - 支持用户在任意Hook节点插入自定义逻辑，可挂载自定义System Reminder系统提醒
   - 提醒支持条件触发、多形式推送，按需精准触达
   - 兼顾低门槛可视化配置与高阶脚本扩展，适配普通用户/开发者
   - 非阻塞式挂载，无侵入不影响Agent核心流程，异常隔离不崩溃主逻辑
   - 支持Hook开关、优先级配置与触发日志追溯，可管可控

## 三、Agent 助手（基于 SDK 的上层应用）需求
Agent 助手是面向用户和团队协作的产品层，负责“多Agent组织 + IM交互 + 主动值班”。

1. **默认内置 Web IM（无需外部IM即可可用）**
   - 系统必须提供默认内置的 Web IM，用户在未接入任何第三方IM时也可完整使用 Multi-Agent 能力
   - Web IM 必须同时支持手机竖屏与电脑浏览器两种形态
   - 外部IM接入属于可选扩展能力，不应成为基础使用前置条件

2. **设备绑定与用户归属（多机）**
   - 用户在本机执行绑定命令后，系统应提供浏览器跳转链接完成登录与绑定
   - 若浏览器未登录则先登录，已登录则直接进入设备绑定确认
   - 绑定完成后，该设备上的Agent应自动归属到当前用户空间
   - 支持同一用户在多台机器部署多个Agent，并在同一空间内统一管理与通信

3. **配置级多 Agent（长期人格）协同**
   - 配置级Agent地位平等、各自独立持久化记忆，通过IM进行协同
   - 支持Agent部署在不同物理机器与不同网络环境
   - 同机器、跨机器通信逻辑完全一致（均复用IM通信）
   - Agent无感知通信部署环境，仅要求IM通道可达，不引入额外专有Agent通信信道
   - 框架内任意配置级Agent可通过IM与其他Agent相互发送消息
   - Agent间协同通信仅依赖IM消息路由能力，不额外设计专用内部消息总线
   - 基于用户账号归属维护同一用户的Agent列表，仅同一用户归属的Agent支持相互发现、消息通信
   - 同一配置级Agent可被拉入多个群、也可与用户单聊；每个群聊/单聊是独立会话（session），但共享该Agent的同一份长期记忆
   - Agent 与 Agent 之间也可形成独立单聊会话；该会话语义上不同于“用户与 Agent 单聊”，不可混用或复用为同一会话

4. **会话组织与可见性**
   - 用户可与团队内任意配置级Agent直接对话、下发指令、查看状态、获取结果
   - 用户可查看Agent之间的单聊会话；该会话的参与者应为对应两个Agent，用户是查看者而非该单聊参与者，并且应在用户自己的会话列表中可发现
   - 用户可手动选择若干Agent创建群聊，并在群内发起协同任务

5. **用户专属主 Agent（替身Agent）**
   - 设定专属主Agent作为用户在框架内的唯一替身入口
   - 该Agent在Agent Core层与其他配置级Agent完全平等：独立记忆、相同工具能力、相同运行机制
   - 核心职责：在IM中代表用户意图进行任务分解与团队指挥，减少用户逐个调度各Agent的操作成本
   - 可执行任务，但其长期定位为用户意图管理、信息中转与执行监督枢纽

6. **Agent 配置管理（Web）**
   - 用户可在 Web 端配置各Agent的 Skill 与系统提示词
   - 配置变更仅对新会话生效，已开始的会话保持原行为，不因中途改配置而漂移

7. **群聊模式行为规范（含不回复协议）**
   - 在群聊场景中，系统需要在Agent系统提示词后追加“群聊行为说明”，明确何时应答、何时保持沉默
   - Agent在判断“无需回复”时，需输出约定的固定字符串（如 `NO_REPLY`）表示本轮不发言
   - 不回复协议用于降低群聊噪声，避免Agent对所有消息机械响应

8. **Heartbeat 周期值班机制（仅配置级持久化Agent）**
   - 每个配置级Agent支持独立的 `HEARTBEAT.md`（与 `MEMORY.md` 分离），用于定义周期巡检待办与执行规则
   - 系统按可配置周期触发heartbeat，定时读取 `HEARTBEAT.md` 并判断是否需要行动
   - 若需要行动，Agent必须新开一个独立session执行对应任务；若无有效任务则安静跳过，不打扰用户
   - 支持“周期提醒 + 轻任务自动执行 + 结果回报”，实现从被动响应到主动推进
   - 汇报链路统一走IM：普通Agent执行完成后汇报给用户替身Agent；若当前Agent即用户替身Agent，则直接汇报给用户
   - `task` 临时子Agent不具备独立heartbeat与 `HEARTBEAT.md`

9. **Token / Turn 统计展示**
   - 群聊与单聊都需展示Token与Turn统计，且在群聊中可按Agent视角分别查看
   - Turn定义为一次LLM API请求-响应往返；若某Agent调用LLM三次，则该Agent为3 turn
   - Token展示默认显示“本轮统计”，并提供“累计统计”查看方式

10. **多媒体/文件输入统一路径交付**
   - IM发来的音频、图片、文件由Channel层统一落盘，并以标准文件路径形式提供给Agent
   - Agent默认不自动读取附件内容；是否读取、何时读取、使用哪种工具读取由Agent自主决策
   - Agent可按已安装工具能力处理附件（例如配置ASR类MCP工具后可读取音频）
   - Channel层仅负责接入、落盘、路径映射与元信息透传，不内置ASR/OCR/文件解析等业务逻辑

## 四、内核与助手的依赖约束
1. Agent 助手必须通过内核/SDK暴露的标准接口调用运行时能力，不直接侵入内核内部模块。
2. 内核保持IM无关，不耦合任何具体IM协议与平台账号体系。
3. 助手层负责用户触点、团队协作策略、渠道编排；内核负责执行、状态、工具、记忆与扩展机制。
