## 现象与复现

### 手动运行 cron 任务不可用

用户让 Agent 立即运行一个已存在的 cron 任务时，工具会要求一个从未配置的 `gateway_cron_url`，随后直接失败。系统中也不存在与之对应的 Gateway HTTP 能力，因此无论如何配置现有产品都无法走通手动运行。

期望体验参考 OpenClaw：用户得到“已入队”的即时确认；任务随后沿用定时触发时的执行、结果投递和运行历史，手动运行不产生第二套任务语义。

### 权限等待异常终结后会话永久不可用

当 Agent 已产生工具调用并等待用户授权时，若 run 异常终结、Gateway 退出或恢复流程没有生成对应结果，会话历史留下未闭合的工具调用。此后用户继续发送任何消息，上游模型都会拒绝整段历史；用户只能手工修改会话文件才能恢复。

同一故障链上的模型错误处理还会把部分实际请求错误当成可重试错误反复尝试，最终只显示包装后的终止消息，而不是最有诊断价值的上游错误。

### Gateway 非正常退出时出现二次 tracing 异常

Gateway 存在运行中任务时退出，日志尾部可能出现 `ContextVar Token ... was created in a different Context`。用户看到的是一个与真正退出原因无关的异常；原始故障可能被二次异常掩盖，进行中的 run 也没有可靠完成有序收尾。

### Web IM 持续请求已删除的用户目录

用户打开 Web IM 后，旧聊天适配层仍会请求已经删除的全局用户目录，浏览器持续出现 404。部分创建直聊、群聊参与者和会话详情路径仍依赖这条旧调用。

当前产品暂不支持发现其他真人用户，也不要求兼容旧用户目录；当前用户、Agent 和已有会话参与者已有各自的数据来源。

## 用户场景与现状痛点

1. 用户可以让 Agent 立即运行某个 cron 任务，马上知道任务已经排队；任务完成后，结果仍出现在原定的目标会话和运行历史中，后续对话可以承接该结果。
2. 用户在权限确认期间中断、退出或遭遇进程故障后，可以继续使用原会话。系统把未完成工具调用呈现为已取消，而不是让整段历史永久失效。
3. 模型服务遇到网络、限流、额度或其他可能恢复的问题时会尽可能重试；只有明确不会因原样重试而恢复的问题才快速失败。最终失败时，用户看到真实上游原因。
4. 用户停止或重启 Gateway 时，进程干净退出；若原本存在真正故障，日志保留该故障，不再被 tracing 的收尾异常覆盖。
5. 用户使用 Web IM 的现有 Agent 对话和已有真人会话时，不再产生用户目录 404；产品不新增真人用户发现入口。

## 验收标准

### Requirement: 手动运行复用 cron 原有任务语义

#### Scenario: 立即运行已有任务
- **WHEN** 用户要求 Agent 立即运行一个已存在且启用的 cron 任务
- **THEN** 用户立即得到任务已入队的确认，不必等待任务执行完成

#### Scenario: 手动任务完成
- **WHEN** 手动入队的 cron 任务执行完成
- **THEN** 结果按该任务原有规则出现在目标会话和运行历史中，效果与定时触发一致

#### Scenario: 手动运行未知任务
- **WHEN** 用户要求立即运行一个不存在的 cron 任务
- **THEN** 用户得到明确的“任务不存在”反馈，且不会创建或执行其他任务

### Requirement: 异常终结不会永久损坏会话

#### Scenario: 等待权限时中断
- **GIVEN** Agent 正在等待某个工具调用的用户授权
- **WHEN** 用户中断当前运行
- **THEN** 当前工具调用显示为已取消，用户随后可以在同一会话继续对话

#### Scenario: 加载已有受损会话
- **GIVEN** 历史会话中已有未闭合的工具调用
- **WHEN** 用户再次打开该会话并发送消息
- **THEN** 系统自动将未完成调用恢复为取消终态，会话无需人工改文件即可继续使用

#### Scenario: 异常恢复保持幂等
- **GIVEN** 某个未完成工具调用已经被恢复为取消终态
- **WHEN** 用户多次重新打开或继续该会话
- **THEN** 不会重复出现取消记录，也不会再次损坏会话

### Requirement: 模型错误按可恢复语义重试并保留真实原因

#### Scenario: 可能恢复的模型故障
- **WHEN** 模型请求遇到网络中断、超时、限流、额度不足或无法明确判定为永久错误的故障
- **THEN** 系统在既定重试预算内继续尝试，而不是仅因 HTTP 状态码属于 4xx 就立即终止

#### Scenario: 明确的永久请求错误
- **WHEN** 模型明确返回请求参数或格式错误、无效凭证、权限不足、资源或能力不存在或不支持
- **THEN** 系统不重复发送相同请求，并立即向用户展示可用于排障的真实错误

#### Scenario: 重试后仍失败
- **WHEN** 可重试错误在重试预算内始终未恢复
- **THEN** 用户看到最后一次真实上游错误及失败结果，而不是仅看到“流未正常结束”之类的替代错误

### Requirement: Gateway 有序关闭

#### Scenario: 有运行中任务时停止 Gateway
- **GIVEN** Gateway 内仍有进行中的 Agent 运行或权限等待
- **WHEN** 用户停止或重启 Gateway
- **THEN** 进行中的操作进入明确终态，进程在关闭时不显示 tracing 上下文二次异常

#### Scenario: 因真实故障退出
- **WHEN** Gateway 因其他错误退出
- **THEN** 用户可以从日志看到真正导致退出的错误，不被关闭阶段的 correlation 异常覆盖

### Requirement: Web IM 不再依赖全局真人用户目录

#### Scenario: 打开和使用现有聊天
- **WHEN** 用户打开 Web IM、浏览会话、进入 Agent 对话或继续已有真人会话
- **THEN** 页面正常展示所需身份和参与者信息，浏览器不再产生用户目录 404

#### Scenario: 创建 Agent 直聊或 Agent 群聊
- **WHEN** 用户选择一个或多个自己可见的 Agent 创建对话
- **THEN** 对话可以正常创建，不依赖搜索、创建或列出全局真人用户

#### Scenario: 真人用户发现
- **WHEN** 用户寻找创建新真人对话的入口
- **THEN** 当前版本不提供全局真人用户搜索或发现能力

## 影响范围

- **手动 cron**：所有使用 `cron run` 的 Agent 均稳定失败；定时触发路径本身不因此失效。
- **会话完整性**：命中权限等待异常终结的会话会持续不可用，属于持久化会话数据的逻辑损坏；已有坏会话需要自动恢复。
- **模型错误**：所有 Anthropic-compatible 和 OpenAI-compatible 模型调用都可能受错误分类影响。当前默认可重试会造成长时间无效等待，部分流式错误又被一律判为不可重试，行为相互矛盾。
- **Gateway 关闭**：主要影响退出可靠性和故障诊断；当前没有证据证明该二次异常本身会丢失已完成消息，但进行中任务缺少完整关闭契约。
- **Web IM**：旧聊天适配层的多个入口会产生 404 或被 404 阻断；新版隔离路径未覆盖仍在运行的旧适配代码。

## 根因分析（RCA）

### 1. 手动 cron 引入了架构中不存在的旁路

`feat-394` 的原始意图是让 Gateway 拥有 cron 调度、隔离执行、结果投递和会话 awareness；定时运行链路已经围绕这一归属建立。`cron run` 在复制 OpenClaw 工具表面时，单独假设了一个通过 session metadata 注入的 Gateway HTTP 地址，但该地址从未被定义或注入。

`refactor-387` 又明确移除了内核 HTTP API，产品与内核改为进程内 SDK。手动运行代码没有随架构迁移重新归位，因而留下一个既无生产者也无消费者的配置键。

该问题能进入主线，是因为测试覆盖了工具 schema、任务增删和定时调度，却没有覆盖“Agent 手动运行已有任务”的完整用户旅程，也没有约束手动触发必须复用定时触发的同一任务语义。

必须保住的不变量：cron 仍由 Gateway 负责；手动触发只改变触发时机，不能绕开既有执行、投递、历史和对话承接行为。

### 2. 会话持久化缺少工具调用闭合不变量

权限等待路径会先持久化 Assistant 的工具调用，再等待外部决策。正常授权或拒绝时会产生对应结果，但异常终结、进程退出和重新加载没有共同保证“每个已持久化工具调用最终都有一个结果”。

因此运行控制、权限等待和会话恢复分别处理了自己的局部状态，却没有一个跨生命周期的数据完整性契约。现有测试验证了授权决策能唤醒运行和中断能结束任务，但没有验证中断后的持久化历史还能被下一次模型调用接受，也没有历史坏数据恢复测试。

原始设计意图来自权限 park 与会话持久化能力：用户可暂停等待决策，并可在进程重启后继续会话。修复不能通过删除权限等待、丢弃整轮历史或新建会话规避坏记录。

### 3. 模型错误提取与重试分类没有统一语义

HTTP 请求失败目前被包装成通用消息，真实响应仅留在附加字段，并因 `ModelError` 默认值而自动可重试；流式错误事件则被统一标为不可重试；未识别到终止事件时又可能用“stream ended without terminal event”替代更早的真实故障。

这使“提取上游错误”“判断是否可恢复”“执行重试”三个职责没有稳定契约。HTTP 状态码也无法独立承担分类：Kimi 的 403 同时表示余额或权限问题；火山方舟的 403 细分欠费、权限、服务未开通等，429 又细分限流、突发流量和周期额度。

该问题能进入主线，是因为 provider 测试主要断言状态码被保留，重试测试使用人工指定的 `retryable`，没有用真实 provider 错误响应验证最终分类和用户可见消息。

必须保住的不变量：错误原文先被完整保留；统一策略默认重试，只有高度确定的永久错误快速失败；策略不要求为每个实际模型来源维护独立分支。

### 4. Registry 停止 event loop 前未收拢其拥有的任务

`RunsRegistry` 在专用线程运行 event loop，但关闭时直接停止 loop 并 join 线程，没有登记、取消并等待该 loop 上仍在运行的 Task。未完成协程随后可能在原 Task Context 之外被清理，`bind_correlation` 在退出时使用原 token reset，触发 cross-Context `ValueError`。

此前 `refactor-387` 已为任务创建补过一次 `copy_context()`，解决任务启动时的 Context 归属；关闭路径仍缺少对任务完整生命周期的所有权，因此只修了入口，没有修出口。

该问题能进入主线，是因为现有 observability 测试只覆盖同一 Context 内的绑定恢复，Gateway 关闭测试也没有在存在真实运行中任务和 correlation scope 时关闭内核。

必须保住的不变量：correlation 信息仍随每个 run 隔离传播；不能通过忽略 reset 失败来容忍错误 Context，也不能让关闭过程遗留未完成 run。

### 5. `/users` 迁移只隔离了新版前端，没有清理仍在使用的旧适配层

`feat-340` 删除全局用户目录以落实 owner 隔离，并明确计划切断前端依赖。但迁移过程中，新版聊天目录增加了“不准引用 `/im/v1/users`”的隔离测试，旧的 `im-chat-api.ts` 仍保留用户 bootstrap、Agent alias 和参与者映射逻辑，且其测试继续 mock 已删除端点。

结果是架构契约和后端测试都认定接口已删除，实际产品入口仍能调用它。门禁按目录而非按运行时调用面检查，制造了迁移完成的假象。

必须保住的不变量：当前登录用户来自认证身份，Agent 是独立 Actor，已有会话自带参与者信息，owner 隔离不因修复 404 而退回全局用户目录。

### 回归引入点

- 手动 cron 旁路由 `c286c536`（`feat(feat-394/M2/R3)`）引入。该提交增加 `cron run` 时写入了 `gateway_cron_url` 假设，但 Gateway 从未提供对应能力。
- 会话毒化不是单一提交造成的语句级回归，而是权限 park、会话持久化和异常终结之间一直缺少“工具调用必须闭合”的跨生命周期不变量；`feat-394/M14` 修复权限链路后，这个遗漏在真实中断场景中稳定暴露。
- provider 的通用 HTTP 错误包装可追溯到 `d98e52db`；`fe25dad2`（`bugfix-380/M1/R1`）又增加了流式错误和提前结束处理，但两类入口没有共享错误事实与分类契约，形成当前相互矛盾的重试行为。
- `RunsRegistry` 的独立 loop 与直接 stop/join 关闭方式由 `b10b064e`（`feat-335`）引入；`9e41b273`（`refactor-387`）修复了 Task 创建时的 Context 归属，但没有补上关闭阶段的 Task 收拢。
- `/im/v1/users` 由 `4c0ca50b` 删除，符合 owner 隔离的原始设计；回归来自同次迁移未清理仍在产品路径上的旧前端适配层，因此正确处理是完成迁移，而不是恢复端点。

## 修复方向

1. 手动 cron 运行进入 Gateway 已有的任务排队入口，复用定时触发的执行、投递、历史和 awareness；不增加临时 HTTP 服务或 `gateway_cron_url` 注入。
2. 建立持久化工具调用的闭合不变量：所有异常终结路径生成取消结果；加载历史时检测并幂等修复已有悬空调用。
3. 将上游错误完整解析为统一错误事实，再由共享语义分类决定重试；默认可重试，明确参数、格式、鉴权、权限和不支持类错误不可重试，最终始终保留真实错误。
4. 让 `RunsRegistry` 明确拥有其创建的 Task，并执行“停止接收、取消或收尾、等待终态、再停止 loop”的有序关闭；tracing 继续严格校验 Context。
5. 直接删除 Web IM 遗留用户目录调用及相关兼容逻辑，改用当前认证用户、Agent 列表和会话参与者；不恢复 `/im/v1/users`，不新增真人发现能力。

## 范围与非目标

### 范围

- 手动运行现有 cron 任务的完整用户旅程。
- 新异常的工具调用闭合与已有受损会话的自动恢复。
- 模型 HTTP、流式和传输错误的统一可恢复语义及真实错误展示。
- Gateway 在有进行中任务时的有序关闭。
- Web IM 现有聊天路径彻底移除全局用户目录依赖。
- 为五类故障建立跨层回归矩阵，覆盖正常、失败、恢复和关闭场景。

### 非目标

- 不新增独立 Gateway/Kernel HTTP API，也不恢复已退役的内核服务。
- 不改变 cron 定时调度、结果目标会话或历史保留的既有产品语义。
- 不按 Kimi、火山等实际模型来源维护独立重试分支。
- 不承诺所有错误都能被精确分类；无法确定时允许保守重试。
- 不新增真人用户搜索、全局通讯录或新真人会话发现。
- 不保留 `/im/v1/users` 的后向兼容端点或前端兼容层。
