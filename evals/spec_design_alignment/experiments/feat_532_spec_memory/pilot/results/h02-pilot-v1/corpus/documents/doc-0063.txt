## 现状痛点

Web IM 的用户当前通过同一个浏览器产品完成多条彼此关联的旅程：登录后进入 Chat，与 Agent 实时对话并
观看文本、工具调用、思考过程和权限卡更新；在会话外收到应用内 toast 或桌面系统通知；在 Chat、Nodes、
Agents 页面看到 Gateway 断连/重连带来的实时状态变化；从绑定链接确认设备；从 Agent 详情进入新的单聊。
这些都是已经存在、重构后必须保持的用户行为。

但当前前端仍处在两代 Chat client 并存的中间态：生产 Chat 已切到 v2，可靠的用户事件流生命周期仍藏在
legacy `im-chat-api.ts`，桌面通知又使用另一套能力较弱的连接；全局 toast、绑定、Agent 详情和状态页面则
继续依赖 legacy client 或 legacy 数据模型。由此形成以下可证实的问题：

- 同一浏览器页面可能同时建立两条用户事件流连接，而两条连接对鉴权、回放、断线重连和全量对齐的处理不一致。
- 桌面通知使用的连接不主动恢复游标、不处理全量对齐，也不在断线后重连；网络波动后通知可能停止，连接建立
  一段时间后还可能把历史事件当作新事件重新处理。
- 较完整的共享连接仍可能在 access token 轮换后拿旧 token 重连；一个消费者异常还可能影响其他消费者收事件。
- 全局 toast 维护 legacy conversation cache，实际 Chat 与移动端未读角标使用另一套 v2 cache；同一会话变化需要
  双重失效，且页面外的会话预览/未读状态存在更新不一致风险。
- legacy client、mock facade、旧类型和已经不再挂到生产路由的旧组件仍保留数千行代码；修改实时行为时，维护者
  必须同时辨认哪些是 current、哪些只是兼容残留。
- 现有“v2 不得依赖 legacy”的测试正则没有识别真实 import 路径，测试全绿也不能证明迁移边界成立；前端 README
  仍把 legacy/mock Chat 描述为当前生产入口。

如果继续保持现状，每次新增浏览器实时事件或修改断线恢复行为，都可能只修到其中一条路径；代码体积和测试量
也会继续被已退出生产入口的 legacy 表面放大。

## 目标状态

- Web IM 在单个浏览器标签页内只有一个权威的用户事件流生命周期，Chat、通知和状态展示共享一致的鉴权、回放、
  断线恢复与全量对齐语义；不同功能仍各自决定如何解释和展示收到的事件。
- access token 更新、短暂断网、IM 服务重启或用户重新登录后，浏览器能恢复当前用户的实时体验，不泄漏前一用户
  的事件，不把历史完成事件重复表现为新通知。
- 生产 Chat 只有一套 current 数据模型和会话缓存；会话列表、未读角标、应用内 toast、桌面通知与当前会话消息
  对同一事件形成一致结果。
- 绑定确认、从 Agent 详情打开单聊等现有入口不再为了少量能力加载整套 legacy Chat client。
- legacy Chat client、运行时 mock facade、旧类型、旧生产组件及仅为其存在的测试可以实际删除；代码库不再需要
  “v2 反向调用 legacy”的兼容解释。
- 重构不改变 IM 后端协议、持久化数据、租户权限或现有 Chat 交互设计；用户正常使用时除恢复可靠性提升外，不感知
  到功能迁移。

## 用户侧验收标准（不变性）

重构前，用户已经可以在 Web IM 中实时聊天、查看过程信息、管理群聊、fork、接收应用内/系统通知、观察 Node 与
Agent 状态、确认设备绑定并从 Agent 详情进入单聊。重构后这些旅程在桌面与移动端保持一致，同时短暂断网、token
更新和服务重连不再造成实时能力永久失效或历史通知重放。

### Requirement: 当前会话继续实时呈现完整消息过程

#### Scenario: Agent 回复实时更新
- **GIVEN** 用户已登录并打开一个与 Agent 的会话
- **WHEN** Agent 依次产生回复文本、思考过程、工具调用或权限请求并最终完成
- **THEN** 当前消息气泡无需刷新即可按既有交互持续更新，完成后的内容与刷新历史后一致

#### Scenario: 静默回复撤销临时气泡
- **GIVEN** 当前会话中已出现一条生成中的临时 Agent 气泡
- **WHEN** Agent 最终选择静默回复
- **THEN** 临时气泡从当前页面消失，刷新页面后也不会重新出现

#### Scenario: 外部 channel 消息实时进入已打开会话
- **GIVEN** 用户已打开一个飞书/Lark 影子会话
- **WHEN** 外部 channel 写入一条新的用户消息
- **THEN** 对应用户气泡无需刷新立即出现，发送者名称与刷新历史后一致

### Requirement: 会话列表、未读状态和应用内提醒保持一致

#### Scenario: 未打开会话收到新消息
- **GIVEN** 用户当前没有打开消息所属会话
- **WHEN** 该会话收到一条可见的新消息
- **THEN** 用户看到既有样式的应用内 toast，会话列表预览、排序和未读角标同步反映该消息

#### Scenario: 当前会话和自己的消息不产生多余提醒
- **WHEN** 用户正在查看消息所属会话，或新消息由用户自己发送
- **THEN** 页面不弹出误导性的应用内新消息 toast，当前会话与列表仍正确更新

### Requirement: 桌面系统通知保持一次且可导航

#### Scenario: 后台标签页收到 Agent 完成通知
- **GIVEN** 用户已开启桌面通知、浏览器已授权，且 Web IM 标签页不在前台
- **WHEN** Agent 的一条回复完成
- **THEN** 系统通知只出现一次，展示既有标题和内容；用户点击后窗口聚焦并进入对应会话

#### Scenario: 不满足通知条件时不弹通知
- **WHEN** 标签页在前台、用户关闭通知开关或浏览器未授权通知
- **THEN** 不弹出桌面系统通知，聊天消息本身仍正常到达和展示

#### Scenario: 恢复连接不重放历史通知
- **GIVEN** 用户已经看过某条完成通知，随后浏览器经历短暂断网或 IM 服务重启
- **WHEN** 实时连接恢复
- **THEN** 已处理的历史完成事件不会再次弹成新系统通知或应用内 toast，断线期间的新事件能通过恢复或刷新正确呈现

### Requirement: Node 与 Agent 状态继续实时变化

#### Scenario: Gateway 断连与重连
- **GIVEN** 用户正在查看 Chat、Nodes 或 Agents 中显示在线状态的页面
- **WHEN** Gateway 断开后重新连接
- **THEN** 对应 Node/Agent 状态无需手动刷新，先显示离线、重连后恢复在线，与实际状态一致

### Requirement: 长时间登录与账号切换后实时体验仍然正确

#### Scenario: 长时间保持登录后发生网络重连
- **GIVEN** 用户已在 Web IM 中持续登录一段时间并一直可以正常操作
- **WHEN** 浏览器之后发生短暂断网并恢复
- **THEN** Web IM 继续接收该用户的新消息和状态变化，不要求退出后重新登录

#### Scenario: 退出后切换为另一用户
- **WHEN** 用户退出当前账号并登录另一个账号
- **THEN** 新账号只看到和接收自己的会话、通知与状态事件，不再收到前一账号的实时事件

### Requirement: 非实时入口保持原有可用性

#### Scenario: 确认 Gateway 绑定
- **WHEN** 已登录用户打开有效绑定链接并确认
- **THEN** 绑定成功并返回 Chat，后续能看到绑定 Node 与其 Agent；错误 token 仍显示明确失败反馈

#### Scenario: 从 Agent 详情打开单聊
- **WHEN** 用户在一个有效 Agent 的详情页选择打开单聊
- **THEN** 成功进入与该 Agent 的会话；失败时仍显示明确错误，不出现无响应按钮

## 范围与非目标

本期范围：

- 浏览器用户事件流所支撑的 Chat 实时消息、会话列表/未读、应用内 toast、桌面通知和 Node/Agent 状态旅程。
- 为退役 legacy Chat client 所必需的绑定确认、Agent 详情打开单聊和小型共享数据转换调用方迁移。
- current Chat cache 收口、legacy 代码与过期测试清理、对应前端开发文档和架构门禁更新。
- token 更新、断线重连、事件回放、全量对齐、用户切换和多消费者互不干扰等恢复行为。

本期非目标：

- 不新增聊天、通知、绑定或 Agent 管理产品功能，不重新设计现有 UI。
- 不修改 IM 后端用户流协议、事件存储、租户模型或 Gateway 协议；若实施阶段发现独立后端缺陷，另行立项。
- 不在本期拆分整个 Chat workspace 的分页、群管理、fork、蒸馏或页面状态；该大文件的进一步深化另作后续候选。
- 不把 Chat、Settings、Binding 的所有 REST 调用合并成万能 client，也不以本重构为由替换 React Query、Zustand
  或其他前端基础库。
- 不要求不同浏览器标签页共享同一条物理连接；单标签页内收口，多标签页仍按现有产品语义各自连接。

## 影响范围

- 直接影响 Web IM 前端的鉴权会话消费、用户事件流、Chat 数据读取与缓存同步、应用内/桌面通知、Node/Agent
  状态消费、绑定确认和 Agent 详情跳转。
- 直接影响上述路径的单元测试、集成测试、前端架构门禁和开发 README。
- 不需要数据库迁移，不改变已有会话、消息、Agent、Node 或用户数据。
- 不改变 `personal_assistant`、`agent` 或外部 channel adapter 的职责和用户行为。

## 迁移与回滚策略

- 先用现有用户行为建立回归基线，覆盖正常实时路径、断线恢复、凭证更新、历史回放、用户切换和通知去重；不能以
  删除旧测试数量代替 current 旅程覆盖。
- 按消费者逐步迁移：每迁移一个 Chat/通知/状态/绑定入口，即验证该入口的用户行为；旧路径在其最后一个生产调用方
  迁走前保留，但同一消费者不得同时启用新旧两条实时路径。
- 所有生产调用方完成迁移且完整前端门禁通过后，再删除 legacy client、旧类型、旧组件、runtime mock 与对应旧测试；
  删除动作必须能由依赖扫描和 current 入口测试共同证明安全。
- 每个迁移阶段保持可单独回退；若新路径导致消息丢失、重复提醒、状态不刷新、跨用户事件或绑定/单聊入口回归，回退
  最近迁移的消费者，而不是恢复已经证明无调用方的整套旧页面。
- 本重构无数据格式变化，代码回滚不需要数据回滚；回滚后已有会话和消息必须继续可读。
