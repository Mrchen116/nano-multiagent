## 澄清记录

- Q1: 这项连续性保证只覆盖 Web IM 直聊，还是也覆盖群聊及 Feishu 等外部渠道中的既有对话？
  A(原话): 好
  Agent 解读: 覆盖所有绑定到同一 Agent 的既有对话，包括 Web IM 直聊、群聊和外部渠道；修改后的配置均从各对话的下一轮开始生效，并保持各自历史连续。
- Q2: 配置生效提示应该显示在哪里——配置保存页提示，还是还要在每个聊天中插入一条提示消息？
  A(原话): 我倒是倾向于在旧的聊天页，到那时不要放在任何消息泡泡中，而是一行小字。因为要提醒他改了配置之前的cache都会不命中。
  Agent 解读: 在受配置更新影响的既有聊天页中，以非消息气泡的一行小字提示配置切换；提示还需让用户知道此前缓存将不再命中。
- Q3: 这行提示应该作为聊天历史中的永久分界线，还是只临时显示一次后消失？
  A(原话): 对。文字要优化下，“缓存将重新建立” 不太清晰。“对话历史保留”不用说，默认大家都知道。“将从下一轮生效”废话
  Agent 解读: 提示作为持久时间线分界线，不进入消息气泡或模型上下文；文案只表达配置发生变化及此前缓存不再命中，不解释默认成立的历史连续性和生效时点。
- Q4: 提示文案用“Agent 配置已更新 · 后续请求将不再命中此前的上下文缓存”是否准确？
  A(原话): ok
- Q5: Agent 有多个既有聊天时，配置更新分界线是在保存时立即写进所有聊天，还是只在某个聊天下次继续时出现？
  A(原话): 对
  Agent 解读: 不在保存时批量写入休眠聊天；某个既有聊天下次继续时，在第一条使用新配置的消息前显示持久分界线。期间连续修改多次配置，只显示一条并以最终采用的配置为准。
- Q6: 哪些配置修改需要显示这条缓存分界线？
  A(原话): 对
  Agent 解读: 仅当 model、system prompt、custom prompt、skills、tools 或其他会改变后续模型请求的运行能力发生变化时显示；名称、头像、描述等纯展示信息变化时不显示。
- Q7: 如果配置保存因版本冲突、网络错误或校验失败而没有成功，聊天页是否保持原样？
  A(原话): ok
  Agent 解读: 保存失败时不显示配置分界线，后续对话继续使用原配置；只有配置成功保存并被 Agent 采用后才显示分界线。
- Q8: 配置更新时，如果 Agent 正在回复，而用户又插入消息，这条插话应使用旧配置还是新配置？
  A(原话): ok
  Agent 解读: 已在进行中的整轮回复继续使用旧配置，包括被纳入这轮的插话；配置更新后新开始的第一轮回复才使用新配置，并在其首条用户消息前显示分界线。

## 现象与复现

用户在同一个既有聊天中与 Agent 形成历史后，打开配置页增加工具，再回到该聊天追问。配置保存成功，下一轮也确实获得了新增工具，但 Agent 不再记得刚才的对话。

稳定复现：

1. 创建一个没有工具权限的 Agent，并在既有聊天中提出需要工具的问题。
2. 等 Agent 基于当前能力回复，形成可见历史。
3. 在 Agent 配置页增加工具并保存。
4. 回到同一个聊天继续追问，例如“现在呢？”。
5. 页面仍显示原消息，但 Agent 的回复表现为从一段空白上下文开始。

2026-07-21 的真实请求证据中，配置修改前的会话请求已包含 5 条历史消息，工具数为 0；配置修改后的同一聊天被切换到另一会话，请求只包含当前一句“现在呢？”，工具数变为 13。IM 仍保存完整可见消息，因此不是聊天记录被删除，而是 Agent 实际使用的上下文与用户看到的聊天历史发生分叉。

## 影响范围

- 所有在既有直聊、群聊或外部渠道对话中修改 Agent 运行配置后继续交流的用户都会受到影响。
- model、system prompt、custom prompt、skills、tools 及其他会改变后续模型请求的运行能力，均可能触发同类失忆。
- 用户无法从界面预知上下文已经被重置；追问、指代和依赖先前工具结果的任务会答非所问或重新询问已知信息。
- IM 中的消息没有损坏或删除，但“页面可见历史”与“Agent 实际记忆”不一致，属于严重的会话连续性缺陷。
- 配置改变也会使此前的上下文缓存不再命中；当前界面没有解释这一响应速度或成本边界。

## 根因分析（RCA）

### 原始设计意图

`refactor-463` 的原始目标是收回 Gateway 入站状态所有权，同时保持用户行为不变。其首文档明确要求：

- 动态 Agent 配置在下一轮生效；
- Gateway 重启后续接原会话和上下文；
- 直聊、群聊、运行中插话与外部渠道的连续体验保持不变。

修复必须同时保住两个不变量：已经开始的整轮回复使用一致的配置快照；配置更新后的新一轮采用最新配置，但仍属于用户正在继续的同一段对话。

### 坏行为来源

`refactor-463` 为 Agent 配置引入带 revision 的运行快照，并把“新配置不能与旧 binding 混用”作为并发一致性规则。配置发布后，旧 revision 的会话绑定会被主动删除；同一聊天的下一条消息因此创建全新会话。新会话取得了最新 model、prompt、skills 和 tools，却没有承接旧会话的对话历史。

回归引入点：

- `e19b0b5ded8148ac8aa0bc6f607acc8a1b05825c`：建立会话 binding 的 revision 失效规则。
- `1d090718dab0a76f7aefa15011274255a9748d82`：把配置发布接到会话失效路径。

`refactor-470` 只迁移了 composition ownership，没有改变这项会话失效语义，因此不是本缺陷的引入单元。

### 为什么缺陷能够进入主线

设计和测试验证了“下一轮拿到完整的新配置”以及配置发布竞态下不会混用新旧 revision，却把“旧 binding 不可复用”等同于“旧上下文可以丢弃”。测试还明确固化了同一聊天在配置更新后换成新会话，但没有验证新会话中的 Agent 是否仍记得页面上已有的历史。

长青契约也存在矛盾：Gateway 已规定历史会话改模型后下一条消息使用新模型，并承诺会话续接不丢历史；IM 配置契约却写着“更新仅对新会话生效”。缺少一条统一的用户契约，使实现只满足配置版本一致性，没有守住聊天上下文连续性。

## 用户场景

用户在 Web IM 直聊、群聊或外部渠道中持续与 Agent 协作。发现 Agent 缺少某项工具，或希望调整模型、提示词、skills 等能力时，用户可以打开配置页修改 Agent，然后回到原来的聊天继续刚才的任务。

已经开始的回复不会在中途改变行为；如果用户在这轮回复进行时继续插话，整轮仍使用开始时的配置。配置更新后新开始的第一轮使用最新配置，同时 Agent 仍理解此前的用户消息、回复以及已经发生的工具调用结果。删除某项工具只限制今后的调用，不会抹掉历史中已经发生的工具交互。

当某个既有 Web IM 聊天下次真正使用新配置时，聊天时间线上在该轮首条用户消息前出现一条非消息气泡的持久分界线：

> Agent 配置已更新 · 后续请求将不再命中此前的上下文缓存

这条分界线不作为聊天消息，不参与 Agent 上下文。用户以后回看聊天时，可以据此理解为什么分界线后的首轮可能响应更慢或缓存成本发生变化。休眠聊天不会在保存配置时被批量写入标记；同一聊天在再次使用前连续修改多次配置，只出现一条分界线，以最终实际采用的配置为准。

## 验收标准

### Requirement: 既有对话采用新配置时保持上下文连续

#### Scenario: 增加工具后继续刚才的任务
- **GIVEN** 用户已在既有聊天中提出需要某工具的问题，Agent 因未配置该工具而无法完成
- **WHEN** 用户为该 Agent 增加工具并回到同一聊天继续追问
- **THEN** Agent 能使用新增工具，并理解此前的问题和回复，不要求用户重新交代上下文

#### Scenario: 删除工具后保留既成工具历史
- **GIVEN** 既有聊天中已经发生过工具调用及其结果
- **WHEN** 用户从 Agent 配置中删除该工具后继续同一聊天
- **THEN** Agent 不能再发起该工具的新调用，但仍能理解历史中已经发生的调用和结果

#### Scenario: 修改模型、提示词或 skills 后继续既有对话
- **GIVEN** 用户已与 Agent 形成对话历史
- **WHEN** 用户修改 model、system prompt、custom prompt、skills 或其他影响后续模型请求的运行能力，再回到原聊天发消息
- **THEN** 新一轮体现更新后的配置，同时仍能引用修改前的对话内容

#### Scenario: Gateway 重启后配置边界两侧的历史仍连续
- **GIVEN** 用户在既有聊天中修改过 Agent 运行配置，并已在分界线后继续交流
- **WHEN** Gateway 重启后用户再次进入该聊天继续发送消息
- **THEN** Agent 仍能理解分界线前后的完整对话，不退回旧配置，也不从空白上下文开始

### Requirement: 配置切换不改变正在进行的整轮回复

#### Scenario: 回复进行中修改配置
- **GIVEN** Agent 正在使用配置 A 回复用户
- **WHEN** 用户把 Agent 更新为配置 B
- **THEN** 已在进行的整轮回复继续使用配置 A，新开始的下一轮使用配置 B

#### Scenario: 回复进行中插话
- **GIVEN** Agent 正在使用配置 A 回复，用户已把 Agent 更新为配置 B
- **WHEN** 用户在当前回复结束前继续插话，且该插话被纳入当前这轮回复
- **THEN** 当前整轮仍保持配置 A 的一致行为；配置 B 从下一轮新开始的回复生效

#### Scenario: 连续保存多次后再继续聊天
- **GIVEN** 某个既有聊天暂时没有新一轮开始
- **WHEN** 用户连续修改并成功保存 Agent 配置多次，再回到该聊天发送消息
- **THEN** 新一轮使用最终实际采用的配置，不依次重演中间版本，也不丢失聊天历史

### Requirement: Web IM 用持久分界线说明缓存边界

#### Scenario: 运行配置更新后继续既有聊天
- **GIVEN** 用户成功修改了会改变后续模型请求的 Agent 配置
- **WHEN** 某个既有 Web IM 聊天下次开始第一轮使用新配置的交流
- **THEN** 该轮首条用户消息前出现非消息气泡的持久分界线“Agent 配置已更新 · 后续请求将不再命中此前的上下文缓存”
- **AND** 分界线在页面刷新或重新进入聊天后仍位于同一时间线位置

#### Scenario: 休眠聊天不被批量插入分界线
- **GIVEN** 同一 Agent 有多个既有聊天
- **WHEN** 用户修改 Agent 运行配置，但其中一些聊天没有继续交流
- **THEN** 未继续的聊天不新增分界线；每个聊天只在实际开始使用新配置时显示自己的分界线

#### Scenario: 连续修改多次只显示最终边界
- **GIVEN** 用户在某个聊天再次发消息前连续成功修改 Agent 运行配置多次
- **WHEN** 用户回到该聊天开始新一轮交流
- **THEN** 时间线只新增一条配置分界线，不为每次中间修改重复显示

#### Scenario: 纯展示信息更新不提示缓存变化
- **WHEN** 用户只修改 Agent 名称、头像、描述等不改变后续模型请求的展示信息，并继续既有聊天
- **THEN** 聊天中不出现上下文缓存分界线

#### Scenario: 配置保存失败不产生错误提示
- **GIVEN** Agent 配置保存因版本冲突、网络错误或校验失败而未成功
- **WHEN** 用户回到既有聊天继续交流
- **THEN** 不出现“Agent 配置已更新”的分界线，Agent 继续按保存前的配置工作

### Requirement: 各聊天入口保持各自连续且互不串线

#### Scenario: 群聊配置更新后保留群上下文
- **GIVEN** 群聊中已有多名成员与 Agent 的历史消息
- **WHEN** Agent 运行配置更新后，群成员继续在同一群聊触发新一轮回复
- **THEN** Agent 使用新配置，并仍能理解此前群消息的发言人、内容和顺序

#### Scenario: 外部渠道既有对话继续使用新配置
- **GIVEN** 用户已在外部渠道与 Agent 形成对话历史
- **WHEN** Agent 运行配置更新后，用户在同一外部对话继续发送消息
- **THEN** Agent 使用新配置并理解外部对话前文，不把它当作新对话

#### Scenario: 不同聊天的历史不因配置更新而合并
- **GIVEN** 同一 Agent 同时存在直聊、群聊或外部渠道的多个独立聊天
- **WHEN** 配置更新后这些聊天分别继续交流
- **THEN** 每个聊天只延续自己的历史，不读取其他聊天的内容

## 范围与非目标

### 范围

- Web IM 直聊、群聊，以及外部渠道及其 Web IM 影子会话的上下文连续性。
- model、system prompt、custom prompt、skills、tools 和其他会改变后续模型请求的运行能力。
- 运行中回复与新一轮之间的配置切换边界。
- Web IM 聊天时间线中的持久配置分界线及刷新、重进后的稳定展示。
- 配置保存失败、连续多次修改、Gateway 重启和多聊天隔离等边界场景。

### 非目标

- 不保证配置变化后继续命中此前的上下文缓存；提示的目的正是说明这一缓存边界。
- 不新增“清空上下文”或“新建直聊”入口；用户明确创建的其他会话仍按其既有产品语义处理。
- 不把配置分界线作为用户或 Agent 消息发送到模型，也不向外部渠道伪造一条聊天消息。
- 不改变历史中已经显示的工具调用结果，不重新执行旧工具调用。
- 不让已经开始的回复在中途切换模型、提示词或能力。
- 名称、头像、描述等纯展示信息更新不属于缓存分界提示范围。

## 修复方向

把“配置版本切换”与“聊天历史归零”解耦：配置更新后，新开始的轮次必须采用最新运行配置，同时延续该聊天已经向用户展示的完整上下文。正在执行的整轮保持其启动时配置，不在中途切换。

为每个实际跨过运行配置版本的 Web IM 聊天记录一条持久、非消息型的时间线分界事件；它只解释缓存不命中，不进入 Agent 上下文。配置成功但聊天尚未继续时不提前写入；连续多次更新在该聊天下次使用时合并为一个最终边界。

实现设计阶段还需拍板：如何在不复用旧运行配置的前提下承接旧上下文；如何让直聊、群聊、外部会话与重启恢复遵循同一连续性规则；如何定义并校正执行轮次所采用的配置版本元数据；以及如何持久化并实时呈现不属于普通消息的时间线分界事件。
