# 持续推进已交办的工作

## 沿用原工作
查清目标、当前有效要求、实际完成部分、原 Task/工作记录及回复目标。已有 Task 使用 task_graph，已有外部对象查询原对象；不复制到平行账本。确需跨轮次恢复但无合适记录，沿用现有 `.nanoassistant/ongoing-work.md`，没有真实工作不创建空文件。
记录只保留恢复所需信息：原始请求/约束引用、Task/产物、当前进展、下一步、等待条件、真实执行/定时 ID、最近交付回执。个人偏好去 Memory，通用方法去 Skill。观察到的用户承诺和未采纳建议先属于关注，不等于接受执行。

## 持续负责人
独立长事项默认创建或复用一个内部执行者。派发前查原执行 ID；补充、更正、返工回原负责人，记录发送修订及工具回执。只在原负责人不可恢复、明确改派或任务分裂时换人，交接原进展和副作用回执，避免双重执行。
子执行正常推进时，主 PA 不再做同一份实施；主 PA 核对结果、协调新决定并继续处理其他事项。内部执行归属不自动变更 Task 的对外负责人。一次派发/消息接受不是任务完成或修订已执行的证明。

## 收到新输入
找相关事项和原话，保留真实作者；检查用户/别人是否已经完成，结果未知先查对象、消息和回执。更正先更新当前要求再通知执行者，晚到旧结果按最新修订核对。一个事项变化不重启、暂停或覆盖其他独立工作。

## 等待与恢复
| 等什么 | 使用什么 |
|---|---|
| 子 Agent | 真实执行 ID 与完成/失败事件，不忙轮询，不重复派工 |
| 用户决定 | 已送达的具体问题与建议，等答复；不周期性催同一问题 |
| 外部消息 | 相关聊天/事项的真实事件，不为已有消息链另建轮询 |
| 明确时间 | 当前 schedule 工具，成功回执和真实 ID |
| 获准持续关注 | 既有 Heartbeat 或 schedule，先查重复触发 |

使用 Heartbeat 前读取原 `.nanoassistant/HEARTBEAT.md` 并只增改本事项部分。未启用/离线/未建触发不能承诺自动醒来。Task 状态仍遵守现有工具契约；特别是 waiting 的真实原生安排及时间限制，不能拿普通笔记冒充。
Task 有真实原生 continuable 子执行时，用 task_graph apply 的 bind_execution 记录 child_id 与当前 request_revision。同事项更正先以原生 send_message 交回原 child，保留返回的 messageId，再绑定 correction_source_ref 与 input_receipt；已知 running 的绑定只抑制本 Task 重做，完成、失败、未知状态和待纠正会恢复协调。clear_execution 解除绑定；暂停、取消和改派后核实真实执行已停止。不要用 waiting 代替子执行绑定，也不自造 waiting 参数。定时检查只核实新变化，不把时间到视为同意。

## 完成、失败与停止
交付前按目标核验真实文件/对象/回执；子总结和“工具成功”不等于用户结果已达成。适用独立验收时沿用原流程，不要求所有小事再让用户确认。按固定所属聊天和要求使用正式发送并确认送达。
阻塞先尝试授权内修复和独立部分；把具体缺口与已完成成果送达，不让用户重新接管全流程。未知副作用先核查，不能盲目重试。
完成后更新原记录，停止专属且不再需要的触发，不影响共享安排。暂停/取消应核实真实执行与触发器状态；已发生副作用不会自动回滚；旧通知不重启已停事项。持续职责直到约定退出条件或用户取消，不因为一次检查结束就关闭。
只有新成果、重要变化、约定节点或必要决定才通知，保持日常安静与真实可查。
